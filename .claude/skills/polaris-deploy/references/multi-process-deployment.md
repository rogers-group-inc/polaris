# Multi-process deployment — systemd, per-role metrics, nginx

> **Liveness vs readiness.** `GET /health` is liveness and deliberately checks
> NOTHING — the first-run setup wizard polls it from localhost before a database
> exists, so a database check there would deadlock provisioning. `GET
> /health/ready` (added with the HA work) is readiness: 200 only when the local
> PostgreSQL is a writable primary, 503 with `in-recovery` | `db-error` |
> `timeout` otherwise, on its own one-connection pool over the DIRECT url so a
> saturated Prisma pool cannot flap a healthy site out of a load balancer. Both
> honour `HEALTH_TOKEN`, both are skipped by the HTTP metrics middleware (which
> matches the `/health` PREFIX for exactly this reason), and both are served
> only by roles with `runsHttp` — `monitor`, `discovery` and `dash` answer
> neither. Point a load balancer at `/health/ready`; see
> `high-availability.md` and `docs/HA.md`.

Verbatim from ARCHITECTURE.md → Multi-process architecture (runtime half: `polaris-monitoring-discovery/references/process-roles-runtime.md`).
**Deployment.** systemd: `polaris-migrate.service` (oneshot, sole migrator) →
`polaris-web.service` / `polaris-monitor@.service` (templated, N) /
`polaris-discovery.service`, grouped by `polaris.target` (`systemctl start
polaris.target`). Docker: one image, per-service `POLARIS_ROLE`, a one-shot
`migrate` compose service the app services gate on, plus an `nginx` service
fronting the stack. The single-process `polaris.service` unit was removed
in Phase 3 — every fresh install via `deploy/setup-*.sh` lands the split-role
+ nginx layout. The `all` role still exists in `src/utils/role.ts` so
`npm run dev` keeps working; it's a runtime mode, not a production
deployment target. See [docs/INSTALL.md](docs/INSTALL.md).

**Per-role metrics endpoint.** prom-client registries are per-process. The
web role exposes `/metrics` on its main HTTPS listener; monitor and discovery
boot a standalone HTTP listener via [src/utils/metricsServer.ts](src/utils/metricsServer.ts)
when `POLARIS_METRICS_PORT` is set. The shipped unit files pin the monitor
template to `910N` (instance N → 9101/9102/…) and discovery to `9110`, both
on `127.0.0.1`. Prometheus must scrape every role endpoint or panels that
depend on consumer-stamped metrics (`polaris_probe_*`, `polaris_monitor_work_duration_seconds`,
`polaris_sample_write_duration_seconds`, `polaris_discovery_*`,
`polaris_fmg_worker_queue_depth` / `_inflight`) silently show no data on the
Grafana dashboard. Dashboard queries already `sum()` across instances, so
panels populate as soon as the scrape job is complete. See
[docs/grafana/README.md](docs/grafana/README.md) for an example scrape job.

**nginx-front HTTPS (only mode post-Phase-4).** nginx terminates TLS for the lifetime of the install. Polaris listens HTTP-only on `127.0.0.1:${PORT:-3000}` and reads nginx's cert at `POLARIS_PROXY_CERT_PATH` to surface the fingerprint each Polaris Agent pins. `POLARIS_PUBLIC_URL` is required — [src/utils/runtimeConfig.ts](src/utils/runtimeConfig.ts) fails fast at boot if it's missing. [src/utils/proxyMode.ts](src/utils/proxyMode.ts) is the single lazy check (no module-load caching, so Vitest tests + runtime config reloads see fresh state). [src/utils/trustProxy.ts](src/utils/trustProxy.ts) resolves the Express `trust proxy` setting — operator override > default `"1"` (first-hop trust) — without mutating `process.env`. [src/services/certInfo.ts](src/services/certInfo.ts) reads the PEM from disk with a layered cache keyed on file-content hash and last-known-good fallback that survives certbot-style atomic-rename windows; public API (`getServerCertFingerprint`, `getServerCertHostnames`, `getServerCertExpiry`) is consumed by the agent-install path and `GET /server-settings/https`. [src/utils/publicUrl.ts](src/utils/publicUrl.ts) parses `POLARIS_PUBLIC_URL` to derive the public-facing port stamped into agent.conf. The nginx reference config at [deploy/nginx/polaris.conf](deploy/nginx/polaris.conf) ships HTTP/2 + HTTP/3 listeners (TCP/443 + UDP/443) on the same vhost with `Alt-Svc` advertising HTTP/3 to browsers; requires nginx ≥ 1.30 (setup scripts pull the nginx.org STABLE branch when the distro's is older; HTTP/3 needs only 1.25, so 1.30 is the supported-branch floor rather than a feature one). Fresh installs land split-role + nginx + a self-signed cert via [deploy/setup-rhel.sh](deploy/setup-rhel.sh) / [setup-ubuntu.sh](deploy/setup-ubuntu.sh); existing installs use [deploy/migrate-to-nginx.sh](deploy/migrate-to-nginx.sh).

**In-app nginx GUI (Server Settings → Certificates).** Operator-facing GUI for six nginx directives (HTTPS listen port, HTTP/3 toggle, TLS protocols, HSTS, Prometheus allow-list — plus cert rotation via the dual-pin stage→swap→retire workflow). Trust model: the polaris OS user has narrow sudo via `/etc/sudoers.d/polaris-nginx` granting only `/usr/local/sbin/polaris-nginx-apply` (shipped as [deploy/scripts/polaris-nginx-apply.sh](deploy/scripts/polaris-nginx-apply.sh)). Subcommands take NO user-supplied paths — staged files live at hardcoded `/run/polaris-nginx-stage/` locations set up by `/etc/tmpfiles.d/polaris-nginx.conf`, and the wrapper holds `flock /run/polaris-nginx-apply.lock` + `timeout 30` for every op. Setup scripts (setup-rhel.sh + setup-rhel-nodb.sh + setup-ubuntu.sh + setup-ubuntu-nodb.sh + migrate-to-nginx.sh) install the wrapper/sudoers/tmpfiles and add the polaris user to the nginx group (or Ubuntu's `www-data` group) so the existing fingerprint pane reads the `0640 root:nginx` cert file directly; existing installs pick the same helpers up through [src/services/updateService.ts](src/services/updateService.ts)'s sync block on every in-app update.

The shipped reference config at [deploy/nginx/polaris.conf](deploy/nginx/polaris.conf) is mirrored by a template at [deploy/nginx/polaris.conf.template](deploy/nginx/polaris.conf.template) that Polaris renders from an operator-settable `proxyConfig` Setting row plus env-derived server_name / upstream port. [src/services/nginxRenderer.ts](src/services/nginxRenderer.ts) substitutes the placeholder tokens and emits the rendered file + sha256 (used downstream for drift detection). [src/services/nginxConfigParser.ts](src/services/nginxConfigParser.ts) is the bootstrap-only counterpart: regex-based extraction of the same six directives out of a live `/etc/nginx/conf.d/polaris.conf` so first boot of this feature seeds the `proxyConfig` row from whatever the operator already has on disk (rather than auto-clobbering). `ProxyConfig` shape lives in [src/types/proxyConfig.ts](src/types/proxyConfig.ts). [src/services/proxyConfigService.ts](src/services/proxyConfigService.ts) is the Setting-table accessor (cached, validated; rejects HTTP/3-with-TLS-1.2-only, port out of 1..65535, etc.). [src/services/privilegedSysadmin.ts](src/services/privilegedSysadmin.ts) wraps the sudo call with output capture + timeout. [src/services/nginxApplyService.ts](src/services/nginxApplyService.ts) is the orchestrator: `applyProxyConfig` renders + stages + sudoes the wrapper + records sha256; `rotateCertAndKey` does libcrypto SPKI cert+key pair validation, atomic-renames, invalidates [src/services/certInfo.ts](src/services/certInfo.ts)'s cache via the new `invalidateCache()` export; `preflightCertRotation` returns the new cert metadata + the current canonical fingerprint (so the GUI knows which old pin to retire via the existing `/agents/cert-pins/bulk-remove` after rotation); `bootstrapProxyConfig` runs once at boot via [src/jobs/bootstrapProxyConfig.ts](src/jobs/bootstrapProxyConfig.ts) (no-op outside proxy mode or when the row already exists); `getDriftStatus` compares the live file hash to `lastAppliedHash` for the refuse-and-banner UX. Beyond the six operator-settable directives the shipped config also carries request-body limits that are NOT operator-settable: `client_max_body_size 8m` at the server level (nginx's 1m default sat below the app's own per-route ceilings and 413'd them at the edge) plus a dedicated `location` for `/api/v1/server-settings/database/restore` that lifts the limit (`0`) and sets `proxy_request_buffering off`, since a restore is a whole-database `pg_dump` streamed to disk with no `fileSize` of its own. The rendered config additionally carries the **`location = /api` docs allow block** (`{{API_DOCS_ALLOW_BLOCK}}`), which is NOT a proxyConfig directive: it renders from the separate `apiDocsConfig` Setting via [src/services/apiDocsAccessService.ts](src/services/apiDocsAccessService.ts)'s `deriveApiDocsNginxAllow`, threaded into `RenderInput.apiDocsAllow` at both render call sites (`applyProxyConfig`, and updateService's restart-time sync — which falls back to the shipped default on a read error rather than aborting). It is defense in depth only — the app-level gate in `src/app.ts` is authoritative on every install type — and the parser deliberately never seeds `apiDocsConfig` from nginx: its `allow`-line collection is scoped to the `/metrics*` location blocks (`extractLocationBlocks`) so the docs block's RFC1918 allows can't cross-contaminate `prometheusAllowIps` at bootstrap. A save of the docs scope best-effort re-applies nginx from `PUT /server-settings/api-docs` when (proxy mode ∧ wrapper installed ∧ managedMode ∧ no drift), reported in the PUT response, never failing the save. These blocks are why `nginxConfigParser` expects **9** location blocks — see polaris-deploy → cross-cutting-deployment.md for the lockstep rule.

Routes live in [src/api/routes/proxySettings.ts](src/api/routes/proxySettings.ts), mounted at `/api/v1/server-settings/proxy/*` ABOVE the blanket `serverSettingsSystem:read` gate so each route declares its own permission level (read on GET, fullwrite on PUT / `/apply` / `/adopt-managed-mode` / `/cert/preflight` / `/cert/rotate`). The cert rotation flow is orchestrated by the frontend modal in [public/js/server-settings.js](public/js/server-settings.js)'s `openRotateCertModal`: it calls `/cert/preflight` (libcrypto validate + return new metadata) → `/agents/cert-pins/bulk-add` (stage the new pin on every active agent so they accept both old + new while reconnecting) → `/cert/rotate` (sudo wrapper atomic-renames the cert files + reloads nginx) → `/agents/cert-pins/bulk-remove` (retire the old pin once uptake is verified). Adopt-managed-mode gate: `proxyConfig.managedMode` starts at `false` on every install; the GUI shows a yellow drift banner (with drift markers from the regex parser) and disables the controls until the operator clicks "Adopt managed mode." In-app updates render the template only when `managedMode=true` and refuse-to-clobber on sha256-drift.
