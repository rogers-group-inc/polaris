# Deployment & updates

Verbatim from CLAUDE.md → Deployment & Updates (the two agent cert-pinning paragraphs live in `polaris-agent/references/cert-pinning-rotation.md`).

The production instance is updated via the **in-app update mechanism** in **Server Settings → Maintenance**. When pushing changes, the user applies the update through that UI rather than manually redeploying. Keep this in mind when giving deployment advice — do not suggest `git pull` or manual restart steps unless asked.

The Application Updates card carries an **update train** selector (`update.train` Setting, default `nightly`): **nightly** tracks the update-branch tip (every commit — the historical behavior), **release** tracks only the highest published release tag (`git tag --sort=-v:refname "v[0-9]*"`, applied via detached-HEAD checkout). The release train stays dormant (reports up-to-date) until the first release is tagged. Logic lives in `checkForUpdates`/`applyUpdate` in [src/services/updateService.ts](src/services/updateService.ts); persisted + surfaced through `GET|PUT /server-settings/updates/settings`.

**A half-finished update is still an available update.** The pipeline pulls BEFORE it installs, builds and restarts, so an update that fails at Install dependencies or later leaves the checkout's HEAD ahead of the process still serving. `checkForUpdates` therefore measures against the commit the running process booted from (`utils/version.ts → getRunningCommit()`), not against HEAD — the card keeps offering Apply Update, with a note that the code is already on disk, and Apply finishes the install, build, migration and restart (the pull is a no-op). Until 2026-09-10 the check compared HEAD to the remote, so prod showed "Up to date (v0.9.2792)" beside "Current Version v0.9.2787" with no button; the only way out was `deploy/update-linux.sh --force`, which remains the fallback when the app itself cannot run the update (its `git pull` also reports "Already up to date" in this state, hence the flag).

Every production install runs the split-role systemd layout (`polaris.target` + `polaris-web` + `polaris-monitor@N` + `polaris-discovery` + `polaris-dash` + `polaris-migrate`). The legacy single-process `polaris.service` was removed in Phase 3 — fresh installs land split-role + nginx-fronted out of the box via `deploy/setup-*.sh`, and `restartService()` in [src/services/updateService.ts](src/services/updateService.ts) only handles the split-role + Windows-NSSM paths. Local dev (`npm run dev` with `POLARIS_ROLE` unset = `all`) is still the "everything in one process" runtime behavior — that lives in `src/utils/role.ts`, not in deploy artifacts.

Before kicking `polaris.target`, the transient unit `restartService()` spawns also syncs every shipped `deploy/polaris-*.service` + `polaris.target` into `/etc/systemd/system/` (cmp-only, no-op when unchanged) and runs `systemctl daemon-reload`. The same transient unit ALSO syncs `deploy/nginx/polaris.conf` into `/etc/nginx/conf.d/polaris.conf`, validates with `nginx -t`, and reloads nginx — before the polaris.target restart so any new location blocks are live by the time Polaris comes back up. So unit-file AND nginx-config changes shipped in a Polaris update take effect on the next in-app update with zero operator intervention. **The PostgreSQL dependency is itself a drop-in, and the sync migrates it.** The shipped units named `Requires=postgresql-15.service` inline until 2026-09-09; they now name no PostgreSQL unit at all, because the unit name is a host fact and these files are overwritten verbatim on every update. Before overwriting, both sync paths read the installed unit, and if it still carries an inline `Requires=postgresql*.service` they write that name into `<unit>.d/20-postgres.conf` — once, never over an existing drop-in, and never on an HA node (where `10-ha.conf` has already reset the ordering to `patroni.service`). Fresh installs get the drop-in from `deploy/dropins/20-postgres.conf.example` via the setup scripts. Without the carry-over the first update after the cutover would silently drop the ordering and let `polaris-migrate` race PostgreSQL at boot. **Operator unit customization must live in `<unit>.d/*.conf` drop-ins** — direct edits to the main unit file in `/etc/systemd/system/` (or to `/etc/nginx/conf.d/polaris.conf` itself) get clobbered by the sync (a `journalctl -t polaris-updater` line records each sync).

### Reverse-proxy (nginx) front-end

nginx terminates TLS for every install. `POLARIS_PROXY_CERT_PATH=/etc/polaris-nginx/cert.pem` + `POLARIS_PUBLIC_URL=https://polaris.example.com` are required in `/opt/polaris/.env` (boot fails fast otherwise). Polaris listens HTTP-only on `127.0.0.1:${PORT:-3000}` (web role); `TRUST_PROXY` defaults to `"1"` (first-hop trust) so `req.ip`/`req.secure` honor nginx's `X-Forwarded-*` headers, and Server Settings → Certificates renders the in-app nginx GUI (six operator-settable directives + cert rotation via the dual-pin stage→swap→retire workflow; the rendered config additionally carries the `location = /api` docs allow block, driven by the separate `apiDocsConfig` Setting rather than proxyConfig). CA records (`category="ca"`) remain operator-editable because outbound TLS to integrations (LDAP, SMTP) still uses them.

**In-app nginx GUI.** Server Settings → Certificates exposes six directives operators actually need to change day-to-day: HTTPS listen port, HTTP/3 toggle, TLS protocols, HSTS (toggle + max-age + includeSubDomains + preload), Prometheus IP allow-list, plus cert+key rotation. `server_name` is derived from `POLARIS_PUBLIC_URL` and is not user-settable. The GUI persists settings to a `proxyConfig` Setting row and applies via a narrow privileged path: `polaris` user → `sudo /usr/local/sbin/polaris-nginx-apply <subcommand>` → wrapper holds `flock /run/polaris-nginx-apply.lock`, takes the staged file from `/run/polaris-nginx-stage/`, runs `nginx -t`, atomic-renames, reloads nginx. The wrapper is the entire privileged surface — sudoers doesn't restrict args, all validation lives in the shell script ([deploy/scripts/polaris-nginx-apply.sh](deploy/scripts/polaris-nginx-apply.sh)). Setup scripts (setup-rhel/setup-ubuntu and the migrate-to-nginx path) install the wrapper + sudoers + tmpfiles entry + add the polaris user to the nginx group so the existing fingerprint pane reads the `0640 root:nginx` cert file directly. Existing installs picking this up via in-app update get the same wiring through [src/services/updateService.ts](src/services/updateService.ts)'s helper-sync block on every restart. **Adopt-managed-mode gate**: `proxyConfig.managedMode` starts at `false` on every install; the GUI shows a yellow drift banner (with up to five specific drift markers from the parser in [src/services/nginxConfigParser.ts](src/services/nginxConfigParser.ts)) and disables the controls until the operator clicks "Adopt managed mode." This prevents silent clobbering of hand-edits beyond the six controls. In-app updates render `/etc/nginx/conf.d/polaris.conf` from the [polaris.conf.template](deploy/nginx/polaris.conf.template) only when `managedMode=true`; they also check sha256 against `lastAppliedHash` and refuse-to-clobber on drift. One rendered block is NOT a proxyConfig directive: the `location = /api` allow/deny block (defense in depth for the API-docs page) renders from the `apiDocsConfig` Setting via `deriveApiDocsNginxAllow`, threaded into `RenderInput.apiDocsAllow` at both render call sites (`applyProxyConfig` + the update-time sync, which falls back to the shipped default on a read error) — the app-level gate in `src/app.ts` stays authoritative on every install type, nginx-less ones included, and a docs-scope save best-effort re-applies nginx only when managed + drift-free.

**Cert rotation via the GUI** orchestrates the existing dual-pin endpoints (see the Dual-pin paragraph below): upload cert+key → `/cert/preflight` libcrypto-validates the pair + returns metadata → `POST /agents/cert-pins/bulk-add` stages the new pin on every active agent → `POST /server-settings/proxy/cert/rotate` does the sudo file-swap + nginx reload → `POST /agents/cert-pins/bulk-remove` retires the old canonical fingerprint. The same Maintenance card workflow stays available for operators who prefer it.

For pre-nginx installs, cutover is operator-driven via `deploy/migrate-to-nginx.sh --public-url https://polaris.example.com --prometheus-ip 10.0.0.42`. The script: ensures nginx ≥ 1.30 (the current stable branch; falls back to the nginx.org stable repo — HTTP/3 itself needs only 1.25, so the floor is a support statement), extracts the active server cert+key from `Setting.certificates`, stages + validates the nginx config (with HTTP/2 + HTTP/3 listeners both on 443), writes `/etc/polaris-nginx/{cert,key}.pem` with `0640 root:nginx` + SELinux `httpd_sys_content_t`, appends env vars to `.env` (with backup), installs the polaris-web systemd drop-in, opens TCP+UDP/443 in firewalld, restarts polaris.target, smoke-tests Alt-Svc + UDP listener + bearer-gated `/metrics-monitor-1`. Idempotent; transactional (rollback at any gate). See [docs/INSTALL.md](docs/INSTALL.md) for the operator-facing walkthrough.

Fresh installs are documented in `docs/INSTALL.md` with three platform sections (RHEL/Rocky/AlmaLinux 9, Ubuntu/Debian, Windows Server). The disk-sizing table at the top of that file is the single source of truth for DB-volume / app-volume / `/var/log` minimums and recommendations — keep it in sync whenever the runtime workload (sample-table cadences, retention defaults, update-staging cost) changes meaningfully. The setup wizard's preflight check uses `RECOMMENDED_DB_FREE_GB = 50` as the threshold for the warning banner; bump that constant in `src/setup/setupRoutes.ts` if the recommended minimum changes and update the docs table to match.

### Disk-space monitoring (post-install)

Three layers catch a filling DB volume before it crashes Postgres:

1. **Boot-time diagnostic** — `runStartupDiskCheck` in `src/utils/startupDiskCheck.ts` statfs's the app/state/backups dirs plus conventional PostgreSQL data directory candidates per platform. Emits an info/warn/error log line per volume. Non-fatal — never blocks boot.
2. **Periodic capacityWatch job** — every 10 minutes, builds a capacity snapshot and calls `recordCapacityTransition` to write a `capacity.severity_changed` Event when severity flips (ok ↔ watch ↔ amber ↔ red). Events flow out through eventArchiveService → syslog/SFTP archival, so the alert reaches on-call independent of whether the UI is reachable.
3. **Maintenance tab volume bars** — Server Settings → Maintenance → Database card renders one bar per distinct filesystem (deduped by stat.dev) with severity-colored fill and the Polaris-named role(s) each volume serves. Severity tiering: **watch** at 20–30% free (Event-only), **amber** at 10–20%, **red** below 10% (drives the non-dismissible sidebar banner).

### First-run setup lock

The setup wizard is unauthenticated by design (the operator needs to reach it from a browser to provision the host). To stop a network attacker from re-running the wizard against an already-configured host whose `.env` got deleted/corrupted, finalize writes a `.setup-complete` marker at the project root. On every boot:

- `DATABASE_URL` set → app boots normally; marker is back-filled if missing (covers existing installs).
- `DATABASE_URL` missing AND no marker → wizard runs (fresh install).
- `DATABASE_URL` missing AND marker present → process logs a recovery message and exits 1; the wizard never starts.

To intentionally re-provision from scratch, an admin with shell access deletes both `.env` and `.setup-complete`.
