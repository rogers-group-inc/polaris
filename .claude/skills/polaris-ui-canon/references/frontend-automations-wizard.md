Create/edit opens the **6-step wizard** in `public/js/automations-wizard.js` (`openAutomationWizard`): 1 name/description only — plus, when CREATING, an **"Import from file…"** control (`automationManagement:fullwrite`; never offered while editing, where replacing the open automation would be a data-loss trap). Import reads the file in the BROWSER (`FileReader`, no upload route, no multer) and reopens the wizard in a new `import` mode layered onto the clone path (`importing || clone` — detached deep copy, saved as a CREATE, `visited = 6`, excluded from the draft stash), so it saves through the ordinary `POST /automations` and the server's `ruleInputSchema` + `assertActionRefs` stay the authority. **The FILE'S NAME becomes the automation's name**, and an import is **always created disabled** whatever the file says (business rule 18: two same-signature automations at the same scope rank both fire). A step-1 banner lists the file's declared **dependencies** as present / missing / can't-tell against this install and names which later steps need attention — Actions always, since an exported file carries no delivery wiring (severity + enabled removed from this step — severity now leads the trigger step, enabled is managed from the list toggle), 2 device filtering — a default-checked **"All assets" checkbox**; unchecking reveals the nested CONDITION BUILDER (root group with AND / OR / NONE / NOT-ALL combinators, rows of field+operator+value with a click-to-suggest combobox fed by `GET /automations/scope-options` + the asset-type registry + tag list, nested sub-groups ≤5 deep, **drag-and-drop** via grip handles — `PolarisConditionBuilder.wireDnD` in the shared `public/js/condition-builder.js`, dashboard tab-grip pattern — moves conditions between groups and groups into groups with a depth-cap check): stored as `scope.condition`, evaluated by the shared `evaluateScopeCondition`; unchecked+empty is a validation error (never silently all-assets); debounced matched-device preview, 3 trigger conditions — **led by severity**: a **"Use multiple severity levels" checkbox** (`#aw-multi-sev`) sits above the Alert severity control. Single mode = one **Alert severity** dropdown (`#aw-trigger-severity`, sets `rule.severity`); on select, the step heading + the conditions group border are **accent-colored to the severity** (`applySevAccent`, palette mirrors `.sev-select`). Device/Polaris-host categories use the **same AND/OR tree builder** (leaf rows = metric or device-state conditions with agg/dims — a condition row has **no window box**: the step's single **"Sustained for (minutes)"** field is the trigger's one time knob, and it means the **measurement window** for an aggregated condition (`avg` / `median` / `min` / `max` — `tgStampWindows` stamps it into every aggregated leaf's `windowSec` and zeroes `forDurationSec`, since the reading already covers the period) or the **sustain clock** for a `latest` one (`windowSec` 0, minutes → `forDurationSec`). For a **windowed-ratio metric** (packet loss) that same field is instead relabeled **History (minutes)** — mandatory, default 15, range 5..1440 — the aggregation control is hidden, and a SEPARATE optional **Sustained for** field (`#tf-sustain-min` → `forDurationSec`, ratio-only, hidden otherwise) carries the hold on top of the window; severity tiers keep their own hold boxes like any other numeric metric (business rule 29c). It is therefore mandatory exactly when an aggregation is chosen — red asterisk + "this is the period the value is measured over" note, toggled live by `syncDurationRequirement`, and refused at save (`tgValidateLeaf`) rather than silently measured over the engine's default lookback; and/or only, ≤3 deep / ≤10 leaves; 1 leaf saves as the legacy single trigger via the client+server collapse, 2+ as a per-asset composite; event/change keep flat fields; live sentence + "Test against current data" — the sentence at the top of the step names EVERY severity the condition can raise, not just tier 0 (`triggerSentence(trigger, {severity, severityBands})` in the pure factory `window.PolarisAutomationSentences`: "…at or above 80 % — warning at this level, serious at or above 90 %, critical at or above 95 % for 5 minutes", a band printing its own sustained-for only when it overrides the base). Directly under it sits the same trigger as a **formula** (`triggerFormula(trigger, {severity, severityBands})` in the same factory → `{lines, note}`, rendered monospace in `.aw-formula`), which exists because the step's ONE "Sustained for (minutes)" field means two different things and prose reads them alike: the formula puts a MEASUREMENT window INSIDE the term (`median(Hardware sensor[class="temperature"], 15m) >= 65 °C`) and a HOLD clock OUTSIDE it (`latest(CPU usage) > 90 %  held 10m  ⇒ warning`), stacks severity bands as blank-padded lines aligned under the shared term, renders a composite one condition per line with the tree-wide hold on its own line, reads min/max over a 0/1 flag as `all(…)`/`any(…)`, and returns NO lines for event/change (they compute no value, so their English sentence is already exact). Its `note` carries the one place the wizard overstates precision: the engine fetches `max(windowSec, 15 min)` of samples and reduces every row it fetched (`SAMPLING_FLOOR_SEC`), so a window under 15 minutes is really measured over 15 — the formula prints the CONFIGURED window and says so rather than quietly substituting either number. Also a metric's **dimensionFilter inputs are pickers, not free text** — populated from `POST /automations/dimension-values` with what the draft's own devices report, as a select for the closed enum (`sensorClass`) and, for the substring-matched ones (`sensorNamePattern` — pick ONE named sensor like "CPU ON-DIE Temperature" out of a firewall's dozen, narrowed to the class already chosen — plus interfaces / mounts / health-checks / members / tunnels / hostnames), the `.aw-combo-dim` **combobox** the Devices step already uses: click opens everything the scoped devices report with per-value device counts, typing filters by substring (case-insensitively, mirroring the engine's `dimensionSubstringMatch`), ArrowUp/Down + Enter pick, and a **match cue** beside the field says whether what's typed actually selects anything — "✓ matches 2 of 14 reported hardware sensors" / "✓ exact match", or a warning that it "matches none … would never fire", because the dimension is a free-text PATTERN the server can't reject, so a typo used to save cleanly and then silently never match. (A datalist was tried first and confirmed nothing — see polaris-ui-canon → "Don't use `<datalist>`".) **Filter rows** (2026-08): the "+ Condition" select also offers **Device identifier** (Hostname / IP address / MAC address / Manufacturer / Model — `deviceFilterDimensions` on `/schema`, valid on EVERY asset metric/state leaf) and **Component name** (Interface name / IPsec tunnel name / Storage mount / SD-WAN rule name — the last narrows `sdwanRuleStatus`/`sdwanSelectedMember` to the named rule via `sdwanRulePattern`) entries, rendered as "`<what>` matches `<value>`" rows with the same picker combobox. **The stored rule never carries a filter row**: `tgFilterCompile` folds each into its AND-group's condition leaves as `dimensionFilter` at save (nested groups included, deeper values win; an OR-group placement or a filter no sibling condition can take is a validation error), and `tgFilterLift` re-derives the rows on edit (a dimension uniform across a group's supporting leaves lifts to the topmost AND group; differing values stay as inline leftover inputs on the leaf — the only time those liftable dims render inline). The engine narrows the ASSET SET via `applyDeviceFilters` (`deviceFilterMatch` in notificationTypes — hostname/manufacturer/model substring; **IP is CIDR / octet-boundary-prefix / exact, never bare substring; MAC is separator-insensitive**, both mirrored client-side for the match cue), which is what lets ONE composite automation mix device-specific branches ("interface wan1 down on CORE-SW OR storage /backup full on BACKUP-01"); identifiers ride `triggerSignature`, so same-metric rules with different device filters never carve each other out, and `getMetricSeverityTiers` skips a rule whose device filter excludes the charted asset. Metric-integral dims (sensor class/name, health-check/member, probe/row, widget) stay inline on the condition row as before. Also a warning note when the selected devices report none of that dimension, i.e. the condition could never match; a stored value the devices no longer report is kept and flagged rather than silently widened to "any". A **0/1 state metric** (`schema.booleanMetrics`, today just `customStateValue`) renders differently throughout: the threshold box becomes a **select of the chosen probe's own two labels** ("Alarm" / "OK" — `tgStateFlagControl`, still carrying `.tgl-threshold` so the saved trigger stays a plain `== 1` numeric comparison and needs no engine special case), the comparator select is narrowed to is / is-not, the aggregation to `latest` / `max` / `min` worded as "current state" / "at any point in" / "throughout", the `stateProbeId` dimension is a NAME select (values are registry UUIDs — the picker's optional `label`), and changing the probe re-renders the row so the value control relabels. The sentence reads "Hardware sensor alarm is Alarm on rows matching TMP1"; severity bands and hysteresis are hidden and server-rejected, since a ladder or a dead band over two values means nothing). The BASE tier's block takes the same layout as the added ones — including its own fold chevron (`t3:base`; keyed on "base" rather than the severity, since unlike a band this block IS the automation's own severity and re-picking it must not read as a different block). Also: severity alone on the header line with the remove **×** right-aligned, and the AND/OR combinator wrapped onto the line below (`flex-basis:100%` + `order`, NOT moved out of the header — `tgCollectGroup` reads it as `:scope > div > .scg-op`, so relocating the select makes trigger collection throw, which silently breaks both Next and the tier mirroring). That × is the single condition's own remove button, proxied into the header by `syncBaseTierRemove`, which keeps exactly one on screen: the header's while the base holds one condition (the only shape multi-severity mode allows, since every tier mirrors one metric), each row's own once there are several to tell apart. **"+ Severity"** appends another accent-colored **condition-group block** (tier) below: a severity header + a locked-metric condition row (metric + aggregation **shared** with the base (the window rides the base tier's duration field) — greyed; only the **operator** + **value** are editable, `band.operator` persisted when it differs) + its own "+ Severity". Fold state lives in a module map keyed by **severity** (`t3:critical`, `t5:base`) rather than on the element, because step 5 rebuilds its sections from the draft on every toggle and step 3 re-renders when the base sampling changes — and keyed by severity rather than index so removing a tier can't slide another tier's state onto it (re-picking a severity re-keys, carrying the state with the tier). Tiers **share the base sampling** (aggregation/window/dimensionFilter) — only severity/threshold/operator/sustained-for vary, 4 reset conditions — default-checked **"Reset when the trigger is no longer true"**, whose sentence says what that MEANS rather than restating it: the trigger's own clause rendered INVERTED through the same phrase builder (`invertedLeaf` → `tgLeafPhrase`), so "CPU usage (avg over 5 minutes) is at or below 90 %", at the hysteresis clear threshold when one is set. A 0/1 metric flips the VALUE instead of the comparator ("Hardware sensor alarm is OK", not "is not Alarm" — a state to look for, not a double negative), and a composite falls back to a generic clause since a tree stops being satisfied in as many ways as it has branches. Two caveats are spelled out because they can't be read off the clause (`resetCaveat`): a **monitor-status** alert clears at the FIRST successful probe, when the status reads `recovering` — not when it is back `up`, which is the difference between "answered once" and "healthy again"; and a numeric alert with no clear threshold resets at the very value that raised it, so a reading on the line can re-alert (the dead-band control is on that same step) (= auto, with hysteresis + clear-sustain extras for single numeric triggers); unchecking reveals **Custom conditions** first, then timed / manual. Custom conditions is the same AND/OR tree builder the trigger step uses (→ reset mode `condition`, with a sustain input + a cooldown nudge) and is offered on EVERY trigger with a continuous condition, not just composites — **seeded with the trigger inverted** (`invertedTree`, De Morgan for a tree; severity bands ignored, since every tier recovers at tier 0), so unchecking the box lands on the editable spelling of what the box did rather than on "manually only". A stored condition is kept verbatim and never re-seeded; one written in the wrong kind (the trigger was switched device↔host on step 3) is dropped and re-seeded rather than left for the operator to hand-fix. Reset leaves carry no window control of their own and inherit the trigger's measurement window (`triggerWindowSec` → `tgStampWindows` in `collectStep4`) — a second minutes field beside "must stay true for" is exactly the window-vs-hold confusion business rule 29c removed, and without the inheritance an aggregated reset leaf was refused by a message naming a field that isn't on the step. A per-dimension trigger additionally gets a note saying whether a reset condition clears one alert or all of them (business rule 32). An **event/change** trigger has nothing to invert and so gets no auto checkbox and no tree; its radios are **When a matching event arrives** (→ `reset.mode="event"`, `#aw-reset-ev-action` / `#aw-reset-ev-restype`, prefilled from the catalog's `resetEventSuggestions` — `agent.disconnected` → `agent.connected` — and a NEW draft with a known counterpart lands on that mode rather than on the four-hour timer that used to be the default) then timed / manual. The **re-notify cooldown left this step in 2026-08** for the Actions step's in-app card (`#aw-cooldown-min`), where it sits with the other two properties of the alert RECORD (`requireAckNote`, `repeat`) — it governs how often a NEW alert may fire and does nothing to one already up, so on the reset step it read as part of how an alert clears (business rule 32), 5 actions — led by the mandatory **in-app card** `#aw-inapp-card` ("Create an in-app alert (always happens)"). **Escalation is PER SEVERITY, not per action** (2026-08): the base actions section hosts the rule-level `escalation` — which is exactly the chain the engine resolves for an alert sitting at the base severity — and each per-severity section hosts its band's own. It used to sit on the in-app card (not about the alert record) and on every action ROW, where "if this stays unhandled, do more" read as "if this email goes unanswered" while the one chain actually fired for the whole tier. A stored per-action chain is **hoisted and MERGED** into its severity's chain on draft load (`hoistActionEscalations`): tiers concatenate and sort by `afterMin`, so since each tier carries its own actions the deliveries and their timings are unchanged; the level's `stopOn` wins when it has one, and the action-level chains are stripped so the sweep can't fire both. Per-action `escalation` stays in the schema and `allRuleActionRefs` still walks it, so a rule this wizard hasn't re-saved keeps working. **Quiet time** (the Actions step, inside the "Repeat this notification" block — business rule 44). The days and hours are the SHARED `PolarisRecurrence` editor (`public/js/recurrence-editor.js`, the same widget the Maintenance modal uses): seven day rows, each off, all day, or carrying one or more hour ranges. `collectQuiet` in `automations-wizard.js` turns it into `draft.repeat.quiet.windows`. Five conventions it must keep. **It lives inside the repeat block**, so unticking reminders drops the quiet time with it — the control modifies the reminder clock and nothing else. **The wizard edits ONE window**, which is enough now that a day carries several ranges ("nights, and all weekend" is one weekly recurrence, not two); the SERVER still accepts the whole vocabulary, so a window only the API can express (a one-shot, a monthly freeze, active-date bounds — `quietWindowEditable`) is listed read-only under the editor, re-sent VERBATIM from its row's `_quietWindow` stash (`stashQuietWindows`), and offers removal but never editing — anything else would be a rewrite into something the rows can say. When such a window is the ONLY one the editor renders with every day off (`allOff`), because seven ticked days would add a window nobody asked for on the next save. **The zone comes from the SERVER**: `repeatMeta.quietMeta.serverClock` rides the automations schema payload rather than `/maintenance-schedules/server-time`, which is gated on `maintenanceManagement:read` — a permission an automation author needn't hold — and a browser prefilling 22:00 from its own clock is the trap `serverClockInfo` exists for. **The editor owns its own handlers** (`PolarisRecurrence.wire(host, onChange)`, delegated, so rows appearing and disappearing need nothing from the wizard) and calls back into `collectStep5` + `syncRepeatNote`. **A half-typed day contributes no window**, so `validateStep5` asks `quietEditorProblem` — which names the day, and the overlapping pair of hours, in the same words the server would; without it a ticked box with nothing behind it saves silently as "no quiet time" and the operator finds out from the reminders still arriving overnight. The live note warns about the two pairings that surprise people: `stopAfterHours` counts quiet time too, and an all-day-every-day window holds every reminder indefinitely.
