# UI canon — tables, column layout, pagination, row menus, filter boxes

Verbatim from UI-CANON.md. Each pattern: **What it is** / **Canonical implementation** (`path/file.js → symbol()`, no line numbers) / **Key conventions** / **When adding a new instance**. Read `design/POLARIS-UI-GUIDE.md` first for the portable contract these implement.

## Token/pill filter box (multi-dimension, typeahead-committed)

**What it is:** One text input that accumulates *filter pills*. The operator types a fragment, a suggestion dropdown built from the data currently on screen offers matches labelled by dimension, Enter turns the pick into a pill, and pills combine **OR within a kind, AND across kinds**. Use it when a surface has many filterable dimensions and a row of checkboxes/selects per dimension would crowd the toolbar (or can't be enumerated up front — hostnames, process names, ports). Use `TableSF`'s per-column controls instead when the filters map cleanly onto table columns.

**Canonical implementation:** the Application Map toolbar — `public/js/appmap.js` (`applyGraphFilter` / `buildFilterCatalog` / `rankSuggestions` / `renderPills` / `addPill` / `removePillAt` / `openSuggest` / `commitInput` / `wireFilterBox`), markup in `public/appmap.html`, CSS `.appmap-filter` / `-pills` / `-input` / `.appmap-suggest{.open}` / `-item{.active}` / `-kind` / `-empty` in `public/css/appmap.css`.

**Key conventions:**
- **Pill model is `{ kind, value }`** and nothing else — serializable, so the whole pill list persists in the page's `polaris-prefs-<scope>-<username>` blob for free.
- **Don't use `<datalist>`.** Most browsers won't open it on click. Reuse the `.aw-suggest` recipe from `public/js/automations-wizard.js` (`scOpenSuggest` / `scCloseSuggest`): absolutely-positioned div, `.open` class, `mousedown` + `preventDefault()` on rows so blur-close doesn't race the tap, `blur` close behind a ~150 ms `setTimeout`, ArrowUp/Down moving an `.active` class with `scrollIntoView({block:"nearest"})`, Escape closing with `stopPropagation()` so a surrounding modal doesn't also close.
- **Catalog is rebuilt from the FULL dataset on every render**, never from the filtered view — otherwise adding one pill hides the suggestions needed to add the next.
- **Rank prefix matches above interior matches** so typing `tc` offers `tcp` first rather than some host whose name merely contains "tc". Cap the list (~50).
- **Matching is substring, not equality.** Catalog-sourced values are full labels (so it behaves as equality for them) while a hand-typed fragment still works; a free-text `text` kind is the fallback when nothing matched.
- **Keep the filter predicate PURE and separate from the DOM**, exposed on a `window.Polaris<Page>` namespace, and unit-test it through a `node:vm` sandbox (`tests/unit/appmapFilter.test.ts`, same approach as `topologyColumns.test.ts`). Pill semantics are exactly the kind of logic that silently drifts.
- **Removal has three affordances**: the pill's `×`, Backspace on an empty input, and (implicitly) clearing all pills to restore the unfiltered view. Debounce only the *suggestion* filtering (~200 ms); committing a pill is a discrete action and should re-render immediately.
- Reuse `.tag-chip` / `.tag-chip-delete` for the pill visuals rather than forking chip CSS; add a dimmed `-kind` prefix span so `host:web01` and `service:web01` are distinguishable at a glance.

**When adding a new instance:** define the kind list up front (each kind needs a haystack function over your row/node shape); decide the cross-kind combinator explicitly and write it into the doc comment (AND-across/OR-within is the default operators expect from a filter bar); make sure an active filter genuinely *narrows* — a "keep these always" rule that survives an active scope means the filter appears not to work.

**Variant — token fields that are the VALUE, not a filter (To / Cc / Bcc):** the automation wizard's Notify recipients (`recipBoxHtml` / `wireRecipBoxes` / `pillsToRecipients` / `recipientsToPills` in `public/js/automations-wizard.js`, CSS `.na-recips` / `.na-recip-row` / `.na-recip-box` / `.na-recip-input` in `styles.css`). Same typeahead recipe, six differences worth copying:
- **Pills are the payload**, not a view filter, so the pill↔wire mapping is its own pure pair at module scope (`window.PolarisAutomationRecipients`) and unit-tested (`tests/unit/automationRecipientPills.test.ts`). Suggestions are TWO halves: catalogues the surface already holds (the dynamic “Asset’s …” recipients, roles, map regions) are filtered locally and painted on the first keystroke, then a SERVER endpoint (`GET /contacts/search`) is called debounced ~250 ms with a min length and its hits are APPENDED to that same list — a stale response is dropped by re-checking the input value before rendering, and the local half is what the box still offers when the fetch fails or the caller lacks the permission behind it. Copy the split: a value the page already knows should never wait on a network round trip to be suggested.
- **Anything a companion PICKER offers must also be typeable, and the fold is where that fails.** The dynamic recipients lived only behind the Address book button, so typing `asset's` matched nothing and read as “we don't have it”. The fix is two lines and both generalize: source the entries from the picker's own export (`PolarisAddressBook.dynamicEntries`) rather than re-declaring them, and compare through a normalizer (`recipNeedle`) that folds the typographic apostrophe your labels are written with onto the straight one every keyboard produces. Suggestions a field can't ACCEPT are withheld there (these are To-only, mirroring `pillAllowedInField`) — offering one into Cc would look like it worked and then send to nobody.
- **One control, a narrower vocabulary — not a second control.** The same To box serves email and Web Push; the box carries a `data-mode` and the kind gate reads it (`pillAllowedInField(kind, field, mode)`), so push simply refuses the kinds its transport cannot reach (an address, an address-book contact) instead of growing a parallel account multi-select with its own pickers, collectors and bugs. Copy that shape: when a second consumer accepts MOST of the vocabulary, narrow the list, don't fork the widget. Two obligations come with it — refuse at the box, with a toast that says why (a pill accepted and then ignored at delivery is the failure being avoided), and carry the mode into the companion picker, which shows what the narrowing means (here a “Push devices” column, since push is opt-in per BROWSER and a named user with no enrolled device receives nothing).
- **An unresolvable pill is kept, not dropped** — a `recipientUserIds` entry with no matching account renders as a dashed "(unknown user)" chip. Silently discarding it on the next save would delete a recipient nobody asked to remove.
- **DOM order IS the model** (`pillsOf(box)` walks `:scope > .tag-chip`), so there's no parallel array to keep in sync; the box is `position:relative` to anchor `.aw-suggest`, and `min-height` keeps an empty box the same height as a full one so the rows don't jitter.
- **Dragging a pill between boxes is a CROSS-CONTAINER move**, so it follows the dashboard-canvas pattern, not the reorder-list one: a custom dataTransfer MIME type (`application/x-polaris-recipient`) makes the drag identifiable during `dragover` (where `getData` is unreadable), the element rides a module-scope var, `.aw-drop-into` marks the destination, and the drop is REJECTED unless source and destination share the same wrapper — otherwise a pill could jump into an unrelated action's recipients.

## Sortable + filterable data table

**What it is:** A `<table>` with per-column sort, inline filter, and (optionally) multi-select dropdown filters. Used for the assets, subnets, blocks, reservations, integrations, events, users, MIBs, and credentials lists.

**Canonical implementation:** `TableSF` in `public/js/table-sf.js`. Used by every list page. The subnets / blocks / reservations lists are the reference for **client-side mode** (whole dataset in the browser, `sf.apply()` filters/sorts/paginates in JS). The **assets** and **events** lists run in **server-side mode** (see below) — assets moved off client-side mode because at 12k+ rows shipping the whole table was slow.

**Key conventions:**
- Mark sortable/filterable columns on `<th>` with:
  - `data-sf-key="<dotted.path>"` — supports nested keys (`block.name`, `_count.subnets`).
  - `data-sf-type="string|number|date|ip|array"` — defaults to `string`.
  - `data-sf-options="value1|value2=Label2|value3"` — when present, renders a multi-select checkbox popover instead of a free-text input.
  - `data-sf-filter="ipnet"` — an IPv4 NETWORK filter in place of the text box (the Assets IP Address column): one box per network, `+` adds a box and `×` drops one, any-of. Each box takes a partial address typed octet by octet (`10.1` = 10.1.0.0/16), a leading-dot suffix (`.50` / `.1.50` = the LAST octets; masks the low bits, `suffix: true`), a full address (exact) or a CIDR; an invalid box is outlined `--color-danger` and never sent. Stored as `{ op: "in-networks", terms: [...] }` (the ▾ menu keeps is empty / is not empty); a legacy plain-string value restores as one term. `TableSF.parseIpNetTerm` is the browser half of `utils/cidr.ts → ipv4TermToMatchPrefixes()` and `sf.apply()` honours it for client-side tables; `tests/unit/ipNetworkFilter.test.ts` runs both parsers over one term × address grid and fails when they disagree.
  - `data-sf-nosort` (bare attribute) — filterable but NOT sortable: no sort caret, and a header click does nothing. For a server-side column the API cannot order by (the Events page's Device column — its name lives on Asset and `Event.assetId` is not a foreign key).
  - `data-sf-nofilter` (bare attribute) — sortable but NOT filterable: renders the header + sort caret only, no filter control. Sorting still works (it hangs off `.sf-header`, independent of the filter block). Use for numeric columns where a filter box adds noise but sort is useful (e.g. the asset Services tab's CPU % / Memory).
- Construct once after rendering the static `<thead>`: `var sf = new TableSF("<tbody-id>", onChange);`.
- Pipe raw rows through `sf.apply(rawData)` before rendering — sort + filters are applied there.
- The `onChange` callback re-runs the row renderer; never mutate `rawData` in place.
- Multi-select filters store an **array** of values matched case-insensitively against the row value via exact equality.
- Every filter popover (`.sf-multi-popover` — multi-select, date, text-operator, and the column chooser) is closed by ONE document-wide wiring installed once per page: `TableSF._wireDocClose()`. It closes on outside click / resize / Escape, and on a scroll that moved it — the scroll listener is capture-phase because the popover is `position:fixed` and would otherwise float away from its button. Two exemptions keep it from closing when it shouldn't: anything that scrolls or is pressed **inside** a popover (the list has its own `overflow-y`, and a scrollbar drag releases outside the popover, so its click lands on a common ancestor), and — mirroring `showRowMenu`'s handler in app.js — a scroll in a container that does **not** contain the popover's button, since that leaves the popover correctly placed. That second one is load-bearing on the dashboard: the NOC auto-scroll creeps every overflowing widget body by a pixel every 80ms, which used to dismiss a filter dropdown in the asset-details slide-over the instant it opened. The button is read back via `TableSF._popoverAnchor(pop)` — stamped as `pop._sfAnchor` by `_positionPopover` and by `openChooser`, defaulting to the popover's parent element. Add new popover kinds by giving them the `.sf-multi-popover` class rather than wiring their own close handlers; if the popover is appended somewhere other than beside its button (the column chooser goes on `document.body`), stamp `_sfAnchor` too or a scroll in the button's own container won't close it.
- `number` / `date` columns sort **blanks last in both directions**: a null / empty / unparseable value resolves to `NaN`, and the comparator must never do arithmetic on it — `NaN - x` made the old comparator inconsistent, so the column came out ordered only within the runs between blank rows (the asset Services tab's CPU % / Memory, where every process without a reading is blank). Pass `null` for "no value" rather than `0`, or the row sorts as a real zero. Pinned by `tests/unit/tableSortApply.test.ts`.
- Status / type / monitored-state pills used as cells should remain plain DOM (not React/components) so `data-sf-key` reads them via the underlying value, not display HTML.

**When adding a new instance:**
- Use `TableSF` — do not hand-roll sort/filter logic per page.
- For enum-style columns (status, role, type), prefer `data-sf-options` over a free-text input — operators almost always want exact-match.
- For columns whose displayed text differs from the underlying value (badges, formatted dates), pull the raw value from the row and stash it as the display source — never let the `data-sf-key` resolution diverge from what the user sees.
- Pagination, if needed, lives **outside** `TableSF` (apply pagination after `sf.apply()`).
- Always wire `onChange` to the render function so filter/sort updates live-refresh.

**Sorting a table that re-renders itself (and nests).** The asset-details **Interfaces** table (`_buildInterfacesTableDOM` / `_wireInterfacesTable` in [public/js/assets.js](public/js/assets.js)) is the reference for a `TableSF` table whose container is rebuilt by a refresh tick AND whose default view is a parent/child tree. Pinned by [tests/unit/assetInterfacesTableDom.test.ts](tests/unit/assetInterfacesTableDom.test.ts). Seven conventions, each of which is a bug the first time it's missed:
- **Build a flat row model beside the tree.** One entry per row carrying the raw record, its tree placement, and the comparable fields `TableSF` reads (`_ifaceEntry` / `_tunnelEntry`). Build it in tree order — that order doubles as the "natural" ordering a filtered-but-unsorted view falls back to.
- **Name each model field for the column's existing `data-col-id`.** `setupColumnLayout` derives a column's persistence id from `data-sf-key` FIRST and `data-col-id` only as a fallback, so adding sort keys to a table that already has saved layouts silently orphans every stored width / hidden column / drag order unless the two match.
- **Two render modes, one tbody rewrite.** No sort and no filter → render the tree with its section headers; either one active → render flat (no section rows, no indentation, no expand toggles — a row's position no longer implies parentage, and a matching child whose parent filtered out would otherwise vanish). Rewrite ONLY the tbody so `TableSF`'s rebuilt header row and `applyTableLayout`'s widths/handles survive; `setupColumnLayout`'s `MutationObserver` re-applies the column order after each render. **The Interfaces table differs (2026-10-26):** only a FILTER goes flat; a sort alone keeps the tree and sorts within it (`sortedTree` in `_buildInterfacesTableDOM` — clusters sorted per section, children sorted per parent, `lastChild` recomputed, collapse state honoured), because a sort by name is the one operators leave on and the FortiSwitch trunk's members lost their nesting and toggle for good. And its filtered view is only HALF flat (2026-10-26, `renderFilteredBody`): no section headers, no toggles, no collapse-hiding, but a child whose parent ALSO matched nests under it with its elbow — a Status filter saved for the FortiSwitch type keeps the FortiLink trunk and its ports, and the old fully-flat view dropped every connector on that device type only. A child whose parent filtered out stays flat with its Member badge. "Filtered" there means a filter that REMOVES a row, not one that is merely set — a saved Status pick of every state (`["down","up"]`) read "All" in the header yet flattened the switch tree; and TableSF's multi-select now stores no filter at all once every option is ticked, matching its "All" label. That table also infers a parent for a dotted name (`br0.10` → `br0`, as a `vlan` row) when the device reports no `ifParent` and the base is listed, and for a FortiAP's abbreviated base (`w01.12` → `wlan01`, `br.10` → `br0`, as a `subIface` row badged Sub-interface — the suffix is not claimed as a VLAN) — a render-time copy, never written back.
- **One record, one HOME — an IPsec tunnel lives on the IPsec tab, never in the Interfaces table.** A FortiGate IPsec tunnel reaches the System tab twice: as an `ipsecTunnels` entry and as a `tunnel`-typed interface row of the same name with `ifParent` null (the CMDB back-fill on REST-polled gates, IF-MIB on SNMP ones). The table used to nest the first under its phase-1 parent and fold the second into it — except when the twin was pinned, which left a loose "Other Interfaces" row per tunnel (prod 1801F, 2026-10-09). `_renderInterfacesTable` now drops BOTH, pinned or not, and `_ipsecTabPointerHTML` says how many went to the IPsec tab with a link that clicks it. The IPsec tab (`_renderAssetIpsec`) took over everything the rows carried: the twin's address (`overlayIp`), the Poll 1m pin (checked by `monitoredIpsecTunnels` OR the twin's `monitoredInterfaces` pin; clearing removes both — `_setIpsecTunnelPin`, which re-reads the asset before the PUT because both arrays are replaced wholesale), and the `.asset-ipsec-link` → `openIpsecTunnelDetailPanel` history panel. A `tunnel` interface with no IPsec twin (GRE / VXLAN / `ssl.root`) stays in the Interfaces table. Never fix nesting with `ifParent` — the underlay is not a containment parent, and `ifParent` feeds the interface filter's `survives` pass, topology and the aggregate maps.
- **Delegate every row handler off the tbody, and mutate shared state in place.** Per-row listeners are dropped on the operator's first keystroke. Likewise, a handler that REBINDS its local copy of a pin-state Set leaves the row builder — which closes over the original — drawing stale pins on the next re-render; mutate the Set the builder holds.
- **A per-row setting is a switch button, not a checkbox** (2026-10-27). The Interfaces table's pin is one `<button class="iface-mon-toggle asset-iface-toggle" aria-pressed>` per row reading **Monitored** / **Unmonitored** (`_ifaceMonToggleHTML` / `_ifaceMonIsOn` / `_ifaceMonSet`), flipped by a delegated `click`; its header is a **Monitor all** / **Unmonitor all** button (`#iface-poll-all`, `data-next`) that offers Unmonitor once every listed row is on. A checkbox in a list table now means nothing — rows are SELECTED by clicking them (§ Row selection below), so a box would read as a selection control.
- **A header "all" control acts on the LISTED rows and leaves the rest alone.** With a filter active the operator can't see the others, so folding them into the write silently changes settings they never looked at. Compute `next = current ∪/∖ listed`, not `next = listed`.
- Persist sort/filter state anywhere the table gets rebuilt (`PolarisPrefs` under a per-user, per-device-type key), and DROP restored state that names a column this render doesn't include — a filter on an absent column matches nothing with no visible control to clear it (`applyState` already drops an unknown `sortKey`).

**Server-side mode (for high-volume tables).** When the table is too large to ship to the browser (Events at 235k–350k rows in a 7-day window, and the assets list at 12k+ rows, are the canonical cases; future telemetry/sample admin views would qualify too), keep using `TableSF` for its header UI but route every filter + sort + page operation through the API. The mode is a consumer convention — no changes to `public/js/table-sf.js` are needed. Canonical implementations: [public/js/events.js](public/js/events.js) + [public/events.html](public/events.html) (simplest), and [public/js/assets.js](public/js/assets.js) (`_buildAssetsQuery` / `fetchAssetsPage`) which adds the favorites-first + cross-page-selection wrinkles below.

- Instantiate once: `_sf = new TableSF("<tbody-id>", onChange)`. **Never call `sf.apply()`** — every row that reaches the tbody came from the server already filtered + sorted.
- The `onChange` callback reads `sf._sortKey`, `sf._sortDir`, `sf._filters` directly, resets offset to 0, and re-fetches. Translate state into API params:
  - Multi-select checkbox arrays (`sf._filters.<key> = [val1, val2]`) → CSV (`?<key>=val1,val2`); the backend treats >1 entry as Prisma `{ in: [...] }` and 1 entry as `{ equals }` so single-value back-compat is preserved.
  - Text-column raw forms (`string` → contains; `{ op: "not-contains", q }` / `{ op: "empty" }` / `{ op: "notempty" }`) → `<field>` + `<field>Op` (the backend operator set is `contains | not_contains | empty | is_not_empty`). The ipnet form `{ op: "in-networks", terms }` → `<field>=<terms CSV>` + `<field>Op=in_networks` (Assets only, `_pushAssetText`). A new raw form ALSO needs a branch in `savedFilterService.sanitizeFilterState`, or saving a preset / view tab holding it is a 400.
  - Date-range filter `{ type: "date", from, to }` → `since` / `until`.
  - Sort state → `sortBy` / `sortDir`. The route must whitelist the column set and 400 on anything outside; Prisma `orderBy` never accepts user-supplied strings unvalidated. When sort semantics differ from string alpha order (e.g. severity), keep a numeric companion column (Event has `levelRank`) and dispatch the user-facing sort key onto it server-side.
- **A column whose value is a SET of known names, filtered by picking several** (the Assets Tags column) is a pick filter: `th data-sf-filter="pick"` (+ optional `data-sf-pick-none="(No tags)"`) and the values from `sf.setColumnSuggestions` (`table-sf.js → _wirePickFilter`). The box is a button; it opens a menu — search, checkbox list, Any / All, Clear / Cancel / OK — and the ticks are a DRAFT until OK (Cancel, Escape, an outside click discard them). Stored `{ op: "pick", mode, values, none }`; the button reads All / the one value / "N selected" (`_updatePickButtonLabel`, full list in its title). A preset holding the column's older text form is kept, applied and described in quotes until the next OK. Two traps found in a real browser, neither visible to happy-dom: the menu focuses its search with `preventScroll` (a plain focus scrolled the table wrapper, and that scroll closes every popover), and it clamps itself inside the viewport (it is wider than its button, and the Tags column sits at the right edge). A page can swap the built-in menu for its own picker with `sf.setPickOpener(key, fn(current, done))` — the opener gets a COPY of the stored pick or null and calls `done(next)` (null or an empty pick clears; never called on cancel). **The Assets Tags column does exactly that** (`assets.js → openAssetTagFilterModal`): the operator asked for the edit form's grouped colour-chip picker, not a scrolling checkbox list, so it opens an `openModal` dialog built from the edit form's own parts (`_tagChipHTML` chips) over the registry read DIRECTLY from `GET /server-settings/tags/catalog` — not `_tagCache`, which drops the Arc-owned `azure:` rows the edit picker must never offer; a FILTER must, so they show under their "Azure Tags" category in their registry colours, as Server Settings → Tags draws them, and the dialog toggles chip hue from the chip's own `hue-pill` class because `_wireChipListeners` looks colours up in `_tagCache` — plus an "Other tags in use" group from `GET /assets/tags`, with discovery's `prev-entra:` / `prev-ad:` breadcrumbs left out (`TAG_FILTER_HIDDEN_PREFIXES`; kept only when a stored pick already names one), with `.tag-filter-picker` lifting `.tag-picker`'s 200px scroll cap. A NEW pick from this dialog starts on **All**, not the generic menu's Any: the operator reported a second tag widening the list as a bug ("adds the assets of each tag instead of filtering"); a stored pick keeps its own mode. Trap: `_tagChipHTML` names its boxes `f-tags-cb` and `getTagFieldValue` reads every one in the DOCUMENT, while the shared modal body lingers hidden after close — the dialog renames them `tag-filter-cb`, or a filter's ticks would ride into the next asset edit save. Its four consumers move together: `_pushAssetText` (desktop) and `pushViewText` (`mobile/assets-tab.js`, parity-tested in `mobileAssetViews.test.ts`) map it to `tagsOp=any_of|all_of`, `savedFilterService.sanitizeFilterState` accepts it, `assets-filters.js → _sflDescribeFilter` words it.
- **A free-text column with a small known value set** keeps its text filter and gains a suggestion list: `sf.setColumnSuggestions("<key>", values | loader)` (`table-sf.js → _wireTextSuggest`). Focus lists every value (a box already holding a known value lists the whole set, so it can be switched), typing narrows it, ↑/↓/Enter or a click picks — which writes the value into the box and commits it exactly as typing would, so substring matching, the ▾ modes, the `!` prefix (kept on pick) and saved presets are unchanged. A loader is called lazily on first open and again once the cache is older than `SUGGEST_STALE_MS` (15 s), so a tag added elsewhere shows without a reload; a failed load keeps the old list. Choose this over `data-sf-options` when substring search on the column must keep working or the stored filter is a string on the server; choose `data-sf-options` for exact-match enums.
- Dynamic multi-select options (operator-extensible enums like resourceType) — call `sf.setColumnOptions("<key>", values)` after each fetch. Pre-this-change checked values are preserved if they're still in the new option set.
  - When the options come from a **registry endpoint** rather than the loaded rows (the assets Type column reads `GET /asset-types` in `_loadAssetTypeOptions`), keep the built-in set in `data-sf-options` as a pre-fetch seed and `await` the registry load **before** restoring saved prefs / hash filters — `setColumnOptions` deletes any stored filter value that has no matching checkbox, so a saved preset naming a custom value is silently dropped if it lands first.
- Persist filter + sort state in the page's `polaris-prefs-<scope>-<username>` localStorage blob alongside the column layout — match the other list pages. Restore via `sf._filters = saved.filters; sf._sortKey = saved.sort.key; sf._sortDir = saved.sort.dir; sf.restoreFilterUI();` before the first fetch.
- Offset-based pagination still lives outside `TableSF` — wire prev/next/page-buttons to bump a module-scope offset and call the same fetch helper.
- Any non-tbody consumer of filter state (PDF/CSV export's "All filtered results" path) must read from `sf._filters`, not the (now-deleted) DOM filter strip. With only one page in memory, "export filtered/all" re-fetches from the server in chunks (assets.js `_fetchAssetsForExport` pages in 10k-row windows up to a ceiling); "export page" just uses the in-memory page array.
- **Favorites-first across pages** (assets.js): when the page has a favorites set (on Assets that's the active view TAB's — see the view-tabs entry below; elsewhere localStorage), send the starred ids as `?favoriteIds=` (CSV) so the server floats them to the top of the *whole* result set, not just the current page. The route resolves this with a two-bucket query — favorites (matching the active filters, sorted) occupy virtual positions `[0, favTotal)`, non-favorites follow; the requested `[offset, offset+limit)` window is split across the boundary. Skip the param (and the second query) when the set is empty.
- **Cross-page bulk selection** (assets.js): the selection `Set` of ids survives page navigation (page changes call the fetch helper directly, *not* the selection-clearing reload). Because only the current page is in memory, keep a parallel `id → {status, assetType}` metadata map (`_assetsSelectedMeta`) captured at check time so the bulk-action bar's button-visibility logic still works for selected rows the operator has paged away from.
- **A bulk verb greys out; it does not vanish** (the assets bulk bar, `_assetsUpdateBulkBar` in assets.js, is the reference). **Since 2026-10-27 the Assets bar is never shown** (`style="display:none"` in assets.html): the operator reaches its verbs by right-clicking a row (Row context menu below), and the hidden bar is kept as the menu's state carrier, the way the hidden `td.cb-col` boxes carry the selection — so every rule in this bullet still decides what the menu offers, greyed items keeping the button's `title` as their reason. The asset Alerts tab's bar went the same way on 2026-10-29 (its Acknowledge / Clear over the selection are the row menu's — `_assetAlertMenuItems` in assets.js). On a visible bar, the bar itself is always on screen — idle-styled with a "No assets selected" count — and each button `disabled`s until its own selection rule is met, carrying a `title` that says what the rule IS (Edit: "Select a single asset to edit"; Compare: "Select two or more assets to compare their telemetry"). Hiding instead makes the verb undiscoverable: an operator has to have already ticked the right NUMBER of rows to find out the feature exists, which is how Compare went unnoticed until 2026-09. **Hide only for a reason the operator cannot fix by selecting differently** — a role that doesn't hold the key (`data-manage-assets` / `data-quarantine-assets`, where a disabled button would advertise a verb no click will ever enable), or the admin-only pairwise Merge. Set the enable/disable rule in ONE place: buttons whose only rule is "something is selected" ride the shared id list, and a button with its own arithmetic (Edit at exactly one, Compare at two to ten — and above ten it greys out in dim yellow, not grey, because "deselect some" is a different fix from "select more") is taken OUT of that list rather than being disabled twice with two different answers. **The one red, still-clickable verb is Upgrade** (group firmware upgrade, rule 122; `public/js/assets-firmware-group.js → syncButton`, called from `_assetsUpdateBulkBar`): grey for an empty or non-Fortinet selection, but when the server's `/assets/firmware-groups/sources` read says the selection spans more than one controlling FortiGate it turns `btn-danger` and stays ENABLED — the operator asked for it explicitly (2026-10-16) — and a click opens an explanation (one section per FortiGate with **Keep only these**) instead of the booking. Red there means "this selection is wrong, click to see why", not "destructive"; the server read is debounced 300 ms, cached by the sorted id list, and a newer answer always wins.

**Saved filter presets (named, shareable filter+sort snapshots).** The Assets page's "Filters ▾" header menu — [public/js/assets-filters.js](public/js/assets-filters.js) backed by [src/services/savedFilterService.ts](src/services/savedFilterService.ts) + [src/api/routes/savedFilters.ts](src/api/routes/savedFilters.ts). Distinct from the per-browser `polaris-prefs-<scope>-<username>` blob above, which persists the LIVE state: a preset is *named*, server-side, and can be published to every operator.

- Save = `sf.getPrefs()` (`{ sfFilters, sortKey, sortDir }`); load = `sf.applyState(preset.state)` then the page's programmatic-refresh entry point (`assetsApplyFilterState()` in assets.js — page 1, re-fetch, persist prefs). `applyState` REPLACES wholesale where `setPrefs` merges: a preset must land on exactly what was saved, and it drops a `sortKey` whose header no longer exists (server-side tables 400 on an unknown `sortBy`).
- Presets carry the query only. Column widths / hidden columns stay per-browser in `applyTableLayout` — decide deliberately before folding another operator's screen layout into a shared preset.
- Authorization has no dedicated function key: the request's `scope` maps to the key that already gates the page (`SAVED_FILTER_SCOPES`), checked inline (`ensureRoleSnapshot` + `hasPermission`) since the key isn't known until the payload is read. Read = list + own private presets; `write` = publish public; `fullwrite` = delete someone else's.
- The stored `state` is replayed into OTHER operators' browsers, so `sanitizeFilterState` accepts only the shapes `table-sf.js` emits, bounded in width/length. Widening the table's filter vocabulary means widening that validator in the same change.
- Adding presets to another list page: one line in `SAVED_FILTER_SCOPES` + a copy of the menu module. No migration, no new function key.
- The menu's dropdown styling is the shared **`.sfl-menu`** class (rows as a flex pair so each can carry a trailing ✕, `.sfl-row` / `.sfl-load` / `.sfl-name` / `.sfl-badge` / `.sfl-owner` / `.sfl-del` / `.sfl-empty`, plus `.sfl-vis` / `.sfl-preview` in the save modal). Any second "named presets" menu wears the same class rather than a look of its own — saved filters and saved dashboards are the same list read two ways, and styling them apart is how they drift.
- Each row's trailing **★** pins that preset as the active view tab's BASE filter (below) — offered only when the page HAS a tab strip, and feature-tested per method on `window.PolarisAssetTabs` so a cached older strip module can't break the menu.

**Saved dashboards (the same pattern on a canvas instead of a table).** The Dashboard page's "Dashboards ▾" menu (beside the pencil, at the page card's top right) — [public/js/dashboard-saved.js](public/js/dashboard-saved.js) backed by [src/services/savedDashboardService.ts](src/services/savedDashboardService.ts) + [src/api/routes/savedDashboards.ts](src/api/routes/savedDashboards.ts). Read it as the reference for "publish this thing I built" beyond a list page, and for a menu that serves an AUTHENTICATED and an ANONYMOUS surface from one file.

- Same skeleton as the filters menu (fetch on every open, My/Shared sections, Public badge + publisher name on others' rows, ✕ for owner-or-`fullwrite`, a save modal with a datalist of your own names + case-insensitive overwrite confirm + a Private/Public radio whose Public half is disabled with the reason inline). Copy that skeleton; don't reinvent it.
- **The page module exposes a SEAM, the menu module knows nothing else.** `window.PolarisDashboard` (`snapshot()` / `widgetCount()` / `loadAsNewTab()` / `viewPublished()` / `clearPublished()` / `publishedId()` / `isEditing()`, plus the `polaris:dashboard-mode` event `setHeaderMode` fires on every mode change) is the whole contract, so the canvas orchestrator keeps its internals and the menu stays testable against a stub.
- **Loading someone else's artifact is a COPY where it can be edited and a LIVE VIEW where it can't.** On the signed-in page a row becomes a new TAB with fresh widget instance ids and no reference back (the view-tabs rule — editing must never rewrite a row another operator is using); on the wallboard it renders read-only so the screen follows the publisher's edits. Don't unify those two.
- **The read-only surface hides the verbs it can't perform, and its inability is structural.** While a published dashboard is on screen the wallboard's Customize / Add Widgets / Done / Create all hide, edit mode refuses to open, and BOTH save paths no-op — and the listener behind it is GET-only app-wide, so there is nothing to enforce twice. A per-browser choice like that belongs in localStorage (pinned, restored at boot before the first paint so the pinned screen doesn't flash the local one), and an unattended screen re-reads its source on a timer, re-rendering ONLY when `updatedAt` moves (a re-render tears every widget down and back up — visible on a wall).
- **Filter what the viewer can't render, on the way in.** A published blob may name a widget type this build doesn't register or this role can't read, so `dropUnknownWidgets` runs on every layout arriving from the server — the same drop-silently rule the orchestrator already applies to its own stored layout.
- **A tab also travels as a FILE** (signed-in page only — the wallboard has no tabs). "Export this tab" / "Import tab from file…" in the same menu, the format in [public/js/dashboard-portability.js](public/js/dashboard-portability.js) (`window.PolarisDashboardPortability`: `exportText` / `filenameForExport` / `parseImportFile`, pure — the menu owns the Blob download and the file picker). `{ polarisDashboard: 1, name, exportedAt, columns:[{width, widgets:[{type,height,config}]}] }` — instance ids are dropped on the way out. An import goes through the SAME `loadAsNewTab` seam a saved row does, so `dropUnknownWidgets` repairs a file exactly as it repairs a published blob; `parseImportFile` additionally refuses `__proto__`/`constructor`/`prototype` keys at any depth, caps size (256 KB, checked before reading), columns (24) and widgets (200), and COUNTS the widget types the viewer's registry lacks so the toast names them instead of a widget silently vanishing. A file whose every widget is unknown is refused rather than adding an empty tab. The menu entries render only where the module is loaded (index.html), and need no permission of their own. Tested in tests/unit/dashboardPortability.test.ts + dashboardSavedDom.test.ts.
- Unlike filters this has its own RBAC key (`savedDashboards`), because the Dashboard page has no key to inherit — it is gated per WIDGET. Keeping a private canvas is `read` (the ungated `/me/dashboard` already stores the same thing); publishing is `write`; deleting someone else's is `fullwrite`.

**Shared Discoveries (the same private/public model on something that ACTS).** The saved-Discovery list — `openList()` in [public/js/assets-discovery.js](public/js/assets-discovery.js) backed by [src/services/networkScanService.ts](src/services/networkScanService.ts). Read it as the third instance, and specifically for the two places a shareable artifact that *does something* diverges from one that is only loaded.

- **Not a `.sfl-menu` dropdown** — a Discovery is a whole configuration with a run history, so its list is a modal table (Name · Owner · Targets · Last run · Result) with the row verbs on a `showRowMenu` off the name, not a two-line preset row. The Owner column carries what `.sfl-badge` / `.sfl-owner` carry in the menus: "You" or the author's username, plus the word **Shared**. Add that column the moment a list can show you somebody else's row — without it a colleague's artifact reads as one you forgot writing, and the missing Delete on its menu has no explanation.
- **Visibility gates SEEING and USING; ownership gates EDITING.** Loading someone else's dashboard is a copy; RUNNING someone else's Discovery is the artifact itself doing work, and that is what publishing one is for — so `POST /:id/run` asks only whether the caller can see it, while PUT/DELETE are the owner's with `fullwrite` as the override. Consequences the UI has to mirror or it will offer 403s: the wizard's **Save button and visibility control are both absent** on a row you don't own (`canEditDraft`), the run step stops claiming it "saves first" and its button reads **Start scan**, and `startRun` skips the save entirely rather than PUTting a row that isn't yours.
- **Publishing rides plain `write` here**, unlike both menus above. Those mounts sit at `read` and spend `write` to mark the publish; this one already requires `write` for any change, and the roles that author Discoveries (`networkadmin` / `assetsadmin`) hold `write` and not `fullwrite` — escalating would have put sharing out of reach of everyone it is for. Check where your mount's floor already sits before copying the filters rule.
- An **absent `isOwner`** on a payload reads as YOURS in both `canEditDraft` and `listRowItems`. The server always sends it, so hiding a verb on an unrecognized payload silently removes a capability, where showing it merely surfaces the route's own refusal.

**Per-user view tabs (a strip of open views over one table).** [public/js/assets-tabs.js](public/js/assets-tabs.js) + [src/services/tableTabsService.ts](src/services/tableTabsService.ts) + [src/api/routes/tableTabs.ts](src/api/routes/tableTabs.ts), CSS `.table-tabs` / `.table-tab*`. Each tab is a name plus the same `{sfFilters, sortKey, sortDir}` state a preset holds; the whole strip persists per user at `/me/table-tabs?scope=…` (whole-blob replace, `/me/dashboard` pattern). Sits alongside presets, not instead of them: a **tab** is scratch space, a **preset** is the durable artifact — and a tab opened from a preset keeps only a reference, so editing it never writes back to something another operator may be using.

- The page module owns ONE "state changed" entry point (`assetsApplyFilterState` in assets.js: page 1 → re-fetch → persist prefs → `PolarisAssetTabs.syncFromTable()`), wired as `TableSF`'s `onChange` AND called after programmatic changes. Everything else hangs off that single seam.
- Applying a tab drives the same entry point, so the module needs an `_applying` re-entrancy guard — without it, switching tabs writes the incoming state back over the tab you just left.
- Load order + one fetch: publish the module on `window` and `await init()` from the page module's `DOMContentLoaded` BEFORE its first fetch (`init` applies the active tab's state but deliberately does NOT fetch). Tabs script tag goes before the page script.
- First visit seeds one tab from whatever the table already shows (the restored localStorage prefs) and writes nothing until the operator actually uses tabs — no server row for people who never touch the feature.
- Writes are debounced (~800ms) with a `beforeunload` flush; a failed save toasts once and keeps the strip working for the session.
- A stale `activeId` is repaired server-side, never rejected — the operator may have closed that tab in another window.
- **The COLUMN ORDER belongs to the tab; the widths and the hidden set do not.** A tab holds `columnOrder` — the `setupColumnLayout` permutation of the movable columns — because an operator arranges the columns each view is ABOUT (a firewall tab leading with the FortiGate columns, an addressing tab with the IPs); widths and hidden columns stay per-browser in the page's `polaris-prefs-*` blob, because those are a property of the screen. The seam is two calls: the strip pushes `_assetsLayout.setPrefs({ order })` — **`order` and nothing else**, or one browser's sizing would ride onto every other — whenever a tab is applied (both the deep-linked and the ordinary load path, since a `#type=` hash narrows rows and says nothing about columns), and the layout's `onChange` calls back into `PolarisAssetTabs.syncColumnsFromTable()`, which no-ops when only a width or a hide changed. Apply the columns BEFORE the page's state entry point: that entry point persists the prefs blob, so it must already see the incoming tab's order. A new tab INHERITS the live order (unlike favorites, which start empty) — a new view that scrambled the arrangement the operator just built reads as a bug — and a tab whose `columnOrder` is null predates the feature and adopts this browser's stored layout once.
- **Favorites belong to the tab.** The Assets stars live on the tab (`favoriteIds`), not in localStorage, because a favorite is part of a view and a view is server-persisted. The integration is ONE call — `registerFavoritesProvider("assets", …)` from the strip's `init` — after which the page's existing `starCellHTML` / `isFavorite` / `getFavorites` call sites resolve to the active tab and switching tabs repaints the stars via the re-fetch it already does. Copy the rest too: cap at the click (with a toast) rather than letting the server drop a tail; name the scope in the star's tooltip, since the next tab shows a different set; and treat a null list as "predates the feature, seed me once from the old per-user set" so a second browser can't re-seed a curated tab.
- **Reusing the strip's LOOK without its machinery.** A fixed set of populations over one table is the other use of `.table-tabs` — the address book's People table (`sourceTabsHtml` in `public/js/automations-address-book.js`: All / Polaris users / one per directory / Manual) renders the same classes with `role="tablist"` and `.table-tab-name`, and none of the machinery above: no server persistence, no close buttons, no per-tab filter state, because these are not the operator's own views. Do NOT reach for `assets-tabs.js` for that, and keep `.page-tabs` for navigating between whole sections (the People / Tags strip sitting above this one on the same panel).
- **Base ("default") filter — filtering inside a filter.** A tab may pin one preset as the view it RESETS to (`defaultState` snapshot + id/name labels), which is how an operator narrows within a saved filter and still has a way back. Consequences worth copying: the page-controls row's "Clear Filters" becomes **"Reset Filter"** while a base is set (label read per render from `activeDefault()`, and the strip asks for a repaint via the page's controls-render function when a base change leaves the query alone); pinning a base APPLIES it, since a click that changed nothing visible reads as a click that didn't take; unpinning leaves the view on screen alone; the snapshot is CLONED on the way in (`applyState` hands filter objects straight to the widgets, so a shared reference would let the next keystroke edit the thing you reset TO); and a preset that has gone leaves the snapshot alone rather than orphaning the tab. Markers: `.table-tab-base` (★) on the tab, `.sfl-star` / `.sfl-row-base` in the presets menu.

## Row selection (click, drag, Shift, Ctrl — no checkbox column)

**What it is:** Since 2026-10-27 list rows are selected the way a file explorer selects files, not by ticking a checkbox. Click = this row only (clicking the only selected row again clears it); Ctrl/⌘+click = toggle; Shift+click = range from the last click (the anchor stays put); click-and-drag across rows = range, with auto-scroll at the scroll box's edge (Ctrl+drag adds to what was selected); Ctrl/⌘+A = every row of the table last clicked; a mousedown OFF the table clears it.

**Canonical implementation:** the "Row selection" block in [public/js/app.js](public/js/app.js) (`_rowSelectBox` / `_rowSelectApplyRange` / `_rowSelectClickOff` and the document-level `mousedown` / `mousemove` / `mouseup` / `keydown` listeners), beside `syncSelectedRows`. Pinned by [tests/unit/rowSelectDom.test.ts](tests/unit/rowSelectDom.test.ts). It covers every tbody row that carries a `td.cb-col` checkbox — today the Assets list, the asset Alerts tab and the network IP panel — with no per-page wiring.

**Key conventions:**
- **The checkboxes stay; only the column goes.** `td.cb-col` / `th.cb-col` are `display:none` (styles.css) and `setupColumnLayout` forces a `cb-col` column hidden (`alwaysHidden`, never written to the saved prefs) so its `<col>` holds no track. The controller sets each box and dispatches a bubbling `change`, so the page's own listener (selection Set, bulk bar, `tr.selected`) runs exactly as for a click on the box. A page needs nothing new — and must keep listening for `change`, not `click`.
- **A replacing gesture announces itself.** Before a plain click, a plain drag, a non-Ctrl Shift+click or a click off the table, the tbody receives `polaris:rowselect-clear` (bubbling `CustomEvent`). A page whose selection outlives the rendered rows (the Assets list keeps picks across pages) drops the off-page ones there; the on-page ones clear through their own `change` events.
- **What does not start a selection:** a press on `a, button, input, select, textarea, label, summary, [contenteditable], [role=button], .row-menu-trigger, [data-row-menu], .fav-star, .copy-on-click, [data-no-row-select]` (`ROW_SELECT_SKIP`) — the row name still opens its menu, a link still navigates. A drag that stays inside one row is left to text selection; it becomes a row drag on reaching another row (`body.row-select-dragging` turns text selection off while it lasts).
- **What is not "off the table":** the bulk bar and pagination (`ROW_SELECT_KEEP`), anything floating over the page — a dialog, a menu, a popover, a slide-over (`ROW_SELECT_FLOATING`) — unless the table itself lives in it, and a press on a scrollbar. So the Assets list survives a confirm dialog, and the Alerts tab's picks clear on a click elsewhere in the asset panel.
- **Ctrl+A is guarded:** not while focus is in a field, and not through an open modal that does not hold the table. Its target is the table last clicked, else the ONE visible table holding a selected row (so one asset selected by a right click or carried through a re-render still answers Ctrl+A); two tables holding picks is ambiguous and does nothing.
- **The rest of the keyboard (2026-10-27)** rides the same keydown listener and target (`_rowSelectKeyTbody`, which also stands down for an open row menu or `.btn-dropdown-menu`, and for a slide-over that does not hold the table), and acts only when that table has a selected row ON SCREEN, so an arrow key on a page with nothing selected still scrolls it. **Esc** clears (with `polaris:rowselect-clear`); it runs before `wireSlideoverEscape`'s handlers and prevents the event, so in a table inside a panel the first Esc drops the picks and the next closes the panel. **↑ / ↓** replace the selection with the next row from `_rowSelCursor` (the row the keys last reached; any mouse gesture resets it), else the anchor; **Shift+↑ / ↓** apply the range anchor → cursor, as Shift+click does; both `scrollIntoView({block:"nearest"})` and stop at the page's ends. **Enter** with exactly one row selected clicks its `.row-menu-trigger` / `[data-row-menu]` — a plain click, so the `primary` verb (Open) — and does nothing when focus is on a button or link, which answers Enter itself.
- **A right click selects, file-explorer style** (`_rowSelectForMenu`, run by the row-menu `contextmenu` listener on a `tr[data-row-menu-row]`): an unselected row becomes the whole selection (with `polaris:rowselect-clear` first), a row already in the selection keeps it. A right-button press never starts or clears a selection — the `mousedown` listener takes button 0 only.
- **Not for a form's device picker.** The Path Monitor wizard's agent-host list and the custom widget's Devices… dialog keep their checkboxes: there a box is a SETTING (run here / poll here), seeded from stored state, and a replacing click would silently switch devices off.

**When adding a new instance:** render `<td class="cb-col"><input type="checkbox" …></td>` as the first cell, handle selection in a `change` listener on the tbody, call `syncSelectedRows` after a wholesale re-render, and — only if the selection spans more than the rendered rows — listen for `polaris:rowselect-clear`. Give the selection somewhere to act: the row menu over the selection — mark the `<tr data-row-menu-row>` (see Row context menu) and, when the right-clicked row is one of several selected, build the selection's verbs instead of the row's (the Assets list; the asset Alerts tab's `_assetAlertMenuItems` is the in-panel instance). No new `.bulk-bar`.

## Expand/collapse tree inside a data table

**What it is:** A `data-table` whose rows form a parent → child (→ grandchild) tree: a caret on the parent row hides and shows its descendants, and the collapsed set persists per user per asset.

**When NOT to use it:** a tree whose nodes have COMPOSITE bodies — a table, an upload control, an inline editor under one node — cannot live in a `data-table` row without a colspan cell that breaks the table's column semantics. Those use the settings **accordion** instead (`renderProfileRow` in `public/js/server-settings.js` is the canonical; `renderFwNode` in `public/js/server-settings-firmware.js` is the same mechanic nested three deep), keeping only this section's persisted collapse state and per-level indent.

**Canonical implementation:** the System tab's **interface tree** in `public/js/assets.js` (`_renderInterfacesCard` and the `iface-expand-toggle` handler) — an aggregate/trunk row with its member ports and VLANs nested under it. The Wireless tab's **radio → SSID → client tree** (`_renderWirelessTree`) is the second implementation and follows it exactly; copy from either, but do not invent a third set of mechanics.

**Key conventions:**
- The parent row carries `<button class="<scope>-expand-toggle" data-parent="<key>">` rendering `▼` when expanded and `▶` when collapsed, with a matching `title`.
- Every descendant row carries `class="<scope>-child" data-parent="<the same key>"` — **the key is the whole subtree's, not the immediate parent's**, so one toggle hides every level below it without walking the tree.
- Indent with `padding-left` on the name cell (1.4rem per level) plus the shared connector, `_treeElbow(isLast)` in `public/js/assets.js` — `├─` while more rows follow at that level, `└─` on the last. Depth is a style, never a separate column. Two glyphs, not one: the bare elbow at half opacity read as a stray character at the head of the name rather than as a line drawn INTO the row, and the tee is what identifies the last member of a group without counting. The MAC Table, ARP Table and IPsec tabs' grouped rows use the same helper, so there is ONE nesting glyph in the app.
- **A state pill in a table row is `badge badge-monitor-*`, never `status-pill`.** `.status-pill` / `.status-pill-<kind>` has NO rule in `styles.css` — it renders as bare text that wraps mid-word in a narrow column (the Interfaces table's status cell emitted it until 2026-10-09). Up/down/partial/dynamic map to `badge-monitored` / `badge-monitor-down` / `badge-monitor-warning` / `badge-monitor-passive`; an admin-shut port is `badge-monitor-passive` (deliberate, not a fault) — the IPsec tab's `_ipsecStatusPill` and the Interfaces table's `statusCell` are the references.
- **Nested rows keep their own per-row controls.** The System tab's Interfaces table renders the Poll 1m pin checkbox on the aggregate AND on each member port, and on nested VLAN sub-interfaces. Withholding the box on members ("the group answers for its children") was tried and reverted at the operator's request on 2026-10-23: a member's own counters answer questions the trunk cannot (load split, a quiet leg). If a future table really must withhold a child's control, keep it on any child that already carries the state, and title the empty cell with where the control lives.
- Collapsed state persists through `_getCollapsedIfaces(assetId, scope)` / `_setCollapsedIfaces(assetId, set, scope)`. **Pass a `scope`** for anything that is not the interface tree — the default key is the interface tree's, and a radio and a port that happen to share a name would otherwise collapse each other.
- Re-render reads the persisted set first, so an expand/collapse survives the tab's next refresh.
- **A tree that starts collapsed persists the OPENED set instead**, under its own scope: the IPsec tab's dial-up templates (since 2026-10-28, `_renderAssetIpsec`, scope `"ipsec-open"`, toggle `ipsec-expand-toggle`, children the existing `tr.ipsec-peer` rows with `data-parent`) — a hub's ADVPN template can carry hundreds of spokes. Only a template with nested peers gets a toggle, and only in the tree view; a sort or filter flattens and shows every match.
- A count shown on a parent row is **counted from the rows rendered below it**, never taken from a source's own tally: a number next to a list that disagrees with the list reads as a bug in the list. **One exception, by request (2026-10-28):** a dial-up template's "N connected" also counts the FortiClient users whose `parentTunnel` is that template — they are listed in the separate Remote access table, not under it, and a remote-access template otherwise always read 0. Both are rows Polaris renders; it is still never a device tally.
- **A filter box over a snapshot tree** (ARP Table, MAC Table, Wireless — `_loadAssetArpTable` is the reference) renders the shell (strip + box) ONCE and re-renders only the counts and the table on a debounced `input` — rebuilding the box being typed into loses the caret. The text is kept per asset in a module map (`_assetArpFilter` / `_assetMacFilter` / `_assetWirelessFilter`) so the strip's Refresh keeps it. Build the tree from EVERY row and filter the built tree (`_filterWirelessTree`), never the rows first, or placement that depends on siblings shifts; a parent that matches by its own name keeps its whole subtree, and a filter shows its matches even under a collapsed parent without writing to the persisted collapsed set.

## Table column layout (resize + hover-gear chooser + reorder)

**What it is:** Drag-to-resize column widths plus a show/hide/reorder column chooser, opened by a gear icon that floats at the top-right corner of the table's scroll wrapper and surfaces on table hover. Replaces the older "Columns ▾" toolbar button — the gear is the only canonical affordance going forward. Pairs naturally with `TableSF` (same `data-sf-key` ids double as column ids) but works standalone on any `<table>` with a `<thead>`.

**Canonical implementations:**
- `setupColumnLayout(tableEl, options)` in [public/js/table-sf.js](public/js/table-sf.js) — the underlying widget. Floats a gear at the top-right corner of the table's scroll wrapper (see the anchor bullet below). Used directly for the long-lived list-page tables (Assets, Blocks, Subnets, Events, IP panel, Users, Roles). Pass `options.onScreenshot(tableEl)` to add a per-table camera button into the same `.sf-col-gear-wrap`, to the **left** of the gear — opt-in, so tables that don't pass it get the gear alone.
- `applyTableLayout(tableEl, typeKey, options?)` in the same file — wrapper for tables that get **re-rendered on every refresh** (asset-detail System tab: Interfaces / Storage / Temperatures / LLDP / Wireless Stations; SD-WAN members/rules; Events; same shape works for any dynamic table). Persists widths + hidden columns + column order under `polaris-table-layout-<typeKey>-<username>` so column widths persist by table type and survive each rebuild (asset-detail tables suffix the asset type onto `<typeKey>` — see below — so a firewall and a switch keep independent layouts). Safe to call after every `innerHTML` replacement. Forwards `options.onScreenshot` through to `setupColumnLayout`; the asset-detail tables pass `onScreenshot: (t) => _screenshotTableEl(t, "<Label>")` (assets.js) which renders only that table — visible columns + headers, titled with the table label and the asset name, with a footer note counting any rows hidden by a collapsed parent.
- **A per-table screenshot is a DOM rasterization, and the capture target is the `<table>`.** `_screenshotTableEl` (assets.js) hands the live table element to html-to-image — the same library and the same clone → inlined computed styles → SVG `<foreignObject>` path `_runScreenshotCapture` uses for a whole tab — then composes it under the title strip at `pixelRatio: 2`. Three things that decision carries, all pinned in [tests/unit/tableShotCaptureDom.test.ts](tests/unit/tableShotCaptureDom.test.ts): (1) the target is the table, **never its scroll wrapper** — a wrapper is a bounded-height scroll container, so capturing it clips every row below the fold and every column right of the horizontal scroll, while the table element is content-sized in both axes; (2) hidden columns and collapsed rows need no special handling, because `display: none` — including the `nth-child` form `rewriteHideStyle` writes into a generated stylesheet — is inlined into the clone by the capture itself; (3) the backdrop is `_shotBackdropColor`, the first ancestor that actually paints, not `--color-bg-primary`: a table declares no background of its own, so composing on the page color puts the wrong ground under the zebra striping in every theme whose cards aren't the page color. Unlike the tab capture there is **no canonical width** — `applyTableLayout` stamps per-column pixel widths under `table-layout: fixed`, so forcing the container wider would leave every column where it is and only add dead space. When the section shows an amber stale banner, its text is drawn as an amber line under the title (both this path and the text fallback) — see `_staleBannerTextFor` in [canon-charts-widgets.md](canon-charts-widgets.md).
- **The text composer is the fallback, and `data-shot-text` / `data-shot-color` exist for it alone.** `_screenshotTableElText` (assets.js) is a synthetic canvas that re-draws each visible cell's flattened text in one resolved color with auto-fit column widths; `_screenshotTableEl` reaches it when html-to-image never loaded, and from its `catch` when a rasterization fell over (a tainted canvas, a webfont fetch wedging the clone). It was the primary path until 2026-09-21, and the reason it stopped being one is that a re-draw can only carry TEXT: the SD-WAN Members Health Check Status column arrived as the words `▼ 36/37 up` where the screen shows 37 green/red segments, its status dots as bare `▲`/`▼`, and a health-check chip's colored bullet as a triangle — a table screenshot losing exactly what it was taken to show. Its two readers are top-level in assets.js (`_shotCellText` / `_shotCellColor`, unit-tested in [tests/unit/sdwanMembersShotDom.test.ts](tests/unit/sdwanMembersShotDom.test.ts)): `_shotCellText` walks the cell inserting a space at every element boundary (inline badges are spaced by CSS margin, with no whitespace text node, so `innerText` would run them together) and honors `data-shot-text="<glyph or summary>"` as a stand-in for an element that carries its meaning with no text at all (its subtree is skipped, so a 48-segment strip states `▼ 46/48 up` — or `▲ 48/48 up · warning` when an automation tier shaded some — instead of nothing); `_shotCellColor` resolves the one color to draw with — an explicit `data-shot-color` first, then the cell's OWN computed color, else the first text-bearing descendant whose color differs from the table's base (status pills, type badges, links), skipping descendants whose text is purely decorative glyphs (`▼`, `└`, `·`) since those are muted and sit first. Pass a **resolved** color, never a raw `var(--x)`: canvas `fillStyle` ignores an unparseable value and keeps painting in the PREVIOUS cell's color, so an unresolved var leaks one row's state onto the next (`_shotCellColor` rejects `var(` for that reason). Only declare `data-shot-color` when one color can speak for the whole cell — the per-health-check chips deliberately don't, since an up chip and a down chip share one cell. A new color-only cell no longer NEEDS the pair to be legible, but adding it is what keeps the fallback honest.

**Key conventions:**
- **Call `setupColumnLayout` AFTER `new TableSF` on the same table — never before.** `TableSF._setup` rewrites each `th[data-sf-key]`'s `innerHTML` to inject the sort/filter UI, which **wipes the `.sf-resize-handle` spans** `setupColumnLayout` appends. Construct in this order (the `_assetsSF` then `_assetsLayout` setup in `public/js/assets.js` is the canonical reference):
  ```js
  _sf = new TableSF("<tbody-id>", onChange);              // 1. builds header sort/filter UI
  _layout = setupColumnLayout(table, { onChange: save }); // 2. appends resize handles on top
  ```
  Symptom of getting it backwards: sort/filter work but **columns can't be resized** (handles silently gone). This has bitten more than one page.
- Mark every `<th>` with a stable `data-col-id="<name>"`. Falls back to `data-sf-key`, then `__col<index>` if neither is present — but explicit ids survive column reordering, so always set them on dynamic-rendered tables.
- Mark "anchor" columns (the ones a sensible table must always show — usually the leftmost identity column plus any actions column) with `data-col-required="true"` — operators can't hide a required column via the chooser, and it also can't be **reordered**: required columns hold their authored index while the other columns are dragged around them, so a leading checkbox / avatar column and a trailing Actions column stay where the table's design put them.
- **Drag-to-reorder lives in the chooser, not the header.** Each chooser row carries a `.sf-col-grip` (`draggable="true"`, same idiom as the automations condition builder's `.aw-grip` and the Assets → Settings → Sources priority list's `.monset-src-row` — copy the last one for a **flat** reorderable list: grip + rank number + label/description, `dragover` picking before/after off the row's vertical midpoint, DOM order as the source of truth read back only on Save, with `_monsetRenumberSources()` re-stamping the ranks after each drop; it's ~60 lines because there's no nesting or drop-into to handle, unlike the shared condition builder's `PolarisConditionBuilder.wireDnD`; with `.sf-drop-before` / `.sf-drop-after` edge cues); dropping rewrites the order and a "Reset column order" button appears while it differs from the authored one. Reordering **physically moves** the `<th>`, its `<col>`, and every body row's cells — there is no CSS way to permute table columns — which is why:
  - Everything position-derived recomputes from **display** order, not authored order: the `nth-child` hide rules (`rewriteHideStyle`), the auto-fill column (`lastVisibleResizableIdx`), and the resize handle's right-neighbor search. Add a position-derived behaviour and it must go through `displayIds()`.
  - **Pages that rebuild their tbody need no changes.** A `MutationObserver` on the table's own `<tbody>` elements re-applies the order after each render — installed lazily, so a table left in authored order pays nothing. Rows whose cell count doesn't match the column set (colspan empty states, the interfaces table's section headers) are skipped.
  - A `WeakMap` records the order each row's cells are **currently** in, so a second drag (or a reset) reads back from where the cells actually are. Mapping an already-moved row as though it were authored-order scrambles it — that was a real bug, and `tests/unit/tableColumnOrder.test.ts` pins it.
  - The persisted `order` is a permutation of the **movable subset only**, never absolute indexes. That's what lets a saved order survive a Polaris update that adds a column: `normalizeOrder` splices the newcomer in next to its authored neighbour and drops ids that no longer exist. Its "is this a real column" lookups are `Object.create(null)`, not `{}` — a saved order is untrusted (localStorage, or the server blob behind the Assets view tabs), and on a plain object `"constructor"` reads as a known column, gets spliced in, maps to no `<th>`, and trips `placeInOrder`'s all-or-nothing guard, so the table silently stops honouring its arrangement at all.
- Mark secondary columns that should ship **off by default** with `data-col-default-hidden="true"` — they appear unchecked in the chooser until an operator enables them. `getPrefs` persists an explicit `shown` snapshot (alongside `hidden`) so an operator's "turn it on" choice survives reloads, and `setPrefs` applies `shown` (un-hide) before `hidden` (hide). This is backward-compatible: older prefs blobs lacking `shown` leave default-hidden columns hidden and still honor previously-hidden columns. Used by the Assets table's inventory columns (Asset Tag, Manufacturer, Model, OS / Firmware, MAC Address, Assigned To, Purchase Order, DNS Name).
- For list pages using `setupColumnLayout` directly: persist via the page's own `polaris-prefs-<scope>-<username>` blob (call `layout.getPrefs()` in `_save…Prefs` and `layout.setPrefs(p.layout)` in `_restore…Prefs`). `getPrefs` returns `{ widths, hidden, shown, order }` — a page already threading the blob through picks up column order for free, no page-level change. The standalone "Columns ▾" button is gone — the gear replaces it.
- **`setPrefs` MERGES, one key at a time** — `{ order }` alone rearranges the columns and leaves `widths` / `hidden` / `shown` exactly where they were (each is applied only when its key is present). That is what lets one caller own the order while another owns the sizing: the Assets view tabs store the order per tab and push it on every tab switch, while the page's own prefs blob keeps the widths and the hidden set per browser. Keep that property if you touch `setPrefs` — `tests/unit/tableColumnOrder.test.ts` pins it.
- For dynamic-rendered tables: use `applyTableLayout(table, typeKey)` instead. Persistence is by-table-type, NOT by individual asset (never key on an asset id). The asset-detail tables (Interfaces, Storage, Hardware Sensors, LLDP, Wireless Stations, SD-WAN members/rules) additionally suffix the **asset type** onto the key via `_assetTableTypeKey(base, asset)` in assets.js (e.g. `asset-interfaces-firewall` vs `asset-interfaces-switch`) — a FortiGate's interface list looks nothing like a switch's, so operators get independent widths/visibility per device class (null/empty type → `"other"`). The Events tab is the deliberate exception: its columns are type-invariant, so it stays on a single shared `asset-events` key.
- The gear (+ optional screenshot button) **floats at the top-right corner of the table's scroll wrapper**, not inside a header cell: `setupColumnLayout` inserts a zero-height `position:relative` anchor `<div class="sf-col-gear-anchor">` immediately before the wrapper (falls back to before the table when the direct parent isn't a scroll container) and absolutely positions the gear in it. Living outside the overflow container means neither horizontal scrolling nor the sticky wrapper's internal vertical scrolling ever moves it — it's always visible without scrolling right, even when the table overflows. Reveal is JS-driven (wrapper/gear `mouseenter`/`mouseleave` toggling `.sf-gear-visible`, 120ms hide delay so the pointer can cross onto the gear) since it's no longer a `thead` descendant reachable by CSS `:hover`; the right inset is recomputed on each reveal to clear the wrapper's vertical scrollbar. The anchor is stamped `data-sf-for=<tableId>` so re-setups on the same DOM reuse it (no duplicates) while a replaced table render reclaims the stale anchor.
- **Sticky headers survive.** The resize handles need a positioning context on their `<th>`, but `setupColumnLayout` only forces inline `position:relative` when the computed position is `static` — a stylesheet `position:sticky` (e.g. `.ip-table thead th` in the IP panel) is left alone, since sticky is itself a containing block for the absolute handles. Never set inline `position` on header cells from new table code; it silently kills stylesheet sticky.
- **Frozen header on a list page** (Assets / Events / IPAM Blocks + Networks, incl. the legacy blocks/subnets pages): add `.table-wrapper-sticky` to the `.table-wrapper` (turns it into the vertical scroll container + pins the `thead` ROW with `position:sticky`, z-index 10; a box-shadow on each th stands in for the bottom border, which doesn't travel with a sticky header under `border-collapse`. Since 2026-10-04 the ROW is sticky, not each cell: the header is glass (`--rail-glass-bg` tint on the cells over a `blur(28px)` on `thead::before`), and only one blur across the whole row avoids seams. A per-cell blur drew every header cell as its own rectangle. The blur is on the pseudo-element, never on the thead, or the thead becomes the containing block for the `position:fixed` filter popovers in its cells. Tables inside `.modal` / `.slideover` keep opaque grounds). The shared `sizeStickyTableWrappers()` in app.js bounds every such wrapper to the viewport (`max-height = innerHeight − document-space top − reserve for the bottom pagination row`); it's hooked into `renderPageControls` / `clearPageControls` (re-measuring after every list render, since the empty top pagination row grows when controls first render) and window resize — so for a page using `renderPageControls`, adding the class is the ONLY step. Pages with their own pagination renderer (Events) call it at the end of that renderer. Scrolling then happens *inside* the wrapper, so bulk bars + top pagination freeze in place for free. Filter popovers are `position:fixed`, so they're unaffected by the inner scroll — but see the transformed-ancestor caveat under the slide-over variant below. Not loaded on /dash (no app.js) — don't add the class to dash-rendered tables. **Slide-over variant:** inside a slide-over use `.table-wrapper-panel-sticky` instead — same sticky-thead CSS, but the wrapper is height-bounded by its OWN sizer in assets.js, and which sizer to copy depends on where the table sits in its tab. A table that IS its tab bounds to the slide-over body's visible bottom (`_sizeAssetSvcTableWrapper`, the Services tab — re-run on every tab activation + after each data load + window resize). A table that is its tab AND should stop the panel body scrolling altogether needs no sizer: the asset Events tab (since 2026-10-28) is a CSS flex column — `#asset-panel-body:has(#asset-view-tab-events.active)` turns `overflow:hidden` + `display:flex`, the content / tab panel / `.asset-events-tab` block chain is `flex:1; min-height:0`, the toolbar and pagination stay `flex:none` and `#asset-view-events-wrapper` takes the rest (styles.css, "Asset Events tab"). Scope any such body rule with `#asset-panel:not([data-view="iface"])`, or its id-specificity `display` beats the interface page's `display:none` on the body. A table that sits MID-tab with sections below it takes a fraction of the body's height instead (`_sizeAssetIfaceTableWrapper`, the System tab's Interfaces table): a distance-to-bottom measurement would yield a different bound every time the operator scrolls the panel, and a fraction of the body also works while the tab is still `display:none` — which matters when the table is built on panel open while a different tab is showing and there's no per-tab hook to re-size from. **Popovers need a containing-block correction here, and it is not optional:** `.slideover` carries a `transform` for its slide animation and `.modal` a `translateY`, and a transform establishes a containing block for `position:fixed` descendants *even at its identity value* — so a fixed popover inside either is laid out from the panel's own padding box, not the viewport, and lands offset by the panel's left edge (vertically correct in a slide-over, since its `top` is 0). `TableSF._positionPopover` handles this for every filter popover by subtracting `TableSF._fixedHost(pop)`'s rect + border; the column-chooser gear sidesteps it by appending itself to `<body>`. Anything else you position `fixed` from a `getBoundingClientRect()` inside a slide-over or modal must do one or the other. Never put `.table-wrapper-sticky` in a slide-over: `sizeStickyTableWrappers()`'s triggers (list re-renders) fire while the panel tab is `display:none`, where rects are garbage, and would stamp bogus heights. **Self-bounding variant:** `.table-wrapper-modal-sticky` (the Application Map → Discovery picker is the reference; the asset-details Alerts tab's active list is the slide-over instance) — same sticky-thead CSS, but the CALLER sets its own `max-height` (e.g. `42vh`) and there is deliberately no sizer, because a modal or panel body already scrolls and its height isn't a function of the viewport top. Despite the name it is the right choice in a slide-over too whenever a fixed bound is acceptable — it needs no per-table sizer and no tab-activation hook, which is the whole cost of the panel variant.
- Drag-to-resize is **divider-style**: a handle sits on a column's right edge and a drag only affects the **two columns it sits between** — the dragged column grows and its immediate right neighbor shrinks 1:1 (or vice versa), 5px floor on both (`MIN_COL_W` — see the sliver note below); every other column stays put. The exception is when the right neighbor IS the **rightmost visible, resizable column** (`lastVisibleResizableIdx`), which is left auto-width so it absorbs the slack and keeps the table's right edge pinned to the border — in that case the dragged column + the auto-fill column are the two that change. The auto-fill column's own handle is hidden/inert (nothing to its right). When fixed columns sum wider than the container the table overflows past `width:100%` and the wrapper's `overflow-x:auto` shows a horizontal scrollbar. `applyWidths` recomputes the auto-fill column on every resize and whenever the chooser hides/shows a column.
- **Every visible column is explicitly pinned, never `width:auto`, and the leftover is SPREAD rather than dumped:** `fitColumnsToContainer` (scheduled after every `applyWidths`, re-run by a self-disconnecting `ResizeObserver` watching the table AND its parent — the parent because a container shrink doesn't change a fully-pinned table's own size) sizes the visible columns to sum to exactly `container content width` (writes only on change, so the observer doesn't re-fire). When the base widths sum NARROWER than the container, the slack is distributed across every resizable column **in proportion to its base width**, the rightmost visible resizable column taking the rounding residual so the right edge lands on the border. It used to hand the whole remainder to that one column, which is what left a narrow table (Users, Roles, Group Mappings) with cramped columns and one enormous last column holding all the blank space. Columns pinned to a declared width — utility `cb-col`/`fav-col` and static-width `data-col-no-resize` — are the "honor the declared width" tier: they're subtracted from the budget first and never stretch, which is why an icon-sized column (the Users table's 24px online-dot) must be marked `data-col-no-resize="true"` or it grows with everything else. Arithmetic, not measure-based, for three reasons. (1) **Scroll-clamp ratchet:** transiently clearing a column's width to "measure the auto-fill result" shrinks the table for one layout pass; when the table overflows horizontally that clamps the wrapper's `scrollLeft` and yanks the view left on every drag frame. Never transiently un-size a column (`applyWidths` doesn't touch the last one at all). (2) **Colspan first `<tbody>` row** (interfaces table's section header): an auto-width column has no per-column width basis, so fixed layout strands the leftover as a trailing gap instead of growing the column. (3) **Distribution circularity:** fixed layout spreads any un-specified remainder across *every* column, so rendered widths can't be trusted as inputs — `baseWidthOf` reads the stored/declared width first and only falls back to a rect, otherwise each pass would treat the previous stretch as the new base. The **over-committed** case (base widths sum to the container or past it → no slack) keeps EVERY column at its base, the auto-fill column included: when the leftover is narrower than its saved/measured width it keeps that width and the row overflows into the wrapper's horizontal scroll. It used to take only the leftover, squeezing to the floor with the table exactly filling the wrapper — cells cut to `▲…` and, the table not overflowing, no scrollbar to reach them (SD-WAN Members' Link column, 2026-10-26). (`UNMEASURED_COL_W` = 40px is a different thing and not a floor: the width handed to a column that never measured at all, so it lands somewhere readable rather than at a sliver nobody chose.) `tests/unit/tableColumnFit.test.ts` pins the arithmetic (proportional spread, declared widths untouched, exact sum, re-fit after a hide, no shrink when over-committed, the auto-fill column keeping its saved width).
- **The floor is a 5px sliver, and the padding comes off with it.** `MIN_COL_W = 5` is the one minimum under every width `setupColumnLayout` writes — the drag clamp (both the dragged column and the neighbor it trades with), the fit pass, and `setPrefs` (so a stale or hand-edited saved width can't seed a sub-floor base for the fit pass to scale from). It's deliberately far below anything readable: the point is that a column an operator parks out of the way still *exists* and still has a grabbable handle to pull it back out, rather than reading as gone. That only renders honestly because of the companion rule — a table cell's border box can't be narrower than its own padding (`0.6rem 1rem` ≈ 33px with borders), so a column under `NARROW_COL_W` (36px) gets `padding: 1px` + `overflow: hidden` from the same generated per-table stylesheet the hidden-column rules use (`rewriteHideStyle`, keyed on DISPLAY position, rewritten only when the text actually changes because it runs on every drag frame). Without it a drag to 5px stops dead around 33px and the floor looks broken; without the `overflow: hidden` a sliver's filter control or button group paints over the neighboring column instead of being clipped by it.
- **Double-click a handle to autofit its column** (`autofitColumn` → `contentWidthOf`). The fitted width is the widest of the header's `.sf-header` (label + sort icon only — the filter input under it has an intrinsic width of its own) and every rendered body cell, plus cell padding and borders. Each cell is measured by cloning its content into an absolutely-positioned, `width:max-content` / `nowrap` `.sf-autofit-probe` appended INSIDE that cell (so descendant selectors still style it) and removed in the same task. Colspan rows are skipped; a column under `NARROW_COL_W` measures with a sibling cell's padding, since rewriteHideStyle stripped its own. It then behaves like a drag to that width: commit the stretch, trade the delta with the right neighbour — which, when asked to GIVE width, gives only down to its own content width; the rest overflows into the wrapper's horizontal scroll — and fires `onChange` so it persists. Capped at the container width. The auto-fill column's handle is hidden, so it has no autofit. Pinned in `tests/unit/tableColumnFit.test.ts` ("double-click to autofit").
- **A drag commits the stretch first, so it tracks the pointer 1:1.** `commitStretchedWidths` (called on `mousedown`, right after `ensureAllWidthsMeasured`) folds the fit pass's rendered widths back into `widths`. Without it the delta would apply to a base that sums narrower than the container, so the divider would move by `dx × scale`. A committed base sums to the container width, so a drag creates no new slack — narrowing a column widens its neighbour, never the whole table. Only *stale* (seeded / restored) narrow widths get stretched; an operator's own layout is left alone.
- **Fixed utility columns** (`cb-col` checkbox / `fav-col` favorite-star) are non-resizable (and a `cb-col` is also always hidden — § Row selection): they get no drag handle, are skipped by `lastVisibleResizableIdx` (never the auto-fill column), and are pinned to a fixed **34px** (`FIXED_COL_W`) so they never take a share of the leftover the fit pass spreads — a page opts one out with an inline `style="width:…"` on its `th`. They're also always `required` (non-hideable). **Set the width in `table-sf.js`, never in CSS**: under `table-layout: fixed` the `<col>` beats a stylesheet rule and the pin loop overwrites `widths[]` anyway, so a CSS width on `.cb-col` is inert. The **auto-fill (last resizable) column is floored** at `max(AUTOFILL_MIN_W = 36, its declared width)` — starved below its label's min-content it wraps one letter per line and stretches the whole `thead` to ~124px, so overflow goes to the wrapper's horizontal scroll instead (recoverable; a broken header is not). The floor sits under the saved-width rule above, so it only bites on a saved sliver. Give a column whose content has a known minimum (SD-WAN Members `Link` 110px, SD-WAN Rules `Status` 100px) a declared `th` width: that floor holds even when a stored width was committed while squeezed.
- **Static-width columns** (`data-col-no-resize="true"` on the `<th>`) are the tier between utility and resizable: no drag handle, skipped by `lastVisibleResizableIdx`, but they keep their own width rather than the 20px utility pin. That width comes from the **inline `style="width:…px"` on the `<th>`, which is the single source of truth** — always declare one, and never rely on a measured render: `thead th` sets `overflow-wrap: anywhere`, so a header's min-content is one character, and an over-committed table's auto-layout pass can crush a declared 120px column to ~40px. With no handle to drag, such a measurement used to lock in permanently (and persist via `getPrefs`), so `setupColumnLayout` now pins these columns from the declared width up front and `setPrefs` ignores saved widths for them exactly as it does for cb/fav. They're also the tier the fit pass leaves alone — declaring one is how a column says "this width is my max, don't spend leftover on me". To resize one, edit the inline width in the HTML. Use it for columns whose content is a fixed-size token — enum badges, MACs, timestamps (Assets Type / State / Status / Monitored Via / MAC Address; Events Timestamp / Level; IPAM CIDR / Version / Networks / Created / VLAN / Status / Reservations; Automations Severity / Enabled).
- **Cell content truncates** with an ellipsis rather than wrapping. This only renders in `table-layout:fixed`, so `setupColumnLayout` **seeds fixed layout on first visible render** (`seedFixedLayout`): it measures each visible column's natural width and locks it in (utility + static-width columns are already pinned, so the seed only fills in the resizable ones). It bails when any column measures 0 (table rendered off-screen in an inactive SPA section), leaving auto-layout intact until a later visible re-render or a `setPrefs` width restore. The truncation CSS is scoped to `table[data-sf-table-id]` and exempts `.actions` (button groups keep wrapping), the cb/fav columns, and `td.cell-wrap` — the opt-in class for long-prose cells that should word-wrap inside their column width instead of ellipsizing (the Events page Message column uses it); the `.sf-label` header text ellipsizes too. Consequence: these tables no longer reflow to fill the container on window resize the way auto-layout did.

**When adding a new instance:**
- Long-lived static table on a list page → call `setupColumnLayout(tableEl, { onChange: _saveYourPagePrefs })` once after the `<thead>` is in the DOM; thread its `getPrefs/setPrefs` into the existing per-page prefs JSON.
- Dynamic table inside a modal or panel rebuilt on every refresh → call `applyTableLayout(container.querySelector("table"), "<stable-type-key>")` immediately after the `innerHTML` assignment. Choose a global, type-level key (e.g. `"server-mibs"`) — **never the asset id or page id**. For asset-detail tables that vary by device class, build the key with `_assetTableTypeKey("asset-<thing>", asset)` (assets.js) so it carries the asset-type suffix rather than hardcoding the bare key.
- Do NOT add a standalone "Columns" button to the toolbar — the gear is the only column-chooser entry point going forward.

## Paginated list controls row

**What it is:** The standard one-row layout sitting above a list table: page
navigation **centered** across the full width, with action buttons + the
page-size ("Show N") selector **right-aligned**. There is **no separate
top-of-page "Show" filter-bar** — the selector lives in the controls row.
Since 2026-10-16 the selector has **no "Show" label on any page**: its options
read `15 / page`, `25 / page`… and it carries `aria-label="Rows per page"`
(`renderPageControls` and the static selects on Blocks, Networks, Events and an
asset's Events tab alike). "Show N" below names the control, not a label.

**Canonical implementation:** `renderPageControls(containerId, total, pageSize, currentPage, onPageChange, onSizeChange, opts)` in [public/js/app.js](public/js/app.js). It renders into `#<containerId>` and `#<containerId>-top` as a **CSS grid** `1fr auto 1fr` — empty left cell, centered pagination in the middle, and a right cell (`.pg-right`) holding `opts.actionButtons` (e.g. Clear / Refresh) followed by the page-size selector. An `actionButtons` entry may be `{ el }` — the page's OWN button (its primary + Add), moved into the row at that position on every render, so its listeners, menu and permission gating travel with the element; it moves only into a row inside a `.table-head-row` (elsewhere it stays where the page put it — the standalone blocks / subnets pages). Pages pass it as `{ el: document.getElementById("btn-add-…") }` and `.filter()` out a missing element. Used by [public/js/assets.js](public/js/assets.js), [public/js/blocks.js](public/js/blocks.js), [public/js/subnets.js](public/js/subnets.js), [public/js/automations.js](public/js/automations.js) (`renderRulesPageControls`).

**Key conventions:**
- **Pass `onSizeChange(size)`** (the 6th arg) to get the "Show N" selector — it renders into the right cell and calls back with the new size. The selector renders **only in the `-top` row** (not duplicated in the bottom pagination). Optional `opts.pageSizes` overrides `[15,25,50,100]`.
- **`opts.topNav: false`** renders the `-top` row as the right cluster only (action buttons + Show N, no page navigation, `display:flex`); the bottom row keeps the full navigation. It is implied whenever the `-top` row sits inside a `.table-head-row`. Pinned by [tests/unit/renderPageControlsTopNav.test.ts](tests/unit/renderPageControlsTopNav.test.ts).

**What it is:** the tab strip and the list controls share one row on the table's top edge. The tabs are drawn as **folder tabs**: the active tab opens into the table below it.

**Key conventions:**
- **The rule is the head row's own bottom line**, drawn as a 1px background with a gap at `--folder-gap-l/-r` under the active tab.
  - A border can't have a hole, and a translucent tab can't hide one painted over it.
  - `.folder-body` gives up its top border: transparent, fill clipped to the padding box, square top corners. A transparent `border-top` beside a radius draws half a corner arc.
  - The head row's `margin-bottom: -1px` puts the rule on that empty border row.
- **The active tab is filled with `--folder-fill`**: the header's stacked `--rail-glass-bg` density, 51% (keep it in step with the 30% token). It has no bottom border, and a `::after` neck with radial-gradient fillets curves its sides into the rule. The accent sits on its top edge.
- **Inactive tabs are shorter and dimmer and sit behind the rule.**
- **A switch animates a transform, never layout.** Every tab is laid out lifted by `--folder-r` (`margin-bottom`), and an inactive tab is pushed back onto the rule with `translateY(var(--folder-r))`.
  - If the lift were a margin, the row's height (set by its tallest tab) would dip mid-switch while one tab rose and another fell, and the table would bob.
  - The neck (`::after`, height 0 → `--folder-r + 1px`) transitions with the same duration and easing, so its bottom stays on the rule.
  - The incoming panel, or IPAM's freshly mounted table, fades in (`folder-panel-in`). `prefers-reduced-motion` drops both.
- **The tab elements must survive the switch.** A rebuilt element starts in its final state, so no transition runs. That is why the Assets strip's `render()` ([public/js/assets-tabs.js](public/js/assets-tabs.js)) updates tabs in place, keyed by tab id, rather than rewriting the list's `innerHTML`. [tests/unit/assetsTabsDom.test.ts](tests/unit/assetsTabsDom.test.ts) pins the element identity.
- **`data-head-for="<data-tab>"` on a control cluster** shows it only while that tab is active. It works by toggling `.head-off` (`!important`, since renderPageControls stamps an inline display).
- **A panel with no `.folder-body`** gets top padding via `:has()`. That padding is on the panel, not a margin on its first child: TableSF inserts a zero-height `.sf-col-gear-anchor` as the first child, and an inline-margined `<p>` would beat a stylesheet margin.
- **`syncFolderTabs` writes the vars only when they change.** The observer watches the row's own `style` attribute, so an unconditional write loops forever.

## Row context menu (per-row verbs behind the row name)

**What it is:** A list row’s actions (Open / Edit / Clone / Delete) reached by RIGHT-clicking the row’s **name** — a plain left click does the row’s primary verb (Open) — instead of a trailing Actions column of buttons. One affordance per row, no column competing with the data for width, and a verb can be added without re-cutting the table layout. The same helper backs the page-header **account menu**, which is the pattern applied off a table: one identity affordance carrying the actions that belong to it.

**Canonical implementation:** `showRowMenu(anchor, items, opts)` / `closeRowMenu()` in [public/js/app.js](public/js/app.js), styled by `.row-context-menu` + `.row-menu-trigger` in [public/css/styles.css](public/css/styles.css). Used by the account menu (`openUserMenu` in app.js — notification preference / timezone / credential rows / help / logout, trigger `.user-menu-trigger`; the theme band sits in the sidebar instead). The notification row is also the canonical **menu-opens-a-menu** case: `_openNotifPrefMenu` re-calls `showRowMenu` against the SAME anchor from inside an item's `onSelect`, which works because the helper tears the first menu down (and nulls `_rowMenuTeardown`) before running the handler — the `openThemeMenu` pattern. Use it whenever a menu row is a CHOICE rather than an action, and keep the choice in a menu rather than a dialog when picking it must retain the click's user activation (choosing Push calls `Notification.requestPermission()` synchronously in the handler; see business rule 39), the Automations list ([public/js/automations.js](public/js/automations.js) — Edit / Clone / Delete), IPAM’s Blocks + Networks lists ([public/js/blocks.js](public/js/blocks.js), [public/js/subnets.js](public/js/subnets.js) — Open / Edit / Delete), the Assets list ([public/js/assets.js](public/js/assets.js) — Open / Edit / Quarantine|Release / Delete off the hostname) and all three Users-page tables ([public/js/users.js](public/js/users.js) — Users, Roles, Group Mappings).

**Key conventions:**
- **The standard row gestures (operator decision 2026-10-29) — every table whose rows can be opened or acted on takes all four, never a subset:** left click on the row SELECTS it; left click on the name (the row's primary column) OPENS it; double click anywhere on the row OPENS it; right click anywhere on the row selects it and shows the CONTEXT MENU. All four come from `<tr data-row-menu-row>` on a row whose name cell holds the `.row-menu-trigger`. A row with no `td.cb-col` checkbox (a table with no bulk verbs) is selected through `_rowClassBox` in app.js, a stand-in box that keeps the state on `tr.selected`, so every gesture in Row selection (Ctrl / Shift / drag / arrows / Enter / Ctrl+A / click-off) works on it unchanged. Opted in: Assets, Users (users, roles, group mappings), Automations, IPAM Blocks + Networks, Path Monitor (checks + Results), saved Discoveries, and in the asset slide-over the ARP Table (`_arpRowMenuItems`: Open device primary when matched, Copy IP / MAC), IPsec Tunnels & peers (`_ipsecRowMenuItems`: a tunnel opens its panel; a peer its device, else its tunnel), Alerts (`_assetAlertMenuItems`: a grouped alert's members are primary; Acknowledge / Clear are never primary) and This Asset's Automations (Edit). A row with no verb at all stays unmarked plain text. Pinned by `tests/unit/rowSelectDom.test.ts`, `tests/unit/rowContextMenu.test.ts` (per-file marker count) and `tests/unit/assetTabRowMenus.test.ts`.
- **Left click opens, right click is the menu (2026-10-26).** Mark the row’s open verb `primary: true`: on a plain click (or Enter on the focused trigger) `showRowMenu` runs that item and draws nothing. A `contextmenu` listener in app.js — right click, the keyboard Menu key, Shift+F10 — on any `.row-menu-trigger` or `[data-row-menu]` element suppresses the browser menu and REPLAYS the click with the menu forced (`_rowMenuForced`), so each call site’s own click handler builds its items unchanged and the menu opens at the pointer (under the trigger for a keyboard-raised event, which reports 0,0). A trigger that is not a `.row-menu-trigger` (the dashboard widgets’ `<a>` / `<div>` rows, the asset Interfaces table’s `.asset-iface-link`) carries `data-row-menu` in its markup, or a right click on it falls through to the browser. A menu with NO primary item (the account menu, Export, Add Asset, a Users-page user row — nothing to open) shows on either button; Shift+right-click keeps the browser’s menu. A caller that builds its items ASYNCHRONOUSLY must read `rowMenuGesture()` synchronously inside its click handler and pass the result as `opts.menuAt`, because the forced flag lives only for the replayed click (`_openInterfaceOrNetwork` in assets.js — a plain click opens the interface with no ip-context lookup, the right click pays for it). Never put a primary on a destructive or state-changing verb: the left click runs it without a confirm surface. Pinned by [tests/unit/rowContextMenu.test.ts](tests/unit/rowContextMenu.test.ts).
- **The whole row can be the right-click target (2026-10-27, the Assets list).** A `<tr data-row-menu-row>` widens the `contextmenu` listener: a right click anywhere on the row replays the click on the row's own `.row-menu-trigger` / `[data-row-menu]`, so the menu is the one the name gives. A field (`input`, `textarea`, `select`, `[contenteditable]`) and a link that leaves the page (`a[href]` other than `#`) keep the browser's menu. In a selectable table the row is selected first (Row selection above), which is what lets the menu act on "the selection".
- **The same attribute makes a double click anywhere on the row open it (2026-10-29).** A `dblclick` listener in app.js replays a PLAIN click on the row's trigger, so the primary verb runs — or, on a row with no primary (a Users-page user), the menu shows under the name. A double click on the trigger itself is ignored (its first click already opened), as is one on a `button`, `label` (a `toggle-switch`), field or leaving link; the word selection a double click leaves is cleared. Rows opted in: the list in the standard-gestures bullet above — `tests/unit/rowContextMenu.test.ts` pins the per-file count of `<tr data-row-menu-row`, so a new list page adds itself there. Mark the `<tr>` only where the row's trigger is the row's one Open; a row with several unrelated triggers would replay the first.
- **The selection's verbs live in the row menu, not a bar (the Assets list, 2026-10-27).** The click handler reads `rowMenuGesture()`: on a right click on a row that is one of SEVERAL selected, it shows `_assetsBulkMenuItems(bar, anchor, at, false)` — every bulk verb but Edit, in three groups (verbs / Quarantine · Release · Delete / Clear selection) under a "N selected" heading; on a right click on a lone row it appends `_assetsBulkMenuItems(…, true)` to `_assetMenuItems(a, extra)` as its own group after the remote-access verbs — only the verbs that make sense for one asset and the row menu lacks (Change type / state, Monitoring, Tags, Deploy agent, Maintenance, Upgrade firmware when enabled), never Compare / Merge (need two), Edit / Quarantine / Release / Delete (the row's own copies), Clear selection, or a greyed one. A left click still runs Open. The builder READS the hidden bar (`_ASSETS_BULK_MENU` maps each button id to its menu label and group) and each item clicks its button, so the bar's gates, enable rules, titles and handlers stay the one decider; a `.btn-dropdown-wrap` (Type / State / Monitoring) becomes the menu-opens-a-menu case, re-anchored with `menuAt` at the original point. A new bulk button needs an `_ASSETS_BULK_MENU` entry or it is not offered — `tests/unit/assetRowMenu.test.ts` builds against assets.html's real bar markup.
- **No trailing "…" on a menu entry — ever (operator decision 2026-10-27).** "Edit", not "Edit…"; "Acknowledge alert", not "Acknowledge alert…" — even when the entry opens a dialog or a second menu. Every `showRowMenu` label in the app was stripped of it that day, and the wiki quotes the labels without it. A progress state ("Saving…", "Loading…") is not a menu entry and keeps its ellipsis; the time-range bars' **Custom…** button was left as it was.
- The trigger is a real `<button class="row-menu-trigger">` carrying `aria-haspopup="menu"` + `aria-expanded`, NOT an `<a href="#">` — it opens a menu rather than navigating.
- **The menu surface is frosted glass**, styled entirely by `.btn-dropdown-menu` in `styles.css` — `.row-context-menu` adds only position and z-index, so every context menu and button dropdown in the app shares one surface. It paints `--menu-glass-bg` (30% of `--color-surface` in every theme — thinner than the panels' 70%, since a menu is small and short-lived) under `--panel-glass-blur` with `--shadow-panel`, matching the modal and slide-over so a menu opened over one reads as the same material. Two knock-ons: the hover row uses `--color-hover-tint` rather than an opaque fill (a solid row inside a translucent menu reads as a bar laid on the glass), and any NEW menu surface must take the same three values rather than a fresh background — `.widget-export-menu` mixed its own `--color-bg-elevated` for one commit and that was enough to make it silently ignore a change to the shared token, so it now reads `--menu-glass-bg` like the rest. Both glass tokens are one mix for all three themes, declared on `:root` (nightfall used to run heavier and the daylight base re-declared thinner mixes, until 2026-10-06; canon-shared-kit.md).
- `items` is `[{ label, onSelect, danger?, disabled?, title?, icon?, primary? } | { separator: true } | { heading }]`; `opts` is `{ label?, align?, menuAt? }`. `icon` is SVG markup rendered before the label (developer constants only — it goes in via `innerHTML`, while the label stays `textContent`), and `align: "end"` right-aligns the menu under its anchor, which is what a trigger at the right edge of the page header wants. Build the items **per row, from that row’s own permission**: `subnets.js` calls `canEditSubnet(s)` because the ownership dimension makes Edit row-specific, while `blocks.js` can use the page-wide `canManageBlocks()` (`ipBlocks:write` — it read `canManageNetworks()`, i.e. `subnets:fullwrite`, until 2026-09-23, so the Blocks tab's Add / Edit / Delete showed to roles the `/blocks` routes 403 and hid from roles they allow).
- **The menu is `position: fixed` and mounted on `<body>`.** List tables scroll inside `.table-wrapper-sticky`, which clips an absolutely-positioned menu — the existing `.btn-dropdown-menu` pattern (absolute inside `.btn-dropdown-wrap`) is for toolbar buttons, not table rows. The cost of `fixed` is that the menu cannot track its anchor, so `showRowMenu` closes on resize and on any scroll **that moved the anchor** — the scroll handler closes only when the scrolled element `contains(anchor)` (a document-level scroll always does). A blanket close-on-any-scroll is wrong on the dashboard, where the NOC auto-scroll creeps every overflowing `.dashboard-widget-body` by a pixel every 80 ms: the page-header account menu flashed open and vanished, though its anchor never moved. (`setHeaderExport`'s menu in `widgets/index.js` solves the same problem by naming `.dashboard-widget-body` explicitly — the containment test is the general form of that exemption.) The second cost of `fixed` + body-mounted is STACKING: the menu's z-index is compared against the other body-level layers, not against the surface the row is on, so the stylesheet's `900` — right for a list page, above the sticky table header and below the modal a verb opens — put the menu BEHIND any overlay it was opened from. That is how the asset-details upstream rows shipped in 2026-09: menu underneath the slide-over that owns the row. `_rowMenuLayer(anchor)` in app.js now lifts it to one above the greatest z-index on the anchor's own ancestors (so a slide-over's `1050` yields `1051`, and the page header's `1050` stops clipping the account menu), and returns 0 below the base so a plain list-page menu keeps the stylesheet's value. It reads COMPUTED style rather than a list of known overlay classes — there are already six layers a menu can be opened from (modal 1000, slide-over 1050, above-slideover modal 1075, monitor-confirm 1100, sf-multi-popover 1200, address-book picker 1300 / its editor 1320) and a hardcoded bump would be wrong for the next one. `ROW_MENU_BASE_Z` in app.js duplicates the stylesheet's 900; keep the two in step.
- **An open menu stamps its anchor `data-rowmenu-open`, and anything that scrolls on its own initiative must hold.** The containment test above cuts both ways: a container that scrolls BY ITSELF while holding the anchor closes the menu without the operator doing anything. That is the dashboard again, from the other side — the NOC auto-scroll creeps an overflowing `.dashboard-widget-body` a pixel every 80 ms, so a row menu opened on Down Assets or Active Alerts lived one tick. Hover does not cover it: the menu is body-mounted, so moving the pointer onto the menu is a `mouseleave` from the widget. `showRowMenu` stamps the anchor for as long as the menu is open (`ROW_MENU_OPEN_ATTR` in app.js, cleared on every close path — Escape, outside click, item select, re-anchor, teardown), and `startAutoScroll` in [public/js/dashboard.js](public/js/dashboard.js) holds the widget whose body `querySelector`s one, settling ~1s after it clears so the list doesn't lurch as the menu disappears. The attribute is spelled out literally in both files — the /dash wallboard runs dashboard.js without app.js — and pinned from both ends by [tests/unit/rowContextMenu.test.ts](tests/unit/rowContextMenu.test.ts) (the stamp) and [tests/unit/dashboardAutoScroll.test.ts](tests/unit/dashboardAutoScroll.test.ts) (the hold). Any future self-scrolling or self-animating container over a row menu reads the same stamp rather than growing its own exemption. When ANY hold ends (hover or menu), the creep re-reads its position from the body's `scrollTop`, so a list the operator scrolled by hand while it held carries on from there instead of snapping back to where the creep had left it (operator request 2026-10-26; pinned in the same test file).
- **Close before running the handler.** Most verbs open a modal or slide-over, and a lingering fixed menu would float above it.
- **Outside-dismissal tests `anchor.contains(e.target)`, not `e.target === anchor`.** A trigger built out of child elements (the account badge’s avatar, name and caret) would otherwise close on the pointerdown and re-open on the click that follows, so a second click on it could never dismiss the menu. A text-only trigger behaves identically either way, which is why the identity check survived until the first composite trigger.
- **A dashboard row opens on a left click and offers its verbs on a right click.** The Down Assets widget's rows go straight to the device (**Open device**, primary); the right-click menu adds **Acknowledge alert** only when there is something to acknowledge. `PolarisWidgets.openAssetRow` in [public/js/widgets/index.js](public/js/widgets/index.js) is the one decider, and every case that withholds Acknowledge is one where the verb would be a dead end: no alert on the row, one someone already acknowledged, a role holding `alerts` below write (withholding a verb beats a menu item that 403s — the route stays the control), or a surface with no dialogs at all (the /dash wallboard loads neither app.js nor the ack modules, so it opens the device and has no right-click menu). `openAlertRow` (Active Alerts) makes **Open device** primary, a device-less grouped alert's **Show alerts in this group** primary instead, and leaves a device-less ungrouped alert with no primary so its Acknowledge / Clear menu shows on either click. Copy this shape before adding a menu to any other outage widget.
- **A body-mounted fixed menu outlives a re-rendered anchor.** `renderUserBadge` closes the menu when it drops the badge it is anchored to — scoped by comparing `_rowMenuTeardown.anchor`, so a re-render can’t shut a row menu elsewhere on the page.
- Keep the row’s open-the-panel behaviour as the **first** item, marked `primary` — it is what the left click does, and listing it first keeps the right-click menu honest about that (`openBlockFromRow` / `openSubnetFromRow` also carry the `tr.row-panel-active` highlight that the old click handler owned).
- When the operator can do nothing to a row, render the name as **plain text**, not a trigger that opens an empty menu (automations.js does this below `automationManagement:write`).
- **Build the items from the row RECORD, not from the trigger’s `data-*` attributes**, whenever which verbs exist is conditional. `users.js` extracts `_userMenuItems(u)` / `_roleMenuItems(r)` as pure builders for exactly this reason — an IdP-managed account has no password to reset, an Azure account’s 2FA belongs to the IdP, and “reset someone else’s 2FA” must not appear on your own row. Pure builders are also what makes that logic testable (`tests/unit/usersRowMenu.test.ts`).
- **Each group of verbs is gated by the key its own routes check, not by one page-level permission.** The Assets menu gates Edit/Delete on `assets:write` but Quarantine/Release on `assetsQuarantine:write`, because those are separate function keys and a role can hold either without the other — gating them together offers an operator a verb whose click can only 403, and (the direction that actually bit) hides quarantine entirely from a SOC-shaped role that may contain a device but not edit inventory. When you add a gate for a verb, check which key its ROUTES use: the asset-details Quarantine tab and the bulk-bar quarantine buttons both shipped gated on `canManageAssets()` against `assetsQuarantine`-gated routes. `canQuarantineAssets()` in app.js plus the `data-quarantine-assets` attribute applier are the correct pair; `tests/unit/assetRowMenu.test.ts` pins all four call sites statically, since they are one-line gates buried in an 18k-line render path. Push separators only immediately before a group that has items, so a divider can never render with nothing after it (`_assetMenuItems` builds this way and it is unit-tested across every permission × row-shape combination).
- **A verb that reaches the DEVICE is gated by what the device permits, not by a Polaris key.** The Assets menu's **Open HTTPS / Open SSH** (`_managementAccessMenuItems` in [public/js/assets.js](public/js/assets.js)) read `Asset.managementAccess` — the `allowaccess` list captured during FortiGate discovery — and offer only the protocols that device actually accepts; a device whose access list couldn't be read (`protocols == null`, the best-effort FortiSwitch path) gets both optimistically, since unknown is not denied. **Where no device can be asked, the ASSET TYPE answers instead, not a guess dressed as a reading**: a `server` offers Open RDP + Open SSH because nothing reads a Windows or Linux host's management surface — same gate, same "unverified" note in the options menu, and no HTTPS (a server's :443 is the application, not a management UI). They ride no permission of their own because opening a management UI is not editing inventory, and a row with no captured access list and no inferable type (every endpoint, everything from a non-Fortinet discovery) contributes nothing rather than dead verbs. Where the same verbs exist as a **split button** on a slide-over header, the row-menu copy performs the operator's stored default rather than growing a submenu — a row menu is a flat list, so the sub-choices stay on the surface that has room for them.
- **A menu is not only for a table row — any VALUE naming a thing you could act on qualifies.** The asset-details General tab's three upstream rows (Last Seen Switch / AP / Firewall) were dead text until 2026-09: an operator who wanted the switch an endpoint hangs off read the name, went back to the Assets list and found it again, and the switch's own Open HTTPS / Open SSH lived two clicks further on. They now use the same `.row-menu-trigger` + `showRowMenu` pair (`_upstreamRowHTML` / `_upstreamMenuItems` / `_upgradeUpstreamRow` in [public/js/assets.js](public/js/assets.js)), with **Open asset** first — the `Open`-comes-first rule, applied where there was no prior click to preserve — and the device's remote-access verbs after it, reused wholesale from `_managementAccessMenuItems` rather than re-derived. Three conventions carry over and one is new: build the items from the resolved RECORD (the row's own stub, not the trigger's text); render **plain text, never an empty-menu trigger**, when the name resolves to no asset (a legitimate state here — an unadopted switch, a gate another integration hasn't discovered yet); and where a value has a part you CANNOT act on, leave that part outside the trigger (the `/port15` half stays text, so the trigger's accessible name is the device). The new one: **upgrade progressively.** The value paints as plain text from the row already in hand and the trigger appears only once the async resolve returns, so a failure or a missing permission leaves the row as it always was rather than blanking it.
- **A menu whose ROWS use different keys needs a multi-key gate on the trigger too.** The single-key `data-*` attributes (`data-manage-assets`, `data-quarantine-assets`, …) each name one capability and can't express "either of two", so a button fronting two separately-gated things gets **`data-perm-any="assets:write,networkScan:read"`** — the element-level twin of the sidebar's `anyPerm`, applied by `hideAdminOnlyElements` in `app.js` alongside the others. Canonical: the Assets page's **+ Add Asset(s)** button, whose rows are an asset form (`assets`) and a network Discovery (`networkScan`). Two things to know when using it: `hideAdminOnlyElements` only ever HIDES, and it runs once off the cached role and again after the live fetch — so a control it left visible can outlive the grant, which is why the click handler must also refuse to open a menu whose builder returned nothing. And **omit a row the role can never reach rather than disabling it**: the disabled-with-a-reason rule below is for a verb that can't apply *right now*, while a missing grant is not a transient state and a permanently greyed row only advertises something the operator cannot be given.
- **A page script that gates a control with `permAtLeast()` at DOMContentLoaded is reading the CACHED user** (localStorage — empty on a first login, stale after a role edit). Never gate by early-returning before the click handler is bound: write the gate as a function, run it at load AND on the `polaris:user-loaded` event `app.js` dispatches once `fetchCurrentUser()` resolves, and re-check inside the click handler. And when you hide with the `hidden` attribute, make sure the element's class doesn't set `display` — `.btn-dropdown-wrap`, `.btn`, `.dashboard-tabs` and others all beat the UA `[hidden]` rule and each needs its own `[hidden] { display: none }`. Both halves at once were the dead **Dashboards ▾** button (`dashboard-saved.js`, 2026-10-16): hidden-but-visible and never wired, even for roles holding `savedDashboards:read`. Pinned by `tests/unit/dashboardSavedDom.test.ts`.
- **A toolbar icon button that has grown a second destination uses the same helper.** The Device Map topology modal's **Reset** (`topology-reset-layout` in [public/map.html](public/map.html), `openResetLayoutMenu` in [public/js/map.js](public/js/map.js)) used to do one thing — back to the automatic layout — and now offers *Reset to last save* or *Reset to baseline*. It stayed a `btn-icon` in the modal header and gained `aria-haspopup="menu"` + `aria-expanded="false"` (which `showRowMenu` maintains) rather than becoming a split button or a confirm dialog: the choice is between two destinations, not a confirmation, and a dialog would cost a click on the common path. A `{ heading }` row names the menu, the unavailable destination is **disabled with the reason in its title** (rather than hidden) per the rule below, and `align: "end"` keeps it under a right-edge trigger. It works over a modal because `_rowMenuLayer` reads the anchor's own stacking (overlay `1000` → menu `1001`); native fullscreen is requested on `document.documentElement`, so the body-mounted menu still renders there. Keep the plain-call fallback (`if (typeof showRowMenu !== "function")` → the default destination) when the surface may load without app.js.
- A verb that can’t apply right now stays **present but `disabled` with the reason as its `title`** rather than being dropped (the Roles table’s Delete on a built-in role, or one that still has users). Don’t also set `danger` on it — red on an inert control reads as “this will do damage” when it does nothing.
- Dropping an Actions column means updating **three** things in lockstep: the `<th>` in *every* page that mounts the table (blocks/subnets have legacy standalone pages **and** the IPAM tab page — all three share the same JS), the static placeholder `<td colspan>` in the HTML, and every `colspan` in the JS empty/error states. A stale `data-col-id` in a saved column-order pref is harmless — `normalizeOrder` in table-sf.js filters unknown ids.

**Tests:** [tests/unit/rowContextMenu.test.ts](tests/unit/rowContextMenu.test.ts) (the helper), [tests/unit/userAccountMenu.test.ts](tests/unit/userAccountMenu.test.ts) (the account menu’s item set — losing a row there removes the only way to log out from every page at once; it stubs `_notifPrefMenuItem`/`_totpMenuItem` and pins their order and the separator, and it pins that the theme row is NOT in the menu, since it lives in the sidebar, covered by [tests/unit/sidebarThemeBandDom.test.ts](tests/unit/sidebarThemeBandDom.test.ts)), [tests/unit/accountMenuTotpRow.test.ts](tests/unit/accountMenuTotpRow.test.ts) + [tests/unit/totpSelfModule.test.ts](tests/unit/totpSelfModule.test.ts) (the two-factor row’s local-accounts-only gate and state labels, and the shared modal module it opens), [tests/unit/usersRowMenu.test.ts](tests/unit/usersRowMenu.test.ts) + [tests/unit/assetRowMenu.test.ts](tests/unit/assetRowMenu.test.ts) + [tests/unit/assetUpstreamRowsDom.test.ts](tests/unit/assetUpstreamRowsDom.test.ts) (the conditional item builders — the latter pins the quarantine permission key and the never-quarantine-infrastructure rule), [tests/unit/listTableColspan.test.ts](tests/unit/listTableColspan.test.ts) (header-count ↔ placeholder colspan across every list page, plus “no Actions column” on the converted ones). ## Utilization bar (a percentage drawn as a bar, not just a number)

**What it is:** A 0–100% reading rendered as a slim filled track with the figure
beside it, so a row of volumes/subnets reads as a shape at a glance instead of a
column of numbers to compare by eye.

**Canonical implementation:** `.util-row` / `.util-bar-track` / `.util-bar-fill` in [public/css/styles.css](public/css/styles.css) — a flex row, a `flex: 1` track and a width-percentage fill with a `0.4s` width transition. Consumers: the shared top-N widget renderer (`rowHTML` in [public/js/widgets/_topnBar.js](public/js/widgets/_topnBar.js)), the subnet-utilization line in [public/js/ip-panel.js](public/js/ip-panel.js), the asset-details Storage table's Used % cell (`_storagePctCell` in [public/js/assets.js](public/js/assets.js)), and the IPAM Networks list's Utilization column (`subnetUtilCellHTML` / `subnetUtilBarColor` in [public/js/app.js](public/js/app.js), shared by [public/js/subnets.js](public/js/subnets.js) and [public/js/block-panel.js](public/js/block-panel.js); pinned by [tests/unit/subnetUtilCell.test.ts](tests/unit/subnetUtilCell.test.ts), which reads the bands out of the widget's own source so the two cannot drift).

**Key conventions:**
- **The track flexes, the label is a fixed-width right-aligned cell.** Inside a resizable table column the fill percentage is a style attribute, never a CSS rule — under `table-layout: fixed` the column width is the `<col>`'s and the bar simply takes what is left after the label. Put the cell in the **last (auto-fill) column** where you can, so the column floor keeps the track from collapsing.
- **Color thresholds must agree with whatever widget shows the same metric.** The Storage table's Used % cell copies the Highest Disk Usage bands verbatim (`#4fc3f7` base, `#ffd600` ≥ 75%, `#ff1744` ≥ 90% — [public/js/widgets/diskUsage.js](public/js/widgets/diskUsage.js)): a volume that reads amber on the dashboard and blue in the slide-over reads as a bug in one of the two. Change one, change both.
- **Round the label, keep the precision in a `title`.** A bar plus `87%` fits a narrow column where `87.4%` does not; the exact figure rides a native tooltip on the row so nothing is lost. No data is a muted em dash — never a 0%-wide bar, which is a positive claim that the volume is empty. A *real* value that rounds to zero (one address on a /24 is 0.4%) says **`<1%`** for the same reason: `0%` beside a bar reads as empty, which is the claim the em dash exists to avoid.
- **Sort on the percentage, do not filter on it.** Give the column `data-sf-nofilter`: `TableSF`'s filters are substring matches with no numeric operators, so a filter box on a percentage offers `8` matching 8, 18, 78 and 80.8. Sorting is the affordance that earns the column — one click puts the fullest rows on top. (The Networks list's Utilization column and the asset Services tab's CPU % / Memory both make this call.)
- Where the row carries an active alert, its **severity color wins over the value bands** (`PolarisWidgets.alertSeverityBarColor`) — see the widget-surface section below.

## Status cell that reports more than one fact ("VIP / Leased")

**What it is:** A Status column whose subject can be true of several things at
once, rendered as `<qualifier> / <primary state>` instead of as whichever fact a
ladder happened to test first.

**Canonical implementation:** `_ipStatusPresentation` / `_ipAllocationPresentation` in [public/js/ip-panel.js](public/js/ip-panel.js), which return `{ dotClass, label, tooltip }` for one address. The allocation half owns the dot and the standalone label; the qualifier (a FortiGate VIP, from `vipInfo`) is prefixed when present, using a SHORT spelling of the allocation so two facts fit one column. Pinned by [tests/unit/ipPanelStatusDom.test.ts](tests/unit/ipPanelStatusDom.test.ts), which slices the functions out of the browser file and asserts every combination. Business rule 77.

**Key conventions:**
- **An if/else ladder silently hides facts as a surface grows.** The IP panel's Status column was one, six rungs deep, and it was correct for years — until addresses started carrying a VIP *and* a lease, at which point it reported the lease and nothing else. Nothing threw, nothing logged, and the fact was simply absent from the page. When a second orthogonal fact appears about a row, split the ladder into a function per fact rather than adding a seventh rung.
- **Standalone labels do not change when you add composition.** Every label an operator already reads stays byte-for-byte what it was; only the composed form uses the short spelling. A rename that rides along with a feature makes the feature look like a regression.
- **The dot and the label answer different questions.** The dot is "is this row spoken for" and the qualifier claims it; the label carries the detail. The exception is any state that asks somebody to ACT — a conflict, a permanently failed push — which keeps its red dot whatever else is true.
- **Every export of the same table reads the same function.** The IP panel's PDF and CSV builders call `_ipStatusPresentation` rather than carrying their own ladders; before this they carried two, both already drifted (the CSV had no VIP branch at all, so a VIP address exported as "Active"). A record that leaves the screen is the one people treat as authoritative, so it must not be able to disagree with the table it came from.
- **Check the server DTO before assuming a rendering bug.** The panel's VIP badge and its two push-state rungs were unreachable for their whole existence because `toReservationDto` in [src/services/subnetService.ts](src/services/subnetService.ts) never shipped `vipInfo`, `pushStatus`, `pushQueuedAt`, `pushAttempts` or `pushError`. A branch that never fires looks identical to a branch that is wrong.
