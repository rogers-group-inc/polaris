# UI canon — SVG charts, dashboard widgets, polling-method subtabs

Verbatim from UI-CANON.md. Each pattern: **What it is** / **Canonical implementation** (`path/file.js → symbol()`, no line numbers) / **Key conventions** / **When adding a new instance**. Read `design/POLARIS-UI-GUIDE.md` first for the portable contract these implement.

## Time-series chart (SVG)

**What it is:** A range-selectable SVG line chart driven by an API endpoint that returns `{ since, until, samples, stats }`. Used for response time, CPU+memory, interface throughput/errors, IPsec bytes, storage usage, sensor temperatures.

**Canonical implementation:** Asset Details → System → **Response Time** graph.
- Loader: `_loadMonitorHistoryFor()` in `public/js/assets.js` — fetches history + polling-method transitions, calls renderer, schedules auto-refresh.
- Renderer: `_renderMonitorChart()` in `public/js/assets.js` — builds the SVG; uses `_chartTimeBounds()` to align to `since`/`until` so empty regions stay visible.
- Range buttons: `_chartRangeBtnsHTML()` in `public/js/assets.js` — produces the `1h / 12h / 24h / 7d / 30d / Custom` toolbar.
- Drag-select: `_stashChartGeometry(container, t0, t1, padL, innerW, viewW)` (called by every renderer after writing the SVG) + `_wireChartDragSelect(container, applySelection)` (wired ONCE per panel open, next to the range-button handlers) + `_applyCustomRangeSelection(ui, fromIso, toIso)` — click-drag on the plot area applies the selection as the chart's custom window and pre-fills the Custom From/To panel. Geometry rides the container's dataset so re-renders never re-wire.
- Persistence: `_getChartRangePref(key, fallback)` / `_setChartRangePref(key, range)` in `public/js/assets.js` — per-user `localStorage.polaris-prefs-charts-<username>` JSON map keyed by chart id (`assetMonitor`, `assetSystem`, `assetSensor`, `assetInterface`, `assetIpsec`, `assetStorage`).
- Tooltip: `_wireChartTooltip(container, formatHTML)` in `public/js/assets.js` — single shared hover handler all charts use.
- Resize: `_observeChartResize(container, rerender)` — re-renders on container resize via ResizeObserver.
- Stats line: `_renderChartStats(container, count, parts)` — single helper every chart calls; produces the canonical `<count> samples · <Label>: <value> · …` shape and writes a plaintext fallback to `container.dataset.summary` for screenshots/tooltips.
- Camera button: `_addChartScreenshotButton(container, label, axisOpts)` — per-chart clipboard PNG with a self-identifying header (title / subject / asset / stats + axis labels drawn in canvas margins). Pass `getStats: _statsSummaryFrom("<stats-el-id>")` so the capture includes the same samples/Avg/Min/Max line shown above the chart (storage's per-mount bars use `_storageStatsSummaryFor(container)` instead — no fixed id).
- Polling-method badge: `_streamSourceBadgeHTML(asset, stream)` (sync first paint) + `_updateStreamSourceBadgesFromEffective(assetId, asset, effP?)` (async overwrite from `/effective-monitor-settings`). Renders `<method> (<details>) · every <interval> · <tier>`. The optional `effP` is a caller-supplied in-flight settings promise — `openViewModal` passes its per-open memo so the panel costs one fetch instead of three; the sub-panel refreshes (interface / sensor / IPsec / SD-WAN detail) omit it deliberately so they re-read live after a settings change. Same contract on `_renderIntermittencyBar(assetId, effP?)`.
- Lookback overflow: route helper `extendSinceForLookback(since, bucketSeconds)` in `src/api/routes/assets.ts` + optional `fetchSince` parameter on every `read*History` service in `src/services/sampleHistoryService.ts` + frontend helpers `_chartClipId(prefix)` / `_chartClipDefs(id, padL, padT, innerW, innerH)` / `_chartClipAttr(id)` near the chart-prefs block in `public/js/assets.js`.

**Key conventions:**
- **Lookback overflow + clip-path.** Each history endpoint extends the data query backwards by one bucket of overflow (`fetchSince = since − 5min` on detail tier, `since − 1 bucket` on hourly/daily) via `extendSinceForLookback` in the route handler. The service uses `fetchSince` for the WHERE clause but filters stats to `timestamp >= since` so operator-visible counts and averages match the visible window. The response keeps `since` / `until` at the visible bounds. The frontend chart renderers wrap the data layer (line segments / dots / baseline failure dots / hit targets) in `<g clip-path="url(#chart-clip-…)">` whose `<rect>` matches the inner plot area exactly — `_chartClipId(prefix)` generates a unique id per chart instance, `_chartClipDefs(id, padL, padT, innerW, innerH)` emits the `<defs><clipPath>` block, `_chartClipAttr(id)` returns the matching attribute. Axis ticks / grid lines / legend / stale banner stay OUTSIDE the clipped group so they render normally. The pattern keeps the operator-visible window literal (X-axis still spans `[since, until]`) while letting the polyline enter the chart from the left edge with continuous data instead of starting partway through.
- **Failure-aware line rendering.** Failed polls plot as red dots pinned to the chart baseline (0 on the y-axis) and stay CONNECTED to their neighbors — the transition segments fade from the series color into red via per-segment `userSpaceOnUse` linearGradients, and consecutive failures draw red along the baseline. Helpers: `_failureAwareSeriesSVG(pts, seriesColor, idPrefix)` (returns `{defs, segments}` — emit `defs` inside a `<defs>` block, `segments` inside the clipped group in place of the polyline) + `_failureDotsSVG(pts)` + the shared `_CHART_FAIL_COLOR`. Response Time derives failures from the per-sample `success` flag (fully-failed rollup buckets count too); streams with NO success flag (CPU/Memory telemetry, storage, interface throughput/errors) get theirs from `_outageMarkers(outages, sampleTimesMs)` with a `data-miss="1"` hit rect whose tooltip reads "Missed poll — no data collected". Because red now means *missed poll*, no data series may use red — the interface Errors chart runs amber (in) / purple (out). **Amber does NOT carry the same prohibition**: it means "a miss that is not yet the verdict" on the response-time chart alone, which is the only chart that resolves a down threshold, so the Errors chart's amber series is safe. Do not generalize the amber to other charts — that is what would break it.
  - **A missed poll is EVIDENCE, not a shape.** The flagless streams' failures come from the response-time probe's own record, served as `outages` (`[{from, to}]`) on the telemetry / storage / interface history endpoints by [src/services/probeOutageService.ts](src/services/probeOutageService.ts). The heavy cadences don't RUN while an asset is down (`runsHeavyCadences` gates them on `up`), so a skipped poll leaves no row anywhere — but the probe keeps running in every state and writes a real `success:false` row per interval. This replaced a `_pollGapMarkers` heuristic (a hole wider than 2.5× the series' median cadence) that could not tell an outage from an unmounted disk, a metric the device never reports, or an operator widening the cadence — and painted red dives straight through maintenance windows. Evidence gets all three right for free: polling stops entirely during maintenance, so those windows contain no failed probes. **Never re-derive a missed poll from the size of a gap.**
  - **A miss the upstream EXPLAINS is grey, not red** (business rule 38). A failed probe taken while the asset was dependency-suppressed — its parent dark — is stamped `AssetMonitorSample.dependencyDown`, and `probeOutageService` labels each window with an `OutageKind` (`"outage"` | `"dependency"`). Same dive, `_CHART_DEP_COLOR` (`#9aa0a6`) instead of `_CHART_FAIL_COLOR`: nothing was measured either way, so the shape is identical; only the accusation is dropped. Deliberately NOT a band — that vocabulary is maintenance's. `_outageMarkers` therefore returns `{ t, dep }` objects rather than bare timestamps, and the three things every chart does with them are `_outagePts` / `_outageDotsSVG` / `_outageHitsSVG` — use those, don't re-inline the loop. `_failureAwareSeriesSVG` compares point COLORS, not `ok` flags, so a red run flowing into a grey one still splits and fades. Tooltip: "Dependency down — upstream device was down, not polled". The response-time chart reads its own per-sample flag (`ptIsDependency`), and on a rollup tier a bucket is grey only when EVERY failure in it qualified (`dependencyFailureCount >= failureCount`). The grey is duplicated in four places by design — `public/js/assets.js` (also read by `assets-compare.js`), `public/js/mobile/charts.js`, `src/utils/sparklineSvg.ts` — exactly like the red; change one, change all. **The Last-30-min strip takes the same override**, off the same `_CHART_DEP_COLOR` at its own alpha: it is stacked directly above this chart, so a suppressed outage that read amber on one and grey on the other would be the two surfaces telling different stories about the same probes. There the grey is layered over `PolarisMonitorStates.replay` rather than resolved inside it (suppression is not part of the state machine) and applies to MISSES only.
  - **The response-time chart speaks VERDICTS, so it carries five colours; every other chart carries two.** It is the one chart that is about reachability rather than a reading, so its line reads as the Status pill reads: `_CHART_UP_COLOR` (`var(--color-success)`) up, `_CHART_MISS_COLOR` (`#ffc107` — the Last-30-min strip's own amber, deliberately NOT a deeper cousin picked for contrast: two ambers a shade apart on stacked surfaces read as two meanings) for a miss that has NOT reached the covering automation's `missedPolls` count, the COVERING AUTOMATION'S OWN SEVERITY COLOUR for the miss that IS the verdict (`PolarisChartSeverity.downColorOf(severity)` — `_CHART_FAIL_COLOR` `#d32f2f` at `critical`, which is every seeded down automation and every unresolved one, so a default install is unchanged; business rule 36 — Down is not inherently red, red is what `critical` looks like, and an operator who rates an outage `warning` has said something about how it should read), `_CHART_RECOVER_COLOR` (`#0288d1` — the light-blue 700, the SAME value the Last-30-min strip's recovering cell uses, which is the point of the two being stacked; purple until 2026-08-29, when the series went green and freed the blue that agrees with the Recovering pill and clears the lavender `#9575cd` maintenance band by more than a shade), and `_CHART_DEP_COLOR` over all of it when the upstream explains the miss. Amber vs red matters because red asserts Down: on a "down after 3 missed" device, painting the first dropped packet red says the outage started two polls before Polaris agreed it had. **The colours are not computed in the renderer** — `_renderMonitorChart` calls `_intermittencyStates`, a one-line delegate to `PolarisMonitorStates.replay` ([public/js/monitor-states.js](public/js/monitor-states.js)), the SAME replay the Last-30-min strip runs immediately above it and the phone's chart runs on its own screen, and maps its four states (`up`/`warning`/`down`/`recovering`) onto the four colours. That module is the browser's single decider; `PolarisMonitorStates.fromPayload` normalizes a history payload's `downDetection` block for it (three answers, never two: covered / passive / unknown). That is what puts the automation's RESET in the picture too: "down after 3 missed, up after 5 received" keeps the climb blue for all five answers, because the bucket LOCKS at 5 on the verdict miss and the drain itself serves the count (business rule 36). The counts AND the colour ride the history payload as `downDetection: { passive, missedPolls, recoveryPolls, severity }` — sent with the samples so the chart can never paint an outage and then repaint it when a second request lands. `passive: true` is a real answer (nothing may reach `down`); an ABSENT block is the unknown case and keeps every miss red. `_chartPointColor` is the single decider — a point with no `down` flag stays red, which is every other chart, unchanged.
  - **An `ok` point can never be `down`, and that is load-bearing** (2026-09-01). `_chartPointColor` offers an answered point exactly two answers — the series colour or `_CHART_RECOVER_COLOR` — so there is no way to paint one in the down colour. The state machine used to hand it one anyway: an answered probe taken while the bucket sat at or above the threshold read `down`, fell past both branches, and came out the plain series GREEN, so a long outage drew red → GREEN → blue → green and read as two recoveries. The strip directly above it drew those same probes RED off the same replay, so the two stacked surfaces described one outage in opposite terms. The fix is in the machine, not the renderer: `monitorStatusFor` returns `recovering` for ANY answered probe with misses outstanding. If you ever widen the machine so an `ok` point can carry a verdict again, this renderer has to gain a third branch in the same change.
  - **A marker landing on a real sample is DROPPED** (`_outageMarkers`' collision guard, half the series' median cadence). The Polaris Agent pushes on its own schedule and is not gated on `monitorStatus`, so an agent host can keep reporting CPU straight through an outage of the server-side probe transport; diving a line that has data would misreport what's actually held.
  - **Two-series charts feed the guard from the UNION of their timestamps, and share one marker set** (interface in/out, storage used/total; CPU & Memory is one such chart on every non-agent asset, and under the agent its two charts still derive markers from the same payload, so they still dive at the same x). Both values ride the same sample row, so an outage is an outage for both, and shared markers keep the lines diving at the same x instead of drawing two offset red notches. A series that simply stops reporting while the other continues has no probe failure behind it and correctly BRIDGES. **Per ASSET, never chart-wide, on any chart that co-plots several devices** — the compare view holds one series per asset, so one device's outage must never pull another's line to the baseline; `_cmpApplyOutageMarkers` folds each series' own `outages` into its own points.
  - **Where the `data-miss` hit rect goes in the paint order depends on the chart's other hit targets.** Charts whose hits are small circles anchored on the line (interface throughput/errors) emit `failDots + missHits + hits`. The CPU and Memory charts' hits are full-height Voronoi *lanes* and a gap sits inside the neighboring sample's lane, so the narrow miss rect has to paint LAST (`hits + missHits`) or it never receives the hover.
  - **Email counterpart:** the charts rasterized into alert emails ([src/utils/sparklineSvg.ts](src/utils/sparklineSvg.ts), fed by [src/services/alertChartService.ts](src/services/alertChartService.ts)) implement the SAME treatment — same `#d32f2f`, same baseline dive, same per-transition fade — because an operator must not have to learn an outage twice. They previously shaded the failed window red and broke the line, which is band vocabulary and therefore wrong. **The email's response-time chart carries the full verdict palette too** (2026-08-29): its series colour is the Up green (`#2e7d32`, the daylight themes' `--color-success` as flat hex, because the card is white), `recoverSpans` paints the climb `#0288d1`, and `failSpans[].kind` is a THREE-way — `"outage"` in the covering automation's severity colour (the `downColor` option, resolved by `alertChartService` through `downSeverityCss`; red `#d32f2f` at `critical` and whenever no automation resolved), `"dependency"` grey, `"missed"` amber `#ffc107`. Only the `"outage"` kind takes the severity: `"missed"` is not a verdict yet so there is no severity to express, and `"dependency"` is not this device's fault. `downSeverityHex` (server) and `DOWN_SEV_COLOR` (browser) are one palette in two files — nothing crosses that boundary — pinned by [tests/unit/downSeverityColor.test.ts](tests/unit/downSeverityColor.test.ts), which also guards each value against colliding with the miss amber, the recovering blue, the dependency grey or the maintenance lavender. Only that chart gets them (`RECOVER_SPAN_TOKENS`); CPU and memory keep their own series colour there for the same reason they keep it in-app. What an email chart may still diverge on: physical size, flat-hex palette (a mail client has no theme to read), no hover targets, and same-state runs collapsed into one polyline rather than a `<line>` per segment (a FortiGate can land thousands of points in an hour). The one band that survives there is `alarmSpans`, and it carries two claims of the same KIND: a hardware sensor's own alarm bit, and (2026-09-09) an SD-WAN health check reporting its member down. Both are the DEVICE's verdict about a reading that is still arriving, which is exactly what separates a band from the dive — a new band must make that same kind of claim or it belongs in the failSpans vocabulary instead. `failSpansFrom` delegates to `foldProbeOutages` so the two surfaces cannot disagree about where an outage began and ended, and to `replayProbeStates` — the server mirror of the browser's shared `PolarisMonitorStates.replay` — so they cannot disagree about which miss was already the verdict or which answer was still climbing. [tests/unit/assetIntermittencyBar.test.ts](tests/unit/assetIntermittencyBar.test.ts) runs both copies over the same patterns and fails when they part.
  - **Mobile counterpart:** the mobile SPA's [public/js/mobile/charts.js](public/js/mobile/charts.js) `lineChart` implements the same treatment with the same `#d32f2f`, **and since 2026-08-29 the same five-colour verdict palette on the response-time chart** — `pointColorFor` is the port of `_chartPointColor`, the series colour is `var(--md-success)` rather than the app accent, and `loadMonitor` in [public/js/mobile/asset-detail.js](public/js/mobile/asset-detail.js) runs the shared `PolarisMonitorStates.replay` over `resp.downDetection` to stamp `rec` / `down` / `downColor` per point exactly as the desktop loader does. **mobile.html loads `/js/chart-severity.js`** for that last one — the phone must resolve `down` to the covering automation's severity colour through the same `downColorOf` the desktop uses, rather than mirroring the palette into `charts.js` and making it a fourth copy. Every other mobile series omits both flags and stays red-only, matching desktop. Failures reach it either as explicit `{ts, v: null, ok: false}` points (response time) or as a per-series `gapFade: true` flag plus the chart-level `outages` list, resolved once across every flagged series by `applySharedOutageMarkers` (the union rule above). Two deliberate divergences from desktop, both forced by the surface: runs of same-state points collapse into ONE polyline rather than desktop's per-segment `<line>` elements (a phone holds a day of per-minute samples, which would otherwise be thousands of nodes), and failure dots are near-zero-length round-capped non-scaling strokes rather than `<circle>` — the mobile plot uses `preserveAspectRatio="none"`, which squashes circles into ellipses. Pinned by [tests/unit/mobileChartsFailureFade.test.ts](tests/unit/mobileChartsFailureFade.test.ts). Note `_pollGapMarkers`' single-midpoint branch (`if (b <= a)`) is unreachable in both copies — it needs `gap ≤ 2×median` but is only reached when `gap > 2.5×median`.
- **Drag-select = custom range.** Every renderer calls `_stashChartGeometry(container, t0, t1, padL, innerW, W)` after writing the SVG; every panel-open wires `_wireChartDragSelect(container, applySelection)` once, where `applySelection(fromIso, toIso)` calls `_applyCustomRangeSelection({btnClass, customBtnId?, panelId?, fromId?, toId?}, …)` then the chart's loader with `{from, to}`. Bars without a Custom… button (SD-WAN, process) pass just `{btnClass}` — presets un-highlight.
- API returns `{ range, since, until, samples[], stats }`. Custom ranges return `range: "custom"`.
- Loader writes the active selection onto the SVG container's `dataset.range` (or `dataset.from` + `dataset.to`) so probe-now / silent ticks can refetch the same view.
- "Custom" ranges do **not** auto-refresh; preset ranges do, on the resolved monitor interval (`_refreshIntervalMs`).
- Silent refresh ticks capture/restore `panelBody.scrollTop` around the swap so the slide-over doesn't jump.
- Range selection is persisted; "Custom" from/to inputs intentionally are not.
- **Plot surface = `.chart-box`** (`public/css/styles.css`). Every SVG chart in the asset slide-over is drawn into a div carrying this class — background, 1px border, 6px radius, 0.5rem padding and `--shadow-card`. Only the parts that genuinely differ stay at the call site (`min-height`, and the flex centring of the "Loading samples…" placeholder). The nine call sites used to stamp those four properties inline, one `el.style.*` block per stream, and none of them carried a shadow — so the charts read as flat cutouts next to the `.table-wrapper` tables stacked with them in the same tab. It is a big opaque box resting on the panel, so it takes `--shadow-card`, not the tables' `--shadow-md` (which is for surfaces floating OVER the page). A new chart adds the class; it does not re-derive the look.
- **Stats line:** call `_renderChartStats(container, count, [{label, value}, …])`. Leading `<strong>{count}</strong> samples` span, then one `<span><strong>{Label}:</strong> {value}</span>` per metric, joined by flex gap. **No** "current/as-of" prose inside the stats line — current readings go in the Status block above the charts, modeled on `Last Response Time` / `Last Poll`. **Each chart owns its own stats line** (don't share one stats container across two charts — see Interface throughput vs errors).
- **Polling-method badge:** every chart's section header carries one. Sync render uses the per-asset override only as a coarse first guess; the async path overwrites with the authoritative resolved value (covers class / integration / manual tiers). Cadence in the badge comes from the same resolved settings as the polling method, NOT a separate lookup.
- **Stale-data banner:** sections rendering `lastTelemetryAt` / `lastSystemInfoAt` / `lastTemperatureAt`-driven data prepend `_staleBannerHTML(assetId, asset, streamKey, lastAt)` (in `public/js/assets.js`). `streamKey` is `"telemetry"` (CPU / memory / hardware sensors), `"systemInfo"` (interfaces / storage / IPsec / LLDP), or `"responseTime"` (special-cased field names: resolved `intervalSeconds`, per-asset `monitorIntervalSec`). Banner text is `⚠ Last successful update <timeAgo>` (`_staleBannerInnerHTML`; the bare box is `_staleBannerBoxHTML(text)` for one-off wordings) and appears only when `lastAt` is older than 3× the resolved polling interval. Resolution priority: `_effectiveResolvedByAssetId` (full `/effective-monitor-settings` walk — covers per-asset / class override / integration / manual tiers) → per-asset override → manual tier from `_monitorSettingsCache` → hardcoded floor (60s telemetry / 600s systemInfo). **The field name each tier is read by comes from the shared mappers `_streamIntervalEffectiveField(stream)` / `_streamIntervalAssetField(stream)`** — the same pair the polling-method badge's `every <interval>` reads, so the threshold cannot disagree with the cadence shown inches above the banner. `_resolveStaleStreamSec` used to derive them as `streamKey + "IntervalSeconds"`, which for `telemetry` / `systemInfo` named a field no tier returns (the columns are `cpuMemoryIntervalSec*` / `systemInfoIntervalSec*`): every tier missed, the walk fell through to the floor, and a 10-minute stream bannered after three. Output is a `.asset-stale-banner-slot` wrapper so `_updateStaleBannersFromEffective(assetId, asset)` can re-evaluate after the eff fetch lands — the sync first paint can't see a class override, the async pass picks it up. The two `effectiveMonitorSettings()` callers (`_populateAssetMonitorTierBadges`, `_updateStreamSourceBadgesFromEffective`) plus the response-time chart loader all populate the cache + fire the re-evaluator on success. **Never measure freshness from a rollup-tier chart series.** A rollup sample's `timestamp` is its `bucketStart`, so the newest daily point is up to 24h old the moment it's written (and the daily rollup only runs at 02:30 UTC) — deriving the banner from it made a healthy 1-minute probe read "Last successful update 17h ago" as soon as the operator picked 30d. The response-time banner (`_updateMonitorStaleBanner`) reads the payload's `lastSuccessAt` (server-side `readLastMonitorSuccessAt`, the newest successful DETAIL sample) whenever present and only falls back to scanning the series on the detail tier / when the last success predates detail retention. Every other section's banner is already safe because it reads a live `Asset` column (`lastTelemetryAt` / `lastSystemInfoAt`), not a chart sample. **A section's empty state renders the banner too.** The banner is emitted inside the chart/table container, so an empty-samples early return swallows it — which is backwards: a window with nothing to draw is exactly when the last successful pull is the only thing that explains the gap. `_renderCpuChart` (the first of the two CPU & Memory charts under the agent; `_renderSystemChart` does the same on the combined shape every other source gets) is the reference; **the memory chart beside it deliberately renders NO banner** — both read the same telemetry rows off the same `lastTelemetryAt`, so two identical amber boxes inside one section would read as two separate problems. The one empty state that stays bannerless is `_notAvailableViaPollingHTML`, where the transport cannot deliver the stream at all and there is no freshness to report.
- **Response Time banner (chart-derived timestamp):** the Response Time section carries a `#asset-monitor-stale` slot that `_updateMonitorStaleBanner(assetId, data, opts)` rewrites on every history load — `lastAt` is the newest SUCCESSFUL sample in the fetched window (not `lastMonitorAt`, which stamps on failed probes too). Cleared on custom from/to windows (fixed historical views say nothing about live freshness); a live window with samples but zero successes renders "No successful update in the last <range>".
- **Current-state tab strip (cadence · freshness · Refresh):** the three SNAPSHOT tabs — **Wireless**, **MAC Table**, **ARP Table** — are not time series: each is a picture of what the device last answered, and read without a cadence and an age an empty client list or forwarding database says "nothing is connected" when it just as often means "not asked since yesterday". All three render `_currentStateStripHTML({ title, suffixHTML, chipHTML, lastAt, cadenceSec, neverText, refreshId, refreshTitle })` as their heading row: the section title, an optional counts parenthetical, a cadence chip, an `_freshnessStampHTML` age stamp, and a Refresh button pushed to the right. **The stamp turns amber at ONE cadence, not the stale banner's three** — the two are deliberately different thresholds: at 1× a poll is merely OVERDUE (the answer to "is this current"), at 3× the data has been abandoned long enough to be wrong. Wireless stacks both; collapsing them onto one threshold is the likely drift and `tests/unit/assetWirelessTreeDom.test.ts` pins it. **Each tab feeds ONE cadence figure into both the chip and the threshold**, so the number an operator reads is the number being compared against: Wireless resolves it client-side with `_resolveStaleStreamSec(assetId, asset, "systemInfo")` (the same resolver its stale banner uses) and shows the full `_streamSourceBadgeHTML(asset, "interfaces")` badge rather than a bare chip, since which transport and credential answered is what an operator asks next when the list is empty; MAC Table and ARP Table take the server's fully-walked `pollIntervalSec` and render `_cadenceChipHTML`, which is the only figure that can see ARP's discovery-only case. `lastAt` null renders `neverText` rather than an empty slot — on these tabs "we have never had an answer" is the single most useful thing the strip can say. The Refresh button is omitted entirely without `canProbeAssets()`, mirroring the route's `assetsProbe` gate. **Every branch of the tab renders the strip, the empty state most of all** — that is the case it exists for. The SD-WAN tab's three sections carry the same badge + stamp pair without a Refresh — next entry.
- **SD-WAN section headers (provenance · freshness, no Refresh):** the asset modal’s **SD-WAN** tab is three snapshots of what the gate last answered — **SD-WAN Members**, **SD-WAN Rules**, **Performance SLA** — and all three head themselves with `_sdwanSectionHeaderHTML(a, title, lastAt, cadenceSec, neverText, extraHTML, rightHTML)`: the heading, optional inline content (Performance SLA’s health-check `<select>`), the full `_streamSourceBadgeHTML(a, "interfaces")` badge, the `_freshnessStampHTML` age stamp, and optional right-pushed content (its range buttons). Same 1×-cadence amber threshold as the snapshot-tab strip above; **no Refresh button**, because `refresh-system-info` re-reads the pass as a whole and the SD-WAN leg is not separately re-askable. **Each section states its OWN `lastAt`, never `asset.lastSystemInfoAt`** — the rules table and the perf-SLA stream are distinct writes on one pass and either can land without the other, so both `lastAt` and `cadenceSec` come from the endpoint that served the section (`collectedAt` / `pollIntervalSec` on `/sdwan-rules` and `/sdwan-members`), the pattern the ARP and MAC tabs set. Performance SLA reads the members’ stamp, both being the same `asset_perf_sla_samples` table, and falls back to `lastSystemInfoAt` only when the endpoint returned none. `tests/unit/sdwanSectionHeaderDom.test.ts` pins the amber threshold, the never-collected text and the null-cadence case (an unmonitored gate, where nothing refreshes SD-WAN, must never amber).
- **Wiring Refresh:** `_wireCurrentStateRefresh(refreshId, assetId, onDone)` calls `api.assets.refreshSystemInfo(assetId)` — `POST /assets/:id/refresh-system-info`, probe-now narrowed to the system-info collector, which writes no monitor state. ONE endpoint serves all three tabs because one pass writes all three tables; `onDone` re-loads whichever tab asked, and runs on failure too so the stamp refreshes either way. `supported: false` is toasted as information, not an error (monitoring off, Interfaces stream Disabled, an agent-managed host pushing on its own schedule are all legitimate) — a spinner that simply stops leaves the operator guessing which. Wireless re-loads through `_reloadWirelessStations`, which re-fetches `/system-info` and repaints that tab alone rather than going through `_loadSystemTabFor` (which would also refetch telemetry history and repaint five sections nobody is looking at); it updates `_assetSystemSiCache` so the System tab stays on the same snapshot.
- **Hardware Sensors:** the section prepends the standard `_staleBannerHTML(…, "telemetry", si.lastTemperatureAt || si.lastTelemetryAt)` banner like every other section (the table-specific timestamp means it fires when CPU/mem succeeds but the sensor pull fails). The header's `#asset-system-temps-updated` slot (`_updateTemperatureUpdatedStamp`) stays as a neutral tertiary-color "updated …" stamp only — it no longer flips amber; staleness is the banner's job.

**When adding a new instance:**
- Pick a unique chart id and add it to the prefs key list above.
- Reuse `_chartRangeBtnsHTML` for the toolbar — don't roll your own.
- Wire `_wireChartTooltip` and `_observeChartResize` — every existing chart does, and skipping breaks behavior parity.
- Draw the X axis with `_chartXTicksSVG(t0, t1, padL, padT, innerW, innerH[, { dateLine }])`, not a loop of your own. It takes its ticks from `_chartTimeTicks`, which puts every tick on a local-time boundary: midnight on a multi-day window, a clock multiple of a nice step inside one. The step is the smallest that keeps labels about 80px apart, and HH:MM labels are never used past 4 days. A label at either end is anchored inward. Every chart used to tick at equal fifths of the window. Over 7 days that is every 1.4 days, so date-only labels skipped whole days and sat between the dashed midnight lines from `_dateChangeMarkers`, and the last label was clipped at the right edge. `dateLine` is the response-time chart's M/D under the first tick and each day change, used on ≤24h windows.
- Wire `_addChartScreenshotButton` with a `getStats` callback (via `_statsSummaryFrom`) — a camera button without it produces screenshots missing the stats line. The button reads the container's `dataset.from/to` at click time (`_chartCustomRangeLabel`) and stamps a "From … to …" header line into the capture when the chart is on a custom window — another reason the loader must stamp the dataset.
- The camera paints the SVG as an `<img>`, which sees no stylesheet and no custom property. `_serializeChartSvgForRaster` (shared by the camera and the interface-panel composite) writes back what the chart inherited: every `var(--…)` in the markup, `currentColor`, and a sans font stack on the root. So colour the SVG with inline `fill`/`stroke` attributes or `style`, whether tokens or literals. Never colour it through a stylesheet class: the capture cannot see one, and the mark comes out black. Until 2026-09-23 only the accent was substituted, and every `var(--color-success)` response-time sample came out black.
- Attach the loader's persisted range to the container dataset so silent refresh and probe-now refetch the same window.
- Call `_stashChartGeometry(container, t0, t1, padL, innerW, W)` in the renderer and wire `_wireChartDragSelect` once at panel setup so drag-to-select works like every other chart.
- Use `_renderChartStats` for the stats line. If your chart has additional "current" readings worth showing, put them in the Status block (or a sibling section that mirrors Status), not inline in the stats line.
- Stats values must come from `data.stats` server-side or be derived once from the same samples the chart renders — don't duplicate aggregation logic.
- Add a polling-method badge to the section header via `_streamSourceBadgeHTML` whenever the chart's data is delivered by a configurable polling stream (response-time / telemetry / interfaces / lldp).
- If the data is unsupported on some monitor transports (e.g. ICMP/SSH), render an empty-state message — don't show an empty chart.
- Prepend `_staleBannerHTML(assetId, asset, streamKey, lastAt)` whenever the section renders sample data driven by a `last*At` timestamp. Use `streamKey: "telemetry"` for CPU / memory / temperature surfaces and `streamKey: "systemInfo"` for interface / storage / IPsec / LLDP surfaces. The slot wrapper auto-rehydrates when `/effective-monitor-settings` resolves — no manual await needed. Render it on the section's EMPTY path as well as its data path — see the stale-data banner entry above.
- **Apply lookback overflow + clip-path.** In the route handler, call `extendSinceForLookback(since, pick.bucketSeconds)` and pass the result to the history service as `fetchSince`. In the service, default `fetchSince` to `since`, use it for the WHERE clause, and gate stats accumulation on `r.timestamp.getTime() >= since.getTime()` so overflow rows drive line continuity without inflating counts. In the renderer, allocate one clip id with `_chartClipId("<chartName>")`, emit `_chartClipDefs(id, padL, padT, innerW, innerH)` inside the SVG, and wrap every data-drawing element (line segments + dots + baseline failure dots + hit targets) in `<g ' + _chartClipAttr(id) + '>…</g>`. Leave axis ticks, grid lines, legends, and the stale banner OUTSIDE the clipped group — they need to render in the y-axis label gutter where pre-since samples must be hidden.
- **Maintenance bands.** Emit `_dateChangeMarkers(t0, t1, padL, padT, innerW, innerH) + _maintenanceBandLayer(t0, t1, …same args…)` together, BEFORE the clipped series group, so windows where polling was paused render as labeled translucent purple bands instead of unexplained gaps. The band data comes from the per-panel `_maintWindowsCache` (fetched once in `openViewModal` from `GET /assets/:id/maintenance-windows`) — the renderer call is synchronous and free when the asset has no windows. Each band carries a native `<title>` tooltip (name + entry → exit), so no custom hover wiring is needed.
- **Automation severity shading (opt-in).** A chart whose metric an automation watches can fade its line into the tier colors instead of a flat accent, so a reading's severity is legible without opening Automations. Fetch the ladder ONCE per subject with `_loadMetricSeverityTiers(assetId, metric, dim)` (`GET /assets/:id/metric-thresholds`, computed server-side by `notificationRuleService.getMetricSeverityTiers` off the same `resolveTierLadder` the engine evaluates — never re-derive thresholds client-side), stash it keyed by subject so range changes and silent ticks reuse it, and render with the tiers in the render `opts` (so `_observeChartResize` keeps them). Then `var sev = _severityChartLayer(kind, opts.tiers, minV, maxV, geo)` and place its four pieces: `sev.defs` in the SVG head, `sev.lines` + the polyline/dots inside the clipped group with `stroke="sev.stroke"`, `sev.labels` OUTSIDE the clip. `sev.stroke` is the plain accent color when nothing watches the metric, so the un-shaded path is byte-identical to before. The gradient math is pure and lives in `public/js/chart-severity.js` (`window.PolarisChartSeverity`) — thresholds outside the visible domain CLAMP (a range entirely above critical is entirely critical-colored) rather than widening the axis. Canonical instance: `_renderSensorChart`.

## Many-series chart (one line per dimension)

**What it is:** A time-series chart whose series count is decided by the DATA, not by the code — one line per logical CPU core today, and the shape any future per-dimension chart should copy. Everything in **Time-series chart (SVG)** above still applies; this section is only the parts that change once "how many lines" stops being a constant.

**Canonical implementation:** Asset Details → System → **CPU** chart.
- Renderer: `_renderCpuChart()` in `public/js/assets.js`.
- Mounted only when the data can HAVE dimensions: `_telemetrySplitsCpuMemory()` gates the section's markup in `assetSystemViewHTML()`.
- Two sources fill the vector: the agent (a host's logical cores) and vCenter (`fetchVcenterPerfSamples()` — a VM's vCPUs, an ESXi host's physical cores). The renderer knows about neither.
- Transpose: `_cpuCoreSeries(samples)` — per-sample vectors into one series per index.
- Palette: `_cpuCoreColor(i, n)` between `_CPU_CORE_HUE_START` / `_CPU_CORE_HUE_END`.
- Legend + toggles: `_cpuLegendHTML()` / `_wireCpuLegend()`, chips built by the shared `_seriesChipHTML()`.

**Key conventions:**
- **A switched-off chip has to stay readable, because it is the only route back.** The strikethrough carries the state, not the dimming — `_seriesChipHTML` measured 1.84:1 on morning / 2.01 noon / 2.17 nightfall at `opacity:0.4`, against 6.1-8.5:1 for a live chip. That is under the floor for non-text UI, on a click target. It renders at 0.8 now (3.93-4.99:1) and only the swatch fades far, that being decoration — though not to nothing, since the colour is how the operator finds the series again.
- **The palette is an HSL ARC that excludes the reserved hues, not a fixed list.** A fixed list runs out; an arc does not. The arc must exclude RED (`_CHART_FAIL_COLOR`, missed poll) and stay saturated enough never to read as the dependency GREY (`_CHART_DEP_COLOR`) — a data line in either is read as an outage marker, which is the one reading an operator must never get wrong. Spread hues by `i / n` rather than `i / (n - 1)`: dividing by `n - 1` puts the last series on the far end of the arc, which at a high series count is a near-neighbour of the first. **Alternate lightness between adjacent indices** — at 64 series each gets under 5° of hue, which is invisible, while a 16-point lightness step is not.
- **The aggregate keeps its own line, on top, and is the only one with dots.** It is the series every threshold, automation and metric actually reads, so it has to stay findable in the thicket. It is also the only failure-aware line (`_failureAwareSeriesSVG`): 64 lines all diving to the baseline together would bury the red marker they are supposed to make legible, so the per-dimension lines are plain polylines.
- **A dimension missing from a sample gets NO POINT, not a zero.** Zero is a reading; "not reported" is not. A vector that shortens mid-window (a resized VM, a payload truncated at a cap) must leave a gap, and a non-finite value must be dropped rather than reaching the path as `NaN` coordinates.
- **The legend is HTML above the SVG, not `<text>` inside it.** It has to wrap — 64 chips on one SVG line run off the panel — and its chips are interactive.
- **A legend chip is a TOGGLE, and there is exactly one piece of state behind it.** Clicking a chip switches that series out of the drawing; double-clicking a dimension isolates it by hiding every other one. Isolation is a bulk edit of the hidden set, not a second mode — "hidden" and "focused" as separate models can disagree with each other, and did. **A double-click also fires two clicks**, so the single-click handler is deferred past the double-click window (220 ms); without that, an isolate first toggles the very chip it was aimed at and leaves the isolated series hidden.
- **Anything that can be switched off needs a one-click way back.** Sixty-three chips of undoing is not a way back, so a `Show all` affordance appears in the legend as soon as something is hidden, and disappears when nothing is.
- **Visibility state lives on the container's dataset, never in a module variable, and per-dimension state is NOT persisted.** The resize observer and the 60-second silent refresh both re-render; state held anywhere else is lost on every tick, which makes hiding a series useless for the one job it has. It is deliberately not written to prefs either: core 5 of one host has nothing to do with core 5 of another, so carrying the choice between assets would hide a different core each time. **Named** series are the opposite case — see the stacked-area section.
- **Opacity and weight key off how many series are DRAWN, not how many exist.** Switching sixty-three cores off must leave the survivor solid, or hiding the rest bought nothing.
- **A tooltip names what is drawn.** A hidden dimension listed there puts a reading on screen with no line to attach it to, which is the opposite of what switching it off was for. Say how many were hidden, though — a tooltip that silently shortens looks like missing data.
- **A tooltip listing every dimension is not a tooltip.** Cap it (the CPU chart shows the six busiest of whatever is still switched on) and say how many were dropped.
- **Say WHY the dimensions are missing when they are.** Per-core data is detail-tier only, so a rollup-tier range legitimately has none; the note distinguishes that from a source that never reports them (checked with `_resolvedStreamPolling`), because "pick a shorter range" sent to a FortiGate operator points at nothing.
- **A source that can never carry dimensions does not get the chart.** The whole CPU & Memory section renders in one of two shapes, decided by `_telemetrySplitsCpuMemory(asset)` — is the RESOLVED telemetry method in `_SPLIT_CHART_METHODS` (`agent`, `vcenter`) — giving either the split pair or the single combined `_renderSystemChart()` below. Those two transports are the ones that report per-core CPU and a memory composition; on FortiOS / SNMP / WinRM / SSH the split produced two single-line charts where one had been, on a tab that is already long. **A method added to that list without a collector filling `cpuCorePcts` or a band set re-creates exactly the bug the list exists to prevent**, which is why `tests/unit/assetSystemSectionShape.test.ts` pins its contents. Degrading INSIDE a renderer (the aggregate-only CPU line, `_renderMemoryPctChart`) is still right for a source that usually reports more and this time did not; it is not a substitute for not splitting a source that structurally cannot. Resolved, not the per-asset column, so a class- or integration-tier method still decides.

**When adding a new instance:** transpose in a named helper so it is unit-testable without a DOM; reuse `_cpuCoreColor`'s arc rather than inventing a second palette; pin the reserved-hue exclusion in a test (`tests/unit/assetCpuMemoryChartsDom.test.ts` asserts the ARC, not the individual colours, so the palette stays free to be retuned).

## Stacked-area chart (parts of a whole)

**What it is:** A time-series chart whose bands stack to a meaningful total, for a reading that is a COMPOSITION rather than a level — memory today.

**Canonical implementation:** Asset Details → System → **Memory** chart.
- Renderer: `_renderMemoryChart()` in `public/js/assets.js`; band tables `_MEM_BANDS_AGENT` and `_MEM_BANDS_VSPHERE`. Legend toggles: `_wireMemLegend()` + `_memBandVisible()` / `_setMemBandVisible()`.
- Mounted only under the agent and vCenter — see the gate in **Many-series chart** above. Every other source's memory rides the combined `_renderSystemChart()` as a percentage instead.
- Per-sample shaping: `_memBandsFor(sample)` — also picks WHICH band table, off the columns the row carries. Gap splitting: `_memRuns(points, gapMarkers)`.
- Degraded fallback: `_renderMemoryPctChart()`.

**Key conventions:**
- **One band per `<polygon>` per contiguous run**, each running left-to-right along its own cumulative top and right-to-left back along the band below it. A single-sample run is dropped rather than emitted as a degenerate polygon that paints as a 1px spike.
- **Split the runs at the SAME outage evidence the lines use** (`_outageMarkers` → `_memRuns`), never at the size of a gap. A band painted flat across a window in which nothing was collected asserts a composition nobody measured.
- **The axis ceiling is the WHOLE, so the gap above the stack is the remainder** — and the remainder band is therefore never drawn, which is also how the chart avoids putting a large neutral-grey fill next to lines whose grey means dependency-down. Draw the whole as a dashed reference line so the headroom has an anchor.
- **Derive the remainder rather than trusting the source's own figure for it.** A `free` that disagreed with total-minus-the-rest would put a tooltip on screen contradicting the picture beside it.
- **A quantity that does not belong in the sum rides as its own line.** Swap is a different device from RAM; stacking it would make the total mean nothing.
- **Degrade through the source shapes, never to an empty panel.** Memory arrives in three: a full breakdown, a bytes-only source which collapses to one band, and a percentage-only source which falls back to a single line on a 0–100% axis. **The legend SAYS which one is in play** — "this source reports a total only" beats letting an operator read a permanently-zero cache band as a fact about their host. The degraded shapes are for a source that usually reports more and this time did not (a container, a BSD, a Windows build with no swap file; a vCenter account without the Performance privilege); SNMP / WinRM / FortiOS assets never reach this renderer at all, because the section does not split for them.
- **A SECOND vocabulary is a second band table, never a relabelling of the first.** `_MEM_BANDS_VSPHERE` exists because vSphere measures how the HYPERVISOR is backing a guest's RAM — private / shared / ballooned / host-swapped / compressed for a VM, consumed / ballooned / host-swapped for an ESXi host — which is not what buffers and page cache mean and does not convert into them. `_memBandsFor` picks the table from the columns the row actually carries, and the collectors guarantee a row carries one set or the other; the renderer then drops any band NO row in the window reported, which is the same mechanism that collapses a bytes-only source to one band. A band reported as 0 is KEPT — a host genuinely not ballooning is a reading. The primary band takes the same orange in both tables, because the two never co-occur and "the big one at the bottom" should read the same on any asset. **Say whose accounting it is in the legend**: a figure measured outside the guest, sitting next to one the guest reports about itself, is the kind of disagreement an operator otherwise files as a bug.
- Byte axes need a wider left gutter than percentage axes (`padL` 58 vs 50): the ticks are `12.5 GB`, not `80%`.
- **A NAMED series' visibility is a standing preference, so it persists** (`polaris-prefs-series-<username>`, `_memBandVisible`) — unlike the per-core toggles next door, which are per container. Bands mean the same thing on every host, so which of them an operator wants to see is an opinion they hold, not a per-visit whim. It is also the only way a DEFAULT is expressible: an absent entry means "never touched this chip", which resolves to the default, and only an explicit boolean overrides — so reading the pref as falsy-means-off would silently switch everything off for every user who has never clicked one.
- **Cache ships OFF** (`_MEM_BANDS_OFF_BY_DEFAULT`). Page cache is reclaimable — the OS fills whatever RAM processes are not using and hands it straight back when they want it — so drawn in the stack it makes a perfectly healthy host look nearly full. That is the single most common misreading of this chart, so the default answers "how much is actually spoken for" and the chip sits there, visibly struck through, for anyone who wants the whole picture.
- **Switching a band off changes the PICTURE, never the arithmetic.** The ceiling is still the installed total and the derived remainder still subtracts every measured band, cache included — so the unpainted gap stops meaning "free" and starts meaning "free, plus what you hid". Say so in the legend, because an operator reads headroom off that gap. The TOOLTIP keeps naming every band the source reported, hidden ones marked: the chart answers what shape the memory is, the tooltip answers what was measured, and that second answer must not depend on which chips are lit.
- **Keep offering the chip for a band you are not drawing.** A chip that disappeared when clicked would be a one-way door.

**When adding a new instance:** declare the bands in a table (`{key, label, color}`) so the legend, the stack order and the tooltip cannot disagree; keep the per-sample shaping in a pure helper that guarantees the bands close on the total; and reconcile any per-source quirks BEFORE the browser — the agent's `meminfo.go` does the OS-specific memory reconciliation precisely so the chart does not need a per-OS branch.

## Operator-customizable widget surface

**What it is:** A page where the operator enters an explicit EDIT MODE, chooses which widgets appear via a full picker (Group-By + search + favorites), arranges them into resizable COLUMNS, and configures per-widget options via a gear popover. Layout persists server-side per user. Read-only by default with a "Customize Page" affordance; empty state prompts the operator to customize. The Dashboard home page is the first instance; future operator-customizable surfaces should match this shape.

**Canonical implementation:** Dashboard home page — entry point is `public/js/dashboard.js` (orchestrator), backed by:
- HTML: `public/index.html` — `#dashboard-empty-state`, `#dashboard-canvas`, the `#dashboard-customize` / `#dashboard-add-widgets` / `#dashboard-done` header buttons, and the `#widget-library-overlay` picker (`#widget-picker-groups`, `#widget-picker-search`, `#widget-picker-sort`, `#widget-library-body`).
- CSS: `public/css/styles.css` — `.dashboard-canvas` (12-col CSS grid of columns), `.dashboard-column*`, `.dashboard-widget*`, `.dashboard-drop-placeholder` (green "+"), `.dashboard-newcol-target`, `.widget-picker*`, `.widget-library-card`, `.widget-config-popover`. **Chrome paints tokens, never literals** — accent states go through `var(--color-accent)` (the retired cyan `#4fc3f7` is not an accent anywhere), pointer feedback on transparent chrome through `var(--color-hover-tint)`, and static faint fills (count badges, chips) through `var(--color-fill-subtle)`. Both tints are defined white-ish on the dark base and black-ish on the daylight base, because a white overlay is invisible on a light surface and morning/noon had no hover feedback at all until they existed. The `.widget-pill-{ok,watch,amber,red}` literals are the one sanctioned exception and carry a comment saying why.
- Widget modules: `public/js/widgets/*.js` — each self-registers via `PolarisWidgets.register({...})` (registry in `public/js/widgets/index.js`).
- Picker: `public/js/widget-library.js` — `WidgetLibrary.open(onAdd)` / `close()` / `isOpen()`.
- Favorites: `public/js/favorites.js` — `getFavorites`/`isFavorite`/`toggleFavorite` (localStorage entity `"widgetlib"`); MUST be `<script>`-included before `widget-library.js`. (A page whose stars belong to something OTHER than the browser calls `registerFavoritesProvider(entity, {get, toggle, titleFor?})` instead of adding a second store — the Assets page does, so its stars follow the view tab; `getStoredFavorites` is the localStorage read that bypasses providers, which is what a provider seeds itself from.)
- Persistence: `UserDashboard` Prisma model + `src/services/userDashboardService.ts` + `src/api/routes/userDashboard.ts` (GET/PUT `/me/dashboard`); client at `api.me.dashboard.{get,put}`. The SHARED (per-resource, not per-user) variant of this pattern is `TopologyLayout` + `src/services/topologyLayoutService.ts` (Device Map topology drag layouts, one row per (site, view); writes RBAC-gated `deviceMap=write`, reads embedded in the topology GET) — copy that when a layout should be one map every operator sees rather than a personal preference.
- Wallboard variant: `public/dash.html` is the unauthenticated read-only mirror (Dash wallboard, served by `src/dash/dashServer.ts`) — same markup/widget list, `dash-mode.js` flags + `dash-boot.js` instead of `app.js`, layout in localStorage (`polaris-dash-layout`) via the `POLARIS_DASH_LOCAL` branch in `dashboard.js`.

**Key conventions:**
- **Tabbed multi-dashboard model (v3).** Layout = `{version:3, dashboards:[{id, name, columns:[{id, width, widgets:[{id,type,height,config}]}]}], activeId}` (max 24 dashboards). Each dashboard is a named tab; `activeDash()` selects the live one. Within a dashboard, columns are CSS-grid items spanning their `width ∈ {3,4,6,12}` (12-col canvas; columns past 12 wrap); widgets stack vertically and carry `height ∈ {1,2,3}` set as a **fixed pixel height** on the article (280/576/872px) so chart/Leaflet bodies get a sized container. Array order IS the layout — no free-grid reflow.
- **Explicit edit mode + tabs.** `state.editing` gates all chrome; "Customize Page" → `enterEditMode()`, "Done Editing" → `exitEditMode()` (forces the debounced save). A "Create New Dashboard" button adds a tab; the active tab's name is click-to-rename inline; tabs remove via their × in edit mode. Toggling edit mode re-renders the canvas (re-runs widget `onUnmount`/mount).
- **v1/v2→v3 migration.** Legacy v1 (`{widgets:[{col,row,...}]}`) and v2 (`{version:2, columns:[...]}`) layouts migrate on load into a single "Dashboard 1" tab; empty fallback on error. GET is server-unvalidated so stored older rows still load; the next save persists v3.
- **Drag = geometry → target.** `dropTargetFromCursor(x,y)` returns `{columnIndex, insertionIndex}` or `{newColumn}` from column rects + card midpoints. A single `.dashboard-drop-placeholder` (green "+") is moved into the target stack; the source widget gets `.lifted`. A trailing `.dashboard-newcol-target` accepts drops into a fresh column. Both dataTransfer mime types (`application/x-polaris-widget` add, `…-move` reorder) + the module-level dragstart stash are kept from v1.
- **Module shape.** `{ type, label, description, category?, defaultSize, minSize?, defaultConfig?, requiredPermission?, fetchData?, renderInstance(el, config, data, ctx), renderPreview(el), renderConfig?(el, config, onChange), onMount?, onUnmount? }`. `category` (default "Other") buckets the picker Group-By. `ctx.onUnmount(fn)` registers cleanup; the orchestrator runs it on remove/re-render.
- **Mini-previews are real renders, not screenshots.** Each widget's `renderPreview(el)` calls the same DOM-emitting code as `renderInstance` with mock data.
- **Per-feed data fetch.** Every widget fetches only the data it renders: the NOC set via `PolarisWidgets.getNocSummary(opts, feeds)` (`/dashboard/noc-summary?feeds=…`), the IP-space set via `PolarisWidgets.getSummary({sections,...})` (`/dashboard/summary?sections=…`) — both 15s-memoized **per (feeds/sections, filter, limit)** with in-flight dedupe, so same-key widgets share one fetch while each widget renders as soon as its own feed returns. The server adds a 10s per-feed TTL cache on top, so distinct widgets/tabs hitting the same feed stay cheap. There is no orchestrator-prefetched `summary` arg on `fetchData` anymore — `fetchData(config)` owns its fetch.
- **Refresh cadence is one of three named tiers.** `PolarisWidgets.REFRESH = { fast: 10000, normal: 30000, slow: 60000 }` in `widgets/index.js` — pick by how fast the underlying thing actually moves: `fast` for in-flight progress (a running discovery), `normal` for outage state (down assets/interfaces, active alerts), `slow` for ranked metrics, forecasts, maps and history. Never write the millisecond literal. **Every widget with a live feed gets a timer**, re-fetching through the same function `fetchData` calls (extract it to a module-local `fetch…()` rather than duplicating the expression, or the two drift) and clearing it in `ctx.onUnmount`. A widget with no timer renders once and is frozen forever on the Dash wallboard, which is where dashboards actually live — six of them were, until 2026-08. Note `NOC_TTL_MS` is 15000, so a `fast` widget gets cached data two ticks out of three; that is fine for a progress readout and must not be copied to anything needing fresh data.
- **Per-widget filters + dynamic title.** `PolarisWidgets.renderNocFilterConfig(el, config, onChange, includeAssetTypes)` appends a shared **Regions** scope (All / My regions → caller's effective `regionTags` / Selected regions… → per-widget checkbox pick of created regions, list from `PolarisWidgets.getRegionOptions()`; "My regions" is hidden on the /dash wallboard) + optional **Asset types** toggle grid to a gear popover; `nocFilterOpts(config)` extracts `{assetTypes, assetTypesOff, regionScope, regions}` to pass to `getNocSummary`. **The type grid is registry-driven and paints twice** — built-ins synchronously (so the popover is never empty), then the full vocabulary from `PolarisWidgets.getAssetTypeOptions()` (built-ins + every operator-added type in the asset-type registry, labelled by its registry row — the registry, not the types the fleet happens to wear, so a type created in Server Settings is filterable before anything is typed as it), keeping any toggle made in between. It edits the switched-OFF list: a change writes `assetTypesOff` (the names to hide, custom included — the only shape that CAN hide a custom type) and `assetTypes` (the checked list, for the header title), and the query goes out as `?hideAssetTypes=`. A narrowed filter is named in the widget's header title (`widgetTitleFor` in dashboard.js, refreshed on gear change) the shorter way round: the types shown ("Highest Avg CPU (Server, Switch)") or, when fewer are off than on, the exclusions ("Down Assets (excl. Printer, Network Camera)").
- **Header pill + severity-tier CSV export.** `PolarisWidgets.setHeaderCount(el, count[, severity])` stamps the overall-total pill on the widget header — pass `PolarisWidgets.maxAlertSeverity(rows)` and the pill colors to the set's most severe active alert off the same `alertSeverityPill` palette (serious → orange, critical → red), so it can't disagree with the row pills below it; per-group count pills get the same treatment via `PolarisWidgets.countPillClass(rows)` (returns the full `class` string). Both fall back to red when no row carries an alert — there's no severity to honor and red is the generic "these are down" count. Down Assets is the reference; a count pill over rows that aren't severity-tiered (Sites With Issues, the threshold-colored Stale Polls / Conflict Queue counts) stays on its own color rule. **When the operator wants the split rather than the worst**, call `PolarisWidgets.setHeaderSeverityCounts(el, rows[, {unalerted, severityOf}])` instead — it renders one pill per active-alert severity in the set (`alertSeverityCounts(rows[, severityOf])`, most severe first, each in its own severity color) so the title reads "2 critical, 12 serious" rather than one number colored to the worst. `unalerted:"neutral"` (default) appends a grey pill counting the non-alerting rows so the pills still sum to the row total, and a set with NO alerting row keeps the plain red total pill; `unalerted:"omit"` drops them, which is what a ranked top-N list wants (its row count is the operator's Row limit, not a fleet total). **Down Interfaces** is the reference for the first mode, `_topnBar`'s `renderRows` for the second (every top-N widget gets it with no opt-in since 2026-08). **Pass the rows you are about to render**, not the fetched set: the convention is that the pills count what's on screen, so stamp AFTER the row limit / horizon / red-guarantee pass and BEFORE the empty-state return (an empty array clears the pills, which is what makes them track the data). The ⤓ export provider is the deliberate exception and stays on the full matched set. Widgets carrying a severity vocabulary of their OWN — Capacity health's ok/watch/amber/red — use `setHeaderTierCounts(el, rows, {keyOf, order, classOf, noun})` instead; never extend `ALERT_SEVERITY_RANK` with a second ladder, or the two start ranking against each other in the min-severity filter and the export tiers. Both modes go through `setHeaderPills(el, [{text, className, title?}])`, the one place that owns the `.widget-header-count` container — which seats the pills at the **head** of the title (`[2][12] Down Assets`, not `Down Assets [2][12]`), and re-seats them there on every call so a host left behind by an in-place title rewrite can't keep trailing. The title is a single `white-space: nowrap` ellipsized line, so a count appended after the name is the first thing a narrow column drops, and the count is the half an operator scans a wall for. `PolarisWidgets.setHeaderExport(el, {columns, rows, filename?, severityOf?})` stamps a ⌄-menu ⤓ export button **in VIEW mode only** — in edit mode the same header slot carries the ⇅ sort button instead (next bullet) — whose tiers (All rows / Critical only / Serious and up / Warning and up, live counts) filter the widget's FULL pre-clip listing on each row's active-alert severity (`ALERT_SEVERITY_RANK`, the client mirror of nocDashboardService's ladder — event levels fold in at error=critical / info=informational) and download a CSV with an auto-appended Severity column (filename defaults from the widget `data-type`; local CSV fallback on the Dash wallboard, which lacks app.js `downloadCsv`). Both are re-call-every-render-tick helpers that no-op outside a dashboard shell (library previews) and remove themselves at zero rows/count. Export is wired on Active Alerts, Down Assets, Down Interfaces, Storage Forecast, and all six top-N widgets (once, inside `_topnBar.renderRows`) — a new severity-bearing listing widget should call it with its own column spec.
- **Sort order is the operator's, and it is an edit-mode header control, not a gear field.** `PolarisWidgets.setHeaderSort(el, {options, config})` stamps a ⇅ button in the header slot the ⤓ export button holds while viewing; `PolarisWidgets.applySort(rows, options, config)` applies the chosen order and `isCustomSort(options, config)` says whether the operator has moved off the default. `options` is `[{key, label, cmp}]` and **`options[0]` MUST be the widget's historical order** — a stored config carrying no `sortBy`, or one naming an option this build doesn't offer, resolves to it (`sortOption`), which is what keeps every dashboard saved before the control behaving exactly as it did. Build the comparators from `PolarisWidgets.sortCmp` (`newest` / `oldest` / `text` / `high` / `low` / `severity` / `flagFirst` / `then`) rather than writing them per widget: they all sink a row with NO value for the sort key to the bottom **in either direction** (an unknown timestamp is not "the oldest"), and `Array#sort` stability then keeps the feed's own order among ties — which is what makes "Hostname A–Z" hold its places across a wallboard's 30s refresh instead of reshuffling equal rows. **Sort before the export provider and before the clip**: every one of these widgets slices to a Row limit AFTER ordering, so the sort decides which rows are CUT, not just where they sit (the Active Alerts row-limit hint says so instead of promising a severity order). A widget that GROUPS its rows keeps its historical group ordering on the default sort and follows the rows on any other — Down Assets orders groups by size until the operator picks an order, then by each group's leading row; Down Interfaces drops its within-group alphabetical pass the same way, since it would otherwise undo the order just asked for. Picking an option persists through `window.PolarisDashboard.setWidgetConfig(id, key, value)` (dashboard.js), the seam for any header control that writes the saved layout — no seam (a library preview, a published dashboard, an isolated harness) means no button rather than one that silently does nothing. Wired on Active Alerts, Down Assets, Down Interfaces, Storage Forecast and all six top-N widgets (once, inside `_topnBar.renderRows`, which takes `valueNoun` so "Highest CPU first" reads as a sentence about that widget). Menu chrome is the export menu's `.widget-export-menu` class plus `.widget-sort-menu` — deliberately NOT renamed, because `design/css/polaris-ui.css` carries the same rules and this repo does not edit the kit snapshot.
- **`.widget-pill-*` carries a daylight override, and the dark values are deliberately left alone.** The six variants are dark-theme colours — a pale ink on an 18% tint — which is right on indigo and unreadable on cream: measured against the palest ground each theme uses, `widget-pill-amber` scored **1.08:1 in morning and 1.24:1 in noon**, i.e. invisible rather than merely low. A `:is([data-theme="morning"],[data-theme="noon"],[data-theme="afternoon"])` block therefore raises the tint to 30% and swaps the ink for a dark hued tone (one set for all three daylight palettes, worst case 5.2:1). BOTH halves are needed — the theme accents alone only reached ~2.8–4.4:1 on an 18% tint, which is why this is not simply `var(--color-accent)`. The `.recent-item-title .widget-pill-*` rules re-assert the dark inks at the same specificity, so the daylight set is re-stated one level deeper to win inside an alert title. The DARK values are untouched (they clear AA at 3.9–7.7:1) — changing them would move rendering in every theme, which the kit flagged as its own decision. The one still under AA anywhere is `widget-pill-red` on nightfall at 3.94:1, unchanged and open.
- **Minimum-severity display filter (gear).** The same ladder drives a per-widget display filter: `PolarisWidgets.renderMinSeverityConfig(el, config, onChange, hint?)` appends the **Minimum severity** select (options from `SEVERITY_TIERS`, the ONE list the export tiers also read — never hardcode tiers), and `PolarisWidgets.filterByMinSeverity(rows, config[, severityOf])` narrows the fetched rows to those carrying an active alert at/above `config.minSeverity`. Call the filter FIRST in the widget's render — before `applySort`, the row limit, the red guarantee, `setHeaderCount` and `setHeaderExport` — so every number the widget shows agrees with what's on screen; client-side filtering is safe because these feeds are `severityFirst`-sorted server-side. Fall back to `PolarisWidgets.minSeverityEmptyText(config) || <your empty text>` so a filtered-empty widget says "No rows at or above serious severity" rather than "No nodes down". Order in the popover: widget-specific controls → `renderMinSeverityConfig` → `renderNocFilterConfig`. A widget that stored severity some other way seeds the control through `severityTierForRank(rank)` (Active Alerts folds its pre-control `severities` checkbox array that way, keeping saved configs behaving as before).
- **In-place asset slide-in.** `PolarisWidgets.openAssetDetail(id, {tab})` opens the canonical asset slide-over via the global `openViewModal` when present (the optional `tab` is the slide-over tab's `data-tab` key — Active Alerts passes `notifications` so an alert entry lands on the device's Alerts tab; the navigation fallback carries it as `&tab=<key>`) (the dashboard loads `assets.js` + its deps — jspdf/html-to-image/table-sf/integrations — mirroring `map.html`; both `assets.js`/`integrations.js` guard their page-init), else navigates to `/assets.html#view=asset:`. Down Assets wires it on row click (ctrl/meta/middle-click keep the href).
- **Row verbs on an alert.** Two shared deciders, split by what the row IS. `PolarisWidgets.openAssetRow(anchor, {assetId, alertId, alertAcknowledged, onAcknowledged})` is for a row that is a DEVICE carrying an alert (Down Assets): it offers Acknowledge / Open device and falls back to opening the device. `PolarisWidgets.openAlertRow(anchor, {alertId, assetId, acknowledged, onChanged})` is for a row that IS the alert (Active Alerts), where the device is the OPTIONAL part — a `host_metric` or event-triggered alert has no asset, and those rows were inert until 2026-09, so the alerts most likely to need a human were the only ones nobody could act on from the widget listing them. It offers Acknowledge alert… (`alerts:write`, unacknowledged only, via `PolarisAlertAckModal`), Clear alert (`alerts:fullwrite`, `showConfirm` first with the asset Alerts tab's own sentence, toasting what the SERVER did — a no-op clear is not a success) and Open device (only when the alert names one); a row left with just Open device opens it without asking, and one with no verb and no device does nothing rather than opening an empty menu. Both go quiet where the click can't work — `POLARIS_DASH_LOCAL`, or a page without `showRowMenu` / the ack modules — and Active Alerts withholds the `recent-item-link` affordance from a device-less row there rather than claiming a click it can't honour. **A widget that mutates an alert must hold the result over its own refresh**: the feed sits behind a 15s client memo over the route's 10s TTL, so a cleared row comes back and reads as a click that did nothing (Active Alerts keeps per-instance `{acked, cleared}` overrides that only ever remove or annotate a row, folded over every fetched payload until the feed agrees).
- **A widget that WRITES what its own feed reports has two more things to get right, and Active Maintenance is the reference.** Its row verbs (Open schedule… / Disable schedule, both `maintenanceManagement:write`) and its `+ New schedule` button open the Maintenance modal in place, so: (1) **the affordance is withheld wherever the click cannot work** — a library preview (no `.dashboard-widget` shell), the `/dash` wallboard, a page that does not load the modal, or a role below the level the modal's own Save needs. A button that opens an editor whose every save 403s is worse than no button; the route stays the control either way. (2) **A REMOVAL is held locally, but an ADDITION cannot be** — a disabled row goes into a per-instance `dropped` set like Active Alerts' overrides, while a newly created schedule has to come from the server, so the widget calls `PolarisWidgets.invalidateNocSummary()` and refreshes when the modal closes, then **once more past the route's own 10s TTL** (the client memo drop cannot reach the server's cache, and a payload computed before the write will not contain it). Waiting out the widget's 30s timer instead reads as the create having done nothing. A modal close is observed, not awaited: `closeModal` fires no event and `openMaintenanceModal` resolves when the dialog is BUILT, so watch the shared overlay's `class` for `open` leaving. **And a post-write refresh that reaches beyond the widget must survive being off its own page** — `_maintSave` calls `loadAssets()`, which repaints the Assets table; on the dashboard there is no table, and `fetchAssetsPage` threw "Cannot set properties of null" into a silent unhandled rejection after an otherwise successful write until it learned to return early.
- **Role gating.** `requiredPermission: { key, level }` checked client-side via `permAtLeast`; the picker hides disallowed widgets (convenience, not security). **Every widget declares one**, and the key MIRRORS the gate the server already applies to the data it reads — `/dashboard/summary` gates its sections on `assets` / `ipBlocks` / `reservations` read, so those are the keys, not whichever picker category the widget sits in (`assetTypes` is filed under IP Space but reads asset counts, so its key is `assets`). Because both `/summary` and `/noc-summary` filter rather than 403, an ungated widget doesn't leak — it renders "No blocks yet" to a role that simply can't see blocks, which is a false statement about the fleet rather than an empty one. That is the reason to declare the key, and the reason the level is always `read`.
- **Favorites are localStorage, layout is server-side.** Per-widget ★ favorites are a pure client preference (`favorites.js`, entity `"widgetlib"`). The layout itself persists in `UserDashboard` (per-user JSON); PUT debounced 800ms; Zod `LayoutSchema` (v3) validates on the route. Don't pivot the layout to localStorage — cross-device is the explicit expectation. (Sole sanctioned exception: the anonymous Dash wallboard, which has no user to persist against — `POLARIS_DASH_LOCAL` in dashboard.js.)

**When adding a new operator-customizable surface (or a new widget to the existing Dashboard):**
- **New widget on the existing Dashboard:** add `public/js/widgets/<type>.js`; self-register via `PolarisWidgets.register`; include a `renderPreview` with mock data; add the `<script src>` line to `public/index.html` **AND `public/dash.html`** (the Dash wallboard mirrors the widget script list — both files carry a lockstep comment). Wire `requiredPermission` to whatever key gates that data server-side — always, not only when it feels sensitive (on dash it resolves against the readonly role). Give it a `PolarisWidgets.REFRESH.<tier>` timer torn down in `ctx.onUnmount` unless the data genuinely cannot change, in which case say so in a comment. If the widget calls an endpoint outside `/dashboard/*`, also add the path to `API_PATH_ALLOWLIST` in `src/dash/dashServer.ts` or it 404s on the wallboard. No backend or registry changes needed when it reads an existing endpoint.
- **A throw at MODULE scope deletes the widget, silently.** `register()` is called at the bottom of each module, so anything evaluated above it — a `var X = window.SOMETHING` read, a table built from a palette, a constant derived from another global — runs first, and an exception there means `register()` is never reached. The widget is then absent from the registry, missing from the picker, and **pruned from every saved layout that names it** (dashboard.js drops widgets whose type no longer resolves, then persists the pruned layout), with nothing in the UI to say so: one page-level error in a file the page loads with 22 others. That is how `statusSummary.js` lost its `var WC = window.POLARIS_WIDGET_STATUS_COLORS` line in "refactor(frontend): shared status palettes in api.js" and stayed gone for six weeks while `docs/wiki/Dashboard.md` documented it as present. Prefer reading such globals INSIDE the render function; when a module-scope constant genuinely needs one (a tile catalogue, a colour table), declare it explicitly at the top of the IIFE — never rely on a name another widget's IIFE happens to define. `tests/unit/widgetRegistration.test.ts` is the guard: it evaluates every module in `public/js/widgets/` in isolation and asserts each one registered, so the failure names its own file instead of vanishing. It also holds `index.html` and `dash.html` to the same widget script list.
- **New NOC top-N widget (reference: `diskUsage.js`).** The cleanest recent end-to-end example of adding a fleet-ranking widget. Steps: (1) add a feed `getHighest<X>` to `nocDashboardService.ts` returning `TopNRow[]` (windowed DISTINCT-ON / aggregate over the relevant hypertable, hydrate names in ONE `findMany`, take the trailing `assetIds: string[]|null` filter arg); (2) register it in the `NOC_FEEDS` registry (name in `NOC_FEED_NAMES`, gate `assets`/`events`, empty value, runner; optional `flatten` only if the response key differs from the feed name) — the route needs no change; (3) add `public/js/widgets/<type>.js` as a `_topnBar` wrapper passing its feed name to `getNocSummary(opts, ["<feed>"])`, `fillTo:20` + color thresholds (+ `detail` on rows if per-sub-entity like volumes); (4) `<script>` it in `index.html`; (5) the gear gets the shared `renderNocFilterConfig(...)`; (6) add a unit test for the feed; (7) refresh ARCHITECTURE (widget catalog + endpoint shape + service line) and the `nocDashboardService` TOUCHES entry.
- **Shared multi-widget fetch (NOC pattern).** When several widgets read the SAME endpoint on their own refresh timers, don't let each one fetch independently — add a memoized accessor on the registry (`PolarisWidgets.getNocSummary(opts, feeds)` in `public/js/widgets/index.js`: ~15s TTL + in-flight dedupe, keyed per (feeds, filter, limit, samples)) and have every widget call it with only the feed(s) it renders. The backend endpoint (`/dashboard/noc-summary?feeds=`) computes just the requested subset via a feed registry in a dedicated service (`nocDashboardService.getNocSummaryPayload`), per-section permission-filtered like `/summary`, with every (feed, filter, cap[, samples]) result served through a 10s `createTtlCache` (`src/utils/ttlCache.ts`) — the model for caching any read-mostly aggregate endpoint hit by many concurrent viewers.
- **Shared row renderer for near-identical widgets.** The five top-N metric widgets (CPU / Memory / Slowest Response / Packet Loss / Disk Usage) are structurally identical, so the row+bar render lives once in `public/js/widgets/_topnBar.js` (`window.PolarisTopN.renderRows/renderConfig`, reusing the `.util-bar-track`/`.util-bar-fill` bar from blockUtilization). Each widget is a ~40-line wrapper supplying unit / color thresholds / empty text. `renderRows` opts: `fillTo` = red-guarantee mode (on CPU/Memory/Response/Disk): the operator's Row limit (default 20) caps the top-N shown, but every **red** row — at/above the top color threshold — always shows even past the limit; `fillTo` itself is only the fallback count when the config lacks a usable rowLimit. Omit on Packet Loss so the threshold stays a hard filter + rowLimit a plain cap. Rows may carry an optional `detail` string rendered muted beside the hostname (Disk Usage uses it for the mount path); the ellipsizing name cell gets a native `title` tooltip with the full name (+ detail). **An alerting row's bar color comes from its severity, not the widget's thresholds** — `PolarisWidgets.alertSeverityBarColor(sev)` (in `widgets/index.js`, one-for-one with the `alertSeverityPill` palette) wins over `pickColor` whenever the row carries an `alertSeverity`, since the operator's automation threshold is rarely the widget's color band and a yellow bar beside a red `critical` pill reads as a bug. Storage Forecast applies the same override over its days-to-full color. Un-alerted rows keep the value-threshold color. Underscore-prefixed filename = shared helper that registers no widget; include its `<script>` BEFORE its consumers.
- **Embedding Leaflet in a widget (siteMap.js).** The widget body has no intrinsic height in the flex column, and Leaflet throws "Map container is already initialized" if a container is reused. Pattern: set `el.style.position="relative"` + append an inner `position:absolute;inset:0` div as the map container (deterministic box inside the fixed grid-row height); keep `map`/`markerCluster` in the **per-instance render closure** (NOT a module-level singleton like the full map page — a widget can be instanced multiple times); set `L.Icon.Default.imagePath` once behind a module flag; read the basemap theme once from `data-theme` (no MutationObserver); a `ResizeObserver` on `el` calls rAF-debounced `map.invalidateSize()`; and `ctx.onUnmount` MUST `ro.disconnect()` + `map.remove()`. Refresh updates markers in place (`cluster.clearLayers()` + re-add), never recreates the map. Marker/cluster CSS (`.fg-marker`/`.fg-cluster`/`.monitor-*`) lives in both `map.css` and (lifted) `styles.css` since the dashboard page loads only the latter — keep them in sync — `map.css` additionally shares each `monitor-*` rule with the Device Map's basemap legend swatch (`.fg-marker.monitor-x, .map-legend i.monitor-x`), which is what keeps a legend row honest about the dot it explains. The **status legend** itself is the widget's `.sitemap-legend` (an absolutely-positioned child of the widget body, since the widget owns its own overlay layer for the weather controls) and, on the full map page, a `bottomleft` `L.control` with click + scroll propagation disabled (`addStatusLegend` in `public/js/map.js`) — prefer the control on a page-level map: it inherits Leaflet's corner stacking and cannot land a stray click on the map beneath it. A legend row per state the page can actually PAINT, not per state the copied legend happened to carry. Reuses the existing `/map/sites` endpoint; needs the Leaflet `<link>`/`<script>` tags in `index.html`.
- **New customizable surface elsewhere:** model the canvas + picker + per-user storage after this Dashboard. Use a sibling `UserSurfacePreference`-style table keyed on `(userId, surfaceKey)` rather than overloading `UserDashboard`. Reuse `PolarisWidgets.register` for that surface's widgets — the registry is global by design so cross-surface widget reuse is one-line.
- **Don't bake widget positions into seeded defaults** unless you genuinely want every user to see the same starting view — the precedent here is "empty = invitation to customize." Operators have explicitly told us they prefer a clean slate.
- **Auto-save, not a Save button.** Every edit-mode mutation still debounce-saves (800ms); "Done Editing" only exits edit mode and forces a final flush — it is NOT a save-confirm gate. Don't add a confirm step around individual edits; it kills the drag/resize feel.

## Polling methods section (per-stream subtab strip)

**What it is:** A configuration surface that exposes per-stream monitoring settings — polling method (dropdown), credential picker, MIB picker (when polling resolves to SNMP), interval, timeout, and failure threshold (Response Time only). Used inside the integration edit modal (per-class × per-stream), the Assets-page Monitoring Settings modal (Manual Monitoring section), and the asset edit modal's Monitoring tab. Without one canonical layout, three near-identical surfaces drift on label text, sub-row visibility rules, "Inherit" labelling, and DOM id conventions — making the resolver hierarchy harder to read at the UI.

**Canonical implementation:** `_classStreamSubtabHTML(idPrefix, sourceKind, klass, stream, settings, credentials, isPrimary, opts)` in [public/js/integrations.js](public/js/integrations.js). Companion helpers (all in `integrations.js`):
- `_polarisPollingDropdownHTML(id, source, stream, currentValue, opts)` — emits the polling-method `<select>`. Honors `opts.showInherit` (default `true`; pass `false` at the bottom of the resolver hierarchy where there's nothing to inherit from) and `opts.fmgDirectMode` (drives the "FortiGate Direct" vs "FortiManager Proxy" label for FMG sources).
- `_polarisSourceDefaultPolling(source, stream)` — mirrors `defaultPollingForSource()` in `monitoringService.ts`; returns the per-source-kind per-stream default Polaris would resolve to. Used to label the "Inherit" option.
- `_polarisSourceLabel(source, opts)` — the per-source-kind name table: FortiGate Direct / FortiManager Proxy / Active Directory / Entra ID / Windows Server / vCenter / Azure Arc / Manual. A missing entry silently falls through to "Manual", mislabelling every `Inherit (Source …)` option for that type.
- `_streamsForClass(klass)` — returns the per-class stream list. FortiAP omits Storage (APs have no mountable storage); every other class gets all six streams.
- `tabbedBodyHTML(prefix, tabs)` + `wireModalTabs(prefix)` — the tab-strip + body-swap helpers reused for stream subtabs. **Shared globals in `app.js`**: `assets.js` and `integrations.js` each grew a byte-identical private copy (`_renderTabbedBody`/`_wireModalTabs` and `_intRenderTabbedBody`/`_intWireModalTabs`), which is exactly the drift the one pair exists to prevent — both are gone.

**Consumers (parallel surfaces):**
- **Integration edit modal** — class-subtab strip (FortiGates / FortiSwitches / FortiAPs for FMG+FGT; Workstations / Servers for AD/Entra/WinSrv) → stream-subtab strip per class. Uses `_classStreamSubtabHTML(..., isPrimary=true)` for the primary class (FortiGate / Workstations — legacy DOM ids `f-mon-tier-<pollField>`) and `isPrimary=false` with namespaced `f-mon-classecho-<klass>-` prefix for the other class subtabs. **Phase 2 save handler**: each class subtab's stream values serialize independently into `Integration.config.<klass>Monitor.streams.<stream>` via `_readClassStreamSubtabs(klass, isPrimary, includeStorage)` — secondary subtabs no longer echo the primary; each class's own input values are persisted. **Phase 2 load handler**: `_classStreamsBlockFor(klass, opts)` picks the matching `<klass>Monitor.streams` block; `_classSettingsOverlay(flatSettings, classStreams)` overlays the per-stream values onto the flat baseline before passing to each stream subtab so each class renders its own saved settings. `showInherit: true`, `showMib: true` (defaults).
- **Assets page → Monitoring Settings modal → Manual Monitoring section** — no class strip (Manual is class-agnostic). DOM id prefix `f-manual-mon-`. Passes `showInherit: false` (bottom of resolver — nothing to inherit) and `showMib: false` (Manual tier doesn't expose per-stream MIB in this iteration). Renderer at `_monsetManualSectionHTML()` in [public/js/assets.js](public/js/assets.js).
- **Assets page → Monitoring Settings modal → Class Overrides editor (Add / Edit)** — no class strip (manual-scope only, per the Phase 1 narrowing). DOM id prefix `monset-ov-`. Passes `showInherit: true` (class overrides legitimately defer to the integration / manual tier below) and `showMib: true` (per-stream MIB pickers are meaningful here). Renderer at `_monsetOpenOverrideEditor()` in [public/js/assets.js](public/js/assets.js). Sub-row visibility is wired locally — `_refreshOvStreamSubRows()` toggles the per-credtype credential rows (`<pollId>-credrow-snmp` / `-ssh` / `-winrm` / `-http`) and the MIB row (`<prefix>tier-<mibStreamKey>-mib-wrap`) based on each stream's polling-method pick. Per-stream credential save: the helper renders one select per (stream × credtype); the override save handler picks the select matching the chosen polling method and stores it in the per-stream column (`responseTimeCredentialId` / `cpuMemoryCredentialId` / …) the backend expects. Source kind is hardcoded to `"manual"` for the Inherit-option label.
- **Asset edit modal → Monitoring tab** — no class strip (single asset's overrides). DOES NOT use `_classStreamSubtabHTML` because its DOM id conventions diverge from the asset modal's legacy `f-responseTimePolling` / `f-cpuMemoryPolling` / `f-monitorInterval` / etc. ids that `extractAssetEditData()` reads on save. Instead the renderer in `assetMonitoringFormHTML()` ([public/js/assets.js](public/js/assets.js)) builds per-stream subtab bodies inline using the same visual shape (polling-method `<select>` → cred sub-row → MIB sub-row → cadence + timeout → failure threshold on Response Time only) and wraps them with `tabbedBodyHTML("asset-mon-streams", streamTabs)`. `showInherit: true` (the Inherit option here legitimately defers to the class / integration / manual tier above the asset). MIB pickers visible per stream. LLDP + Storage subtabs share the system-info cadence with Interfaces (Asset row carries only 4 cadence columns: `monitorIntervalSec`, `cpuMemoryIntervalSec`, `temperatureIntervalSec`, `systemInfoIntervalSec`) — those two subtabs render a "shared with Interfaces" hint instead of duplicating the inputs.

**Key conventions:**
- **Stream list and order:** Response Time → CPU/Memory → Temperature → Interfaces → LLDP → Storage. FortiAP omits Storage (handled by `_streamsForClass("fortiap")`).
- **Per-stream subtab body shape:** polling-method dropdown → credential sub-row (visible when polling needs auth — `snmp`/`winrm`/`ssh`/`rest_api`/`http`) → MIB sub-row (visible when polling = `snmp` AND `showMib !== false`) → interval input → timeout input (+ failure threshold on Response Time only). A method may add ONE row of its own: the asset edit modal's Response Time subtab renders `f-httpCheckPath-wrap` (the per-asset HTTP-check path override) between the credential row and the interval, shown only while that stream resolves to `http`. Keep such a row inside `refreshStreamCred`'s show/hide pass and HIDDEN rather than removed, so a typed-then-reconsidered value survives a method flip-flop before save — and send it even when hidden, which is how switching away from the method clears a stale override.
- **Inherit-option visibility:** `showInherit: true` is the default everywhere EXCEPT the bottom of the resolver hierarchy (Manual Monitoring section). When false, the `<select>` simply lacks the empty-value option; the first concrete method becomes the default. Routes still accept `null` / empty body fields as "no override"; the UI just doesn't offer it.
- **Inherit-option label format:** `Inherit (Source <SourceLabel>: <ResolvedMethod>)` or `Inherit (Source <SourceLabel>: not delivered)` when the source doesn't deliver that stream by default. The asset edit modal's `_populateAssetMonitorTierBadges` overwrites this with the actual resolved value from `/effective-monitor-settings` (e.g. `Inherit (class override: SNMP)`) once the response lands.
- **ICMP filtering:** `_polarisPollingDropdownHTML` filters ICMP out of every stream except `responseTime` — telemetry / interfaces / LLDP / storage all need a real protocol. The backend `validateStreamPollingMethod()` applies the same filter on writes.
- **Stream-scoped methods live in `_streamAllowedMethods`, not the dropdown helper.** Two methods are restricted by STREAM rather than by source, mirroring the method-level guards in `isMethodValidForStream` (`pollingCompatibility.ts`): `vcenter` is cpuMemory-only, and `http` is responseTime-only (a GET returns a status code and a body — no CPU figure, interface list, sensor reading or mount table). Both are filtered there, AFTER the source intersection, so a new stream-scoped method needs an entry in that function as well as in `_POLLING_COMPAT` — and the backend rejects the pair at write time in `assertPollingCompatible` (tiers) and `validateAssetUpdate` (per asset), so a UI that forgets the filter shows an option that 400s.
- **Source-kind defaults:** `_polarisSourceDefaultPolling` returns `rest_api` for fortimanager/fortigate on CPU/mem/interfaces/temperature, `icmp` for responseTime, `disabled` for LLDP + Storage. AD/Entra/Win/Manual default `icmp` on responseTime, `null` (= "not delivered") elsewhere.
- **DOM id discipline:** stream-subtab inputs use the prefix the consumer's save reader expects. The integration modal's primary subtab uses legacy `f-mon-tier-<pollField>` so `_polarisReadPollingFourStream("f-mon-tier-")` finds them; secondary class subtabs use namespaced `f-mon-classecho-<klass>-` ids that are rendered but never read on save. Manual Monitoring uses `f-manual-mon-tier-` (read by `_polarisReadPollingFourStream("f-manual-mon-tier-")`). Asset edit modal uses bare `f-<pollField>` (read by `_polarisReadPollingFourStream("f-")`).
- **Storage stream MIB:** Storage has no per-stream MIB column on Asset or MonitorClassOverride — `HOST-RESOURCES-MIB` + the vendor disk fallback in `pickDbProfile` covers it without operator input. The helper skips the MIB sub-row for the storage stream regardless of `showMib`.
- **A surface that branches on a stream's polling method reads `_resolvedStreamPolling(asset, stream)` — never `asset.<stream>Polling`, and never a hand-rolled source default.** That column is the per-asset OVERRIDE and is null on almost every asset, so re-deriving from it means the integration tier, the class override and the manual tier are all invisible: the System tab's Storage section used to be dropped from the DOM on a guess (`rest_api` for anything an FMG or FortiGate discovered) and hid itself from the very switches an integration-tier SNMP override had enabled. The resolver prefers the cached `/effective-monitor-settings` walk, then the column, then the shared `_polarisSourceDefaultPolling` mirror. Two consequences for a section that renders this way: **emit the container unconditionally** and decide its CONTENT from the method (`_notAvailableViaPollingHTML` for "this transport can't deliver it", a plain empty-state for "not collected yet" — a device with the stream off must not read as a device with no disks), and **re-render it from `_updateStaleBannersFromEffective`**, since the sync paint happens before the effective walk lands. Hardware Sensors is the reference implementation; Storage follows it.
- **LLDP + Storage cadence at the asset tier (Phase 2):** the Asset row gains its own `lldpIntervalSec` / `storageIntervalSec` cadence columns and `lastLldpAt` / `lastStorageAt` last-touched stamps alongside `lldpPolling` / `storagePolling`. Each rides its own pg-boss queue (`polaris-monitor-lldp` / `polaris-monitor-storage`) on independent cadences resolved from the per-class streams blocks; the publisher in `monitorAssets.ts` checks `last*At + *IntervalSeconds` to decide when to fire. The legacy `collectSystemInfo` still walks both as session-coalesced side effects on a shared SNMP session — `persistLldpNeighbors` (full-replace + 48 h stickiness) and `enqueueStorageSamples` are idempotent against the dedicated queues' double-walks. Cursor mode keeps both on the systemInfo cadence — the dedicated queues are pg-boss-only.

**When introducing a new polling-method surface:**
- **Reuse `_classStreamSubtabHTML`** — don't fork the helper. Pass the right `idPrefix` and `isPrimary` flag so your save reader can find the inputs.
- **Pick the right `showInherit` flag:** `true` everywhere except the very bottom of the resolver hierarchy (where Inherit would be a misleading no-op).
- **Pick the right `showMib` flag:** default `true` works for every tier above Manual today; pass `false` only when the tier deliberately doesn't expose per-stream MIB picking.
- **Pass the correct `source`** so the Inherit label names the actual source ("FortiGate Direct", "FortiManager Proxy", "Active Directory", "Entra ID", "Windows Server", "Manual"). FMG additionally needs `opts.fmgDirectMode` flipped to match the integration's current Direct Polling toggle state.
- **Use `_streamsForClass(klass)`** to enumerate the streams — never hardcode the six names. FortiAP-specific surfaces will automatically drop Storage.
- **Wrap with `tabbedBodyHTML(prefix, streamTabs)`** and call `wireModalTabs(prefix)` after mounting so the tab strip actually swaps bodies on click. Pick a prefix that doesn't collide with other tab strips on the same page.
- **If your surface diverges in DOM id conventions** (the asset edit modal does), build the per-stream body HTML inline using the same visual shape — polling dropdown + cred sub-row + MIB sub-row + interval + timeout — and reuse `_polarisPollingDropdownHTML` for the dropdown itself so the Inherit-label semantics stay consistent.
