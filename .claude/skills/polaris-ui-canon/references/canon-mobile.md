# UI canon — mobile PWA patterns

Verbatim from UI-CANON.md. Each pattern: **What it is** / **Canonical implementation** (`path/file.js → symbol()`, no line numbers) / **Key conventions** / **When adding a new instance**. Read `design/POLARIS-UI-GUIDE.md` first for the portable contract these implement.

## Mobile bottom sheet

**What it is:** A modal slide-up panel anchored to the bottom of the viewport on the mobile SPA. Dismissed by tapping the scrim, tapping the X button, or swiping the sheet down. Used for the Device Map site detail, asset interface drilldown, reservation edit + create-by-IP, subnet reserve, topology node detail, the per-asset alerts sheet, the full asset detail screen, a list's "Sort & filter" picker, and the **network IP sheet** (`PolarisNetworkSheet` in [public/js/mobile/subnet-detail.js](public/js/mobile/subnet-detail.js)) — a network's addresses opened over the Networks tab instead of on a page of their own. That last one is the pattern for a sheet OTHER sheets stack on: it sits at z-index 890/891, under the asset sheet (900) so its "Open asset" lands on top and under the generic `.sheet` (1000) so the Reserve / Edit sheets it opens stack over it; it is anchored above the navbar like the asset sheet so the tabs stay reachable, and it closes itself on `hashchange` so a tab tap never leaves it hanging over another tab.

**Canonical implementation:** `openSiteSheet()` in [public/js/mobile/map-tab.js](public/js/mobile/map-tab.js) + matching `closeSiteSheet()` — use this for the common two-state (open/dismiss) sheet.

**Three-state minimizable variant:** the asset detail sheet (one fixed `height: 80vh`, not content-sized — 2026-10-27, by request: a short page such as Storage shrank the sheet as the operator paged) (`PolarisAssetDetail.open(id)` in [public/js/mobile/asset-detail.js](public/js/mobile/asset-detail.js)) extends the pattern with a **peek** state for content-heavy sheets the operator wants to keep open while using the page behind. Scrim tap → minimize (slides the sheet down to its header band, measured into `--asset-peek-y`, and hides the scrim so the page behind is reachable); peek-bar tap → expand; close button → dismiss. **Two-stage swipe-down:** the first swipe-down from expanded snaps to peek, the second swipe-down from peek dismisses. **Swipe-up from peek re-expands** (in expanded state baseline is 0, so upward gestures fall through to native scroll). Wired through `attachSwipeToDismiss`'s `onSwipeDown` / `onSwipeUp` opts (override the default translate-100% animation and the default release-for-native-scroll respectively) plus `baselineTranslate` opt (so drags from a peeked position continue from the peek offset instead of jumping back to natural). Minimize never tears down the DOM, so charts/scroll/per-feature state survive. **The handle + header are one pinned band** (`PolarisTabs.pinSheetHead(sheet)` in [public/js/mobile/tabs.js](public/js/mobile/tabs.js) → `.sheet-pinned-head`, 2026-10-13; every sheet with a header row uses it — see the bottom-sheet section): both header rows — the toolbar (page back / forward, then screenshot, refresh and close) and under it the status dot + name (edit menu) at full width, or a sub-page's title over its asset's name (`paintTitleRow`) — stay at the top of the scrolling sheet however far down the operator is, and a scrolled sheet minimized to peek shows that band rather than whatever was mid-scroll; dragging the handle works from any scroll position, since `attachSwipeToDismiss` accepts a handle drag regardless of `scrollTop`. **The phone's Back button walks the same states** (2026-10-27): while open the sheet holds ONE history entry of its own (`pushSheetEntry` — `pushState({polarisAssetSheet: true})` at the SAME url, so no hashchange and no route render). Popstate (`onPopState`) reads a pop of that entry as Back, nearest thing first: a sheet stacked over the asset sheet closes (`closeStackedSheet` — the newest `body > .sheet` after `#asset-sheet`, closed by clicking the `.scrim` appended right before it, so every child sheet's own teardown runs: the edit menu and edit sheets, the confirms, the acknowledge-note prompt), then the page history steps back (`pageBack`, the header's ‹), then expanded → peek, each followed by re-pushing the entry; then peek → `dismiss()` whatever page shows. The history has ONE entry however many pages deep the sheet is: each Back handles one step and puts the entry back, so the browser's own stack never grows with the pages. Tap / swipe minimize and expand leave the entry alone, so Back from a peek always closes. The X and the second swipe-down go through `closeSheet()`, which takes the entry back off (`history.back()`, its popstate counted in `_popsToIgnore`). A forward hash navigation (a navbar tap — Chrome fires popstate for it too) is told from Back by the url: the entry sits over one with the same url. An entry left behind by a sheet closed from another route is stepped over when Back lands on it. **An in-app back control that calls `history.back()` must call `PolarisAssetDetail.historyBack()` instead** (search's arrow in app.js `closeSearch`, the detail chevron in details.js `wireBack`): with the sheet open over the page its entry is on top, and a bare `back()` would minimize the sheet rather than navigate — the helper does `go(-2)` and re-pushes the entry on the page it lands on. The listeners are installed once per page (`window.__polarisAssetSheetPop` / `__polarisAssetSheetHash`) because the unit tests evaluate the file repeatedly. Pinned by `tests/unit/mobileAssetSheetBack.test.ts`. Capped at 80vh (vs. the generic `.sheet`'s 90vh) and anchored at `bottom: var(--navbar-h) + safe-area` so both expanded and peek states stop at the navbar's top edge instead of covering it. The bottom nav (`.m3-navbar`, z-index 950) sits above the asset sheet (901) and its scrim (900) — so the navbar stays visible + tappable while the asset is open — but below the generic `.scrim`/`.sheet` (1000/1001), so deep drilldowns still take the full screen. Model new minimizable sheets on this; keep simple sheets on `openSiteSheet`.

**The asset sheet is a page history** (2026-10-27, by request): it shows ONE page at a time — the asset, or a page opened from it: the Dependency Tree (`deptree`, the hero's first button, every asset; re-fetches `/dependencies` on every visit), SD-WAN, IPsec (`ipsec`, a button directly above Interfaces gated like the desktop IPsec tab — Fortinet firewall + a non-empty read, drawn from `_ipsecCache`, re-read on Refresh; the Interfaces list drops each tunnel-type interface whose name is in `systemInfo.ipsecTunnels` and points at the page, mirroring the desktop's `_renderInterfacesTable`), the ARP / MAC / Wireless tables, an interface, the alerts list, Storage, a volume, a drive, or another asset (`open(id)` on an open sheet, which every in-sheet asset link and neighbor pivot calls). Opening one goes FORWARD (`goToPage`, dropping any pages ahead, as a browser does); the header's ‹ / › (`pageBack` / `pageForward`, `#asset-sheet-back` / `#asset-sheet-fwd`, disabled at the ends, aria-labelled with the page they lead to) walk the list; a fresh open of a closed sheet starts a new one. A page is `{ kind, assetId, title, sub, … }`; `PAGE_KINDS` says how each kind draws (into a FRESH `.asset-page` element inside `#asset-host`, so a listener it delegates goes with it — the alerts and table pages delegate), refreshes (the header's Refresh and pull-to-refresh: `refreshPage`) and is left (`leave` clears the page's late-load state: `_tableSheet`, `_sdwanSheetState`, `PolarisMobileAlerts.close`). Each page keeps its scroll offset. The asset page is redrawn through `loadAsset` on return (its sections' open state lives in `mountState`); `_pageSeq` guards a load against a page no longer on screen, since two pages of one asset share `_openId`. These used to be sheets stacked over the asset sheet; they are pages now, so a new drill-down from the asset is a `PAGE_KINDS` entry and a `goToPage` call, never another `.sheet`. Only forms and questions (edit sheets, confirms) still stack. The peek band is the pinned head MEASURED (`peekBandPx`), since the title row's height follows the page. Pinned by `tests/unit/mobileAssetSheetBack.test.ts` (page history), `mobileAssetStorage.test.ts` and `mobileAssetIpsecDepTree.test.ts`.

**Key conventions:**
- DOM shape: one `.scrim` and one `.sheet` element, both appended to `document.body` with unique IDs (`<feature>-sheet-scrim` + `<feature>-sheet`). Close = `remove()` both.
- The sheet's first child is `<div class="sheet-handle"></div>` — the small grabber bar that both signals draggability and is the always-on swipe-dismiss start zone.
- Next comes a `display:flex` header row with the title block on the left and an icon `<button class="icon-btn" id="<feature>-sheet-close" aria-label="Close">` carrying `<svg><use href="#i-close"/></svg>` on the right.
- Three close paths, all calling the same close function: `scrim.addEventListener("click", closeXxx)`, the close button click, and `PolarisTabs.attachSwipeToDismiss(sheet, closeXxx)`. The swipe helper lives in [public/js/mobile/tabs.js](public/js/mobile/tabs.js).
- CSS comes from [public/css/mobile.css](public/css/mobile.css) — the `.scrim`, `.sheet`, `.sheet-handle`, `.sheet-title` rules. Don't invent new container classes; reuse these so the swipe helper's transform composes correctly with the `sheet-in` open keyframe.
- Forms inside the sheet keep their native gesture handling — the swipe helper opts out of `input`, `textarea`, `select`, and `[contenteditable=true]` so iOS text-cursor drag and selection handles work.
- **A sheet is also how the phone asks a question.** `window.prompt` / `window.confirm` are unstyled and suppressed outright in some installed PWAs, which leaves an operator unable to finish an action with no visible reason why — so `promptAckNote` and `confirmClear` in [public/js/mobile/alerts.js](public/js/mobile/alerts.js) are `.sheet`s stacked at z-index 1010/1011 over whatever opened them, and they follow `showPrompt`'s null-vs-empty contract (dismissed resolves `null`, a blank REQUIRED field is refused with a stated reason rather than a bare red border). Reuse those two rather than reaching for the native dialogs; the More tab's fleet-wide alerts list delegates to the same note prompt, which is what keeps the `requireAckNote` rule in one place.
- **Mobile SD-WAN charts are intentionally simplified.** The asset detail sheet's SD-WAN page (`renderSdwanPage` in [public/js/mobile/asset-detail.js](public/js/mobile/asset-detail.js)) renders the per-member **Latency / Jitter / Packet-loss** numeric charts (driven by `loadSdwanPerfSla`), but it deliberately omits the desktop SD-WAN tab's **rule member-selection categorical timeline** — the mobile chart helper is numeric-only, so the page shows each rule's *current* selected member instead of its failover history (see the "Out of scope for v1" header comment in `asset-detail.js`). When porting a categorical/timeline chart to mobile, expect to fall back to a current-state list rather than reusing the numeric chart helper.
- **Current-state table pages share one shell.** The hero's "View ARP Table" (firewall) / "View MAC Table" (switch) / "View Wireless" (monitored access point) buttons sit below the SD-WAN button and are driven by `TABLE_BUTTONS` in [public/js/mobile/asset-detail.js](public/js/mobile/asset-detail.js); the device classes are the desktop's tab conditions and must move with them. All three are pages of the asset sheet (`PAGE_KINDS.arp` / `mac` / `wireless`) drawn by `renderTablePage()` (`#table-sheet-controls` / `-meta` / `-body` in the page element, one delegated click handler for `.tbl-group-head` collapse; a `[data-open-asset]` link is the document-level `onAssetLinkClick`'s, which opens that asset a page forward) and guard late responses with `beginTableLoad()`'s token. The title is the header's, Reload is the header's Refresh. The filter row scrolls with the table (as a page it is not part of the pinned band). Groups start collapsed past 40 rows unless a filter is typed. The Wireless page reuses `_systemInfoCache` on open and re-fetches only on Refresh, and leads its body with `wirelessMeshRoleHtml` — the desktop strip's Mesh root / Mesh leaf label (`_wirelessMeshRoleChipHTML`), same two signals, with the tooltip's leaves and parent serial spelled out inline because a phone has no hover; change one, change both. A fourth table belongs in `TABLE_BUTTONS` + its own loader, not a second shell. Pinned by `tests/unit/mobileAssetTableSheets.test.ts`.
- **Storage is a page, and the only physical-drive view on the phone.** "View Storage" (`.asset-storage-entry`, between the Interfaces section and Discovery sources, on EVERY asset — the page explains an empty answer) opens `renderStoragePage`: the storage stream's volumes (`system-info` `storage` rows; `.storage-vol`, a `.storage-bar` toned `.warn` / `.crit` at the desktop's 75 / 90 %, a Poll 1m mark from `monitoredStorage`), and on an Unraid / TrueNAS / Proxmox host its pools as arrays (`GET /assets/:id/virtualization` → `virtualization.pools`; `.pool-card`, groups, `.pool-drive` rows), a pool's own storage row NOT repeated as a volume; on a vCenter host the datastores' type and backing ride the volume line. An unhealthy array starts open, a healthy one closed (the desktop's Pool devices rule); the health tests (`healthClass`, `memberUnhealthy`, `poolUnhealthy`, `poolScanText`) are the desktop's `_storageHealthCell` / `_poolMemberUnhealthy` / `_poolScanText` word for word — change both. A volume opens `renderVolumePage` (figures + used % from `GET /assets/:id/storage-history`), a drive `renderDrivePage` (rows the platform does not report are left out). The line under the button (`paintStorageSummary`) counts arrays, drives, volumes and degraded arrays from the asset row's pools and the system-info volumes. Normal usage is `--md-sev-info`, never `--md-primary` (terracotta on daylight read as a warning). No other device reports physical drives: the page says so rather than inventing them. Pinned by `tests/unit/mobileAssetStorage.test.ts`.
- **An action can live IN a General row, not only in the hero.** The firmware upgrade (business rule 87) sits in the switch / access point / firewall's **OS** row (`FW_ELIGIBLE` in `public/js/mobile/asset-detail.js`; firewall since 2026-10-06): `osRowValue` renders the version plus an `#asset-fw-slot` that `loadFirmwareRow` fills from `GET /assets/:id/firmware-upgrade` (assets:read) — the button at `assets:write` (rule 43(g)), a muted "available — needs Read-Write on Assets" line below it, the progress line while a run is live. The confirm is a stacked `.sheet` at 1010/1011 in `confirmClear`'s shape (`confirmFirmwareUpgrade`, a Promise resolved true / false, closed by `dismiss()` too), then "Upgrade started" and `watchFirmwareRun` polling `api.assets.firmwareUpgradeRun` (the per-asset run read) every 3 s, stopped by `dismiss()` and by any other asset opening. Primary image only; the backup choice, run history and log stay on the desktop card. Booking a flash for later (business rule 93) is the SAME sheet: `fwConfirmBodyHtml(asset, fw, { mode, existing, defaults })` adds a "Schedule for later" box (`#fw-confirm-schedule`) revealing a `datetime-local` + recipients and turning the verb into "Schedule" (modes as on desktop: `choose`, `schedule-only` for `blocked` — the Upgrade verb shows there too, box ticked and disabled — `change`, and `now-only` while a booking exists); `confirmFirmwareUpgrade` resolves `{ now: true }` or `{ schedule: { scheduledFor, notifyEmails } }`. A pending booking draws `fwScheduleLineHtml` in the row with Change / Cancel at `assets:write`. Pinned by `tests/unit/mobileFirmwareUpgrade.test.ts`. The OS row also carries an inline `#asset-fw-badge` — "✓ Up to date" (`fwBadgeHtml`) ONLY when the availability is `up-to-date` AND `vsPrimary === "current"` (the device runs exactly the platform's primary image), never for a device past it or one the Repository cannot place.
- **The reboot verb lives in General's Uptime row** (business rule 115), the same row-action pattern: `uptimeRowValue` renders the uptime (`uptimeSecondsNow` — last reading + elapsed, frozen while down; the desktop System tab's rule) and an `#asset-reboot-slot` that `loadRebootRow` fills from `GET /assets/:id/reboot`: "Reboot…" at `assets:write` (`canFlashFirmware`), "Schedule reboot…" plus the reason when only a booking is possible (`RB_SCHEDULABLE`), the server's reason otherwise. The row is always rendered so the slot exists, and `dropEmptyUptimeRow` removes it when the device reports no uptime and nothing can reboot it. The confirm is a stacked sheet at 1010/1011 (`confirmReboot` / `rbConfirmBodyHtml`, the firmware sheet's modes and "Schedule for later" fields) whose verb stays disabled until "I understand this device will go down" is ticked; `watchRebootRun` polls the run every 5 s and is torn down by `dismiss()`. Pinned by `tests/unit/mobileUptimeReboot.test.ts`.

- **Editing an asset is a menu, then a sheet per desktop tab.** The asset's NAME in the asset sheet header is a button (`#asset-sheet-name-btn`, disabled until the row loads, inert while peeked) that opens `PolarisAssetEdit.openMenu` in [public/js/mobile/asset-edit.js](public/js/mobile/asset-edit.js) ("Asset actions"). The menu's first group is the desktop header's device verbs, `.ae-menu-action` rows (NOT `.ae-menu-item`, which is the tab list the parity test reads): **Discover Now** (`POST /assets/:id/rediscover`, `assets:write`; the row only describes — the server's 400 reason comes back as an error snackbar) and **Reboot** (drawn only when the caller passes `opts.onReboot`; starts "Checking…", then `rebootRowState` over `GET /assets/:id/reboot` fills it, disables it with the reason, or drops it on `unsupported`; a tap closes the menu and hands the answer to asset-detail.js's `startRebootFlow`, so there is one reboot confirm sheet). Then a ruled-off group with one `list-item` per tab of the desktop `openEditModal` (General / Monitoring / Maintenance), in its order, an entry the viewer can't use drawn disabled with the reason. Each entry opens a stacked generic `.sheet` (`#asset-edit-sheet`) that re-reads the asset, renders the phone build of that tab, and saves ONLY its own fields through the partial `PUT /assets/:id` — never the other tabs' (a save of all three, as the desktop does, would need every sheet's DOM at once). Rules the desktop enforces on save are kept, asked as 1010/1011 confirm sheets: rule 40(i) duplicate IP and rule 103 confidence (General), rule 10 status gate (Monitoring). Vocabulary comes from the desktop's own files, never a copy — `polling-methods.js` for the Monitoring dropdowns, `monitor-down-after.js` for the Declaring Down sentence, `assets-maintenance.js` (loaded on first use) for the ad-hoc window and the server clock; the few constants that are copied (`UNMONITORABLE_STATUSES`, `DESCRIPTION_DEVICE_TARGETS`, `isAssetTypeLocked`, the type seed) are parity-tested. Long forms put field labels ABOVE the field (`.ae-sheet .tf-outlined .lbl`) because the notched label paints `--md-surface` as a box on frosted glass, and the sticky Save row (`.ae-footer`) is opaque: a backdrop blur on it does nothing, since the sheet's own `backdrop-filter` makes the sheet the backdrop root. Desktop-only by design: Delete Asset, creating a registry tag, agent install/upgrade, the merge review, the other-asset-overrides list. Pinned by `tests/unit/mobileAssetEdit.test.ts`.

- **Another asset's name is a link that opens its sheet** (2026-10-27). Draw it with `PolarisAssetDetail.linkHtml(id, name)` in [public/js/mobile/asset-detail.js](public/js/mobile/asset-detail.js) → `<a class="asset-link" data-open-asset>` (escaped text when `id` is empty; modules that may load without asset-detail.js wrap it in a local `assetNameHtml` that falls back to `escapeHtml`). Never wire a click per surface: ONE capture-phase document listener (`onAssetLinkClick`) opens it, so a row handler underneath (a collapsible IP row, a table group head) never sees the tap; when the link sits in a sheet stacked ABOVE the asset sheet it first clicks that sheet's `[aria-label="Close"]` button (so the sheet's own teardown runs — every sheet header's close carries that label), and it leaves only `#asset-sheet` itself and the `.network-sheet` (891, below) in place. Users: ARP / MAC / Wireless matched device (`matchedDeviceHtml`), the interface sheet's LLDP neighbor, the firmware row's HA primary and group gate (`fwSlotHtml`), the site sheet title, the topology node sheet title (inventory roles, and a path-overlay `endpoint` whose node id is the asset id), the network sheet's Hostname detail row, and the per-asset alerts sheet subtitle when the caller passes `linkName: true` (the Assets list; from the asset sheet it is the open asset). The open asset's own name (header, General, confirm sheets) is never a link, and confirm sheets stay inert. Not linked for lack of an id: sightings (`fortigateDevice` text), Last seen port / AP, a network's `fortigateDevice`, an unmatched LLDP neighbor. Search rows keep their own row targets. Pinned by `tests/unit/mobileAssetNameLinks.test.ts`.

**When adding a new instance:**
- Mirror the DOM shape — `.sheet-handle` first, header row with `icon-btn` close button second.
- Wire all three close paths: scrim click, close-button click, and `PolarisTabs.attachSwipeToDismiss(sheet, closeXxx)`.
- The close function `remove()`s both the scrim and the sheet by ID; idempotent so double-fire from a swipe finishing while the user also taps scrim is safe.
- If the sheet is scrollable, the swipe-dismiss helper handles "scroll first, dismiss only when at top" automatically — no extra wiring needed.
- **Pin its header**: call `PolarisTabs.pinSheetHead(sheet)` (guarded — `if (window.PolarisTabs && PolarisTabs.pinSheetHead)`, since unit tests stub `PolarisTabs`) right after the markup lands. It wraps `.sheet-handle` + the element right after it into a sticky `.sheet-pinned-head`, so the title and close (and whatever buttons the row carries) stay reachable from the bottom of a long sheet; `{ also: ["#id"] }` pins further direct children with them (no caller today; the table filter row used it until the tables became pages of the asset sheet). A sheet that REPAINTS its innerHTML calls it again after each paint (Sort & filter does); it is idempotent and attaches its scroll listener once. The band bleeds to the sheet edges (`margin: 0 -24px`, matching `.sheet`'s 24px pad — a sheet with other side padding needs its own override), is `display: flow-root` (2026-10-27: otherwise the handle's 12px top margin collapses through the band, which then rests 12px down and jumps to `top: 0` on the first scroll — the header "shifted up"), and is transparent ALWAYS (2026-10-27, by request: the old opaque `--md-surface` fill on `.scrolled` read as the header "losing its transparency" the moment the body moved). Instead the body FADES OUT under it — the lists' `.list-sticky-head` treatment: `sheetFade` in tabs.js (run from the same rAF-throttled scroll listener that toggles `.scrolled`, and on every `pinSheetHead` call) sets `--fade-from` / `--fade-to` on each sheet child after the band, in that child's own coordinates — clear down to `SHEET_FADE_CLEAR_PX` (12) above the band's bottom edge, opaque `FADE_LEAD_PX` (24) below it, both capped at `scrollTop` so a sheet at rest is unmasked — and mobile.css masks `.sheet > .sheet-pinned-head ~ *` with them. Scrolled text therefore never reads through the buttons. A backdrop blur inside a sheet still does nothing (the sheet's own `backdrop-filter` makes it the backdrop root). An html-to-image capture of a sheet body must pass `style: { maskImage: "none", webkitMaskImage: "none" }` or a scrolled capture prints the fade (`screenshotSheet` does). Users today: the asset sheet (its band carries every page's title — interface, SD-WAN, the tables, alerts, Storage), the network address sheet, the Assets list's per-asset alerts sheet, the edit menu and every edit sheet, the site sheet, Sort & filter and chat history (pinned by `tests/unit/mobilePinnedChrome.test.ts`). Short confirm sheets (acknowledge, clear, firmware confirm, push offer, notify-me) don't scroll and skip it.

## Mobile pull-to-refresh

**What it is:** Touch-pull-down on a mobile tab or detail page to re-fetch its data. MD3-style: only a small circular puck moves, body content stays put. The puck rotates with pull progress, flips primary-tinted past the trigger threshold, spins while the caller's onRefresh promise is in flight.

**Canonical implementation:** `PolarisTabs.installPullRefresh(scrollEl, onRefresh)` in [public/js/mobile/tabs.js](public/js/mobile/tabs.js). Wired into the route lifecycle by `installPtrForSpec(spec, ctx)` in [public/js/mobile/app.js](public/js/mobile/app.js) — every route change releases the prior handle + installs a fresh one if the new spec has `onPullToRefresh`.

**Key conventions:**
- Tab specs and detail specs opt in by exposing `onPullToRefresh(ctx)` that returns a Promise. The PTR puck spins until the promise settles; sync returns / non-promises get a 600 ms held-puck fallback.
- Optional `enablesPullToRefresh(ctx)` predicate disables install entirely for one route within a multi-page spec (the More tab uses this to skip its static root menu while still PTR-ing the blocks / subnets / events sub-pages).
- Only tracks a gesture that starts with `scrollEl.scrollTop === 0` — pulling from mid-scroll is left to the browser as normal scroll behavior.
- Form controls (`input`, `textarea`, `select`, `[contenteditable=true]`) opt out so iOS text-cursor drag still works inside any forms on the page.
- Click suppression is left to the browser: a touchmove past ~10 px already cancels the underlying button's `click`, so no `preventDefault` is needed — listeners stay `passive: true`.
- `.app-body` carries `overscroll-behavior-y: contain` so iOS rubber-band doesn't compete with the pull gesture.
- CSS (`.ptr-indicator`, `.ptr-circle`, `.ptr-svg`, `.ptr-indicator.ready`, `.ptr-indicator.refreshing`) lives in [public/css/mobile.css](public/css/mobile.css).
- Skipped on routes where it makes no sense or where touch is owned by another library: Map tab (Leaflet captures touch), Topology tab (Cytoscape captures touch), Site detail (delegates to Map), Search tab (results are query-driven), More root menu (static), Block detail (placeholder), Login.

**When adding a new instance:**
- Define `onPullToRefresh(ctx)` on the tab or detail spec. Return the Promise from the same data-load function the topbar Refresh button uses (or equivalent) — don't fork a separate refresh path.
- The spec's render-time DOM must still be present when the promise resolves; loaders that target `getElementById` should be safe because the user can't navigate away during the PTR gesture without releasing first.
- Whenever the refresh action has variant behavior depending on user role / route parts (e.g. More's per-sub-page dispatch), branch inside `onPullToRefresh` rather than inside the install wiring. Use `enablesPullToRefresh` only for "no PTR at all on this route."
- **A route that redirects must redirect a tick late.** `routeChanged` installs PTR for a spec AFTER that spec's `render()` returns, so a `render()` that synchronously `PolarisRouter.go`es elsewhere has its own (absent) PTR installed over the destination's — silently releasing it. The `#subnet/<id>` shim in subnet-detail.js defers its redirect with `setTimeout(…, 0)` for exactly this.

## Mobile list toolbar (filter + sort)

**What it is:** The row above a list tab's chips: a filter field and a sort chip, and behind the chip a "Sort & filter" bottom sheet carrying the sort column, its direction, and any filter the chip row has no room for. On the Alerts, Assets and Networks tabs.

**Canonical implementation:** `window.PolarisListControls` in [public/js/mobile/list-controls.js](public/js/mobile/list-controls.js) — `toolbarHTML` / `wireToolbar` / `updateSortChip` / `openSortSheet` / `loadPrefs` / `savePrefs`. Consumers: [public/js/mobile/assets-tab.js](public/js/mobile/assets-tab.js) (server-side), [public/js/mobile/networks-tab.js](public/js/mobile/networks-tab.js) and [public/js/mobile/alerts-tab.js](public/js/mobile/alerts-tab.js) (client-side).

**Key conventions:**
- **The module draws and reports; the tab does the work.** Where the work runs is decided by the list, not the control: a PAGED list (Assets) must sort and filter server-side, because a client sort only orders the pages already loaded; a list that is loaded whole (Networks, the same `limit: 10000` the desktop page fetches) sorts in the browser.
- **A server-side sort offers only keys the route accepts.** Assets' sort keys are the route's `ASSET_SORT_COLUMNS` and its status values `monitorClause`'s cases; `tests/unit/mobileAssetsSortFilter.test.ts` reads both out of `src/api/routes/assets.ts` and fails on a key the server would 400.
- **A server sort that orders a ranked value by its text is not offered.** The alerts route sorts `severity` as a string ("warning" above "critical"), so the Alerts tab loads the active list whole (one fetch at the route's 500 cap) and ranks severity in the browser by `PolarisMobileAlerts.sevRank`; its severity FILTER is by rank too, so Critical catches `error`. When more are active than loaded, the count line says `newest N of M active` rather than reading as complete. Its **region scope** (My regions / All regions, offered only to a viewer whose `user.regions` is non-empty, default mine) narrows the same way, on the phone. "Mine" matches the desktop Active Alerts widget (`getRecentAlerts`): an alert whose snapshotted `regionTags` share one of mine, OR a system alert with no `assetId` — NOT an alert on a device carrying no region tag (keeping those, as the server's permissive `regionScopeWhere` does, filled My regions with every untagged device in the fleet; fixed 2026-10-06). The route's `region` param is `hasSome` only, which would drop the device-less alerts, hence client-side. A scope shown by default is still named on the chip (`Time · My regions`). Above the toolbar sits a **severity breakdown** (`renderSummary`, `.sev-summary` / `.sev-tile`): one tile per rank with something in it, counting the rows every filter EXCEPT severity leaves, so the numbers hold still while the operator taps; a tile toggles the same `severity` pick the sheet edits (via `toggleValue`), and a picked tile with a zero count stays drawn so it can be un-picked. The pick DEFAULTS to Critical + Serious + Warning (`["5","4","3"]`); the prefs key is `polaris-mobile-alerts-list-v2` because the earlier key already held a saved empty pick that `loadPrefs` would have kept over the new default — **changing a list default means bumping its prefs key**, or every viewer who has used the list never sees it.
- **Reuse the desktop's comparators.** Network order is `TableSF.prototype._ipNum` — mobile.html loads table-sf.js for that one function rather than carrying a fourth IP comparator.
- **Choices apply as they are tapped.** The sheet is a picker, not a form: no Apply button to forget. Tapping the selected column again flips its direction; a new column takes its own `defaultDir` (Utilization and Last seen start descending).
- **A filter hidden in the sheet is named on the chip** (`Name · Down`, chip `selected`) — a list narrowed by something the operator can't see reads as missing data. A multi pick names up to two (`Name · Down, Missed`) and counts beyond that (`Name · 3 statuses`), since the chip shares its row with the filter field.
- **A sheet filter can be multi-select** (`multi: true` on the filter spec; its value is an array). Each tap toggles one value; the `""` option ("Any") reads selected while nothing is picked and clears the pick. **Picked chips are drawn first, in pick order, then the rest as listed** — "Any" stays in front of them so the clear button never moves, and an un-picked chip returns to its listed place. Assets' Status filter is one: the array rides `monitor` as a CSV, which the route already ORs clause by clause. `loadPrefs` carries a saved single-string value over as a one-item pick for a key whose default is an array.
- **Sort / direction / sheet filters persist per viewer; the filter TEXT does not** — a stale term hiding rows on the next visit reads the same way. Storage is guarded; blocked storage falls back to the defaults.
- **The field is a funnel (`#i-filter`), never the magnifier.** The app-wide search magnifier sits in the top bar directly above it on every page; two magnifiers read as the same control twice.
- **Assets carries the desktop's view tabs above the toolbar** (2026-10-13, `viewTabsHTML` / `applyViewState` / `toggleFavorite` in [public/js/mobile/assets-tab.js](public/js/mobile/assets-tab.js)). It reads the SAME layout as the desktop strip (`api.tableTabs.get("assets")`, re-read on every render and pull-to-refresh) and draws it as MD3 secondary tabs (`.view-tabs`, underline, never chips, so it cannot read as a second type-filter row). The phone's pick is its own (`polaris-mobile-assets-view`, seeded from the layout's `activeId`) and is never PUT back. The tab's `sfFilters` map onto the list route through `applyViewState`, a MIRROR of the filter half of `_buildAssetsQuery` + `_pushAssetText` in `assets.js`, which mobile.html does not load; `tests/unit/mobileAssetViews.test.ts` lifts the two desktop functions out of assets.js and fails when the mirror disagrees for any state, so a column added to the desktop query must be added here too. The phone's own controls then OVERRIDE the field they speak to (type chip → `assetType`, status pick → `monitor`, sheet sort → `sortBy`; "Recently added" means "no override" while the tab sorts, and the chip names the tab's sort). Favorites are the tab's `favoriteIds`, sent as `favoriteIds` so they float server-side. A star tap is optimistic, then RE-READS the layout and PUTs the whole blob with only that tab's `favoriteIds` changed (so a desk-side edit since the list loaded is kept), and reverts on failure. The cap is `MAX_TAB_FAVORITES` (500). A tab whose `favoriteIds` is `null` (predates per-tab favorites) is written as an array on the first phone star, which ends the desktop's one-shot legacy seed for it. **The tab's own filter is removable from the phone** (2026-10-15, `resetChipHTML` / `viewResetTarget` / `resetViewFilter`): the phone's controls only narrow ON TOP of the tab, so without this a filter built at the desk could not be undone on a phone. A `#assets-reset-filter` chip leads `#assets-chips` whenever the showing tab is not already at its reset target — the tab's `defaultState` snapshot when it pins a base ("Reset filter", mirroring assets-tabs.js `resetToDefault`), otherwise `sfFilters: {}` with the sort KEPT ("Clear filters", mirroring the desktop's `_assetsSF.clearFilters()`). A tap uses the favorites write path: re-read the layout, set only that tab's `state`, PUT the whole blob, then `setViews` + reload; a failure snackbars and repaints the chip enabled. It resets the TAB only — the phone's search text, type chip and status picks have their own clears. `renderViewTabs` repaints the chips, so the chip follows tab switches and resets. No tabs, or no `api.tableTabs`, means the plain list: no strip, no stars. **The strip, the toolbar and the type chips are ONE pinned block** (`.list-sticky-head`, sticky at the top of `.app-body`, the scroller) so they stay in reach at the bottom of a long list — and so are the Alerts tab's severity tiles + toolbar + state chips and the Networks tab's toolbar + status chips; it takes the `.m3-topbar` treatment — no fill, a bare `blur(20px)` on `::before`, no `saturate()` — because it sits right under that bar on the page glow. A list that gains the same need wraps its controls in the same class. **On a page with that block the list also runs under the TOP BAR and fades out** (2026-10-15): `.app:has(> .app-body > .list-sticky-head)` pulls `#topbar-slot` down over the body (negative margin, `z-index: 6`) and pads `.app-body` by `--topbar-h`, so the bar's blur has the list behind it and reads as the same glass as the block (before, it had only the glow and looked solid beside it). The block keeps `top: 0` — a sticky box pins inside the scroller's padding, and a `top` of the bar's height pinned it a bar too low; the absolutely placed PTR puck is dropped by the bar explicitly. Every element after the block carries a `mask-image` gradient, transparent at `--fade-from` → opaque at `--fade-to`, which `PolarisTabs.installListFade` ([public/js/mobile/tabs.js](public/js/mobile/tabs.js), installed once on `#app-body` by app.js `renderShell`) re-places in the element's own coordinates on every rAF-throttled scroll: transparent at the body's top edge, opaque 24px (`FADE_LEAD_PX`, capped at `scrollTop` so a list at rest is unmasked) below the block. A mask makes its element a backdrop root, so a list row must never carry its own `backdrop-filter` — it would frost only the list, not the glow. Pages without the block (map, chat, detail, More) keep the old layout.

**When adding a new instance:** call `toolbarHTML({id, placeholder, value, sortLabel, dir, active})` in `render()`, `wireToolbar(id, {onFilter, onSort})` after it, and `openSortSheet` from `onSort`. Give it its own `polaris-mobile-<list>-list` prefs key and validate what `loadPrefs` hands back against the current option list, since a saved key can outlive the option it named.

## On-screen keyboard fit (login/form screens)

**What it is:** Keeping the focused field and its submit button above the on-screen keyboard on a viewport-height-locked screen. iOS Safari (and the installed PWA) do **not** shrink the layout viewport when the keyboard opens, so `100vh` / `height:100%` still measure the whole screen and a vertically-centered card doesn't move — the password field and Sign in button end up behind the keyboard. Android Chrome shrinks the layout viewport itself and needs no help.

**Canonical implementations:** the IIFE at the `visualViewport` block in [public/js/login.js](public/js/login.js) (desktop login page, pins `.login-wrapper`) and the `installKeyboardFit` block in [public/js/mobile/auth.js](public/js/mobile/auth.js) (mobile SPA login + TOTP, pins `.app`). CSS lives beside each: the `.kb-open` rules inline in [public/login.html](public/login.html) and in [public/css/mobile.css](public/css/mobile.css). Behavior is unit-tested in [tests/unit/mobileLoginKeyboardFit.test.ts](tests/unit/mobileLoginKeyboardFit.test.ts). A third instance is the phone's Chat tab (`installKeyboardFit` in [public/js/mobile/chat-tab.js](public/js/mobile/chat-tab.js), `.chat-kb-open` in mobile.css, pinned in [tests/unit/mobileChatTab.test.ts](tests/unit/mobileChatTab.test.ts)): there the screen is a scroller that DOES have room, but iOS left it running on behind the keyboard, so a composer grown to three lines left a sliver of log that could not be scrolled to the newest answers. It differs from the auth instances in three ways — **its own class and custom properties** (`--chat-vv-height` / `--chat-vv-offset-top`), because auth.js's reset strips `.kb-open` whenever no login form is mounted and would fight it; **the navbar steps aside** while the keyboard is up (and `.app-body` drops the navbar pad) so the composer sits on the keyboard; and instead of `scrollIntoView` on a form it **follows the end of the log only on the open edge and only for a reader already at the bottom** (`atBottom()`, 24 px slack) — the same rule `autosize()` applies as the composer grows, so a reader scrolled up to read is never dragged back.

**Key conventions:**
- Measure with `window.visualViewport` — the only API that reports the actually-visible rect on both engines. Treat the keyboard as open when `max(window.innerHeight, documentElement.clientHeight) - vv.height > 120`. The threshold is what tells a keyboard from a collapsing URL bar, and it is also what keeps Android out: there the layout viewport shrinks too, the delta stays ~0, and the native behavior is left alone.
- Pin the container to the visible rect through CSS custom properties (`--vv-height` / `--vv-offset-top`), never by writing layout properties from JS. Include `offsetTop` — iOS scrolls the layout viewport under the keyboard even when the page can't scroll.
- **Top-align in `.kb-open`.** This is required, not cosmetic: overflow above a `justify-content:center` flex item is unreachable because `scrollTop` can't go negative. Shortening the container without flipping the alignment trades one hidden control for another.
- Coalesce every handler through one `requestAnimationFrame` (`if (!pending) pending = rAF(apply)`), bound to `resize` + `scroll` on the viewport, `orientationchange`, and `focusin`. `focusin` is what re-measures when a step swaps the form in place (password → TOTP) with the keyboard already up.
- `scrollIntoView({block:"end"})` the focused element's **form**, and only when that target differs from the last one scrolled — re-running it on every viewport event fights the user's own scrolling.
- Where the screen is replaced wholesale with no teardown hook (the mobile SPA's auth screens), re-check on every measurement that the form is still mounted and unpin when it isn't, rather than trusting a lifecycle callback. Clear the class explicitly on the success path too: the next viewport event may be a long way off, and a stale pin sizes the authenticated shell to a dead height.

**When adding a new instance:** reuse the threshold, the rAF coalescing, and the top-align flip verbatim — the failure modes above are all silent. Anything inside a scroll container that already has room to scroll doesn't need this at all; the browser's own scroll-into-view handles it.

## Theme strip (the phone's theme control)

**What it is:** The 24-hour clockface unrolled into a flat strip that travels LEFT under a fixed centre marker — since 2026-09-21 the desktop's sidebar band is the same control, so this is no longer the phone's own geometry. The phone keeps a **marker and a caption** where the desktop band was stripped to bare artwork: same travel, different chrome, and a change to one is not automatically a change to the other, on the More tab under “Appearance”. One tap steps to the next selectable theme; there is no menu and no on/off state. It replaced a two-line Dark/Light row.

**Canonical implementation:** `window.PolarisTheme` in [public/js/mobile/app.js](public/js/mobile/app.js) — `set()` / `advance()` / `seatStrips()` / `get()`, with `_paintThemeStrips()` and `_advanceThemeStrips()` doing the travel; markup in `renderMenu()` in [public/js/mobile/more-tab.js](public/js/mobile/more-tab.js); `.theme-strip*` rules in [public/css/mobile.css](public/css/mobile.css). The desktop counterpart is `advanceTheme()` + `_paintThemeBands()` + `.theme-band` in [public/js/app.js](public/js/app.js) — same clock, same palettes, same one-way rule and now the same geometry, implemented twice because neither document loads the other's JavaScript. `tests/unit/themeBandParity.test.ts` reads both files and fails when the two halves drift: the position tables, the artwork, the 800ms, the one-strip anchor, the seam and the forward-only loop.

**Key conventions:**
- **The art is repeated THREE times in the track.** `_paintThemeStrips` anchors the track one strip width left of the marker, so copy two sits under it and copies one and three cover the window on either side. With two copies the right-hand half of the window falls off the end of the art as the position approaches the seam, and bare surface shows beside the engraving. (The kit's own CSS comment and apply-prompt say “twice”; its JS says three and its arithmetic requires three. Three is right.)
- **The seam is what makes a finite strip endless.** The art loops, so travelling past the end of one copy lands on identical pixels in the next; once a leg lands past it the JS subtracts exactly ONE strip width with the transition switched off. It has to be a whole strip (anything else lands on different pixels and the jump is visible) and it must never run mid-transition — `_advanceThemeStrips` settles an owed normalisation before measuring the next leg, or that leg starts a full strip width from where it looks.
- **Positions are quarter-spaced** (`THEME_STRIP_POS`): the engraving is a 24-hour clock, so six hours is a quarter of it and the two faces land half a strip apart. Editing one position alone puts the marker beside a face instead of on it — keep the spacing and move the anchor.
- **Forward only.** A target “behind” the current position is reached by continuing off the end of the strip, never by running backwards; that is the whole reason the day reads as moving forward.
- **Widths are MEASURED, not assumed** — the art is a 2x asset sized by height, so its rendered width depends on the row height and the device pixel ratio. Before the image loads there is nothing to measure, so the painter re-seats on its `load` event rather than giving up; otherwise the first tap travels from the strip's left edge instead of from the theme showing.
- **The tap is delegated** from `document`. Never add a listener to a `.theme-strip` as well — one tap would advance two themes.
- **A strip rendered after boot must be seated.** The More tab is built on demand, so `renderMenu` calls `PolarisTheme.seatStrips()`; without it the track has no position until something else paints it.
- **The caption span carries BOTH classes** — `.name` is what the CSS styles, `.theme-strip-name` is what `PolarisTheme.set` repaints by class so every strip on the page updates. An id there matches only one and the caption silently stops following the theme.
- **`PolarisTheme.get()` answers a FAMILY and resolves it through the theme list**, never by naming ids. map-tab's basemap pair and topology-tab's node palette both read it, and the `afternoon` waypoint has to answer “light” or both flip to dark halfway through the sweep.
- **A transit palette is applied but never persisted**, so a reload mid-sweep lands on a real theme rather than on a waypoint nothing can name.
- **Every theme on the strip has its own `[data-theme="<id>"]` block in mobile.css**, hued from the desktop's tokens. One without a block still renders, on `:root`'s neutral Material greys — which is how nightfall shipped grey on the phone beside the desktop's indigo until 2026-09-23. The daylight token mapping in mobile.css does NOT carry over to a dark theme as written: it sends `--color-bg-secondary` (the darkest ground) to `cont-high`, which inverts every raised surface when "higher" means lighter. The nightfall block keeps `:root`'s lightness ladder and takes only the hues. The phone's chrome colour (`theme-color` in mobile.html, `PolarisTheme.set`, `THEME_COLOR` / `BACKGROUND_COLOR` in `src/api/routes/pwa.ts`) is nightfall's `cont` / `surface`, and those must move together. **Each theme block also declares `--status-bar-color`** (2026-10-15), the colour MEASURED at the top edge of the screen in that theme, glow included (headless Chrome, 412px wide, averaged along the top row): morning `#f7e6c8`, noon `#fcf0d1`, afternoon `#d5cad5`; nightfall stays `#1d2244`, the manifest colour. app.js `_syncStatusBar` writes it into the `theme-color` meta from `_applyMobileTheme` AND from the boot IIFE right after `data-theme` is set, so the bar is right from the first paint. Before, every daylight theme got one cool near-white `#eef0f7`, which sat on morning's parchment as a white band on Android (Pixel 8 Pro report), and the boot path never touched the meta at all. The family colours remain only as the fallback for a stylesheet without the token. Re-measure when a theme's surface or glow changes; `tests/unit/mobileThemeStripDom.test.ts` fails when a theme block lacks the token. `tests/unit/themeBandParity.test.ts` fails when a `THEME_STRIP_POS` id has no block that sets `--md-surface`.
- **`data-theme` now changes once PER LEG, not once per tap.** Anything watching it with a MutationObserver — map-tab's basemap swap and topology-tab's graph re-render both do — runs twice across a noon → nightfall sweep. Both are safe today (the strip lives on the More tab, so neither surface is open when it is tapped, and morning/noon/afternoon are all one basemap family so the tiles swap once), but a new observer that does expensive work per change has to expect a waypoint, and a new TRANSIT theme in a different family would make the basemap flip mid-sweep. Prefer the `themechange` event or a family comparison over reacting to every attribute write.

- **Adding a theme block also means the elevation and glow tokens.** Every `[data-theme]` block carries `--shadow-card` / `--shadow-sheet` (and noon / nightfall their `--page-glow-color`, morning the glow's `@property` parts, never a whole `--page-glow`); see § Elevation and the page glow below. A block that skips them keeps `:root`'s black cast, which reads as grime on a daylight ground.

**When adding a new instance:** there should only be one, but a second surface rendering a `.theme-strip` needs no wiring — the delegated listener and the class-wide repaint already cover it; just call `PolarisTheme.seatStrips()` once it is in the DOM. Adding a THEME means a `MOBILE_THEMES` (or `MOBILE_TRANSIT_THEMES`) entry, a `THEME_STRIP_POS` position, a `--md-*` block in mobile.css, and the desktop's matching `THEMES` / `THEME_BAND_POS` / token block — the two surfaces' theme lists move together, and the two position tables are now the same numbers, so the parity test fails until both are edited. Keep the quarter spacing: a fifth theme means re-anchoring all of them, on both screens, against the same engraving.

## Elevation and the page glow

**What it is:** how a phone surface shows that it is raised, and the light behind every tab. Added 2026-10-04 so cards and slide-ups read as the same raised objects they are on the desktop.

**Canonical implementation:** the `:root` token block of [public/css/mobile.css](public/css/mobile.css) — `--shadow-card`, `--shadow-sheet`, `--page-glow-color` / `--page-glow-strength` / `--page-glow` — re-declared in each `[data-theme]` block.

**Key conventions:**
- **A card takes `--shadow-card`, never `--elev-*`.** `.card-elevated`, `.card-filled`, `.card-outlined` and `.asset-card` all carry it. The values are the desktop's `--shadow-card` per theme, number for number (canon-shared-kit.md § Floating-surface tokens explains the two drop layers and the inset rim). The MD3 `--elev-1..3` ladder is a 1-3px blur, invisible under a phone-width card; it stays only for small chrome (FAB, snackbar). The app-wide search bar (`.m3-searchbar`) moved off it on 2026-10-08 and takes `--shadow-card` too, so it lifts by the same amount as the navbar (`--shadow-sheet`, the same recipe cast up).
- **A bottom sheet takes `--shadow-sheet`**: the same recipe cast UPWARD, because its only free edge is its top. `.sheet` carries it, so the asset sheet and every generic slide-up inherit it.
- **The glow is painted by the fixed `html::before` layer**, over `html`'s `--md-surface` (`body` is transparent, or its background would cover the layer); `.app` is transparent so it shows through. The glow parts don't inherit and the gradient tokens live on that layer, not `:root` — the desktop's performance rule (canon-shared-kit.md). The glow colour is `--md-primary`, except on noon, which takes sunlight yellow `#ffc928`, and nightfall, whose glow is the sliding night layer, moonlight blue `#6d97ff` at 25% throughout (it never changes colour, only position and size), sliding in as a circle that settles into the oval and leaving the same way reversed (`night-glow-in` / `night-glow-out`, 90vw circle → 180vw × 66vh oval; canon-shared-kit.md has the mechanism). The strength is 17.6% on the dark family (12.3% on nightfall), 11.2% on the daylight base and 24% on noon, in a wide horizontal ellipse (180% × 66% of the screen). The glow is built from the same eleven `@property`-registered parts as the desktop's (registered again at the top of mobile.css, since the phone loads no other stylesheet) and `html[data-theme-fading]` transitions them. Morning sets those parts, never a whole `--page-glow`: a sunrise rising from the BOTTOM centre (180% × 60%, warm-white core → gold → orange haze, the desktop's stops), under the frosted nav bar, which climbs to noon's top wash on the turn, rounding by 12.5% (0.25 s) and holding it to 75%, at constant width (the height grows to `180vw`) (the same `page-glow-round` keyframes on `data-glow-turn`, sizes in vw/vh — canon-shared-kit.md has why percentages blank the glow). Nightfall's glow is the sliding `--night-glow` layer, in from the left on noon → nightfall and out to the right on nightfall → morning, parked at −130% / 50% / 230% (noon / nightfall and its afternoon waypoint / morning) — wider than the desktop's because the phone's ellipse is. Noon's glow sinks off the bottom on that turn (main `--page-glow-y` 150% on nightfall and afternoon), on the palette's 1.6 s, and the sunrise rises from there to its 100% on nightfall → morning; morning's red band lasts 1 s of the climb to noon (`page-glow-band-fade`). The glows run on bare `html` over 2 s, longer than the 800 ms palette; see canon-shared-kit.md. The desktop makes the same exceptions; canon-shared-kit.md § Floating-surface tokens has the mechanism.
- **`.m3-topbar` is blurred, not filled.** It is pinned at the top of the screen, where the glow is brightest. The user rejected a tinted frost (55% of `--md-surface`) on 2026-10-04 because it read as a dark box. What remains is a bare `blur(20px)`, which can't be seen at rest and only smears content that scrolls under the bar. It lives on the bar's `::before`, because a `backdrop-filter` on the bar itself would make the bar the backdrop root and the containing block for anything mounted inside it. A new full-width bar at the top of a tab follows the same pattern. Painting it `--md-surface` would cut a hard band across the glow. **No `saturate()` in that blur.** Saturation deepens the glow's colour inside the bar, so the box comes back even with no fill.
- **The bottom `.m3-navbar` is frosted glass.** It takes the desktop's floating-surface material: `--md-surface-cont` at `--nav-glass-mix` (30% in every theme, the desktop sidebar's number; nightfall ran 40% until 2026-10-06), plus `--glass-blur`, and wears `--shadow-sheet` (since 2026-10-05): the bottom sheet's upward cast with its inset top rim, per theme, because the bar's only free edge is its top too. Saturating is fine here because the bar has a tint. Glass needs something behind it, so the bar overlaps `.app-body` by `margin-top: calc(-1 * var(--navbar-h))`, and `.app-body` pads its bottom by the same height. That padding applies only while the bar is shown, not on `data-tab=""` (the auth screens) or `__fullbleed`. A tab that sizes itself `height: 100%` (the map) still stops above the bar, because percentage height resolves against the padded content box. Any new fixed or absolute control near the bottom must clear `--navbar-h` exactly as the FABs already do. The blur sits on the bar itself, not on a `::before`: the bar is a grid, so a pseudo-element would become a sixth cell.
- **The navbar is Alerts · Assets · Networks · More** — or **Alerts · Assets · Networks · Chat · More** when the AI assistant is usable here (2026-10-13: Chat gets a slot of its own, spliced in before More; it no longer displaces Networks, and the More menu has no Networks row). **Alerts is the home route**: app.js `boot` opens an empty hash on `#alerts`, and `routeChanged` bounces an unknown route there (detail back buttons fall back to it too). **Search has no slot** — it is a ROUTE_TAB with `navTab: ""`. **The search bar is hidden until opened** (`#search-slot { display: none }`, shown by `.app.searching`, which `syncSearchChrome` toggles from the route). The entry point is a **magnifier the shell injects FIRST into every `.m3-topbar .trailing`** (app.js `addTopbarSearch`, called right after each `renderTopbar`), so it sits between the page title and the page's own buttons (refresh…) and no page can ship without search; a page with no `.m3-topbar` gets none (the topology graph, which has its own site search) — which is why the Device Map tab and `#site/<id>` now render a titled top bar (`Device Map`). The magnifier's `openSearchFromButton` adds `.searching` and calls `input.focus()` INSIDE the tap, before the route change lands — iOS raises the keyboard only for a focus made in the user's gesture, and the input is `display:none` until the class is on. `openSearch` then PUSHES `#search` (the browser's back closes it); the bar unrolls leftward from the magnifier's side (`searchbar-reveal`, a `clip-path` inset, so nothing inside it is squashed) while the hint panel unfolds (`.search-expand-in`); the leading arrow or a second Escape runs `closeSearch`, which clears the box and pops back to the page search was opened over — or navigates there when another route has since been pushed. The avatar initials now show only while search is open (they live in the bar). The grid is `grid-auto-flow: column` + `grid-auto-columns: 1fr`, one column per item, because the bar is four slots or five; a fixed `repeat(5, 1fr)` left a dead column beside the four. Chat's slot: `PolarisTabs.setChatInBar`, decided in app.js `refreshChatSlot` from `assistant` read + `GET /assistant/status` `enabled`, cached per phone in `polaris-mobile-chat-available` so the bar keeps its shape on load; otherwise `#chat` is a slotless route tab that explains why it is unavailable. The chat view is [public/js/mobile/chat-tab.js](public/js/mobile/chat-tab.js): it loads the desktop `assistant.js` only for `readEventStream` / `parseSlash` / the report helpers / `_idleExpired` and shares its localStorage keys; its composer is sticky at `bottom: 0` — NOT `var(--navbar-h)`: `.app-body` already pads its bottom by the navbar height and sticky offsets are measured inside that padding, so the navbar height there floated the box a whole bar above it — and `.app[data-tab="chat"] > .app-body` is a flex column so `.chat` (flex: 1 0 auto) fills it — a percentage min-height does not resolve there and left the composer floating mid-screen on a short chat. The textarea grows UPWARD to 3 lines (`autosize`, `COMPOSER_MAX_LINES`) and then scrolls inside. The top bar carries the same R.A.L.P.H. toggle button as the desktop (`.chat-ralph`, glowing in `--md-primary`). ## Orientation (none — the app turns with the phone)

**What it is:** the phone app has no orientation of its own. Every screen, the per-site topology included, turns with the phone; there is no `screen.orientation.lock()`, no `orientation` in the manifest, and no rotate prompt or lockout. Removed 2026-10-27 by request (the portrait lock, the topology's landscape lock and its `.topo-rotate` "Turn your phone sideways" prompt; the whole-app "rotate back to portrait" lockout had already gone 2026-10-26 because an iPhone can never be locked).

**Canonical implementation:** nothing to copy — the absence is the rule. [tests/unit/mobileOrientation.test.ts](tests/unit/mobileOrientation.test.ts) fails if a lock call, an `html[data-orient]` switch, an orientation media query or the topology's rotate prompt comes back; [tests/unit/pwaManifest.test.ts](tests/unit/pwaManifest.test.ts) fails if the manifest declares an `orientation`.

**Key conventions:**
- **Every screen must WORK sideways (≈390 px tall) and upright**, not merely survive it. Do not reintroduce a lock or a prompt to dodge a layout problem; fix the layout.
- **The topology re-fits on a turn.** Its resize handler re-fits the graph after the container changes shape — until the operator touches the graph or picks a search hit (`_viewTouched`), after which a resize only reflows.
- **Landscape puts the notch at a side**, and `viewport-fit=cover` lets even a Safari tab paint under it: `.app` pads `env(safe-area-inset-left/right)` in every display mode (top/bottom stay standalone-only), and so do the screen-spanning fixed surfaces — `.sheet`, `.sheet.network-sheet`, `.snackbar`, and `.topo-screen` (all four sides, see the next section; its `.topo-bar` must NOT add them again, or the bar is inset twice). A new fixed, full-width surface must pay them too. The `-24px` full-bleed rows inside a sheet (`.sheet-pinned-head`, `.ae-menu`, `.ae-footer`) deliberately bleed only to the safe-area line.

## A fixed full-screen surface pads its own safe area

`.app` takes the iOS top and bottom safe-area insets as padding only in standalone mode, so anything that leaves it with `position: fixed; inset: 0` gets none of that padding. Under the installed app's `black-translucent` status bar, the surface's top row is then drawn behind the clock and notch, where it can't be tapped. The topology screen (`.topo-screen`) shipped that way and trapped operators with no way out (fixed 2026-10-26). Such a surface pads the `env(safe-area-inset-*)` sides it owns itself, and its absolutely positioned children add the inset to their own offsets, because absolute offsets are measured from the padding box and ignore the padding. Since 2026-10-27 the topology keeps the navbar (`__fullbleed` no longer hides it): `.topo-screen` ends at `bottom: calc(var(--navbar-h) + env(safe-area-inset-bottom))`, the asset sheet's anchor, and pads only top and sides. Because the router has no leave hook, a navbar tap swaps the topology out without `closeTopology`; `leftTopology()` disposes the graph on the next resize or theme change. Every node is `panify()`d (and every node added later, through an `add` listener) so a one-finger drag that starts on a location hull or a device pans the map — Cytoscape pans only a drag that starts on background or a `pannable` element, and `autoungrabify` alone leaves a hull dead to the touch. **The phone drills into location groups as the desktop does** (2026-10-27, by request): `renderViewRows` in [public/js/mobile/topology-tab.js](public/js/mobile/topology-tab.js) draws the desktop switcher's rows (`viewSwitcherRows` in topology-render.js — never a phone copy of it) under the search bar, with Base folded into the head of the first row (`viewChipRows`), and `setView` re-renders through the same shared helpers map.js uses: `partitionElementsForFloor`, the saved layout under the view's key (`savedLayouts[<view>]`), `renderLocationGroups` with the view's suppressed tiers (`locSuppressKinds`, the mirror of map.js `_locSuppressKinds`), and a portal tap jumping to its `targetView`. Every open starts on Base; a refresh keeps the view unless the payload no longer offers it. A search pick whose device is not in the view on screen drops back to Base and centres it there (`_pendingFocusId`) — the desktop leaves that pick doing nothing. The rows sit IN the flow, not over the graph, so a pan that starts under them is never eaten; a row too long for the screen scrolls natively with no scrollbar, and a chip its edge cuts fades AS A WHOLE (`fadeViewRow`: opacity = the share still showing, cleared once whole), the desktop tab strips' edge (canon-tables-lists.md § tab strips) — never a gradient mask. Pinned by `tests/unit/mobileTopologyViews.test.ts`.
