### SPA shell, navigation, and the assets page

Vanilla JavaScript SPA served from `/public/`. No build step — plain ES modules. Multi-page layout with client-side navigation (`app.js` — every sidebar entry whose page can 403 carries a permission gate, `perm: [key, level]` or `anyPerm: [[key, level], …]` for a multi-key page like IPAM, kept in lockstep with `pageRequiredPermission` in `src/app.ts` which bounces a typed URL for the same page; an ungated entry advertises a page whose first list fetch is the only thing telling the operator they can't be there), **three themes in two families** (`morning` / `noon` daylight, `nightfall` dark; the retired `dark`/`light` ids are recognized nowhere, and any surface picking art or a palette by brightness branches on `isLightTheme()` rather than on an id), an **account menu** behind the page-header user badge (`openUserMenu` in app.js, built on the shared `showRowMenu`: Web Push enrollment, **two-factor (TOTP) enrollment** for local accounts, Logout — these used to sit at the bottom of the sidebar, where per-account actions competed with navigation. The theme control went WITH them and then back, and now lives at the sidebar bottom below Server Settings and above the version line (`btn-theme-toggle` in `renderNav`, repainted by `_setTheme`). Since the three-theme cutover it is a PICKER, not a toggle: it is labelled with the CURRENT theme and opens the full list through `openThemeMenu` → `showRowMenu` (past two themes a two-way switch makes the third reachable only by cycling past one you didn't want). `_setTheme` fires a `themechange` CustomEvent on `document` carrying `{theme, family}` — anything that cached colors at render time (Leaflet basemaps, Cytoscape stylesheets, canvases, the brand art) listens for that rather than hooking the control. ### Service & Process Discovery Rules (Integrations → Polaris Agent)

**Service & Process Discovery Rules** (Integrations → **Polaris Agent** tab, the card above the agent-build card; `public/js/appmap-discovery.js` renders the inline list via `window.PolarisDiscoveryRules.init`, `public/js/appmap-rules-wizard.js` is the builder — both load on integrations.html now, not appmap.html): named rules that pin process/service items on the assets they select, now AND on assets discovered later via the `reconcileAppMapAutoMap` job; several rules' pins union per asset. Each rule has a **mode** — *Monitor + map* (Application Map + telemetry; mapping implies monitoring) or *Monitor only* (per-program CPU/RAM + logs, per-unit journal tailing; never touches map pins) — chosen on step 1 of the 4-step wizard (name → devices → items → summary, `openAutomationWizard` idiom, shared `.stepper` CSS). The device step is a flat `TagCriteria` builder (ported from the maintenance criteria UI with `apr-` prefixed ids — NOT the automations condition tree, which can't round-trip through `normalizeCriteria`), and the item step is **scope-driven**: it lists only what the selected devices report (services-only by default, with a running selected count), which is what keeps a rule from pinning a unit on every host that happens to run it. Rules only ever target `PROCESS_CAPABLE_ASSET_TYPES` (workstation + server) since nothing else reports an inventory. **Auto rules:** ticking Monitor/Map on an asset's Services tab mints a single-item `source:"auto"` rule targeting just that asset (`scope:null` + explicit `assetIds`); pinning the same item on another asset consolidates into the existing auto rule, un-ticking removes the asset (an auto rule losing its last asset is deleted), manual rules are never consolidated, and editing an auto rule in the wizard converts it to manual. Auto rules wear an "Auto" badge; the Devices column renders their hostnames via the GET's `assetLabels`. **Mapping implies monitoring, one-way:** every item a map-mode rule maps is also pinned for monitoring (note the log volume that implies); monitoring never implies mapping, so nothing writes a map pin from a monitor pin — computed against the full want-set, so an item mapped before this behaviour existed catches up on the next reconcile. Removing an item or disabling/deleting a rule stops future auto-pinning; a separate *Unmap everywhere* action does the actual strip.

### SSH Deployment (Integrations → Polaris Agent)

**SSH Deployment** (Integrations → **Polaris Agent** tab, the card below the agent-build card; `public/js/agent-ssh-onboarding.js` renders it via `window.PolarisAgentSshOnboarding.init`, lazy-mounted by integrations.js alongside the other two cards). Polaris generates the ed25519 keypair used to install the agent on Windows over OpenSSH, owns the `ssh` Credential holding it ("Windows SSH (Polaris-managed)" — selectable in the normal Install Agent / bulk-deploy pickers), and emits the PowerShell that authorizes the public half across the fleet. Routes live under `/server-settings/agents/windows-ssh*` (the agent-build card's UI-on-Integrations / routes-on-serverSettings split); `POST /generate` carries a **chained gate** — `serverSettingsSystem:fullwrite` AND `credentials:write` — since it mints a fleet-wide admin credential. The private half is sealed at rest and **never returned by any read path** (the VAPID posture; no escrow — recovery is regenerate + re-run the script, which is why the script is idempotent), while `SshConfig.publicKey` is deliberately non-secret so the script can be re-rendered without rotating the key. Account settings are **per platform** (`windows` / `linux` blocks in the Setting; `polarisServerIp` is shared), and Polaris maintains **one managed credential per platform** carrying the same keypair — a Credential holds one username and a Windows `DOMAIN\user` is meaningless on Linux. Two scripts come out **per platform**: **remediation** (installs the OpenSSH Server capability, starts sshd, optionally creates the local admin account, appends the key to `%ProgramData%\ssh\administrators_authorized_keys` with the Administrators+SYSTEM ACL sshd demands, optionally scopes inbound TCP/22) and **detection** (exit 0 = onboarded, 1 = remediate) — pairing them under an Intune Remediation or SCCM Configuration Baseline is what makes rollout self-healing, since a plain platform script runs once per device and never retries. Both share one key-presence predicate so they can't disagree. The **Linux** pair differs where the platform does: the key goes in the user's `~/.ssh/authorized_keys` (700/600, correctly owned) with a `restorecon` for SELinux, and the script installs a **NOPASSWD sudoers drop-in** — `visudo -cf`-validated before install, since a bad one locks sudo out for everyone — because the agent installer runs `sudo -n`, so key auth alone cannot install an agent. It deliberately does not install `openssh-server`. Linux detection also checks the account + drop-in, unlike Windows. The scripts are **delivery-neutral and fleet-generic** (no machine-specific values; `administrators_authorized_keys` is one group-wide file), so the same body runs under Intune / GPO startup / SCCM / Arc / RMM / a one-off `Invoke-Command` — worth knowing that Intune does not manage traditional Windows Server, so the Servers class needs GPO/SCCM/Arc regardless. Operator input (`username`, `polarisServerIp`) is **rejected, not escaped**: it lands in a script an admin runs fleet-wide as SYSTEM. See `sshOnboardingScript.ts` / `windowsSshOnboardingService.ts` in polaris-change-impact.

### Script publishing (Intune + Azure Arc)

**Script publishing** (the SSH Deployment card's Publish pane + a *Script Publishing* tab on the Entra and Azure Arc integrations). Delivers the generated onboarding scripts instead of the operator downloading and uploading them. Both vehicles are **opt-in per integration, off by default** (`EntraIdConfig.publishToIntune` / `AzureArcConfig.allowRunCommand`), because each needs a vendor-side grant the read-only discovery credential deliberately lacks — the tab renders the setup steps and the cost of the grant inline. **Intune** (`intunePublishService`, Windows only) upserts a Remediation by displayName and **never calls `/assign`**: assignment is the human review gate for a script granting fleet-wide administrative SSH, and it is test-pinned. The Graph API version is probed (v1.0 then beta) since `deviceHealthScripts` has historically been beta-only — a 404 means wrong version, a 403 means the endpoint exists and permission is missing. **Azure Arc** (`arcPublishService` → `azureArcService.dispatchRunCommand`, Windows AND Linux, the only vehicle reaching Linux or Windows Server) runs the script via Run Command. Arc has **no inert state** — a run command executes on creation — so the review gate is explicit target selection: no 'all machines' affordance, ids re-resolved against the live roster, 200-target cap, and an undeterminable OS is skipped rather than guessed. Its grant is an Azure **RBAC role assignment** (`Microsoft.HybridCompute/machines/runCommands/write`), NOT a Graph permission. Both routes live under `/server-settings/agents/script-publish/*` behind a chained **fullwrite on BOTH** `serverSettingsSystem` and `integrations` — `integrations:write` is the blanket gate on that whole router and must not confer tenant writes. See `intunePublishService.ts` / `arcPublishService.ts` in polaris-change-impact.

### Automation export / import / view code

**Export / import / view code** (`public/js/automations-portability.js`, `window.PolarisAutomationPortability`; loaded after the wizard on all five pages that carry it). One automation travels as a `.automation.json` file whose **`dependencies` block comes first**, because that is what a human opening the file reads: everything install-specific is STRIPPED from the rule and recorded there by NAME instead (delivery channels, registry scripts, state probes, custom roles / regions / tags, pinned devices), so the file is portable and — the security half — carries no ids and **no secrets**: dropping api_call actions is what keeps an `api_call.headers` bearer token, stored unmasked by design, out of a file operators email and commit. It also means an imported file can never name a `script` action, so the RCE surface is untouched and `automationScripts:fullwrite` is never involved. **Export and "View code" are deliberately different serializations**: export is portable, the code editor is FULL fidelity (ids and headers included) because an edit there must round-trip losslessly onto the same automation, and it says so. Three traps the module exists to hold, each pinned by a test: (a) the top-level `actions` list is emitted **explicitly** as `[{type:"event"}]` — the server re-injects the audit Event only for `actions === undefined`, which `_awDraftFromRule` never produces (it coerces absent to `[]`), so omitting would save a rule that writes a Notification row, and therefore looks like it fired, while logging nothing; (b) an empty `scope` is never emitted — `{}` means MATCH NOTHING to the engine's `scopeWhere` while `step2Html` renders it with **"All assets" checked** and `validateStep2` calls it valid, so a scope that strips to nothing becomes an empty CONDITION TREE, which `validateStep2` does refuse (note `{}` and `{condition:{op:"and",children:[]}}` are OPPOSITES server-side, and an emptied nested group is REMOVED from its parent rather than kept, an empty AND group being true for every asset); (c) `dimensionFilter.stateProbeId` / `.widgetId` are optional and the engine applies them only when present, so blanking one **widens** the trigger from one PSU-alarm probe to every state probe on the device — it is recorded as a dependency AND `tgValidateLeaf` now refuses to save a `customStateValue` / `customWidgetValue` leaf without it (a latent builder bug fixed in passing). The code editor's own hazard is that **PUT is a full replace**: `normalizeRuleInputCore` maps an absent nullable JSON column to `null` and `jsonOrClear` turns that into `DbNull`, while `enabled` / `severity` / `reset` fall back to SCHEMA DEFAULTS — so deleting `enabled` takes a disabled automation live. It therefore renders the complete body, strips the legacy mirror (`targets` / `clearBehavior` / `clearAfterSec`: leaving `targets` in lets a deleted `actions` be silently rebuilt from it, losing per-action escalation and script/api_call actions), says that removing a key removes the setting, and confirms a diff of the destructive fields with the dangerous ones called out.

### Dash wallboard

**Dash wallboard** (`public/dash.html`): an unauthenticated, read-only duplicate of the Dashboard at `/dash`, served by its own process (`POLARIS_ROLE=dash`, `src/dash/dashServer.ts`) for NOC wallboards/kiosks. Default-off; enable toggle + source-IP scope on Server Settings → **Web Server** → Dash Wallboard. `dashConfig.ipScope` is `rfc1918` (RFC1918+loopback, default) / `all` / `custom` (an operator-entered IPv4-CIDR allow-list in `allowedCidrs`). **Unauthorized source IPs are silently dropped** (socket destroyed, no HTTP response) rather than 403'd, so a scanner can't confirm the surface exists — behind nginx that manifests to the remote client as a 502. Answers as the built-in `readonly` role (widgets the role can't read hide themselves via `PolarisWidgets.getAllowed()`); layout persists per-browser in localStorage (`polaris-dash-layout`); page flags in `dash-mode.js` (`POLARIS_DASH_LOCAL`, `__polarisApiBase=/dash/api/v1`) + slim boot `dash-boot.js` replace `app.js`. Keep dash.html's widget script list in lockstep with index.html.
**Published dashboards** (2026-09): the wallboard's own **Dashboards ▾** menu offers "My layout — this browser" plus every `public` `SavedDashboard`, read through the two GET routes this listener adds to its allowlist (`/saved-dashboards` exact + `/saved-dashboards/` prefix for the by-id read), mounted behind the same `savedDashboards:read` floor the main router uses and satisfied by the readonly identity. A session-less caller gets PUBLIC rows only, and every write verb 405s app-wide — so a wallboard viewer can build a local layout OR show a published one and can never save either to the server. The choice is pinned per browser in `polaris-dash-published` and restored at boot; a 5-minute poll re-reads it and re-renders only when `updatedAt` moves; a row deleted or unpublished under a live wallboard falls back to the local layout with a toast.

### Mobile PWA and Web Push

**Mobile PWA** (`public/mobile.html` + `public/js/mobile/*` + `public/css/mobile.css`): the phone SPA is an **installable PWA with push notifications**. Phones hitting `/` or `/index.html` are UA-redirected to it (`src/app.ts`, `?desktop=1` escapes); `/mobile.html` itself stays out of `protectedPages` so an installed app cold-starts into the in-app mobile login rather than a chrome-less desktop `/login.html`. That exemption also skips the **“Skip login page”** redirect app.ts applies to protected pages, so `renderLogin` in `public/js/mobile/auth.js` enforces the setting itself — the choke point every local login goes through (boot, the api.js 401 hook, Cancel out of TOTP) reads `skipLoginPage` off `GET /auth/azure/config` and redirects SAML-then-OIDC, falling through to the form when neither provider resolves. An explicit Sign out spends a one-shot `sessionStorage` marker (`PolarisAuth.markSignedOut`, set by more-tab.js) to draw the form once, since a silent `prompt=none` provider would otherwise sign the operator straight back in — the desktop's counterpart is `/signed-out.html`, the form-less page every desktop logout lands on, whose Sign in button opens the bare `/login.html` (since 2026-09-06 the setting redirects `/login.html` itself, with `?error=` and the anti-lockout `?local=1` as the only ways to draw the form). **Install identity is mobile-only** — `/manifest.webmanifest` is generated per-install from branding by `src/api/routes/pwa.ts` (`start_url=/mobile.html`, `id=/mobile.html` — never change it, it keys the install; `scope="/"` so the "Desktop view" link, `/login.html`, and push deep links don't eject the standalone window), with icons rasterized from the operator's logo by `appIconService`. Desktop pages deliberately carry **no** manifest link. The manifest + icon routes are **unauthenticated**: a `<link rel="manifest">` without `crossorigin` is fetched with credentials omitted, so a gated manifest 401s for everyone. Standalone layout needs the `@media (display-mode: standalone)` safe-area insets on `.app` in `mobile.css` — with `viewport-fit=cover` + `black-translucent` there's no browser chrome, and the existing asset-sheet/snackbar anchors (`calc(var(--navbar-h) + env(safe-area-inset-bottom))`) already assume the navbar sits above the inset. **Push:** the More tab's Notifications row is a **preference**, not a switch — it names the account's current choice (Email / Push / both) and opens a bottom sheet with the three options; the second half of its supporting line is about THIS phone (“tap to allow push on this phone”, “blocked in your browser settings”), because the preference can be perfectly saved and still reach nothing here. The load-bearing state is **iOS-outside-standalone** — Apple grants Web Push only to a home-screen-installed app, but `"PushManager" in window` is true in plain Safari from 16.4, so the line says "Add to Home Screen to receive push here" and CHOOSING a push-bearing preference routes to `#more/install` and saves nothing, rather than prompting for something that always throws (a preference this phone cannot honour, chosen on this phone, is a promise Polaris would break). **Alerts reach the phone in four places.** The Assets tab flags a device that has live ones — a strobing **Alerts** control beside the hostname, coloured by the worst active alert and going steady once everything on it is acknowledged, off the `activeAlert` summary the list payload already carries (so no extra request per card, and no extra query per row — see `activeAlertSummaryByAsset`). Tapping it opens the **per-asset alerts sheet** (`PolarisMobileAlerts.openForAsset` in [public/js/mobile/alerts.js](public/js/mobile/alerts.js)) over `GET /assets/:id/alerts`, which is the mobile counterpart of the desktop slide-over's Alerts tab: one card per active alert with Acknowledge at `alerts:write` (per row, plus one batched control for the whole device) and **Clear at `alerts:fullwrite`** — the phone's first clear, previously desktop-only. The sheet hands its recomputed summary back through `onSummary`, so the flag on the card behind it settles without a list re-fetch and the last alert being cleared stops the strobe. That module also owns the mobile severity vocabulary (`--md-sev-*` tokens in mobile.css, ranked the way `ALERT_SEVERITY_RANK` ranks them) and the two sheet-based prompts — the acknowledge note and the clear confirm — because `window.prompt`/`confirm` are suppressed in some installed PWAs. The **asset detail sheet** carries the same flag on its hero, beside the monitor pill (the two together are how the device is doing), loaded by its own `GET /assets/:id/alerts` because `activeAlert` is enriched onto the LIST payload only and the sheet opens from places that never went through the list — a search hit, a push deep link, a pasted `#asset/<id>`. **Search results** carry the same statement reduced to a dot (`dotHTML`, deliberately not a tap target — the row opens the device): `SearchHit.alert` is stamped by `withAlertSummaries` in `searchService`, ONE `activeAlertSummaryByAsset` call over the asset AND site hits of a whole result set, mutating the hits in place so the mobile renderer's virtual Device Map rows inherit it when they clone. The **desktop search dropdown** draws it too, from the same field: `assetAlertStrobeColor` / `_alertSevRank` / `assetAlertDotHTML` MOVED from `assets.js` to **`app.js`** to make that possible — the dropdown renders on every page and half of them never load `assets.js`, so a guarded call would have shown the dot on some pages and not others. `alertSummaryDotHTML(summary)` is the new core (same markup from a bare summary, for callers holding no asset row); `assetAlertDotHTML(asset)` delegates to it. The dot sits before the monitor pill in a hit — the alert is the reason to look, the monitor state is the detail, and a hit can carry both since an alerting device is often Up. `#more/alerts` is the fleet-wide list and the mobile push deep-link destination (and acknowledges in place: each unacknowledged row gets a one-tap **Ack** control with `alerts:write`, rendered as a SIBLING of the row button rather than inside it — a nested `<button>` swallows the tap that opens the device. Clearing stays desktop-only, being the fullwrite half) (without it `routeChanged` bounces to `#search`). `public/js/pwa-install.js` (loaded FIRST — `beforeinstallprompt` can fire before boot) exposes `window.PolarisInstall`. **Web Push generally** (both surfaces, `public/js/push.js` + `public/sw.js`): there is **no enable/disable control anywhere** since business rule 39 — the account menu row, the mobile More tab row and the Automations page's `#btn-enable-push` were all replaced by ONE per-account preference (`User.notificationPreference`). `polarisPush.syncToPreference(pref, surface)` is what enrolls or un-enrolls a browser, called at boot by `wireNotificationPrefs` (desktop, app.js — caches the preference into `_notifPref` and the push status into `_pushState`; `_notifPrefMenuItem` renders “Notifications: Email” and `_openNotifPrefMenu` the three-way chooser, the openThemeMenu pattern) and by `wireNotifPrefRow` (mobile, more-tab.js) — and, on the phone, by `initPushOnce` in [public/js/mobile/app.js](public/js/mobile/app.js) at BOOT, not only when the More tab is opened: the point of storing the preference on the account is that a device the operator never touches again still honours a choice made somewhere else (a failed preference read there falls back to the bare `reconcileSubscription`, so a network blip costs the sync but never the rotated-endpoint repair). It **never prompts** — a boot-time call has no user activation — so it enrolls silently only where permission is already granted, and a browser that has never been asked stays un-enrolled until the operator picks the preference there. Choosing a push-bearing preference calls `enable()` FIRST, synchronously in the click/tap handler, before persisting. `enable()` calls `Notification.requestPermission()` **before** any network await (Safari drops transient user activation across a fetch, so no click handler may `await status()` — both preference surfaces cache the status for exactly that reason). Where the old toggle HID itself unless `status().enabledOnServer`, the preference row stays visible and disables only the two push OPTIONS: the choice belongs to the account, so an unsupported or permission-denied browser must not be able to withhold it (the operator's phone may honour what this laptop cannot). Only the SERVER having no Web Push channel makes them pointless. Both surfaces also wrap the boot-time preference read in `Promise.resolve().then(...)` — it runs inside the sidebar / More-tab render, and a synchronous throw there would take the navigation down with it. a push carrying an `ackUrl` grows an **Acknowledge action button** whose `notificationclick` branch POSTs the token (`credentials: "omit"` — the token is the credential, so no cookie and no CSRF header) and replaces the alert in the tray with a silent confirmation; iOS/Safari renders no action buttons, so the body tap remains the path there. `sw.js` has **no fetch handler and no Cache Storage** (online-only tool; a unit test enforces this) and gets its icon from `/icons/app-192.png`.

## Server Settings → High Availability

**What it is:** the tab that turns a single host into an active/standby pair — the operator enters the three nodes, enables HA, and downloads a generated bootstrap script per node. Its own module, `public/js/server-settings-ha.js`, exposing `window.PolarisHaTab = { load }`, which `server-settings.js` calls on every activation of the `ha` tab (not once — returning to it must show current cluster state). Backed by `/api/v1/ha`; operator-facing walkthrough in docs/HA.md.

**Canonical implementation:** `public/js/server-settings-ha.js` → `render()`, which concatenates five cards in build order: `guidanceCard()` (what enabling costs, measured on this install) · `nodesCard()` (the three-node form) · `scriptsCard()` (one generated script per node) · `approvalsCard()` (pending nodes) · `clusterCard()` (live Patroni members).

**Key conventions:**
- **It never claims a node is installed.** Everything shown comes from Patroni or from what a node has actually asked for, so before adoption the tab renders instructions rather than status, and `clusterCard()` says so explicitly instead of erroring.
- **The guidance card states measured figures and admits what it could not measure.** `advisoryRow()` renders one of four levels (`ok` / `warn` / `bad` / `unknown`) with a coloured badge and a sentence — never a bare number, and never a green tick standing in for "probably fine".
- **Approving is a decision made against evidence.** The pending panel shows the source address and the SSH host key fingerprints the node presented, next to the Approve button, and the `showConfirm` text repeats them plus exactly what the bundle contains. A witness gets a different sentence, because its bundle holds no application secrets.
- **Scripts are presented the SSH-Deployment way** (`agent-ssh-onboarding.js` is the precedent): a read-only `<textarea class="mono">` plus Copy and Download buttons, with the route returning `{script, filename}` as JSON so one fetch feeds both and only one route needs gating.
- **It polls every 10s while visible, and never clobbers a form.** A node registering arrives from another machine and is the one event an operator is actively waiting for, so the tab refreshes itself; the tick skips when the panel is hidden, when `document.hidden`, and when the focused element is one of its own inputs.
- **Every destructive or consequential action goes through `showConfirm`**, and the witness-placement warning is part of the Enable confirmation text rather than a footnote — choosing the standby datacenter is the decision most likely to be regretted.
- Write controls are gated on `permAtLeast("serverSettingsSystem", "fullwrite")` with a stated reason when disabled. The non-admin tab-hiding loop at the top of `server-settings.js` already hides the whole tab for roles that only reach Credentials.

**When adding to it:** a new card goes in build order and returns "" when HA is not enabled (the tab is a procedure, and a card for step 5 must not appear before step 2). Anything showing a secret is wrong by construction — `GET /ha/status` returns presence flags only.
