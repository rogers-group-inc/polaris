## Mapping (Leaflet + OpenStreetMap tiles)

Every geographic surface draws its basemap from **one host, one URL**: `https://tile.openstreetmap.org/{z}/{x}/{y}.png`. The OSM tile usage policy permits that URL and no other — the older `{s}` a/b/c subdomain form spreads a single viewport across three hosts instead of one multiplexed HTTP/2 connection, and OSM's operators read it as a policy violation and answer with the "Access blocked" tile image in place of the map. Polaris shipped the subdomain form until 2026-09-15, when a personal install's maps came back blocked while the Rogers Group production install — same code, different viewer egress IP — kept rendering.

Four files declare the URL and they move together: `public/js/map.js → applyBasemapTheme()` (Device Map), `public/js/mobile/map-tab.js → applyBasemapTheme()` (phone Map tab), and `public/js/widgets/deviceMap.js → applyBasemap()` + `public/js/widgets/siteMap.js → applyBasemap()` (the two dashboard widgets). `src/utils/securityHeaders.ts → buildHelmetOptions()` whitelists exactly that host in CSP `imgSrc`, deliberately **without** a `*.tile.openstreetmap.org` wildcard, so a reintroduced subdomain form fails loudly at the CSP instead of quietly earning another block.

**The gate is the `Referer` header, not the URL and not the IP.** Measured 2026-09-15 with curl from the corporate network: the same tile URL returns a real tile when a `Referer` is sent (on the `a.` subdomain too) and the "Access blocked" image, with an `x-blocked: Access denied` response header, when it is not — OSM blocks every referer-less request outright. Polaris does its part: `src/utils/securityHeaders.ts → buildHelmetOptions()` sends `Referrer-Policy: strict-origin-when-cross-origin` (on OSM's accepted list), every layer renders the `© OpenStreetMap contributors` attribution, and `public/sw.js` registers no fetch handler, so the PWA never re-requests a tile the browser has cached. So when an install on current code still shows blocked tiles, the Referer is being dropped between browser and OSM — almost always a **reverse proxy in front of Polaris appending its own `Referrer-Policy: same-origin` / `no-referrer`** (SWAG's `ssl.conf` hardening block, Nginx Proxy Manager advanced config, Traefik/Caddy/Cloudflare header rules; browsers apply the *last* Referrer-Policy value they receive, so the edge wins), less often a browser privacy extension, rarely an IP-level block. That is why `deploy/nginx/polaris.conf` and `polaris.conf.template` carry a comment forbidding a Referrer-Policy at the edge, and why `docs/INSTALL.md` has the operator-facing section "Map tiles come back as Access blocked". Diagnose with DevTools → Network → a tile request's `Referer` header, or `curl -sI <polaris>/login | grep -i referrer-policy` (one line, `strict-origin-when-cross-origin`). **Never** by pasting a tile URL into the address bar: an address-bar navigation carries no Referer and shows the blocked image on every network, including ones where the map works — the home install's first diagnosis went wrong on exactly that.

Dark mode is the same tiles under a CSS filter (`.polaris-basemap-dark` in `public/css/styles.css`, `.sitemap-dark` for the widget flavor), never a second tile source: CARTO's Dark Matter served the dark half until CARTO began requiring an API key on its basemap CDN. That history is why the rule is *one unkeyed host* — moving to a keyed provider, or making the tile URL an operator setting (offered and deferred 2026-09-15), is a design change across all four files plus the CSP, not a drop-in swap.

## Graph layout (Cytoscape.js column solver, dagre fallback)

Cytoscape.js for the Device Map topology modal; nodes positioned by a deterministic Dijkstra-weighted **column solver** (`computeTopologyColumns` in `topology-render.js`). Column **anchors** (FortiGate + switches + branch APs — mesh roots / bridged-switch parents) land on even columns by weighted depth; **leaves** (wired endpoints, wireless stations, and *terminal* managed APs) hang in the odd column right of their parent. Rows come in two passes: a **nearest-free-slot packing** pass over the anchors (first anchor child continues the parent's row so chains stay flat; every other anchor scans downward from just below its parent's row for the first lane where its whole footprint fits — its own cell, the spine chain that inherits its lane into later columns, each chain member's planned AP block, the **spine-edge cell** (leaf column, own row) every continuing member's links leave through, and the **corridor cells** a child four or more columns from its parent runs through along its own row — so rows pack tight near the spine and spread only where subtrees congest, instead of every subtree pre-claiming a disjoint band), then a leaf pass that slides each parent's leaves as one **contiguous window** starting at the parent's row (one below it when its spine continues), blocks ordered by parent row — so a switch's APs line up directly beneath it, grouped together, never split apart or interleaved by another switch's APs. **Fan-out edges** — any edge between two nodes two-plus columns apart on different rows (a switch to its non-spine child switches, a mesh root to its leaves) — are drawn orthogonally, not diagonally: an L hugging the shallow end — a turn in the gutter HALF a column along, then along the deep end's row through the leaf column. The turn sat at 1.5 columns until 2026-10-16, which ran the edge along the shallow row beside the switch's straight spine link, so two child switches read as hanging off one port; at 0.5 the spine's port label sits right of the L. Off the grid (the level layout, a saved layout, a drag) the 0.5-column turn can cut across the shallow switch's own AP lines (operator screenshot 2026-11-09: an uplink rising out of House MCC through the line to its AP), so the routing wrapper's `retuneFanOutTurns` slides any crossing turn to the nearest clear spot along the span, drawn as `segments`; a clear turn keeps its taxi. Where any bent or shared link's label goes is `refreshBentEdgeLabels` (below), not Cytoscape's midpoint. The leaf pass dodges the deep-row run through the leaf column (`edgeLaneAt` → `fanOutLaneAt`, which answers the deep row for every crossed column), and the anchor footprint reserves the corridor cells past it; `markFanOutEdges(cy, columns, {colSpacing, orientation})` stamps the matching `taxi` geometry (`isFanOut` / `fanOutDir` / signed `fanOutTurn`, measured from the shallow end) after the preset layout on both surfaces — `orientation` is `"horizontal"` on the desktop and `"vertical"` on the phone, which transposes the grid. Before this, a sibling's spine edge sliced through the row an earlier sibling's last AP was planned for and the leaf pass slid the whole AP block rows away from its switch. A **mesh / bridge leaf's** only bogus edge is the parent → leaf uplink (the same test `buildTopologyElements` drops by); its own downstream edges — a bridged switch's wired FortiAP, a switch chained behind it — stay, and physical verification flows through mesh and bridge edges, so nothing behind an AP is orphaned into the stray rows or exiled as a FortiLink fallback. **Location codes** (`a:`/`b:`/`f:`/`r:`/`jb:` = area/building/floor/room/junction-box, parsed from device descriptions/notes by `src/utils/locationCodes.ts`) additionally cluster non-spine sibling anchors sharing an area (then building, then floor, then room, then junction box — `stableBucketByTiers`; fallback-exile roots and each parent's leaf block are ordered through the same tier chain, so room/jb co-members take contiguous lanes and their hulls come out as tight bands) into adjacent row bands, and draw **grouping hulls** as synthetic bottom-layer Cytoscape nodes (nested rounded rectangles color-coded per level — area rose > building sky-blue > floor violet dashed > room green > jb amber dashed, fitted inside-out with a sibling-separation sweep so shapes never overlap; plain nodes, not compound parents, so `cy.png()` screenshots capture them); when any device carries `b:` or `f:`, the modal offers a one-row-per-level drill-down switcher (**Base** — the whole site, view key `flat` — alone on top; then the **area view** chips plus any area-less building, or just the **building views** on a site with no areas; under a selected area its buildings; under a selected building its **floor view** chips, per (area, building, floor); every chip on the selected path lit — `viewSwitcherRows`) with dashed **portal** stubs where a member's edge crosses views (tap → jump; `computeFloorViews` / `partitionElementsForFloor`) — the FortiGate itself appears only in Base and its own tagged views, a dashed `isRootPortal` stub (`→ Base: <FG>`) standing in for it, and rooting the solver, in a view where a member links to it DIRECTLY — only there (2026-11-07: a stub in a view whose switches reach the FortiGate through Scale House read as a direct link). Members with any link out of the view carry `viewEntry`. **Group stubs** (2026-11-07, operator: "each group should connect back to the group of the previous level and next level"): every member link leaving the view lands on ONE stub per neighbouring GROUP (`portal:group:<view key>`, `_groupRefFor`: the far end's group at the view's level, else its nearest coded group, else `flat` = "Base") — `isUpstreamPortal` + "← X" when the far end is shallower than the member on the WHOLE-site solver (`computeTopologyColumns(elements)` inside the partition), else "→ X"; one line per member link. `computeTopologyColumns` on a FortiGate-less view roots on an invisible `__view_anchor__` joined to every upstream stub and FortiGate stub (so they share the first column), else to the `viewEntry` members; a lone FortiGate stub still roots by itself. The anchor is excluded from the result. **Stubs in a saved layout** (operator exports, 2026-11-07): a view saved before group stubs existed placed a new stub at its EMPTY-map spot — meaningless in the saved frame, and twice exactly on a device — so `applySavedPositions` puts an unsaved stub two columns left (a "←" / FortiGate stub) or right (a "→" stub) of the saved devices it links to, on that device's row, and `separateNodes` now counts stubs as taking space (`_isLayoutDevice`). Evaluate layout changes against the operator's anonymised exports by REPLAY (rebuild the view from the export, lay it out fresh, route, re-export, measure) — a picture of a saved layout mixes old and new code. **Operator-drawn connection lines** (`public/js/topology-edge-editor.js` → `attach()`, desktop modal only): dragging a line adds a selected bend, clicking it shows bend dots + an end-point ring per device that slides around the device outline (an undrawn line shows the corners the router / fan-out gave it as bend dots — `renderedCorners`; moving or deleting one seeds the whole shape first via `seedFromRendered`, 2026-11-09), Delete removes the selected point; a drawn line is `customPath` and the inter-group router leaves it alone. The router (`routeInterGroupEdges`) never places a bend inside either end device (`_nodeClearance`: outer radius + 6 px): Cytoscape cannot find where a segment starting inside a node leaves it, marks the edge `badLine` and draws NOTHING, leaving only its selection handles. A run fanned a few px off its target's row therefore steps back to that row just before the target instead of jogging inside it (pinned by `tests/unit/topologyRouteBendClearance.test.ts`). Its geometry is saved in the view's layout blob as `edgepath:` entries keyed by kind + source + target (element ids are payload indices), so Save / Reset need nothing of their own; the handles are `noExport`, which `graph-export.js → readScene` skips. **The modal opens view-only**: a dashboard-style Edit button (pencil / Done check, `#topology-edit`) switches on dragging, line editing and the edit-only corner tools — Grid, Snap devices, Snap line points, and Save / Reset / Undo / Redo in a column under Edit (map.js → `_ensureTopologyCornerTools` / `_applyTopologyEditMode`; the full inventory is in polaris-change-impact → file-map/public-2.md). Lines are always straight between their points (a curved Photoshop-wing mode was built and removed 2026-10-26). **No two devices on one spot**: every device move — drag release (after snap), a box drag's `free`, Snap devices' re-snap (live view AND the arithmetic snap of other views' blobs), and the saved-position restore at `layoutstop` — runs `topology-render.js → separatePositions` / `separateNodes` (via map.js → `_separateDevices`): bodies (`width()` × `height()` — NOT outer: a selected device's thicker border grew its footprint 46 → 49 px and blocked a nudge; NO clearance — the snap cells are 65 px squares and any two devices on neighbouring cells must both fit) overlapping = one spot; the moved device steps to the nearest free offset in whole snap cells (snap on) or thin-line cells (snap off), the one already there and every unmoved device hold; boxes, portals and line handles are not devices. A new place a device can move must call it too. **Arrow keys** (edit mode, map.js → `_nudgeSelection`) move the selected devices — else the selected bend handles — by one 65 px snap cell (Snap devices) / one thin-line cell at the drawn split (Snap line points) / 1 px, Shift 10 px; a device step hops over occupied cells via `separatePositions`. The move runs the drag pipeline (`grab` → position → `free` → `dragfree` emitted by hand, so the edge editor carries bends and dragfree saves), then `_layoutHistoryFlush()` closes the undo step synchronously — the 0 ms `_layoutHistoryRecordSoon` timer folds two fast presses into one step otherwise (seen in Chromium). **Location-box names sit INSIDE the box, under the top wall** (2026-11-06; until then centred above it): stylesheet `node[isLocGroup]` keeps `text-valign: top` and pushes the label down with a positive `text-margin-y` (`LOC_LABEL_MARGIN_Y`), and `_layoutLocationGroups` tops each named box with `LOC_LABEL_BAND` + `LOC_LABEL_GAP` (34 px) INSTEAD of the level's padding — so nested walls step a uniform 34 px at the top, while sides and bottom keep the per-level pad (42/34/26/18/12) and widens a box narrower than its estimated name width (`_locLabelMinWidth`) — change the three together. The box fit still ignores DEVICE labels (`includeLabels: false`), so a nested box can start just under the name of a device above it. **Two Cytoscape traps** this surface hit, both invisible to headless unit tests: (1) never snap a GRABBED node's position inside its `position` handler — Cytoscape moves a grabbed node by the pointer delta since the last event, so per-event snapping discards every sub-half-cell move and the node freezes; accumulate the raw drag position and snap that (the editor's `dragRaw`); (2) a press on an EDGE that code turns into a drag is still a CLICK to Cytoscape on release (edges are not grabbable), so `selectionType: "single"` selects what is under the pointer and drops the rest — re-assert selection in a `setTimeout(0)` after `tapend`. Verify drag work with the CDP mouse harness in small steps, logging every step. Every site — coded or not, so the first code never switches layouts — gets the **level layout** (`computeGroupedLayout`, 2026-11-06; replaced the quotient layout, whose box order came from flat-solver LANES that tier clustering reshuffles on every code change and whose shelf packing wrapped at the tallest box, so one description edit moved everything). A device's level is its flat-solver `depth`; a box's level is its shallowest member's; boxes nest a > b > f > r > jb by the same scoped keys `renderLocationGroups` draws. Inside every box (and the site) items are placed branch by branch (BFS over the upstream tree, `_upstreamMap`: nearest strictly-shallower linked device, MCLAG excluded), each at x = its upstream device + one cell per level (global depth ranks, `_levelRankMemo`) and on the upstream's row, else the CHEAPEST free spot — cost = cells right + cells off the row (up costs a hair more than down) — past, below or above what blocks it. **No site-wide columns** (2026-11-07): with them, column x cleared the widest item of the column before, so one wide area pushed every deeper item on the map past its right edge, far from its uplink (operator screenshot: towers fed from Scale House strung out past Mine; 47.5 → 26 cells wide and total link length 371 → 173 on a synthetic site of that shape). Among one upstream's children the SPINE claim goes first (a child with children of its own, else one that skips a level), so a switch chain keeps one flat row; a straight same-row link becomes a CORRIDOR nothing may sit across, and a device that links OUT of its box keeps its row clear to its right (OUTBOUND), so no straight link runs through a device. Devices with no link at all go in a strip under the site. **The layout fits its window's shape** (2026-11-07, operator: a deep site came out as a tall column on a 16:9 screen): a cell off the row costs `rowWeight` cells right, and `computeGroupedLayout(elements, { aspect })` runs the whole layout once per `LEVEL_ROW_WEIGHTS` (1 … 9) and keeps the run whose device-centre span (+1 cell each way) is nearest `aspect` in log ratio, ties to the lighter weight (shorter links). Each surface passes its graph container's width / height through `layoutAspect(el)` — the desktop modal `#topology-graph`, the phone `#topo-graph` (portrait → tall), the widget its tile; none / a zero-size container → 16:9. Seven runs cost ~25 ms on 65 devices. `routeInterGroupEdges` scores a second route family besides out-the-side-facing-the-target: out the source box's TOP or BOTTOM (from the device's column or a lane beside it), so a target just below a wide box is a short drop, not a trip out the far wall and back. **Bundling** (operator sketch, 2026-11-07: "only stack in the middle, and only lines from roughly the same source to the same destination"): the router PLANS every inter-group edge first, then assigns geometry over all of them — a BUNDLE (source top box + exit kind (a top/bottom exit per source device) + left/right + up/down) shares ONE trunk x exactly; a different bundle's trunk or lane block that would come within `BUNDLE_GAP` (22 px) over a shared stretch steps away; inside a bundle, members whose corridors coincide take their own `LANE` (16 px), nearest target nearest the targets; the k-th link out of / into one device is fanned `END_FAN` (12 px) with a stub just outside the icon, so every line can be hovered at its device. The level layout keeps EVERY same-row link between placed devices as a corridor (not only the upstream link — `neighborsOf` / `linkedPlaced`) and marks a device OUTBOUND for any link leaving its box to a device as deep or deeper, and an item whose upstream is OUTSIDE its box INBOUND (its row reserved from the left: a second switch fed from the same outside switch otherwise landed on the first one's row with its link running through it — the operator's PUG57/PUG8), so no device sits on another link's straight line. Spacing is what boxes DRAW (`_levelSep`: two walls' reach + `LOC_GROUP_SIBLING_GAP`, rounded up to half cells — devices stay on the 65 px snap grid; `_levelLinkSep` for a link through a column). Nothing reads flat-solver lanes, so tagging one device moves only the boxes it joins/leaves and what stacks after them (browser-measured: tagging one switch into an area moved only that switch). Saved layouts go through ONE helper on all three surfaces: `applySavedPositions(cy, saved, elements)` pins saved devices and places an unsaved one at its level-layout offset from its nearest saved upstream ancestor; `renderLocationGroups(cy, { fixedIds })` then never pushes a box holding a pinned device. Change the layout and `markFanOutEdges` / `routeInterGroupEdges` together — both read the same {depth, lane} grid. dagre + cytoscape-dagre (bundled under `public/js/vendor/`) remain the fallback when there's no FortiGate root

**The graph's palette is APP-themed, and its stylesheet is not reactive.**
`topologyStylesheet(family)` in `topology-render.js` takes a theme FAMILY — `"dark"` or
`"light"`, never a theme id — and is evaluated once per render. Two rules follow. First,
the family must be the one the *canvas* is painted in: `.topology-graph` paints
`--color-bg-secondary`, an app-themed token, so the desktop modal derives it from
`isLightTheme()` (`appThemeFamily()` in `map.js`). It used to take the per-user **basemap**
preference on the theory that one toolbar toggle should drive the map and the modal
together — but the topology modal has no basemap, so a nightfall operator who preferred
light OpenStreetMap tiles got `#1a1a1a` node labels on a `#0d0d1a` pane. The basemap toggle
now leaves the modal alone. Second, because nothing re-reads the stylesheet, any palette
input that changes under an OPEN modal has to re-render it: `map.js`'s `data-theme`
observer calls `repaintOpenTopology()`, and the phone's topology tab does the same.
`topologyStylesheet` also resolves anything that isn't a family from the document's own
`data-theme` rather than falling through to the light branch, so a caller that passes an id
degrades to the right palette instead of the opposite one.

**Links are coloured by speed and signal, not by kind** (operator design 2026-11-06, approved
on the "Device Map link colors" canvas). Every link is `EDGE_COLORS[family].neutral` until it
has something to say. `markLinkClasses` (run by `buildTopologyElements`) stamps a wired link
`linkSpeed` = `linkSpeedClass(min of the two ends' srcIf/tgtIf.speedBps)` — `10g` (≥ 10 Gb,
aggregates included) / `5g` / `2g5` / `1g` / `100m` / `10m` / `unknown` — and a mesh link
`meshSignal` = `meshSignalClass(signalDbm)` — `good` ≥ −65 / `fair` ≥ −72 / `weak` ≥ −80 /
`poor` / `unknown` (no reading, drawn like `good`). The stylesheet has one rule per class
(colour + `LINK_SPEED_STYLE` weight; 10 Mb a round-capped dot pattern); how a link was found
(isIface / isLldp / isApLink / controller) no longer has a colour and lives in the tooltip.
**Warm hues are reserved for signal** — no speed may take yellow / orange / red, which the
palette test enforces. MCLAG stays dashed in its speed's colour; the ring halo is
`EDGE_COLORS.halo` (white / near-black — yellow was given to signal). The server side:
`attachIfDetails` covers bridge and MCLAG edges too, and a mesh leaf's station row carries
`signalDbm` / `noiseDbm` / `band` / `channel` / `channelWidthMhz`
(`topologyGraphService → meshLinkDetail`, the root AP's `AssetApRadio` for channel and width;
signal only exists where the controller's REST overlay ran). The tooltip
(`edgeTooltipHtml` → `_speedTipRows` / `_meshTipRows`) writes every value out in words, so
colour is never the only carrier. Under each end's port line `_opticsTipRow` adds that port's
SFP readings (`srcIf` / `tgtIf.optics`, rule 143) — Rx at or below `OPTICS_RX_LOW_DBM` (−20,
the Interfaces table's `RX_LOW_DBM`; keep the two equal) in red, plus one line naming the end
receiving too little light; a port whose readings are all null (copper SFP, empty cage) gets
no line. Temperature goes through `PolarisTempUnit` when the page loaded it. Desktop page and widget only — the phone draws the same
colours but has no link tooltip.

**Link and location-box colours are per family** (since 2026-10-16). `EDGE_COLORS.dark` is
the 300/400 pastel set; on the daylight grounds those measured 1.3–2.4:1, so
`EDGE_COLORS.light` and `LOC_GROUP_KINDS[kind].colorLight` step each hue to its 600/700
shade — ≥ 3.2:1 on morning's `#e8d4ad`, ≥ 3.8:1 on noon's `#eae8e5` (WCAG non-text 3:1). The
neutral is the FAINTEST line in both families. Same hue per class in both families. `locGroupColor(kind, family?)` and `topologyLegendSpec(family?)` resolve the
family like the stylesheet does (`paletteFamily`, omitted → the document's), so the hulls,
their tooltip and the legend follow the canvas; `map.js`'s `data-theme` observer also
re-renders the legend body, which is otherwise filled once. Node health fills are the
monitor-state palette and are NOT remapped. `topologyColumns.test.ts` holds the stylesheet's
speed / signal rules equal to the legend's rows (colour and weight) in both families — add a
class to both or it fails. The legend's `edges` rows carry `section` (speed / signal / also),
`style` (solid / dashed / dotted) and `width`; `map.js`'s screenshot legend and export key
treat any non-solid row as a broken line.

**Port labels on bent and shared links** (operator rule, 2026-10-16). Cytoscape puts an
edge label at the path midpoint — on a taxi / routed link, a middle leg far from both
devices. `refreshBentEdgeLabels(cy)` in `topology-render.js` re-places them: one bend →
halfway along the second leg; two or more → halfway along the first leg plus a copy halfway
along the last; and never on a stretch another link runs along (within 3 px, parallel) — the
label takes the middle of the longest unshared run (≥ 24 px) of its leg, else the next leg
inward, else it is hidden (`label: ""`). Straight links keep the midpoint unless it is shared;
curved beziers are skipped. It writes per-edge bypasses (`text-margin-x/y` from the midpoint
— Cytoscape adds the margin before rotating, about the shifted point — an explicit
`text-rotation`, and `target-label` + `target-text-offset` for the copy) and keeps a
signature in `data(_bentLabel)` so an unchanged edge is never re-styled. Overlap lookup is an
axis-line bucket index, not a pass per edge pair: the pass runs once per frame while a node
is dragged (`wireBentEdgeLabels` — `position` + `layoutstop`, rAF-coalesced; both surfaces
wire it). Geometry changed by style alone must call it: the EXPORTED `routeInterGroupEdges`
does, and so does map.js's Locations-off branch that strips the routed bypasses. The PDF /
Visio export reads the shifted main label (it applies text-margin, printed horizontal) and
does not draw the target-label copy. Pinned by `tests/unit/topologyBentEdgeLabels.test.ts`.

**The side panel follows the boxes.** With the Locations chip on (`topoState.hasLocationCodes
&& _readShowLocations()`), `renderTopologyInfo` lists FortiSwitches and FortiAPs in the
boxes' nesting order — area › building › floor › room › junction box, numeric-aware names,
unlocated devices last — under one `li.topology-loc-group` heading per group
(`_sortByLocationGroups` / `_topologyLocationHeadings` in `map.js`); the chip re-renders the
panel. Chip off → the payload's order, unchanged.
