# Observability

Verbatim from CLAUDE.md → Observability, followed by the full metric catalogue from ARCHITECTURE.md.

`GET /health` (gated by `HEALTH_TOKEN`) and `GET /metrics` (Prometheus, gated by `METRICS_TOKEN`). Tokens are auto-generated by the first-run setup wizard; clearing either surfaces a watch-severity capacity reason. Metrics use the `polaris_` prefix and cover monitor pass duration, per-cadence work duration sliced by asset type + transport, probe RTT, queue depth (cursor + pg-boss), FMG worker dual-lane saturation, DB pool, capacity severity + dead-tuple ratios + steady-state size, discovery duration + per-phase histograms, sample-write + rollup duration, HTTP request latency, per-job duration, per-tick integration-tester outcome (`polaris_integration_test_total{integration_type, outcome}` — `outcome ∈ {success, failure, skipped}`, where `skipped` is the in-discovery branch that preserves prior `lastTestAt`/`lastTestOk`), down-detection index build time + coverage (`polaris_down_detection_build_seconds`, `polaris_down_detection_assets{coverage="covered"|"passive"}` — a climbing `passive` is the signal that devices have stopped being judged, and `polaris_down_detection_unavailable_total` counts the degraded all-passive path), and process crashes (`polaris_process_crash_total{role, kind}` — stamped by the last-resort `unhandledRejection`/`uncaughtException` handlers in `src/utils/crashHandlers.ts` just before `process.exit`; the counter dies with the process, so the signal is `increase()` over a window, not the instantaneous value), and refused boots from the active/standby active-instance guard (`polaris_ha_active_instance_conflict_total{holder}` — same dies-with-the-process reading as crashes, see the catalogue entry below).

**Multi-process scrape.** prom-client registries are per-process. In the split-role layout (`polaris-web` + `polaris-monitor@N` + `polaris-discovery`), the web process exposes `/metrics` on the main HTTPS listener, but every metric stamped from inside a monitor worker (`runProbeFor`, `runTelemetryFor`, `recordWorkOutcome`, sample-write timers) or discovery consumer (`recordDiscovery`, `observeDiscoveryPhase`, FMG proxy-lane gauges) lives in that worker's local registry. Each non-HTTP role boots a standalone `/metrics` listener via [src/utils/metricsServer.ts](src/utils/metricsServer.ts) when `POLARIS_METRICS_PORT` is set — systemd units default to 910N per monitor replica and 9110 for discovery. Prometheus must scrape **all** role endpoints; dashboard queries aggregate across instances (`sum` for per-process partitions like db_pool / sample buffers / workers, `max` for fleet-wide gauges that one process broadcasts and the others export as 0 — the metric is registered in every process's local registry by virtue of `src/metrics.ts` being imported everywhere) so panels populate as soon as the scrape job is complete. Single-process (`POLARIS_ROLE` unset / `=all`) is unaffected — one registry, one endpoint.

## Metric catalogue (from ARCHITECTURE.md)

- `GET /health` — gated by `HEALTH_TOKEN` (auto-generated at first-run setup; clearing it reopens the endpoint and surfaces the `health_token_unset` watch-severity reason on the Maintenance tab). Returns `{status: "ok"}` once the app has booted; the first-run setup wizard polls it (from localhost) with the bearer it just generated to detect when the main app has come up after finalize.
- `GET /metrics` — Prometheus text-format endpoint, gated by `METRICS_TOKEN` (auto-generated at first-run setup; clearing it reopens the endpoint and surfaces the `metrics_token_unset` watch-severity reason on the Maintenance tab — leaving `/metrics` open on a public deployment leaks fleet size, monitor health, monitor pass duration, and queue depth as recon data). **In the split-role layout, prom-client registries are per-process** — the web role serves `/metrics` on its main HTTPS listener, while monitor + discovery boot a standalone `/metrics` HTTP listener via [src/utils/metricsServer.ts](src/utils/metricsServer.ts) when `POLARIS_METRICS_PORT` is set (shipped systemd units pin monitor instances to `910N` and discovery to `9110`, both `127.0.0.1`). Prometheus must scrape every role endpoint; metrics stamped from monitor workers (`polaris_probe_*`, `polaris_monitor_work_*`, `polaris_sample_write_*`) or discovery consumers (`polaris_discovery_*`, FMG proxy lane) only exist in those processes' registries. Exposes default Node.js process / GC / event-loop metrics (un-prefixed so standard Grafana dashboards work) plus Polaris-specific gauges, histograms, and counters defined in `src/metrics.ts`. Polaris-specific metric names are prefixed `polaris_`. Currently exported:
  - `polaris_monitor_pass_duration_seconds` (histogram) — wall-clock of one `runMonitorPass`. Watch this rise toward the configured cadence as a saturation signal.
  - `polaris_monitor_work_duration_seconds{cadence,asset_type,transport}` (histogram) — per-work-item wall-clock. `cadence` is `probe | fastFiltered | telemetry | systemInfo | lldp | storage` (LLDP and Storage carved into their own queues + cadences in Phase 2 of the monitoring-tab redesign); `asset_type` is the `Asset.assetType` enum value (`firewall` / `switch` / `access_point` / `server` / `workstation` / `router` / `printer` / `other`); `transport` is the resolved per-cadence polling method (probe → `responseTimePolling`, telemetry → `cpuMemoryPolling`, systemInfo + fastFiltered → `interfacesPolling`, lldp → `lldpPolling`, storage → `storagePolling` — `rest_api` / `snmp` / `winrm` / `ssh` / `icmp` / `disabled` / `not_delivered` / `unknown`). Lets operators slice by device-class × transport to find which combo is the bottleneck (e.g. "SNMP on workstations is the slow tail, FortiOS REST on firewalls is fine"). Labels fall back to `unknown` when a pg-boss job was enqueued by an older release and replayed after upgrade.
  - `polaris_monitor_work_total{cadence,asset_type,transport,outcome}` (counter) — same label set; `outcome` is `success | failure | crash`.
  - `polaris_monitor_queue_depth{cadence}` (gauge; `cadence` gained `lossSample` in 2026-08 for the ICMP packet-loss sampler, which also reports through `polaris_work_duration_seconds` / the work-outcome counter with `transport="icmp"` whatever the asset's response-time stream uses -- that IS the finding the label should carry) — cursor mode only; queued items at the start of each `runMonitorPass` call. Frozen at the last probe-now value in pg-boss mode — use `polaris_pgboss_queue_jobs` instead for pg-boss deployments.
  - `polaris_probe_duration_seconds{transport}` (histogram) — per-probe RTT; `transport` is the resolved `responseTimePolling` for the asset (`rest_api` / `snmp` / `winrm` / `ssh` / `icmp`), with the source default substituted when the asset has no per-asset override.
  - `polaris_probe_total{transport,outcome}` (counter) — `outcome` is `success | failure`.
  - `polaris_monitored_assets` (gauge) — total assets with `monitored=true`. Updated by `setMonitoredAssets()`: in cursor mode fires inside `runMonitorPass`; in pg-boss mode fires inside `publishDueWork` at the end of every probe/heavy tick (~every 5–30s).
  - `polaris_monitored_assets_by_status{status}` (gauge) — `status` is `up | down | unknown`. `unknown` rolls up `null`, `"unknown"`, `"warning"`, and `"recovering"` states. Same update cadence as `polaris_monitored_assets`.
  - `polaris_monitor_queue_mode{mode}` (gauge) — always 1 for the queue mode captured at boot (`cursor` or `pgboss`). Set once by `initializeQueue()`. Use this to select which queue-depth metric family is authoritative on a given instance.
  - `polaris_monitor_workers{queue}` (gauge) — configured worker count per cadence queue. Static for the life of the process: in pg-boss mode this is each queue's `localConcurrency` (set by `startPgbossWorkers`) — `probe` / `fastFiltered` / `telemetry` / `systemInfo` / `lldp` / `storage` plus `floating`. LLDP + Storage default to 12 workers each (env `POLARIS_MONITOR_LLDP_WORKERS` / `POLARIS_MONITOR_STORAGE_WORKERS`); the rest default to 24. In cursor mode probe/fastFiltered map to `POLARIS_PROBE_CONCURRENCY` and telemetry/systemInfo map to `POLARIS_HEAVY_CONCURRENCY` (set at module load in `monitorAssets.ts`); LLDP + Storage stay coalesced inside the systemInfo handler in cursor mode (no dedicated pool). pg-boss mode also exposes `queue="floating"` showing the configured ceiling for the floating pool that polls all six queues in priority order (probe > fastFiltered > lldp > storage > telemetry > systemInfo; env `POLARIS_MONITOR_FLOATING_WORKERS`, default 32). Use this to confirm a restart picked up a new `cpus().length` after adding cores, or to verify an env-var override took effect.
  - `polaris_pgboss_queue_jobs{queue,state}` (gauge) — pg-boss mode only. Refreshed every 15s from `pgboss.job` by `refreshPgbossMetrics()` in `queueService.ts`. `queue` is one of the six `polaris-monitor-*` queue names (`probe` / `fastFiltered` / `telemetry` / `systemInfo` / `lldp` / `storage`) plus the `polaris-discovery-run` queue; `state` is `created` (queued), `active` (being processed), or `failed`. Zero-filled per queue×state on each refresh so stale values don't linger when a queue drains.
  - `polaris_fmg_worker_queue_depth{integrationId}` / `polaris_fmg_worker_inflight{integrationId}` / `polaris_fmg_worker_native_inflight{integrationId}` (gauges) — per-integration FortiManager worker (see `src/services/fmgWorker.ts`). Queue depth + inflight apply to the **proxy lane** (strict concurrency=1) which carries every `/sys/proxy/json` call; queue depth = waiting tasks, inflight = 0/1 for executing. Native-inflight is the **native lane** (unbounded) current concurrent count for CMDB / dvmdb / auth calls. A persistently non-zero proxy queue depth means the proxy lane is the bottleneck; a persistently high native-inflight count means the native lane is genuinely parallelizing (good). Correlate against `polaris_monitor_pass_duration_seconds` and discovery slow-run telemetry.
  - `polaris_db_pool_in_use` / `polaris_db_pool_peak_observed` / `polaris_db_pool_polaris_capacity` / `polaris_db_pool_max` (gauges) — DB connection-pool saturation. `in_use` is the live `pg_stat_activity` count; `peak_observed` is the rolling high-water mark `capacityService` tracks in module memory (resets on process restart); `polaris_capacity` is the combined Polaris-owned headroom (`prismaPoolSize + pgbossPoolSize`); `max` is the cluster-wide `SHOW max_connections`. Refreshed every 10 minutes by `capacityWatch.ts` after `getCapacitySnapshot()`. The actionable signal is `peak_observed / polaris_capacity` climbing toward 1.
  - `polaris_capacity_severity` (gauge, 0=ok, 1=watch, 2=amber, 3=red) plus `polaris_disk_free_ratio{volume,roles}`, `polaris_db_dead_tuple_ratio{table}`, `polaris_db_size_bytes`, `polaris_db_steady_state_size_bytes` — capacity headroom view. Refreshed every 10 minutes from the same `getCapacitySnapshot()` payload that drives the Maintenance tab. Volumes are pre-deduped by stat.dev. Lets you alert on "any disk < 20% free" or "dead-tup > 30%" without an admin loading the UI; `db_steady_state_size_bytes` plotted against `db_size_bytes` gives a long-term capacity-planning trend line.
  - `polaris_pgboss_oldest_job_age_seconds{queue,state}` (gauge) — age of the oldest pg-boss job per queue × state (`created` | `active`). Refreshed every 15s alongside `polaris_pgboss_queue_jobs`. Pg-boss mode only — stays at 0 in cursor mode. The pair of gauges (count + oldest age) distinguishes a 50-deep queue draining in 5s (fine) from a 50-deep queue stuck for 5 min (stalled worker).
  - `polaris_discovery_duration_seconds{integration_type}` (histogram) and `polaris_discovery_total{integration_type, outcome}` (counter, outcome ∈ `success | failure | aborted`). Recorded once per completed run alongside the existing `discoveryDurationService.recordSample()` callsite in `discoveryEngine.ts`. The histogram observes durations for successful runs only; failures and aborts increment the counter without polluting the latency distribution. Lets you answer "is discovery getting slower fleet-wide?" with a P95-over-time panel instead of crunching `integration.discover.completed` Event JSON.
  - `polaris_discovery_phase_duration_seconds{integration_type, phase}` (histogram) — wall-clock of one phase inside `syncDhcpSubnets` (FMG + standalone FortiGate). Observed at every `phaseMark()` transition in `discoveryEngine.ts` — same instrumentation point that the integration's verboseLogging flag uses to emit `discovery.phase.complete` log lines, but ALWAYS-ON regardless of the flag (the histogram is the bucketed-distribution story across runs; the log line is the per-line journalctl story for a single run). `phase` labels are the marker names used in code: `"1"`, `"2"`, `"2a"`, `"2b"`, `"2c"`, `"3"`, `"3b"`, `"3c"`, `"4"`, `"5"`, `"5b"`, `"6"`, `"7"`, `"7b"`, `"7.5"`, `"8"`, `"9"`, `"10"`, `"11"`, `"12"`, `"13"`. Pairs naturally with the run-level `polaris_discovery_duration_seconds`: when a discovery starts taking longer overall, this histogram shows which phase widened.
  - `polaris_sample_write_duration_seconds{table}` (histogram) — wall-clock of one bulk write into a monitor sample table. `table` ∈ `asset_monitor_samples`, `asset_telemetry_samples`, `asset_hardware_sensor_samples`, `asset_interface_samples`, `asset_storage_samples`, `asset_ipsec_tunnel_samples`, `asset_associated_ips`, `asset_lldp_neighbors`. Splits DB-write cost out of the broader monitor-work duration so a slow autovacuum / index bloat / lock contention is visible separately from network probe time. For the six buffered tables (everything except `asset_associated_ips` and `asset_lldp_neighbors`) the histogram observes one batched `createMany` per 2 s flush window — sample counts will be much lower than the per-asset work count, but each observation covers many rows.
  - `polaris_sample_buffer_depth{table}` (gauge) — rows currently held in `sampleWriteBuffer` per table. Oscillates between near-0 and the steady-state batch size between flush ticks; a value that climbs and stays elevated means flushes can't keep up with the enqueue rate (DB write contention or a stuck flush). Tables: same six as the histogram above minus the two synchronous ones.
  - `polaris_probe_patch_write_duration_seconds` (histogram) — wall-clock of one bulk `UPDATE … FROM (VALUES …)` flush from the probe-patch buffer (one observation per 2 s flush tick; each observation covers state writes for many assets at once). Splits the probe-path state-write cost out of `polaris_monitor_work_duration_seconds{cadence="probe"}` so a slow autovacuum or row-lock contention on the `assets` table shows up here distinct from network probe time.
  - `polaris_probe_patch_buffer_depth{table=assets:probe}` (gauge) — patches currently held in the in-memory probe-patch buffer. Oscillates between near-0 and the steady-state batch size between flush ticks. A persistently rising value means the flush can't keep up with the enqueue rate — usually DB write contention on the `assets` table. Single label value `assets:probe` so the gauge can grow into the telemetry/systemInfo cadences without renaming if the same pattern lands there.
  - `polaris_sample_rollup_duration_seconds{tier,table}` (histogram) — wall-clock of one `INSERT...ON CONFLICT` rollup statement. `tier` ∈ `hourly | daily`; `table` ∈ the six source names (monitor / telemetry / temperature / interface / storage / ipsec). Hourly cadence runs every 30 minutes; daily runs once at 02:30 UTC. Watch this to spot a rollup tick that starts dragging behind its cadence at fleet growth — the heavy-loop equivalent for the rollup writer. Buckets sized 50 ms to 5 min since rollup latency falls between sample-write latency and discovery-pass latency.
  - `polaris_db_connection_mode{mode}` (gauge) — set once at boot. The detected mode reads 1, the other label stays at 0. `mode="pgbouncer"` means Polaris detected POLARIS_DB_DIRECT_URL set distinct from DATABASE_URL (or DATABASE_URL carries `?pgbouncer=true`); `mode="direct"` is the single-URL default. Use this to confirm Polaris recognized the operator's PgBouncer setup without grepping logs.
  - `polaris_http_request_duration_seconds{method,route,status_class}` (histogram) and `polaris_http_in_flight` (gauge) — HTTP request latency + concurrent request count. `route` is the matched Express route template (e.g. `/api/v1/assets/:id`) so cardinality stays bounded; unmatched paths roll up to `unmatched`. `status_class` is `2xx`/`3xx`/`4xx`/`5xx`. `/metrics` and `/health` are excluded so scrape requests don't show up as application traffic. Mounted right after the CSRF middleware in `src/app.ts` so rate-limited and CSRF-rejected requests are still observed (their non-2xx status matters). Lets you tell at a glance whether a "the UI is slow" complaint is "DB pool exhausted" (latency up across all routes) or "this one route is hanging" (latency up on one route only).
  - `polaris_process_crash_total{role, kind}` (counter) — incremented by the last-resort handlers in `utils/crashHandlers.ts` immediately before the process exits; `kind` ∈ `unhandled_rejection | uncaught_exception`, `role` is `POLARIS_ROLE` (`all` when unset). The counter dies with the process, so its value in any single scrape is 0 or 1 — the operational signal is the RESTART: `increase(polaris_process_crash_total[1h])` summed across a role's instances turns an otherwise-invisible systemd `Restart=on-failure` loop into a graph. Before these handlers existed, an escaped rejection produced only Node's raw stack trace on stderr: no pino line, no metric, and the process came straight back.
  - `polaris_ha_active_instance_conflict_total{holder}` (counter) — incremented in `src/app.ts` immediately before `process.exit(1)` when `services/haHeartbeatService.ts → checkActiveInstanceConflict()` finds an active-instance heartbeat younger than 90 s written by a DIFFERENT hostname: two app instances pointed at one database, which double-polls every device and duplicates every alert. `holder` is the hostname that owned the stamp, or `unknown` when the stamp carried none. Only the role that runs schedulers evaluates the guard (`utils/role.ts → runsSchedulers`, i.e. `web` or `all`), so a monitor or discovery replica never contributes. Same reading discipline as `polaris_process_crash_total` above — the counter dies with the process, so any single scrape reads 0 or 1 and the signal is `increase()` — with one extra caveat: the process exits immediately, so a scrape can miss the increment altogether. A non-zero increase is definitive; its absence is NOT evidence the guard never fired, and the durable record is the `logger.fatal` line naming the holder and the stamp age. Read a bar as the guard WORKING: the boot was refused, not admitted. Graphed by the "Active-instance guard" row of `docs/grafana/polaris-monitoring-dashboard.json`. `POLARIS_HA_HEARTBEAT=off` disables the guard, and therefore this metric, entirely.
  - `polaris_job_duration_seconds{job}` (histogram) and `polaris_job_total{job, outcome}` (counter, outcome ∈ `success | failure`) — every scheduled background job ticks through `runInstrumentedJob(name, ...)` from `src/jobs/_metrics.ts`. Job labels are stable identifiers: `monitorAssets.probe` and `monitorAssets.heavy` (the two ticking loops in `monitorAssets.ts`), plus one entry per job module (`expireReservations`, `discoveryScheduler`, `discoverySlowCheck`, `pruneEvents`, `capacityWatch`, `dependencyReconciler`, `retryQueuedReservationPushes`, `reconcileMapRegions`, `decommissionStaleAssets`, `flagStaleReservations`, `ouiRefresh`, `updateCheck`, `reclaimBloatedChunks`, plus the one-shot startup migrations `clampAssetAcquiredAt`, `clampMonitoredForStatus`, `clampFailureBucket`, `normalizeManufacturers`, `backfillAssetSources`, `backfillFortigateEndpointSources`, `migrateMonitorSettingsHierarchy`, `migrateMonitorStatusRename`, `scrubLegacySidGuidTags`, `fixInfraAssetTypes`, `mergeFortiswitchEndpointGhosts`, `backfillDependencyTree`, `resolvePolarisPushedConflicts`, `resolveStaleReservationConflicts`). The wrapper observes duration + outcome but never changes a job's existing error semantics — thrown errors still propagate to the caller's existing try/catch. The actionable signal is a tick that starts taking longer than its interval (e.g. `dependencyReconciler` exceeds 60 s, or `monitorAssets.heavy` exceeds 30 s) — early warning that scheduled work is lagging.

  - `polaris_integration_test_total{integration_type, outcome}` (counter, outcome ∈ `success | failure | skipped`) — one increment per per-integration tick of `integrationConnectionTester`. `skipped` is the in-discovery-run branch at [src/jobs/integrationConnectionTester.ts](src/jobs/integrationConnectionTester.ts) which preserves prior `lastTestAt`/`lastTestOk` to avoid stamping a false-positive failure on a healthy FMG during a long-running discovery; `success` / `failure` mirror the lastTestOk write. The job already emits `integration.test.recovered` / `integration.test.failed` Events only on state transitions, so steady-state ticks were previously invisible — the counter + a `logger.info` line per outcome (in journalctl) close that audit gap. Watch a sustained `failure` run on one `integration_type` without a `success` follow-up to spot an integration stuck in the Failed state across multiple ticks.

  Settings-resolver cache hit/miss and per-FMG-task duration histograms remain deferred — low signal at current scale.
