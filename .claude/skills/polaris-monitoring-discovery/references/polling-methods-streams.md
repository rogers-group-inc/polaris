# Polling methods and streams

The monitor-settings route group and the per-stream polling-method matrix, verbatim from CLAUDE.md, plus the monitoring transport summary from the Tech Stack table and the FortiManager authentication note.
- **monitorSettings** (manual + integration + class overrides + asset overrides + per-stream resolver). Streams: `responseTime` / `cpuMemory` / `temperature` / `interfaces` / `lldp` / `storage`, plus the cross-transport **`processes`** + **`eventLog`** streams (collectable via agent / SNMP / SSH / WinRM / REST per a per-stream method matrix in `utils/pollingCompatibility.ts`; surface as stream tabs next to Storage on the integration Monitoring tab). `processes` is **agent-default-ON** (the `/config` drift self-heal stamps `processesPolling="agent"` for any installed agent, so agent hosts collect their process inventory automatically — like interfaces/storage); the agentless transports stay opt-in via the polling method — **SSH and WinRM are now implemented server-side** (the `"processes"` monitor cadence: `runProcessesFor` → `agentlessProcessService`, inventory at `processesIntervalSec` + a 60s pinned/mapped sub-pass for cpu/mem telemetry (monitoredProcesses) and Application Map connections (mappedProcesses); anchors `lastProcessesAt`/`lastProcessPinsAt` stamp even on failure so a bad credential can't retrigger every tick), SNMP (hrSWRunTable) remains declared-but-unimplemented. **`eventLog` is now collectable agentlessly too** — `runEventLogFor` (its own cadence, queue and `Asset.lastEventLogAt` anchor) runs `journalctl -o json -p warning` over SSH or `Get-WinEvent` levels 1–3 over WinRM into the SAME `ingestOsEventLog` sink the agent uses, gated by the SAME global `agentEventLog` master switch; the window is derived from the stream's interval (1.5×) rather than a row count, so a poll neither drops a burst nor re-ingests a quiet hour, and the anchor is stamped even on failure. It stays opt-in everywhere (PII/volume). **`cpuMemory`, `interfaces` and `storage` are now collectable agentlessly too** — `agentlessHostService` reads `/proc/stat` (twice, a second apart: CPU is a rate) + `/proc/meminfo` (MemAvailable), `/sys/class/net/*` and `df -PkT` over SSH, or `Win32_OperatingSystem` + `Get-NetAdapter`/`Get-NetAdapterStatistics` + `Get-Volume` over WinRM, on ONE connection per host per tick. Temperature and LLDP stay agent/SNMP-only (no dependable Windows thermal source, no shell LLDP at all). (The **`http`** polling method was RETIRED in 2026-08 — the HTTP check it ran is now a manufacturer custom widget, so it no longer appears in any stream's method list. See business rule 33.) **`rest_api` is gated on being able to make a FortiOS call at all**: a FortiManager on the PROXY transport with no `fortigateApiToken` cannot, because every FortiOS collector builds its config through `buildFortinetConfig()`, which has no `useProxy` branch — it dials the asset's own IP and needs that token. `defaultPollingForSource` therefore returns `disabled` for cpuMemory / temperature / interfaces there (response time stays `icmp`, unchanged deliberately), and the resolver's validity gate skips a *stored* `rest_api` the same way it skips any method the source can't use, so the layer below stays — non-destructively, since the stored value returns the moment a token is supplied. **A per-asset REST API credential is the SECOND token source, and the escape hatch from the fleet-wide one** (2026-09): the integration's token is shared by every gate it manages ("must be the same across all managed FortiGates", says the field's own hint), so a fleet where each gate carries its own api-user could not be polled over REST at all. `buildFortinetConfig` now prefers the `restapi`-typed Credential the operator selected on that asset's stream — chain `asset.<stream>Credential ?? asset.monitorCredential`, type-filtered, in `utils/fortinetRestCredential.ts`; the class-override tier is deliberately NOT consulted, a credential shared by a whole asset class being the fleet-wide token this exists to escape. It contributes **auth plus port and TLS verification only — the target stays the asset's own address**, so one credential mistakenly selected on twenty gates cannot poll ONE device and file its CPU under all twenty; the `baseUrl` host is read for the port and otherwise ignored (it is what the credential's own Test button dials, and a wrong host is a mis-attribution that looks exactly like real data). A stream carrying one is also **exempt from the skip above** (`assetStreamCredentialId`), since a per-asset token is precisely what makes the call possible where the fleet-wide one is absent — discarding it there would hide the operator's fix for the condition being detected. Wired for all five REST streams (responseTime / cpuMemory / temperature / interfaces / lldp) and deliberately not for the FortiAP controller-cache reads, which authenticate to the PARENT gate. The asset modal had been offering that picker on every `rest_api` stream all along (`_credTypeForPolling` maps rest_api → restapi) while the collector never read it, so the selection persisted, resolved, and collected nothing — the `pollingCapability.ts` failure class, one layer further in. The one exception is a managed FortiSwitch / FortiAP's response time, which rides the parent gate's controller table via `fetchViaFortinetTransport` (the one monitoring path honouring `useProxy`) and works on FMG's own credential; the shared predicate is `fortiosRestUsable(stream, assetType)`. Note the condition is NOT "proxy mode" — proxy WITH a token is a valid setup and keeps the normal REST defaults. The **`fortimanager`** polling method (2026-08-28) asks FortiManager's own device database instead of the device: **response-time only** (`FORTIMANAGER_STREAMS`) on the **`fortimanager` source only**, reading `conn_status` / `ha_slave[].status` out of one NATIVE `/dvmdb/adom/<adom>/device` call that is outside the `/sys/proxy/json` concurrency-1 lane and covers the whole fleet — so ~187 gates cost one round trip, and a gate Polaris has no route to is still reachable. Keyed by **serial, never the FMG device name**; **FMG unreachable ⇒ `ProbeResult.skipped`**, never a miss (one manager outage must not down a fleet — the vCenter rule). It is lagged, second-hand, and carries **no uptime** (so no reboot detection), and FMG stores no metrics of any kind, which is why it is one stream rather than a transport. **Not a source default** — response time stays ICMP. The **`vcenter`** polling method covers FOUR streams (`VCENTER_STREAMS` in `pollingCompatibility.ts`, enforced by `isMethodValidForStream`): `responseTime`, `cpuMemory`, `interfaces` and `storage` — everything the vCenter server publishes about a VM or an ESXi host. It is the **source default for all four on both roles** (it was cpuMemory-only until 2026-08, with response time on ICMP), which is what lets a vCenter fleet be monitored with no credential in the guest, no SNMP enabled on ESXi and no reachable guest IP. Two warm caches in `monitoringService` (30s TTL + promise-singleton, one SOAP round trip per integration per tick each) back it: `fetchVcenterQuickStatsCached` for VMs (CPU/RAM, power state, uptime, `guest.disk`, `guest.net`) and `fetchVcenterHostSnapshotCached` for ESXi hosts (CPU/RAM, connection state, uptime, pNICs + VMkernel ports + virtual switches, paired with the datastore inventory in ONE session — the SAME fetch discovery's Phase 2 uses, whose two halves report failure separately so a host-property gap can't cost discovery its datastore detail). **A host's interfaces arrive nested**: `buildVcenterSystemInfo` writes each vSwitch (standard, or the host's end of a DVS) as an `ifType:"aggregate"` row and stamps `ifParent` on its uplink pNICs and on the vmks riding its port groups — the FortiSwitch-trunk shape, so the System tab nests it unchanged — and each vmk picks up its port group's `vlanId` through the same name-to-name join. A vSwitch's `operStatus` is derived (up while any uplink is up, **null with no uplinks at all**, since an internal-only vSwitch is not an outage) and carries no `speedBps`, vCenter publishing no aggregate rate. Teaming policy, port counts and the port-group VLAN table are inventory and render on the host's General-tab Virtualization section instead; a DVS's own configuration is a per-vCenter object and is deliberately not read. `readVcenterAsset` resolves the reading through the asset's `vcenter-vm` **or** `vcenter-host` AssetSource — not `discoveredByIntegration` — which is also why the method is allowed on the directory source kinds (a vCenter sync merges into AD/Entra-discovered VMs); the per-asset PUT validation requires that row. **Absent ≠ unreachable**: vCenter answering without this asset in it is a real finding and fails the probe, while Polaris being unable to ASK skips it (`ProbeResult.skipped` — no sample, no counter, cadence anchor only), so a vCenter outage can never declare an entire virtual fleet down at once. Temperature and LLDP stay unavailable on the method; the dedicated storage-only cadence (`runStorageFor`) stays SNMP-only because vCenter storage already rides the system-info pass.

## FortiManager authentication

**FMG auth note:** FortiManager 7.4.7+ / 7.6.2+ removed `access_token` query string support. The service uses the Bearer `Authorization` header exclusively. The standalone FortiGate integration (`fortigateService.ts`) uses the same Bearer pattern. **Never call `/sys/logout`** — Polaris authenticates with a predefined REST API Admin api-key, which per Fortinet's FMG API Best Practices Guide is permanent and shares one session per user; logout/login endpoints are for session-based auth only. A prior hourly `/sys/logout` (commit 3e70476) tore that shared session out from under the split-role monitor/discovery processes and caused RPC `-11` "no valid session" churn — removed. The transport layer (`rpcInner`) retries transient faults only (5xx/network, ≤2 retries, exponential backoff, serialized in the FmgWorker lane) and fails fast on permanent ones (401/403/404/405, `-11`).

## Monitoring transports (Tech Stack cell)

net-snmp (SNMP v2c/v3 authenticated GETs against `sysUpTime`); ssh2 (SSH connect+authenticate); built-in `node:https` / `node:http` (FortiOS REST + WinRM SOAP Identify + the **HTTP check** health probe — one GET, status code + optional response-body match, `utils/httpCheck.ts`, run as a manufacturer custom widget); spawn the system `ping` for ICMP — **batched**: ICMP is the one transport where a single process serves many hosts, so due assets are published as chunks and pinged through one fping per distinct `probeTimeoutMs` (`pingTargets`), one echo each. **One reading per cadence, stamped when the echo went out**: a chunk runs until its slowest target times out, which is a whole 5 s publisher tick, and the stately probe queue lets that next tick's copy of the chunk queue behind the ACTIVE one. Every item therefore carries its resolved `intervalSec`, and `runProbeBatchFor` drops the assets the earlier job already polled (`probeStillDue` in `utils/monitorStatus.ts`, which also reads the unflushed probe-patch stamp). Each reading is recorded at the instant the echoes were sent (`recordProbeResult`'s `observedAt`), not when the chunk finished. Without both, every ICMP asset charted two readings a few seconds apart on a ~75 s rhythm and counted every miss twice toward `missedPolls`. Per-asset probe jobs carry `probeIntervalSec` for the same pickup re-check, returning `ProbeResult.duplicate` (which, unlike `skipped`, does not even stamp `lastMonitorAt`). Every other transport stays one job per asset, because SNMP / WinRM / SSH / REST each need their own authenticated conversation — `snmpMultiGet` batches OIDs WITHIN a session and cannot span hosts. The two existing cross-device batchers are REST: `fetchFmgRosterCached` (one `/dvmdb` read serves every gate FMG manages) and the vCenter warm caches. **Packet loss is a separate measurement**: a uniform burst of 5 echoes at every eligible asset each cycle, batched through **fping** when it is installed (one process per 500 targets) and falling back to per-host `ping` bursts when it is not — `utils/burstPing.ts` / `utils/lossSweep.ts`. fping is an OPTIONAL dependency (EPEL on RHEL, no Windows build at all), so the fallback is a supported path rather than a safety net; "not available" covers NOT INSTALLED **and installed-but-unexecutable** — `fping`/`ping` carry `cap_net_raw=ep` on Debian, so a process without CAP_NET_RAW fails execve with EPERM, which `spawn` throws synchronously rather than reporting on the child (see `detectFping` in the src-utils-1 file map: an uncaught throw there was memoized as a rejection and killed every monitor pass); the sweep cadence is floored at what the installed pinger can actually finish
