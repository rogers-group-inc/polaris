## Entra ID / Intune Discovery Workflow

`entraIdService.ts` queries Microsoft Graph via OAuth2 client-credentials flow to sync registered devices as assets. **Produces assets only** — no subnets, reservations, or VIPs — so it uses a dedicated `syncEntraDevices` path in `discoveryEngine.ts` rather than the shared `syncDhcpSubnets` pipeline.

- **Auth** — `POST https://login.microsoftonline.com/{tenantId}/oauth2/v2.0/token` with `grant_type=client_credentials`, scope `https://graph.microsoft.com/.default`. Tokens are cached in-memory by `tenantId:clientId` until expiry.
- **Endpoints** —
  - Always: `GET /v1.0/devices` (paged via `@odata.nextLink`, `$top=999`, hard cap 10,000). Requires `Device.Read.All` (application permission, admin consent).
  - When `enableIntune=true`: `GET /v1.0/deviceManagement/managedDevices`. Requires `DeviceManagementManagedDevices.Read.All`. Merged onto Entra devices via `azureADDeviceId ↔ deviceId`; Intune data wins on any shared field.
- **Device identity** — the Entra `deviceId` (GUID) is the stable key. Persisted as the `externalId` on per-source `AssetSource` rows (`sourceKind="entra"`/`"intune"`). Phase 4d retired the legacy `Asset.assetTag = entra:{deviceId}` mirror — re-discovery and search both query AssetSource directly. Existing assetTag values on rows discovered before Phase 4d are preserved (back-compat); new Entra-discovered assets have `assetTag = null`.
- **Multi-source asset model (Phase 2 cutover)** **and the projection layer** (Phase 3b.1 cutover) — the Entra/Intune sync is on the new `AssetSource` model. Each Graph endpoint that contributed to a discovered device produces its own row: `sourceKind="entra"` for the `/v1.0/devices` view (trustType, accountEnabled, SID, registration/sign-in timestamps, compliance flags, original entra `displayName`) and `sourceKind="intune"` for the `/v1.0/deviceManagement/managedDevices` view (serial, manufacturer, model, Ethernet+WiFi MACs, `userPrincipalName`, `chassisType`, `complianceState`, `lastSyncDateTime`, original intune `deviceName`). Both rows share the same `externalId = deviceId.toLowerCase()` but different `sourceKind`s. Hybrid devices have both rows; Entra-only and Intune-only devices have just one. **Discovery-owned Asset fields** (hostname, os, osVersion, learnedLocation, serialNumber, manufacturer, model) come from `projectAssetFromSources()` — every update path (primary existing-asset, SID-takeover, duplicate-Entra-registration "incoming wins" auto-resolve) upserts the entra/intune sources first, re-fetches all sources for the asset (which may include AD on hybrid devices so the projection's AD-FQDN-first hostname rule kicks in), computes projection, and writes a single Asset.update with projected + non-projected fields. The create path projects from a synthetic source array built directly from the new device's observed blobs (entra/intune as appropriate per `dev.sources`) — pure, no DB roundtrip needed for new assets. After upsert, `upsertEntraIntuneSources` **sweeps stale entra/intune rows on the same Asset whose externalId differs from this device's deviceId** — covers the duplicate-Entra-registration "incoming wins" auto-resolve path so the prior identity doesn't orphan-link a future discovery to the wrong asset. The `entraIdService` `DiscoveredEntraDevice` shape carries a `sources: ("entra"|"intune")[]` field plus original `entraDisplayName` / `intuneDeviceName` so the sync can split the merged record back into source-shaped blobs without lossy heuristics.
- **Re-discovery** — Assets are matched in this order: (1) any `AssetSource` row of `sourceKind in ("entra","intune")` with matching `externalId = deviceId.toLowerCase()`, (2) on-prem SID match — resolves through `entra.observed.onPremisesSecurityIdentifier` or `ad.observed.objectSid` (hybrid-joined devices the AD integration already created — Entra **takes over** in that case, signaled by the SID-matched asset having no entra/intune source yet), (3) hostname collision against an untagged asset → a `Conflict` (entityType `"asset"`, deduped on `proposedDeviceId`) is created for admin/assetsadmin review. "Untagged" under the new model means **the asset has no entra/intune source AND no AD source**. The slide-over panel renders a side-by-side comparison; **Accept** adopts the existing asset (writes the Entra assetTag + fills empty fields from the snapshot), **Reject** creates a separate asset with the Entra tag so future runs find it by tag.
- **Asset type** — inferred from Intune `chassisType` (`desktop/laptop/convertible/detachable` → `workstation`; `tablet/phone` → `other`); Entra-only devices default to `workstation`. Admins can recategorize via the asset edit UI; re-discovery only overwrites `assetType` if it is still `other`.
- **User** — Intune `userPrincipalName` → `Asset.assignedTo`. Entra-only runs do not populate this field.
- **MACs** — Intune supplies both `wiFiMacAddress` and `ethernetMacAddress` per managed device. Both are stored as separate entries in `Asset.macAddresses[]` with sources `"intune-wifi"` and `"intune-ethernet"`, and the asset's primary `macAddress` column is set to whichever was most recently updated (Ethernet preferred when both are reported on the same sync, since modern Windows / iOS / Android randomize the WiFi MAC per network and the Ethernet MAC is the more stable identity). The asset details panel renders both in the "All MACs" list with pretty source labels ("Intune — Ethernet" / "Intune — Wi-Fi"). The `mac-collision` conflict pathway only matches against the **Ethernet MAC** for the same randomization reason; WiFi MAC is informational and used by FortiGate DHCP-discovery's MAC-based asset matching to broaden the chance of an incoming DHCP lease landing on the right asset row.
- **Disabled devices** — `accountEnabled` is fetched for every Entra device. When `includeDisabled=true` (default), disabled devices are synced as `decommissioned` assets and get an `entra-disabled` tag. When `includeDisabled=false`, they are skipped entirely — matching the AD integration's `includeDisabled` behavior.
- **Filters** — `deviceInclude` / `deviceExclude` arrays match against `displayName` with wildcard support (`LAPTOP-*`, `*-lab`).

## Active Directory Discovery Workflow (On-premise)

`activeDirectoryService.ts` queries an on-premise domain controller via LDAP simple bind (over LDAP or LDAPS) and syncs computer objects as assets. **Produces assets only** — no subnets, reservations, or VIPs — so it uses a dedicated `syncActiveDirectoryDevices` path in `discoveryEngine.ts`.

- **Library** — `ldapts` (Promise-based LDAP client; TypeScript types bundled).
- **Auth** — simple bind using `bindDn` (full DN of a read-only domain user) and `bindPassword`. No Kerberos/GSSAPI. Default port 636 (LDAPS) or 389 (plain LDAP).
- **Query** — paged subtree search under `baseDn` with filter `(&(objectCategory=computer)(objectClass=computer))`, page size 1000, hard cap 10,000. Search scope `sub` (default) or `one`.
- **Device identity** — AD `objectGUID` (decoded as lowercase hex). Persisted on `Asset.assetTag` as `ad:{guid}` when the AD integration creates the asset.
- **Disabled accounts** — `userAccountControl & 0x2` (ACCOUNTDISABLE). When `includeDisabled=true` (default), these still sync but are created/updated with `status = decommissioned` and get an `ad-disabled` tag. When `includeDisabled=false`, they're skipped.
- **Attribute mapping** — `dNSHostName` (fall back to `cn`) → `hostname`+`dnsName`; `operatingSystem` → `os`; `operatingSystemVersion` → `osVersion`; `description` → `notes` (only if empty); `whenCreated` → `acquiredAt` (only if older); `lastLogonTimestamp` (Windows FILETIME) → `lastSeen` **only if newer than the existing value** — never regresses fresher data from Entra/Intune; `distinguishedName` OU path → `learnedLocation`; `operatingSystem` fed through `inferAssetTypeFromOs()` → `assetType` (only if still `other`).
- **Note on `lastLogonTimestamp`** — this attribute replicates approximately every 14 days by design. Use it as a coarse "last seen" signal; it will lag reality.
- **Filters** — `ouInclude` / `ouExclude` arrays match against the computer's full `distinguishedName` with wildcard support (e.g. `*OU=Workstations*`, `*OU=Servers,OU=HQ*`).
- **Forward-DNS IP backfill** — AD computer objects don't carry an IP, so `syncActiveDirectoryDevices` runs a forward-DNS pre-pass (A/AAAA lookup via `getConfiguredResolver()`) before the per-device upsert loop. Fills `Asset.ipAddress` on **new devices** and **existing devices whose `ipAddress` is empty**; devices that already have an IP from any source (FortiGate DHCP/ARP, Entra/Intune, operator-typed) are skipped — DNS can lag the real network state and we don't want to overwrite authoritative data. Failures (NXDOMAIN, resolver timeout, etc.) leave the IP null and retry on the next discovery cycle; a temporarily-missing DNS record self-heals. Bounded concurrency via the existing `batchSettled` helper (50 in parallel). Result Map keyed by `objectGuid.toLowerCase()` so each update/create looks it up cheaply. IP source stamped `ipSource = "activedirectory-dns"` to distinguish background AD-driven lookups from the operator-triggered `POST /assets/:id/forward-lookup` (which stamps `"dns"`). The Prisma extension in `src/db.ts` auto-populates `AssetIpHistory` rows on the write. If the configured DNS resolver factory throws (misconfigured DoH URL, etc.), the pre-pass logs a warning event and the rest of the sync proceeds without IP backfill — non-fatal.
- **Monitor default for realm-monitorable hosts** — Computer objects whose `operatingSystem` contains "windows" or "linux" are stamped with `discoveredByIntegrationId` *on first sight* so the polling-method resolver can see the AD source link. The default response-time polling method for AD-discovered assets is **ICMP** (the source default for the activedirectory source kind) — modern hardened Windows hosts often refuse WinRM by default and most domain-joined Linux doesn't enable SSH. Operators who want the bind-credentials probe set `responseTimePolling = "winrm"` (Windows) or `"ssh"` (realm-joined Linux) on the asset; the dispatcher's AD bind-credentials fallback (`probeAsset` in `monitoringService.ts`) routes those calls through the integration's `bindDn`/`bindPassword` — WinRM SOAP Identify against `https://<host>:5986` for Windows, SSH connect+auth on port 22 for Linux. **The bind DN must be in UPN form (`user@domain.com`) or down-level form (`DOMAIN\user`)** so WinRM/realmd accept it; raw LDAP DN form (`CN=svc,OU=...`) authenticates against LDAP bind but fails the probe. No separate Credential row is needed — the integration's bind credentials cover any AD asset whose `monitorCredentialId` is null. The legacy "discovery stamps `monitorType = activedirectory`" pathway was retired in step 3i of the polling-method redesign; existing AD-discovered assets that were on the bind-creds probe before the redesign keep that behaviour because the migration job (3e) projected `monitorType="activedirectory"` to `responseTimePolling="winrm"` / `"ssh"` per `getAdMonitorProtocol(os)` before the column was dropped.

### Hybrid-join cross-link (AD ↔ Entra ID)

Active Directory and Entra ID identify the same hybrid-joined device with two unrelated GUIDs (AD `objectGUID` vs Entra `deviceId`). The reliable cross-link is the on-prem **SID** — AD's `objectSid` equals Entra's `onPremisesSecurityIdentifier`.

- **AD discovery is on the multi-source asset model** (Phase 2 cutover) **and the projection layer** (Phase 3b.1 cutover): the AD sync writes an `AssetSource` row with `sourceKind="ad"`, `externalId=<objectGUID>`, and a rich source-shaped `observed` blob containing the raw LDAP fields (objectSid, cn, dnsHostName, distinguishedName, ouPath, OS+version, description, whenCreated, lastLogonTimestamp, accountDisabled). Lookups for re-discovery (GUID match), hybrid-cross-link (SID match), and hostname-collision detection all read from `AssetSource` (joining Entra rows for SID matches via `observed.onPremisesSecurityIdentifier`). The legacy `assetTag = "ad:{guid}"` and `tags = ["ad-guid:{guid}", "sid:{SID}", ...]` markers are still written for back-compat with the rest of the codebase; they're retired in Phase 4. **Discovery-owned Asset fields** (hostname, os, osVersion, learnedLocation, serialNumber, manufacturer, model) come from `projectAssetFromSources()` instead of inline merge logic — for the existing-asset path the AD source is upserted first, then all of the asset's sources are re-fetched and projected; for the create path the AD source's observed blob is projected synthetically (single-source array, no DB roundtrip needed). Operator-owned fields (status, lastSeen, acquiredAt, assetType, notes, tags, monitor stamps, dnsName) keep their inline logic — projection only owns what discovery owns. Single Asset write per device per cycle.
- Both services still stamp `sid:{SID}` (uppercase) in the asset's `tags` array.
- AD additionally stamps `ad-guid:{guid}` (lowercase hex) in `tags` so the AD GUID stays findable even after Entra takes over the primary `assetTag`.
- **Priority rule:** when both sources have the same device, Entra "takes over" the existing Asset row by upserting its own AssetSource entra/intune row keyed on `deviceId`. If AD created the asset first, the next Entra run finds it via the SID cross-link (entra.observed.onPremisesSecurityIdentifier ↔ ad.observed.objectSid) and stamps the entra source row alongside the existing ad source row — both AssetSource rows now live on the same Asset. If Entra created it first, the next AD run finds it via SID and stamps the ad source row in the same way. Phase 4d retired the assetTag mirror; AssetSource.externalId is the only canonical lookup key going forward.
- **MAC cross-link (Entra-only, tertiary).** When the Entra deviceId lookup misses AND the SID lookup misses (or the device has no SID — e.g. cloud-only Azure AD joined with no on-prem identity), the Entra sync falls through to a third match: incoming **Ethernet MAC** against `Asset.macAddress` and `Asset.macAddresses[]` history (any entry, any source). MAC matches are treated as positive identity confirmation — same physical box, just got a new Entra deviceId (re-enroll, re-image, NIC swap into a previously-known device) — and silently take over the matched asset the same way SID does. WiFi MAC is *not* used for this cascade because it randomizes per-network on modern Windows / iOS / Android. Every silent take-over writes one info-level `syncLog` event (`MAC cross-link: ...`) so the merge is auditable. This pathway replaced the noisy `mac-collision` conflict flavour, which was raising operator-review queues that almost always resolved as "yes, same device."
- **Integration filter** — `assetMatchesIntegrationFilter` for AD prefers the AD AssetSource's `observed.ouPath` over the merged `Asset.learnedLocation`. Source-side data is authoritative because the merged `learnedLocation` field can drift between integrations (a FortiGate sighting can overwrite AD's OU path), but the AD source's own observation is fixed by what LDAP returned at the last AD sync. Falls back to `learnedLocation` for callers that haven't loaded sources yet (back-compat).
- **Conflict records** — the asset-conflict schema now carries `proposedAssetFields.assetTagPrefix` (`"ad:"` or `"entra:"`) so the accept/reject route applies the correct tag. Entra-only conflicts predating this field still default to the Entra prefix for backward compatibility. vCenter-raised conflicts carry `proposedAssetFields.sourceType = "vcenter"` instead (with `assetType` discriminating VM vs ESXi host); `conflictSourceFor` in `conflictResolutionService.ts` dispatches the accept/reject tag + AssetSource handling across all three source families.

### vCenter discovery workflow

`vcenterService.ts` discovers VMs, ESXi hosts, and datastores from a VMware vCenter server (7.0U2+). **Produces assets only** — the dedicated `syncVcenterDevices` path in `discoveryEngine.ts` consumes the result, and `"vcenter"` is in the `assetsOnly` set so the AD/Entra post-sync passes (agent auto-deploy + interface/storage auto-monitor for the `virtual_machine` klass — a class-key name only; the assets it selects are `server`-typed and scoped by `discoveredByIntegrationId` — presence verification for everything) run after the sync.

- **Transports** — vSphere Automation REST (`POST /api/session` with Basic auth → `vmware-api-session-id` header; one automatic re-auth on a mid-run 401; logout in `finally`) for inventory, plus SOAP property-collector calls against `/sdk` for what REST doesn't expose: batched VM quickStats (`summary.quickStats.overallCpuUsage`, `summary.runtime.maxCpuUsage`, `guestMemoryUsage`, `uptimeSeconds`, `config.hardware.memoryMB`, plus `guest.disk` + `guest.net` for the monitored guest's filesystems and vNICs), batched ESXi host stats (`runtime.connectionState`/`powerState`/`inMaintenanceMode`, `summary.quickStats.overallCpuUsage`/`overallMemoryUsage`/`uptime`, `summary.hardware.cpuMhz`/`numCpuCores`/`memorySize`, `config.network.pnic` + `vnic` + `vswitch` + `proxySwitch` + `portgroup`) and datastore facts (`summary.*`, `host` mounts, `info` backing — VMFS extent NAA ids / NFS remote host). SOAP failures degrade to nulls; datastores fall back to the REST list (no mounts/backing/provisioned).
- **Call plan** — clusters → hosts (+ per-cluster membership; absent from every cluster = standalone) → datastores + host virtual networking (SOAP-primary, ONE `fetchVcenterHostSnapshot` shared with the monitor loop; the host half is best-effort — a failure logs `discover.vcenter.hostnet` and leaves `vswitches` null, while a datastore-half failure still triggers the REST fallback) → per-host VM lists (`GET /api/vcenter/vm?hosts=<moref>`, which pins VM→host placement and sidesteps the 4000-item global list cap) → per-VM detail + Tools state + (Tools RUNNING only) guest identity / networking at bounded concurrency (8) → quickStats merge → DNS-resolve host FQDNs (REST exposes no host mgmt IP).
- **Identity** — VM externalId = `instanceUuid` (survives vMotion), falling back to `${integrationId}:${moref}`; host externalId = `${integrationId}:${hostMoref}` always (morefs repeat across vCenters). AssetSource kinds `vcenter-vm` / `vcenter-host`.
- **Sync order** — hosts first (so VM blobs can link `hostAssetId`), then VMs, then dependency edges, then datastores + the stale-AssetSource sweep. VM match cascade: vcenter-vm source by externalId → vNIC MAC (positive-identity takeover, mirrors the Entra Ethernet-MAC rule; connected NICs first) → hostname collision → pending Conflict → create (`assetType="server"` — the dedicated `virtual_machine` built-in was retired by migration 20260722000000; VM identity lives in `Asset.virtualization` + the vcenter-vm AssetSource row). Merged directory assets keep their assetType (flip only from `"other"`) and `discoveredByIntegrationId`. Because VMs share the `server` type with directory machines, the VM-class behaviors (dependencyLayer=2 stamp, vmMonitor monitored-sweep) gate on ownership (`discoveredByIntegrationId === this integration`, or the other→server flip in the same write) — never on the type — so vCenter can't fight a directory integration over a MAC-matched server it merely enriches. In `monitorOverrideService` / `pickClassStreamsBlock`, `server` dispatches by integration type: vcenter → `vmMonitor`, directory → `serverMonitor`.
- **Sibling hostname collision (both assets exist)** — when a VM/host already has its own Polaris asset AND a *second*, non-vCenter asset shares its hostname (directory discovered the guest separately; no vNIC MAC tied them), both the host pass and the VM pass raise a review Conflict carrying `proposedAssetFields.bothAssetsExist=true` (mirrors the Entra sibling check, which now stamps the same flag). This surfaces the duplicate in the **Conflicts** queue with an **Apply merge** action instead of forcing the operator through asset-details → Sources → Merge asset → search. Accept runs the standard `acceptAssetConflict` ghost-absorb (the collision-target asset survives; the vCenter asset is absorbed — fields + MACs + **all** of its AssetSource rows, re-bound not cascade-dropped, see "The absorb preserves the duplicate's provenance" above — then deleted). Reject records the decision and creates nothing: `rejectAssetConflict` short-circuits when the proposed `(sourceKind, externalId)` already owns an asset, and the resolved conflict row suppresses re-raise.
- **Projection** — `vcenter-vm`/`vcenter-host` rules sit directly below `polaris-agent` in every relevant rule array (hostname ← Tools guest hostname else VM name; os ← Tools guestOsFullName / constant "VMware ESXi"; manufacturer/model constants for VMs; ipAddress ← Tools guest IP / DNS-resolved host FQDN, above `fortigate-endpoint` but below the infra `mgmtIp` rules). No serial rule (the VMware pseudo-serial would fight agent DMI serials); no host osVersion (not exposed by REST).
- **Dependency edges** — `buildVcenterDependencyEdges` writes `AssetDependencyParent` rows with `source="vcenter"`, `detectedVia="hypervisor"`: one edge per cluster-member host for clustered VMs (all-down semantics → suppression only when the whole cluster is dark → vMotion-safe), single edge for standalone hosts. Delete-replaced per run scoped to `source="vcenter"` on this integration's VM assets; the Fortinet recompute (`source="computed"`) and operator overrides are never touched, and `loadEffectiveParents` buckets any non-override source as computed so the reconciler needs no changes.
- **Datastores** — current-state `VcenterDatastore` rows (delete-replace per run) with `backingLabel` derived from the NAA OUI prefix (e.g. `naa.624a9370…` → "Pure Storage") or `NFS: <remoteHost>`. Rendered on the ESXi host's Virtualization section via `GET /assets/:id/virtualization`, and — for a host on the `vcenter` storage stream — sampled per host as `AssetStorageSample` rows keyed by datastore name, so the System tab's Storage table charts them with history and alerting like any other mount.
- **Disappearance sweep** — the last pass of `syncVcenterDevices`. Source rows from this integration whose externalId is no longer in the inventory are deleted, and an asset that is left with **no AssetSource row at all** is flipped to `status="decommissioned"` (`asset.vcenter.decommissioned` Event, `releaseAssetsForDecommission` first so an open maintenance window is force-closed and the 30s reconcile can't re-flip it). An asset that keeps ANY other source — a directory record, an `arc` row, a reporting Polaris Agent, the `manual` row of an operator-created asset — is left exactly as it is: vCenter losing sight of it is not the fleet losing sight of it. Three innocent causes of absence are excluded first, and the two decisions are pure + unit-tested in `vcenterService.ts`: **`vcenterSweepBlockedReason`** refuses the whole pass on an incomplete read (`inventoryComplete=false`, i.e. some per-host VM list failed — those failures are caught and logged so one unreachable ESXi host can't fail the run, which makes a partial inventory indistinguishable from a deleted fleet) and on an empty one (zero hosts AND zero VMs, business rule 35's shrunken-read reasoning), skipping the source deletes too — deleting them alone would leave the next complete run with nothing to notice. **`partitionStaleVcenterSources`** then RETAINS rows whose moref is still in `result.presentVmMorefs` (the raw per-host listing, taken before the `vmInclude`/`vmExclude` filter and before the detail fan-out), so a filter change or one failed detail call reads as "still there" rather than as a deletion — the same call the FortiGate roster sweep makes. Host rows are never retained that way: the host list arrives whole or throws. Time-based aging (months of inactivity) stays with `decommissionStaleAssets`; this is the evidence-based path.

- **Scoped (single-device) vCenter runs.** The asset slide-in's **Discover Now** narrows a run to one VM (`vcenter-vm` scope, by `Asset.virtualization.vmMoref`) or one ESXi host (`vcenter-host`, by `hostMoref`) — the moref comes from that blob, NOT from the source row, whose externalId is the instanceUuid. The collector keeps Phases 1/2/5/6 (bounded by HOST count) and skips the expensive part: Phase 4's 3–4 REST calls PER VM. Phase 1 is not optional even for a VM scope — VM→host placement is derived from the per-host listing, and a VM written without its host would clobber `virtualization.hostAssetId` — so a VM-scoped run still asks each host for that ONE moref (`vms=` filter, 0 or 1 rows each). A host-scoped run skips VM listing entirely and returns only the target host.

  **Three passes are suppressed**, via the pure exported gate `vcenterPassEnabled(mode, pass)` in `discoveryEngine.ts` (unit-tested beside `sweepPhaseEnabled`): the **dependency-edge** delete-replace (its scope is `priorVmAssetIds` — EVERY VM asset the integration owns — so a one-VM run would wipe VM→host suppression fleet-wide), the **datastore** delete-replace (keyed on the integration, and a scoped result carries no datastores, so it would empty the table), and the **disappearance sweep** above. The sweep gets a SECOND, independent guard: a scoped result sets `scoped: true` AND `inventoryComplete: false`, and `vcenterSweepBlockedReason` refuses on either — `scoped` is checked first so the operator is told "the run was scoped to a single device" rather than the misleading "a per-host VM list failed". Two guards because that pass decommissions assets and fails silently.

- **Scoped Arc runs** (`arc-machine` scope, by ARM resource id — the `arc` source's externalId) need no sync-side mode: `syncArcDevices` has NO fleet-absence passes. It deliberately never writes `status` (a Disconnected agent is a REACHABILITY fact; mapping it to a lifecycle state would decommission a fleet during an outbound-proxy outage) and issues no bulk delete/update. The scope is applied CLIENT-SIDE beside the resource-group/name/tag filters — only GUID-validated subscription ids ever reach the Resource Graph KQL — and there is nothing to gain by pushing it down, since Arc discovery is a fixed ~3 queries regardless of fleet size. A scoped Arc run also skips the connected-Kubernetes cluster query: clusters are separate assets, and refreshing one server has no business creating them.
- **lastSeen** — powered-on VMs / CONNECTED hosts get `bumpLastSeen(..., "vcenter")`; the source is in `POLLING_DEFERRED_SOURCES` so monitored assets stay probe-authoritative.
- **Monitoring** — the `"vcenter"` polling method is the source default for **four** streams (`VCENTER_STREAMS`: response-time, CPU+memory, interfaces, storage) on BOTH roles, and the asset itself is never contacted. Two warm caches in `monitoringService` (30s TTL + promise-singleton; ONE SOAP round trip per vCenter per tick each) serve every monitored asset on the integration: the VM quickStats fetch and the host-stats + datastore fetch. `readVcenterAsset` resolves the reading through the asset's `vcenter-vm` / `vcenter-host` AssetSource row — NOT `discoveredByIntegration` — so directory-discovered VMs that a vCenter sync merged into work too. What each stream reads: **response-time** = a VM's power state / a host's connection + power state, reporting the upstream fetch duration as the RTT; **cpuMemory** = guest memory vs configured RAM / consumed host memory vs installed RAM, CPU MHz over the max (VM) or cores×clock (host); **interfaces** = guest vNICs named from their device key (`Network adapter 1` = key 4000, because two adapters on one portgroup would collide on the portgroup name) / host pNICs + VMkernel ports **nested under their virtual switch** — `buildVcenterSystemInfo` emits each vSwitch (standard, or the host's end of a DVS) as an `ifType: "aggregate"` row and stamps `ifParent` on its uplink pNICs and on the vmks riding its port groups, which is exactly the shape `overlayFortiswitchTrunkMembers` already draws for a trunk, so the System tab nests it with no UI change; a vmk also picks up its port group's `vlanId` through that same name-to-name join. A vSwitch's own `operStatus` is DERIVED — up while any uplink is up, down when all are dark, **null when it has no uplinks at all** (an internal-only vSwitch is working as configured and must not read as an outage), and deliberately no `speedBps`, since vCenter publishes no aggregate rate and summing live uplinks would invent a figure; **storage** = guest filesystems / the host's mounted datastores. `readVcenterAsset` distinguishes **absent** (vCenter answered and this asset wasn't in the answer — a real finding, the probe fails and says why) from **unreachable** (Polaris couldn't ask — the probe is SKIPPED via `ProbeResult.skipped`, writing no sample and moving no counter, so one vCenter outage can't declare an entire virtual fleet down). Operators who want the guest's own network latency point Response Time at ICMP instead; ESXi hosts still accept SNMP/SSH on any stream.

## Azure Arc Discovery Workflow

`azureArcService.ts` discovers **Arc-enabled machines** (`Microsoft.HybridCompute/machines`) — hosts running the Azure Connected Machine agent (`himds`). Because that agent runs IN the guest, Arc reports host truth rather than a directory record: the running OS SKU, the real domain-joined FQDN, live SMBIOS serial/manufacturer/model, and a heartbeat status. **Produces assets only** — the dedicated `syncArcDevices` path in `discoveryEngine.ts` consumes the result, and `"azurearc"` is in the `assetsOnly` set so all three post-sync passes (agent auto-deploy, interface/storage auto-monitor, presence verification) run after the sync exactly as they do for AD/Entra.

- **Auth** — OAuth2 client credentials at scope `https://management.azure.com/.default`, via the shared `buildClientCredentialsTokenRequest` (`src/utils/entraClientCredentials.ts`) — the same helper the Graph client uses, only the scope differs. Token cached per `tenantId:clientId`, refreshed 60s early, invalidated on 401 with one automatic retry. **No Microsoft Graph permissions are required at all**; this is an ARM-only integration, which is the step operators most often carry over by mistake from an Entra ID setup.
- **RBAC** — the service principal needs **Reader**, ideally at the management-group root. Resource Graph returns only what the principal can already read, so a PARTIAL Reader assignment silently yields a PARTIAL roster rather than a 403. `testConnection` therefore probes three levels and reports the deepest reached: acquire a token (tenant/client/secret valid) → read each configured subscription (the Reader grant actually resolves) → one bounded machine list (the `Microsoft.HybridCompute` resource provider is registered). A token-only test would report a false success on by far the most common misconfiguration.
- **Read paths** — **Resource Graph** by default (`config.useResourceGraph`, one `POST /providers/Microsoft.ResourceGraph/resources` across every subscription in scope; ~2 requests where the per-subscription path needs ~65 at a 60-subscription tenant), falling back transparently to the **per-subscription list** on 403 / provider-not-registered, logging one `discover.arc.arg_fallback` line. Both normalize through `normalizeArcMachine`, and a unit test asserts an ARG row and an RP list row produce an identical record — if that ever drifts the two paths would mint different assets for the same machine. ARG is an indexed snapshot trailing the resource provider by seconds-to-minutes; irrelevant on a multi-hour poll, and called out in the service header so nobody debugs it as a bug.
- **Query-language injection surface** — only GUID-validated subscription ids are interpolated into the Resource Graph query. Resource-group, machine-name and tag filters are free-form operator wildcards and are applied CLIENT-side in `filterArcMachines`, which removes the injection surface entirely at the cost of a few hundred KB of response body.
- **Identity** — `AssetSource.sourceKind = "arc"`, externalId = the lowercased ARM resource id (stable for the resource's lifetime).
- **Match cascade** — arc AssetSource by ARM id → **`properties.vmUuid`** (the SMBIOS UUID, matched under BOTH endian variants) → hostname (FQDN first, then short, NetBIOS-truncation tolerant via the shared `indexHostname`/`lookupHostname`) → Conflict → create. The vmUuid step is what merges an Arc machine onto its already-discovered vCenter VM: the index is seeded from existing `arc` rows AND from `vcenter-vm` rows' `instanceUuid`/`biosUuid`. Every cross-link takeover writes an info-level `syncLog` line. Deliberately ABSENT: no MAC pathway (Arc reports none) and no duplicate auto-resolve-by-timestamp — an ARM resource id doesn't churn the way an Entra deviceId does, so a duplicate is a real operator situation and goes to the Conflicts queue.
- **Serial bridge (the Polaris Agent as identity anchor)** — Active Directory carries NO hardware identity (objectGuid / cn / dnsHostName / objectSid / ouPath) and Arc carries no MAC, so an AD-discovered server and an Arc machine share nothing definitive but the hostname. The agent closes that gap: it runs on the host, reads the same SMBIOS serial Arc reports, and stamps it on whatever asset it was installed on — so the cascade matches Arc's `detectedProperties.serialNumber` against `polaris-agent` source serials, ranked below `vmUuid` and above hostname. Only `polaris-agent` seeds the index (Intune's serial is an enrollment-time value that can be stale or describe a replaced chassis). **Two guards are mandatory, and the second is not optional hygiene:** `normalizeHardwareSerial` (`src/utils/hardwareIdentity.ts`) rejects vendor placeholders ("To Be Filled By O.E.M.", all-zeros, too-short), and `indexUniqueBy` DROPS any serial claimed by two different assets — because our own agent falls back to Windows `SystemSKU` when `SystemSerialNumber` is empty, and a model SKU is a well-formed string shared by an entire model line that normalization cannot possibly reject. A serial match onto an asset that already carries a *different* Arc machine is refused outright (cloned VM) and falls through to the Conflict path. Availability is privilege-tier-shaped on Linux: both `product_serial` and `product_uuid` are `0400` root-only, so the default `unprivileged` agent tier reports no serial and gets no bridge; the `ptrace` tier reads them via `CAP_DAC_READ_SEARCH`, and Windows (LocalSystem) reads the registry without elevation.
- **Status is never a lifecycle signal** — unlike Entra's `accountEnabled` (which maps to `decommissioned`), an Arc `Disconnected`/`Expired` agent is a REACHABILITY fact. `syncArcDevices` never writes `Asset.status`; mapping it would decommission a whole fleet during an outbound-proxy outage. `decommissionStaleAssets` already owns aging-out. Disconnected machines are kept and tagged `arc-disconnected`.
- **Presence** — `arcStatusIsConnected(status)` gates a `bumpLastSeen(..., "arc")` with **run time** as the evidence timestamp, never `properties.lastStatusChange` (which records when the status last CHANGED — a machine Connected for 90 days carries a 90-day-old value). `"arc"` is in `POLLING_DEFERRED_SOURCES`, so monitored assets stay probe-authoritative (business rule 12). Second-order effect: most Arc assets then classify `fresh` in `presenceVerificationService` and never enter the ICMP queue.
- **Projection** — arc sits directly below `polaris-agent` for os / osVersion / serialNumber / manufacturer / model (in-guest, refreshed every check-in — strictly better than AD's `operatingSystem`, which lags until re-registration, and than Tools' `guestOsFullName`, which is the configured guest identifier). For **hostname** it sits below vCenter and above AD, deliberately leaving the 2026-07 "vCenter is definitive" decision untouched; the FQDN rule only fires on a value containing a dot. `learnedLocation` ← `resourceGroup` (below AD's `ouPath` — a resource group is an Azure billing container). The Azure REGION is never projected as a location; it stays in `observed.azureRegion`.
- **Tags** — `azurearc` + `auto-discovered`, plus `arc-<status>` and `arc-<cloudprovider>`. Azure RESOURCE tags are deliberately NOT mirrored into `Asset.tags` (an unbounded stream of cloud tags would fight `tagAssignmentService`'s managed add-and-remove sync and pollute the tag registry) — they live in `observed.azureTags`.
- **Class blocks** — reuses `workstationMonitor` / `serverMonitor` verbatim. Most downstream registries key on the BLOCK NAME rather than the integration type, so `monitorOverrideService`'s three raw-SQL CASE expressions, `classToBlockKey`, `ClassQuerySchema` and `StorageClassQuerySchema` all needed zero change. `inferArcAssetType` types Windows Server SKUs and Linux (with no desktop marker) as `server`, Windows client SKUs as `workstation` — deliberately NOT `inferAssetTypeFromChassis`, which defaults to `workstation` and would route an entire Linux server estate through the wrong class block. **An explicit client SKU is the only "this is a workstation" signal Arc gives**, so anything else falls through to `server` on BOTH platforms (Arc onboarding is overwhelmingly a server-estate play). It used to default Windows the other way, which silently typed every Windows host with an empty `osSku` as a workstation — Arc frequently reports only `osName: "windows"` — and since assetType selects the per-class config block those machines resolved `workstationMonitor` instead of `serverMonitor`, picking up the wrong addAsMonitored / agent-deploy / auto-monitor settings. `osType` is authoritative but falls back to sniffing windows/linux out of the SKU+name text when an older agent left it empty.
- **Scale** — two preload queries for the whole fleet (no `macAddressRows` hydration — the cascade never needs MACs) plus chunked `$transaction` writes at 200/batch, so 2000 machines cost ~2 preloads + ~30 write round trips rather than the ~6000 sequential ones a verbatim copy of the pre-2026-09 `syncEntraDevices` would have paid (the Entra and AD syncs have since adopted Arc's preload via their in-memory source mirrors, though their writes still land per-device). Progress Events are PHASE-level only, like Entra/AD/vCenter: `onProgress` calls `logEvent` on every invocation, so per-machine steps at 2000 machines would write ~4000 rows per run into a 7-day-retention table. Consequence: no per-device progress bar on an Arc run. `config.fetchNetworkProfile` is the one dangerous knob — ONE GET per machine — so it defaults off, caps concurrency at 8, stops at a pass deadline, and reports what it skipped.
- **Extension resources (VMware/SCVMM + SQL Server)** — opt-in per integration (`config.enableVmInstances` / `config.enableSqlServer`, both default off). **Neither creates an asset**: both describe a machine the main pass already discovered, so they fold into that machine's record and from there into `observed.vmInstance` / `observed.sqlInstances`. Each is ONE additional Resource Graph query for the whole tenant, not one per machine — which is exactly why the enrichment is **Resource-Graph-only**: when the main pass fell back to the per-subscription list, `attachExtensionResources` logs `discover.arc.extensions_skipped` and does nothing rather than silently degrading to a per-machine read. The parent link differs by resource: a VM instance NESTS under its machine (`parentMachineIdFromExtensionId` takes everything before the last `/providers/`), while a SQL instance is a TOP-LEVEL resource that POINTS AT its machine via `properties.containerResourceId`. Rows whose parent this run filtered out are counted as orphaned, not treated as errors. Adds the `arc-vmware` / `arc-scvmm` and `arc-sql` tags.
- **VM-instance dedupe** — `vmInstance.instanceUuid` is EXACTLY the value `vcenterService.pickVmExternalId` prefers as its externalId, so with Phase 2 on it becomes the FIRST entry in the sync's UUID match cascade — an exact key match ahead of the SMBIOS `vmUuid` inference (which is only a match because Arc and vCenter happen to read the same BIOS field, and needs the endian-variant dance to work at all). Order: `vmInstance.instanceUuid` → `vmInstance.biosGuid` (± endian swap) → `vmUuid` (± endian swap).
- **Connected Kubernetes clusters** — opt-in (`config.enableKubernetes`, default off) and the ONE Arc entity that isn't detail on a machine: each `Microsoft.Kubernetes/connectedClusters` resource becomes its own asset, typed **`kubernetes_cluster`** (a built-in added by migration `20260807020000`). Synced by `syncArcClusters`, a much simpler path than the machine one — a cluster has no SMBIOS UUID, no MAC and no guest OS, so the cascade is just `arc-k8s` AssetSource by ARM id → create; there is no hostname-collision Conflict, because a cluster name matching an existing asset is far more likely to be a genuinely different thing than the same device seen twice. Projection: hostname ← cluster name, os ← the constant `Kubernetes (<distribution>)`, osVersion ← `kubernetesVersion`, learnedLocation ← `resourceGroup`; no hardware fields at all. Presence uses `connectivityStatus`, and — like the machine path — `status` is never written from it.
- **Why Kubernetes was the expensive phase** — introducing a new asset type (rather than reusing `workstation`/`server`) is what forces the registry work Phases 1–3 avoid entirely: the `k8sMonitor` reduced class block (addAsMonitored + streams only — no agent, no interface/storage auto-monitor; it shares `VcenterHostClassMonitorSchema` with vCenter's ESXi hosts), a `classBlockKeyForAssetType` arm, an `AddAsMonitoredAssetType` union member, a `pickClassStreamsBlock` branch, **and all three raw-SQL `CASE` expressions** in `monitorOverrideService`. The asset-type registration itself is a **three-way lockstep** — the migration's `INSERT … ON CONFLICT DO UPDATE`, `BUILT_IN_ASSET_TYPES` in `src/utils/assetTypes.ts`, AND the `BUILT_IN_SEEDS` entry in `assetTypeService.ts`, because `seedBuiltInAssetTypes` SKIPS any seed whose name is absent from the former. Doing two of the three is a silent no-op on fresh Docker volumes and restored backups; `tests/unit/arcAssetTypeLockstep.test.ts` guards it.
