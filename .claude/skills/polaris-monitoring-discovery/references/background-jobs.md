# Background jobs

Verbatim from CLAUDE.md → Background Jobs, followed by the full per-job table from ARCHITECTURE.md.

~64 files in `src/jobs/` (62 jobs + two helpers: `_metrics.ts` `runInstrumentedJob` and `_runOnce.ts` `hasRunMarker`/`stampRunMarker`, the shared one-shot-marker idempotency guard): continuous ticks (`monitorAssets` light + heavy loops, `dependencyReconciler`, `maintenanceScheduler` (30s — reconciles maintenance-schedule windows: enter/exit + status parking/restore + self-heal), `retryQueuedReservationPushes`, `deliverNotifications` (15s — drains the `NotificationDelivery` queue to the configured channels: email/Slack/Teams/Pushbullet/web-push + api_call HTTP dispatch), `runAutomationScripts` (5s — executes pending server-side automation script runs)), periodic safety nets (`capacityWatch`, `evaluateNotificationRules` (60s — drives the notification rules engine), `escalateNotifications` (60s — sends escalation-tier emails for unhandled notifications), `hostMetricsCollector` (30s — Polaris host CPU/mem/load → `HostMetricsSample`), `reconcileMapRegions`, `reconcileAppMapAutoMap` (30m — re-applies the Application Map auto-map selection so assets discovered later pick up their pins), `discoverySlowCheck`, `flagStaleReservations`, `decommissionStaleAssets`, `reconcileInfraReservations` (6h — releases managed FortiSwitch/FortiAP reservations whose device is decommissioned or gone; backstop for the lifecycle hooks, see business rule 23), `mergeDuplicateHostnameAssets`, `detectDuplicateIpAssets` (10m — the duplicate-address sweep behind business rule 40: one grouped query raises / refreshes / auto-closes the `duplicate-ip` Conflict flavor, and a fleet with no duplicates issues zero writes), `scheduledBackup` (5m — automatic database backups on the operator's cadence + retention prune + off-host copy; default-OFF, so the tick is a cheap due-check until enabled)), nightly maintenance (`pruneEvents`, sample-table prune, `runSampleRollup` hourly + daily ticks, `reclaimBloatedChunks` compressed-chunk heap reclaim), and one-shot startup migrations (manufacturer-alias seed, asset-source backfill, `migrateContactFilterShape` (folds each address-book contact's flat `assetCriteria` forward into an `assetCondition` tree, skipping — and logging — any row whose criteria names a field the tree can't express, since converting it would widen who the contact covers and dropping the rule would narrow it), `migrateTagFilterShape` (the same fold for the tag registry's `criteria` → `assetCondition`, same skip rule; match-equivalent by construction so it triggers no reconcile, and a tag deleted mid-fold is skipped per row rather than abandoning the loop and leaving the marker unstamped), `clearNotificationCooldowns` (nulls `NotificationRule.cooldownSec` fleet-wide with the retirement of the re-notify-cooldown control, stamping ONE `automation.cooldown.retired` Event that names each affected rule and its old value **before** the update destroys it), the `mergeFortiswitchEndpointGhosts` NULL-MAC ghost cleanup, monitor-settings hierarchy migrations, `seedBaselineAutomations` = seed-once baseline automation rules: the widget-mirror set (marker `seedBaselineAutomationsSeededAt`) + the v2 event-based set — 12 enabled in-app-only event-trigger rules over notable system Event families (discovery/push/agent failures, capacity escalations, conflicts, lockouts), gated by its own marker `seedBaselineAutomationsV2SeededAt` so existing installs pick them up without duplicating the first set — plus the **v3 down-detection set** (`seedBaselineAutomationsV3SeededAt`), which unlike the other two is COMPUTED from live data rather than a static array: it reads each install's effective pre-cutover `failureThreshold` per monitored asset and mirrors it into automations (one all-assets rule at the dominant value + one `assetTypes:[t]` rule per class that differed, which outranks it on `scopeRank`), then retires the pre-cutover "Asset down" row **only if `updatedAt === createdAt`** — an edited row is kept and flagged with `automation.seed.v3_retained`, since it still governs its devices at `DEFAULT_MISSED_POLLS` and the operator has to be told the number is now theirs. Creates BEFORE it retires (the reverse order leaves a window with zero down automations, i.e. a momentarily blind fleet) and refuses to retire at all if the replacement failed to save. Known gap: `scopeRank` doesn't rank `integrationIds`, so one class carrying different thresholds across two integrations collapses to the more-sensitive value with an `automation.seed.threshold_conflict` warning Event rather than being silently flattened). Two startup jobs are deliberately NOT marker-guarded because they must retry until the environment allows them to succeed: `enforceSubnetUniqueIndex` (creates the `subnets_block_cidr_key` unique index once any pre-existing duplicate CIDRs are cleaned up — migration `20260806000000` skips it rather than failing the upgrade) and `backfillSecretEncryption` (seals previously-plaintext secrets once `POLARIS_SECRET_KEY` is configured, which may happen after the upgrade that ships the code).

| `mergeDuplicateHostnameAssets` | Boot + every 30 min | Idempotent. Periodic safety net — discovery re-creates duplicate-hostname rows continuously, so it runs at boot and on a 30-min interval (a boot-only pass let duplicates accumulate between restarts on long-lived prod). Broader sibling of `mergeFortiswitchEndpointGhosts` — catches every shape of accumulated duplicate-hostname Asset row that the narrower NULL-MAC job misses (workstation ghosts where the FortiGate created one `fortigate-endpoint` per MAC sighting, Phase-1 backfill `manual`-only placeholders, post-baseMac FortiSwitch ghosts, FortiAP equivalents). | `resolveIpUpstreamChain` | Boot + 90s, then every 10 min | Idempotent. On a 48-port switch with one pinned interface that's ~110 OID-fetches in one PDU vs ~770 across 16 column walks under the legacy full-walk path — drops fast-cadence p90 from multi-second to sub-second on busy fleets and cuts the Capacity Advisor's recommended `POLARIS_MONITOR_FAST_WORKERS` proportionally. LLDP and wireless are always omitted on the fast cadence (LLDP rides the heavy pass; wireless isn't a fast-pin target). The FortiOS REST path still pulls the full `/api/v2/monitor/system/interface` payload and filters in code — the endpoint has no per-name query param. Storage and IPsec rows ride the same monitorInterval setting (default 60s) so the operator gets sub-minute disk-usage and tunnel-state history for chosen mountpoints / tunnels without re-walking the full tables. ICMP/SSH cannot deliver telemetry/system-info; WinRM/AD return supported=false until WMI Enumerate-over-WS-Management lands. **Worker scheduling**: cadences are split across two independent ticking loops. The **light loop** (probe + fastFiltered) ticks every 5 s with concurrency `cpus().length * 2` (clamped 8..64, env-overridable via `POLARIS_PROBE_CONCURRENCY`); the **heavy loop** (telemetry + systemInfo) ticks every 30 s with concurrency `cpus().length` (clamped 4..32, env-overridable via `POLARIS_HEAVY_CONCURRENCY`). Each loop has its own `running` guard, so a 75-second wedged systemInfo on a dead host blocks ONLY the next heavy tick — the light loop keeps firing on its own clock and probes stay close to their configured cadence regardless. Within a pass, workers don't reserve assets; they just pull the next item from the cadence queue. `runMonitorPass({cadences})` selects which cadences a given call owns; the default (no `cadences` arg) covers all four for legacy callers like `POST /assets/:id/probe-now`. **Five-state monitor machine**. `Asset.monitorStatus` is one of `up | warning | recovering | down | unknown`, driven by two counters: `consecutiveFailures` (existing) + `consecutiveSuccesses` (added with the hierarchy work). The resolved `failureThreshold` doubles as the recovery threshold — same number of confirmations gates both directions. (UI label note: `recovering` shows as **Recovering**, `unknown`/null shows as **Pending**; same blue color, different labels.) **(5) ICMP loss sweep** (2026-09-01, replacing the per-asset sampler of 2026-08-19 that was disabled a day after shipping) when `lastLossSampleAt + the sweep interval` has elapsed — a UNIFORM burst of 5 echoes at every eligible asset, whatever monitor state it is in, writing one `AssetMonitorSample` per asset with `probeKind="icmp"`, a NULL `responseTimeMs` and the `packetsSent` / `packetsReceived` pair that makes loss a ratio of PACKETS instead of poll outcomes. The sampler it replaces ran only while an asset was `warning` or `recovering`, and that window was itself the oversampling bias that got it switched off (business rule 29d); uniform spacing is what makes the ratio mean what an operator thinks it means. Affordable only because it is BATCHED: one queued job is one CHUNK of up to 500 assets measured in a single `fping` process (`utils/burstPing.ts`), bounded by burst period rather than host count, so a 2000-asset fleet costs four process spawns per cycle against the ~2000 a per-asset design would need. fping is OPTIONAL — RHEL ships it only via EPEL and Windows Server has no build — and a bounded per-host fan-out keeps loss correct where it is missing, with `resolveSweepIntervalSec` flooring the cadence at what the installed pinger can actually finish. It NEVER calls `recordProbeResult`, so it cannot touch the counters or `monitorStatus` (ICMP does not authenticate the device it reaches). Eligibility (`utils/lossSweep.ts`) excludes only unmonitored, `maintenance`, and `responseTimePolling === "disabled"`; `down`, dependency-suppressed and agent-monitored assets are all deliberately IN. Keeps the `lossSample` cadence name / pg-boss queue (`polaris-monitor-losssample`, 15s expiry, 2s polling) / worker pool (`POLARIS_MONITOR_LOSS_SAMPLE_WORKERS`, default 24 — now sizing concurrent CHUNKS) so the cutover orphans no persisted queue and no operator-set env var, and still deliberately NOT in the floating pool's priority list: if its budget is saturated the right answer is to drop resolution, not to borrow capacity from the pool that absorbs real monitoring work. Replaced the fast-confirm re-probe, which was removed the same day: the response-time poll no longer accelerates mid-run, so time-to-down is `failureThreshold x intervalSeconds` (business rule 30).

`Asset.consecutiveFailures` is a **leaky bucket**, not a run length (business rule 30): a missed poll adds one, an answered poll takes one back, floored at zero. The verdict is then a pure function of the bucket level plus the outcome of the current probe — the previous status is not an input at all.

| Bucket after this probe | This probe answered | This probe missed |
|---|---|---|
| `cf ≥ threshold` | `down` | `down` |
| `0 < cf < threshold` | → `recovering` (answering, misses outstanding) | → `warning` (rendered **Missed**) |
| `cf = 0` | `up` | — (unreachable: a miss always raises the bucket) |

**The LEVEL decides and the current probe only breaks the tie below the threshold.** Letting a success win outright would mean a device dark for an hour (cf=60) reads `recovering` — and clears its down alert, which tests `monitorStatus == down` — on ONE answered packet out of sixty; it has to pay the debt back under the threshold first. Draining 3 → 2 → 1 → 0 therefore takes exactly `threshold` answers, the same number of confirmations `consecutiveSuccesses` used to count, which is why the machine no longer consults it (the column is still written — it is a true fact and it is charted — it simply decides nothing). `recovering` correspondingly no longer means "was down": it means answering with misses still outstanding, reachable straight out of `warning`. The Status pill on the assets list and asset details modal renders the five colors: green (up), amber **Missed** (`monitorStatus="warning"` — the stored value is unchanged; the label is "Missed" because the alert severities are also named warning/serious/critical, so the pill read as "an alert fired" when it only ever meant "a poll was missed"), blue **Recovering** (was-down, now succeeding — `#0288d1`, the SAME value the Last-30-min strip and the response-time chart below it paint a recovering probe, and the same `POLARIS_HEALTH_COLORS.recovering` the Device Map uses; it was keyed to `var(--color-accent)` until 2026-08-29, the only monitor badge pointed at a theme token rather than its own colour family, which rendered it in the morning theme's GOLD — the family of the amber **Missed** pill beside it), red (down), grey (`monitored=false`, "unmonitored"). The `unknown` / null state (asset never probed) reuses the same blue CSS treatment but with the label **Pending** so operators can distinguish "we don't know yet" from "we know it's recovering". The `monitor.status_changed` audit Event still fires only on `up ↔ down` transitions; the per-tick failures show up visually in the asset System tab's intermittency bar (one cell per probe sample over the 1h window). The bar's cells come wholly from the machine: amber for a miss while the bucket is below the covering automation's `missedPolls`, red at or above it, and BLUE for an answered poll while misses are still outstanding — held past the drain until the automation's reset run of answers has landed (business rule 36). That split is the point: a single missed poll still reads as one amber cell (green-amber-green) rather than a multi-cell warning run, and a failed probe is never painted blue, but the multi-cell stretch the pill spends in **Recovering** is now visible on the one surface built to show it (it used to be green, i.e. indistinguishable from confirmed-up). A blip during recovery keeps the machine in `recovering`, so the successes after it stay blue. Both counters are warmed up across the full hour before slicing the trailing 30 cells, so a dip — or a recovery — that began before the visible window keeps its correct color; the pre-window state is assumed `up`, since seeding `unknown` would paint the first cells of every bar blue (unknown and down share the same success arrow). The replay is the pure `PolarisMonitorStates.replay` in `public/js/monitor-states.js` (reached from `assets.js` under its historical name `_intermittencyStates`), shared with the response-time charts on both desktop and phone and mirrored server-side by `probeOutageService.replayProbeStates` for the alert-email charts; unit-tested — and pinned against that server mirror — in `tests/unit/assetIntermittencyBar.test.ts`.

**Heavy-cadence suppression**: telemetry / systemInfo / fastFiltered run **only** when `monitorStatus === "up"`. Every other state — including `warning` (mid-degradation), `recovering` (mid-recovery), `down`, and `unknown` — suppresses heavy cadences so the System tab stops accumulating samples that aren't going to be reliable. The cheap response-time probe keeps firing in every state.

**No probe backoff** — down hosts keep probing at the resolved `intervalSeconds`. Recovery is detected within one base-cadence tick (worst case 60 s on default settings, vs. up to 30 min under the old bucketed backoff that was dropped along with the new monitor-settings hierarchy). Trades a small amount of worker budget on chronically-down hosts for fast recovery detection. `lastSystemInfoAt` doesn't advance during the outage (only bumps when a scrape returned data), so systemInfo is due immediately on recovery and the System tab refreshes naturally. The same "only on data" rule also stops a transport failure from silently emptying the System tab Interfaces table — the GET endpoint anchors interface display to `lastSystemInfoAt`, and bumping it without inserting any rows would point the query at a moment with zero samples. Once a day the job prunes the sample tables (`monitor.sampleRetentionDays` for monitor, `telemetryRetentionDays` for telemetry **and temperatures**, `systemInfoRetentionDays` for interface + storage + IPsec tunnels **and LLDP neighbors** — LLDP rides system-info retention because it's collected on the same cadence; the per-scrape full-replace already drops gone-away neighbors so the prune mostly catches rows for assets that have stopped scraping entirely). |
