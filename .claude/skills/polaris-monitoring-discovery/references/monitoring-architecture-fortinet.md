# Monitoring architecture — FortiSwitch/FortiAP polling, decommission sweep, CMDB policy, push and quarantine lifecycles, verbose logging

Verbatim from ARCHITECTURE.md → Monitoring Architecture (second half).
**Branch-class FortiGate workaround.** Small-branch FortiGates (60F/61F/91G class) sometimes 404 the FortiOS REST sensor-info / interface endpoints on FortiOS 7.4.x. Operators flip the relevant streams to `snmp` at the integration tier (covers the whole fleet) or per-asset (one box at a time) — the resolver routes the affected streams over `FORTINET-FORTIGATE-MIB::fgHwSensors` + IF-MIB while leaving the working streams on REST API. **IPsec tunnels always go via REST** regardless of the interfaces polling method — SNMP has no equivalent and we don't want flipping "Interfaces" off REST to silently kill IPsec history. LLDP is decoupled from interfaces because the FortiOS REST endpoint and SNMP LLDP-MIB don't always agree on coverage; the transport resolver dispatches LLDP independently in `collectSystemInfo`, overlaying a `collectLldpOnlySnmp` / `collectLldpOnlyFortinet` call when the LLDP method differs from the interfaces method.

**REST API telemetry + temperature for managed FortiAPs.** The same `/api/v2/monitor/wifi/managed_ap` row that the probe path consumes carries `cpu_usage`, `mem_free` / `mem_total` (in MB), and `sensors_temperatures` per AP. `fetchFortinetControllerInventory` parses those fields once at fetch time into `entry.apTelemetry` so the 30 s controller-inventory cache absorbs all three consumers (probe + telemetry + hardware sensors) — one upstream call per controller serves N APs on every telemetry tick. When the resolved `cpuMemoryPolling` is `rest_api` on an `access_point` asset, `collectTelemetry` dispatches to `collectTelemetryFortiapRest` which converts MB → bytes (`memTotalBytes = memTotalMb × 1024²`, `memUsedBytes = (memTotal − memFree) × 1024²`) and writes the standard `AssetTelemetrySample` shape; `memPct` is left null because the bytes form is more useful for charts across AP models with different RAM sizes. When the resolved `temperaturePolling` is `rest_api`, `collectHardwareSensors` dispatches to `collectHardwareSensorsFortiapRest` which projects `sensors_temperatures` into the `HardwareSensorSample[]` shape (one row per sensor, all `sensorClass="temperature"` — the controller cache only exposes AP temps). APs whose model doesn't publish CPU/memory/temperature (some older indoor units) come back with `data: []` or null fields rather than an error — the System tab renders "no sensors" instead of a failure pill. Managed FortiSwitches still have no REST telemetry path (the controller-status table reports up/down only); operators wanting switch telemetry flip to SNMP at the integration or per-asset tier.

**Controller-link sweep for managed FortiSwitches / FortiAPs (business rule 59).** The probe path below renders the controller's up/down verdict only for assets whose resolved `responseTimePolling` is `rest_api` — and for those the link state IS their `monitorStatus`, so it tells an operator nothing new. The devices it says something new about are the ICMP- and SNMP-polled ones, because **a FortiSwitch whose FortiLink session to the gate is dead answers every ping and every SNMP get perfectly well**: it is up by every measure the monitor loop has, and no switch-controller config is reaching it. `jobs/sweepFortinetLinkState.ts` (60s, scheduler role only, `POLARIS_FORTILINK_SWEEP_SEC`) therefore sweeps EVERY FortiGate-managed switch and AP regardless of polling method, through `services/fortinetLinkStateService.ts`, and projects the answer onto four `Asset` columns — `fortilinkStatus` (`up`|`down`|`unknown`) / `fortilinkStatusRaw` / `fortilinkCheckedAt` / `fortilinkChangedAt`. It reads through the SAME `fetchFortinetControllerInventory` + 30s per-controller cache the probe uses (now exported for this caller), so cost tracks controller count rather than fleet size: ≤2 upstream calls per controller per tick at any fleet size, and ~1.5/min per kind on a controller the probe path already reads — the two 60s timers coalesce only when they land in one 30s window, so budget 1.5, not 1. **Three refusals carry it**: a controller the sweep could not READ writes nothing at all (an expired token must not report a fleet-wide link outage; failures are isolated per controller, and a `fortilinkCheckedAt` that stops advancing is what the asset-details row reads to mark the value last-known rather than current); a device the controller answered about but did not LIST reads `unknown`, not `down` (the probe path's absent-is-failure rule is right for a probe and wrong here — a post-config-push window looks identical, and down-detection authority is business rule 36's); and it never touches `monitorStatus` or `consecutiveFailures`, because the column's whole value is that it may DISAGREE with the monitor pill. Transitions write one `asset.fortilink.changed` Event each (`warning` down, `info` up and on first observation) and the field is exposed as the `fortilinkStatus` `asset_state` automation trigger, anchored on `fortilinkCheckedAt` so a poll-counted hold counts times the CONTROLLER answered. Rule 37 still gates alerting: a managed switch with `monitored=false` shows the details row and never fires. Unmonitored assets are swept anyway — the controller call is per-controller either way, and the row should be right on a device nobody polls.

**REST API probe path for managed FortiSwitches / FortiAPs.** Managed FortiSwitches and FortiAPs aren't directly REST-able — the only authoritative up/down signal is the parent FortiGate's `managed-switch/status` (switches) or `wifi/managed_ap` (APs) inventory table. When the resolved `responseTimePolling` is `rest_api` AND the asset's `assetType` is `switch` or `access_point` AND the asset was discovered through an FMG or FortiGate integration, `probeAsset` dispatches to `probeFortinetController` instead of hitting the asset's own IP. The helper resolves the controller via `Asset.fortinetTopology.controllerFortigate` (FMG) or the integration's own host (standalone FortiGate), fetches the appropriate inventory once, and looks up the asset by serial. `status === "Connected"` (switches) or `status ∈ {"online","connected"}` (APs) is success; everything else (including "not present in the controller's table") is failure. The **per-controller inventory cache** is module-local in `monitoringService.ts` with a 30s TTL keyed on `(integrationId, deviceName, "switches"|"aps")` — N switches or APs sharing one controller make exactly one controller call per cache window, important for FMG proxy mode (concurrency=1). The result flows through the standard `recordProbeResult` → five-state machine → `failureThreshold` → `monitor.status_changed` Event pipeline like any other probe, so a switch that goes Disconnected and stays that way for `failureThreshold` consecutive probes (default 3) ends up as `down`. Cadence implication: at the default 60s `intervalSeconds` and threshold 3, "down" detection takes ~3 minutes; operators on slower cadences should adjust accordingly.

**Per-class FortiSwitch / FortiAP direct polling and auto-Monitor flag:** The FMG/FortiGate integration's `config` JSON accepts `fortiswitchMonitor` and `fortiapMonitor` blocks, each `{ enabled: boolean, snmpCredentialId: string | null, sshCredentialId: string | null, addAsMonitored: boolean, autoMonitorInterfaces: AutoMonitorSelection | null, streams: ClassStreamsBlock }`, plus a `fortigateMonitor: { addAsMonitored: boolean, autoMonitorInterfaces: AutoMonitorSelection | null, pullSnmpLocation: boolean, pushGeocodedCoords: boolean, latitudeMetavar: string, longitudeMetavar: string, addressMetavar: string, streams: ClassStreamsBlock }` block. The three metavar-name fields (FMG-only) name the per-device metavariables used for the coord read + write-back (`latitudeMetavar`/`longitudeMetavar`, default `Latitude`/`Longitude`) and the opt-in address geocode source (`addressMetavar`, blank-disabled); edited from the **Geographic Location** tab. **Phase 2** added the `streams` field on each class block — the per-stream config consumed by the resolver under that class's assetType (see "Monitor Settings Hierarchy" above). AD / Entra / Windows Server gained matching `workstationMonitor` / `serverMonitor` blocks with the same `streams` shape. Shape per stream cell: `{ polling: PollingMethod | null, credentialId: uuid | null, intervalSeconds: number | null, timeoutMs: number | null, mibId: uuid | null, failureThreshold?: number | null }` (failureThreshold only honored on `responseTime`; FortiAP omits the `storage` stream entirely). The integration-tier resolved `responseTimePolling` decides which credential gets stamped on a freshly-discovered switch/AP — `ssh` picks `sshCredentialId`, anything else falls back to `snmpCredentialId`. The `autoMonitorInterfaces` field is the "Auto-Monitor Interfaces" selection — see the dedicated subsection below for its three modes. Edited from the **FortiSwitches** and **FortiAPs** subtabs (full block) and the **FortiGates** subtab (auto-Monitor checkbox only) of the Monitoring tab. The two switch/AP flags are independent and drive these discovery-time outcomes:

| `enabled` (direct polling) | `addAsMonitored` | Stamped on new switch/AP |
|---|---|---|
| false | false | ensure monitored=false (sweep off) |
| false | true | `monitored=true`; resolver picks ICMP source default |
| true (with credential) | false | `monitorCredentialId=<id>`; ensure monitored=false (sweep off) |
| true (with credential) | true | `monitorCredentialId=<id>`, `monitored=true` |

Discovery always stamps `discoveredByIntegrationId=<integration>` on any of these "non-empty" rows so the resolver can pick the source default polling method. Existing switch/AP assets are *only* re-stamped with a credential when their existing `monitorCredentialId` is null OR matches the integration's class credential — operator-pointed credentials are preserved. The `monitored` flip is gated by `Asset.monitorOverride`: discovery enforces `monitored = addAsMonitored` on every cycle EXCEPT when override is true (an explicit operator pin). `monitorOverride` is an **explicit operator-intent bit** — it is written ONLY at the moment of an operator action (the asset write paths compute `monitored XOR addAsMonitored` for the touched ids; re-aligning monitoring to the flag clears it on the same write; the Reset-to-integration-default action clears it). It is **never re-derived from incidental divergence** by a boot job or integration save: an asset that ends up `monitored=false` for a non-operator reason (decommission clamp, created-before-flag-enabled, HA standby) keeps `monitorOverride=false` and self-heals — the next discovery sweep retakes it to the flag's value. (This replaced an earlier convergent model whose every-boot/every-save re-derivation wrongly stamped incidental divergence as an override and stranded those assets unmonitored.)

For **FortiGates**, `fortigateMonitor.addAsMonitored` drives a bidirectional sweep on the same model — `buildFortigateMonitorStamp()` runs on both create and update paths and sets monitored to match the flag (skipping asset rows with `monitorOverride=true`; it reads the override but never writes it). **HA standby members are actively swept to `monitored=false` (+ `consecutiveFailures=0`)** rather than skipped — a standby isn't probe-reachable (its IP is nulled; the cluster IP routes to the active member), so polling one is guaranteed-failure waste, and the per-cycle sweep is what un-monitors an ex-primary after failover. The standby's effective default is `false` at every point that consults the class flag: `recomputeMonitorOverrideForAssets` + `sweepMonitoredForIntegration` (nested `haRole='secondary'` CASE in the SQL), the monitor-override reset endpoint, and the auto-monitor preflight counts — so a deliberate operator opt-in on a standby computes `monitorOverride=true` and sticks. The polling method comes from the resolver (REST API source default for fortimanager / fortigate sources).

For **AD / Entra / Windows Server** integrations, `workstationMonitor.addAsMonitored` and `serverMonitor.addAsMonitored` carry the same semantics on workstation- and server-typed assets. The Entra and AD sync paths call `buildMonitoredSweep()` from `src/services/monitorOverrideService.ts` on every asset write to enforce the flag.

**Integration save sweep.** When the operator changes any per-class `addAsMonitored` value on an integration's edit modal and clicks Save Changes, the PUT /integrations/:id handler runs `sweepMonitoredForIntegration()` (bulk SQL UPDATE that sets `monitored = addAsMonitored` on every **non-override** asset under this integration matching the affected class). It deliberately does **not** recompute `monitorOverride` — a flag flip respects existing operator pins (operators re-align a pinned asset per-asset via the Reset-to-integration-default action, `POST /assets/:id/monitor-override/reset`). Writes one `integration.auto_monitor_swept` Event with the touched-asset count when the sweep was non-trivial. Pairs with the frontend confirm modal (see "Operator confirm flow" below) that protects against accidental fleet-wide disables.

**Operator confirm flow.** The Add/Edit integration modal's Monitoring tab → per-class subtabs render an **Enable Auto-Monitoring** (blue) / **Disable Auto-Monitoring** (red) button instead of a checkbox (`_classAddAsMonitoredHTML` and `_fortigateAddMonitoredHTML` in `public/js/integrations.js`). The button toggles a hidden checkbox of the same id the save path already reads, so persistence is unchanged. On Save Changes the frontend POSTs the proposed flag map to `/integrations/:id/auto-monitor-assets/preflight` and, when any class reports `wouldDisable > 0`, surfaces a confirm modal listing the per-class impact ("Disabling Auto-Monitoring will sweep monitoring OFF for N FortiSwitch(es) — P protected by per-asset override"). Decline aborts the save with no API call.

**Auto-Monitor Interfaces (per-class):** Each `*Monitor` block above also carries an `autoMonitorInterfaces` field that pre-selects which interfaces on every discovered asset of that class are added to the "Poll 1m" fast-cadence pin-list. Real interfaces land in `Asset.monitoredInterfaces` (IF-MIB); synthetic IPsec-tunnel rows land in `Asset.monitoredIpsecTunnels` (the IPsec sampler's list) — the apply pass routes by provenance via `splitPinsByProvenance`. Multi-block union — each block is optional, presence = on, and the apply pass takes the **union** across whichever blocks are present:

```ts
autoMonitorInterfaces: {
  byNames?:    { names: string[] }                                                    // explicit ifNames from the aggregated checklist
  byPatterns?: { patterns: string[]; regex: boolean; onlyUp: boolean }                // wildcards (* and ?) when regex=false, raw anchor-free regex when regex=true
  byTypes?:    { types: Array<"physical"|"aggregate"|"vlan"|"loopback"|"tunnel">; onlyUp: boolean; includeDownTunnels?: boolean }
  byLldp?:     { neighborTypes: Array<"firewall"|"switch"|"access_point"|"server"|"workstation"|"router"|"printer"|"other"> }
} | null                                                                              // null (or all keys missing) = feature off
```

Edited from a card on each Monitoring subtab (FortiGates / FortiSwitches / FortiAPs). Each block has its own master checkbox so operators can mix and match (e.g. "By pattern: `wan*` + By LLDP: switch" on FortiSwitches). `onlyUp` filters candidate interfaces to those with `operStatus === "up"` on their latest `AssetInterfaceSample`; available on byPatterns + byTypes, intentionally not on byNames (explicit names always pin even when the link is down). Default `onlyUp: true` for byTypes, `false` for byPatterns. **`byTypes.includeDownTunnels`** is a tunnel-only exception to `onlyUp`: when both are set, fully-`down` IPsec tunnels still pin (a down tunnel is often exactly what an operator wants to watch). No-op on non-tunnel types and moot when `onlyUp` is false. **Dead-parent exclusion** overrides everything above: an IPsec tunnel whose phase-1 parent interface (`AssetIpsecTunnelSample.parentInterface`, e.g. `wan2`) is currently down AND holds no usable IP (null / `""` / `0.0.0.0`) can never establish, so `mergeTunnelsIntoInterfaces` stamps its row `parentDownNoIp` and `resolvePinnedInterfaces` excludes it from EVERY block — byNames, byPatterns, byTypes (even with `includeDownTunnels`), byLldp. A parent that is down but still addressed does not trigger it (that's a flapped link, the `includeDownTunnels` use case), nor does a missing parent row or unknown operStatus. Hand-pins on the asset are unaffected (apply is additive). The UI renders an **"Include down tunnels"** checkbox inline to the right of the `tunnel` type row, shown only when `tunnel` is checked (`_amonTypeRowHTML` + `wireInclDown` in `public/js/integrations.js`; the check state survives the post-aggregate type-list re-render via the `inclDownState` closure). **By LLDP** semantics (UI label: **By LLDP (includes inferred interfaces)**): for each interface on the discovered asset, look up its `AssetLldpNeighbor` row AND any peer-inferred edge from `Asset.fortinetTopology` and pin if any match resolves to a Polaris asset whose `assetType` is in the selected set AND `monitored=true` — automatically tracks fleet topology (a new FortiGate uplink to a managed switch gets pinned on the next discovery, no operator action). The inferred half (`loadInferredLldpByAsset` in `autoMonitorInterfacesService.ts`) covers managed FortiAPs whose FortiSwitch consumes LLDP without re-publishing via SNMP LLDP-MIB — same data source as the inferred Neighbor column on the System tab (see `peerInferredLldpService`). Class-aware: `fortigate` walks switches whose `controllerFortigate` names this FortiGate and pins on `switch.uplinkInterface`; `fortiswitch` walks APs whose `parentSwitch` names this switch and pins on `ap.parentPort`; `fortiap` resolves the AP's own `parentSwitch` + `uplinkInterface` and pins on the AP-local port. Apply logic lives in `autoMonitorInterfacesService.ts` (pure resolver `resolvePinnedInterfaces` + DB-bound `applyAutoMonitorForClass`); the apply pass runs as Phase 2c at the end of every successful discovery and from the integration edit modal's **Save Changes** button via `POST /integrations/:id/interface-aggregate/apply` (which now fires the apply in the background and returns `202` so the modal doesn't block on the fleet-wide resolve), once per per-class block whose selection is non-null so operators don't have to wait for the next discovery cycle. **Strictly additive**: never strips operator-pinned interfaces, only adds. Removing a name from the selection on subsequent saves doesn't unpin it on existing assets — operator-owned. The "By name" UI pulls its checklist from `GET /integrations/:id/interface-aggregate?class=...`, served from `Integration.interfaceAggregateCache` (precomputed at end-of-discovery by `computeAndCacheInterfaceAggregate`, with a live-compute fallback before the first post-feature run) and returns one row per distinct ifName with a device count. A client-side filter box above the checklist (`applyNamesFilter` in `public/js/integrations.js`) substring-matches the ifName (case-insensitive) and hides non-matching rows — view-only, so a row hidden by the filter keeps its checkbox state, and the filter re-applies whenever the checklist re-loads. **The "By interface type" checklist is sourced from the same aggregate response** at lazy-load time (frontend filters `rows[*].ifType` against the canonical `IF_TYPES` set in `autoMonitorInterfacesService.ts`) so operators only see ifType values that actually appear on this integration's discovered devices — a fleet whose tunnels register as FortiOS `ipsec` (normalized to `tunnel` in `normalizeFortiIfType`) shows `tunnel`; a fleet with no tunnels won't show it at all. **IPsec tunnel augmentation (fortigate class only):** the data loader `loadLatestInterfaces` is called with `includeIpsecTunnels = klass === "fortigate"`; when set it also pulls the latest `AssetIpsecTunnelSample` per `(asset, tunnelName)` (same 72h-bounded DISTINCT ON, run in parallel) and merges each tunnel in as an `ifType:"tunnel"` interface via the pure helper `mergeTunnelsIntoInterfaces` (status maps to operStatus with only fully-`down` → `"down"`). This exists because FortiOS phase1-interface tunnels are real `config system interface` entries but the REST `/api/v2/monitor/system/interface` endpoint omits them, so on REST-polled FortiGates they never reach `asset_interface_samples` and would otherwise be invisible in both pickers. Each tunnel row is tagged `isIpsecTunnel`. **The IPsec SA status is authoritative:** if a tunnel name collides with a real interface row (e.g. an SNMP-polled gate whose IF-MIB reports the tunnel's `ifOperStatus` as always "up" regardless of SA state), the merge OVERRIDES that row's operStatus with the SA-derived value and tags it `isIpsecTunnel` rather than skipping the synthetic — without this, `onlyUp` would pin a tunnel whose SA is down (the bug that surfaced once tunnel pins started fast-polling). The merge augments the resolver feed too, so By name / By type selections of a tunnel actually pin — and `splitPinsByProvenance` routes those pins to `Asset.monitoredIpsecTunnels` (read by the dedicated IPsec sampler → `asset_ipsec_tunnel_samples` for SA-status + throughput), NOT `Asset.monitoredInterfaces`. This is what makes a "By type: tunnel" selection fast-poll IPsec tunnels on REST-polled gates, where an IF-MIB pin would yield nothing. Switches/APs have no IPsec and skip the extra query. Saved-selection types not present in the latest aggregate are preserved across renders so a stored value isn't silently dropped. The card's live preview block is computed **client-side from the cached aggregate** for `byNames`/`byPatterns`/`byTypes` selections (`computeClientPreview` — instant, no round-trip; the prior live `POST .../preview` on every toggle was the same slow fleet-wide query as the old list-load and left the box blank while it ran), with a client-side `Change since last edit: +X / −Y` ifName-level diff vs the prior preview. Only `byLldp` selections still call `POST /integrations/:id/interface-aggregate/preview` (topology isn't cached), showing a "Computing matches…" placeholder while it runs and rendering the server `diff` block. **The preview box stays quiet until the operator actually changes a selection** (a `userHasEdited` flag in the wire function gates `runPreview`, so the automatic renders on modal-open / aggregate-load no-op) — opening the modal on a saved selection no longer flashes a full count + "First matches" preview the operator didn't ask for. `lastSentSelection` is still seeded to the saved selection at open, so the first operator-triggered preview shows the diff vs the saved state; each subsequent toggle's diff is per-click. The **Test against fleet** button under the By pattern block fires the same preview endpoint with *only* the patterns block populated so the operator can verify their regex without noise. Results above the rough warn threshold (currently 500 pinned interfaces total across the three classes — defined as `AUTO_MONITOR_INTERFACE_WARN_THRESHOLD` in `public/js/integrations.js`) trigger a confirm modal on Save Changes. **This confirm gates the save, not just the apply**: the Save handler splits the old `performSave` into `buildEditConfig()` (reads the form, no PUT) + `commitSave()` (the PUT + monitor-settings persist), runs the capacity confirm against the in-flight `buildEditConfig` result, and only calls `commitSave` once confirmed — cancelling leaves the integration unsaved and the edit modal open (previously the PUT had already landed before the confirm appeared, so Cancel still persisted the change). Legacy single-mode shape (`{mode: "names"|"wildcard"|"type", ...}`) from earlier releases is auto-coerced on read (Zod preprocess + apply path + frontend renderer all call `coerceLegacySelection`) and one-shot-migrated by `migrateAutoMonitorInterfacesShape` at boot.

**Decommission sweep for managed switches/APs.** Discovery tracks two new `DiscoveryResult` arrays — `switchInventoriedDevices` and `apInventoriedDevices` — listing the controller FortiGates whose `managed-switch/status` / `wifi/managed_ap` query returned successfully (including 404, which means the feature isn't licensed but the controller is reachable). At the end of the run, in the same pass that deprecates stale subnets (Phase 2), `syncDhcpSubnets` flips any switch/AP whose `discoveredByIntegrationId` matches this integration AND whose `fortinetTopology.controllerFortigate` is in the inventoried-devices set AND whose serial/hostname is no longer in the discovery's sighting set to `status="decommissioned"`. Switches/APs behind a controller whose inventory query *failed or timed out* are left alone (we didn't get a fresh answer). Re-discovery by serial number flips a decommissioned asset back to `active` (or `storage` for FortiSwitches reported as `Unauthorized`). Each decommission writes one `asset.fortiswitch.decommissioned` or `asset.fortiap.decommissioned` Event with the reason `missing-from-controller`.

**CMDB-vs-monitor query policy (proxy mode):** All CMDB-side data is queried natively from FMG (`/pm/config/device/<name>/...` or `/dvmdb/...`), NOT via `/sys/proxy/json`. Native FMG calls don't hit the per-device proxy throttle, so they parallelize freely even when `useProxy=true`. Only **live monitor** endpoints — DHCP leases, ARP, switch-controller detected-device, managed-switch/AP status, wireless-controller managed_ap, system resource usage — go through the proxy because they must be served fresh from the FortiGate. Currently native-from-FMG: device roster + per-device interface config + DHCP server CMDB + interface IPs + firewall VIPs + system/global (geo coords). Currently proxied (or direct): all `/api/v2/monitor/...` endpoints. The mgmt-IP resolver (`resolveDeviceMgmtIp`) reads from `/pm/config/device/<name>/global/system/interface` filtered by the integration's configured `mgmtInterface` — *not* the `ip` field on the FMG device DB record (that field can be a public/NAT IP and is not what Polaris should use to reach the device).

**Offline FortiGate CMDB pull.** A FortiGate that is offline in FMG (`conn_status !== 1`) is no longer skipped. FMG retains a cached copy of each managed device's config, so `processDevice` runs the **native-FMG CMDB steps only** for offline gates (interface IPs, DHCP subnets + static reservations, VIPs, geo, CMDB switch/AP rosters) and skips every `/sys/proxy/json` live-monitor query (leases, ARP, device inventory, live switch/AP status, detected-device) since the device is unreachable. This works in direct mode too: an offline gate skips the direct call (`if (!useProxy && !offline)`) and falls back to reading FMG's cache. The pull is strictly **config-only**: `DiscoveredDevice.offline=true` flows to the firewall sync, which withholds `bumpLastSeen` and does **not** resurrect a decommissioned firewall from an offline read (business rule #12 — cached config is not verified presence); and every `did*Query` flag is forced false before `processDevice` returns, so an offline gate's possibly-stale cache can never drive a stale-row release or switch/AP decommission (additive/refresh only). Offline gates stay in `knownDeviceNames`, so their subnets are preserved by the Phase 2 stale-subnet sweep exactly as before.

**Per-device transport (`useProxy` toggle):** The FMG integration has two per-device query transports, selectable in the integration edit modal. The UI checkbox is labeled "Query each FortiGate directly (bypass FortiManager proxy)" — *checked = direct, unchecked = proxy*. The on-disk field is still `useProxy` (true=proxy); the UI just inverts the semantics so the more aggressive option (direct) is the explicit affirmative action. The modal also surfaces a "more than 20 FortiGates → switch to direct" recommendation since proxy mode polls one device at a time.
- **Proxy mode** (default, `useProxy: true`): live `/api/v2/monitor/...` queries funnel through FMG's `/sys/proxy/json`. Parallelism is force-clamped to 1 because FMG drops parallel proxy connections past very low parallelism, surfacing as `fetch failed` on random calls. CMDB-side queries still run native-from-FMG and are NOT subject to this throttle (see "CMDB-vs-monitor query policy" above).
- **Direct mode** (`useProxy: false`): FMG is only used to enumerate the managed FortiGate roster + resolve mgmt IPs (still via the interface CMDB lookup, not the device-DB `ip` field — that one can be a NAT/public IP). Per-device live queries go direct to each FortiGate's management IP using shared REST API credentials stored in `config.fortigateApiUser` / `config.fortigateApiToken`. Each managed FortiGate must have the same REST API admin provisioned with a trusthost that includes Polaris. Delegates per-device work to `fortigateService.discoverDhcpSubnets` and remaps the device name back to FMG's label. Unlocks `discoveryParallelism` (up to 20).

**Reservation push (`pushReservations` toggle):** Both the **FortiManager** and **standalone FortiGate** integrations expose a `pushReservations: boolean` flag (default `false`) in their `config` JSON, edited from the **DHCP Push** tab on the integration's Add/Edit modal. When enabled, every manual reservation created on a subnet that this integration discovered is written to the FortiGate at create time; the Polaris row only flips `sourceType="manual" → "dhcp_reservation"` and stamps `pushStatus="synced"` after the write+verify round-trips successfully. **Transient device-side failures** (FortiGate offline, FMG unreachable, network timeout, generic 5xx — classified by `classifyPushError` in `reservationPushService.ts`) **persist the Polaris row with `pushStatus="pending"`** and the `retryQueuedReservationPushes` job pushes it once the gate recovers (see "Queued push lifecycle" below). **Permanent failures** (4xx, verify mismatch, auth failure) still abort the create — no Polaris ghost when the device write fundamentally can't land. Transport is dispatched by `buildTransportForIntegration()` in `reservationPushService.ts` based on integration type:
- **FMG, proxy realtime** (`type=fortimanager`, `useProxy: true`): the reserved-address row is written via FMG's `/sys/proxy/json` endpoint (`fmgProxyRest()` in `fortimanagerService.ts`) — FMG forwards the call to the FortiGate using its own stored device credentials. Lands on the FortiGate's running config in real time; FMG sees the change on its next config sync.
- **FMG, direct realtime** (`type=fortimanager`, `useProxy: false`): the device's management IP is resolved via FMG (`resolveDeviceMgmtIpViaFmg()`), then the write goes straight to the FortiGate's REST API using `config.fortigateApiUser` / `config.fortigateApiToken`.
- **Standalone FortiGate** (`type=fortigate`): the write goes directly to the FortiGate's REST API using the integration's own `apiUser` / `apiToken`. There is no FMG layer to choose, so `useProxy` doesn't apply.

Push scope resolution: `reservationPushService.findScopeIdForCidr` matches the subnet's CIDR against the FortiGate's `system.dhcp.server` table by reconstructing each scope's network from `default-gateway` + `netmask` (fall back: `ip-range[0].start-ip` inside the subnet). The matched `scopeId` and the new entry's `entryId` are stamped on the Reservation as `pushedScopeId` / `pushedEntryId` so unpush hits the exact device-side row without re-resolving. **Required FortiManager admin profile changes:** `Device Manager → Manage Device Configurations → Read-Write` is the only sub-permission that needs to flip from the existing read-only baseline; all other Device Manager and Policy & Objects sub-items can stay where they are. Importantly, `Install Policy Package or Device Configuration` should remain **None** — Polaris never triggers installs in this path. The blast radius warning surfaced in the modal is real: FMG profiles have no per-object DHCP-reservation knob, so granting Manage Device Configurations write enables write across every CMDB tree on every FortiGate in the ADOM. The modal also recommends direct mode + a per-FortiGate Custom profile (`Network → Custom → Configuration → Read/Write`) for shops that want least-privilege.

Description written to the FortiGate carries two formats keyed on whether operator notes are set: `Polaris/<username>: <notes> [<hostname>]` when notes are non-empty, `Polaris/<username>: <hostname>` when notes are blank (`Polaris: …` when no authenticated user is in scope, which currently never happens through the UI but covers system-initiated paths). The notes-first ordering exists because operators type Notes specifically as the FortiGate-side reservation comment; the bracketed hostname trails so `subnetRefreshService.extractHostnameFromDescription` can still recover a hostname during subnet refresh if Polaris ever loses it. Capped at 64 chars to fit comfortably in the FortiOS reserved-address `description` field across versions (older FortiOS 6.2 capped at 35; 7.x supports up to 255) — under truncation the trailing `[<hostname>]` is what gets clipped first, which is the right call (notes are the operator's intent; hostname is recoverable from Polaris itself). The "Polaris/" prefix lets a FortiGate admin looking at the device immediately identify entries written by Polaris and who pushed them.

`sourceType` flip on push success: when the FortiGate write verifies, the Polaris row's `sourceType` is updated from `manual` to `dhcp_reservation`. Two reasons: (1) the entry really is a DHCP reservation on the device now, and the UI badges should reflect that; (2) the next discovery run sees a matching `dhcp_reservation` row and the existing conflict-detection gate in `syncDhcpSubnets` (`if (existingRes.sourceType === "manual") upsertConflict(...)` in `discoveryEngine.ts`) is bypassed cleanly — no spurious conflict raised against our own echo. `pushedToId` remains the audit-trail answer to "did Polaris push this?" (and the `reservation.push.succeeded` Event also pins the origin in the audit log).

**Queued push lifecycle.** When create-time push hits a transient failure (or the pre-flight check sees the firewall asset is monitored AND `monitorStatus="down"` and skips the transport attempt entirely), the Polaris reservation is **kept** with `pushStatus="pending"`, `pushQueuedAt=now`, `pushAttempts=0..1` (0 on the monitored-down pre-flight skip, 1 after a real failed attempt), and `pushError=<message>`. `sourceType` stays `"manual"` because nothing has been written to the device yet — only successful push flips it. `pushedToId` IS stamped at queue time so the UI can render the target integration name without a second fetch, but no `pushedScopeId`/`pushedEntryId` (the device-side row doesn't exist yet).

The `retryQueuedReservationPushes` job (60s tick in `src/jobs/retryQueuedReservationPushes.ts`) drives `reservationService.retryPendingReservations`, which scans every `pushStatus="pending" AND status="active"` row, oldest first by `pushQueuedAt`. Each row passes through four per-row gates before the push attempt:

1. **Eligibility re-check** — subnet deprecated → cancel queue (`pushStatus=null`); subnet's `fortigateDevice` cleared → cancel; integration deleted / disabled → cancel; `pushReservations` flipped to false → cancel. Cancellation never deletes the Polaris row — operator's claim on the IP stands; they just won't get a device push for it. Writes `reservation.push.queued.cancelled` Event with the specific reason.
2. **Discovery-supersede** — another active reservation now at this `(subnetId, ipAddress)` from a discovery cycle? Flip to `pushStatus="failed_permanent"` with `pushError="IP collided during queue — discovered <sourceType> by <MAC>"`. Discovery row wins. Writes `reservation.push.queued.collided` (warning).
3. **Monitored-gate gate** — firewall Asset (joined on `hostname=fortigateDevice + discoveredByIntegrationId`) is monitored AND `monitorStatus !== "up"` → skip without incrementing `pushAttempts`. Recovery is signaled by the `monitor.status_changed → up` hook below.
4. **Unmonitored backoff** — no firewall Asset found, or `monitored=false` → compute backoff window `min(60 * 2^(pushAttempts-1), 1800)` seconds. If `pushLastAttemptAt + window > now`, skip without incrementing.

Past all four gates: increment `pushAttempts`, stamp `pushLastAttemptAt`, call `pushReservation`. Outcome stamped: success → standard `sourceType="dhcp_reservation"` + `pushStatus="synced"` + push pointers + clear queue cols + `reservation.push.queued.succeeded` (info). Transient failure → leave pending, update `pushError`, `reservation.push.queued.retry_failed` at **info** level (intentionally low-volume so a multi-day outage doesn't spam warning). Permanent failure → flip to `pushStatus="failed_permanent"` + `reservation.push.queued.failed_permanent` (warning) — operator action required.

**Latency-optimized retry on gate recovery.** `monitoringService.recordProbeResult` fires `triggerRetryAfterStatusChange(assetId)` whenever an asset transitions to `monitorStatus="up"`. The helper count-gates on `prisma.reservation.count({where: {pushStatus: "pending", subnet: {fortigateDevice: asset.hostname, discoveredBy: asset.discoveredByIntegrationId}}})` — zero pending = early return — so most up-transitions cost one indexed COUNT(*). When the count is non-zero, fire-and-forget invokes `retryPendingReservations` so the queued rows on the recovered FortiGate's subnets push within seconds of the gate coming back, instead of waiting up to 60s for the periodic tick.

**Edit / release while queued.** `updateReservation` and `releaseReservation` both early-branch on `pushStatus === "pending"`: edits just rewrite the queued payload (no device contact; MAC may be freely changed, still required for push-eligible subnets), and releases skip both the `unpushReservation` call AND the lease-release call (nothing on the device to clean up) — the cleaner `reservation.push.queued.released` (info) Event fires instead of the `reservation.unpush.failed` warning the regular release path would log.

**Operator-triggered retry.** `POST /reservations/:id/retry-push` (ownership-gated — own rows for `reservations:write`, all rows for `fullwrite`) calls `retryReservationNow` which bypasses the monitored-gate gate AND the unmonitored-backoff window. Still respects eligibility re-check and discovery-supersede. Allowed for `pushStatus IN ("pending", "failed_permanent")` so an operator can rescue a permanently-failed row after fixing whatever the permanent error called out — `failed_permanent` is flipped back to `pending` first so the retry path treats it uniformly.

**Discovery collision handling** in both `subnetRefreshService.ts` (per-subnet Refresh) and the full-discovery `syncDhcpSubnets` in `discoveryEngine.ts` adds two new behaviors when a fresh DHCP entry collides with an existing pending row at the same IP: (a) **fast-path adopt** — fresh entry is a `dhcp_reservation` with matching MAC → promote the pending row in place to `synced` with `pushedScopeId`/`pushedEntryId` stamped from the discovered entry; covers the "operator added it on the device while we were waiting" race and the "previous retry succeeded but Polaris missed the response" case; (b) **hard collision** — fresh entry is a `dhcp_lease` OR a `dhcp_reservation` with a DIFFERENT MAC → flip the pending row to `pushStatus="failed_permanent"` and SKIP the discovery create at this IP (the unique-on-active constraint would block it anyway). Operator must release the failed_permanent row to free the IP. To enable the fast-path-adopt to stamp device-side pointers without a separate REST roundtrip, the `DiscoveredDhcpEntry` shape in `fortimanagerService.ts` + `fortigateService.ts` carries `scopeId` + `entryId` (populated from `server.id` + `entry.id` at CMDB-read time) on `dhcp-reservation` entries.

Frontend MAC enforcement: the subnet IPs endpoint (`GET /subnets/:id/ips`) attaches a `pushEligible: boolean` field to its `subnet` payload, derived from `(integration.type === "fortimanager" || integration.type === "fortigate") && integration.config.pushReservations === true && fortigateDevice` (and IPv4 only — IPv6 reservations are not push-eligible in v1). The IP-panel reserve and auto-allocate modals read this and (a) re-label the MAC field as "MAC Address *" with a hint naming the target FortiGate, and (b) refuse to submit without a MAC. The backend `reservationService.createReservation` enforces the same rule server-side as the source of truth.

Release-time unpush is best-effort — a device-side failure logs `reservation.unpush.failed` (warning) but does not block the Polaris release, so an offline FortiGate doesn't stop operators from letting go of an IP. Two ownership paths mirror the MAC-update split: **Polaris-pushed** rows unpush by the pinned `pushedScopeId`/`pushedEntryId` (fires regardless of the current toggle state — cleaning up what Polaris created); **discovered** (never-pushed) `dhcp_reservation` rows — which carry no push pointers — also unpush on release **when the originating integration's `pushReservations` (DHCP writeback) toggle is on**, with `unpushReservation` resolving the scope by CIDR and the entry by IP at release time (read-only-discovery installs with the toggle off leave device config untouched). In **both** paths the release also drops any active DHCP lease for the IP via `releaseDhcpLease` (`/api/v2/monitor/system/dhcp/release-lease`), so deleting the MAC→IP binding fully frees the address rather than leaving a client holding the lease until expiry; the lease-release is independently best-effort and logs `reservation.lease_release.succeeded`/`.failed`. **MAC update on pushed reservations:** `PUT /reservations/:id` accepts `macAddress` (string; empty clears the stored MAC). When the originating subnet is push-eligible AND the MAC value changes, `reservationService.updateReservation` calls `updatePushedReservation()` in [reservationPushService.ts](src/services/reservationPushService.ts) which PUTs the new MAC + a refreshed description to the FortiOS reserved-address entry and verifies by read-back BEFORE the Polaris row is written — a device failure throws and the Polaris row stays untouched, so the two views never drift. Two ownership paths: Polaris-pushed reservations use the pinned `pushedScopeId`/`pushedEntryId`; discovered (never-pushed) reservations resolve the scope by CIDR and find the entry by IP, and the row is upgraded to "Polaris-pushed" on success. The FortiOS `description` is regenerated from the (possibly updated) hostname so it stays current as a side effect — but Polaris does NOT re-push for hostname-only changes; the description only refreshes when MAC changes. Audit lands as `reservation.push.updated` (info) on success or `reservation.push.update_failed` (warning) on failure. Clearing a MAC on a push-eligible subnet is rejected with 400 (DHCP reservations are MAC→IP — operators release the reservation instead). IP changes are still out of scope: an IP move = release + re-reserve.

**Quarantine push (`pushQuarantine` toggle):** Both the **FortiManager** and **standalone FortiGate** integrations expose a `pushQuarantine: boolean` flag (default `false`) in their `config` JSON, edited from the **Quarantine Push** tab on the integration's Add/Edit modal (alongside the DHCP Push tab). When enabled, `quarantineAsset()` pushes one `user.quarantine` target entry per asset (MACs carrying `drop: enable`, which is what actually blocks the traffic — the object's own `firewall-groups` attribute is the operator's and Polaris never writes it) to every FortiGate sighted by this integration within the `quarantine.sightingMaxAgeDays` window. If the toggle is `false` (or absent), quarantine push is skipped entirely for that integration's sightings — the asset's `quarantineTargets` array is left empty (or only populated from integrations that do have the toggle enabled). Release-time unpush iterates the recorded `quarantineTargets` directly (which only contain integrations that were enabled at push time) — toggling off `pushQuarantine` after quarantine has been pushed does not prevent unpush on release. Transport is dispatched by `buildTransportForIntegration()` in `assetQuarantineService.ts` and follows the same FMG-vs-standalone routing as reservation push.

**Verbose debug logging (`verboseLogging` toggle):** Every integration type (FortiManager, FortiGate, Entra ID, Active Directory, Windows Server) exposes a `verboseLogging: boolean` flag (default `false`) in `config`, edited from the **Debug** section at the bottom of the integration's edit modal General tab. When on, four things light up — all routed to pino at `info` level with a `verbose: true` payload tag, visible via `journalctl -u polaris -f -o cat`:
1. **Per-step discovery logs:** the `onProgress` callback in [src/services/discovery/discoveryEngine.ts](src/services/discovery/discoveryEngine.ts) emits one info-level line per step (`discover.dhcp`, `discover.leases`, `discover.fortiswitches`, etc.) alongside the existing Event row.
2. **Per-phase sync logs:** `syncDhcpSubnets`'s phase markers (1, 2, 2a, 2b, 2c, 3, 3b, 3c, 4, 5, 6, 7, 7b, 7.5, 8, 9, 10, 11, 12, 13) each emit a `discovery.phase.complete` line with elapsed ms when the next phase starts.
3. **Per-job worker logs:** every monitor job published for an asset owned by this integration gets `verboseDebug: true` stamped on its pg-boss payload; the worker handler emits `monitor.worker.pickup` + `monitor.worker.finish` lines with the worker slot id (`probe-W07`, `floating-F03`, etc.), `jobId`, `cadence`, `assetId`, outcome, and elapsedMs.
4. **Per-phase monitor handler logs:** the `verboseDebug` flag is forwarded into `WorkItemLabels.verbose`, which `runSystemInfoFor` reads to wrap the handler body in an `AsyncLocalStorage<MonitorPhaseContext>` (see `monitorPhaseStorage` + `startPhase` near `withSnmpGate` in `monitoringService.ts`). Every collector inside the chain — `collectSystemInfo`, `collectSystemInfoSnmp` (storage / interfaces / lldp / wireless walks), `collectSystemInfoFortinet` (cmdb / monitor-interface / ipsec / lldp REST calls), `recordSystemInfoResult` (assoc-IPs txn, lldp persist, wireless persist, update_asset), `persistLldpNeighbors` (lldp_match_index, find_existing, lldp_upsert, deleteMany — the legacy `createMany` + per-row `update_txn` pair collapsed to one bulk `INSERT … ON CONFLICT (id) DO UPDATE` raw-SQL statement so the connection isn't held across N pipelined updates inside a transaction; `persistWirelessStations` follows the same shape) — emits one `monitor.phase` line with `phase`, `assetId`, `cadence`, `elapsedMs`, and contextual extras when the span closes. No-op closure when verbose is off, so zero per-tick allocation in the steady state. **Two `withSnmpGate` + `buildLldpAssetMatchIndex` logs ARE always-on** regardless of the flag: a WARN line when an SNMP collector waits >5s in the per-host FIFO behind another collector, and an INFO start/complete pair around the LLDP match index rebuild (`lldp_match_index.rebuild_*`) — both bounded in volume by their own gating (gate wait threshold + 60s cache TTL respectively), and both diagnose the leading "systemInfo handler wedges at 300s" hypotheses without needing any toggle flipped.

**Auto-disable after 30 minutes.** When `verboseLogging` is enabled the backend stamps `verboseLoggingEnabledAt` (ISO timestamp) in the integration's `config` JSON. Every subsequent read of the flag (`isVerboseLoggingActive()` in `discoveryEngine.ts`) enforces a 30-minute TTL — expired flags are treated as `false` without a DB write. The `expireVerboseLogging()` function (called every 30 s from `discoverySlowCheck`) writes `verboseLogging: false` and clears `verboseLoggingEnabledAt` back to the DB when the window is up, so the checkbox in the edit modal reflects the true state on next open. Legacy rows created before this feature (no timestamp) are treated as active and self-correct the next time the operator toggles the flag. The UI checkbox label shows an amber countdown ("— auto-disables in N min") while the window is open.

No restart needed — the next discovery cycle and next monitor tick pick up the flag. Default off everywhere so existing installs see no extra log volume. Operator workflow: flip the checkbox in the integration's Debug section → `journalctl -u polaris -f -o cat | grep <integration-name>` (or `| jq 'select(.verbose==true)'`) → flag clears itself after 30 minutes.
