# Monitoring architecture — polling-method resolution, agentless streams, credentials

Verbatim from ARCHITECTURE.md → Monitoring Architecture (first half). Polaris Agent paragraphs live in `polaris-agent/references/agent-server-side.md`; the Fortinet-specific half is `monitoring-architecture-fortinet.md`.

> Moved from CLAUDE.md's Authentication & RBAC section. Covers polling-method resolution, the Polaris Agent, branch-class FortiGate workarounds, per-class FortiSwitch/FortiAP direct polling, push toggles, and verbose-logging behavior.

**Polling-method redesign (resolved per stream from a four-tier hierarchy).** There is no longer a per-asset `monitorType` column. Each of the six streams (response-time probe / CPU+memory / temperature / interfaces / LLDP / storage) gets a polling method picked from a hierarchy: per-asset `*Polling` columns → `MonitorClassOverride.*Polling` → `Integration.config.monitorSettings.polling.*` (or the manual-tier `manualMonitorSettings.*Polling` Setting for orphan assets) → source default. Source defaults: FMG/FortiGate → **`icmp`** on response-time, `rest_api` on CPU+memory / temperature / interfaces, **`disabled`** on LLDP, **`disabled`** on storage (FortiOS appliances don't expose meaningful mountable storage, so the SNMP storage walk would burn cycles on every scrape — operators flip storage to `snmp` per-asset when they have a device that does); AD / Entra ID / Windows Server / Manual → `icmp` for response-time, null (= "not delivered") on the other five; **vCenter → `vcenter` on response-time, CPU+memory, interfaces AND storage** (temperature + LLDP null), because one batched fetch per integration per tick answers all four for both VMs and ESXi hosts — see "vCenter Discovery Workflow". Response-time defaults to ICMP across every source kind because ICMP is the cheapest universal liveness probe — operators wanting a heavier transport (REST `/sys/status`, SNMP `sysUpTime`) opt in per-asset, per-class, or at the integration tier. The compatibility matrix from `utils/pollingCompatibility.ts` enumerates the methods each source can use plus `"disabled"` (universally allowed; expresses "do not poll this stream") and `"agent"` (Polaris Agent installed locally on the host — allowed on AD / Entra / Windows Server / Manual sources only, never appliances). The storage stream is **SNMP or vCenter** (HOST-RESOURCES-MIB `hrStorageTable` + the vendor disk fallback in `pickVendorProfileMerged`; or the guest filesystems / host-mounted datastores in the vCenter warm cache); operators set `storagePolling=snmp` at any tier to opt in on an SNMP device, and the SNMP collector reuses the asset's interfaces credential (no separate storage credential / MIB column on Asset or MonitorClassOverride). The dedicated storage-only cadence (`runStorageFor`) stays SNMP-only — vCenter storage rides the system-info pass, which is already one Map lookup. Methods that don't apply to the asset's source kind are silently ignored at resolution time; the route layer rejects them at write time with a clear 400.

**FortiOS REST reachability gates the FMG source defaults (2026-08-28).** The `rest_api` defaults above assume Polaris can make a FortiOS call to the device. On a **FortiManager on the proxy transport with no `fortigateApiToken`** it cannot: every FortiOS collector builds its config through `buildFortinetConfig()`, which has **no `useProxy` branch** — it dials the asset's own IP and requires that token — so `rest_api` on CPU+memory / temperature / interfaces threw `409 FortiManager direct-mode API token not configured` on every tick, forever, on an integration left at its defaults. `loadIntegrationTierSettings` now stamps a `tierFortiosRestUnavailableCache` sidecar off the config it already reads (no extra query, invalidated with the tier cache), and `defaultPollingForSource(source, stream, {assetType, fortiosRestUnavailable})` returns `disabled` for those three instead. **Response time is deliberately unchanged (`icmp`)** — moving it would silently change how up/down is decided for every gate on every affected install. The one exception is a managed FortiSwitch / FortiAP's response time, which stays `rest_api`: that read goes to the PARENT gate's controller table via `fetchViaFortinetTransport`, the one monitoring path that honours `useProxy`, so it works on FMG's own credential. The shared predicate is `fortiosRestUsable(stream, assetType)`.

**Compatibility vs capability (2026-08-28).** `utils/pollingCompatibility.ts` says whether a method is MEANINGFUL for a source; `utils/pollingCapability.ts` says whether the COLLECTOR EXISTS. Only the write validators' silence about the second let a stream be configured into permanent quiet — `ssh`/`winrm` on cpuMemory / temperature / interfaces / storage / lldp, `snmp` on processes, `rest_api` on FortiOS storage or on anything beyond up/down for a managed FortiSwitch, and `eventLog` on every transport but the agent all resolve fine and collect nothing, while `runTelemetryFor` records a successful tick. The validators now WARN (not refuse — a 400 would punish an operator re-saving a pre-existing value), the dropdowns stop offering them, and `auditPollingCapability` names what is already stored. The one thing promoted to a hard refuse is **ICMP on a non-response-time stream via `PUT /assets/:id`**: the integration-tier and class-override validators always rejected it and the per-asset path never did.

**Agentless host streams (2026-08-28).** `ssh` / `winrm` now deliver **cpuMemory, interfaces and storage** as well as processes, via `agentlessHostService`. The queue gates that used to drop them before enqueueing are gone (`canTelemetry` in both `computeDueWork` and `jobs/monitorAssets`, and `runStorageFor`'s hardcoded SNMP-only test — that cadence now covers SNMP + ssh + winrm, while the agent pushes on its own schedule and vCenter storage rides the system-info pass). The credential chain is the one `runProcessesFor` already used, lifted into the shared `resolveAgentlessCredConfig` (per-stream asset credential → class override → AD bind fallback) so three collectors cannot drift. Interfaces and storage ride ONE connection when both are on the same transport. Still absent over a shell and correctly reported so by `pollingCapability`: **temperature** (Linux hwmon is readable but `MSAcpi_ThermalZoneTemperature` is unimplemented on most real Windows hardware, so neither side ships rather than working on half a fleet) and **LLDP** (no shell equivalent at all).

**Agentless OS event log (2026-08-28).** `eventLog` had settings at every tier and a working sink — `ingestOsEventLog`, which curates entries into the audit Event table with a min-level filter, dedupe, a per-push cap and a per-asset hourly rate cap — but no server-side collector and no cadence, so only the Polaris Agent ever delivered it. `runEventLogFor` closes that: `journalctl -o json -p warning` over SSH (**line-delimited JSON, not an array**) or `Get-WinEvent` at levels 1–3 over WinRM, into the SAME sink, gated by the SAME global `agentEventLog` master switch — an operator who turned the feature off must not have an agentless poller keep filling the audit log. It is the ninth `MonitorCadence`, with its own queue (`polaris-monitor-eventlog`), pool (`POLARIS_MONITOR_EVENTLOG_WORKERS`, default 8 — smaller than processes because what it collects ships off-host through the syslog / SFTP archivers) and anchor (`Asset.lastEventLogAt`, migration `20260828060000`).

Two decisions worth knowing. The collection window is derived from the stream's own interval (1.5×) rather than a row count: a poll asking for "the last N entries" either misses a burst or re-ingests the same quiet hour, whereas asking for "everything since a bit longer ago than my last run" neither drops nor duplicates — the deliberate overlap is cheap because the sink dedupes. And `lastEventLogAt` is stamped **even on failure**, exactly as `runProcessesFor` stamps its anchors: an agentless stream that re-fires every tick against a bad credential is an AD-lockout risk, and this is the one stream where a retry storm would also flood the table it writes into.

**The `fortimanager` polling method (2026-08-28).** A ninth `PollingMethod`, valid on the **response-time stream only** (`FORTIMANAGER_STREAMS`) and the **`fortimanager` source only** — a standalone FortiGate has no FortiManager to ask, and neither does `manual`, which is why that source's set is now spelled out instead of inheriting `ALL_METHODS`. Instead of touching the device it reads FortiManager's own device database: `fetchRosterConnectivity` issues one NATIVE `/dvmdb/adom/<adom>/device` call (no `fields` list — naming fields makes FMG authorize each one and fail the query with `-11`) and `extractRosterConnectivity` projects it to per-serial reachability, walking the same rows and the same `ha_slave[]` members as `extractRosterIdentities` so the two cannot disagree about which serials exist. Encodings match discovery's: top-level `conn_status === 1` is connected with **absent counting as connected** (an FMG that stops reporting the field must not mass-down a fleet), and `ha_slave[].status` 1/0 per member — the standby's only appearance anywhere.

Cost is the point: native reads are outside the `/sys/proxy/json` concurrency-1 lane, and `fetchFmgRosterCached` (30 s TTL + promise-singleton, the controller/vCenter cache shape) makes one request serve every gate on the integration — ~187 gates for one round trip rather than 187 serialized proxy calls or 187 direct dials. It also reaches a gate Polaris has no route to, since only FortiManager must be reachable. `probeFortimanagerNative` dispatches in `probeAsset` **before the IP guard** and identifies the chassis by **serial, never by name** (`fortinetTopology.deviceName` is FMG's device name, which diverges from the gate's configured hostname on real fleets — the `utils/fortinetParentKey.ts` trap; a name mismatch would read as "gone from FortiManager"). **FMG unreachable ⇒ `ProbeResult.skipped`**, not a failure — the vCenter reasoning in business rule 30: the thing that answers for the device is not the device, so one manager outage must never down a whole fleet at once. A gate FMG answers about and reports disconnected IS a real failure.

What it trades away, and why it is one stream rather than a transport: the reading is FMG's, on FMG's check-in cadence, so it is **lagged and second-hand** — it says the chassis is talking to its manager, not that it is serving traffic. It carries **no uptime**, so it drives no reboot detection. And FMG's database holds nothing else worth polling: no CPU, memory, temperature, interface counters or session count, and no live switch/AP status (those are FortiOS monitor endpoints, which is why they ride the proxy or a direct call). **Not a source default** — response time stays `icmp`, because repointing a default would silently change how up/down is decided for every gate on every FMG install.

The same predicate feeds the resolver's validity gate, so a **stored** `rest_api` (authored in bypass mode, or before the token was cleared) is skipped like any other method the source cannot use and the layer below stays — which is what makes the UI's "locked to inherited" true at runtime. It is **non-destructive**: the stored value is never rewritten and returns the moment a token is supplied. Note the condition is NOT simply proxy mode — proxy WITH a token is a legitimate configuration (discovery and writes ride FMG, monitoring reaches the gates directly) and keeps the normal REST defaults. Mirrored client-side by `_fortiosRestUsable` / `_fmgFortiosRestUnavailable` / `_applyFortiosRestLocks` in `public/js/integrations.js`, which disable the affected dropdowns and render a note naming the token as the thing that unlocks them; the FMG-FortiGate class's stream subtabs are no longer hidden behind the transport toggle, since hiding them explained nothing and left the stored values invisibly in force.

**A per-asset REST API credential is the second token source (2026-09).** The gate above assumes the only FortiOS token is the integration's, which is fleet-wide by construction — the FMG Monitoring tab's own hint says it "must be the same across all managed FortiGates". A fleet where each gate carries its own api-user therefore had no way to be polled over REST at all, no matter which method was selected. `buildFortinetConfig(host, integration, credential?)` now prefers a `restapi`-typed `Credential` over the integration's token, resolved per stream through `utils/fortinetRestCredential.ts` and threaded into all five REST collectors: `probeFortinet` (responseTime, `responseTimeCredential`), `collectTelemetryFortinet` (cpuMemory), the `collectHardwareSensorsFortinet` dispatch (temperature), `collectSystemInfoFortinet` + `collectIpsecOnlyFortinetSafe` + `applyFortilinkLldpExclusion` (interfaces), and `collectLldpOnlyFortinet` + `overlayCrossTransportLldp` (lldp). The FortiAP controller-cache reads (`collectTelemetryFortiapRest` / `collectHardwareSensorsFortiapRest`) deliberately get none — those go to the PARENT gate's `wifi/managed_ap` table and authenticate as the parent, so an AP's own credential would be the wrong one. A stream carrying such a credential is additionally **exempt from the skip in the paragraph above** (`assetStreamCredentialId` → the resolver's `ok()`): a per-asset token is precisely what makes a FortiOS call possible where the fleet-wide one is absent, so discarding the method there would silently throw away the operator's fix for the condition being detected. The credential's TYPE cannot be known without a DB read and the resolver takes none on the hot path, so a wrongly-typed credential surfaces as a collection error naming the missing token rather than as a stream that quietly resolves elsewhere. Before this, selecting that credential persisted, resolved, rendered in the modal — and collected nothing, forever, with the tick reporting success: the `pollingCapability.ts` failure class one layer further in, where the collector exists but reads a different token than the UI offered.

**The `http` method — RETIRED (2026-08).** There WAS an `http` polling method: a responseTime-only GET that decided up/down from a status code and an optional body match. It is gone from `PollingMethod`, from every `COMPATIBILITY` set, from `probeAsset`'s dispatch, from both route enums and from the UI mirrors; `tests/unit/pollingCompatibility.test.ts` asserts it cannot come back silently. The check itself survives and is now a **manufacturer custom widget** (`widgetType: "http"`, business rule 33). The reason is ownership of the DEFINITION: as a polling method the check had to ride an `http`-typed Credential, so the row that answers "how do I log in to this vendor" also carried "which path, expecting what" — a second path meant a second copy of the same password. Keyed by manufacturer + optional `modelPattern` it varies on the axis a check actually varies on, and the credential is authentication only. `probeHttp` is unchanged as the socket owner; what changed is who calls it (`collectAndRecordCustomWidgets`, on the telemetry cadence) and where the result lands (`AssetStateSample` 0/1 + an `AssetCustomWidgetSample` response-time gauge, NOT `monitorStatus`).

**Where the polling method comes from.** Per-stream dropdowns appear at four tiers in the UI:
- **Manual tier** — Assets page → Monitoring Settings modal → Manual Monitoring section. Accepts any method (covers any source).
- **Integration tier** — each integration's edit modal → Monitoring tab → Cadence & Retention section. Methods filtered to the integration's source kind.
- **Class override** — Assets page → Monitoring Settings modal → Class Overrides. Methods re-render when the source picker changes; integration-scoped overrides are pinned to the integration's source kind.
- **Per-asset** — asset edit modal → Monitoring tab. Methods filtered to the asset's source kind.

`/api/v1/assets/:id/effective-monitor-settings` returns the resolved values plus per-field provenance (`asset` / `class` / `integration` / `manual`) so the asset edit modal can render tier badges. Each "Inherit" option in every dropdown is labeled with the resolver's expected fallback ("Source default: REST API" / "Source default: ICMP" / "Not delivered for this source") so operators see what they'd inherit without clicking through.

**Credential resolution.** A polling method that needs authentication (`snmp`, `winrm`, `ssh`, `rest_api`) walks four tiers, most-specific first: per-stream asset credential (`Asset.responseTimeCredentialId` / `telemetryCredentialId` / `interfacesCredentialId` / `lldpCredentialId`) → asset's generic `Asset.monitorCredentialId` → class-override per-stream credential (`MonitorClassOverride.responseTimeCredentialId` / etc — surfaced by `resolveMonitorSettings` onto the resolved `*CredentialId` fields, looked up in the dispatcher via `loadClassOverrideStreamCredential`) → integration fallback. The integration fallback is FMG/FortiGate-discovered firewalls reading `Integration.config.monitorCredentialId` (SNMP) or the stored API token (REST API), and AD-discovered hosts reading the integration's `bindDn` / `bindPassword`. The asset's monitor credential picker is type-agnostic — the operator pairs it with their chosen polling method. Credential / method mismatches fall through silently at probe time to a clear error; setting a SNMP credential on an asset whose `responseTimePolling` is `winrm` is allowed but the probe will report "No WinRM credential selected" until one is attached.

**Where vendor SNMP knowledge lives (the boundary, 2026-09-15).** Polaris ships the engine and the IETF/IEEE standard MIBs (`src/services/stdMibs/`); every vendor-specific SNMP fact is data the operator owns. A vendor's OIDs come from the MIB the operator uploads and resolve BY SYMBOL NAME through `oidRegistry.ts → resolveOidSync(symbol, { manufacturer, model })`; which symbol means CPU, or which table is the sensor table, is a `ManufacturerProfile` row. The rule is mechanical: **no enterprise-arc OID literal (`1.3.6.1.4.1.*`) anywhere in `src/`**, enforced by `tests/unit/noEnterpriseOids.test.ts` as a burn-down — `ENTERPRISE_OID_ALLOWLIST` names the three files that still carry literals (`oidRegistry.ts`'s vendor seeds, `monitoringService.ts`'s Fortinet table map, `fortiapRadioSnmp.ts`'s column tables) and each phase of the uniform-SNMP plan removes one. Standard arcs may stay numeric; decoding logic (a MAC packed in a table index, an enum, the FortiSwitch trunk string) may stay code — code may know how a table is shaped, never where a vendor put it. `snmpIdentity.ts` is identity, not telemetry: its escaped regex extracts an IANA enterprise NUMBER to name a vendor and walks nothing. An unresolved symbol degrades to "not collected for this asset" with a log line naming the symbol — never a throw, never a wipe of existing inventory rows. Full contract, phases and blast radius: `polaris-change-impact` → cross-cutting/vendor-snmp-knowledge-boundary.md.
