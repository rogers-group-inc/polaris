## FMG Discovery Workflow

> See `polaris-monitoring-discovery/references/fmg-discovery-decision-tree.md` for the at-a-glance decision tree (transport mode, roster filtering, per-class stamping, push toggles) — that doc is the operator-facing reference; this section is the phase-by-phase narrative and data shapes.

### Asset projection priority table

For each discovery-owned Asset field, the table below lists the ordered set of `AssetSource.sourceKind` rows that `projectAssetFromSources()` consults. First non-empty observed value wins. Inferred sources are skipped. Source kinds not listed for a field = the projection deliberately doesn't consult them. When an asset holds several rows of the SAME kind (one `fortigate-endpoint` row per MAC on a device that changed NICs), the freshest row by `lastSeen` speaks for that kind — the kind's position in the order is unchanged. The actual rules live in `src/utils/assetProjection.ts` — keep this table in sync when editing them.

**One post-pass runs after the priority resolution:** `normalizeWindowsOs` (`src/utils/osNormalize.ts`) rewrites the winning `os` / `osVersion` pair for Windows CLIENTS, because the priority order can't help here — *every* source in the `os` row reads the registry `ProductName` key Microsoft froze at "Windows 10" when Windows 11 shipped, so whichever one wins is equally wrong on a Windows 11 machine. The build number decides the family and gets labeled with its release ("Windows 10 Pro" + "10.0.22631.7219" → "Windows 11 Pro" + "23H2 (10.0.22631.7219)"). `provenance` still names the source the raw value came from. Windows Server, non-Windows, and undeterminable builds pass through untouched.

| Asset field         | Priority (high → low)                                                                                                                                                                        |
|---------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `hostname`          | `polaris-agent` (`hostname` — `os.Hostname()` on the host itself) → `ad` (`dnsHostName` containing a dot — FQDN only) → `intune` (`deviceName`) → `entra` (`displayName`) → `ad` (`dnsHostName` short or `cn` fallback) → `fortigate-firewall` (`hostname`) → `fortiswitch` (`switchId`) → `fortiap` (`name`) → `fortigate-endpoint` (DHCP client id) |
| `serialNumber`      | `polaris-agent` (DMI `product_serial` / IOPlatformSerialNumber / Windows registry) → `intune` → `fortigate-firewall` → `fortiswitch` → `fortiap`                                              |
| `manufacturer`      | `polaris-agent` (DMI `sys_vendor` / ioreg manufacturer / BIOS registry, alias-normalized) → `intune` (alias-normalized) → `fortigate-firewall` / `fortiswitch` / `fortiap` (always literal `"Fortinet"`) → `fortigate-endpoint` (`hardwareVendor`, alias-normalized) |
| `model`             | `polaris-agent` (DMI `product_name` / ioreg model / BIOS registry) → `intune` → `fortigate-firewall` → `fortiap` → `fortigate-endpoint`                                                       |
| `os`                | `polaris-agent` (os-release `PRETTY_NAME` / sw_vers / Windows edition string) → `ad` → `intune` → `entra` → `fortigate-endpoint`                                                              |
| `osVersion`         | `polaris-agent` (os-release `VERSION_ID` / sw_vers `ProductVersion` / Windows build) → `intune` → `entra` → `ad` → `fortigate-firewall` → `fortiswitch` → `fortiap` → `fortigate-endpoint`     |
| `learnedLocation`   | **OPERATOR-ORDERED** — the one projected field whose priority is configurable (Assets → Settings → Sources; `assetSourcePriority` Setting, `assetSourcePriorityService`). Default order (closest-to-a-place first) = `fortigate-endpoint` (FortiGate device name as site label) → `arc` (label `"Azure Arc"`) → `intune` (label) → `entra` (label) → `arc-k8s` (label) → `vcenter-vm` (`clusterName`, else `hostName`) → `vcenter-host` (`clusterName`) → `ad` (`ouPath`) → `fortiswitch` (`controllerFortigate`) → `fortiap` (`controllerFortigate`). The sighting gate leads because it is the only contributor naming a physical place; the label-only cloud sources come next because for a cloud-only device nothing else can answer at all; AD is late because an OU path is org structure that reads as a location only by the accident of most sites naming OUs after buildings; fortiswitch/fortiap sit at the bottom where their rank is inert (those kinds only exist on switch/AP assets, which have no other contributor). This is NOT the pre-feature hardcoded order, which led with `ad` — an install that never saved its own order re-labels on its next discovery run. Contributions come from `utils/assetSourceLocation.ts` (declaration order IS the default); the rule list is BUILT from the order rather than declared in `assetProjection.ts`. Two things the order can't override: `fortigate-endpoint` is **suppressed when ANY Fortinet infra source exists** (`LOCATION_SUPPRESSING_INFRA_SOURCES` = fortigate-firewall / fortiswitch / fortiap — a firewall's site label is its own hostname and a switch/AP's is its controller, so the gate that sighted it as a DHCP client pre-adoption must not relabel it; that stale endpoint row outlives the adoption), and `polaris-agent` / `manual` / `fortigate-firewall` never contribute. With `integrationPrefix` on, Fortinet contributions render `<integration name>:<device name>` from `observed.integrationName`. |
| `ipAddress`         | `fortigate-firewall` (`mgmtIp`) → `fortiswitch` (`mgmtIp`) → `fortiap` (`mgmtIp`) → `fortigate-endpoint` (live DHCP/ARP — effectively first for plain endpoints, which carry no infrastructure source). Infrastructure mgmtIp outranks the endpoint sighting because a newly-deployed FortiGate/switch/AP is often first discovered as a DHCP client of an existing gate, then adopted into FMG — post-adoption the management IP is the address monitoring must probe, not the pre-adoption lease. |
| `latitude` / `longitude` | `fortigate-firewall` — three tiers walked in order on the same source: (1) `snmpGeocodedLatitude` / `snmpGeocodedLongitude` (the geocoded-location tier; source string is the FMG **address metavar** when set+populated, else SNMP `sysLocation` when `pullSnmpLocation` is on) → (2) `metavarLatitude` / `metavarLongitude` (FMG per-device coordinate metavars named by `latitudeMetavar`/`longitudeMetavar`, default `Latitude`/`Longitude`; FMG-only, undefined on standalone) → (3) `latitude` / `longitude` (CMDB `gui-device-*` mirrored by FMG / fetched direct by standalone). Each picker validates the (lat,lng) pair as a whole via `isValidGeoCoord` so a half-valid tier falls through. |
| `snmpLocation`      | `fortigate-firewall` (`snmpLocation`) — FortiGate-only. Surfaced on the asset details General tab independent of whether geocoding produced usable coords.                                    |
| `learnedAddress`    | `fortigate-firewall` (`metavarAddress`) — FMG address metavar string, FMG-only. Surfaced as "Address" on the General tab. Only (re)written by discovery when an address metavar is configured that cycle.                                    |

**Fields the projection does NOT own** (and why):
- `macAddress` / `macAddresses[]` — DHCP discovery + Intune writes feed these directly to Asset; merge happens inline in the discovery sync. Infrastructure management MACs are stamped the same direct way: FortiSwitch/FortiAP `baseMac` and the FortiGate firewall's interface MACs. For firewalls, discovery reads `/api/v2/cmdb/system/interface` (no name filter) and captures **every physical interface MAC** (`macaddr`, all-zero loopback/tunnel MACs dropped) — not just the mgmt interface — because a peer FortiGate can sight the firewall in its ARP/device-inventory table on any interface. All of them are written to `macAddressRows` (scalar `macAddress` = the mgmt-interface MAC when present) so discovery's in-memory `byMac` index recognizes the firewall regardless of which interface was sighted, and never spawns a duplicate `fortigate-endpoint` ghost. Primary HA member only. The observed blob records `mgmtMac` + `interfaceMacs` for the Sources tab, but projection does not consume them.
- `status` / `quarantine*` — multi-actor (discovery / quarantine code / decommission job / manual operator) — too many writers for projection to arbitrate.
- `assetType` — usually inferred at create time from OS string and stable thereafter; manual recategorization is sticky.
- `location`, `department`, `assignedTo`, `notes`, `tags`, `monitor*`, `dnsName` — operator-owned or system-owned, not from discovery sources.

**FMG/FortiGate projection apply pass (slice 4f cutover):** The five FMG/FortiGate discovery pathways (DHCP-reservation / DHCP-lease / device-inventory / MAC-table / ARP) each still write Asset fields opportunistically inline (set-when-empty for OS / manufacturer / learnedLocation, set-always for osVersion, etc.) — EXCEPT on Fortinet-infrastructure assets (firewall/switch/access_point), where the inline os/osVersion writes are skipped entirely: those assets get canonical FortiOS firmware strings from their own discovery loops via projection, the device-inventory os_version for the same boxes is FortiOS's cached client fingerprint in display format ("7.4.5 Build 0734") that lags upgrades, and Phase 11 excludes infra assets so a stale inline write was never corrected (prod 2026-07: Phase 7 re-staled AP firmware minutes after the AP loop healed it, every cycle). After Phase 10 stamps the `fortigate-endpoint` source rows, **Phase 11 of `syncDhcpSubnets` re-projects every touched asset** and writes back any field where projection priority disagrees with the inline-written value. Fixes the long-standing bug where Intune's verbose `osVersion = "10.0.19045"` gets overwritten by FortiOS's coarser `osVersion = "10.0"` on every device-inventory pass, plus mirror cases where AD's `"Windows 10 Pro"` should beat Intune's `"Windows"`. Only writes fields where the projected value is non-null AND differs from current Asset; quiet syncs skip the round-trip. `ipSource` is set to `<integrationType>:fortigate-endpoint` whenever the projected ipAddress wins, mirroring the existing inline ipSource convention. **Inline-only fields** (not subject to Phase 11): `lastSeenSwitch`, `lastSeenAp` (no source kind besides fortigate-endpoint observes them; "stamp inline, never project" is correct), `macAddresses[]` (multi-source merge happens inline at write time), `status` / `quarantine*` / `assetType` / operator-owned fields.

> **Multi-source asset model (Phase 2 cutover, infrastructure scope) and projection layer (Phase 3b.1 cutover):** Every discovered Fortinet infrastructure asset is on the new `AssetSource` model — firewalls (`sourceKind="fortigate-firewall"`), managed FortiSwitches (`sourceKind="fortiswitch"`), and managed FortiAPs (`sourceKind="fortiap"`) each get an explicit row keyed on `externalId = serialNumber` with a rich source-shaped `observed` blob. Discovery-owned Asset fields (hostname, model, osVersion, manufacturer, serialNumber, ipAddress, latitude, longitude, learnedLocation for switches/APs) come from `projectAssetFromSources()` instead of inline merge logic — every update path upserts the source first, fetches all sources, computes projection, then writes a single Asset.update; every create path projects from a synthetic single-source array (no DB roundtrip) and uses the result in the Asset.create payload. Firewall `learnedLocation` deliberately stays inline (set to the firewall's own hostname / site label) since the projection layer leaves it null for firewall sources by design. Firewall: serial, hostname, model, osVersion, mgmtIp, lat/long, managedBy: "fortimanager"|"fortigate". FortiSwitch: serial, switchId, model, osVersion, mgmtIp, **baseMac** (management MAC of the FortiLink-peer interface, cross-joined at discovery time from the `/api/v2/monitor/switch-controller/detected-device` rows where `is_fortilink_peer===true` and `switch_id===<this switch's switch-id>`; null when the join misses), controllerFortigate, uplinkInterface, state, connected, joinTime. FortiAP: serial, name, model, osVersion, mgmtIp, baseMac, status, state (controller admission — "authorized"/"discovered"/...), controllerFortigate, parentSwitch, parentPort, parentVlan, uplinkInterface (AP-local port from `wan_status.interface` or LLDP `local_port` — `lan*` physical / `wbh*` wireless bridge), peerSource, meshUplink, parentApSerial, plus the live telemetry snapshot the discovery query already paid for: cpuPct, memFreeMb, memTotalMb, sensorTemperatures. Re-discovery keys on `Asset.serialNumber` via the in-memory `findBySerial` index — the source row exists for the per-source detail view rather than for primary lookup, so the discovery hot path is unchanged. **Endpoint scope (post-Phase-4d):** every endpoint asset the FMG/FortiGate sync touches gets a unified `sourceKind="fortigate-endpoint"` source row (externalId = MAC, normalized colon-uppercase) covering all five discovery pathways — DHCP reservations, DHCP leases, device-inventory (FortiOS `device/list` with hardware/OS/user fingerprinting), switch-port MAC table, ARP enrichment. Whichever pathway found the device contributes its observed fields (hostname, ipAddress, ipSource, os, osVersion, hardwareVendor, model, learnedLocation, lastSeenSwitch, lastSeenAp, discoveredVia); pathways that didn't run leave their fields null. Stamping happens at end-of-sync via a touched-asset-id Set populated as each pathway updates an asset; the upsert helper also sweeps any "manual" Phase-1 placeholder source on the same asset. Backfill startup job `backfillFortigateEndpointSources` covers existing endpoint rows that predated the cutover.

### FMG worker (per-integration, two lanes)

Every code path that talks to FortiManager funnels through a per-integration `FmgWorker` (`src/services/fmgWorker.ts`), which exposes two lanes. The FMG concurrency constraint — "FMG drops parallel API calls past 1-2 for the same API user" — is specifically about `/sys/proxy/json` passthrough calls, not native FMG endpoints. Native endpoints (`/pm/config/...`, `/dvmdb/...`, auth) hit FMG's own database and don't share that constraint, so serializing them was leaving discovery throughput on the table.

- **Proxy lane** — strict single-consumer FIFO (concurrency=1). Honors the hard FMG limit. Used for every `/sys/proxy/json` call: per-device monitor scrapes in proxy mode (DHCP leases, device inventory, managed switches/APs, detected-device MAC table, ARP table), proxy-mode reservation push, proxy-mode quarantine push, and the operator-facing manual `/sys/proxy/json` proxy endpoint.
- **Native lane** — unbounded. Just tracks inflight count for observability. Used for every native FMG call: device roster (`/dvmdb/...`), management-IP resolution (`/pm/config/device/<n>/global/system/interface`), DHCP server CMDB, interface config CMDB, switch/AP CMDB rosters, firewall VIPs, geo coords, auth, testConnection.

Dispatch happens inside `rpc()` (fortimanagerService) by inspecting the JSON-RPC payload's first param URL — callers don't pick the lane manually. Cross-feature serialization still holds on the proxy lane: an operator clicking "Reserve IP" mid-discovery still has the reservation-push proxy call wait behind in-flight discovery proxy calls. Native parallelism lets discoveryParallelism actually deliver on its promise: in direct mode, mgmt-IP resolution for cache-cold devices is now parallel (was the dominant serial bottleneck on fresh installs); in proxy mode, the ~7 native CMDB scrapes per device overlap with each other and with the proxy lane's serial monitor scrapes.

Beneath both lanes, `rpcInner`/`rpcAttempt` apply a bounded transient-retry policy (FMG API Best Practices Guide): HTTP 5xx and network/timeout faults retry up to 2 times with exponential backoff (500ms, 1500ms), **inside** the lane slot so the proxy lane stays concurrency=1 and a struggling FMG isn't piled on; permanent faults (HTTP 401/403/404/405 and FMG RPC `-11`) fail fast. Outward `AppError.httpStatus` stays 502 for all transport faults — the upstream code is encoded in the message, never re-exposed to Polaris's own clients. There is no `/sys/logout`: the predefined api-key shares one permanent session (a prior hourly logout, commit 3e70476, tore that session out from under the split-role consumers and was removed). Projected CMDB `get` calls set `loadsub: 0` to skip child-table loads, except `system/interface` (secondary-ip) and `firewall/vip` (mappedip) which need the child table.

Exposed metrics: `polaris_fmg_worker_queue_depth{integrationId}` (proxy lane queued tasks), `polaris_fmg_worker_inflight{integrationId}` (proxy lane 0/1), `polaris_fmg_worker_native_inflight{integrationId}` (native lane current concurrent count).

### Direct-mode discovery flow (warm-cache producer + FMG-verify producer)

Direct-mode (`useProxy=false`) `fortimanager.discoverDhcpSubnets` runs **two concurrent producers** feeding one `discoveryParallelism`-wide FortiGate work pool:

- **Warm-cache producer** — queries `Asset` rows for this integration where `assetType="firewall" AND monitorStatus="up" AND ipAddress IS NOT NULL` and dispatches each one immediately using its cached `ipAddress` (no FMG round-trip). The query is built in `buildFmgWarmCacheIps()` in `discoveryEngine.ts` and passed in via the new `warmCacheIps?: Map<string,string>` parameter on `discoverDhcpSubnets`. On big fleets this fills the worker pool to its `discoveryParallelism` cap from `t=0` instead of dripping in behind the serial FMG resolver.
- **FMG-verify producer** — for FortiGates NOT in the warm cache (cache-cold, monitor-down, or new in the FMG roster), serially resolves each mgmt IP through the FMG worker and dispatches as each IP lands. Same shape as the legacy resolver path; the difference is that the verify list is now a strict subset of `devicesData` instead of the whole set.

**Cache-miss fallback** lives inside `processDevice`: if the first direct REST call fails AND the IP came from the warm cache (`cachedNames` set), it submits one `resolveDeviceMgmtIp` to the FMG worker, retries at the freshly-resolved address, and updates `mgmtIpByDevice` + the firewall Asset's IP via the standard sync path. If the re-resolve returns the same IP (or no IP), the FortiGate is treated as unreachable and the device is skipped. Self-healing without a second discovery cycle.

**Case-insensitive keying for all FMG name-keyed state.** `mgmtIpByDevice`, `cachedNames`, `warmDispatched`, and `devicesByName` all key on `fmgNameKey(name)` (lowercased). The warm cache is built from `Asset.hostname` which may be FortiOS-cased (e.g. `EVANSVILLE-FW-1`) while the FMG roster supplies the same device as `evansville-fw-1` — both writes land in the same bucket so the worker's `mgmtIpByDevice.get(deviceKey)` lookup succeeds regardless of which source seeded the entry. Display names in log lines and Events still use the original casing carried on the raw FMG device record / asset row.

Proxy mode (`useProxy=true`) ignores the warm cache — every per-device monitor call funnels through `/sys/proxy/json` which is FMG-bound, so a cached mgmt IP offers no speedup. The FMG worker's proxy lane serializes those proxy calls along with any concurrent reservation push / quarantine push against the same integration. The native lane runs CMDB scrapes (DHCP server config, interface CMDB, VIPs, geo coords, etc.) concurrently both across devices and with the proxy lane, so per-device discovery is genuinely faster in proxy mode than the previous single-lane architecture even though the proxy calls themselves are still serial.

`fortimanagerService.ts` connects to FortiManager via JSON-RPC and discovers:

- **DHCP scopes** → Subnet records (`discoveredBy`, `fortigateDevice`)
- **DHCP reservations** → Reservations (`sourceType: dhcp_reservation`). Discovery walks two sources: the CMDB tree at `/pm/config/device/<name>/vdom/root/system/dhcp/server` (every configured static reservation, regardless of client state) and the live monitor at `/api/v2/monitor/system/dhcp` (currently-active leases plus reservations whose target is online). The two are **merged** — CMDB is the base set, monitor adds anything not already covered, and CMDB wins on overlap by IP. This is intentional: monitor only returns reservations whose target is currently leasing, so trusting only monitor would silently drop static reservations whose target device happens to be offline at discovery time. **The FortiGate is authoritative for CMDB DHCP reservations:** Phase 5b at the end of every per-device sync releases any active `dhcp_reservation` row whose subnet's `fortigateDevice` is in `DiscoveryResult.dhcpReservationsInventoriedDevices` (the CMDB DHCP query succeeded this cycle) but whose `(subnetId, ip)` isn't in `result.dhcpEntries`. Covers both fresh-from-CMDB rows AND Polaris-pushed manual reservations that flipped to `dhcp_reservation` on first sight — operator-deleted-on-gate is the same observable state in both cases. Push pointers (`pushedToId`/`pushedScopeId`/`pushedEntryId`) are cleared on release so a future re-reservation makes its own push. Writes a `reservation.dhcp_reservation.released` Event. `dhcp_lease`, `fortiswitch`, and `fortinap` source types are intentionally NOT swept: leases age out via `expireReservations` + the stale-reservation alert system, and fortiswitch/fortinap rows are device-presence indicators whose lifecycle is owned by Phase 2b decommission. **Phase 5 infra branch:** an existing `fortiswitch`/`fortinap` row at a discovered DHCP entry's IP previously matched no branch at all and fell through with no write and no path counter (quietly falsifying the phase summary's "path-* counters sum to entriesTotal"). It now records `Reservation.dhcpBinding` — `"lease"` vs `"reservation"` per the entry's own type — plus a fill-only `macAddress` from the lease entry and the `lastSeenLeased` presence bump, via the pure `decideInfraDhcpBinding` (`src/utils/infraDhcpBinding.ts`) which returns a patch only on change so the steady state issues no write. `sourceType` is never flipped and `expiresAt` is never stamped (see business rule 23). This is what lets the IP panel distinguish a FortiLink-leased AP — offer Reserve, label it a lease — from one backed by a real MAC→IP entry.
- **DHCP leases** → Reservations (`sourceType: dhcp_lease`); captures `expire_time`, `access_point`, `ssid`
- **Interface IPs** → Reservations (`sourceType: interface_ip`) — note: discovery no longer mirrors these into `Asset.associatedIps`. The System tab's interface scrape (run on the monitoring cadence once monitoring is enabled on the firewall asset) is the single source for `Asset.associatedIps` per-interface entries. **Secondary IPs are included** alongside primaries: the FortiOS `system.interface` `secondary-ip` child table is iterated in both transport paths (FMG adds `"secondary-ip"` to the CMDB `fields` list; standalone reads the full interface object) and each row is pushed as a `DiscoveredInterfaceIp` with `role: "secondary"`. Phase 4's notes builder labels them as **Secondary IP** on the resulting reservation so operators can tell at a glance.
- **Virtual IPs (VIPs)** → Reservations (`sourceType: vip`). The FortiGate is authoritative for its own VIPs: **Phase 5b** at the end of every per-device sync releases any active `vip` reservation whose `vipInfo.device` is in `DiscoveryResult.vipInventoriedDevices` (the gate's VIP query succeeded this cycle) but whose IP isn't in the gate's current VIP list. **VIP succession**: when a DHCP lease/reservation lands at an IP whose VIP has just disappeared, Phase 5 converts the existing row in-place — `sourceType` flips to `dhcp_*`, `vipInfo` clears, MAC fills in if empty, but operator-edited `hostname` / `owner` / `notes` survive (only the canonical `"fortimanager-vip"` / `"fortimanager-vs"` owner and the `"Firewall VIP ..."` / `"Virtual server ..."` notes are replaced). Pending VIP-merge conflicts on the row are auto-rejected. **VIP + DHCP collision** (both live at the same IP): VIP metadata takes precedence over the DHCP side's owner / projectRef, so the merge conflict is raised **fill-only** — `computeConflictFields(proposed, existing, "fill-only")` (exported from `discoveryEngine.ts`, unit-tested) reports only fields the existing row left BLANK, so a populated VIP owner/projectRef never produces a card. Accepting a merge conflict has only ever filled blanks (`conflictResolutionService`'s merge mode), so those cards changed nothing on accept; pre-existing ones close themselves on the next cycle via the empty-`conflictFields` auto-resolve. In the other arrival order (VIP discovered onto an existing `dhcp_*` row) the canonical DHCP-discovery placeholders — owner `"dhcp-lease"` / `"dhcp-reservation"`, projectRef `"<Integration> Integration"` — are additionally overwritten in place with the VIP values (mirror of VIP succession); anything else (operator-typed, or an asset's `assignedTo`) survives untouched. Writes `reservation.vip.replaced` (Phase 5 in-place) or `reservation.vip.released` (Phase 5b sweep) Events. `vipInfo` is stamped at create (not just by the next cycle's refresh branch) so the badge renders and the Phase 5b sweep is armed from the row's first cycle. **Load-balance Virtual Servers** ride the same `firewall/vip` query (`type` + the `realservers` child table added to the FMG field list; standalone REST returns them natively). `parseVipServerInfo()` — exported from `fortimanagerService.ts` and imported by the standalone path so the two transports can't drift — classifies a row as a VS structurally (non-empty realserver pool) with the `type === "server-load-balance"` string as fallback for empty-pool VSes — verified live (FMG 7.x, 2026-06): the FMG `/pm/config` get returns `type` as a numeric enum (0 = static-nat, 3 = server-load-balance) and `realservers: null` on non-VS rows, so the string fallback only ever fires on the FortiOS-REST transport and an *empty-pool* VS discovered via FMG proxy classifies as a plain VIP (harmless — no pool members to reserve). The same verification showed FMG's fields-projected get **flattens `extip`/`extintf` to single-element string arrays and `mappedip` to flat range strings** (vs. FortiOS REST's plain strings + `{ range }` objects); the FMG parse handles both encodings — the `{ range }`-only parse it replaced silently dropped every mapped IP in proxy mode. VS rows get owner `fortimanager-vs`, projectRef `VS: <device>`, and notes prefixed `Virtual server "..."`; the VS's external IP reserves with `role: "external"` and **each realserver pool member IP gets its own reservation with `role: "realserver"`** (deduped across ports), all participating in the same Phase 5/5b lifecycle via `currentVipKeys`. `vipInfo.isVirtualServer` flows to the IP panel, which renders a **VS** badge (vs. **VIP**) with a virtual-server tooltip.
- **FortiSwitch devices** → Asset records (`assetType: switch`); via FMG proxy to `/api/v2/monitor/switch-controller/managed-switch/status`. `fortinetTopology` stamped with `{ role: "fortiswitch", controllerFortigate, uplinkInterface, uplinkPhysicalPort }` so the Device Map renders the FortiLink uplink as an edge. `uplinkInterface` is the FortiGate-side *logical* interface (`fgt_peer_intf_name`, almost always `"fortilink"`); `uplinkPhysicalPort` is the switch's own *physical* uplink port (e.g. `"port47"`), resolved from one extra managed-switch **CMDB** read per controller per discovery run (`/api/v2/cmdb/switch-controller/managed-switch` → `findFortiswitchUplinkPorts`, both the FMG-proxy and standalone-FortiGate collectors for parity). It's set only when the switch has exactly one directly-cabled uplink (chain-head switches); chained / dual-homed switches leave it null and the FG↔switch edge's switch-side label falls back to LLDP. The Device Map labels the FG↔switch edge's **switch side** from `uplinkPhysicalPort` and leaves the **FortiGate side** to the LLDP backfill (which only overwrites still-`unknown` halves, so the two compose). Switch↔switch FortiLink ISL edges are labeled from physical ports independently — see `buildFortiswitchTrunkMembers` (the trunk→member `ifParent` overlay feeding `preferPhysical`).
- **FortiAP devices** → Asset records (`assetType: access_point`); via FMG proxy to `/api/v2/monitor/wifi/managed_ap`. `fortinetTopology` stamped with `{ role: "fortiap", controllerFortigate, parentSwitch, parentPort, parentVlan, uplinkInterface, peerSource, meshUplink, parentApSerial, state, profile }` — `state` is the controller admission state ("authorized" / "discovered" / …, distinct from connectivity `status`) and `profile` the bound `wtp_profile`; both render as their own row on the asset details General tab (desktop + mobile). The row's parse is centralized in `src/utils/fortiapMonitorRow.ts` (`parseFortiapMonitorRow`) so the FMG proxy path and the standalone FortiGate REST path can't drift on field handling. IP picker order (first non-empty wins, `0.0.0.0` normalized to empty): `ip_addr → ip_address → local_ipv4_address → local_ipv4_addr → wtp_ip → connecting_ip`. MAC picker: `base_mac → board_mac → mac`. Model derives from `model → wtp_profile → deriveFortiapModelFromSerial(serial)` — operators have reported APs whose live model field comes back blank from /managed_ap even on healthy units, so the serial-prefix fallback (`FP234F` → `FortiAP-234F`) closes the gap. `uplinkInterface` is the AP-local port (lan1/lan2/wbh0…) extracted from `wan_status[].interface` first, falling back to the matching LLDP entry's `local_port`. ### FMG proxy field filtering

FortiOS monitor endpoints support field selection via the `format` query parameter (pipe-separated):

```
/api/v2/monitor/switch-controller/managed-switch/status?format=connecting_from|fgt_peer_intf_name|join_time|os_version|serial|switch-id|state|status
```

**Do not use `?fields=`** — that is the CMDB filter syntax and does not work on monitor endpoints.

### FortiSwitch fields (managed-switch/status)

| API field | Meaning | Maps to |
|-----------|---------|---------|
| `switch-id` | Switch hostname | `hostname` |
| `serial` | Serial number | `serialNumber` |
| `connecting_from` | Management IP of the switch | `ipAddress` |
| `fgt_peer_intf_name` | FortiGate interface/FortiLink the switch is on | `learnedLocation` |
| `os_version` | Firmware version | `osVersion` |
| `join_time` | Unix timestamp when switch was first authorized | `acquiredAt` (only update if older) |
| `state` | `Authorized` / `Unauthorized` | `status: storage` if Unauthorized |
| `status` | `Connected` / `Disconnected` | informational |

When a discovered value conflicts with an existing manual reservation, a `Conflict` record is created instead of silently overwriting. Admins accept (apply discovered values) or reject (keep existing) via the conflict slide-over panel on the Events page.

### Excluded address space (Phases 1 and 2)

`syncDhcpSubnets` loads the `SubnetExclusion` set ONCE per run (it rides the same top-of-function `Promise.all` as the block / subnet / reservation / asset reads) and matches every discovered scope against it with the pure `findCoveringExclusion` — business rule 42. A covered entry is skipped WHOLE, and the position of that skip is the point: it sits ABOVE the existing-row branch, not just the create. The conflict this exists to stop is raised by the UPDATE side — a management VLAN several sites serve identically is one row in Polaris, so each site's gate re-stamps it and answers with its OWN serial, which `classifyChassis` correctly reads as `replaced` and rule 41 correctly raises a `chassis-replaced` card about, every run, forever. Skipping only the create would have left that untouched. The run reports it as `<cidr> (excluded as "<name>")` in `skipped`, so a shared subnet is visibly accounted for rather than silently absent.

Phase 2 exempts them too: with Phase 1 no longer re-stamping the row, its `fortigateDevice` is frozen at whichever site claimed it first, so the moment that ONE gate leaves the roster the stale sweep would deprecate a subnet the operator told discovery to leave alone — and a deprecated row is the state business rule 41 exists to keep subnets out of (unrecordable CIDR, every lease and VIP inside it dropped by `findSubnetForIp`). The create seam (`createSubnetRowChecked`) still gets the run's loaded set passed to it as a backstop, so the check costs no extra read per created subnet.

### Stale-subnet deprecation (Phase 2)

After all per-device polling finishes, `syncDhcpSubnets` deprecates subnets whose `fortigateDevice` is no longer in `DiscoveryResult.knownDeviceNames` — the full roster of FortiGates configured in FortiManager, captured up front from `/dvmdb/adom/<adom>/device` with **no `conn_status` filter**. An offline FortiGate stays in `knownDeviceNames` and its subnets are left alone; only devices that have been *removed* from FMG are treated as stale. Devices filtered out by `deviceInclude`/`deviceExclude` also remain in the roster for the same reason — changing a filter shouldn't nuke previously-discovered subnets. The roster check is **case-insensitive** (lowercase on both sides via `knownDeviceNamesLc`) because the FMG-stored device name and the FortiOS system-status hostname can disagree in case — same device, different casing on each side. Phase 2 is skipped entirely if the run was aborted.

### Stale-firewall decommission (Phase 2a)

Right after Phase 2, `syncDhcpSubnets` flips firewall Asset rows discovered by this integration whose identity is no longer in the FMG roster to `status="decommissioned"` and writes one `asset.fortigate.decommissioned` Event each. Same roster semantics as Phase 2 — pre-filter, any conn_status — so an offline-but-still-configured FortiGate is left alone, and changing a deviceInclude/exclude filter doesn't churn firewall asset state.

**Match order:** (1) **serial (case-insensitive)** — chassis identity in `knownFirewallSerials`, never renamed; every cluster member's serial including `ha_slave[]` entries is in the set, so a standby whose hostname never appears at top-level still matches. (2) **hostname (case-insensitive)** — fallback for legacy/partial rows where `Asset.serialNumber` is null; uses `knownDeviceNamesLc.has(a.hostname.toLowerCase())` so FMG-vs-FortiOS casing drift doesn't spuriously decommission anything. (3) **HA standby of a cluster nobody read this run** — the exported pure guard `haStandbyOfUnreadCluster(fortinetTopology, knownFirewallSerials, haRosterPublished)`.

**Where the HA identities come from is load-bearing.** `knownFirewallSerials` is seeded from `DiscoveryResult.knownDeviceSerials` — the serial sibling of `knownDeviceNames`, captured from the RAW roster (`extractRosterIdentities`, pre-filter, any conn_status, `ha_slave[]` names and serials included) — and only then topped up from the devices that processed this run. It used to be built from the processed devices alone, which tied a standby's survival to its cluster answering: a gate that failed its direct read, was skipped for an unresolved management IP, or was dropped by the include/exclude filter contributes no processed device at all, so its primary lived on the raw-roster name while its standby — an identity only `ha_slave[]` carries — matched nothing and was decommissioned, every cycle, with the Standby pill still on the row.

Rule (3) covers what the roster cannot: a cluster whose membership was never enumerated at all (an FMG API user without the field, a FortiOS build whose `ha-peer` endpoint 404s on the standalone integration). `haRosterPublished` holds the serials of clusters that DID publish their members this run, so a member missing from a roster that was read is judged normally — it genuinely left the cluster — while a member of a cluster nobody enumerated is protected. Absence of evidence is not evidence of absence, the same posture the switch/AP sweeps take.

A decommissioned firewall is reactivated by the existing Phase-3b firewall update path on a future cycle when the device returns to the FMG roster. Skipped on aborted runs along with Phase 2. Both this flip and the controller cascade below also write `status="decommissioned"` back onto the in-memory `AssetIndex` rows: that index is snapshotted before the sweep, and in `"full"` mode (the standalone FortiGate integration — one pass, Phase 2a ahead of the Phase 3 fan-out) it is what Phase 3 reads, so a row left looking `active` there would skip the resurrection clause and strand the DB row decommissioned with nothing able to flip it back.

**Controller cascade — a decommissioned FortiGate takes its managed FortiSwitches/FortiAPs with it.** In the same Phase 2a pass, every non-decommissioned switch/AP asset of the integration whose `fortinetTopology.controllerFortigate` matches a just-decommissioned gate's hostname (case-insensitive — the exported pure matcher `cascadeControllerOf`, unit-tested alongside `sweepPhaseEnabled`) is decommissioned too, with its own `asset.fortiswitch.decommissioned` / `asset.fortiap.decommissioned` Event (`reason: "controller-decommissioned"`) and the same `releaseAssetsForDecommission` maintenance-window force-exit. Phase 2b cannot cover this case: it only judges children whose controller was successfully **inventoried** this run, and a roster-removed gate is never queried again — pre-cascade, its switches/APs sat `active` forever as unpollable ghosts. Children rehomed to a surviving gate earlier in the same run already carry the new controller name and never match. Never runs in `finalize-scoped` (it lives inside the Phase 2a gate). Resurrection is symmetric: the gate returns via Phase 3b, and its children return through their own Phase 3b/6 update paths once the controller reports them connected.

**Maintenance windows do not shield a deleted device.** Both this sweep and Phase 2b judge assets in `status="maintenance"` (only `decommissioned` is excluded from the candidate query) and hand the stale ids to `releaseAssetsForDecommission` (maintenanceScheduleService) before the status flip: open `AssetMaintenanceWindow` rows close with `endReason="decommissioned"`, `maintenanceReturnStatus` clears, and `status="decommissioned"` lands in the SAME transaction — so the 30s maintenance reconcile never sees a half-state it would re-enter or self-heal-reflip, and the `monitored=false` clamp keeps the asset out of the schedule's target set afterwards. Roster/inventory absence is CONFIG truth, not a reachability signal (an offline device stays in the roster; a powered-off switch/AP stays `cmdbProtected`), so it outranks the window — before this, a device deleted from FortiManager mid-window sat in maintenance for the rest of the window and was then restored to `"active"`. `decommissionStaleAssets` (the `lastSeen`-aging job) keeps its maintenance guard, since maintenance freezes `lastSeen` by design.

### Auto-Monitor Interfaces apply pass (Phase 2c)

After Phase 2 + 2b finish, `syncDhcpSubnets` runs `applyAutoMonitorForClass` from `autoMonitorInterfacesService.ts` for each per-class block (`fortigate` / `fortiswitch` / `fortiap`) whose `Integration.config.<klass>Monitor.autoMonitorInterfaces` is non-null. Resolves the selection (names / wildcard / type) against each discovered asset's latest `AssetInterfaceSample` rows (plus synthetic IPsec-tunnel rows for the fortigate class) and unions the result into `Asset.monitoredInterfaces` for real interfaces and `Asset.monitoredIpsecTunnels` for IPsec-tunnel pins (routed by `splitPinsByProvenance`) — strictly additive on both fields, never strips operator pins. Idempotent: skips the per-asset write when nothing would change. Runs on `mode in {"full", "finalize"}`, so both standalone-FortiGate runs and FMG finalize hit it; per-device FMG syncs (`mode: "skip-deprecation"`) do not. Writes one `integration.auto_monitor_interfaces.applied` Event per class when something actually changed; silent otherwise. First-run edge case: when `onlyUp` is set but no system-info pass has run yet, the resolver finds no candidates and the apply pass quietly no-ops; the next discovery cycle catches up. The same logic is exposed via `POST /integrations/:id/interface-aggregate/apply` and is invoked by the integration edit modal's **Save Changes** button so saving applies the selection to existing assets — that route now runs the apply in the background (202) instead of blocking the request, since the fleet-wide resolve can take minutes; this Phase 2c pass is the discovery-time backstop that makes the fire-and-forget safe.

### AD/Entra post-sync passes (agent auto-deploy + interface/storage auto-monitor + presence verification + address-book directory sync)

`syncDhcpSubnets` Phase 2c is FMG/FortiGate-only — the assets-only AD/Entra integrations call `syncActiveDirectoryDevices` / `syncEntraDevices` directly in `runDiscovery`, so three sibling passes run there (only when the sync completed, not aborted), each wrapped so a failure logs and continues:

1. **Agent auto-deploy** (`runWorkstationServerAgentAutoDeploy` → `agentAutoDeployService.runAutoDeployForClass`). Runs FIRST so newly-discovered, agent-less devices get the Polaris Agent kicked off this cycle. Reads each class block's `agentDeploy` config (opt-in, default off). Run-level preconditions (HTTPS cert pin + callback URL) are checked once up front; if they fail the whole pass skips with one warning Event rather than minting rows that all fail enrollment. Eligible = this integration's assets of the class with NO `ManagedAgent` row (the `assetId @unique` idempotency guard — a failed install is the operator's to retry, never auto-retried) and a reachable host (`ipAddress || dnsName || hostname`; AD objects often lack IP, so skip-not-fail when none resolve). Platform is inferred from `Asset.os` (`inferAgentPlatform`); transport/credential picked per class (`pickTransportAndCredential`: windows→WinRM-or-SSH, linux/macOS→SSH); arch defaults `amd64` (enrollment re-validates and fails the row on mismatch). Bounded: ≤`maxConcurrent` new installs per class per cycle minus in-flight, with a `RUN_CEILING=200` backstop; the rest are picked up on subsequent cycles (paced rollout). Emits `agent.autodeploy.{kickoff,skipped,batch}` Events.
2. **Interface + storage auto-monitor** (`applyWorkstationServerAutoMonitor`). Reuses `applyAutoMonitorForClass` (interfaces) + `applyAutoMonitorStorageForClass` (storage) for the `workstation` / `server` classes, resolving each class block's `autoMonitorInterfaces` / `autoMonitorStorage` selection against the assets' latest samples and unioning into `Asset.monitoredInterfaces` / `monitoredStorage`. Strictly additive, runs every discovery. Because these devices only produce interface/storage samples once an agent is deployed and reporting, a freshly-auto-deployed device gets its pins on the NEXT discovery cycle once samples exist — self-healing by design. Read-only aggregate/preview power the modal cards via `GET/POST /integrations/:id/{interface,storage}-aggregate[...]` (the interface class param was widened to accept `workstation` / `server`; storage routes are AD/Entra-only with a `workstation|server` class enum).
3. **Network-presence verification** (`presenceVerificationService.runPresenceVerification`; gated by `config.verifyPresence`, default ON). Directory timestamps don't write `Asset.lastSeen` (see the Asset field note), so this pass establishes presence for the integration's directory-sourced assets (status active/quarantined — maintenance is skipped: a maintenance window pauses all server-driven contact and `lastSeen` deliberately freezes), cheapest signal first per asset: already-fresh `lastSeen` (within the integration's `pollInterval` window — typically a FortiGate integration sighted the device on the wire) → agent heartbeat → answering monitor probe → single ICMP echo against `dnsName||hostname` (the stored `ipAddress` is often stale on directory-discovered assets). A failed ping writes nothing — Windows firewalls commonly drop ICMP and Entra-joined laptops are legitimately off-LAN. Bounded (16-way ping concurrency, 2s timeout, 3-min pass deadline with reported skip counts); writes batched via `$transaction`; one `integration.presence_verification` summary Event per pass.
4. **Address-book directory (GAL) sync** (`directorySyncService.runDirectorySync`; gated by `config.enableDirectorySync`, default OFF, and by integration TYPE — only `entraid` / `activedirectory` have a directory of people, so vCenter and Arc skip it even though they share the `assetsOnly` gate). Runs **LAST**, deliberately: a directory outage, an expired secret or a revoked Graph grant must not be able to affect the three asset passes above, and it is wrapped in the same `.catch` → `integration.directory_sync.error` shape they use. It is NOT its own scheduler job — the run it belongs to already holds the credentials, already has an interval the operator chose, and already reports progress; a second timer would be a second thing to reason about for no gain. Reads in bulk through each service's own `listDirectoryPeople` (Graph: paged `$select`+`$filter`+`$top=999`, deliberately NO `$search`, so it doesn't inherit the live search's unverified `$search`+`$filter`+`$count` shape; LDAP: the paged-results control with `pageSize: 1000`, identity from `objectGUID` rather than the DN a rename would change). Then diffs against `DirectoryContactSource` provenance and writes in chunks of 200 — creates via `createMany({skipDuplicates})` + re-read, provenance updates and projection updates through chunked `$transaction`. **A steady-state run issues ZERO writes** (the stored `observed` blob is compared, the `NotificationRuleState` writes-only-on-transition idiom), which is what makes a 20,000-person directory affordable on every cycle. A Polaris `User` or a manual `Contact` on an address always wins; deletion is refused wholesale when `scanned === 0` or the delete set exceeds `max(50, 20%)` of what the integration owns; a contact dies only when its LAST provenance row goes. The summary Event carries **counts only** — no address, name, title, department, phone, DN or object id, because `Event.details` is readable by anyone with events access and is shipped off-host by the syslog and SFTP archivers. Stamps `observeDiscoveryPhase(type, "gal-sync", secs)` — a new label value on an existing metric, so no Grafana panel obligation. See business rule 35.

### Auto-Monitor aggregate-cache refresh (end of every successful run)

The final step of a successful `runDiscovery` (any integration type, success branch only — skipped on abort/error) recomputes the "By name" checklist sources and stashes them on the Integration row: `autoMonitor.computeAndCacheInterfaceAggregate(id, type)` → `Integration.interfaceAggregateCache` and `autoMonitorStorage.computeAndCacheStorageAggregate(id, type)` → `Integration.storageAggregateCache`. Each runs the same fleet-wide DISTINCT ON the `GET .../{interface,storage}-aggregate` routes used to run on every modal open, but now once per discovery cycle in the discovery process, and persists only the UI-rendered fields (interface: `ifName`/`ifType`/`deviceCount`; storage: `mountPath`/`deviceCount`) plus a `computedAt` stamp — so the edit modal loads the checklist instantly from cache. Both calls are best-effort (`.catch` → one `integration.aggregate_cache.error` warning Event), so a cache failure never fails an otherwise-good run. Class set is derived from integration type: Fortinet types cache `fortigate`/`fortiswitch`/`fortiap` interfaces (no storage); AD/Entra/Windows-Server types cache `workstation`/`server` interfaces + storage. The GET routes serve the cache and fall back to a live compute only when no entry exists yet for the requested class. This replaced the operator-facing "Refresh from latest discovery" button on both Auto-Monitor cards.

### Dependency tree recompute (Phase 12)

After every infra-asset write phase has settled (Phase 3 / 3b firewall + switch + AP creates and updates) AND the projection apply (Phase 11) has reconciled multi-source fields, `syncDhcpSubnets` calls `recomputeDependencyTree(integrationId)` from `dependencyTreeService.ts`. The recompute walks `Asset.fortinetTopology.controllerFortigate` (FortiGate→switch) + `parentSwitch` (switch→AP) + `inferInterfaceTopology` (switch→switch chains, MCLAG aggregates) + `AssetLldpNeighbor.matchedAssetId` (cross-vendor / edge cases) into a parent→child DAG, prunes via **physical-first** BFS layer assignment from each FortiGate (layer 1) outward — interface + LLDP edges form the primary adjacency, controller edges are a fallback for assets the physical pass didn't reach, with simple-path detection so a 3+ switch daisy chain that's only LLDP-visible between siblings (not back to the FortiGate) still chains correctly instead of collapsing every switch into a same-layer sibling of the FortiGate. MCLAG pairs and any branching / cycled controller-only component still attach as siblings. A mesh-leaf AP (station-match in `AssetWirelessStation`, OR `fortinetTopology.meshUplink === "mesh"` — the stamped FortiOS classification covers leaves whose root AP has no station scrape) and a FortiLink switch bridged behind a FortiAP (AP↔switch LLDP where the switch is not the AP's controller parent, or where the AP is a mesh leaf — a mesh leaf's wired LLDP adjacency is always bridged-behind) have their backwards controller edge suppressed and depend on the AP instead. Kept edges prefer the most-physical `detectedVia` (mesh > interface > lldp > controller) for the audit-trail row, and replaces this integration's `source="computed"` rows in `AssetDependencyParent` plus updates `Asset.dependencyLayer` for in-scope assets — all in one transaction. `source="override"` rows (operator pins via the admin override endpoints) are never touched. Multi-parent rows model MCLAG / dual-homed switches; "all-down" semantics in the reconciler then mean a redundant uplink keeps an asset polling normally. Runs on `mode in {"full", "finalize"}` only — per-device skip-deprecation passes skip the recompute since they see only a partial slice of the fleet. The same call then refreshes the **endpoint half** (`syncEndpointDependencyEdges`): fleet-wide rather than integration-scoped, since an endpoint's upstream device is resolved from its own `lastSeenSwitch` / `lastSeenAp` / `AssetFortigateSighting` columns against the global infra inventory and most endpoints belong to an AD/Entra/vCenter integration that never reaches this phase. Best-effort: failures `syncLog("error", ...)` and don't block the sync return. Pairs with the `dependencyReconciler` 60s job which evaluates the suppression flag from this DAG.
### Per-asset change events (Phase 11.5)

`syncDhcpSubnets` keeps a run-scoped `changeBaseline` map recording each tracked field's value at its FIRST touch this run — `os` / `osVersion` / `lastSeenSwitch` / `lastSeenAp`, noted via `noteChangeBaseline()` at Phase 3b (FortiAP wired uplink), Phase 7 (device inventory), Phase 7.5 (MAC-table port enrichment) and Phase 11 (corrective re-projection). After Phase 11 settles, one pass diffs each baseline against the final in-memory value and writes a single `logEventsBatch` of `asset.firmware.changed` / `asset.switch_port.changed` / `asset.wireless_ap.changed` rows. A steady fleet produces an empty batch.

**Why a baseline rather than an event at each write:** two sequences legitimately ping-pong WITHIN one run, and inline emission would report both halves as changes every run forever. Phase 7 stages FortiOS's coarse cached client fingerprint (`"10.0"`) and Phase 11 puts the projected MDM value (`"10.0.19045"`) back; and Phase 7 stages `${inv.switchName}/port${n}` while Phase 7.5 stages `${row.switchId}/${row.portName}` for the SAME port. Diffing against the cycle boundary nets both to zero. Consequences to preserve: **any new write of those four fields inside `syncDhcpSubnets` must call `noteChangeBaseline()` first** or the change goes unaudited; every such write must also mirror the value onto the in-memory asset row (Phase 3b's FortiAP branch needed that added); and **Fortinet-infra os/osVersion is deliberately never baselined** — it reaches Asset through projection, where `logDiscoveryAssetUpdated` emits the firmware event itself, so recording it here too would double-emit. Firmware for the endpoint half is the same action string, so one automation covers both. Events are optimistic with respect to Phase 7.5's `batchSettled` flush (the Arc path's existing caveat), and the whole flush is wrapped so an audit failure never fails a discovery run.

### Management-access read (Phase 13.6)

After the firewall-tag reconcile, `syncDhcpSubnets` reads each Fortinet device's management-access (`allowaccess`) config and stamps `Asset.managementAccess`. It groups the discovered firewalls / FortiSwitches / FortiAPs by controller FortiGate, then calls `collectManagementAccess` (`fortinetManagementAccessService.ts`) — one transport per FortiGate via `buildTransportForIntegration` + `callFortiOs`, so FMG-proxy / FMG-direct / standalone all work. Reads: firewall `/api/v2/cmdb/system/interface` (the operator-named `config.mgmtInterface` interface's allowaccess), FortiAP `/api/v2/cmdb/wireless-controller/{wtp-profile,wtp}` (serial→profile→allowaccess), FortiSwitch `/api/v2/cmdb/switch-controller/managed-switch` + `/api/v2/cmdb/switch-controller.security-policy/local-access` (the controller's local-access POLICY is the real source for a managed switch — one read per controller, half chosen by `config.switchManagementInterface`, default `internal`; a per-switch interface allowaccess still wins where firmware exposes one, `protocols: null` when neither can be read). The returned `Map<serial, summary>` is joined to assets via the `AssetSource` rows discovery just wrote (`externalId === serial`) and written in chunked `$transaction` batches (no per-row awaits — bounded at the 2000-asset end). Always-on (no opt-in toggle); FMG/FortiGate only; gated to `mode in {"full", "finalize"}`. Read-only — never writes the device. Best-effort: per-device failures are swallowed and the overall pass `syncLog("error", ...)` on failure without blocking the sync return. Drives the asset slide-over's **Open HTTPS** / **Open SSH** buttons (the SSH button emits an `ssh://[user@]host` URI the OS hands to its registered handler, with a per-user localStorage fallback to copy the `ssh` command) and the FortiAP **"SNMP not enabled in profile"** warning banner. ⚠️ The FortiAP REST field shapes still need verification on a live FortiOS 7.x device — parsers degrade to `protocols: null` (unknown) rather than guessing, and the UI then shows buttons optimistically with an "unverified" note. The switch half is settled: the local-access policy is fleet-wide (no per-switch attachment exists), so `default` is the policy in force.

### Description-sync reconcile (Phase 13.7)

After the management-access read, `syncDhcpSubnets` runs the description-sync reconcile — gated on the integration's `syncDescriptions` toggle (default off = the phase costs nothing). `runDescriptionSyncForIntegration` (`descriptionSyncService.ts`) groups the integration's non-decommissioned Fortinet assets under their controller FortiGate (`fortinetTopology.deviceName` for firewalls — the FMG dvmdb name stamped at discovery — `controllerFortigate` for switches/APs; HA-secondary members skipped), builds one transport per FortiGate via `buildTransportForIntegration`, and reads the current device-side descriptions in a handful of CMDB GETs per gate (`system/interface`, `system/global`, `switch-controller/managed-switch`, `wireless-controller/wtp`). It then applies the **Polaris-primary rule** over every `AssetInterfaceOverride` + device-level `Asset.description`: **push** wherever a non-empty Polaris value differs from the device — including over device-side edits, which are overwritten (also the retry path for save-time pushes that failed transiently) — and **adopt** device values into empty Polaris description fields (`asset.description.adopted` Events). A device-side clear never removes a Polaris value. Per-surface read failures skip that surface's decisions without touching state; DB writes happen only on change (chunked `Promise.all`). ⚠️ FortiOS field shapes (system/global `alias` + cap, ports child-table PUT patch semantics) need verification on a live FortiOS 7.x device — the wtp `location` cap is confirmed at 35 chars — the wtp surface self-gates on the `location` attribute actually appearing in the read (`location`, not `comment`, is the FortiAP surface: it's AP Manager's field, and `comment` is absent from FMG's copy so installs strip it — confirmed on live FMG 7.x). Confirmed on FortiOS 7.6.7: the managed-switch mkey (`switch-id`) is often renamed away from the serial (e.g. to the hostname) and a serial-keyed PUT 404s — the reconcile keys its switch-row map by both `switch-id` and `sn`, and the save-time pushes resolve the row via `matchManagedSwitchRow` before PUTting; the 63-char switch/port description cap is also confirmed.

**FMG central-management mirror.** FortiManager ADOMs manage FortiAPs (AP Manager) and FortiSwitches (FortiSwitch Manager) in central or per-device mode; in central mode FMG's ADOM-level copy is what installs push, so a device-direct description write gets **reverted by the next central-pane install**. Each FMG discovery start runs `fortimanagerService.detectCentralManagement` — primary signal: the ADOM's dvmdb `flags`, where an ABSENT `per_device_wtp` / `per_device_fsw` flag means central (bit values decoded per-box from the `/dvmdb/adom` syntax dump via `decodeCentralManagementFlags`, confirmed on a live FMG 7.x); the ADOM-level `obj/wireless-controller/wtp` / `obj/fsp/managed-switch` table probes supply the UI row counts and the fallback verdict — and stamps the result on `Integration.config.centralManagement` (system-owned key — the PUT handler's config merge preserves it across operator edits; rendered on the integration card after the FMG Proxy row, changes logged as `integration.central_management` Events). For a centrally-managed class, both the save-time path and the reconcile mirror successful device pushes into FMG's copy via plain JSON-RPC `update` + read-back verify (`mirrorToFmg` — never `set`, which would create objects FMG never had, and **never an install**). Mirror targets, confirmed on live FMG 7.x for wtp: FortiAP `location` in the controller FortiGate's DEVICE DB (`/pm/config/device/<fgt>/vdom/root/wireless-controller/wtp/<wtp-id>` — the per-AP rows AP Manager displays; the ADOM obj table is empty there); FortiSwitch description / port description in the ADOM-level `obj/fsp/managed-switch` table (unverified — inert on per-device-managed installs). The reconcile's `mirrorCentralDbDrift` batch pass (one FMG-table GET per class, per controller FortiGate for wtp) heals FMG-side drift for values the device already agrees on. Mirror failures log `asset.description.fmg_mirror_failed` warning Events and never affect device-side sync state; the summary line reports `FMG mirror N ok / M failed`.

### Scoped single-FortiGate re-discovery

`POST /assets/:id/rediscover` (see the assets endpoint catalog) backs the asset slide-in’s **Discover Now** button and re-runs discovery for ONE FMG-managed FortiGate on the full run machinery. Which integration runs, and what the run is narrowed to, is decided by `resolveDiscoveryScopeForAsset` (`src/services/discovery/assetDiscoveryScope.ts`) — a `fortiswitch`/`fortiap` asset resolves to its CONTROLLER gate through `src/utils/fortinetParentKey.ts` and scopes the run to that gate, so the per-controller decommission below doubles as its refresh path. The mechanism: `triggerDiscovery(integrationId, actor, { scopeDeviceName })` threads the device name through the pg-boss `DiscoveryJobPayload` (or the in-process fallback) into `runDiscovery` → `discoverDhcpSubnets`. Inside the FMG service the roster is narrowed to the one device (case-insensitive `fmgNameKey` match on name/hostname) **after** the deviceInclude/deviceExclude filter and **after** the raw roster is captured into `knownDeviceNames` — the same seam that protects filtered-out gates from the sweeps — so the returned `knownDeviceNames` still carries the whole fleet. No roster match throws (message distinguishes "not in ADOM roster" from "excluded by device filter") and the run lands `status="error"` with the failure on the DiscoveryRun row.

The per-device pass runs unchanged (`skip-deprecation`: Phases 1, 3–7 + the per-device-gated 5b), but the finalize call switches to **`"finalize-scoped"`** — a `SyncMode` that runs **Phase 2b only** (per-controller FortiSwitch/FortiAP decommission, inherently safe scoped because it only judges assets whose `controllerFortigate` had a successful inventory query this run — so a scoped run doubles as a per-gate ghost-switch/AP cleanup). Phases 2/2a are excluded because `knownFirewallSerials` is built from `result.devices` (the *processed* chunks — one device in a scoped run), not the raw roster: a scoped finalize would see a one-device fleet and deprecate/decommission everything else. Phases 8–9/12/13.x keep their `full|finalize` gates and Phases 10/11 no-op on the empty endpoint touch set. The mode→phase matrix is the exported pure helper `sweepPhaseEnabled(mode, phase)` in `discoveryEngine.ts` (unit-tested in `tests/unit/syncSweepPhaseGate.test.ts`). When the scoped gate's switch AND AP inventory queries both came back empty (offline gate), the finalize-scoped call is skipped entirely. Scoped runs also skip the `Integration.lastDiscoveryAt` stamp (the scheduler's next full run is not delayed) and the integration-level slow-run duration sample (a seconds-long scoped run would poison the full-run baseline; the per-device sample still records). The DiscoveryRun row carries `scopeDeviceName`, surfaced by `/discoveries` so the integration card shows "Discovering \<device\>…".

Discovery can be triggered manually or runs automatically on each integration's `pollInterval` via `discoveryScheduler.ts`.

## FortiGate Discovery Workflow (Standalone)

`fortigateService.ts` talks directly to a single standalone FortiGate (one not managed by FortiManager) via the FortiOS REST API. It consumes the same `DiscoveryResult` shape as `fortimanagerService` — the sync pipeline in `discoveryEngine.ts` handles both identically.

Scope is the same as FMG (DHCP scopes + reservations + leases, interface IPs, VIPs, managed FortiSwitches, managed FortiAPs, device inventory). Key differences from the FMG path:

- **Endpoint style** — requests go straight to `/api/v2/cmdb/...` and `/api/v2/monitor/...` on the FortiGate, no JSON-RPC wrapper
- **Scoping** — `vdom` query param (default `root`) instead of FMG `adom`
- **Device identity** — the FortiGate itself is the single entry in `result.devices`; its hostname is resolved from `/api/v2/monitor/system/status`
- **Auth** — Bearer API token from System > Administrators > REST API Admin (optional `access_user` header for parity with FMG; FortiOS ignores it)
- **HA discovery** — per-FortiGate query fan-out is now **seven** parallel chains, not six. Chain G calls `GET /api/v2/monitor/system/ha-peer` to enumerate cluster members; the response's `serial_no` is the calling unit (current primary, since the cluster IP routes only to active), and each peer in `results[]` is added to `haMembers[]` with `isPrimary: false`. 404 / empty results are normalized to `haMode: "standalone"` so the downstream sync has a single branch. Phase 3 of `syncDhcpSubnets` consumes `haMembers[]` identically to the FMG path — one Asset per physical serial, role/IP swaps on failover with no conflict rows. The standby member's `model` / `osVersion` are inherited from the cluster's REST response (HA members run identical builds); the FMG path additionally pulls these from `ha_slave[].name` for member hostnames.
