# Domain model — automations, alerts, delivery, contacts, maintenance, scripts

Each entity below carries its CLAUDE.md definition + load-bearing invariant, followed (in the **Schema** and **Notes** parts) by the field-level schema dump and the extended notes that lived in the skill references (formerly ARCHITECTURE.md). `prisma/schema.prisma` is the source of truth for types; these are the semantics.

## Definitions and invariants

> **The builder offers only MONITORED devices' values — and since 2026-08 so does matching.** Every inventory-derived list behind a device filter — `listScopeOptions`' manufacturers + models + `interfaceNames` (the values behind the **Device interface** condition field, one `assetInterface.groupBy` capped at 500 names), the `tag` catalogue (`listAssetTags`), and the trigger step's interface (already pin-scoped) and storage-mount dimensions — reads `monitored: true` devices only: a value that only unmonitored inventory reports is a choice that can't produce an alert AT ALL, and offering it is how an operator builds a filter, sees it match nothing, and stops trusting the picker. The **previews** follow suit and report the two halves separately (`unmonitoredCount` on `POST /automations/preview`, `matchCount` + `unmonitoredCount` on `POST /contacts/preview`) rather than hiding the remainder. **Matching now agrees**: `scopeWhere(scope, monitoredOnly)` pushes `monitored: true` into the WHERE on every EVALUATION load — threshold, composite, and the metric/state previews — and the event/change tail applies the same `assetCanTrigger` gate per row, so an unmonitored device triggers nothing. Event and change triggers were the deliberate exception until 2026-08 and no longer are (see business rule 37). The raw, unfiltered resolver survives for the surfaces asking a different question: the device-list preview (which REPORTS the remainder), the dimension-value picker, mass pinning, and `Contact.assetCondition` — a contact still OWNS a device nobody polls, ownership being an address-book fact rather than an alerting one. The storage-mount picker is the one place where offered ⊂ can-fire: unpinned mounts do get samples (`cadence:"slow"`, 24h, never rolled up) and the engine has no pin gate for storage, so a stored rule on one still evaluates — the picker steers to mounts that actually keep history. The IPAM subnet list is not inventory and stays unfiltered.

- **NotificationRule** — operator-defined alert definition — user-facing name: an **Automation**; a fired instance is an **Alert**. Carries a discriminated `trigger` (`asset_metric` | `asset_state` | `host_metric` | `event` | `change` | `composite`), an asset `scope` (nested AND/OR condition tree), unified `actions` (`notify` | `api_call` | `script` | `event`), `reset` (manual/auto/timed/condition/event — the last being the counterpart audit Event that says it recovered, for the two triggers that fire on an instant), optional `severityBands`, `escalation`, `repeat`, `resetActions` and `emailComposition`. **Rule-shape v2 supersedes the legacy `targets`/`clearBehavior` columns, which CRUD keeps rewritten as a lossless mirror** — every reader normalizes through `normalizeRuleToV2`, and input accepts both shapes. `allRuleActionRefs` is the canonical walk over all **eight** action locations. A `notify` action is **plural**: `channelIds` carries several channels behind one recipient list (`channelId` remains the primary + lossless single-channel mirror; read the pair ONLY through `notifyChannelIds`), and `respectUserPreference` narrows each recipient to the channel their own `User.notificationPreference` accepts — gated on the action group offering both methods, business rule 39. Evaluated by `notificationEngine`; CRUD gated `automationManagement` (script actions additionally require `automationScripts=fullwrite`). Vocabulary + builder catalog live in `src/services/notificationTypes.ts`.

- **Notification** — a triggered alert instance. Carries snapshotted `regionTags` + `assetHostname` so it renders after the asset is deleted, plus `templateCtx` (the fire-time token context escalation emails render from) and `escalationState`. Soft-clear preserves history. View gated `alerts:read`, acknowledge `alerts:write`, clear `alerts:fullwrite`.

- **NotificationRuleState** — per-(rule, asset, dimension) firing state machine (`clear`→`pending`→`firing`) for sustained-duration, debounce and auto-clear. **Writes only on transition**, so the engine hot path scales with *changes*, not fleet size. `metRun` / `clearRun` / `lastReadingAt` carry poll-counted holds for the sources with no sample series to count (rule 19); they are zeroed with the timers whenever a row returns to `clear`, since a stale run would let the next qualifying reading skip the hold entirely. `assetId=""` for host/global rules. **Nothing may strand a firing row the engine can no longer see** — the vanished-state sweep clears rows whose asset left scope or whose dimension stopped reporting. **Every interface trigger reads only PINNED interfaces** (`interfaceIsPinned`), and the IPsec pair gates the same way (`tunnelIsPinned`).

- **Contact** — an address-book entry: a named email address alerts can route to, whether or not the recipient holds a Polaris account. `origin` (`manual` | `entra` | `ad`) says WHO owns the row — a directory-synced row is the sync's until an operator adopts it, and the backend names line up with `AddressBookEntry.source` so the picker's badges need no translation. `kind`, `jobTitle`, `department` and `phone` carry directory identity (employee PII at rest — see business rule 35). Synced rows are visible only to `automationManagement:read`, not to the `contacts` key every built-in role holds. `email` is unique, trimmed and lower-cased. Device ownership is stated once on the contact via `assetCondition` (the same condition tree automations use, over the wider `DEVICE_FILTER_FIELD_OPS` vocabulary) unioned with explicit `assetIds`. "All devices" is reachable only through an explicit `assetAllDevices` flag, so a half-built empty tree can never hand a contact the whole fleet. Fire-time lookup evaluates against the ONE triggering asset — never a fleet scan.

- **MaintenanceSchedule** — operator-defined maintenance window definition. Targets = union(criteria matches, explicit `assetIds`) ∩ `monitored=true`; `schedule` is recurrence JSON in **server-local wall-clock**, evaluated per tick so DST is automatic — each day off, all day, or carrying one or more hour ranges (`hours` / `hoursByDay`), shared verbatim with an automation's quiet time (business rule 44). Reconciled by `maintenanceScheduler` (30s) and inline on every CRUD write. Ad-hoc one-shots self-delete once spent. See business rule 16.

- **AssetMaintenanceWindow** — one realized maintenance window per (asset, schedule). **Open rows (endedAt NULL) are the restart-safe source of truth** for "in maintenance"; closed rows power the chart bands (`scheduleName` snapshotted so labels survive schedule deletion). Plain table with a real FK.

- **NotificationChannel** — operator-configured outbound delivery integration (Automations → Delivery tab). `type` ∈ `smtp | oauth_m365 | pushbullet | slack | teams | web_push` selects transport + `config` shape; secrets masked on read, preserved on write. `web_push` is a singleton (one server VAPID keypair).

- **NotificationDelivery** — one outbound delivery per (notification, channel, concrete recipient), carrying `transport`, `target`, `meta` and retry state. Destination secrets stay on the channel and are read at send time. Expanded at fire time by `notificationRecipientService`, drained (≤3 retries) by `deliverNotifications`. Cascades with the Notification.

- **Alert email** — leads with **what fired, in the builder's own words, with the reading in it** (`{trigger.summary}`), then the chart that explains that trigger, a device facts table (closing with **what happens if nobody acts** — `{repeat.policy}` / `{escalation.policy}`, the two sentences from the pure `followUpPolicy`, severity-resolved so a banded alert advertises its OWN band's chain and snapshotted at fire time so a reminder can't describe the alert differently from the original; both prune away on an automation that neither repeats nor escalates, and `followUpLine` joins them for the push body, which has no table to prune), last-hour CPU/memory/response-time charts, and Acknowledge + Open device buttons. The default body is a shared TEMPLATE (`src/utils/alertEmailTemplate.ts`), not server-side string building, and the wizard prefills new Notify actions with the same strings so what Polaris sends is what an operator can edit. Charts are built at DELIVERY time by `alertChartService` and degrade to a text line when samples or the rasterizer are unavailable. **A gap in those three charts is drawn exactly as the in-app charts draw it** (UI-GUIDE section 15): the line DIVES to the baseline across the outage and climbs back out, each transition fading between the two colors. **The response-time chart carries the full verdict palette, in the email as on the device page** (2026-08-29): green up (`#2e7d32`), **amber** (`#ffc107`) for a miss that has not yet reached the covering automation's `missedPolls` — the down colour asserts Down, so spending it on the first dropped packet of a three-miss threshold dates the outage two polls early — the **covering automation's own SEVERITY colour** for the miss that IS the verdict (`#d32f2f` red at `critical`, which is every seeded down automation; see business rule 36 — Down is not inherently red), and **blue** (`#0288d1`) for a poll that answered while misses were still outstanding, which since 2026-09-01 is EVERY answered probe during an outage rather than only those below the threshold: an answered probe painted `down` had no colour available on an `ok` point and came out the plain series green, so an outage drew red → green → blue → green. CPU and memory keep their own series color: those are about a reading, not a verdict. Both halves come from ONE replay per surface — `probeOutageService.replayProbeStates` server-side, `PolarisMonitorStates.replay` (`public/js/monitor-states.js`) in the browser for BOTH the desktop and phone charts and the Last-30-min strip, mirrors of each other with a parity test — never from a second copy of the leaky bucket. The four colors are the same values on all three surfaces: green, amber `#ffc107` (the strip's own, deliberately not a deeper cousin picked for contrast — two ambers a shade apart read as two meanings), red `#d32f2f`, blue `#0288d1`, grey `#9aa0a6` — and the **Recovering pill** was repointed at that same blue in the same change (it was `var(--color-accent)`, the one monitor badge keyed to a theme token instead of its own colour family, so the morning theme drew it in that theme's gold, the family of the Missed pill next to it). Recovering was PURPLE until 2026-08-29, chosen when this chart's series was still the theme accent; the series going green freed the blue, which agrees with the Recovering pill instead of contradicting it and puts real distance between this and the lavender `#9575cd` that means maintenance. Excluding failed probes keeps the values honest but leaves the polyline interpolating a healthy-looking segment through the exact minutes nothing answered, so the dive is what says an outage happened. It was a red BAND until 2026-08-27, which is band vocabulary — reserved for maintenance windows, i.e. a gap that IS explained — and therefore backwards. **A miss the upstream explains dives GREY, not red**: a failed probe taken while the asset was dependency-suppressed is stamped `AssetMonitorSample.dependencyDown`, and `probeOutageService` hands every reader an `OutageKind` per window — same dive (nothing was measured either way), no accusation, because Polaris knows exactly why that probe missed. A window splits at a change of kind, so misses that were unexplained when they happened are never retroactively excused. The email surface may still diverge on size, flat-hex palette, absence of hover and run-collapsing; never on the shape of an outage, nor on which colour it is. The one band left is `alarmSpans` on the sensor chart, a different claim about a reading that is still arriving. `failSpansFrom` delegates to `probeOutageService.foldProbeOutages` so email and in-app cannot disagree about an outage's bounds. Rendered bodies are **pruned** so an under-populated device never mails blank cells — note `pruneEmptyRows` **may never match across a nested `<table>` or a second `<tr>`**, which once closed the 600px card early and mailed a visibly broken box. An alert about Polaris itself says so.

- **PushSubscription** — a browser/PWA Web Push subscription owned by a User. **Enrollment is no longer a decision of its own** — it is the consequence of `User.notificationPreference`, which every client reconciles this row against at boot (business rule 39). Carries **`surface`** (`desktop` | `mobile`) recorded at subscribe time — the only moment it is knowable, since on Android the installed PWA and the browser share one subscription — which selects the push deep link. A 410/404 prunes the row; endpoint rotation retires the old row scoped to the caller's own `userId`.

- **AutomationScript** — operator-authored script registry for Automation `script` actions. **RCE-equivalent surface**: CRUD and attaching script actions are gated by `automationScripts`, seeded fullwrite only for admin-equivalent roles; creation and body changes stamp warning Events with old/new sha256.

- **AutomationScriptRun** — one execution of a registry script. Server runs are claimed by the `runAutomationScripts` job and executed via `automationScriptRunner` (0600 temp file + execFile, SIGKILL on timeout) — **never inline in the engine or drain**. Two hardening properties: the interpreter resolves to a known absolute path, and the child environment is `process.env` **stripped of secret-shaped keys** (stdout is stored on the row and rendered in the UI, so a one-line `env` used to copy `DATABASE_URL` into a displayed column). Agent runs ride the AgentCommand queue.

- **AgentCommand** — the agent command queue. The only queued action is agent-side script runs (`run_script`, sha256 VERIFIED by the agent before executing). The agent polls, executes in the `scriptexec` sandbox, reports back — it **never self-acts and refuses unknown actions**. Process/service start/stop/restart control was removed in the Satellite-posture change.

Evaluated by `notificationEngine` on the evaluateNotificationRules job; targets expanded by `notificationRecipientService` on fire. CRUD gated `automationManagement`. Owned by `notificationRuleService`; vocabulary in `notificationTypes`. **Rule-shape v2 (2026-07):** nullable `reset` Json ({mode manual|auto|timed|condition, clearThreshold? hysteresis, sustainSec? clear-sustain, afterSec?, condition? reset tree}) supersedes clearBehavior/clearAfterSec, and nullable `actions` Json (array of notify | api_call | script) supersedes `targets`. Every reader goes through `normalizeRuleToV2`; the `migrateAutomationRuleShape` one-shot persists v2 onto pre-v2 rows; CRUD writes v2 AND rewrites the legacy columns as a lossless mirror (`legacyMirrorOfV2` — condition mode mirrors as clearBehavior="auto") so pre-wizard UIs / pre-upgrade backups stay coherent. Script actions validate against the AutomationScript registry at save and additionally require automationScripts=fullwrite at the route. **Composite triggers (2026-07):** the trigger union gains `{type:"composite", kind:"asset"|"host", op:and|or, children:[leaf|group], forDurationSec}` — a nested AND/OR tree whose leaves are the asset_metric/asset_state (kind=asset) or host_metric (kind=host) conditions minus per-leaf forDurationSec; ≤3 deep / 2–10 leaves, and/or only (negation ops would fire on data absence), validated by `validateCompositeTrigger`. Composite rules evaluate PER ASSET (multi-dimension leaves met on ANY dimension, one alert per device at dimensionKey "") while single-condition rules keep per-dimension alerting + hysteresis; the input transforms enforce that split via `collapseCompositeTrigger` (a 1-leaf composite folds to the legacy single trigger with forDurationSec hoisted, whatever client authored it). Reset mode `condition` = a custom reset tree (same leaf vocabulary, v1-restricted to composite triggers of the same kind); `isAssetScopedTrigger` is the scoped-trigger check (composite is scoped iff kind="asset"). **Severity bands + precedence (2026-07, migration 20260726000000):** nullable `severityBands` Json (numeric asset_metric/host_metric triggers only) stacks higher tiers on tier 0 (base severity+threshold) — each `{threshold, severity, operator?, forDurationSec?, actions[], escalation?}` carries its own actions + time-escalation + **sustained duration** (omitted = inherit the base trigger's `forDurationSec`; 0 = apply immediately); `severityForValue` picks the most-severe satisfied tier instantaneously while `resolveTierLadder`/`updateTierMetSince`/`sustainedSeverity` add the per-tier hold time (the engine's actual severity decision, backed by `NotificationRuleState.bandMetSince`), the alert climbs/eases severity in place per the nullable `bandNotify` Json policy ({onIncrease, onDecrease, onResolved, resolvedMode reuse|dedicated, resolvedActions?}), validated by `validateSeverityBands`. Precedence carve-out (no column — derived at eval time): `triggerSignature` (metric/field+dimensionFilter; null for host/event/change/composite) + `scopeRank` ladder (all<type<os<manufacturer<model<tag<region<subnet<hostname) let a more-specific automation shadow same-signature lower-rank ones (`buildShadowIndex`/`isAssetShadowed`); `scope.condition` `assetId` still evaluates but is off the builder + off the ladder. **Reset actions (2026-08, migration 20260812010000):** nullable `resetActions` Json — plain (non-escalatable) actions that run when the alert ENDS: auto/hysteresis/condition recovery via `recover()`, both timed sweeps, `runEventRuleTimedClear` (which now selects the alerts rather than bulk-updating a count, since an action is per-alert), and an operator clear via notificationService.clearNotifications. Executed by `fireReset` BEFORE the notification is cleared so deliveries + ack tokens attach to a live id; context uses the `resolved` pseudo-severity and the message names how it ended. NULL = silent (every pre-feature rule). Eighth location in `allRuleActionRefs`. **Actions redesign (2026-08):** top-level + severity-band actions may carry their OWN `escalation` chain (`escalatableActionSchema`; tier actions + resolvedActions stay bare so chains can't nest — state keys `a<i>:t<j>` per `escalationTierStateKey`, level chain keeps bare numeric keys), notify actions/targets take `recipientDeviceRegion` (route to users matching the TRIGGERING asset's region: tags; scope-region flag still honored on old rules), and `allRuleActionRefs` is the canonical walk every gate (automationScripts route check, assertActionRefs, ruleWantsAssetDetail) collects through. **Repeat until handled (migration `20260825000000`):** nullable `repeat` Json (`{everyMin: 5..1440, stopOn: acknowledge|clear, stopAfterHours?, quiet?: {windows: 1..8 recurrence shapes}}`) re-sends the alert's own notifications while it stays unhandled. Only escalation TIERS could repeat before — the engine's `fire()` sends the base actions once and never revisits them, so an alert nobody acknowledged went quiet after one email. Swept by the SAME `escalateNotifications` tick (it already owns unhandled-detection, the suppression pause, per-key state and templateCtx rendering), keyed `REPEAT_STATE_KEY` (`"repeat"`) in `Notification.escalationState.tiers` — collision-free against the level chain's bare numerics and the per-action chains' `a<i>:t<j>`. **Three deliberate asymmetries with escalation:** it re-runs `REPEATABLE_ACTION_TYPES` (notify) ONLY, because unbounded re-execution of a ticket-creating `api_call` or a registry `script` is not the same blast radius as an extra email (and `validateRuleV2` refuses a repeat on an automation with no notify action anywhere — a repeat that can never send is a dead setting that looks alive); it is UNBOUNDED unless the operator sets the optional `stopAfterHours`, which is why it needs its own `repeatIsDue` rather than `tierIsDue` (that resolves `maxRepeats ?? 5` and would silently cap the one behaviour that was asked to be uncapped); and it labels its email `[REMINDER n]` via the normal-fire composition path, never escalation's per-field tier→rule merge, with `meta.repeat` as a key separate from `meta.escalation`. A repeat and a due escalation tier in the same sweep BOTH send — skipping the reminder would drift its clock and make "every 15 minutes" a lie. `repeat` had to reach `DbRule` because `ruleWantsContext` gates the `templateCtx` snapshot: without it a repeat-only automation snapshots nothing and every reminder loses `{value}` / `{threshold}` / `{trigger.summary}` / every `{asset.*}`. Audited as its own `notification.repeated` Event, not `notification.escalated`. NULL = never repeats, which is every pre-feature automation, and it is deliberately NOT seeded into the baseline automations. `quiet` (business rule 44) holds a DUE reminder inside any of its windows instead of sending it — the windows are the Maintenance scheduler's own recurrence shapes (`utils/quietTime.ts` on `scheduleShapeSchema`, so server-local wall clock), `lastSentAt` is NOT advanced (the held reminder stays due and goes out on the first tick after the window), and the hold is recorded on `Notification.escalationState.quietHeldSince` / `quietHeldCount` — which is what lets that reminder carry `{repeat.quiet}` and a ` · ACTIVE <elapsed>` subject marker. It sits INSIDE `repeat` because it modifies the reminder clock and nothing else: the first alert, the escalation tiers and the reset notifications are never quiet.

## Notes

#### NotificationRule

**NotificationRule** — operator-defined alert definition. Flexible discriminated `trigger` (JSON union: `asset_metric` | `asset_state` | `host_metric` | `event` | `change` | `composite` — the last a nested AND/OR tree `{kind: asset|host, op, children}` of metric/state leaves, ≤3 deep / 2–10 leaves, and/or only; composite rules alert PER ASSET (ANY-dimension leaves, dimensionKey ""), while a 1-leaf composite collapses server-side to the legacy single trigger — `collapseCompositeTrigger` — keeping per-dimension alerting + hysteresis) + asset `scope` (which narrows EVERY trigger type except `host_metric` — an `event` or `change` rule's scope filters the Event's subject, business rule 46; `{}` on an event rule predates that and means "any device"), per-rule `clearBehavior` (manual / auto-resolve / timed), `cooldownSec`, `messageTemplate`, `requireAckNote` (refuse an acknowledgement with no note — business rule 25), `channels` (default `["in_app"]`), and `targets` (JSON array of outbound deliveries: `{ channelId, recipientUserIds?, addresses?, recipientScopeRegion?, recipientTags?(legacy) }` referencing **NotificationChannel** rows — recipients combine individual user accounts, custom emails, and (when `recipientScopeRegion`) users matching the rule's scope `region:` tag(s); recipient routing only applies to email/web_push channels). Also carries optional `emailComposition` (rule-level outbound-email customization: `subjectTemplate` / `bodyTextTemplate` / `bodyHtmlTemplate` + `cc`/`bcc` recipient sets; templates use the single-brace `{token}` vocabulary in `src/utils/notificationTemplate.ts`, surfaced to the builder via `/schema.templateVariables`; when set, each email target sends ONE message with its full To list + Cc + Bcc instead of the default per-address fan-out; NULL = pre-feature behavior) and optional `escalation` (≤5 tiers, `stopOn: "acknowledge"|"clear"` — stored as posted in EITHER shape: legacy email tiers `{afterMin, channelId, to, cc?, bcc?, template overrides?, repeat*}` or **v2 tiers of actions** `{afterMin, actions[≤10 notify|api_call|script], repeat*}`; readers normalize via `normalizeEscalationToV2`, and the `escalateNotifications` sweep runs due tiers through `automationActionService.executeActions` — legacy tiers produce byte-identical emails: per-field tier→rule composition fallback + the `[ESCALATION n]` default-subject prefix; a tier's state bumps only when ≥1 action executed). Evaluated by `notificationEngine` on the `evaluateNotificationRules` job; in-app is always implicit, `targets` drive email/chat/push via `notificationRecipientService` → `NotificationDelivery` → the `deliverNotifications` job. CRUD gated by the `automationManagement` RBAC key (renamed from `notificationManagement` in the Automations cutover, migration `20260721000000`). The trigger/scope/target vocabulary + builder catalog live in `src/services/notificationTypes.ts`. `scope.condition` is a nested AND/OR/NONE/NOT-ALL rule tree (fields assetType/manufacturer/model/hostname/os/tag/subnet/interfaceName/status/assetId; ≤5 deep, ≤100 rules) evaluated by the pure `evaluateScopeCondition` — `interfaceName` ("Device interface") matches the device's current-state `AssetInterface` inventory rather than a column, resolved in SQL by `scopeInterfaceIndex` instead of joined, and contributing nothing to `scopeRank` — shared by the engine's post-SQL filter, the in-memory matcher, and `scopeRegionTagsOf` (which also mines positive `region:` tag rules from trees for recipientScopeRegion routing); flat scope dimensions remain valid and AND with a condition when both are present. User-facing name: an **Automation**; a fired instance is an **Alert**. **Repeat until handled (migration `20260825000000`):** nullable `repeat` Json (`{everyMin: 5..1440, stopOn: acknowledge|clear, stopAfterHours?, quiet?: {windows: 1..8 recurrence shapes}}`) re-sends the alert's own notifications while it stays unhandled. Only escalation TIERS could repeat before — the engine's `fire()` sends the base actions once and never revisits them, so an alert nobody acknowledged went quiet after one email. Swept by the SAME `escalateNotifications` tick (it already owns unhandled-detection, the suppression pause, per-key state and templateCtx rendering), keyed `REPEAT_STATE_KEY` (`"repeat"`) in `Notification.escalationState.tiers` — collision-free against the level chain's bare numerics and the per-action chains' `a<i>:t<j>`. **Three deliberate asymmetries with escalation:** it re-runs `REPEATABLE_ACTION_TYPES` (notify) ONLY, because unbounded re-execution of a ticket-creating `api_call` or a registry `script` is not the same blast radius as an extra email (and `validateRuleV2` refuses a repeat on an automation with no notify action anywhere — a repeat that can never send is a dead setting that looks alive); it is UNBOUNDED unless the operator sets the optional `stopAfterHours`, which is why it needs its own `repeatIsDue` rather than `tierIsDue` (that resolves `maxRepeats ?? 5` and would silently cap the one behaviour that was asked to be uncapped); and it labels its email `[REMINDER n]` via the normal-fire composition path, never escalation's per-field tier→rule merge, with `meta.repeat` as a key separate from `meta.escalation`. A repeat and a due escalation tier in the same sweep BOTH send — skipping the reminder would drift its clock and make "every 15 minutes" a lie. `repeat` had to reach `DbRule` because `ruleWantsContext` gates the `templateCtx` snapshot: without it a repeat-only automation snapshots nothing and every reminder loses `{value}` / `{threshold}` / `{trigger.summary}` / every `{asset.*}`. Audited as its own `notification.repeated` Event, not `notification.escalated`. NULL = never repeats, which is every pre-feature automation, and it is deliberately NOT seeded into the baseline automations. `quiet` (business rule 44) holds a DUE reminder inside any of its windows instead of sending it — the windows are the Maintenance scheduler's own recurrence shapes (`utils/quietTime.ts` on `scheduleShapeSchema`, so server-local wall clock), `lastSentAt` is NOT advanced (the held reminder stays due and goes out on the first tick after the window), and the hold is recorded on `Notification.escalationState.quietHeldSince` / `quietHeldCount` — which is what lets that reminder carry `{repeat.quiet}` and a ` · ACTIVE <elapsed>` subject marker. It sits INSIDE `repeat` because it modifies the reminder clock and nothing else: the first alert, the escalation tiers and the reset notifications are never quiet. **Reset actions (migration `20260812010000`):** nullable `resetActions` Json — actions that run when the alert **ENDS**, on every path that ends one: auto / hysteresis / custom-condition recovery, the timed sweep (including the event-tail timed clear, which now selects the alerts instead of bulk-updating a count), and an operator clearing by hand (`clearNotifications`). Plain `actionSchema`, never escalatable — an escalation chases an unhandled alert and there is nothing to chase about a recovery, the same reason `bandNotify.resolvedActions` stay bare. They run **before** the clear (mirroring `fireResolved`), so their delivery rows and acknowledge tokens attach to a live notification; the message names how it ended, and the context uses the `resolved` pseudo-severity. NULL = silent, which is what every stored automation keeps until it is edited — nothing retroactively starts emailing on recovery. The wizard’s **“When this resets”** list (Actions step) MIRRORS the trigger’s notify actions as they are created and detaches a row the moment it is edited or deleted, so telling the same people it came back costs nothing. On a NEW automation it also seeds the same default `event` action the fire list carries, so a recovery is audited the way the firing is (an ordinary removable row — the mirror leaves it removed). Emptying the list **unticks the toggle**: `collectStep5` saves an empty list as `null`, so a ticked box over no rows was a state the next open would contradict. `resetActions` is the **eighth** location in `allRuleActionRefs`. **Rule-shape v2 (migration `20260722000000`):** nullable `reset` Json (`{mode: manual|auto|timed|condition|event, clearThreshold?, sustainSec?, afterSec?, condition?, resetEvent?}` — hysteresis + clear-sustain for auto; `condition` = a custom AND/OR reset tree, allowed on ANY trigger with a continuous condition — `TRIGGER_TYPES_WITH_RESET_CONDITIONS`, i.e. everything but `event`/`change`, which fire on an instant and have nothing to recover — restricted to leaves of the trigger's own kind (device vs Polaris-host), mirrored to legacy as `clearBehavior:"auto"`. Those two get **`mode:"event"`** instead (`TRIGGER_TYPES_WITH_RESET_EVENT`, the exact complement): `resetEvent` names the counterpart audit Event that clears the alert (`agent.disconnected` → `agent.connected`), matched in the SAME event-tail pass as the triggers and scoped to the same subject the alert is filed under — `assetId` when the event names an asset, else the resource label — with a rule that matched an event as a TRIGGER dropping that event's reset hit so a wide glob can't clear the alert it just raised. Also mirrored to legacy as `clearBehavior:"auto"`. See business rule 32) supersedes `clearBehavior`/`clearAfterSec`, and nullable `actions` Json (unified outcome list: `notify` | `api_call` | `script` | **`event`**) supersedes `targets`. **`event` = write the `notification.triggered` audit Event** — present by default (migration `20260810120000_event_action` appended it to every stored rule, and both normalizers inject it when folding a legacy shape forward) and removable for a deliberately noisy automation; the engine writes that Event only when the action is present. It carries no config and takes no `escalation` (an instantaneous Event has nothing to chase), and it is deliberately NOT added to `event`/`change`-triggered rules, whose tail writes no Events by design. The in-app **Alert** is NOT optional: `NotificationDelivery` rows, the escalation sweep, acknowledge/clear and `NotificationRuleState` all key on `Notification.id`, so a notify/api_call action can't exist without one. Every reader normalizes via `normalizeRuleToV2`; the `migrateAutomationRuleShape` one-shot persists v2 onto old rows; CRUD keeps the legacy columns rewritten as a lossless mirror (`legacyMirrorOfV2`) so the pre-wizard UI and pre-upgrade backups stay coherent. Input accepts BOTH shapes (legacy bodies fold into v2). Script actions validate against the `AutomationScript` registry at save and require `automationScripts=fullwrite` on top of `automationManagement`; escalation input accepts both the legacy email-tier shape and v2 tiers-of-actions. **Severity bands (migration `20260726000000`):** nullable `severityBands` Json (numeric asset_metric/host_metric triggers only) stacks higher tiers on the base trigger threshold/severity (tier 0) — each band `{threshold, severity, operator?, forDurationSec?, actions[], escalation?}` carries its OWN actions + time-escalation + **sustained duration** (tiers share the trigger's sampling — aggregation/window/dimensionFilter — but may override the comparison `operator` and the hold time; omitted `forDurationSec` inherits the base trigger's, 0 = apply immediately); `severityForValue` resolves the most-severe satisfied tier instantaneously, and `resolveTierLadder`/`updateTierMetSince`/`sustainedSeverity` (all pure, in notificationTypes) layer the per-tier hold on top — backed by `NotificationRuleState.bandMetSince`. Nullable `bandNotify` Json `{onIncrease(def true), onDecrease(def false), onResolved(def true), resolvedMode: reuse|dedicated, resolvedActions?}` is the per-automation transition policy. One alert per asset climbs/eases severity in place (re-notifying with the entered band's actions per policy) and clears below tier 0. `validateSeverityBands` enforces a numeric ordered operator (base + any per-tier override) + **strictly-increasing severities** (thresholds need not be monotonic — most-severe-met wins); band/resolved/per-band-escalation actions get the same `automationScripts=fullwrite` gate + ref checks. **Precedence / carve-out:** when two automations watch the SAME thing (`triggerSignature` = metric/field + dimensionFilter; null for host/event/change/composite = exempt) a more-specific one (`scopeRank` ladder least→most: all assets < device type < OS < manufacturer < model < tag < region < subnet < hostname) carves the assets it covers out of the less-specific one — those assets drop their readings, any active alert clears (`notification.superseded`), pending debounce resets; same-rank ties both fire. `buildShadowIndex`/`isAssetShadowed` in the engine; `previewRule` surfaces it both authoring directions (`carveOut.carvedOut`/`carvesFrom` + per-match `excludedBy` + `specificity`). See business rules 18–19. `scope.condition`'s `assetId` field still validates + evaluates for saved rules but is no longer offered in the builder. **Actions redesign (2026-08):** (1) **Per-action escalation** — top-level and severity-band actions may carry their OWN `escalation` chain (`escalatableActionSchema`; escalation-tier actions and `bandNotify.resolvedActions` stay bare, so chains can't nest); the sweep iterates `escalationChainsForSeverity` — the rule/band LEVEL chain (state keys stay the bare numeric tier indexes) + one chain per effective action (state keys `a<i>:t<j>` via `escalationTierStateKey`), with per-chain `stopOn`. `allRuleActionRefs` is the canonical walk over all seven action locations — the `automationScripts` route gate, `assertActionRefs`, and `ruleWantsAssetDetail` all collect through it; `ruleWantsContext` uses `ruleHasAnyEscalation`. (2) **Device-region + address-book recipients** — notify actions/targets take `recipientRoles` (every user holding one of the named Roles — role IDS, so a rename can't reroute; resolves to users, so it works on email and push alike and in cc/bcc) and `recipientAssetContacts` (route to the address-book **Contact** rows whose device filter covers the TRIGGERING asset — ownership is stated once on the contact instead of per rule; email transports only, since a contact is an address with no push endpoint behind it; the addresses are resolved by `automationActionService` and handed to `expandDeliveries` as `assetContactEmails`, because `contactService` imports `notificationRecipientService` and the expander fetching them itself would close an import cycle) and `recipientDeviceRegion`: route email/push to users whose region tags match the TRIGGERING asset's `region:` tags (engine passes `regionSnapshot(reading.tags)`; the sweep reads `Notification.regionTags`); `recipientScopeRegion` (rule-scope region) still honored on old rules but no longer offered in the builder. (3) **Event-path hardening** — the event tail now enforces `cooldownSec` (against recent Notification rows keyed rule + assetId-or-resourceName, self-deduping within a batch) and `runEventRuleTimedClear` clears timed-reset event/change notifications after `afterSec` (they have no state rows, so the regular timed sweeps never saw them).

#### Notification

**Notification** — a triggered alert instance. UI surfaces: the dashboard's **Active Alerts** widget (Notification-backed since 2026-08 — it read audit Events before, so automation-less discovery/sync failures showed as permanent un-clearable "alerts" and `Event.level`'s critical/serious collapse rendered a `serious` automation as "error"; it now gates on `alerts:read`, carries the automation's own severity, and drops a row when the alert clears) + the asset-details Alerts tab (the dedicated page-level Alerts list was removed from /automations.html 2026-07; the `/alerts` API + acknowledge/clear flows and the `alerts` RBAC key are unchanged). /notifications.html remains a permanent redirect for delivered push deep links; both pages now gate on `automationManagement:read`. Carries snapshotted `regionTags` (stripped of the `region:` prefix → compares directly to a viewer's region tags) + `assetHostname` so it renders/scopes after the asset is deleted, plus (when the rule has emailComposition/escalation) `templateCtx` — the fire-time token→string context snapshot escalation emails render from — and `escalationState` (per-tier `{ firstSentAt, lastSentAt, count }` written by the escalation sweep, keyed per chain — bare numeric indexes for the rule/band-level chain, `a<i>:t<j>` for per-action chains). Soft-clear (`cleared`) preserves history. View gated `alerts:read`; acknowledge (note + by/at) gated `alerts:write` (readonly cannot); clear gated `alerts:fullwrite` (admin + assetsadmin). (`alerts` = the renamed `notifications` key.)

#### NotificationRuleState

**NotificationRuleState** — per-(rule, asset, dimension) firing state machine (`clear`→`pending`→`firing`) for sustained-duration + debounce + auto-clear. Writes only on transition (capacityWatch-style guard) so the engine hot path scales with *changes*, not fleet size. `assetId=""` for host/global rules. `firingSeverity` (severity-bands) tracks the band the active alert is currently in, so the engine detects increase/decrease/same crossings across ticks; `metRun` / `clearRun` / `lastReadingAt` carry POLL-COUNTED holds for the sources with no sample series to count — the Asset columns, the delete-replaced SD-WAN rule table, the windowed-ratio metrics recomputed per tick, and a composite tree's own outcome: the run advances only when that stream's poll anchor moved (`advanceRun`), so the engine's 60-second tick can't count five polls against a device polled every five minutes, and all three are zeroed whenever the row returns to `clear` (a stale `metRun` would let the next qualifying reading skip the hold outright). A series-backed trigger stores none of them — its run is the leading count of qualifying samples, computed per tick (`leadingRun`). `bandMetSince` Json (`{[severity]: epochMs}`) holds each tier's continuously-satisfied run, which is what makes a wall-clock "sustained for" per-band (business rule 19) — rewritten only when a tier enters or leaves, so the transition-only write property holds. **Nothing may strand a firing row the engine can no longer see:** the engine's vanished-state sweep clears rows whose asset left the rule's scope or whose dimension stopped being reported (`system:out-of-scope`; suppressed assets and in-scope assets with zero readings stay frozen), and the rule service clears active alerts on trigger-identity edit / disable / delete. **Every** interface trigger reads only PINNED interfaces (`Asset.monitoredInterfaces`) — the state fields `ifOperStatus`/`ifAdminStatus`/`ifIpAddress`/`poeStatus` and the counter metrics `ifInBps`/`ifOutBps`/`ifInErrorRate`/`ifOutErrorRate` alike, through the shared `interfaceIsPinned` predicate; a device reports every port it has, so the pin is the operator's statement of which ones may alert and there is no opt-out (the builder's interface picker lists the pin set for the same reason). Plus an admin-up gate on ifOperStatus — unplugged or deliberately-disabled ports never alert. `poeStatus` (POWER-ETHERNET-MIB, SNMP only) carries the same shape plus two gates of its own: a NULL reading means "not a PoE port" rather than "PoE is off" and is dropped (otherwise a not-delivering rule fires on every uplink and SVI), and `"disabled"` is excluded as the PoE analogue of the admin-up gate. A *fault* rule is unaffected by that second gate — a disabled port reports `disabled`, never `fault`. The IPsec pair `ipsecStatus`/`ipsecThroughputBps` gates the same way (2026-08) through `tunnelIsPinned` over `Asset.monitoredIpsecTunnels`: unlike interfaces, whose sample table is pinned-only, the IPsec stream still samples EVERY tunnel the gate reports (unpinned rows ride `cadence="slow"`, 24h — they feed the slide-over display), so the engine gate is the only thing keeping a tunnel-down automation from alerting on tunnels nobody selected — and the builder's tunnel picker lists the pin set for the same reason.

#### Contact

**Contact** — an address-book entry: a named email address alerts can route to, whether or not the recipient holds a Polaris account (a distribution list, an on-call rotation, a vendor NOC). `email` is unique and stored trimmed + lower-cased, so the index is case-insensitive and the value compares directly against the normalized set `resolveEmailRecipients` builds. Optional `name` / `description`, plus **device ownership**: `assetCondition` — the SAME nested AND/OR condition tree the automations device filter stores, evaluated by the same `evaluateScopeCondition` — unioned with explicit `assetIds` pins, deliberately NOT intersected with `monitored=true`, since an unmonitored device still has an owner and event/change automations fire on it. It supersedes the flat `assetCriteria` (`tagAssignmentService` vocabulary) it shipped with, so operators aren't asked "which devices?" in two languages: both columns are still READ but only ONE is live per row (a write of the condition nulls the criteria), and pre-cutover rows fold forward through the pure `criteriaToCondition` on read, persisted by the `migrateContactFilterShape` one-shot — the `normalizeRuleToV2` pattern. The tree validates against **`DEVICE_FILTER_FIELD_OPS`**, a strict SUPERSET of the automations scope vocabulary: it keeps the four fields the flat builder carried and the automations scope lacks (`osVersion` / `department` / `location` / `fortigate` = "behind FortiGate", matched against `learnedLocation` OR any sighting — where a NEGATIVE operator must hold for EVERY candidate name, or "not behind gate X" would be true for a device sighted behind it the moment it was also sighted elsewhere) plus a wildcard `matches` operator, because losing them would be a regression in exactly the dimension device ownership cares about, and because it's what makes every stored criteria blob convertible. `fortigate` is deliberately NOT added to the automations scope — that filter runs over the whole fleet on every engine tick and the sighting join would land on the hot path. "All devices" is stored as the empty AND group (true for any asset by boolean identity) but is reachable ONLY through an explicit `assetAllDevices` input flag, so a malformed or half-built empty tree can never quietly hand a contact the whole fleet. `createdBy` backs the ownership dimension on the `contacts` key. Owned by `contactService`; the fire-time lookup (`resolveContactsForAsset`) evaluates each contact's filter against the ONE triggering asset — the pure `evaluateScopeCondition` for a tree (which does its own CIDR math, so a folded-forward address book makes no containment query at all), `assetMatchesCriteria` for a legacy blob — never a fleet scan. Surfaced on Automations → Address Book and in the automation wizard's recipient picker.

#### MaintenanceSchedule

**MaintenanceSchedule** — operator-defined maintenance window definition (Assets page → Maintenance modal, gated `maintenanceManagement`). Targets = union(criteria matches, explicit `assetIds`) ∩ `monitored=true`; `criteria` reuses the tagAssignmentService vocabulary (hostname/model/manufacturer/os contains|exact|pattern, subnet `inCidr` — a bare IP is a /32; `integration` = discovered-by integration id, exact-only, matched against `discoveredByIntegrationId` OR any AssetSource row; `fortigate` = "behind FortiGate" device name with string ops, matched against `learnedLocation` OR any AssetFortigateSighting — contains on a site prefix covers every gate at the site; `status` rules rejected since the feature itself flips status); `schedule` is the recurrence JSON validated by `src/utils/maintenanceRecurrence.ts` (oneshot | recurring daily/weekly/monthly/yearly, optional time-of-day range that may span midnight, optional active date bounds — SERVER-LOCAL wall-clock, evaluated per tick so DST is automatic). Reconciled by the `maintenanceScheduler` job (30s) and inline on every CRUD write (so the ad-hoc pill path takes effect immediately). Per-schedule `suppressChildren` (default true) controls whether in-window assets count as down for child dependency suppression. **Ad-hoc lifecycle:** the pill/edit-modal "enter maintenance until…" path creates a single-asset one-shot with `schedule.startNow: true` (the SERVER stamps startAt — a browser-stamped start lands in the server's future whenever the operator's clock runs ahead, breaking immediate entry); any schedule matching the ad-hoc shape (one-shot + no criteria + exactly one explicit asset) self-deletes once spent — operator ends maintenance early (`operatorReleaseAsset`) or the window ends naturally (reconcile sweep; `nextWindow` guard keeps future-edited one-shots) — with closed window rows keeping the `scheduleName` snapshot for chart bands. Disable is an operator choice and never auto-deletes. See business rule 16.

#### AssetMaintenanceWindow

**AssetMaintenanceWindow** — one realized maintenance window per (asset, schedule): opened when the scheduler enters the asset, closed with `endedAt` + `endReason` (`schedule`/`operator`/`disabled`/`deleted`/`criteria`). Open rows (endedAt NULL) are the restart-safe source of truth for "in maintenance"; closed rows power the chart maintenance bands (`GET /assets/:id/maintenance-windows`; `scheduleName` snapshotted so labels survive schedule deletion). Plain table with a real FK to Asset (the no-FK rule is hypertables-only); rows older than ~400 days pruned by the reconcile.

#### NotificationChannel

**NotificationChannel** — operator-configured outbound delivery integration (Automations → Delivery tab; set up like the Integrations page). `type` ∈ `smtp` | `oauth_m365` | `pushbullet` | `slack` | `teams` | `web_push` selects transport + `config` shape; secrets in `config` are masked on read / preserved on write. `web_push` is a singleton (one server VAPID keypair). Owned by `notificationChannelService`; CRUD gated `automationManagement`. Rules reference channels by id in `targets`.

#### NotificationDelivery

**NotificationDelivery** — one outbound delivery per (notification, channel, concrete recipient). `channelId` → NotificationChannel (SetNull; null on a pending row = permanent fail — EXCEPT `transport="api_call"` rows, whose NULL channel is the designed shape: the whole request spec + fire-time-rendered body ride `meta`, dispatched by `apiCallChannel.sendApiCall` with SSRF re-check and normal retries) + `transport` (email/webhook/web_push/pushbullet/api_call) + `target` (recipient address/endpoint; "" for fixed-destination channels; for a composed email, the joined To list — one row carries the whole send, since the acknowledge link names the alert rather than a person (business rule 25)) + `meta` (web_push keys, or the composed-email snapshot `{ composed: true, to[], cc[], bcc[], subject, text, html?, escalation? }` — rendered content + recipient addresses only, never channel secrets) + `status` (pending/sent/failed) + `attempts`. Destination secrets stay on the channel, read at send time. Expanded at fire time by `notificationRecipientService` (escalation rows inserted by the sweep); drained (≤3 retries) by `deliverNotifications` — rows without `meta.composed` (incl. pre-upgrade pending rows) take the legacy per-address path. Cascades with the Notification.

#### Alert email

**Alert email** — leads with **what fired, in the builder's own words, with the reading in it** (`{trigger.summary}` → "Response time (median over 5 minutes) is 760 ms"; `utils/triggerSummary.ts` mirrors the wizard's `triggerSentence` phrasing, states a hardware sensor's value in the install's display unit, reads an alarm bit as a STATE rather than "is 1", and falls back to the CONDITION when no reading is available rather than a sentence fragment). It covers every trigger type, not just metrics: a device-state alert reads "**Monitor status is down**" (the builder's `FIELD_META` label, never the column name) and an event alert names the **event that actually happened** rather than the pattern that was configured — "integration.discover.error on FMG-Ashfield" — with `{event.action|resource|resourceType|actor|level|message}` tokens behind matching facts rows, which for an event about an integration or a user are the only identifying facts the email has. **`{event.message}` is the event's own text — the REASON** ("Discovery failed: RPC -11 no valid session"), and it rides its own **Detail** row rather than `{message}`: the 12 seeded event automations set `messageTemplate: "{value}"` purely to surface that text, so a row of its own is what keeps the reason in the email when an operator replaces the message template. The chart that explains THAT trigger comes first (`{chart.trigger}` resolves via `chartTokenForMetric` against the new `Notification.metric`, which is stamped for asset_state fields too; the specific token for the same chart later in the body is deduped so it never appears twice). "Asset down" points at the response-time chart — the climb before the device stopped answering — and a **packet-loss chart** (`{chart.probeLoss}`, derived by bucketing `AssetMonitorSample` success/failure — 2-minute buckets scaled up so ~30 points cover the span, empty buckets skipped rather than plotted as healthy) carries the alerts where every probe failed and there is no latency left to plot; **its window follows the automation's own History** (`lossChartWindowMs` in the delivery drain reads the rule's trigger through the shared `probeLossWindowSec`, so the graph spans exactly the period the ratio that fired was measured over — the axis label and summary line state the real span), while CPU / memory / response time stay last-hour context. **Its caption quotes the window's PROBE ratio, not the mean of its buckets** (`probeLossSeriesFrom` returns both; `sparklineSvg`'s `avgOverride` prints the ratio): a mean of per-bucket ratios weighs a 10-probe bucket and a 1-probe bucket equally, so the caption drifted from the alert's own reading whenever sampling was uneven — a polling gap, the anchor trimming a partial bucket, a suppressed asset's 2× interval, or (while it ran) the ICMP loss sampler oversampling the failures that started it. Prod 2026-08-20 mailed "18.3 %" over a chart captioned "avg 6.7 %". The chart applies the ratio's **anchor** to its CAPTION ONLY (samples before the window's first success and before `Asset.recoveryStartedAt` are left out of the number, per (b) below) while the LINE plots the whole window: anchoring the picture too meant a loss graph that began when the device came back, so the outage the operator was paged about was missing from the chart sent to explain it. `probeLossSeriesFrom` returns `measuredFromMs` whenever the anchor excludes plotted samples and `sparklineSvg` draws it as a dashed **measured** rule (same clause on the text summary, for a reader whose client blocks images), so the loss to its left reads as outside the caption's number rather than as a contradiction of it — and with NO success in the window every row is measured and it reads 100 %, the widget's `includeFullyDown` semantics, because an asset-down alert embeds this chart too and a blank one there would read as "no loss". A hardware-sensor automation (**value or alarm — both**) charts the sensor's VALUE with the device's own alarm periods shaded (`{chart.sensor}`, keyed on `Notification.dimension` = the bare sensor name). A metric that reported nothing in the window is dropped from the body entirely rather than printing "no data". **An alert about ONE PORT gets no charts at all** and the port's **LLDP neighbour** instead (`isPortScopedAlert` in alertChartService → `services/alertInterfaceService.ts`'s `{interface.lldp}`): a switch with a dead port is answering probes — that is how the port is known to be down — so CPU, memory, response time and packet loss are all flat and healthy, and four graphs of a healthy device bury the finding. What the reader actually wants is what was plugged into port2, which the switch already told us. Only the interface STATE fields (`ifOperStatus` / `ifAdminStatus` / `ifIpAddress` / `poeStatus`) drop their charts — an `ifInErrorRate` / `ifOutBps` alert plausibly correlates with device load and keeps them, while still getting the LLDP block. The block is findable at all only because `persistLldpNeighbors` holds a vanished neighbour for a 48-hour sticky window, which is also why it always prints **Last advertised**: the row predates the outage by definition, so its staleness IS part of the finding. `{interface.lldp}` is DEFERRED like `{chart.*}` (`isDeferredToken` matches the whole `interface.` prefix) and expands to a complete `<tr>` with its own heading or to nothing, so no pruning pass of its own is needed; its plain-text form uses no colons anywhere, since `pruneEmptyTextLines` would otherwise delete the heading as a valueless "Label:" line. The default outbound body is a shared TEMPLATE (`src/utils/alertEmailTemplate.ts`), not server-side string building: a TWO-COLUMN header — severity line / subject / trigger sentence on the left, and the install’s **letterhead** right-aligned opposite it (`{brand.header}` → `services/alertBrandService.ts`: the logo as an inline CID attachment, the application name, the subtitle; a DEFERRED token like `{chart.*}`, so an escalation sent hours later carries the CURRENT branding rather than a fire-time snapshot). Which mark and whether the name prints are business rule 27’s decisions, not the email’s: the card is white so the LIGHT-inked `polaris-horiz-light.png` wordmark is the shipped choice, and because that art already spells the product name the name is printed only beside an operator’s OWN logo (which also picks up the accent composite when one is enabled), while the subtitle renders either way. Note the header is therefore a two-cell row — the exact label/value shape `pruneEmptyRows` deletes — and the one-cell `<table>` wrapped around the token is what keeps that pass from taking the headline along with an empty letterhead. Then severity header, the alert sentence — and **`{message}` is deliberately NOT printed under it in either body**, since the sentence is generated from the automation's own trigger and the message restates it ("Monitor status is down" over a grey "HARBOR-61F-1 is down"); the message keeps its real homes, the in-app alert card and every chat/push body, which carry no trigger sentence. A **recovery** is the one case where the message is not a restatement, so the three reset/resolved paths (`fireResolved` / `fireReset` / the operator-clear `runResetActionsForCleared`) stamp their sentence through `setRecoverySentence`, which writes the HEADLINE as well as `{message}` — re-rendering the recovered reading under a green "resolved" header would otherwise read as a fresh alert about a healthy device — a device facts table (IP, connected switch/AP, location, model, **description** — `{asset.description}`, last of the asset rows because it's the only free-text one and a paragraph must not push the identifying facts out of first glance; on a description-synced install this is the device's own admin description, business rule 14 — automation, raised-at), the **last hour of CPU / memory / response time as inline charts**, and **Acknowledge** + **Open device** buttons. The wizard prefills a new Notify action with those exact strings (`schema.defaultEmailTemplate`) so what Polaris sends is what the operator can edit; any piece left blank falls back to the same template server-side, so stored automations get the new body with no migration. Charts are built at DELIVERY time by `alertChartService` (SVG via `utils/sparklineSvg` → PNG via @resvg/resvg-js → inline `cid:` attachment) and degrade to a now/avg/peak text line whenever samples, the asset, or the rasterizer are unavailable. Rendered bodies are pruned (`pruneEmptyRows` / `pruneEmptyDivs` / `pruneEmptyTextLines` / `pruneDeadLinks` at compose time, `pruneEmptyChartSection` at delivery time once `substituteChartTokens` has decided which charts had data) so an under-populated device never mails blank cells, an empty headline, an `<a href="">` button, or a "LAST HOUR" heading over nothing. **`pruneEmptyRows` may never match across a nested `<table>` or a second `<tr>`** — see the alertEmailTemplate.ts entry in the skill references (formerly ARCHITECTURE.md): a container `<tr><td>` plus the first fact row's empty value cell reads as a label/value pair, and dropping that span took the facts table's opening tag with it and closed the 600px card early, so every alert about Polaris itself mailed a visibly broken box. **An alert about Polaris itself says so**: a system-scoped audit Event (capacity, backups, updates) names no resource, so `utils/alertSubject.ts` supplies `"Polaris server"` as the subject for the `{asset}` token, the stored `Notification.assetHostname` and the event-path cooldown key alike — before it those alerts had a blank headline and a subject line reading "[WARNING]  — Capacity severity escalated". The facts table's label column is a fixed 140px (auto layout gave the labels most of the card once the device rows pruned away) and "Raised" prints `{time.local}` — the server-timezone form — since ISO-8601 is both unfriendly and a 24-character unbreakable string that wrapped mid-token; `{time}` stays catalogued for operator templates that want the machine form.

#### PushSubscription

**PushSubscription** — a browser/PWA Web Push subscription owned by a User (`endpoint` unique + `p256dh`/`auth` keys). Stored via `POST /push-subscriptions`; the web_push channel sends to a recipient user's endpoints via `web-push` signed with the channel's VAPID keypair; a 410/404 prunes the row. Carries **`surface`** (`desktop` | `mobile`, default desktop — migration `20260807000000`): which Polaris surface enrolled, recorded at subscribe time because that's the only moment it's knowable (on Android the installed PWA and the browser share one subscription). It rides the delivery row's `meta` and selects the push deep link — mobile → `/mobile.html#more/alerts`, desktop → `/automations.html` (`pushDeepLinkUrl` in `src/utils/notificationTemplate.ts`, which — unlike `notificationsPageUrl` — falls back to a RELATIVE path instead of null when `POLARIS_PUBLIC_URL` is unset, so an unset public URL can't force every push to the desktop page). Endpoint rotation (`pushsubscriptionchange`) posts `oldEndpoint` alongside the new one; the retiring row's surface carries forward and the row is retired, scoped to the caller's own `userId`.

#### AutomationScript

**AutomationScript** — operator-authored script registry for Automation `script` actions (name unique, interpreter bash|sh|powershell|cmd|python3, body ≤64KB, runTarget server|agent|either, timeoutSec ≤600, sha256 recomputed every save, enabled). **RCE-equivalent surface**: CRUD + attaching script actions gated by the `automationScripts` key (seeded fullwrite only for admin-equivalent roles); creation + body changes stamp warning Events with old/new sha256. Owned by `automationScriptService`; routes at `/automations/scripts` (mounted before `/automations`).

#### AutomationScriptRun

**AutomationScriptRun** — one execution of a registry script (server- or agent-side): scriptName/sha256 snapshots, notificationId/ruleId/assetId (no FK), runOn, args snapshot, status pending|running|succeeded|failed|timeout, exitCode + stdout/stderr (≤64KB each). Server runs are claimed and executed by the `runAutomationScripts` job (5s) via `automationScriptRunner` (0600 temp file + execFile, args as a single argv, SIGKILL on timeout — never inline in the engine/drain). Two hardening properties of that executor: the interpreter resolves to a known **absolute path** where one exists rather than to whatever the inherited PATH names first (bare name only as a last-resort fallback, so a non-standard layout still runs), and the child environment is `process.env` **stripped of secret-shaped keys** (`buildScriptEnv`: `/SECRET|TOKEN|PASSWORD|PASSWD|DATABASE_URL|SESSION|CREDENTIAL|PRIVATE_KEY|_KEY$/i` — a denylist, so PATH/HOME/proxy/locale stay inherited and existing scripts keep working). The scrub matters because **stdout is STORED on the run row and rendered in the Scripts tab**: before it, a one-line `env` copied `DATABASE_URL` and `POLARIS_SECRET_KEY` into a displayed, backed-up column. Authoring a script is already RCE-equivalent so this crosses no privilege boundary — it removes the accidental copy; agent runs ride the AgentCommand queue (`run_script` payload, sha256-verified by the Go `scriptexec` package, results via `/agents/command-result`); pruned after ~90 days.

#### AgentCommand

**AgentCommand** — the agent command queue. The only queued action is **agent-side script runs** (`action="run_script"`, nullable `payload` Json `{runId, interpreter, body, sha256, args, timeoutSec}` — body inline ≤64KB, sha256 VERIFIED by the agent before executing; queued only for active agents ≥0.13.0 via `requestScriptRun`'s version gate, linked to `AutomationScriptRun.agentCommandId`). Agent polls `GET /agents/commands` (the ≤20s poll is the guaranteed floor; a `commands-pending` WS frame wakes it sooner — see `agentCommandWake`), executes via the `scriptexec` sandbox, reports `POST /agents/command-result` (exitCode/stdout/stderr, ≤64KB each). The agent never self-acts and refuses unknown actions. **Process/service start/stop/restart control was removed** (Satellite-posture change, 2026-07): the `stop`/`start`/`restart` actions, their routes, and the agent-side servicecontrol collectors are gone; the `processControl` RBAC key remains in the catalogue but gates nothing.
