# Domain model — current-state inventory tables behind Asset

Each entity below carries its CLAUDE.md definition + load-bearing invariant, followed (in the **Schema** and **Notes** parts) by the field-level schema dump and the extended notes that lived in the skill references (formerly ARCHITECTURE.md). `prisma/schema.prisma` is the source of truth for types; these are the semantics.

## Definitions and invariants

- **AssetSdwanRule** — current-state SD-WAN service rules (one row per `(asset, ruleName)`), delete-replaced per scrape by `persistSdwanRules`. FortiOS only, gated by `config.pullSdwan`. Not a hypertable, not a retention entity — no history.

- **AssetProcess** — current-state process inventory (one row per `(asset, name)` program, aggregated across PIDs), delete-replaced per scrape by `persistAssetProcesses`. Operator pins live on `Asset.monitoredProcesses` (telemetry + logs) and `Asset.mappedProcesses` (Application Map).

- **AssetService** — current-state service inventory (one row per `(asset, unit)` systemd unit / Windows service), delete-replaced by `persistAssetServices`. The **unit-centric sibling** of `AssetProcess`: a service running as a shared runtime is visible as itself, and exited oneshot units still appear. Agent-only. Read-only — service control was removed in the Satellite-posture change.

- **VcenterDatastore** — current-state vCenter datastore inventory (one row per `(integration, datastore MoRef)`), delete-replaced per discovery run by `syncVcenterDevices`. `Asset.virtualization` is the per-asset counterpart (role-discriminated vm/host blob, single writer).

- **AssetInterface** — **current-state** interface inventory (one row per `(asset, ifName)`, plain table with a real FK), delete-replaced per FULL system-info scrape by `persistInterfaces`. Exists because every all-interface consumer wants current state, not history. It also backs the device-filter condition tree's **`interfaceName`** ("Device interface") field — "switches that have a fortilink port" — which is the FIRST condition field reading a relation (`AssetApVap.ssid` — "Broadcast SSID" — is the second), so a fleet-scale filter resolves it in SQL via `scopeRelationIndex` rather than joining it onto a per-tick asset read, and deliberately reads the FULL inventory rather than the pinned subset every interface TRIGGER is limited to (a trigger needs a metric, this asks what the device has). **Single-writer cadence is load-bearing**: only the full pass and the agent push may write it — never `recordFastFilteredResult`, which sees only pinned interfaces. Both callers **skip an empty list rather than wiping**, because empty is ambiguous. One carve-out: a **FortiLink trunk interface** (named for its peer's serial) leaves the ifTable while the link is down, so a dropped row whose name resolves to a still-active peer switch whose own inventory reciprocates is **preserved and marked down** rather than deleted — deleting it made a downed trunk vanish from the System tab, the pin picker and the alert dimension at the moment its down alert fired (`resolvePreservedTrunkNames`). Switch-port VLANs come from SNMP first, the controller CMDB second. It is also the **identity of record for interface names**: the SNMP collectors name a port `ifName` with an `ifDescr` fallback, and on a FortiSwitch `ifDescr` is the operator's port DESCRIPTION — so a tick whose `ifName` walk failed renamed `port9` to `MORGAN-221E-1`, the AP plugged into it, and that name became an identity in the inventory, the pin list, the sample table and the alert dimension (prod 2026-08-25). Every writer therefore reconciles collected names through `loadInterfaceIdentity` + `utils/interfaceIdentity.ts` first: a real `ifName` wins, a label two ports claim resolves to nothing, an unknown name passes through, and `repairInterfacePins` rewrites a pin that names a description onto the port.

- **AssetInterfaceOverride** — operator-typed Interface Comments override. Polaris-local by default; description-synced to the device when the integration's `syncDescriptions` is on, carrying per-row sync state. See business rule 14.

- **AssetMacTableEntry** — the switch's layer-2 forwarding database (CAM table), from Q-BRIDGE-MIB with a BRIDGE-MIB fallback. Current-state, delete-replaced per scrape by `persistMacTable`. **The MAC is not always in the INDEX** — `resolveFdbIdentity` reads the address COLUMN first, because a FortiSwitch indexes the table by row number. A table that answered but decoded to zero rows returns `undefined` (preserve), never `[]` (wipe). Feeds MAC-derived topology inference; **display-only — it writes no LLDP neighbour and no dependency edge.**

- **AssetArpEntry** — the FortiGate's layer-3 neighbour cache, one row per `(IP, MAC, interface)` binding — the L3 sibling of `AssetMacTableEntry`. **Accumulate + age**, not delete-replace, which is what makes its two writers (the monitor system-info pass and discovery Phase 7.5b) safe. `ifName` is `""`, never NULL — it is part of the business key and Postgres treats NULLs as distinct. `matchedAssetId` is MAC-only. History is an interval, not a timeline.

- **AssetTrunkMember** — FortiSwitch trunk → local physical port, from the `fsTrunkMember` SNMP scalar (`1.3.6.1.4.1.12356.106.3.1.0`). The trunk name is the **peer serial left-truncated to 15 characters** on a trunk the switch auto-created, so matching is a SUFFIX test (`matchTrunkPeer`), never a reconstruction; an ambiguous tail resolves to NULL rather than a guess. **A trunk name is a parent/member edge always and a peer identity only sometimes** — the same scalar carries the operator's hand-configured LAGs, named for whatever is plugged into them (`Storage Node 2`, `_FlInK1_ICL0_`) — so a tail that isn't serial-SHAPED (alphanumeric, ≥10 chars) never reaches the peer lookup at all. Delete-replaced per scrape; covers the FortiLink links LLDP does not republish. **It is also the only source of the trunk/member relationship on a directly-polled switch**, so the same scrape overlays it onto the interface list (`ifParent` + `ifType="aggregate"`, `trunkMemberMap` → `overlayFortiswitchTrunkMembers`) — the ifTable publishes no aggregation of its own, and the controller-CMDB overlay that used to be the only writer of that edge reaches only switches with a resolvable controller.

- **AssetPhysicalEntity** — field-replaceable hardware inventory from ENTITY-MIB (transceivers, PSUs, fan trays with serial + model for an RMA). Current-state, delete-replaced per scrape, plain table with a real FK. `firstSeen` survives a re-scrape and resets on a serial change, i.e. on a swap. `ifName` is on the model but **deliberately never populated** — correlating by index is right often enough to look correct and silently wrong the rest of the time.

- **AssetLldpNeighbor / AssetWirelessStation** — current-state tables refreshed per scrape. **`localIfName` is a JOIN KEY, not a caption** — the System tab's Neighbor column, the alert email's LLDP block and auto-monitor's By-LLDP rule all look interfaces up by it, so `persistLldpNeighbors` canonicalizes it through the `AssetInterface` identity: LLDP-MIB hands over whatever `lldpLocPortId` / `lldpLocPortDesc` say, which on a FortiSwitch is the port DESCRIPTION (rows arrived keyed `MORGAN-221E-1` and `Tim Smith` instead of port9 and port12, duplicating one neighbour under two names and teaching By-LLDP to pin a port that doesn't exist). A stored row whose label resolves to a different port is a duplicate by construction, so it is deleted immediately rather than waiting out the 48h stickiness window. **That 48h grace is a DISPLAY contract, and a dependency edge is not display** — it decides whether an alert is suppressed, so `recomputeDependencyTree` filters these rows through `filterFreshLldpRows` (kept if refreshed within 6h OR carrying the newest `lastSeen` for its (asset, source) — the second arm keeps slow-cadence installs whole, `lldpIntervalSeconds` being settable to 24h). Tight on purpose, because the failure directions are asymmetric: under all-down semantics a SPURIOUS parent breaks suppression outright (an extra parent that is up keeps the child alerting as plain Down when its real upstream dies), while a MISSING LLDP parent is usually covered by the same asset's `controller` and `interface` edges. A row orphaned under a retired `localIfName` can never be superseded — the supersede check is keyed on that name — so it rides out the full 48h carrying whatever `matchedAssetId` it was written with; one written while two FortiGates shared a management address gave a switch a second, wrong parent (prod 2026-09-03).

- **AssetApRadio / AssetApVap** — a FortiAP's radios and the SSIDs each one broadcasts: the two levels ABOVE `AssetWirelessStation`, so the Stations tab renders as radio → SSID → station. Current-state, delete-replaced per scrape, plain tables with real FKs. **Two writers carrying COMPLEMENTARY columns** — the controller's `wifi/managed_ap` `radio[]` array (source `fortios`, written by discovery, which is what reaches the many APs with SNMP disabled) and the AP's own `fapRadioTable` + `fapVapTable` (source `snmp`, walked on the SNMP system-info pass; the only source for the CONFIGURED and MAXIMUM tx power, the radio mode and the country) — so the write **merges per column**: a null from a source that doesn't collect a column never erases the other's value, at the cost that a column can't be cleared back to null by a scrape (which is why nothing fluctuating is stored here). Radio IDENTITY is not merged — a `radioIndex` absent from a scrape is deleted along with its VAPs, which hang off `(assetId, radioIndex)` with no FK of their own. A VAP's identity is `vapName`, never the SSID (several VAPs commonly share one) and never the BSSID (absent on some sources) — but the two sources disagree on the NAME (FortiOS publishes the VAP object's, the MIB only the SSID), so a write matches on **BSSID first** and treats the name as an attribute of the matched row, or each source would insert its own row and delete the other's every pass; `bssid` is instead the join key down to `AssetWirelessStation.bssid`. `ssid` additionally backs the device filter's **"Broadcast SSID"** condition field — the SECOND relation-backed field, resolved through the same `scopeRelationIndex` prefetch as `interfaceName` and offered from the same monitored-only picker. Tx power is stored as each source states it and never normalized: `txPowerPct` is the controller's PERCENTAGE of the radio's ceiling, while `txPowerConfig` / `txPowerOper` / `txPowerMax` are the MIB's bare integers — that module carries **no `UNITS` clause**, so they are rendered without one rather than labelled dBm on a guess, and converting between the two would need a per-model ceiling Polaris doesn't have. The MIB publishes no MINIMUM; what it has is the CONFIGURED value, and the gap between it and the operating value is what DARRP did.

- **AssetProcessConnection** — **accumulate + age** socket facts (listening ports / outbound / inbound peers) for MAPPED processes and units. Plain table with a real FK; rows upsert on the business key behind a churn gate and age out on the `appMapConnections` retention window. `unit` is attribute-only and **backfill-only on conflict**. Unmapping deletes matching rows immediately.

- **AssetMclagPeer** — current-state MCLAG ICL peers (one row per local `mclag-icl-port`), delete-replaced per scrape by `persistMclagPeers`. `peerSn` is the canonical pairing key and resolves to `matchedAssetId`.

AssetInterface                  -- CURRENT-STATE interface inventory: one row per (assetId, ifName), full-replaced per FULL system-info scrape by `persistInterfaces` / `persistInterfaceRows` (services/interfaceInventoryService.ts — the AssetPhysicalEntity / AssetMacTableEntry delete-replace pattern). Plain table with a real FK to Asset; the no-FK rule is hypertables-only and this deliberately is not one. Columns mirror the 22 the System tab renders (adminStatus, operStatus, speedBps, ipAddress, macAddress, in/outOctets, in/outErrors, ifType, ifParent, vlanId, nativeVlan, taggedVlans, trunksAllVlans, alias, description, addressingMode, poeStatus, poeClass) plus firstSeen/lastSeen. **The three switch-port VLAN columns have two sources, in precedence order.** SNMP Q-BRIDGE-MIB fills nativeVlan/taggedVlans on every switch-class asset (`collectPortVlansSnmp` → `utils/portVlans.ts`, walked beside the forwarding database and sharing its dot1dBasePortIfIndex join via `collectBasePortIfNames`); the parent FortiGate's managed-switch CMDB then overlays on top where it can reach (`overlayFortiswitchCmdbOntoSnmp`), because it is config truth and the only source that can express `allowed-vlans all` (trunksAllVlans, which SNMP cannot represent — a q-bridge trunk just enumerates). That overlay writes only where the CMDB actually says something: a port it lists with no native VLAN and no allow-list leaves the SNMP-derived values standing, since "the CMDB disagrees" and "the CMDB is silent about this port" are different claims. Exists because every all-interface consumer wants CURRENT STATE, not history: the System tab renders exactly one timestamp, and topology inference / auto-monitor's pin candidate list / FortiAP lan1↔eth0 name normalization all want "latest row per (assetId, ifName)" — which against the hypertable is a DISTINCT ON that had to be time-bounded after being measured at 13.5 min / 90M rows / 9 GB I/O on prod (see interfaceTopologyService). It is what lets AssetInterfaceSample carry ONLY operator-pinned interfaces. **SINGLE WRITER CADENCE (load-bearing):** only the full system-info pass and the Polaris Agent push write here — never `recordFastFilteredResult`, which sees only the pinned subset (so a per-asset delete-replace from it would wipe every unpinned row each probe tick) and writes ifType/ifParent/vlanId as NULL (the exact topology-column loss this table exists to prevent). Both writers SKIP an empty interface list rather than wiping: unlike LLDP, empty is ambiguous — a FortiOS token without monitor scope answers 200 OK with empty results, and the pre-existing lastSystemInfoAt guard already treats that as "preserve rather than display nothing while the device is online". firstSeen survives a re-scrape while the interface is present and resets when a name disappears and returns; capped at 2000 rows/asset with a loud truncation warn (a hidden port is invisible in the pin picker, which is the only way to start collecting its history). Not a retention entity and not pruned — current state, not a time series.

AssetLldpNeighbor               -- Current-state LLDP neighbor table per (asset, local interface). Refreshed on every system-info pass that successfully queried LLDP — FortiOS `/api/v2/monitor/system/interface/lldp-neighbors` for fortimanager/fortigate-monitored assets, SNMP LLDP-MIB walk (`lldpRemTable` + `lldpLocPortTable` + `lldpRemManAddrTable`) for SNMP-monitored assets. Managed FortiAPs get their rows a third way: the parent FortiGate's `/api/v2/monitor/wifi/managed_ap` row carries the AP's full `lldp` table, which FMG/FortiGate discovery parses (`parseApLldpNeighbors` in `utils/fortiapLldp.ts`) and persists per online AP per discovery run via `monitoringService.persistManagedApLldpNeighbors` (source `"managed-ap"`) — the agentless LLDP streams can't reach an AP directly (rest_api targets the asset's own IP with a FortiOS endpoint APs don't serve; SNMP LLDP-MIB on the AP is usually disabled). The wrapper normalizes AP-local port names against the AP's recent interface samples (lan1 ↔ eth0, `utils/fortiapInterfaceAlias.ts`) and SKIPS only when a monitored AP's resolved `lldpPolling` is `snmp` AND that stream is actually delivering (rows from another writer refreshed within the 48h stickiness window) — a live SNMP stream owns the table (two full-replace writers would alternate row sets), but a configured-yet-dead one (FortiAPs usually don't expose LLDP-MIB) must not leave the table empty forever. The sync layer's `apOnline` presence gate uses `isFortiapStatusOnline` (`utils/fortiapMonitorRow.ts`) which accepts both `"online"` (the common FortiOS value) and `"connected"` (firmware variant), matching the controller-status probe's accept set. An absent `lldp` array on the managed_ap row (firmware variance) means "unknown" — the sync layer doesn't call the persist, so existing rows survive; an empty array is a real "no neighbors" scrape. `firstSeen` survives across persists; `lastSeen` is bumped on every refresh. **Stickiness rule**: a row that's missing from a fresh scrape is dropped only when (a) the same local port just observed a DIFFERENT neighbor (real topology change — supersede immediately) or (b) the row's `lastSeen` is older than 48 hours (truly stale). Within 48h with no fresh neighbor on that port the row is preserved — LLDP advertisements get missed intermittently (packet drops, peer reboots, brief unplugs), and a hard "delete on every miss" rule made the Neighbor column flap empty for those gaps. **That window is a DISPLAY contract, and a reader that treats a row as physical-cable evidence must bound it tighter itself** — a sticky row outlives its cable by up to two days after a re-patch, which is exactly how the Device Map's member expansion drew one cable as two parallel lines (it now skips rows older than its own 1h cutoff; see `GET /map/sites/:id/topology`). `matchedAssetId` is resolved at persist time by joining each neighbor against the asset inventory across four match arms in priority order: management IP, chassis MAC (chassisIdSubtype=macAddress), port MAC (portIdSubtype=macAddress — workstation LLDP agents commonly put the Ethernet MAC there rather than in chassisId), system name (case-insensitive hostname with FQDN/short-form fallback), and chassisId-as-hostname (when chassisIdSubtype is not macAddress and the value looks like a printable hostname — covers LLDP implementations that leave systemName empty and put the hostname in chassisId with subtype local(7) or chassisComponent(1)). The FK uses `SetNull` on delete so removing the matched asset just clears the back-pointer. `source` is `"fortios"`, `"snmp"`, or `"managed-ap"`. **FortiLink exclusion**: when the owning integration's `config.excludeFortilinkLldp` is on (default off; both `FortiManagerConfigSchema` + `FortiGateConfigSchema`), the system-info dispatch drops neighbors learned on FortiLink-enabled interfaces (the fortilink-flagged aggregate + its member ports) before persist, so internal FortiGate↔FortiSwitch links stay out of the Neighbor column. The set is authoritative from the FortiGate CMDB `fortilink` flag (`fortilinkInterfaceNamesFromCmdb`): the REST-interfaces path reuses the CMDB it already fetched (`SystemInfoSample.fortilinkInterfaces`), the SNMP-interfaces path makes one gated CMDB call (`fetchFortilinkInterfaceSet`) only when the toggle is on. FortiGate firewalls only; peer-inferred FortiLink rows are unaffected (synthesized from topology, not LLDP). The collector signals "unsupported transport" by leaving `lldpNeighbors` undefined in the SystemInfoSample (so the persist layer leaves stored rows alone); an empty array signals "queried successfully, no neighbors" → wipe. Capabilities are decoded from LLDP-MIB `lldpRemSysCapEnabled` (8 defined IEEE 802.1AB capability bits) into tokens like `"bridge"` / `"router"` / `"wlan-access-point"` matching FortiOS naming. Read by `GET /assets/:id/system-info` (full set with matched-asset cross-link), `GET /assets/:id/interface-history?ifName=...` (just the neighbors on that interface), and `GET /map/sites/:id/topology` (drives the dashed orange "LLDP edges" + ghost neighbor nodes for non-Polaris devices in the Device Map graph). Pruned alongside the other system-info tables on the daily cycle, but retention rarely matters in practice — the per-scrape full-replace already removes neighbors that have gone away.

AssetApRadio                    -- Current-state table of a FortiAP's RADIOS — the parent level of the Stations tab's radio -> SSID -> station tree, and the answer to "what channel, how wide, at what power". Plain table (asset_ap_radios), real FK, NOT a hypertable: nobody wants a timeline of what channel a radio was on, they want the one it is on. TWO WRITERS carrying COMPLEMENTARY columns — the controller's `/api/v2/monitor/wifi/managed_ap` `radio[]` array (source "fortios", written by `discoveryEngine`'s FortiAP loop via `apRadioService.persistApRadioInventory`, which reaches every managed AP INCLUDING the ones with SNMP disabled) and the AP's own FORTINET-FORTIAP-MIB `fapRadioTable` + `fapVapTable` (source "snmp", walked on the SNMP system-info pass by `collectApRadiosSnmp`; the only source for the CONFIGURED and MAXIMUM tx power, the radio mode and the per-radio country). NOT a hypertable and NOT a retention entity — no history/timeline (dropped 2026-06; the SD-WAN SLA-metrics stream `AssetPerfSlaSample` remains the only SD-WAN time-series). **Delete-replace means a reader arriving LATE sees only the present**, which is why an SD-WAN failover alert carries the member it left on the Notification itself (`alertChartService.chartKeysForChangeEvent` stamps `"<ruleName>|<member>"` from the Event's details): by the time the email is composed this table says only where the traffic went, so a chart resolved from it alone draws the healthy link.

#### AssetProcess

**AssetProcess** — CURRENT-STATE process inventory (one row per `(asset, name)` program, aggregated across PIDs; plain table `asset_processes`, NOT a hypertable), replaced in full per scrape by `persistAssetProcesses` — same delete-replace pattern as `AssetSdwanRule`. Carries `instanceCount` + summed `cpuPct`/`memRssBytes` snapshot + `exePath`/`username`/`startedAt` + `serviceUnit`/`controllable` (Phase 4 control). Drives the merged asset **Services** tab's *Include processes* view (`GET /assets/:id/processes`) — the Processes tab was folded into Services 2026-07. Operator pins live on `Asset.monitoredProcesses` (per-minute CPU/RAM telemetry + log tailing — Feature C) and `Asset.alertWatchedProcesses` (flagged for future alerting; storage-only — no longer surfaced in the tab, alerting moved to Automations). The per-pinned-program time-series + logs are `AssetProcessSample` (hypertable + rollups) / `AssetProcessLogSample` (standalone hypertable); per-program log config is `AssetProcessConfig`; operator-defined log-flag rules (read-time eval over the log viewer) are `LogFlagRule` (CRUD at `/api/v1/log-flag-rules`).

#### AssetService

**AssetService** — CURRENT-STATE service inventory (one row per `(asset, unit)` systemd unit / Windows service; plain table `asset_services`, NOT a hypertable), replaced in full per scrape by `persistAssetServices` (`serviceInventoryService.ts`) — same delete-replace pattern as `AssetProcess`/`AssetSdwanRule`. The **unit-centric** sibling of `AssetProcess` (keyed by unit, not backing program): a service running as a shared runtime (e.g. a Spring Boot app as `java`) is visible as itself, and oneshot/exited units with no live process still appear. Carries `platform` (systemd/windows) + `displayName`/`loadState`/`activeState`/`subState`/`enabledState` + `mainPid`/`mainProcess` (cross-link to Processes) + `memBytes` + `controllable` (derived: systemd loaded/non-masked or any Windows service). Agent-only (`serviceInventory` stream; agentless SSH/WinRM doesn't resolve units). Drives the merged asset **Services** tab (`GET /assets/:id/services`; the tab shows units by default and folds the process inventory in via an *Include processes* checkbox) — read-only (Start/Stop/Restart control was removed in the Satellite-posture change). Operator pins live on `Asset.monitoredServices` (per-unit journalctl tailing → `AssetServiceLogSample` via the agent `serviceLog` stream, Linux-only; surfaced in the Services detail-panel log viewer at `GET /assets/:id/service-logs`) and `Asset.mappedServices` (per-unit connection attribution — the agent stamps `AssetProcessConnection.unit` for the unit's PIDs; surfaced in the Services detail panel's Ports & Connections + filterable on the Application Map). `AssetServiceLogSample` is a standalone detail-only TimescaleDB hypertable (mirrors `AssetProcessLogSample` with `unit` for `name`).

#### VcenterDatastore

**VcenterDatastore** — CURRENT-STATE vCenter datastore inventory (one row per `(integration, datastore MoRef)`, plain table `vcenter_datastores`, NOT a hypertable), delete-replaced per discovery run by `syncVcenterDevices`. Carries capacity/free/provisioned (provisioned = capacity − free + uncommitted, SOAP-only), the mounting ESXi hosts' morefs, and `backing`/`backingLabel` (VMFS extent NAA device ids → array vendor via `vendorFromNaa`, e.g. "Pure Storage"; NFS remote host). Rendered on the ESXi-host asset's Virtualization section. `Asset.virtualization Json?` is the per-asset counterpart (fortinetTopology precedent): role-discriminated vm/host blob with VM→host link (`hostAssetId`), cluster, power state, VMware Tools state, vCPU/RAM (+ usage snapshot), per-VM disks (with datastore refs), and Tools-reported guest filesystems — single writer `syncVcenterDevices`, surfaced via `GET /assets/:id/virtualization`.

#### AssetInterface

**AssetInterface** — CURRENT-STATE interface inventory (one row per `(asset, ifName)`, plain table `asset_interfaces` with a real FK, NOT a hypertable), delete-replaced per FULL system-info scrape by `persistInterfaces` — the `AssetPhysicalEntity` / `AssetMacTableEntry` pattern. Carries the 22 fields the System tab renders (status/speed/IP/MAC/counters/ifType/ifParent/VLAN/alias/description/PoE) plus `firstSeen`/`lastSeen`. Exists because every *all-interface* consumer wants current state rather than history — the System tab reads a single timestamp, and topology inference, the auto-monitor pin picker and FortiAP `lan1`↔`eth0` normalization all want "latest row per (assetId, ifName)", which against the hypertable is a `DISTINCT ON` measured at 13.5 min / 90M rows / 9 GB I/O on prod. **Single writer cadence (load-bearing):** only the full pass and the agent push write it — never `recordFastFilteredResult`, which sees only pinned interfaces (a delete-replace from it would wipe every unpinned row per probe tick) and nulls `ifType`/`ifParent`/`vlanId`. Both callers SKIP an empty interface list rather than wiping, because empty is ambiguous (a FortiOS token without monitor scope answers 200 OK with empty results). **FortiLink trunk rows survive the replace while both ends vouch for them:** FortiSwitchOS removes a trunk aggregate — named after the PEER's serial, the `AssetTrunkMember` convention — from the ifTable entirely while the link is down, so to the delete-replace a downed inter-switch trunk looked identical to a port that never existed and vanished from the System tab, the pin picker and the alert dimension at exactly the moment its down alert fired. `resolvePreservedTrunkNames` therefore keeps a dropped row, marked `operStatus="down"` (lastSeen deliberately stays at the last real sighting), when its name suffix-resolves (`trunkPeerNameTail` + `matchTrunkPeer`, ambiguity refuses) to exactly one OTHER active/maintenance asset whose own inventory carries a reciprocal trunk row naming this asset's serial. Reciprocity stays satisfied through the outage because preserved rows remain in the table — whichever side scrapes first still sees the other's row, then each side's preserved row satisfies the other's check; decommissioning either switch (or unpairing them) breaks a condition and the row ages out on the next full scrape. A preserved row also keeps `firstSeen` across the outage, since it never left the table. Capped at 2000 rows/asset with a loud warn; not a retention entity and never pruned. **The switch-port VLAN columns come from SNMP first, the controller CMDB second.** Q-BRIDGE-MIB fills `nativeVlan`/`taggedVlans` on every switch-class asset (`collectPortVlansSnmp` → `utils/portVlans.ts`), and the parent FortiGate's managed-switch CMDB overlays on top where it can reach — it is config truth and the only source that can say `allowed-vlans all` (`trunksAllVlans`, which q-bridge cannot express). Two decisions carry that: `dot1qVlanStaticUntaggedPorts` is believed only when it is a STRICT SUBSET of the egress bitmap, because FortiSwitch publishes it as a verbatim copy and the RFC egress-minus-untagged subtraction against a copy reports every trunk as carrying nothing; and the CMDB overlay writes only where it has a value, so a port the controller is silent about keeps what SNMP found.

#### AssetInterfaceOverride

**AssetInterfaceOverride** — operator-typed Interface Comments override. Polaris-local by default; when the originating integration's `syncDescriptions` toggle is on it is description-synced to the device (FortiGate `system/interface` description / FortiSwitch port description, Polaris-primary) and carries per-row sync state (`syncStatus` ∈ synced/failed — `conflict` only on legacy rows from the retired newest-wins engine, `lastSyncAt`, `syncError`, `syncedValue` = last synced value). See business rule 14.

#### AssetMacTableEntry

**AssetMacTableEntry** — the switch's layer-2 forwarding database (CAM table), from Q-BRIDGE-MIB `dot1qTpFdbTable` (RFC 4363, VLAN-aware — preferred) with a BRIDGE-MIB `dot1dTpFdbTable` fallback (RFC 4188, no VLAN dimension, hence `vlanId` NULL rather than a guess). Current-state, delete-replaced per scrape by `persistMacTable` — an FDB entry ages out on the switch in minutes, so history would answer a question the switch itself can't. **Both source tables report a `dot1dBasePort`, NOT an ifIndex**: the join runs through `dot1dBasePortIfIndex` then the scrape's ifIndex→ifName map, and unlike the PoE correlation this join is defined by the MIB and reliable. **And the MAC is not always in the INDEX**: the RFCs index both tables by the address, but agents in the field don't all honour it — a FortiSwitch indexes `dot1dTpFdbTable` by a plain ROW NUMBER (`…17.4.3.1.3.1`, `.2`, `.3`) and publishes the MAC only in the `dot1dTpFdbAddress` COLUMN, so an index-only decode drops every row on the very devices this table exists for (prod 2026-08). `resolveFdbIdentity` therefore reads the address column FIRST and falls back to the index — which is also right for the conformant case, since Q-BRIDGE's `dot1qTpFdbAddress` is an index object and typically not-accessible, so that walk answers nothing and the index decode runs unchanged. The VLAN still comes from the index, the only place Q-BRIDGE carries it. `basePort` is stored alongside `ifName` so a row whose join failed stays identifiable instead of appearing to belong to no port — and the MAC Table tab — which groups INTERFACE-FIRST, one expandable row per port with its MACs nested under it and the per-port count on the header line — **hides those rows by default** behind a count + Show toggle, since a FortiSwitch trunk/LAG pseudo-port (base port 32768 and up) publishes no `dot1dBasePortIfIndex` row, so every MAC behind the trunk lands there unattributable and swamps the real per-port entries. Hidden, never dropped: they are legitimate sightings that just can't be placed on a port. `status` keeps the RFC distinction — only `learned` is a real endpoint sighting, `self` is the reporting bridge's OWN address — useful only to exclude it from endpoint counts, NOT a peer signal (a peer switch appears in this table as a `learned` entry on the port facing it) — and `invalid` (an aged-out entry the agent hasn't reaped) is dropped at collection. `matchedAssetId` resolves through the SAME cached MAC index LLDP matching uses, because a per-row lookup would dominate the write at a few thousand rows per switch. Capped at 4000 rows per asset with a **loud** truncation warning — a partial table makes the per-port MAC counts, and any uplink inference drawn from them, quietly wrong. Collected SNMP-only on the system-info (heavy) cadence and gated to `assetType="switch"`; `undefined` preserves stored rows, `[]` wipes — so a table that ANSWERED but decoded to zero rows returns `undefined` (a read failure is not an empty forwarding database) and warns with `undecodable`/`unusableStatus` counts, because that silence is exactly what made the index-shape mismatch above read as a switch with nothing plugged into it. Surfaced at `GET /assets/:id/mac-table` (`assets:read`, returns entries + per-port learned-MAC counts) and the asset-details **MAC Table** tab. Also feeds **MAC-derived topology inference**: `peerInferredLldpService` emits `source:"mac-inferred"` neighbours for ports with exactly ONE learned asset-matched MAC (`inferDirectAttachments`), merged read-time into the Device Map + interface slide-over alongside the existing `peer-inferred` rows — so inference is no longer LLDP-only. **Display-only by design: nothing writes `AssetLldpNeighbor` and nothing writes `AssetDependencyParent`**, because dependency edges drive all-down suppression and a wrong edge silences real alerts; edge-writing waits on bidirectional confirmation validated against a real fleet. A multi-MAC port infers nothing (an uplink's data says "a switch with a network behind it", not which device the port IS).

#### AssetArpEntry

**AssetArpEntry** — the FortiGate's layer-3 neighbour cache, one row per `(IP, MAC, interface)` binding. The **L3 sibling of `AssetMacTableEntry`**: that table answers "what is plugged into port 7" from a switch's forwarding database, this one answers "what is at 10.4.12.63" from the router's own resolution of the address. **Accumulate + age** (the `AssetProcessConnection` pattern), NOT delete-replace: a binding still present has its `lastSeen` bumped, `firstSeen` survives, and rows age out on the flat **`arpEntries`** retention window (Server Settings → Retention, default 30 days). That is what lets the tab's range selector — Current / 1h / 12h / 24h / 7d / 30d — answer "who was at this address last Tuesday" at ONE row per distinct binding instead of one per poll; a snapshot table would be ~52M rows/month across a 40-gate fleet at the 600 s cadence. History is therefore an **interval, not a timeline**: a MAC that flips away and back between two polls is invisible, and a binding recurring after a gap collapses into one row spanning it. Plain table with real FKs, not a hypertable. **`ifName` is `""`, never NULL**, for a row the device attributed to no interface — it is part of the business key, and Postgres treats NULLs as DISTINCT in a unique index, so a nullable column would insert a fresh duplicate every poll for exactly those rows; the route maps `""` back to null on the way out. **TWO WRITERS, which accumulate makes safe** (a partial view bumps what it saw and touches nothing else — under delete-replace the pair would wipe each other): (1) the **monitor system-info pass** (`systemInfoIntervalSeconds`, 600 s default) for monitored firewalls, over **FortiOS REST** (`/api/v2/monitor/network/arp`, `includeArp`) or **IP-MIB SNMP** (`collectArpNeighborsSnmp`) per the resolved polling method — the SNMP half additionally carries **IPv6 NDP** entries and a real per-entry age from `ipNetToPhysicalLastUpdated`, neither of which the REST endpoint exposes; and (2) **discovery Phase 7.5b** (`pollInterval`, 12 h default for both Fortinet types), which covers gates that are unmonitored or have system info off and costs nothing extra, because those rows are already read for the Phase 7.6 `Reservation.lastSeenArp` presence stamp (business rule 17) and Phase 7.7 placeholder-MAC adoption (business rule 26). Neither writer can express "the cache is empty" — nothing is ever wiped by a poll, only aged out by retention — so discovery's delete-replace scoping (`arpQueriedDevices`, the per-device `didArpQuery` flag) now only decides which gates get *recorded*, not which get cleared. **The gate resolves name → serial → assetId** (the run's own `DiscoveredDevice` list, then the `fortigate-firewall` `AssetSource` row whose externalId IS the serial), never through the hostname — the mismatch `utils/fortinetParentKey.ts` exists to prevent. **`matchedAssetId` is MAC-only** and is filled in but never cleared (`COALESCE` in the upsert), since the monitor pass has no warm asset index while discovery does: joining on the IP as well would attribute the row to the very asset it disproves, an ARP entry asserting that address belongs to that MAC being exactly the evidence that an asset still carrying it under a different MAC is stale. Pure shaping in `utils/arpTable.ts` (normalize, fold an empty interface, dedupe on `(ip, mac, ifName)` keeping the **freshest** row, order interface-then-numeric-IP, cap 4000/asset with a **loud** warn); pure SNMP decoding in `utils/arpNeighbors.ts` (RFC 4001 length-prefixed index, `invalid`/`incomplete` rows dropped). Two MACs claiming one IP are deliberately kept as two rows — a duplicate-address finding, not a dedupe. Surfaced at `GET /assets/:id/arp-table?range=` and the asset-details **ARP Table** tab (firewall-class only), which states the device's actual cadence and warns that short-lived entries can be missing entirely.

#### AssetTrunkMember

**AssetTrunkMember** — FortiSwitch trunk → local physical port, from the `fsTrunkMember` OctetString at `1.3.6.1.4.1.12356.106.3.1.0` (a SCALAR, hence the trailing `.0`). The trunk name is built from the PEER's serial number, so this is the switch stating its own adjacencies over SNMP rather than leaving them to be inferred — and it covers exactly the FortiLink switch↔switch and switch↔FortiGate links LLDP does not republish in managed mode. Current-state, delete-replaced per scrape by `persistTrunkMembers` (the `AssetLldpNeighbor` / `AssetMclagPeer` pattern; shape deliberately close to MCLAG, both being "local port faces peer device, keyed by serial"). **The name is the peer serial left-truncated to 15 characters**, with `-0` on a switch trunk eating two of them — which is why a switch appears to lose three leading characters and a FortiGate only one. Matching is therefore a SUFFIX test (`matchTrunkPeer` in `utils/fortiswitchTrunkMap.ts`), never a reconstruction: rebuilding the serial would hard-code a cap a firmware release could change. An ambiguous tail (two serials sharing it) resolves to NULL rather than to a guess, and so does one that is not serial-SHAPED: only the trunks the switch auto-creates are named for a peer, while the operator's hand-configured LAGs ride the same scalar named for whatever is plugged into them (`Storage Node 2`, `APPHOST01`, `_FlInK1_ICL0_`), so `isPeerSerialTail` (alphanumeric, ≥10 chars) gates the lookup — those rows are still a real trunk/member edge, they just name no peer. The OID was read one level too deep (`…106.3.1.1.0`) until 2026-08-28, which answers noSuchObject: a scalar GET resolves an error varbind to null, and null is the same "device does not publish this" signal a non-Fortinet switch produces, so the whole trunk half of the scrape was silently absent on every switch. Feeds `peerInferredLldpService` as `source:"trunk-mapped"` — named for being device-STATED, not inferred, unlike its `peer-inferred` and `mac-inferred` siblings. Collected SNMP-only on the system-info cadence, gated to `assetType="switch"`; `undefined` preserves stored rows, `[]` wipes. **The same read is the only source of the trunk/member edge on a directly-polled switch**, so the scrape does not just persist these rows — it regroups them (`trunkMemberMap`) and runs the shared `overlayFortiswitchTrunkMembers` against the interface list, stamping `ifParent` on each member and `ifType="aggregate"` on the trunk. Without that the System tab listed a trunk and its member ports as unrelated flat rows on every switch outside the controller-CMDB overlay's reach (which needs a resolvable `controllerFortigate`), because IF-MIB itself publishes no aggregation.

#### AssetPhysicalEntity

**AssetPhysicalEntity** — field-replaceable hardware inventory from ENTITY-MIB (RFC 4133) `entPhysicalTable`: transceivers, PSUs and fan trays with the vendor / model / serial / hardware-rev an operator needs to raise an RMA or find the spare. Current-state, delete-replaced per scrape by `persistPhysicalEntities` (the `AssetLldpNeighbor` / `AssetMclagPeer` pattern), plain table with a real FK to Asset — the no-FK rule is hypertables-only, and this deliberately is not one: inventory changes on a maintenance window, not a cadence. Scoped by `entityPhysicalIsInventory` to rows the device flags `entPhysicalIsFRU`, else module/powerSupply/fan rows carrying a serial or model — a chassis publishes a row per container, port and sensor, hundreds of them naming nothing replaceable. Capped at 500 rows per asset with a **loud** truncation log. `firstSeen` survives a re-scrape for a module still in place (so "this SFP has been in this port since March" holds) and resets when the serial in that slot changes, i.e. on a swap. SNMP heavy cadence only; `undefined` from a transport that can't supply it preserves stored rows, `[]` wipes — the LLDP contract. `ifName` is present on the model but **deliberately never populated**: correlating a module to an interface by entPhysicalIndex == ifIndex is the same equivalence the FortiSwitch sensor annotation was reverted for (97e54fd2), right often enough to look correct and silently wrong the rest of the time. The honest chain is entPhysicalContainedIn → entAliasMappingIdentifier (RFC 4133), which needs a real switch to validate against; the column waits for it.

#### AssetProcessConnection

**AssetProcessConnection** — ACCUMULATE + AGE socket facts (listening ports / outbound connections / inbound peers) for MAPPED processes (`Asset.mappedProcesses`, the Processes-tab "Map" toggle — independent of `monitoredProcesses`). Plain table with a real FK to Asset (not a hypertable); rows upsert on the business key via `persistProcessConnections` (batched `INSERT … ON CONFLICT` bumping `lastSeen` behind a 5-minute churn gate, `firstSeen` kept; per-(process,kind) caps 200/500/200) and age out on the flat `appMapConnections` retention window (Server Settings → Retention; `POLARIS_PROCESS_CONN_RETENTION_DAYS` is now only its default seed). Collected per-minute for mapped processes ONLY (never full-host collect-then-filter): agent stream `processConnections` (gopsutil `net.Connections`, direction heuristic on-agent — local port ∈ own listen set ⇒ inbound, ephemeral ports never stored) or the agentless ssh/winrm `processes` cadence. Also carries `unit` (Phase 3, attribute-only, not in the business key, **backfill-only on conflict** — an empty stored value adopts the incoming unit, a non-empty one is never overwritten): the owning systemd unit / Windows service resolved from the PID's cgroup, so rows can be attributed to a UNIT — the agent additionally collects connections for PIDs whose unit is in `Asset.mappedServices` (Services-tab "Map"). Unmapping a process (by name) OR a unit deletes the matching rows immediately. Drives the **Application Map** page + the process detail panel's Ports & Connections section + the Services detail panel's (via `GET /assets/:id/process-connections?unit=`).

#### AssetMclagPeer

**AssetMclagPeer** — current-state MCLAG ICL peers (one row per local `mclag-icl-port` on a FortiSwitch), full-replaced per scrape by `persistMclagPeers` (delete-replace, plain table — same pattern as `AssetLldpNeighbor`/`AssetSdwanRule`). Parsed from the parent FortiGate's `switch-controller/managed-switch` CMDB; `peerSn` (the canonical pairing key) resolves to `matchedAssetId`. Drives the asset-detail "MCLAG Peer" General-tab row + the Device Map sibling ICL edge (`mclagEdges`). FortiManager + standalone FortiGate (shared `fetchFortiswitchControllerPortsCmdb`).
