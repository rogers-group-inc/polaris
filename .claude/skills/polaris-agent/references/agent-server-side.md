# Polaris Agent — server side (polling method, API surface, install, build, signing, upgrade)

Verbatim from ARCHITECTURE.md → Monitoring Architecture (the agent paragraphs).
**Polaris Agent polling-method (`"agent"`).** Seventh value in the polling-method enum. Represents a Polaris-managed agent installed locally on the target host (Linux/macOS/Windows × amd64/arm64) that pushes samples back via `POST /api/v1/agents/samples` on its own schedule and holds a long-lived outbound WebSocket for on-demand probes. The four streams it produces: **response-time** measures the agent → Polaris RTT via a `/heartbeat` ping (so a TLS / firewall / DNS failure surfaces as a real packet-loss sample — not a process-local liveness noop); **telemetry** captures CPU% + memory bytes via gopsutil per-OS (Linux `/proc/stat`+`/proc/meminfo`, macOS `host_statistics`+`sysctl`, Windows `GetSystemTimes`+`GlobalMemoryStatusEx`) plus host thermal sensors when available; **interfaces** enumerates every NIC with its MAC, IP, link state, and cumulative byte+error counters via gopsutil/net merged with stdlib `net.Interfaces` for MAC/IP association; **storage** walks every local mountpoint via gopsutil/disk and skips network filesystems (NFS/SMB/AFP) by default to avoid stalls when the server is unreachable. Default cadences: 60 s response-time / 60 s telemetry / 600 s interfaces / 600 s storage — operator-overridable via `*_interval_sec` keys in `agent.conf`. A separate **system-info push** (`POST /api/v1/agents/system-info`) fires on the heartbeat cadence (default 300 s) and carries the host's identity (hostname, OS family + version + kernel, DMI manufacturer / model / serial / BIOS, primary MAC + IP, agent version itself). The server upserts an `AssetSource` row with `sourceKind = "polaris-agent"` and `externalId = managedAgent.id`, then re-projects the asset — `polaris-agent` is at the top of the projection priority for hostname / serialNumber / manufacturer / model / os / osVersion, beating AD / Entra / Intune because the agent runs ON the host and reads DMI/SMBIOS directly while inventory sources infer from elsewhere. **MAC is written inline** alongside the projection step — `primaryMac` is normalized to colon-uppercase, reconciled into `AssetMacAddress` with `source="polaris-agent"` (preserving entries from other sources), and the freshest entry becomes `Asset.macAddress`. MAC isn't owned by `projectAssetFromSources` (see "Fields the projection does NOT own"), so every discovery path including the agent writes it directly. Falls through cleanly when DMI fields are unreadable (Linux `product_serial` is often 0400 on hardened deployments; the agent's DynamicUser sees empty and AD / Intune fill in instead). Compatible source kinds: `manual`, `activedirectory`, `entraid`, `windowsserver` (anywhere we can install software via stored SSH/WinRM credentials). Explicitly NOT compatible with `fortimanager` / `fortigate` — Fortinet appliances can't run third-party binaries. When any stream resolves to `"agent"`, the periodic puller (probe + telemetry + systemInfo + fastFiltered) becomes a no-op for that stream — the agent owns its own cadence and the synthetic ticking-loop pass returns success-with-zero-write so the `polaris_probe_total{transport="agent"}` counter increments but no DB sample is created. `recordProbeResult` and the `record*Result` writers early-return on agent-mode so the agent's real pushed samples are the only signal that drives the state machine; the inbound `/api/v1/agents/samples` handler calls `recordProbeResult(..., null, { fromAgent: true })` to bypass that guard for the agent's real RTTs. Per-stream credential pickers on the asset edit modal hide when polling-method is `"agent"` — the agent's own per-asset bearer (issued at install time) is implicit.

**Polaris Agent API surface (Phase 2 — inbound + operator-facing routes).** Three inbound endpoints handle the agent runtime: `POST /api/v1/agents/enroll` is public — body carries the one-shot enrollment token plus the cert fingerprint the agent observed during its TLS handshake. The server cross-checks the pin against the value baked into the `ManagedAgent` row at install kickoff (mismatch → 400 + `agent.install_failed` event + bearer revoke), and on success atomically swaps the enrollment token for a long-lived bearer (atomic via `agentTokenService.consumeEnrollmentToken`), transitions `installStatus → "active"`, auto-enables `Asset.monitored` in the same transaction (unless the asset is decommissioned/disabled or already monitored — `shouldEnableMonitoringOnEnroll`; a post-write `recomputeMonitorOverrideForAssets` keeps `monitorOverride` consistent so the discovery sweep can't flip it back off; emits `monitor.enabled_by_agent`), and emits `agent.enrolled`. `POST /api/v1/agents/samples` (bearer-gated via `requireAgentBearer`) accepts a discriminated-union body keyed on `stream: "responseTime" | "telemetry" | "interfaces" | "storage" | "eventLog" | "processInventory" | "processTelemetry" | "processLog"` — sample rows are enqueued through `sampleWriteBuffer.enqueue*` (same 2 s batched-flush path the periodic puller uses) with `req.managedAgent.assetId` stamped server-side so a stolen bearer cannot write samples for a different asset. The probe stream additionally calls `recordProbeResult` with `fromAgent: true` to drive the five-state machine; telemetry/interfaces/storage bump the corresponding `last*At` stamps directly; the process streams persist via `persistAssetProcesses` / `enqueueProcessSamples` / `enqueueProcessLogSamples` and `eventLog` flows through `osEventLogService.ingestOsEventLog`. `GET /api/v1/agents/config` (bearer) returns the resolved cadences + which streams are agent-mode + an `ETag` so the agent can issue `If-None-Match` to short-circuit polls when nothing changed. The handler **self-heals polling-method drift on every call** — `consumeEnrollmentToken` already stamps the asset's per-stream polling columns to `"agent"` at enroll time (the seven agent-owned streams: response-time / CPU+memory / temperature / interfaces / LLDP / storage / processes — `eventLog` is deliberately excluded so it stays opt-in/OFF for PII), but assets enrolled before a given stream landed in that list, or assets where an operator manually cleared a column afterward, would otherwise inherit source defaults (ICMP / not-delivered) and the agent's pushes for that stream would be ignored by the resolver. When `/config` sees any of `responseTimePolling` / `cpuMemoryPolling` / `temperaturePolling` / `interfacesPolling` / `lldpPolling` / `storagePolling` / `processesPolling` is not `"agent"`, it re-stamps all seven in a single update, invalidates the monitor-settings cache for that scope, and writes one `monitor.polling_overridden_by_agent` Event with the prior values for audit. Idempotent — once stamped, subsequent /config polls find no drift and skip the write. **The heartbeat ETag (`computeConfigEtag`) hashes every agent-owned stream's resolved (polling, interval, timeout) plus the monitored-process pin count** — a running agent only re-fetches `/config` when this ETag changes, and the self-heal above only fires on that re-fetch, so omitting a stream from the ETag (storage / processes / eventLog were originally left out) deadlocks that stream's collection on already-running agents until a restart. `POST /api/v1/agents/heartbeat` (bearer) bumps `lastSeenAt` + refreshes `agentVersion` + (agent ≥0.17.1, Linux) stores the raw `capEff` mask from the agent's /proc/self/status into `ManagedAgent.reportedCapEff` — the VERIFIED privilege state, decoded server-side by `utils/capEff.decodeCapEff` (surfaced as `caps` on `GET /assets/:id/agent` and `/server-settings/agents/installed`; a ptrace-tier agent whose mask lacks CAP_DAC_READ_SEARCH renders as "stale unit — reinstall" since it collects no Application Map connections). The three operator-facing endpoints on `/api/v1/assets/:id/agent` are: `GET` (any auth role) returns the redacted `ManagedAgent` row (hashes stripped) or 404; `POST /install` (assets-admin) validates the credential type matches the chosen OS (ssh for linux/darwin, winrm for windows) and validates the optional `scriptId` install-method variant against the target OS (`resolveInstallScriptId` — the server-side OS-lock; persisted on `ManagedAgent.installScriptId`, re-checked in `runInstall` before executing), captures the live Polaris HTTPS cert fingerprint via `certInfo.getServerCertFingerprint()`, creates the `ManagedAgent` row in `pending`, mints a 10-min-TTL enrollment token, emits `agent.install_kickoff`, and (Phase 2) returns the enrollment token in the response so an operator can stand up the agent by hand — the SSH/WinRM file-push that automates this work lands in Phase 4 via `agentInstallService`. `DELETE` (admin-only) is a two-phase op: synchronous `revokeBearer` is always immediate; `?force=true` additionally hard-deletes the row and emits `agent.force_removed` (for unreachable hosts). Without force, the row is left in place with `installStatus="revoked"` so the Phase-4 async remote-uninstall job has something to drive.

**Polaris Agent remote install (Phase 4a — SSH).** `src/services/agentInstallService.ts` fires the async background work when the operator clicks Install Agent: open ssh2 connection → SFTP upload binary + agent.conf + installer script to `/tmp/` → `sudo -n bash /tmp/polaris-agent-install.sh` → cleanup. The installer script (embedded as a string in the service, not shipped alongside the binary so it stays version-locked with FortiOS-style "Polaris release == one bundle" semantics) writes `/usr/local/bin/polaris-agent` + `/var/lib/polaris-agent/agent.conf` (Linux — under systemd's `StateDirectory=` so the agent can rewrite it after enroll; `/etc/` is read-only via `ProtectSystem=strict`. **The installer chowns `agent.conf` to whatever owns that state directory, never to root**: with `DynamicUser=yes` systemd chowns the state *directory* to the dynamic UID but leaves files already inside it alone, so a `root:root` conf written on a **reinstall** — where `/var/lib/polaris-agent` is already a symlink into `/var/lib/private/` owned by the dynamic user — leaves the agent crash-looping on `load config: permission denied` with the row parked at `enrolling` and no error surfaced, since the installer itself exited 0. First installs mask the bug because systemd migrates the brand-new directory and chowns the whole tree. Prod incident 2026-07-27) or `/etc/polaris-agent/agent.conf` (macOS) + a systemd unit (Linux) or launchd plist (macOS). The systemd unit uses `DynamicUser=yes` so the agent runs as a non-root system-managed user; the macOS plist runs the agent as root (operators tighten this in a follow-on if needed). State transitions: `pending → uploading → enrolling → active` (the last step happens when the agent's first POST /enroll lands). The `ManagedAgent.installCredentialId` column stores which SSH credential was used, so the default DELETE path can reuse it for the remote uninstall mirror — `sudo -n bash /tmp/polaris-agent-uninstall.sh` stops + disables the service, removes the unit/plist/binary/config, and on success hard-deletes the ManagedAgent row (audit trail lives in Event). Binaries live under `<STATE_DIR>/data/agents/<version>/`; the manifest at `<STATE_DIR>/data/agents/manifest.json` names the current default version + maps platform-arch tuples to filenames. The URL stamped into `agent.conf`'s `server_url` resolves in this order: (1) `Setting.agent.serverUrlOverride` — operator-settable from Server Settings → Maintenance → Polaris Agent card via the **Server URL stamped into agent.conf** input (PUT `/server-settings/agents/server-url` with `{url}`; empty string clears the override and falls back to the cert-derived default); (2) `POLARIS_PUBLIC_URL` env var (legacy operator override, still honored for scripted deployments); (3) first DNS SAN on the running HTTPS leaf cert + live HTTPS port — the natural default, since operators generate the cert with the hostname they expect Polaris to be reachable at and the agent's pin is verifying that exact cert; (4) cert CN + port; (5) first IP SAN + port (covers IP-only certs in isolated networks); (6) `POLARIS_PUBLIC_HOST` env + PORT; (7) `localhost` + PORT. The install kickoff route guards against producing `https://localhost:<port>` for a non-loopback target. Reverse-proxy / TLS-termination shops set either the UI override or `POLARIS_PUBLIC_URL` so the agent dials the proxy's public hostname rather than the upstream's internal IP. The Polaris Agent card surfaces the **effective** URL pre-filled (so operators can see what install would use right now) and the **cert-derived default** as helper text so it's obvious what they'd inherit if they cleared the override.

**Polaris Agent remote install (Phase 4b — WinRM).** Windows hosts install via the same agentInstallService entry point but use a different transport: instead of SFTP-uploading the binary, the PowerShell installer running on the host **pulls the binary over HTTPS** from a new public endpoint `GET /api/v1/agents/binary/:filename` (filename whitelist-checked against `data/agents/manifest.json`, directory-traversal protected, no-store cache). The pull is gated by a server-cert pin: `[Net.ServicePointManager]::ServerCertificateValidationCallback` is wired to compare the leaf SHA-256 against the pin embedded in the PowerShell command, then restored after the download. We avoid implementing the WS-Management `Send` verb (chunked stdin file upload) entirely — saves ~1000 lines of XML envelope code that's only used here. The WinRS shell verbs we DO implement live in `src/utils/winrm.ts`: `CreateShell` → `RunCommand` → `Receive` (polled loop until `CommandState=Done`) → `DeleteShell` (always in a `finally`). PowerShell is invoked via `-EncodedCommand` (UTF-16-LE base64) so command-line escaping never bites. The installer creates the service via `New-Service` (canonical, ships in every Windows since 5.1) and stamps recovery actions via `sc.exe failure`. Deliberately avoids `Get-WmiObject Win32_Service` (DCOM-based, removed in PowerShell 7+) and `Remove-Service` (PowerShell 6+ only, missing from stock Server 2019); uses `sc.exe delete` for the uninstall. The host's `%ProgramFiles%\Polaris\Agent\polaris-agent.exe` + `%ProgramData%\Polaris\agent\agent.conf` are written with admin-only ACLs (the bearer is in agent.conf so it must not be world-readable). Same install lifecycle as SSH: `pending → uploading → enrolling → active`, with the agent's first POST /enroll flipping to active. WinRM needs to be enabled on the target host on port 5986 (HTTPS preferred) or 5985 (HTTP fallback); the credential must have local admin rights.

**Polaris Agent in-app build (Server Settings → Maintenance → Polaris Agent).** Operators click Build to produce all six platform binaries (linux/darwin/windows × amd64/arm64) right from the web UI; no shell access needed. Driven by `src/services/agentBuildService.ts` which spawns one `go build` per platform serially (parallel calls thrash the shared GOCACHE), writes binaries under `<STATE_DIR>/data/agents/<version>/`, and writes `manifest.json` atomically (`.tmp` + rename) only after all six succeed. Version comes from `getAgentVersion()` (reads `agent/VERSION` text file with a 5s mtime cache) — DECOUPLED from `getAppVersion()` so Polaris patch releases that don't touch `agent/` produce zero build noise. Install scripts (`deploy/setup-rhel.sh`, `setup-ubuntu.sh`, `setup-windows.ps1` and their `-nodb` variants) install Go alongside Node; the Dockerfile pulls `golang-go` from trixie-backports. UI gates the Build button on `goAvailable()` and surfaces a clear notice when the toolchain is missing OR present-but-below `GO_MINIMUM` — two distinct messages, because sending an operator who already has Go 1.21 off to "install Go" is the wrong instruction. The card shows a per-platform inventory grid (size / built-when / present-✓), a drift hint when `manifest.currentVersion` lags `agent/VERSION`, a queued-builds strip (FIFO depth 3; 4th simultaneous click 409s with "queue full"), per-build × cancel buttons, and an Auto-build toggle. **Build queueing:** two operators clicking near-simultaneously land in a stable FIFO order (Node's single thread guarantees no interleave between the queue-length check and the enqueue); each build re-reads `getAgentVersion()` at start-of-run so a queued build picks up a VERSION bump that landed during its wait. **Cancellation:** `state.activeChild` holds the running `go build` ChildProcess; DELETE sends SIGTERM, then SIGKILL after 5s grace. The `manifest.json` is only written after ALL platforms succeed so a cancelled build leaves partial binaries under `data/agents/<version>/` but the previous manifest still points at the previous version's files (operator-visible: nothing happened). **Per-version retention:** after every successful build the helper prunes deletable version directories — deletable = NOT `manifest.currentVersion` AND NOT in use by any live `ManagedAgent` AND NOT within the most-recent N (env `POLARIS_AGENT_KEEP_VERSIONS`, default 3). A manual "Clean up old binaries" button on the card fires the same helper. **Auto-build:** `src/jobs/autoBuildAgents.ts` fires 60s after boot, refuses unless `manifest.json` exists (operator opted in), Polaris's `getAgentVersion()` differs from `manifest.currentVersion`, Go is available AND meets `GO_MINIMUM`, AND `Setting.agent.autoBuildOnVersionMismatch !== false`. Actor stamped as `"system:auto-build-on-version-change"` so the audit trail distinguishes this from operator clicks. Skipped builds emit `agent.build.auto_skipped` with the reason so operators see the staleness on the Events page.

**Windows binary code signing (internal-CA PKCS#12, opt-in, FAIL-OPEN).** When the `agent.codeSigning` Setting is enabled (Integrations → Polaris Agents → Code signing), `agentBuildService.signWindowsBinaries()` runs between the platform loop and the manifest write: it invokes `java -jar tools/jsign.jar --storetype PKCS12 --keystore <pfx> --storepass env:POLARIS_SIGNING_PASSWORD [--alias <alias>] --tsaurl <tsa> --tsmode RFC3161 <exe>` per Windows binary — the keystore password rides the child env, never argv, and `scrubSecrets` keeps it out of step errors/Events. There is NO credential-exchange step (a PKCS#12 store is read directly), so unlike the prior hosted-service path there is no whole-phase token failure mode before the per-file loop. **Timestamping is explicit and required:** jsign auto-enables RFC3161 only for hosted store types, so `tsaUrl` is part of `isSigningConfigured()` and a cleared field falls back to the default rather than silently disabling it — without a countersignature every signature in the fleet goes invalid the moment the signing cert expires, all at once. A public TSA is correct with an internal-CA cert (a TSA attests to *when*, not *who*). Progress strip gains `sign/windows-{amd64,arm64}` step rows under phase `signing`; cancellation rides the same `state.activeChild` SIGTERM path as `go build`. **Fail-open:** any signing failure marks the step failed, stamps the durable `agent.signing.lastFailure` Setting, and emits `agent.build.sign_failed` (warning) — but the build completes and ships unsigned; `agent.build.completed` carries `signed: true|false|"disabled"`. The stamp drives a dismissable sidebar alert (`#signing-failure-alert` in [public/js/app.js](public/js/app.js), 30s poll of `GET /assets/agent-signing-alert`, visible to `assets:write` roles, per-user-per-failure localStorage dismissal) and clears on the next fully-signed build or when signing is disabled. Host tooling (Java 25 headless + the SHA-256-pinned jsign 7.5 jar at `<app dir>/tools/jsign.jar`) is provisioned by the setup scripts + Dockerfile, and the floor the card states comes from the server (`JAVA_MINIMUM` → `availability.javaMinimum`) rather than a literal in the page — the card said "Java 17+" for two days after the scripts moved to 25, which is the same drift `GO_MINIMUM` exists to prevent; `signingAvailability()` re-probes uncached so "install Java and reload" just works. The two Windows exes also carry a committed VERSIONINFO resource (`agent/cmd/polaris-agent/winres.json` → `rsrc_windows_{amd64,arm64}.syso`, regenerated by `make -C agent winres` on VERSION bumps) so the PE shows publisher/product/version metadata independent of signing. **Trust is fleet-scoped, not public:** an internal CA contributes nothing to SmartScreen reputation; what it buys is a deterministic allow via a Defender for Endpoint certificate indicator (leaf certs only, ~3h to propagate) or an App Control publisher rule, and any host that does not trust the internal root sees an UNTRUSTED signature. PKI-side setup + operator walkthrough: docs/INSTALL.md → "Optional: Code signing for agent Windows binaries".

**Polaris Agent upgrade-already-installed (`POST /assets/:id/agent/upgrade` + bulk).** `startUpgrade` in `src/services/agentInstallService.ts` does an SSH/WinRM-driven binary swap that preserves `agent.conf` — bearer + cert pin survive, agent reconnects with the same identity. SSH path SFTPs the new binary to `/tmp/polaris-agent.new` and runs an embedded upgrade shell script that stops the systemd unit / launchd job, `install -m 0755`s over the old binary, restarts. WinRM path runs an embedded PowerShell `-EncodedCommand` that re-uses the install-flow's cert-pin-verified `Invoke-WebRequest` to pull the new binary from `/api/v1/agents/binary/:filename`, then `Stop-Service` → atomic `Move-Item` → `Start-Service`. State transitions: `active → upgrading → active` on success, `active → upgrade_failed` on remote error — and `upgrade_failed` is itself an upgradeable status (`UPGRADEABLE_INSTALL_STATUSES` / `canUpgradeFromStatus`, exported from the same service and used by the guard, the bulk filter and the two `outOfDate` flags alike), because every failure path leaves the old binary and `agent.conf` untouched. That is what lets a host asleep during one fan-out be retried by the next build instead of needing an uninstall/reinstall. **The credential is resolved, not merely read** (business rule 49): `resolveUpgradeCredential` tries the operator's explicit `credentialId`, then `ManagedAgent.installCredentialId`, then the Polaris-managed SSH deployment credential for the platform — so a row whose credential was deleted (`ON DELETE SET NULL`) or that predates the column (migration `20260514010000`, no backfill) is no longer permanently un-upgradeable. **The transport comes from the credential's `type`, not from `installTransport`**, because migration `20260609000000` backfilled `winrm` onto every pre-existing Windows row and the managed credential is key-only; honouring the column would fail those rows in `winrmConnectionFromCred`. An adopted credential + transport is written back onto the row **only on success** — reaching the host is the proof — and an operator override is never adopted. Before this, `startUpgrade` threw before touching `installStatus`, so such rows stayed `active` + out-of-date and every fan-out re-skipped them with no Event and no `installError`; a skip now writes `agent.upgrade_skipped` against the asset. Per-asset Upgrade button on the asset details modal Agent panel (Retry Upgrade on a failed row); bulk Upgrade-all line on the Maintenance Polaris Agent card with a Promise pool of 4. The bulk path's "N of M out-of-date" line is backed by `GET /server-settings/agents/installed-summary` which returns a per-version histogram (cheap groupBy on `ManagedAgent.agentVersion`).

The `ManagedAgent` table tracks each install (lifecycle: pending → uploading → enrolling → active → revoked / uninstalled / upgrading / upgrade_failed; one row per asset, FK cascade). See the plan at `~/.claude/plans/the-app-needs-a-glowing-knuth.md` for the implementation roadmap.

**SSH deployment (Integrations → Polaris Agent → "SSH Deployment" card).** Installing the agent on Windows over SSH rather than WinRM has been supported since the `installTransport` split (`sshWindowsInstall` / `sshWindowsUninstall` / `sshWindowsUpgrade`), and the `ssh` credential type has always accepted a `privateKey` in place of a `password`. What this card adds is everything around them: Polaris now GENERATES the deployment keypair and emits the script that authorizes it fleet-wide, instead of the operator running `ssh-keygen`, pasting the private half into the credential form, and hand-writing the push. That hand-written step is the error-prone part — Windows OpenSSH ignores `%USERPROFILE%\.ssh\authorized_keys` for anyone in the Administrators group (it reads only `%ProgramData%\ssh\administrators_authorized_keys`) and refuses that file unless it is owned by Administrators/SYSTEM with inheritance disabled; neither mistake produces a client-side error, authentication just fails.

Four routes under `/api/v1/server-settings/agents/windows-ssh` (beside the agent-build routes, matching that card's existing UI-on-Integrations / routes-on-serverSettings split): `GET` (card state — `serverSettingsSystem:read`), `PUT` (accountMode / username / polarisServerIp — `fullwrite`), `POST /generate` (mint or rotate the keypair) and `GET /script?kind=remediation|detection`. **`/generate` carries a CHAINED gate** — `serverSettingsSystem:fullwrite` **AND** `credentials:write` — because it creates and mutates a Credential row; without the chain a custom role holding system settings but no credential access could mint a fleet-wide admin key. Same chaining shape as `PUT /application-map/discovery`.

`SshConfig` gained `publicKey`, deliberately **not** in `SECRET_FIELDS_BY_TYPE.ssh` so it survives `stripSecrets` — otherwise the onboarding script could not be re-rendered without rotating the key and re-touching every endpoint. The private half is sealed at rest by the `db.ts` extension and returned by no read path.

**Linux (Phase 1b)** works the same way with three platform differences that matter. The key goes into the USER's `~/.ssh/authorized_keys` (700 dir / 600 file, correctly owned) rather than one group-wide file; `restorecon` fixes the SELinux context, which RHEL-family sshd otherwise refuses just as silently as a bad Windows ACL; and the script installs a **NOPASSWD sudoers drop-in**, because the agent installer runs `sudo -n bash /tmp/polaris-agent-install.sh` — SSH key auth alone does not install an agent, so onboarding without it would just move the manual step. The drop-in is validated with `visudo -cf` BEFORE being installed: a malformed one locks sudo out for every user on the host, which is far worse than a failed onboarding. Deliberately NOT installed: `openssh-server` (distro-specific package management, and a host you cannot already reach over SSH is not one the script was delivered to) — it detects and reports instead. The Linux detection script also checks the account and the sudoers drop-in, unlike the Windows one, because both are prerequisites the install genuinely fails without and both are cheaply observable.

Account settings are **per platform** (`config.windows` / `config.linux`); `polarisServerIp` is shared. Polaris maintains **one managed credential per platform**, both carrying the same keypair — a `Credential` holds exactly one username, and a Windows `DOMAIN\user` is meaningless on Linux, so a single shared row would leave one platform unable to log in.

The generated scripts are **delivery-neutral and fleet-generic**: no machine-specific values (public key, username, account mode and server IP are fleet constants; `administrators_authorized_keys` is one group-wide file authorizing any local Administrator presenting the key), so the identical body runs under an Intune Remediation, a GPO startup script, an SCCM Configuration Baseline, Azure Arc, an RMM job, or a one-off `Invoke-Command` loop. The **detection** script is what makes rollout self-healing when paired with the remediation one — a plain Intune platform script runs once per device and never retries, so machines offline at assignment time or reimaged afterwards stay unconfigured. Note that Intune does not manage traditional Windows Server, so the Servers class needs GPO/SCCM/Arc even on an Intune estate. An unsupported Windows build (pre-1809 / pre-Server 2019, no OpenSSH capability) reports `unsupported:` and exits **0** from both scripts on purpose: returning non-zero would loop the pair forever against a device remediation cannot fix.

**SSH host-key verification (opt-in, all SSH paths).** Until 2026-08 Polaris passed no `hostVerifier` to ssh2, so **every** SSH connection accepted whatever host key was presented — the server was never authenticated to the client. That covered agent install/upgrade/uninstall (which SFTPs a script and runs it as root), agentless process collection, and the SSH monitor probe alike; anything able to answer on the target's address could impersonate it and, on an install, be handed a credential.

`SshConfig.verifyHostKey` turns on trust-on-first-use pinning against the `SshHostKey` table. It is **opt-in, default OFF**, defaulting ON only for newly created credentials — the exact shape of the WinRM `verifyTls` remediation (2026-06-03 review, H1), because enabling it globally would break every install whose hosts have never been pinned. `buildHostVerifier` in [remoteExec.ts](src/utils/remoteExec.ts) is shared by BOTH `ssh2.connect` call sites (`withSshClient` and `monitoringService.probeSsh` — the only two in the tree) so they cannot drift on whether the server is checked, and it **fails closed**: an operator who asked for verification gets a refused connection on an internal error, never a silently unverified one.

Pins live in their own table rather than on `Credential.config` because host keys are per-HOST while one credential legitimately spans a fleet. The operator surface (list + Delete) is on the Windows SSH Deployment card, since deleting a pin is the documented recovery after a legitimate rebuild or re-key — and it is audited at warning level precisely because it re-opens first-use trust. **TOFU is only as good as the moment you pin:** enabling this against a running fleet pins whatever currently answers, so it detects a key *changing* rather than a host that was already impersonated. It is genuinely strong for a greenfield rollout, where the pin is taken at deploy time.
