Seven steps: Name → Targets → Methods → Run → Results → Monitoring → Summary, in the `appmap-rules-wizard.js` idiom (one closure-scoped draft, HTML/Wire/Collect/Validate per step behind COLLECT/VALIDATE tables, a footer synced per step, free navigation to visited steps, shared `.stepper` CSS with the stepper a DIRECT first child of `.modal-body`); ids are `nd-` prefixed. Three things differ from the other two wizards. (1) **Steps 4–5 are a RUN, not authoring** — step 4 SAVES the Discovery then POSTs a run and polls it (self-rescheduling `setTimeout`, a try cap, per-tick errors swallowed — the `runScriptTest` shape), and re-entering it REATTACHES to the newest run rather than losing a scan the operator closed the modal on (the agent-build.js progress-strip precedent). Progress is a text ratio plus a thin determinate bar, affordable here because the denominator is known up front unlike integration discovery. (2) **Step 6 reuses the integrations page's auto-monitor builders** (`_autoMonitorInterfacesHTML` / `_readAutoMonitorInterfaces` / `_autoMonitorStorageHTML` / `_readAutoMonitorStorage` — module-level functions in integrations.js and therefore globals; assets.html already loads it). Deliberate: the selection vocabulary is resolved server-side by ONE pair of pure resolvers, and a second render of it here is how the two surfaces would come to disagree about what a stored selection means. What this file supplies instead of that page's wire function is the DATA — the integrations version fills its checklists from `/integrations/:id/interface-aggregate` (assets that already exist and have been polled), while at scan time neither is true, so names and types come from the inventory the SCAN collected. The row contract is a documented selector pair (`input[data-name-checkbox="1"][data-prefix=…]`, `input[data-stor-name-checkbox="1"][data-prefix=…]`), and selections are grouped by POLLING METHOD because what can be pinned depends on what answered. (Moving those builders into a shared module is the better end state; it is a ~500-line move inside an 8k-line shared file and is deliberately not bundled with a feature commit.) (3) **Every control is gated by the key its own route checks** — a read-level caller gets a read-only walkthrough with no Save and no Run, and a caller who may scan but not create sees Export/Save but no "Add N assets", with a line saying to hand the run to someone who can (the results are saved with it). │       ├── topology-render.js        # Shared Cytoscape element + stylesheet builders consumed by both desktop map.js and mobile topology-tab.js. Exposes `buildTopologyElements(data)`, `topologyStylesheet(theme, opts)`, `topologyLegendSpec()`, `computeTopologyColumns(elements)`, and `computeGroupedLayout(elements)` (quotient two-level layout for location-coded sites: per-group rank-compressed interiors + height-budgeted shelf packing of group boxes; returns the same {depth,lane} contract or null on untagged sites) so node colors per monitor health, edge styles for controller / interface-inferred / LLDP / mesh edges, ghost LLDP nodes, cross-site remote assets, and operator-uploaded icons stay consistent across surfaces. FG→switch controller edges are labeled with the real port pair (`srcIf.name ↔ tgtIf.name`, post trunk→member swap) when the edge is `verifiedUplink` AND the server attached interface details on both ends; otherwise they fall back to the logical `fortilink` label (dashed gray when unverified). **`computeTopologyColumns` is the deterministic layout solver** (replaces dagre auto-ranking): a node-weighted Dijkstra from the FortiGate (firewall 1 / switch 2 / AP 3 / endpoint 4) places **column anchors** on **even** columns by weighted depth (distinct depths compacted to contiguous columns), **leaves** on the **odd** column right of their parent, FortiLink-fallback switches (no interface/LLDP-verified path to the FortiGate) in **negative** columns (-2, their endpoints -3). An anchor is infra (FortiGate / switch / AP) that isn't a *terminal* AP — `isLeafAp` classifies a FortiAP hanging off a switch port with no wireless mesh/bridge children of its own as a **leaf** (placed in the parent switch's leaf column, NOT its own anchor column), so a FortiGate's switch chain stays in tight consecutive columns with each switch's APs hung directly off it instead of every AP's weighted depth fanning the switches across the canvas; mesh-root and bridged-switch-parent APs stay anchors. Rows come in **two passes**: (a) a **nearest-free-slot packing** pass over **anchors only** (a node's first anchor child in a different column continues the parent's row so chains stay flat; every other anchor scans downward from just below its parent's row for the first lane where its whole footprint fits — its own cell, the spine chain that will inherit its lane into later columns, and each chain member's planned leaf block one column right, that block starting one row below a member whose chain continues since the continuing spine edge occupies the member's own row — so rows pack tight near the spine and drift down only where subtrees congest, instead of every subtree pre-claiming a globally disjoint row band that pushed a left-column switch's later children below everything placed before them) and (b) a leaf pass that slides each parent's leaves as one **contiguous window** (grouped by parent, blocks ordered by parent row) starting at the parent's row, slid down as a whole to dodge occupied lanes or a drawn edge passing through the column (per-leaf dodging would fragment a block around another chain's spine running through it) — so each switch's AP stack lines up just below it, grouped together, never staircased rightward or split apart/interleaved by another switch's APs even when the `/topology` payload lists APs in interleaved order; orphans stack below everything. Mesh leaves (AP-as-station-on-AP, `isMesh`) and LLDP wireless-bridge switches (`bridgeEdges` → `isBridge`) stay anchors and route through their AP. Wired AP↔switch links (a managed AP's switch uplink or a bridged switch behind an AP) carry `isApLink` and render solid blue (#3b82f6) with a directional arrow — distinct from the dashed violet wireless mesh backhaul and the gray controller edges. `markPhysicalLoops` (exported; runs at the end of `buildTopologyElements`) stamps `inLoop: 1` on every wired edge lying on a cycle — Tarjan bridge-finding over the simple graph of interface/LLDP/AP-link/verified-uplink edges **plus MCLAG ICLs** (an ICL is a real cabled link, so when it closes a cycle — the usual MCLAG shape where both peers uplink to a common parent — it's part of a physical loop and gets haloed; an isolated ICL that's the only path between its peers is a bridge/cut-edge and stays unflagged; wireless and unverified controller edges are excluded; parallel cables between one pair collapse to one adjacency so a trunk pair isn't flagged) — and the stylesheet halos those edges yellow (`line-outline-color` #eab308) around their own line color, with a matching legend row. `fortinetNodeColor` renders dependency-suppressed ("Dep. Down") nodes gray. `topologyLegendSpec()` is the single source of truth for the desktop Legend overlay — node + monitor-health + edge (incl. Mesh/bridge) swatches with descriptions, mirroring the constants the stylesheet uses. │       ├── automations-portability.js # Export / import ONE automation as a portable JSON file, plus the "view code" editor (`window.PolarisAutomationPortability`). Two deliberately different serializations: `stripForExport(body, catalogs)` removes every install-specific reference (delivery-channel / user / role / script ids, api_call actions and their unmasked headers, escalation chains, emailComposition, `scope.assetIds`/`integrationIds`, `assetId` condition leaves, `dimensionFilter.stateProbeId`/`widgetId`) and records each one as a NAMED **dependency** instead, so the file is portable and carries no secrets; `forCodeView(body)` keeps everything (ids included) because an edit there must round-trip losslessly. `buildExportFile` puts `dependencies` BEFORE `rule` — the nested schemas are `.strict()`, so a hint cannot ride next to the thing it describes, and a top-level block is also where a human opening the file looks. Three invariants the module exists to hold, each pinned by a test: the top-level `actions` list is emitted EXPLICITLY as `[{type:"event"}]` and never omitted (the server re-injects the audit Event only for `undefined`, which the wizard draft never produces — omitting saves a rule that writes a Notification row but logs nothing); an empty `scope` is never emitted (`{}` means MATCH NOTHING to `scopeWhere` while `step2Html` renders it as "All assets" checked, so a scope that strips to nothing becomes an empty CONDITION TREE, which `validateStep2` refuses); and a blanked `stateProbeId`/`widgetId` is reported back (both are optional and the engine applies them only when present, so blanking WIDENS the trigger to every probe on the device — the wizard's `tgValidateLeaf` now refuses to save one). `parseImportFile(text, filename, triggerTypes)` is the import gate — size cap, `JSON.parse`, `__proto__`/`constructor`/`prototype` rejection, depth cap, envelope-version check, unknown-trigger-type refusal — and RE-STRIPS on the way in, so "an import never carries a foreign id" is a property of the code rather than a promise about the file. `checkDependencies` answers present / missing / can't-tell against the catalogs the wizard already holds (`present: null` for a kind with no catalogue, never a false "missing").
