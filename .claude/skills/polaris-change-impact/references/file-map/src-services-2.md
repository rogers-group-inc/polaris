│   │   ├── vendorTelemetryProfiles.ts # Per-vendor SNMP CPU/memory/temperature/disk profile registry. Maps `manufacturer + os + model` regex → symbolic OID names; resolved through oidRegistry at probe time. Seeded into the editable `ManufacturerProfile` model on first boot (Slice 6a); the runtime probe path now consults the DB via `pickVendorProfileMerged` (Slice 6c) which layers operator-edited symbol choices + per-model overrides on top of a clone of the hardcoded entry. The constant stays as a fresh-install fallback while the DB cache warms up. Transforms from `symbolTransforms.ts` are not yet applied at sample-write time — that plumbing lands in a follow-up. Profile shape carries optional `cpu` / `memory` / `disk` / `temperature` queries — temperature is a single-scalar form for vendors whose hardware publishes one Celsius reading instead of the table-based ENTITY-SENSOR-MIB walk (consumed by `collectTemperaturesSnmp` as a third fallback after ENTITY-SENSOR-MIB + the Fortinet `fgHwSensorTable` sensor-name heuristic). Profile selection is `pickVendorProfile(manufacturer, os, model, assetType)`: the regex haystack is `manufacturer + os + model` PLUS the class hint from `fortinetClassHint(manufacturer, model, assetType)`, which returns "FortiSwitch" / "FortiAP" for a Fortinet-manufactured `switch` / `access_point` whose model doesn't already name a class. That was a deadlock, not a miss: the FortiOS profile carries no `model` query, so `fsSysVersion` was never read and the empty model could never be filled in (prod 2026-08-31, FSR-112D-POE — see business rule 24 for why the misroute charted a flat 0% instead of an error). `pickVendorProfileMerged` applies the same hint when matching the DB profile's `modelPattern`, which is tested against the model ALONE and would otherwise fall back to the manufacturer-wide `fgSysCpuUsage` default and overwrite the correct symbol. Built-ins for Cisco / Juniper / Mikrotik / Fortinet FortiSwitch (matched before generic Fortinet via `model="FortiSwitch"` or the assetType hint; CPU uses `fsSysCpuUsage` @ 12356.106.4.1.2 scalar percent; memory uses bytes form via `fsSysMemUsage` @ 12356.106.4.1.3 + `fsSysMemCapacity` @ 12356.106.4.1.4 — NOT a percent like the FortiGate variant — all three seeded into oidRegistry so the probe works without uploading FORTINET-FORTISWITCH-MIB) / Fortinet FortiAP (matched before generic Fortinet via `model="FortiAP"` or the assetType hint; distinct OID root @ 12356.120 — FortiAPs don't expose anything under FortiGate's 12356.101 or FortiSwitch's 12356.106; CPU = `fapCpuUsage` @ 12356.120.3.41 scalar percent; memory = `fapMemoryUsage` @ 12356.120.3.42 scalar percent (single-value form like FortiGate, NOT FortiSwitch's bytes form); temperature = `fapTemperature` @ 12356.120.3.44 scalar Celsius; all three seeded into oidRegistry so the probe works without uploading FORTINET-FORTIAP-MIB) / Fortinet (SNMP path) / HP-Aruba / Dell. │   │   ├── monitoringService.ts     # Authenticated response-time probes (fortimanager/fortigate/snmp/winrm/ssh/icmp) + System tab telemetry (CPU/memory) + system-info (interfaces/storage) collection. runMonitorPass dispatches all three cadences; per-stream tier-aware retention prune helpers. **Prune layer is fleet-coordinated**: `runRetentionPrune` (the single entry called from `monitorAssets`'s heavy loop) gates on a persisted `Setting("lastRetentionPruneAt")` (24h cadence, `RETENTION_PRUNE_INTERVAL_MS`) and takes a Postgres session-level advisory lock (`pg_try_advisory_lock(0x504c5253,1)` on a dedicated `getDirectDatabaseUrl()` connection) so only ONE monitor replica prunes at a time — the rest return `{skipped}`. Inside the lock it runs `pruneMonitorSamples` / `pruneTelemetrySamples` / `pruneSystemInfoSamples`, one prune per (table × tier) — detail (column `timestamp`), hourly + daily (column `bucketStart`) — with retention from `getSampleRetention()` (per-class: `default` / `switch` / `accessPoint`), then bumps the persisted timestamp. LLDP neighbors ride the systemInfo detail retention since they're current-state, not time-series. `dropChunks(cutoff)` is the O(1) pre-filter for whole aged chunks; the residue row-DELETE is compression-frontier-safe — `pruneTierByDays` routes through `tieredPruneWindow` (skips the DELETE entirely when the whole delete set is past the compress-after frontier, the common rollup case) and `pruneSelectionAwareDetail` through `unselectedSlowPruneWindow`, so a row-DELETE never decompresses a compressed chunk (prod incidents 2026-06-08, 2026-06-17). The old in-memory `lastPruneAt=0` trigger fired the prune on every process boot and, under a monitor restart loop, fanned into the 2026-06-17 hourly-table DELETE pile-up that pinned the xmin horizon. **Sample writes are async-buffered**: every `record*` function (`recordProbeResult` / `recordTelemetryResult` / `recordSystemInfoResult` / `recordFastFilteredResult`) hands sample rows to `sampleWriteBuffer.enqueue*` instead of issuing per-call `prisma.<table>.create*` — those are batched into one `createMany` per 2 s flush window. **The probe-path Asset.update (status/counters/last*At) is also buffered** via `probePatchBuffer.enqueueProbePatch` — one bulk `UPDATE … FROM (VALUES …)` per 2 s window covers every asset's state write instead of one `prisma.asset.update` per probe. The five-state machine reads its own writes via `getPendingProbePatch(assetId)`: `recordProbeResult` overlays the in-flight patch onto the loaded Asset row BEFORE computing the next state, so the threshold counters advance correctly across same-window probes. Telemetry/systemInfo cadences still issue per-asset `prisma.asset.update` for `lastTelemetryAt` / `lastSystemInfoAt` — those run on slower cadences (60 s / 600 s+) where per-tick connection pressure is much lower; if needed, the same buffer pattern applies straightforwardly. Three writes stay synchronous because they need per-asset replace semantics: the `$transaction` for `assetAssociatedIp` (delete-non-manual + createMany inside `recordSystemInfoResult`), `persistLldpNeighbors` (per-asset full-replace of the LLDP neighbor table with a 48 h stickiness grace), and `persistWirelessStations` (per-scrape full-replace of the connected-client table; no stickiness because clients are transient by design — its endpoint `lastSeenAp` stamp is now edge-triggered: one bounded pre-read of the matched endpoints, only the rows whose AP actually changed are updated (a steady station set issues zero UPDATEs per scrape), and each real move emits an `asset.wireless_ap.changed` audit row AFTER the transaction commits. The id-sorted `$transaction` ordering is a documented 3-way-deadlock fix and survives the filter, which is applied before the sort). The LLDP and wireless paths use a single bulk `INSERT … ON CONFLICT (id) DO UPDATE` raw-SQL statement (plus a separate `deleteMany` for stale rows) so the connection isn't held across N pipelined updates inside a transaction — caller pre-assigns ids in JS so insert-vs-update is controlled by id collision, not by the business-key unique constraint which can't be used as a conflict target since Postgres treats NULL as distinct in unique indexes. **Probe path issues exactly one Asset findUnique** — `probeAsset(assetId, out?)` stashes its loaded asset row into the caller's optional out-object so `recordProbeResult(assetId, result, preloadedAsset?)` can skip its own findUnique on the state-machine update path. The hot loop (runProbeFor) and pg-boss probe workers both pass the out-object; the /probe-now route doesn't bother (one operator-triggered request per click). **LLDP asset match index is module-cached** with a 60 s TTL — `persistLldpNeighbors` used to call `buildLldpAssetMatchIndex` on every system-info pass (`findMany` over every Asset row plus its associatedIpRows + macAddressRows), now goes through `getLldpAssetMatchIndex()` which dedups concurrent rebuilders via an inflight Promise and returns the cached map within the TTL window. Worst-case stale-cache effect is one cycle of "LLDP neighbor matched to wrong asset" which self-corrects on the next scrape; `invalidateLldpMatchCache()` is exported for future callers that want explicit refresh after a bulk asset write. **FortiSwitch port-VLAN overlay**: in the SNMP systemInfo path on `assetType="switch"` assets with a Fortinet source AND a resolvable `controllerFortigate`, `collectSystemInfo` calls `fetchFortiswitchControllerPortsCmdb(integration, controllerName, timeoutMs)` after `collectSystemInfoSnmp` returns and overlays per-port `nativeVlan` + `taggedVlans` onto matching `InterfaceSample` rows by ifName == port-name. The fetcher hits the parent FortiGate's `/api/v2/cmdb/switch-controller/managed-switch?datasource=1` once per (integration, controller) per 30 s (`fortiswitchControllerPortsCache` mirrors the `fortinetControllerCache` TTL); the response carries every managed switch's full ports table including `vlan` / `allowed-vlans` / `untagged-vlans`, parsed via `parseFortiosVlanList` which handles FortiOS's three shapes (array of `{vlan-id}` objects, raw number array, comma+range string) and drops `"all"` placeholders. Tagged set is `allowed-vlans − untagged-vlans` so a port carrying only its native isn't duplicated as tagged. The **same CMDB fetch also carries trunk membership** (a `ports[]` entry that lists `members` IS a trunk — the auto-ISL FortiLink uplink is named after the switch serial and has exactly one member): `overlayFortiswitchTrunkMembers` stamps `ifParent=<trunk>` + `ifType="physical"` onto each member's `InterfaceSample` row (synthesizing the row when IF-MIB omitted the subordinate port) and marks the trunk row `ifType="aggregate"`, mirroring the FortiGate-side aggregate back-fill in `collectSystemInfoFortinet`. This parent/member linkage lets the topology layer (`interfaceTopologyService.preferPhysical` + the single-member swap in `topologyGraphService.ts`'s `ifDetail`) render a single-member trunk as its physical port — so the Device Map FortiLink tooltip shows the real cable port (e.g. `port52`) instead of the opaque serial-named trunk. The member-list parser (`parseFortiosMemberList`) is deliberately permissive across FortiOS shapes (array of `{member-name}`/`{q_origin_key}`/`{name}` objects, bare-string array, or space/comma string); the exact CMDB field still wants confirmation on a live FortiOS 7.x device, so the overlay is best-effort and degrades to "no trunk resolved" on an unexpected shape. Best-effort — any overlay failure leaves both VLAN fields null/empty on every row and the interface scrape proceeds. Strictly additive to the SNMP IF-MIB walk. **Interface MAC fold**: when the scrape returns interfaces, EVERY interface MAC (monitored or not) is reconciled into `AssetMacAddress` (source="monitor-interface") via `reconcileInterfaceMacs` — contiguous MACs coalesce into `[mac, macEnd]` range rows (a 48-port switch stores one row), full-replace scoped to that source only so rows owned by discovery/agent/manual writers are never touched. Gated on the scraped-MAC set being non-empty, so the no-MAC case costs zero extra round-trips.
│   │   ├── sampleWriteBuffer.ts     # Periodic batch-flush buffer for the six append-only monitor sample tables (asset_monitor_samples / asset_telemetry_samples / asset_hardware_sensor_samples / asset_interface_samples / asset_storage_samples / asset_ipsec_tunnel_samples). Per-table in-memory arrays + a 2 s `setInterval` flush + a 5,000-row size threshold for burst publishers (e.g. a manual probe-all-now). `flushTable` snapshots the array up front so concurrent enqueues during the awaited `createMany` land in a fresh buffer; on flush failure the snapshot is re-prepended for the next tick's retry. Deadlock retries go through `retryOnDeadlock` (3 attempts, 25-75 ms jitter — same as `reconcileMacAddresses`). Flush duration is observed via the existing `polaris_sample_write_duration_seconds{table}` histogram; current depth per table is exported as `polaris_sample_buffer_depth{table}`. Trade-off: up to 2 s of sample rows are lost on a hard crash — acceptable because samples are an append-only time series and the next cadence tick re-supplies fresh data. **State-side writes (Asset.monitorStatus / counters / lastMonitorAt / monitorStatusChangedAt) live in the companion `probePatchBuffer` with last-write-wins-with-stamp-preservation semantics** instead of this append-only buffer; same 2 s window but different shape because state needs replace semantics and the buffer needs to serve reads (the state machine's threshold counters require read-your-writes). `shutdownFlushSampleBuffers()` is awaited from the SIGTERM/SIGINT hook in `src/app.ts` so a graceful restart doesn't drop the in-flight buffer. **The buffer covers only the six DETAIL tables — the twelve rollup tables (`*_hourly` / `*_daily`) use `INSERT ... ON CONFLICT DO UPDATE` from `sampleRollupService.ts` instead** because rollup writes need upsert semantics (idempotent re-runs over the same window must rewrite buckets in place); the append-only buffer contract intentionally has no upsert path.. **The monitor rollup scans ALL probeKinds but keeps its row-count and RTT columns PRIMARY-only** (a `PRIMARY` fragment FILTERed onto every one of them). The two column families describe different transports: sampleCount / successCount / failureCount / dependencyFailureCount are the operator's configured status poll — `probeOutageService` reads them to decide what an outage looked like — while `packetsSent` / `packetsReceived` sum the ICMP burst sweep. The WHERE clause used to exclude `probeKind='icmp'` outright, for a reason that expired with the per-asset SAMPLER it was written for: that ran only during warning/recovering windows, so folding it into 400-day aggregates counted quiet and incident-heavy months at different sampling rates. The sweep that replaced it is UNIFORM (business rule 29), which is exactly what makes it comparable across time and worth rolling up. Packets are SUMMED, never averaged, so a long range stays a true packets-lost/packets-sent ratio rather than a mean of per-bucket percentages; and they stay **NULL rather than 0** where no sweep row exists — including in the daily roll-up, deliberately unlike `dependencyFailureCount`, whose 0 is a truthful "none" where 0 packets sent would claim a 0%-loss day for a day nobody measured
│   │   ├── probePatchBuffer.ts      # Companion to sampleWriteBuffer for the STATE-side write inside `recordProbeResult`. Replaces the per-probe `prisma.asset.update` (one Prisma pool connection per probe; the dominant remaining per-tick connection draw on the monitor hot loop at 2000+ assets) with an in-memory `Map<assetId, ProbePatch>` flushed as one bulk `UPDATE … FROM (VALUES …)` statement per 2 s window. Last-write-wins per asset within the window EXCEPT `monitorStatusChangedAt`, `lastUptimeSec`, `lastRebootAt`, `lastSeen`/`lastSeenSource`, `recoveryStartedAt` (the packet-loss recovery anchor -- an ordinary probe merging onto the recovery probe must not erase it, or the loss ratio keeps counting the outage), and `awaitingRecoveryConfirm` (the recovery confirmation run's one bit of memory, business rule 36 -- note it is a BOOLEAN, so the merge and the flush both use `??` / COALESCE rather than truthiness: `false` is a real value that has to land), which are preserved on merge (and COALESCE'd in the flush SQL) so a transition stamp / SNMP uptime reading / reboot stamp isn't NULL-erased by a subsequent same-window probe that didn't carry one (e.g. a non-SNMP probe has no uptime). The state machine reads its own writes via `getPendingProbePatch(assetId)` — `recordProbeResult` overlays the in-flight patch onto the loaded Asset row BEFORE computing the next state, so two failed probes in the same window correctly advance `consecutiveFailures` to 2 instead of both computing it as 1 against the on-disk 0. On flush-retry-exhausted failure, the snapshot is conditionally re-prepended (only entries the buffer no longer holds — concurrent enqueues represent fresher state and win). Trade-off: up to 2 s of state writes lost on hard crash, and the `monitor.status_changed` Event / `propagateAfterStatusChange` / `triggerRetryAfterStatusChange` side effects that fire on transitions run against in-memory `(previousStatus, nextStatus)` values and don't wait for the flush — propagate/retry hooks then read the DB before the buffer lands, so their effects can lag by up to one flush window before the 60 s `dependencyReconciler` and `retryQueuedReservationPushes` ticks catch up as the sources of truth. Acceptable because the state machine is self-healing within one additional probe cycle. Exports `polaris_probe_patch_buffer_depth{table=assets:probe}` gauge + `polaris_probe_patch_write_duration_seconds` histogram. `shutdownFlushProbePatchBuffer()` awaited from the SIGTERM/SIGINT hook so a graceful restart doesn't drop in-flight state.

│   │   ├── probeOutageService.ts    # "When was this device unreachable?", read from the response-time probe stream for the charts of streams that have none of their own.
