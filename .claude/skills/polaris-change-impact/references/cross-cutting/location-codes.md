## cross-cutting/location-codes

**What it is:** Physical-location codes (`a:` area / `b:` building / `f:` floor / `r:` room / `ra:` rack / `jb:` junction box, e.g. `a:Mine b:Shop f:2 r:North Closet ra:R2 jb:112-305` — `ra:` added 2026-11-10, nested between room and junction box; `TOKEN_RE` lists `ra` before `r` so a rack is never read as a room) embedded in FortiSwitch/FortiAP admin descriptions and/or Asset notes/description, parsed server-side by `src/utils/locationCodes.ts` and shipped per topology node as `location: {area, building, floor, room, junctionBox} | null`. Drives three Device Map features: grouping hulls (nested rounded rectangles color-coded per level — area rose > building sky-blue > floor violet dashed > room green > jb amber dashed, fitted inside-out with a sibling-separation sweep so no two shapes overlap; `collapseLocationChains` drops every box whose devices are exactly those of a box nested in it (a single-child chain draws only its innermost box, the dropped levels riding on `locAbsorbed` for the hover), a box with no box inside it uses `LOC_LEAF_PAD` instead of its level padding, and member labels count toward the bottom wall; synthetic bottom-layer Cytoscape nodes so `cy.png()` screenshots include them), full-tier (area→building→floor→room→jb) sibling row clustering in the column solver (anchors, fallback-exile roots, AND each parent's leaf block — so room/jb hulls come out as tight contiguous bands), and a one-row-per-level drill-down switcher ("Base" = the whole-site `flat` view; then every root view — areas first, then anything with no area; then, for each view on the selected path, the views directly inside it — `topology-render.js → viewSwitcherRows()`). Views exist for every level (`VIEW_LEVELS`: area `a|<a>` only beside a deeper code, building `b|<a>|<b>`, floor `f|<a>|<b>|<f>`, room `r|<a>|<b>|<f>|<r>`, jb `jb|<a>|<b>|<f>|<r>|<jb>`, a skipped level an empty segment — the same keys as the boxes), and each view's parent is the nearest level the device HAS (`ancestors` / `parentKey`), so an area lists a room tagged straight into it beside its buildings (operator, 2026-11-09). `viewSuppressKinds(key)` (map.js, mobile) hides the view's level and every level above it; the widget's pin containment is `ancestors` with cross-view portal stubs. An `a:` code earns an area view only beside a `b:` or `f:` code. Notes are operator-only — discovery never writes them on an existing asset (CLAUDE.md business rule 15).

**Writers** (files that mutate or emit this state):
- `src/services/fortimanagerService.ts` — FMG capture: switch `description` from the already-fetched `/sys/proxy/json` managed-switch CMDB rows (`descriptionBySerial`, zero extra RPCs); AP `location` (preferred — the sync surface; the only field in FMG's copy under central AP management) + `comment` fallback in the Step 3d.4 WTP CMDB roster fields, joined onto `localAps` (zero extra RPCs). `DiscoveredFortiSwitch.description` / `DiscoveredFortiAP.description`.
- `src/services/fortigateService.ts` — standalone capture: `fetchFortiswitchCmdbMeta` (renamed from `fetchFortiswitchUplinkPorts`; returns `Map<serial, {uplinkPort, description}>`) + best-effort `fetchFortiapDescriptions` (`GET /api/v2/cmdb/wireless-controller/wtp`, `location` preferred / `comment` fallback; 404/any error → empty map, never fails discovery).
- `src/services/discovery/discoveryEngine.ts` — `buildDeviceDescriptionStamp(description)` computes `{deviceDescription}` (merged into `swTopology`/`apTopology` every cycle). The former description→notes mirror (and `shouldSyncDescriptionToNotes` gate + `notesSyncedFrom` provenance) was removed 2026-07 — notes are operator-only; discovery seeds the `Auto-discovered from FortiGate …` boilerplate at creation and never writes notes again. `description` also lands in the fortiswitch/fortiap `AssetSource.observed` blobs (Sources-tab truth, not projected).
- `src/services/eventLogService.ts` — `notes` is in `MATERIAL_ASSET_FIELDS` so the device-driven notes overwrite surfaces via `logDiscoveryAssetUpdated` (only fires when notes actually change — no per-cycle Event flood).
- `public/js/map.js` — right-click (cxttap) description editor on asset-backed topology nodes: operator edit of `Asset.description` (with a:/b:/f:/r:/jb: shortcut hints in the popup, plus the nesting diagram `public/js/app.js → locationCodesDiagramHTML()` — also under the asset Edit form's Description hint in `assets.js`; its `LOC_DIAGRAM_TIERS` colours mirror `LOC_GROUP_KINDS`, held equal by `tests/unit/locationDiagram.test.ts`, so a hull colour change edits both) through the existing `PUT /assets/:id` route — so rule-14 description sync applies — then a silent topology refresh re-resolves codes. Gated client-side on `canManageAssets`.
- `src/services/topologyViewService.ts` → `applyLocationCodeChanges` (business rule 148) — the asset half of saving a Topology-mode view: each device dropped inside a group polygon takes that polygon's codes (`utils/locationCodes.ts → setLocationCodes`: the free text before the first code kept, every old code dropped, the new ones appended a: b: f: r: jb:), committed through `POST /map/sites/:id/topology/location-codes` at `assets=write` + the assets write scope, with an `asset.updated` Event and `syncDescriptionsOnSave` per changed asset. A drop outside every polygon writes nothing.

**Readers** (files that consume it):
- `src/services/topologyGraphService.ts` (the map topology GET's graph builder) — selects `notes`/`description` on the FG + sibling queries, reads `fortinetTopology.deviceDescription` (`TopologyMeta`), and emits `location` (via `resolveEffectiveLocation`: the description's codes when it carries any, exclusively; else deviceDescription's) + raw `deviceDescription` per node. FortiGate: description only.
- `public/js/topology-render.js` — `locationData()` stamps `locA/locB/locF/locR/locRa/locJb` grouping keys (+ `loc*Name` display casing) onto node data; the solver clusters through the FULL tier chain via `stableBucketByTiers` (`LOC_TIERS = [locA, locB, locF, locR, locRa, locJb]`, synthetic `"\tnone"` bucket for tier-skipping codes): `regroupAnchorsByLocation` on non-spine sibling anchors AND fallback-exile roots (spine selection untouched — cross-subtree adjacency deliberately NOT guaranteed), plus pass 5b ordering each parent's leaf block so same-room/jb leaves take contiguous lanes; `computeLocationGroups`/`renderLocationGroups`/`refreshLocationGroups` draw the hulls (`LOC_GROUP_KINDS` padding/shape tiers, `z-compound-depth: bottom`); `computeFloorViews`/`partitionElementsForFloor`/`compareFloors` (underground-aware: `-2 < B1 < 1 < Mezzanine`) build the area / building / floor / room / jb views + portals, `viewSwitcherRows` the switcher's rows as data; `routeInterGroupEdges` (each device's outermost box from the top boxes' `memberIds`, never from its area/building codes — a collapsed chain's outermost box can be any level) fans out BOTH corridor axes in 9px steps (incl. the straight-into-target-row corridor, so parallel horizontal runs never combine into one line).
- `public/js/map.js` — location boxes always render when codes exist (the Locations chip and its `polaris.topology.showLocations` pref were removed 2026-10-26), Snap devices corner tool (`polaris.topology.snapToGrid`, default OFF, edit mode), location-view switcher chips (top-left, drawn from `viewSwitcherRows`; `topoState.activeView`, never persisted), portal tap → `_setTopologyView`, per-view position persistence (server `TopologyLayout` first via the payload's `savedLayouts[view]`, localStorage `polaris.topology.positions:<siteId>[:<viewKey>]` fallback), hull suppression (`suppressKinds`: `["area"]` in an area view, `["area","building"]` in a building view, `["area","building","floor"]` in a floor view), `[isLocGroup]`/`[isPortal]` exclusions in `saveNodePositions` + `_openAssetForNode`.
- `public/js/mobile/topology-tab.js` — flat hulls only (always-on, rendered on layoutstop; no switcher in v1).

**Invariants:**
- **Free text goes BEFORE the codes when Polaris writes them** — a code's value runs to the next code or the end, so text after the last code would be read as part of its value. `setLocationCodes` is the only writer that builds a description from codes; `locationCodeValueProblem` refuses a value holding another code.
- The grammar lives ONLY in `src/utils/locationCodes.ts` — the client receives resolved display values and normalizes grouping keys with the trivial `locKey()` (trim/collapse/lowercase, mirroring `locationGroupKey`); never re-implement token parsing client-side.
- `fortinetTopology` is written WHOLESALE by the switch/AP sync blocks — `deviceDescription` must ride every `swTopology`/`apTopology` object or it's silently dropped on the next cycle.
- Discovery must never write `Asset.notes` on an existing asset — notes are operator-only (the description→notes sync was removed 2026-07; boilerplate at creation is the sole exception).
- Synthetic nodes (`isLocGroup`, `isPortal`, and the connection-path handles `isEdgeHandle` from `topology-edge-editor.js`) must stay out of: position persistence (`_currentNodePositions` — a handle's geometry is saved as its path's `edgepath:` entries instead), the column solver input (hulls and handles are added after layout), `computeLocationGroups` membership, asset-open tap handling, grid snapping, and the hull re-fit `position` listener. Portals and path handles are the only interactive synthetic nodes. A line with a drawn path is marked `customPath` and owns its geometry: `routeInterGroupEdges` and the Locations toggle's style reset skip it, and handles draw above devices at the default (auto) `z-index-compare` — `manual` sorts them UNDER every device, so pressing an end point grabs the device. The desktop graph's `selectionType` is `single` (a plain click replaces the selection; a held Shift adds). Hulls are created `selectable: false` so a box-select never sweeps one in — a selected hull would ride along on the next device drag and its own drag handler would move its members twice — and map.js makes a hull selectable only for as long as a CLICK keeps it selected (`selectify` on tap, `unselectify` on unselect). Path handles are dropped from a box-select (`boxselect` → unselect) so Delete never removes a point nobody picked. The modal opens **view-only** (`topoState.editing` false → `cy.autoungrabify(true)` plus every node `panify()`d — an `add` listener covers group boxes rebuilt after layout — so a drag on a device or box pans, as on the phone; editing `unpanify()`s them and Ctrl+drag pans; the edge editor's `isEditable` false: drawn paths draw, no bends / handles / Delete; Save, Reset and the edit-only corner tools — Grid, Snap devices, Snap line points — hidden, the grid undrawn); the floating `#topology-edit` button (the dashboard's Customize pencil / Done check) flips it through `_applyTopologyEditMode`, which also runs at the end of every render so a refresh keeps the mode. Never persisted — every open starts view-only.
- The FortiGate is drawn only in **Base** and in the location views its own codes place it in. Every other view replaces it with a ROOT portal (`isPortal` + `isRootPortal`, id `portal:<fgId>`, label `→ Base: <FG>` or `→ <its view>: <FG>`, `targetView` `flat` or its view key) — `partitionElementsForFloor` rewires member↔FG links onto it and drops FG links with no member end. `computeTopologyColumns` places a root portal as a `fortigate` and roots on it when no real FortiGate is in the set, so the view keeps the column layout instead of falling to dagre. Re-adding the real FortiGate to every view puts it in every lower group (the 2026-10-26 operator report); `topologyFloorViews.test.ts` pins both cases.
- descriptionSyncService interplay (rule 14): with description sync ON for the device class, description codes are Polaris-primary — a code edited in Polaris pushes to the device; device-side code edits are overwritten unless the Polaris description is empty (adopt). Maintain codes in Polaris.

**When changing this:**
- Adding a code key (e.g. `ra:` rack)? Extend `TOKEN_RE` + `KEY_TO_FIELD` in locationCodes.ts (longest-match order!), the `LocationCodes` type, `locationData()` stamps, `LOC_GROUP_KINDS` (shape/padding tier), the legend `locations` section, and the parser tests.
- New discovery pathway for switches/APs? Capture the admin description into `Discovered*.description` and route asset writes through `buildDescriptionSyncStamp` — both FMG and standalone (parity rule).
- Touching the solver's sibling ordering? `regroupAnchorsByLocation` must stay stable and a no-op on keyless sites — the `topologyColumns.test.ts` legacy-order cases enforce this.
- FortiOS field variance: managed-switch `description` presence and wtp `location` support vary by firmware (descriptionSyncService already flags `wtp_location_unsupported`) — verify on a real device before relying on a new field.

---

**Group and view keys with a rack.** A rack's box key is `ra|<a>|<b>|<f>|<r>|<ra>`. A junction box's key keeps its pre-`ra:` shape `jb|<a>|<b>|<f>|<r>|<jb>` when the device has no rack, and only inside a rack gains the segment, `jb|<a>|<b>|<f>|<r>|<ra>|<jb>` (`topology-render.js → jbKey`, and `_viewKeyAt` skips an empty rack segment below its own level). That is what keeps layouts saved against a junction box before 2026-11-10 matching; a change that always inserts the rack segment orphans every one of them. `topologyLayoutService.isValidViewKey` accepts the `ra|` prefix. Adding a tier is a lockstep across `utils/locationCodes.ts` (type, `KEY_TO_FIELD`, `TOKEN_RE`, `CODE_ORDER`, `locationCodeValueProblem`), `topologyViewService` `CODE_FIELDS`, `alertDependencyPathService` (`BOX_STYLE`, inner box), `topology-render.js` (`locationData`, `LOC_GROUP_KINDS`, `computeLocationGroups`, `VIEW_LEVELS`, `LOC_TIERS`, `_LEVEL_KIND`, `_locPath`, `_ANON_KIND`, the legend), `map.js` (the code lists, `LOC_KIND_LABELS`, `_TOPO_LOC_TIERS`), `topology-physical.js` `CODE_FIELDS`, `app.js` `LOC_DIAGRAM_TIERS` (pinned equal to `LOC_GROUP_KINDS` by `tests/unit/locationDiagram.test.ts`) and the two description hints (assets.js, mobile/asset-edit.js).

**Short codes through the region tree (rule 153).** `topologyGraphService.buildSiteTopology` resolves every node's written codes through the site's `RegionNode` tree (`regionTreeService.resolveLocation`), so the payload's `location` is the FULL chain and `locationWritten` the codes as typed. Everything that reads the payload's `location` (Layer 2 boxes, lists, polygons, the region-mapped views, the info card) therefore sees full chains without a code change; the consumers that parse descriptions themselves resolve too — the alert dependency path (per device's site, `siteForAsset`) and the region prompt (`POST …/regions/resolve`) — and saved views' `region` / polygon codes come back resolved. A new consumer of codes must do the same, and a new place that STORES a region name must be added to `regionTreeService.carryStoredChains` or a rename orphans it. With an empty tree nothing changes.
