## cross-cutting/alert-acknowledgement

**What it is:** Every path from "an alert reached a human" to `Notification.acknowledged`. Three read surfaces, ONE write path, and — since business rule 25 — no credential anywhere in the link.

**The chain, in order:**
1. `utils/notificationTemplate.ackUrlForEmail(notificationId)` / `ackUrlForPush(notificationId)` build `/alert-ack.html?id=<id>`. Email is NULL without `POLARIS_PUBLIC_URL` (a relative link in an inbox resolves against nothing); push falls back to the relative path, which the service worker resolves against its own origin.
2. `notificationRecipientService.expandDeliveries` resolves the deferred `{ack}` **once per alert** through `fillComposedAckUrl` — the context was built before `prisma.notification.create` returned, so the id did not exist at compose time. A composed email is ONE delivery row, always — every recipient on one To line, whatever their role or timezone. It briefly went out as two (an ack copy and a no-ack copy, `splitAckVariants` + `ackCapabilityByAddress`); that was reverted on 2026-09-15 because a split To line hides from each reader who else is on the alert, which is the thing rule 25 collapsed the send to show.
2b. `expandDeliveries` also takes `noAck` — the WHOLE send carries no button, whoever reads it. `automationActionService.executeActions` sets it from `ctx["severity"] === "resolved"`, the pseudo-severity the three all-clear paths (`notificationEngine.fireResolved` / `fireReset`, `notificationService.runResetActionsForCleared`) already stamp to colour the email green. Every body is then `fillComposedAckUrl(body, null)` and every plain-email and web-push row is stamped `meta.noAck`. (Since 2026-09-15 this is the only thing that withholds the EMAIL button: a fire is one row too, so an all-clear no longer differs from it in row count — only in carrying no link.)
3. `notificationDeliveryService` puts the same URL in the plain-text tail (`appendAckLine`) and in the web-push payload's `ackUrl` — both skipped when fan-out stamped `meta.noAck`. Those two paths decide per ROW rather than per body, because each row already names one recipient (one address; one subscription, which always has an account behind it).
4. `public/sw.js` renders an Acknowledge action that **opens** that URL (same-origin checked via the shared `sameOriginOr`, `src=push` appended). It acknowledges nothing itself. It competes for two tray slots with **Open device** (the payload's `assetUrl`) and **Ignore** (sticky alerts only) — `ACTIONS` are listed in priority order and sliced to `Notification.maxActions`, so Acknowledge is never the one dropped. Adding a third candidate means deciding what it outranks, not just appending it.
5. `public/alert-ack.html` + `public/js/alert-ack.js` render the card. The page is in `app.ts`'s `protectedPages` and `pageRequiredPermission` (`alerts:read`). Its markup for the alert itself is `public/js/alert-ack-view.js` (`PolarisAlertAckView`) — lifted out when a second surface needed the same card, and loaded by the page before alert-ack.js.
5b. `public/js/alert-ack-modal.js` (`PolarisAlertAckModal.open`) is that card IN THE APP, opened from the Down Assets widget's row menu (`PolarisWidgets.openAssetRow`) — same shared markup, same states, same three properties (a 403 is a state not a toast; the note policy is the server's; it re-reads after the write). It sends **no `source`**: that closed set names the emailed page and the push action only. It also re-reads BEFORE showing the form, the widget row being up to 30s stale on top of the feed's 10s cache.
6. `utils/loginRedirect.ts` carries the reader back after a login, in two carriers — the `polaris_next` cookie, consumed by `public/js/login.js` (local/TOTP) and by auth.ts's OIDC / entra-proxy callbacks, and the SAML RelayState, which is what survives the IdP's cross-site POST to `/azure/callback`.
7. `GET /alerts/:id` → `notificationService.getNotificationForViewer`, then `POST /alerts/acknowledge` → `acknowledgeNotifications`.

**Invariants:**
- **The URL names the ALERT and nothing else.** No recipient, no user id, no token. The moment it names a person, the composed body stops being shareable and the per-recipient fan-out has to come back.
- **`acknowledgeNotifications` is the only write path**, and the only place the note policy is enforced. Every surface's required field is a local courtesy.
- **The note policy is answered for the ALERT'S SEVERITY, not the rule's** (business rule 56): a severity band may carry its own `followUp.requireAckNote`, so both the page's form (`getNotificationForViewer`) and the write path resolve through `ackNotePolicyOf` — one helper, so the form and the refusal cannot disagree. A band that states nothing inherits the rule's flag. (The same rule's other half, per-action reminders, touches nothing here: acknowledging is what STOPS them.)
- **Loading is a GET, acknowledging is a POST.** Mail gateways prefetch every link; a state-changing GET would acknowledge Polaris's whole outbound alert volume at scan time.
- **The PAGE gate is `alerts:read`, the ACTION gate is `alerts:write`.** A reader who cannot acknowledge must land on the page and be told so, not be bounced to "/".
- **A withheld button is a KNOWN refusal, never a guess — and on PUSH only.** A subscription always has an account behind it, so a role holding `alerts` < write gets no `ackUrl` and `sw.js` renders no tray action. EMAIL withholds from nobody: the button rides every copy and `/alert-ack.html` refuses a read-only reader with a reason, which is what "the page decides" always meant. The role policy underneath is migration `20260828030000_alerts_ack_write_capable_roles` — every role holding write anywhere else holds `alerts:write` — so what is left is a genuinely read-only role.
- **ONE email copy per notify action. Nothing splits it.** Not the reader's acknowledge capability, not their timezone (the body renders in the install's zone and names it — `{time.zone}`). Both splits existed, composed into (zones × 2) copies of one alert, and were invisible from inside a copy: an operator who named two people saw one address on their own To line and read it as Polaris mailing each of them separately. Anything that splits a composed send again is the fan-out this rule exists to prevent — and it must first answer: can a reader still tell, from the copy in their hand, who else is on the alert?
- **An alert that is OVER carries no button, on any surface.** "May this reader acknowledge" and "can this alert be acknowledged" are different questions, and the second one is answered for the whole send: the all-clear's notification is cleared in the same breath its reset actions are enqueued, so the button's only destination is `alert-ack.html`'s "already cleared" state — and on a rule with `requireAckNote`, a 400 asking for a note about an outage that is over first (`acknowledgeNotifications` filters on `acknowledged: false`, never on `cleared`). The signal stays the pseudo-severity rather than a second flag, so a new all-clear path gets the behaviour by writing the line it already writes.
- **`GET /alerts/:id` answers 404, not 403**, for an alert outside the caller's region scope.
- `source` on the acknowledge POST is a CLOSED set (`ack_page` | `web_push_action`) and audit provenance only — it lands in an Event's `details`, so it must never accept free text.
- `polaris_next` is NOT HttpOnly (login.js reads it) and is therefore only ever safe because `safeNextPath` reduces it to a same-origin path and refuses `/login.html`. The same reduction runs on the path a RelayState brings back, which is untrusted for a second reason: it round-tripped through the IdP.
- **The link has to survive the login that follows it, on EVERY provider** — an Acknowledge button that lands the reader on the dashboard is the alert lost, and they go back to the mail and click it again. One carrier does not cover five paths: `SameSite=Lax` is not sent on the SAML callback's cross-site POST (which is why the cookie goes out `None` on HTTPS), and `None` needs `Secure`, which needs `req.secure`, which a proxy that drops `X-Forwarded-Proto` leaves false (which is why RelayState carries it too). Changing either carrier means re-checking all five: local, TOTP, SAML, OIDC, Entra App Proxy. The price of `None` is that a cross-site SUBRESOURCE can provoke a cookie the browser now keeps, so `rememberLoginTarget` writes one only for a top-level navigation (`Sec-Fetch-Dest: document`, or the header absent) — otherwise a foreign page's `<img>` picks the operator's next landing.

**When changing this:** a new acknowledge surface calls `POST /alerts/acknowledge` with its own `source` — never a private write. A change to the URL shape has to move `ackPath` in `notificationTemplate.ts` (both helpers read it), the `protectedPages` entry, and `tests/unit/alertAckPage.test.ts`, which pins that the URL carries no recipient. A change to WHO gets a button touches the push branch's `canAcknowledge` read in `expandDeliveries` + the `meta.noAck` readers in `notificationDeliveryService`, and is pinned by `tests/unit/alertAckRecipientGate.test.ts` — which now pins the opposite of what its name suggests for email: that a read-only recipient rides the SAME message. A change to WHICH SENDS get one at all touches the `noAck` option and the `ctx["severity"]` gate in `automationActionService` — a new kind of send that should carry no button is a caller-side decision, not a new branch inside the expander, and a new all-clear path only has to stamp the `resolved` pseudo-severity it already needs for the colour. Anything that would make the link per-recipient again needs business rule 25 rewritten first: the fan-out it forces is what the rule exists to prevent.
