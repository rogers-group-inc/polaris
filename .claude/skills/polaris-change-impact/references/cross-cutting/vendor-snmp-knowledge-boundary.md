## cross-cutting/vendor-snmp-knowledge-boundary

**What it is:** The rule for where a vendor-specific SNMP fact may live, and the test that enforces it. Decided 2026-09-15: **Polaris ships the engine and the IETF/IEEE standard MIBs; every vendor-specific fact is data the operator owns.** A vendor's OIDs come from the MIB the operator uploads and resolve by SYMBOL NAME through `services/oidRegistry.ts → resolveOidSync()` at the asset's (manufacturer, model) scope; the vendor *mapping* (which symbol means CPU, which table is the sensor table) lives in `ManufacturerProfile` rows. A vendor changing or adding an object is fixed by uploading a MIB or editing a profile — never by a Polaris release. This is the property SolarWinds' monolithic MIB database lacks, and it is what makes coverage for a lesser-known product a shareable file instead of a release.

The line, stated once: **an OID under the enterprises arc (`1.3.6.1.4.1.*`) never appears as a literal in `src/`.** Standard arcs (`1.3.6.1.2.1.*` mib-2, `1.0.8802.*` IEEE) may stay numeric — they are vendor-neutral. Decoding and structure logic (a MAC packed in a table index, an enum, a `::`-separated string, a column join) may remain code until a declarative form exists for it: code may know *how a table is shaped*, never *where a vendor put it*.

**Writers** (files that hold or change vendor SNMP knowledge — the burn-down):
- `src/services/oidRegistry.ts → BUILT_IN_OIDS` — **done (Phases 1 + 3).** Now 21 SMI/IETF/IEEE scaffolding arcs only; the 15 vendor ANCHOR arcs (`fortinet`, `fnFortiSwitchMib`, `cisco`, `juniperMIB`…) and 18 vendor LEAF telemetry symbols (`fsSysCpuUsage`, `fapTemperature`, `cpmCPUTotal5secRev`…) are gone, and the two BRIDGE-MIB anchors with them (the standard layer resolves the bundled modules together). Off the guard's allowlist.
- `src/services/monitoringService.ts → OID` — a second hardcoded map, 11 enterprise entries (fgHwSensor×3, fapSta×4, fapRadio×2, fsTrunkMember×2) walked directly by `collectHardwareSensorsFortinetSnmp` / `collectWirelessStationsSnmp` / the trunk-map block, never through the registry. Become symbol names in **Phase 5a**.
- `src/utils/fortiapRadioSnmp.ts → FAP_RADIO_OID / FAP_VAP_OID` — 14 FortiAP column OIDs + 2 entry roots. Become symbol names in **Phase 5a**.
- `src/services/vendorTelemetryProfiles.ts → VENDOR_TELEMETRY_PROFILES` — the per-vendor mapping (symbol names, walk semantics, a JS `parse` function for the FortiSwitch model string, a `match` regex). Carries no OID literals, so the guard does not see it; it becomes seed data only in **Phase 4**, when `ManufacturerProfile` rows become the runtime authority.
- The dispatch keys `/fortinet/i.test(manufacturer)` (sensor-table walk) and `assetType === "access_point"` (station/radio walks) in `monitoringService.ts` — replaced by profile data in Phases 4 and 5a.

**Readers** (what depends on the line holding):
- `tests/unit/noEnterpriseOids.test.ts` — the guard. Walks `src/**/*.ts` (skipping `src/generated/`), strips comments, fails on `1\.3\.6\.1\.4\.1\.\d` in any file not in `ENTERPRISE_OID_ALLOWLIST`. Three properties keep it honest: a planted-literal self-check (the scanner cannot go vacuously green), a file may not leave the allowlist while it still has a literal, and a file may not STAY on it once its literals are gone. Terminal state: the allowlist is empty.
- `src/utils/snmpIdentity.ts → enterpriseFromSysObjectId()` — the one place the enterprise arc appears in code, as the escaped regex `1\.3\.6\.1\.4\.1\.(\d+)` that extracts an IANA enterprise NUMBER to name a vendor (`SNMP_ENTERPRISE_VENDORS`, 42 PENs). Identity, not telemetry: it is an IANA registry fact and the OID is never walked. An escaped regex never matches the literal pattern, so the file needs no allowlist entry; the guard pins that it keeps that shape and grows no walked OID behind the identity story.
- Every SNMP collector that calls `resolveOidSync()` and treats `null` as "unsupported at this scope" — the graceful path the boundary relies on (`collectCpuVendor` logs *"vendor CPU symbol unresolved — upload its MIB to enable"* and returns null; `collectAndRecordCustomWidgets` `continue`s).

**Invariants:**
- No enterprise-arc OID literal in `src/` outside `ENTERPRISE_OID_ALLOWLIST`; the allowlist only shrinks.
- Symbol NAMES in code are legal — they are the seed defaults a profile is created with, and a name is inert without a MIB. Only the number is banned.
- An unresolved symbol degrades to "this stream is not collected for this asset", with a log line naming the symbol; it never throws mid-probe and never wipes existing inventory rows (`undefined` = unsupported, `[]` = queried and empty).
- Identity (enterprise number → vendor name; OUI → vendor; sysDescr layout parsers) and telemetry (which object to walk) stay separable — `snmpIdentity.ts`, `snmpDescrIdentity.ts` and `ouiService.ts` hold no telemetry OIDs.

**When changing this:**
- Adding a new SNMP collector: name the MIB symbols, resolve them with `resolveOidSync(symbol, { manufacturer, model })`, decide the discriminator column whose absence means "unsupported", and add the file to nothing — the guard should pass without an allowlist edit. If it does not, the design is wrong, not the test.
- Removing literals from an allowlisted file: delete its `ENTERPRISE_OID_ALLOWLIST` entry in the same commit — the "still needs its exemption" case fails otherwise, by design.
- Standard-arc OIDs in code are tolerated, not encouraged: a standard MIB is bundled under `src/services/stdMibs/`, so a symbol name resolves there too (once Phase 1 lands). Prefer the name.
- The phases this boundary is delivered in, each its own worktree: **0** the guard (this entry) · **1** shipped standard MIBs become the registry's base layer · **2** readiness — upload responses and profile rows name the module a symbol needs · **3** the vendor seed leaves `BUILT_IN_OIDS` (a hard break for installs with no vendor MIBs, made visible by 2) · **4** `ManufacturerProfile` rows become the runtime authority, gated by a parity test against today's merge · **5a** collector OIDs become symbols (decoders stay code) · **5b** the hardware-sensor table becomes the first declarative table stream · **6** profile packs (export/import by MIB module name). The owner's framing, worth keeping: "baking in some OIDs and not others is weird; SolarWinds bakes in ALL and updates monolithically, which leaves lesser-known products behind."
