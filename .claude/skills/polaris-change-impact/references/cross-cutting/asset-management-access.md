## cross-cutting/asset-management-access

**What it is:** `Asset.managementAccess` is a read-only summary of a Fortinet device's management-access (`allowaccess`) config: `{ source, interfaceName, profileName, mgmtIp, protocols: string[] | null, https, ssh, snmp, checkedAt }`. Read during FMG/FortiGate discovery; drives the asset slide-over's Open HTTPS / Open SSH buttons, the SAME verbs in the Assets list row menu, and the FortiAP SNMP-disabled warning. Monitor/discovery-owned — never projected from `AssetSource`. **The blob is not the only source of a remote-access verb:** `_assetMgmtAccess` also offers Open RDP + Open SSH for `assetType === "server"` off the TYPE alone, there being no allowaccess to read on a Windows or Linux host — same function, same optimistic posture, no backend field and no new payload (the list already ships `assetType` + `ipAddress`).

**Writers** (files that mutate this state):
- `src/services/fortinetManagementAccessService.ts → summarizeGateManagementAccess` — builds one gate's summaries, keyed by serial, from the tables that gate's OWN discovery pass read (pure; nothing here talks to a device). Its callers are the two collectors: `fortigateService.discoverDhcpSubnets` (standalone FortiGate AND FortiManager direct mode — `allowaccess` rides `FORTIOS_INTERFACE_CMDB_FORMAT`, `wtp-profile` rides `FORTIAP_WTP_DISCOVERY_FORMAT`, plus one `wireless-controller/wtp-profile` read on a gate with APs and one `switch-controller.security-policy/local-access` read on a gate with switches) and the FortiManager proxy path in `fortimanagerService` (FMG's DEVICE DB, native lane only: `allowaccess` on Step 1's `global/system/interface`, `wtp-profile` on Step 3d.4's wtp roster, and `fmgStepMgmtAccessTables` (Step 3d.6) for the two extra tables — device DB first, then the ADOM `obj/wireless-controller/wtp-profile` table / the `vdom/root` local-access scope). Both put the result on `DiscoveryResult.managementAccess`. A managed switch has no per-device profile the way an AP does, so its list comes from the controller's local-access POLICY — `parseLocalAccessPolicies` (name → `{mgmt, internal}`), `pickLocalAccessPolicy` (the `default` policy, which is the one in force: the policy is FLEET-WIDE, FortiOS offering no per-switch attachment — confirmed against prod 2026-09-03; a site with one renamed policy resolves to that one), `localAccessHalfFor` (`mgmt*` interface → `mgmt-allowaccess`, everything else → `internal-allowaccess`). Every parser accepts both encodings (FortiOS REST strings, FMG device-DB string arrays / one-element reference arrays / `[addr, mask]` ips) and returns `null` for anything else. Pure parsers exported + unit-tested.
- `src/services/discovery/dhcp/finalizeReconciles.ts → runFinalizeReconciles` (syncDhcpSubnets Phase 13.6) — WRITES `result.managementAccess`: joins serial → asset via the `AssetSource` rows (externalId === serial), writes in chunked `$transaction` batches. Makes no device or FortiManager call (pinned by `tests/integration/managementAccessPhase.test.ts`). Gated `mode in {full, finalize, finalize-scoped}`; always-on; FMG/FortiGate only; best-effort. A device absent from the list keeps what it had.

**Readers** (files that consume it):
- `public/js/assets.js` — `_assetMgmtAccess` / `_managementAccessButtonsHTML` (slide-over header Open HTTPS + the Open RDP and Open SSH split-buttons) + `_managementAccessNoticeHTML` (AP warning banner) + `_managementAccessMenuItems` (the same verbs in the Assets list ROW MENU, off `_assetMenuItems`; one flat item per verb performing the operator's stored default rather than the header's caret submenu). Both split buttons are wired by the ONE shared `_wireRemoteAccessMenu(cfg)` (`kind` → `btn-asset-<kind>` / `asset-<kind>-menu` / `data-<kind>` ids, `actionKey` → the localStorage default) and one document-level closer (`_assetRemoteMenuCloserWired`) closes both menus. SSH launch via `ssh://[user@]host` URI or copy-command, per-user prefs in localStorage (`polaris-ssh-action`, `polaris-ssh-user`). RDP launch via a generated `.rdp` file (the DEFAULT — mstsc.exe registers no URL scheme, only the Microsoft Remote Desktop app family honors `rdp://`), the `rdp://` URI (`_rdpUri`, pure), or a copied `mstsc /v:<host>`; prefs `polaris-rdp-action` ∈ {file, uri, copy} + `polaris-rdp-user`. `_rdpFileBody` writes address + maximized window + optional username and NEVER a credential — `prompt for credentials:i:1` leaves that to the client, so nothing sensitive lands in the download. `managementAccess` rides on the `GET /assets/:id` payload (full-row `include`, no narrowing select) AND on the list payload — `ASSET_LIST_SELECT` selects it and `shapeManagementAccess` in `src/services/assetListService.ts` reduces it to `{ mgmtIp, protocols, https, ssh }`, the four fields the row menu gates on. `protocols` stays an array-or-null on the wire because NULL is the "couldn't read it" signal the client branches on; collapsing it to a boolean would erase that. Both consumers gate through `_assetMgmtAccess`, so the row menu and the slide-over can never disagree about which protocols a device permits.
- `public/js/assets.js` — the asset-details General tab's three UPSTREAM rows (`_upstreamRowHTML` / `_upstreamMenuItems` / `_upgradeUpstreamRow`): Last Seen Switch / AP / Firewall each carry a row menu whose verbs come from `_managementAccessMenuItems` applied to the RESOLVED device's stub, so a FortiSwitch offers exactly what its controller's local-access policy permits. Two-pass: the value paints as plain text off the asset row, then `GET /assets/:id/upstream` upgrades the ones that resolved. A name resolving to no asset stays text — never a trigger that pops an empty menu.
- `src/services/assetUpstreamService.ts → resolveAssetUpstream` — attaches `shapeManagementAccessForClient(asset.managementAccess)` to each resolved upstream device, which is what lets the rows above gate their verbs through the same `_assetMgmtAccess` the list and the header use.
- `tests/unit/assetUpstreamRowsDom.test.ts` — pins the upstream rows: the shared gate (https-yes/ssh-no on a policy-read switch), unknown-is-not-denied, unresolved-stays-text, and the port half staying outside the trigger.
- `tests/unit/assetRowMenu.test.ts` — pins the row-menu half (which protocols each shape offers, the unknown-access-list optimism, the server's type-inferred RDP + SSH, and that the verbs ride no Polaris permission).
- `tests/unit/assetRemoteAccessRdp.test.ts` — pins the server half end to end: the type-driven gate (RDP + SSH, never HTTPS; never RDP on a Fortinet device; no other type inherits it; still needs an address), the rendered split button, the `.rdp` body, and the file-not-URI default.

**Invariants:**
- Read-only — nothing here writes the device. `protocols: null` means the access list couldn't be read (best-effort switch path); the UI renders buttons optimistically with an "unverified" note rather than hiding them. A server has no blob at all, which reads as the same unverified state.
- **One gate, two sources.** Every surface offering a remote-access verb resolves it through `_assetMgmtAccess` — never by testing `assetType` or the blob itself — so the row menu and the slide-over header cannot disagree about what a device offers. Adding a verb means adding a `show*` flag there and rendering it in both consumers.
- Firewall management interface is the operator-named `Integration.config.mgmtInterface` (reused, not a new field). FortiSwitch defaults to `internal` (override: `config.switchManagementInterface`), and that same value picks which HALF of the local-access policy is read — change one and the other follows.
- **A policy that states no list for the half in use is still `null`, never `[]`.** An empty allowaccess reads as "no protocol permitted", which is a positive claim the payload never made and which would hide both verbs on a device that may well accept them.
- `shapeManagementAccessForClient` (in the service) is the ONE reducer to the four fields a browser gates on. `shapeManagementAccess` in `src/services/assetListService.ts` delegates to it; a second copy is how the list and the upstream rows start disagreeing about a device.
- **The switch policy is fleet-wide.** There is no per-switch local-access attachment in FortiOS (confirmed against prod 2026-09-03), so `default` governs every managed switch a controller has. The per-switch interface `allowaccess` and the shape-matched assignment lookup that used to run first were dropped 2026-11 (never seen on any firmware, and they cost a whole managed-switch table per gate). If firmware ever grows one, match on the key's SHAPE rather than a guessed literal — a wrong literal resolves to nothing silently.
- **Collected in the gate's pass, never in a second sweep.** Until 2026-11 Phase 13.6 re-read every gate after the run — up to five whole tables per gate, on the concurrency-1 proxy lane in proxy mode, and a management-IP lookup per gate in direct mode that missed every HA pair (`0.0.0.0` on the mgmt interface), silently. A new input to the summary rides a read the collector already makes, or is one narrow read in the same pass; adding a field to a `format=` list means adding it to the fixture in `tests/unit/fortiosDiscoveryFormats.test.ts`.
- **An unreadable value is `null`, never `[]`** — at every level: `parseAllowaccess` (a number / object / odd array entry), a profile the profile table does not list, a local-access half that is unstated. `[]` would claim "nothing permitted" and hide the buttons.
- FortiAP REST field shapes are still **not verified on a live FortiOS 7.x device**, and the FortiManager device-DB shapes of `allowaccess` / `wtp-profile` and the two Step 3d.6 paths are **not verified on a live FortiManager** — keep parsers defensive (never throw; degrade to `protocols: null`). Verify with the integration console's "FortiAP profile access" / "FortiSwitch local-access policy" presets.
