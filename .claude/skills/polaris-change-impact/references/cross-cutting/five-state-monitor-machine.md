## cross-cutting/five-state-monitor-machine

**What it is:** Asset.monitorStatus ∈ {up, warning, recovering, down, unknown, passive} driven by the `consecutiveFailures` **leaky bucket with a CEILING** — a miss adds one, an answer takes one back floored at 0, and the level LOCKS at `bucketCapFor(missedPolls, recoveryPolls)` the moment a miss declares the outage (business rule 30). The machine is TWO PURE FUNCTIONS, `nextFailureBucket` + `monitorStatusFor` in `src/utils/monitorStatus.ts`, which every writer CALLS rather than reimplements. `consecutiveSuccesses` is still written but decides nothing at all: draining the bucket to 0 IS the recovery, and it costs exactly the cap however long the outage ran. `Asset.awaitingRecoveryConfirm` is DORMANT (2026-09-01) — the cap serves the automation's reset count through the drain, so nothing reads it.

**Writers** (files that mutate or emit this state):
- `src/services/fortinetLinkStateService.ts` — **a deliberate NON-writer, listed so the next person does not "fix" it.** It owns `Asset.fortilinkStatus` (business rule 59), the controller's own view of its FortiLink / CAPWAP session to a managed switch or AP, and it touches NOTHING here — not `monitorStatus`, not `consecutiveFailures`, not the bucket. Folding it in looks tempting ("the gate says it is down, so mark it down") and would destroy the feature: the entire value of that column is that it may DISAGREE with this machine. A switch reading `up` here with `fortilinkStatus=down` is answering ICMP while the gate has stopped managing it, which is a fault this machine is structurally unable to see, because it is asking the switch and the switch is fine. Down-detection authority stays business rule 36's.
- `src/services/monitoringService.ts` — runProbeFor() updates Asset.monitorStatus/consecutiveFailures/consecutiveSuccesses after each probe result, THROUGH `nextFailureBucket` + `monitorStatusFor` (never inline arithmetic — `tests/unit/monitorStatusStateMachine.test.ts` pins the call sites). It no longer writes `awaitingRecoveryConfirm`: that bit is dormant since the bucket cap took over the recovery count, business rule 36, stamps Asset.monitorStatusChangedAt whenever monitorStatus changes value (any-to-any, not just up↔down), emits monitor.status_changed Event on transitions INTO up/warning/down (not recovering/unknown, never per-poll), fires propagateAfterStatusChange() — but only on the confirmed up/down edge, NOT on the warning edge — to push the change into descendant dependencySuppressed state. **Reboot detection:** the SNMP probe (probeSnmp) now keeps the sysUpTime TimeTicks it already reads as its reachability OID and returns it as ProbeResult.uptimeSec; recordProbeResult stamps it onto the AssetMonitorSample (uptimeSec) + Asset.lastUptimeSec via the probe-patch buffer, and when the reading drops vs. the cached lastUptimeSec (>60s tolerance) sets Asset.lastRebootAt and emits a `device.reboot` Event (level warning). Non-SNMP probes carry no uptime — the probePatchBuffer flush COALESCEs lastUptimeSec/lastRebootAt so they're preserved, not nulled.
- `src/jobs/monitorAssets.ts` — Light/heavy ticking loops invoke runMonitorPass() which dispatches probe collection
- `src/jobs/backfillMonitorStatusChangedAt.ts` — One-shot startup (60s after boot): seeds Asset.monitorStatusChangedAt for pre-existing warning/down/recovering assets from the latest monitor.status_changed Event when one is still within the 7-day retention window
- `src/api/routes/assets.ts` — recordProbeResult() on manual /probe-now endpoint
- `src/api/routes/assets.ts` — PUT /assets/:id validateMonitorConfig handler resets consecutiveFailures on manual disable
- `src/db.ts` — Prisma extension, BOTH directions of business rule 10: clampMonitoredForStatus() forces monitored=false + resets consecutiveFailures when a write stages one of the four unmonitorable statuses (decommissioned / disabled / **storage** / **quarantined** — `UNMONITORABLE_STATUSES`), and enforceMonitorableStatus() reads the row when a write stages `monitored: true` with NO status so the operator toggle / discovery monitored-sweep can't re-enable polling on one of them. updateMany narrows its WHERE instead. NOTE: neither clears `monitorStatus` — the last verdict stands so the assets table can show where a device was when polling stopped, which is exactly why automations gate on `monitored` rather than on the pill (business rule 37).
- `src/jobs/clampFailureBucket.ts` — boot sweep: clamps `consecutiveFailures` to `MAX_MISSED_POLL_BUCKET` (100) on rows written before the bucket had a ceiling, and zeroes the dormant `awaitingRecoveryConfirm`. Not a correctness requirement — `nextFailureBucket` clamps with `min(cap, cf)` before it moves the level either way, so the next probe converges the row on its own automation's cap — but the column is read by surfaces that reach it first (the strip tooltip, `runsHeavyCadences`, `consecutiveFailures` as an automatable field)
- `src/jobs/clampMonitoredForStatus.ts` — boot sweep: one indexed UPDATE turning monitored off on every already-unmonitorable row (rows predating the widened status set, raw-SQL writers, best-effort guard misses). Migration `20260827000000_monitorable_status_clamp` does the same pass once at upgrade.
- `src/services/assetQuarantineService.ts` — quarantine turns monitoring off through that clamp and PARKS the flag in `Asset.monitoredBeforeQuarantine`; release stages the restored status + monitored in ONE write so the clamp judges the restored status

**Readers** (files that consume it):
- `public/js/assets.js` — Status pill renderer colors by monitorStatus (green/amber/blue/red/grey). The PILL is deliberately the one down-painting surface that does NOT take the covering automation's severity colour (business rule 36): its text already names the state, and recolouring it would make Down and Missed the same badge colour in a list column where they are read as a set
- `src/services/downDetectionService.ts` — supplies the THREE things the machine needs per asset, all from ONE winner so they cannot resolve onto different rules: `threshold` (missedPolls), `recoverySustainSec`/`recoverySustainPolls` (→ `recoveryPollsFor`, which is the bucket's cap), and `severity` (the colour every chart paints `down` in)
- `public/js/monitor-states.js` — `PolarisMonitorStates.replay`, the ONE browser copy of the machine, read by the Last-30-min strip, the desktop response-time chart and the phone's. A MIRROR of `nextFailureBucket` + `monitorStatusFor` (no import crosses that boundary), pinned by `tests/unit/assetIntermittencyBar.test.ts`, whose last describe block also pins it against the server copy
- `src/services/probeOutageService.ts` — `replayProbeStates`, the SERVER mirror, for the charts rasterized into alert emails
- `public/js/assets.js` — the intermittency bar's `_intermittencyStates` is now a one-line delegate to that module. Failures are literal (amber, red on the Nth consecutive miss); successes come from the machine, so the exit from `down` is blue until `failureThreshold` consecutive successes confirm the device. Pre-window state is assumed `up`. Dependency suppression is NOT part of the machine and must never be folded into it: `AssetMonitorSample.dependencyDown` rides alongside the replay and the strip layers the dependency grey over a missed cell afterwards (business rule 38), the same precedence `_chartPointColor` applies on the chart below
- `src/services/monitoringService.ts:runMonitorPass()` — Heavy-cadence suppression gate: telemetry/systemInfo only run when monitorStatus==="up" AND !dependencySuppressed; probe interval doubles when dependencySuppressed (parent down)
- `src/services/monitoringService.ts:resolveProbeIntervalSec()` — the counters ALSO drive probe spacing (business rule 30): an asset mid-confirmation (`0 < cf < failureThreshold && cs === 0`, or the recovery mirror) is re-probed at `fastConfirmIntervalSec` instead of a full interval, floored at `max(probeTimeoutMs, 5s)` and overridden by the dependency-suppressed 2×. Shared by `computeDueWork` and the pg-boss publisher in `src/jobs/monitorAssets.ts` — both candidate selects must carry `consecutiveFailures` + `consecutiveSuccesses`
- `src/services/dependencyTreeService.ts` — reconcileDependencySuppression() reads monitorStatus to evaluate "all-down" suppression — only the confirmed-down edge propagates INTO suppression (warning/recovering do NOT), and only `up` (plus the two non-verdicts `unknown` / `passive`, via `RELEASES_SUPPRESSION`) releases a child OUT of it: `recovering` and `warning` both hold the subtree, business rule 38a. So this file's state vocabulary is read asymmetrically — adding a state means deciding, explicitly, which side of that it lands on
- `src/api/routes/map.ts` (GET /sites) + `src/services/topologyGraphService.ts` (the topology graph builder) — Device Map reads monitorStatus for FortiGate/switch/AP health coloring via monitorStatusToHealth() (lives in topologyGraphService, imported back by map.ts)
- `src/jobs/monitorAssets.ts` — Queue eligibility check consults monitorStatus + dependencySuppressed
- `src/api/routes/dashboard.ts` — `/dashboard/summary` reads `monitored=true AND monitorStatus in (warning, down)` for the Monitor Alerts card and orders by `monitorStatusChangedAt asc nulls last` so the oldest outages surface first
- `src/services/nocDashboardService.ts` — `/dashboard/noc-summary` reads monitorStatus (status tiles, down assets, sites-with-issues), asset_monitor_samples.responseTimeMs (slowest response = avg of each asset's most-recent 10 probes), asset_storage_samples used/total (highest disk usage, per-volume), lastMonitorAt (stale polls), and the `device.reboot` Events (recent reboots) for the NOC widgets. Per-widget filters: `resolveFilteredAssetIds` reads `Asset.assetType` + `Asset.tags` (region:<name>) to constrain every feed
- `public/js/dashboard.js` — Monitor Alerts card renders the duration since monitorStatusChangedAt; re-ticks the label every 30s without re-fetching

**Invariants:**
- State machine accepts only {up, warning, recovering, down, unknown}; no other string values permitted.
- THE LEVEL DECIDES WHAT A MISS MEANS; THE OUTCOME DECIDES EVERYTHING ELSE: `cf = 0` → up; an ANSWERED probe → recovering whatever the level; a MISS → down at `cf ≥ threshold`, warning below it. The answered branch became unconditional on 2026-09-01 — it used to sit below the threshold test, and an answered probe reading `down` is a state the response-time chart cannot paint on an `ok` point, so it came out the plain series GREEN and an outage drew red → green → blue → green. It does not clear a down alert early: `recovering` is in `DOWN_ALERT_HOLDING_STATES`, so the alert still ends at `up`. (The old wording is kept here for its reasoning: "a success must NEVER win outright — that would clear a down alert on one answered packet out of an hour's worth of misses." The concern is real; it is now answered by the alert's holding states and by the CAP, not by withholding the `recovering` label.)
- "recovering" no longer means "was down" — it means answering with misses still outstanding, which is reachable straight out of "warning" AND out of "down". It exits to "up" when the bucket reaches 0.
- THE BUCKET IS CAPPED. `nextFailureBucket` locks it at `max(missedPolls, recoveryPolls)` on the verdict miss and every miss after it, so recovery costs the operator's number and not the outage's length. Unbounded, an overnight outage left `cf` near 480 and the asset owed 480 answered polls — eight hours of its down alert repeating and escalating after it came back. A miss during the climb RE-LOCKS it at the cap, so a flapping device cannot walk itself out of an outage.
- `down` IS NOT NECESSARILY RED. It is drawn in the covering automation's own `severity` on all four painting surfaces — strip, desktop chart, phone chart, alert email (business rule 36). One palette, duplicated by necessity in `downSeverityHex` (`src/utils/severityStyle.ts`) and `DOWN_SEV_COLOR` (`public/js/chart-severity.js`), pinned by `tests/unit/downSeverityColor.test.ts`. `critical` keeps `#d32f2f`; an absent or unrecognized severity falls back to it.
- "warning" is mid-degradation (was-up, now accumulating failures but below threshold). Exits to "down" when threshold crossed, back to "up" on success.
- monitor.status_changed Event is edge-triggered: it fires on the transition INTO up / warning / down (so an operator sees the first successful poll, the first warning, and the first down — plus recovery, which is a →up edge). It never fires per-poll (up→up etc. are suppressed by previousStatus===nextStatus) and never fires for the intermediate "recovering"/"unknown" states. Level is "info" for →up, "warning" for →warning and →down. propagateAfterStatusChange() and triggerRetryAfterStatusChange() are decoupled from the event: they fire from a SEPARATE guard gated to the confirmed up/down edge only (a "warning" edge logs an event but does NOT propagate suppression or kick the retry job) — dependency suppression still follows the confirmed-down edge, never the flap.
- monitorStatusChangedAt is stamped on EVERY transition (any-to-any), independent of the Event audit trail. The column is the source for the Dashboard's "how long has this been warning/down" duration. Backfill from the Event log seeds it from the latest monitor.status_changed Event still within the 7-day window; older outages render "—".
- Heavy cadences (telemetry/systemInfo/fastFiltered) are suppressed when monitorStatus ≠ "up" OR dependencySuppressed. The probe runs at 2× cadence when dependencySuppressed AND responseTimePolling !== "disabled".
- Response-time probe runs in every state; it's the cheap path that detects recovery.

**When changing this:**
- Verify every state assignment matches the rules above (no bypass paths).
- FOUR copies of the machine, and a change lands in all four: `nextFailureBucket` + `monitorStatusFor` (`src/utils/monitorStatus.ts`, the authority the probe path calls), `replay` (`public/js/monitor-states.js`), `replayProbeStates` (`src/services/probeOutageService.ts`), and the parity assertions in `tests/unit/monitorStatusStateMachine.test.ts` + `tests/unit/assetIntermittencyBar.test.ts`. The two mirrors exist because nothing crosses those boundaries (no frontend build step; probeOutageService is kept dependency-free), and the strip sits directly above the chart, so a drift is visible on one screen. `tests/unit/monitorStatusStateMachine.test.ts` carries a PARITY block that reads monitoringService.ts itself, because that file's stub silently pinned the old run-length machine through the rewrite that replaced it — in particular that the down→recovering→up run still renders blue, since that is the only surface showing it per-sample.
- Confirm monitor.status_changed Event audit trail only has →up / →warning / →down transitions (never →recovering, →unknown, or same-state per-poll repeats = bug).
- Test manual /probe-now against a down asset — should DECREMENT consecutiveFailures by one and transition straight to `recovering` (it answered), NOT hold at `down` until the bucket falls under the threshold. That was the pre-2026-09-01 behaviour and it is what the chart could not draw.
- Adding a painting surface for `down`? Take the colour from the `downDetection.severity` on the payload through `downColorOf` / `downSeverityCss` — never hardcode the red. Adding a colour to the palette? Both copies plus the collision assertions in `tests/unit/downSeverityColor.test.ts`, which guard against re-using the chart's miss amber / recovering blue / dependency grey / maintenance lavender.
- Check Map topology endpoint colors match asset list Status pills (monitorStatusToHealth must be consistent).
- Verify clamp logic in db.ts doesn't interfere: disable should reset, but re-enable (flip to active) should not auto-resume monitoring.
- If touching the cadence dispatch (runMonitorPass / publishDueWork): mirror EVERY change in BOTH `src/services/monitoringService.ts` AND `src/jobs/monitorAssets.ts` — they're parallel implementations and must stay in lock-step.
- **Every cadence's publisher gates on its own resolved polling method before queueing** — lldp and storage and processes each check theirs inline, and the response-time probe checks `responseTimeProbeShouldQueue(eff.responseTimePolling)` (`utils/pollingCompatibility.ts`) in BOTH publishers. The probe had no such gate until 2026-08-28, which is how `"disabled"` reached `probeAsset`, matched no dispatch branch, and got recorded as a missed poll — an operator switching Response Time off marched the asset to `down` (business rule 30). A shared predicate rather than a fourth inline condition precisely because these two files drift. Adding a new cadence means adding its gate to both.
