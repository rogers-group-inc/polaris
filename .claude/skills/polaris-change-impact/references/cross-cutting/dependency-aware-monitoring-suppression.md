## cross-cutting/dependency-aware-monitoring-suppression

**What it is:** AssetDependencyParent edges + Asset.dependencyLayer + Asset.dependencySuppressed coupled to the response-time five-state machine. Parent (FortiGate / upstream switch) confirmed-down → all transitive descendants pause heavy cadences and slow probe to 2× interval; recovery resumes within one base-cadence tick. "All-down" multi-parent semantics — a switch with redundant uplinks suppresses only when every effective parent is down or itself suppressed. **Since 2026-08 this covers ENDPOINTS too** (`source="endpoint"`, one leaf edge off the last-seen switch / AP / FortiGate): the tree was infra-only, so a server or camera behind a dead gate alerted as plain Down while the switches behind the same gate read "Dep. Down".

**Writers** (files that mutate or emit this state):
- `src/services/dependencyTreeService.ts` — recomputeDependencyTree() rebuilds source="computed" rows in AssetDependencyParent + Asset.dependencyLayer at end of every FMG/FortiGate discovery cycle. Source="override" rows are operator-managed (admin override endpoints) and never touched by recompute.
- `src/services/dependencyTreeService.ts` — syncEndpointDependencyEdges() maintains the `source="endpoint"` half: fleet-wide (NOT integration-scoped — most endpoints are discovered by AD/Entra/vCenter, which never call recompute), diff-based rather than delete-replace, at most one parent per endpoint, skipping anything already parented by `source="vcenter"`. Called from recomputeDependencyTree; failures are caught so the endpoint half can never fail the infra recompute.
- `src/services/dependencyTreeService.ts` — reconcileDependencySuppression() is the source of truth for Asset.dependencySuppressed; emits monitor.dependency_suppressed / monitor.dependency_resumed Events on transitions.
- `src/services/dependencyTreeService.ts` — propagateAfterStatusChange() is the latency-optimization hook called from recordProbeResult on the confirmed up/down edge (a separate guard from the monitor.status_changed Event emission, which also covers the warning edge — propagate does NOT fire on warning).
- `src/jobs/dependencyReconciler.ts` — 60s tick that calls reconcileDependencySuppression(); the source of truth catches anything the event hook missed.
- `src/jobs/backfillDependencyTree.ts` — one-shot startup runs recomputeDependencyTree() so existing installs see populated rows without waiting 4h.
- `src/services/discovery/discoveryEngine.ts` — Phase 12 of syncDhcpSubnets calls recomputeDependencyTree(integrationId) on mode in {full, finalize}.

**Readers** (files that consume it):
- `src/services/monitoringService.ts:runMonitorPass()` — Cadence dispatch: heavy cadences gated on `monitorStatus==="up" && !dependencySuppressed`; probe interval doubles when dependencySuppressed AND responseTimePolling !== "disabled".
- `src/jobs/monitorAssets.ts:publishDueWork()` — Same gate, mirrored for the pg-boss publisher path.
- `public/js/assets.js:assetMonitorBadge()` + `_mapAsset()` — Status pill renders slate-blue "Dep. Down" whenever `dependencySuppressed` (suppression outranks the five-state label, including probe-down — the own-probe state moves to the tooltip); the `_monitor` filter array maps suppressed rows to the "Dep. Down" chip, and `monitorClause` in `src/api/routes/assets.ts` mirrors it server-side (directional chips exclude suppressed rows).
- `public/js/map.js:monitorClass()` / `clusterIcon()` / `fortigateNodeColor()` — Pin/cluster/topology-node colors render slate-blue (`monitor-dep-down`) under the same priority rule (suppressed wins). Cluster aggregation counts suppressed children as dep-down; a non-suppressed probe-down/degraded child still rolls the cluster up red/amber.
- `public/js/mobile/asset-detail.js:renderMonitorPill()` / `monitorDotCls()` — Same priority + slate-blue treatment on the mobile asset-detail surface.
- `src/services/notificationEngine.ts:evaluateThresholdRule()` + `fire()` — **the one automation-side reader that does not merely drop a suppressed asset** (business rule 76): a `monitorStatus == down` automation with `trigger.alertWhenDependencyDown` keeps its dependency-suppressed assets (maintenance still silences), reads each as a synthesized `down` flagged `Reading.dependencyDown`, and at fire asks `dependencyTreeService.resolveDependencyBlame` who silenced it. The alert row carries `Notification.dependencyDown` + `dependencyBlame`; a live alert whose flavour disagrees with the asset's current flag is handed off (`handoffDependencyFlavour`) and raised again in the other flavour.
- `src/services/notificationService.ts:clearSuppressedAlerts()` — retires every live alert on a suppressed asset EXCEPT `dependencyDown = true` rows (rule 76): those are supposed to be there, and the engine owns their end.
- `src/services/dependencyTreeService.ts:blameFromGraph()` / `resolveDependencyBlame()` — the upward walk that turns the suppression verdict into a NAME (upstream device + root cause), for the alert above. Reads the same `SuppressionAssetState` shape the reconciler builds, hop by hop through a per-tick `BlameLoadCache`.
- `src/api/routes/assets.ts` — Three endpoints: `GET /assets/:id/dependencies`, `PUT /:id/dependencies/override` (admin, with cycle validation), `DELETE /:id/dependencies/override` (admin). The GET's effective/computed parent split counts every non-`override` source. Its DOWNWARD view (children + grandchildren + `childCount`) is **infra-only**, filtered in SQL and capped (`DEP_INFRA_CHILD_CAP` 300 / `DEP_GRANDCHILD_CAP` 500, `childrenTruncated` in the payload): endpoints are real children of the switch/AP/gate that last saw them, but listing them buries the infra chain the tree exists to show, and a site gate is the last-seen device for the entire site. Operator decision 2026-08 — do not re-admit them without asking. `childCount` is deduped per child and infra-filtered too, so the UI's "+N" can't become an endpoint tally.
- `public/js/assets.js:renderDependencyTreeBlock()` — General-tab tree, now rendered for EVERY asset type (it used to return "" for non-infra). An endpoint sees its own dependency here as the PARENT row above it — that's the only surface where an endpoint edge is displayed. Parent rows carry a `detectedVia` tag ("last-seen switch port" / "last-seen access point" / "last-seen firewall") because an edge that silences alerts should say which signal put it there; an endpoint with no resolvable upstream gets an explicit "dependency suppression can't apply" empty state rather than a missing block.
- `src/api/routes/assets.ts:GET /` and `GET /:id` — Stamps `dependencyLayer` + `dependencySuppressed` on every asset returned so the pill renderer doesn't need a second fetch.
- `src/api/routes/map.ts:GET /sites` and `GET /sites/:id/topology` (graph built in `topologyGraphService.buildSiteTopology`) — Stamps the same fields on each pin / topology node. (The topology builder still computes edges via per-request BFS through `interfaceTopologyService` — full DAG-as-source-of-truth refactor is a follow-up; current state is "DAG drives suppression, BFS still drives graph rendering.")

**Invariants:**
- **A retired device is nobody's parent.** `recomputeDependencyTree` drops `decommissioned` / `disabled` infra assets from the graph (`EXCLUDED_LIFECYCLE_STATUSES` — the same constant the endpoint half already used) while KEEPING them in scope, so their own computed rows are deleted and `dependencyLayer` nulled instead of frozen. Both halves matter: filtering the read alone would stop a retired gate being a parent but strand a retired switch's stale parent rows forever, since nothing would ever bring it back into scope. Why it is not cosmetic: rule 10 forces `monitored=false` on both statuses, and `evaluateSuppression`'s unmonitored-parent branch is TRANSPARENT — it recurses to grandparents and returns `true` (ok) when there are none. A firewall is layer 1 with no parents, so a retired gate is a permanent ok vote that vetoes suppression for every child still bound to it, and it can never go down again to lift the veto; a switch behind a replaced gate sat at plain Down instead of Dep. Down. `storage` / `quarantined` are deliberately still in the graph (present devices, reversible) and therefore still carry that ok vote — an open gap, fixable in `evaluateSuppression` rather than by dropping them.
- **The gate's own managed inventory BOUNDS the graph; it never authorizes a sweep.** Discovery asks each FortiGate for its managed switches and APs and stamps the answer on the GATE (`fortinetTopology.managedSwitchSerials` / `managedApSerials`). FMG reads FortiManager's device DB natively (`/pm/config/device/<dev>/.../switch-controller/managed-switch`, `.../wireless-controller/wtp`) — those steps deliberately run for OFFLINE gates, unlike the proxy steps behind `if (offline) return` — and standalone reads the gate's own `/api/v2/cmdb/...`. `violatesMembership` in `buildDependencyEdgesFromInputs` then drops any interface/LLDP adjacency a gate's list contradicts, BOTH directions (undirected adjacency in `assignLayers`), plus child↔child edges across different gates. **Tri-state**: absent = unknown = no constraint; `[]` = "manages none"; populated = constrains. The field is stamped ONLY when the roster read answered (`DiscoveryResult.managedMembership.switchDevices` / `apDevices`), which is what keeps a failed read from reading as "manages nothing" — blur that distinction and a gate silently loses its subtree. **Kept strictly separate from `cmdbSwitchSerials` / `cmdbApSerials`**, which vouch for assets against the Phase 2b decommission sweep: FMG's device DB is INTENDED config, so letting membership reach a sweep would turn a config-retrieval lag into deleted inventory. Membership can only REJECT an edge, never assert one. Matched on serial — the switch roster reads `sn`, never the `switch-id` mkey (renamed to the hostname on FortiLink fleets, which had silently broken the roster's own decommission protection). HA needs no carve-out: the stamp is written per cluster member. Supersedes the retired child-side `contradictsController` veto — prod 2026-09-03, a switch whose LLDP `matchedAssetId` had frozen pointing at an unrelated gate, which under all-down semantics BREAKS suppression rather than merely looking wrong.
- An LLDP row good enough to DISPLAY is not automatically good enough to draw a dependency edge from. `AssetLldpNeighbor` keeps a vanished neighbour for 48h (LLDP_STICKY_WINDOW_MS) so the System tab's Neighbor column does not flap on a missed advertisement; `recomputeDependencyTree` filters those rows through `filterFreshLldpRows` first (kept if refreshed within 6h OR carrying the newest lastSeen for its (asset, source)). The bound is deliberately tight because the failure directions are asymmetric: a SPURIOUS parent breaks suppression outright under all-down semantics (an extra parent that is up keeps the child alerting as plain Down when its real upstream dies), while a MISSING LLDP parent is usually covered by the same asset's `controller` and `interface` edges. Prod 2026-09-03: a switch kept a stale row under a retired local-port label — nothing could supersede it, since the supersede check is keyed on `localIfName` — still naming a FortiGate from a period when two gates shared a management address, and the recompute gave the switch two parents.
- Suppression follows the **confirmed-down** edge only. propagateAfterStatusChange() is called only from the up/down guard in recordProbeResult — NOT from the monitor.status_changed Event emission (which also logs the →warning edge). Warning / recovering flapping logs an event but does NOT propagate.
- **Entering and leaving read the parent differently (business rule 38a).** Entering needs the parent confirmed `down`. LEAVING needs it genuinely back: `evaluateSuppression` releases an already-suppressed child only for a parent in `RELEASES_SUPPRESSION` — `up`, `unknown`, `passive` — so `down`, `recovering` AND `warning` all hold the subtree. The child's persisted `dependencySuppressed` (`SuppressionAssetState.currentlySuppressed`) is what selects the side, which is why that field is load-bearing input and not merely a seed. The whitelist is a whitelist on purpose: a new monitor state holds a subtree until someone decides it means "back". `unknown` and `passive` release because neither is a claim about reachability and gating on them would strand a subtree forever; `warning` does not, because it is transient by construction and is the one state in which the parent has just missed a poll. Releasing early is not cosmetic — every child's own probes are still failing, so the subtree instantly starts its own down runs and re-alerts device by device as plain Down, which is the storm suppression exists to prevent.
- "All-down" multi-parent: an asset with N effective parents suppresses iff every parent is down or itself dependencySuppressed. Empty parent set = never suppressed. **This is why a broken parent lookup is invisible-but-total**: a child that resolves no parent doesn't fail loudly, it just never suppresses — which is how the FMG-device-name/hostname split (see cross-cutting/fortinet-parent-key-resolution) showed up as "a FortiGate in maintenance leaves its switches reading Down" rather than as an error anywhere.
- Override resolution: if any source="override" row exists for an asset, those are the effective parents (computed rows ignored). Empty override set = explicit "no parents" pin (asset opts out entirely).
- Unmonitored parents are transparent — the suppression walk skips them and continues to their grandparents. A monitored ancestor must say "down" before suppression can fire.
- recomputeDependencyTree only touches source="computed" rows for in-scope assets; out-of-scope rows and source="override" rows are never deleted. The endpoint pass only touches `source="endpoint"` rows, and only by diff — it never deletes an infra or override or vcenter row.
- An endpoint gets ONE parent (most-specific of switch-port → wireless → firewall sighting → the gate that owns its address per IPAM), never a union. All-down semantics are for redundancy; a switch and its gate are in series, so listing both would let a dead switch under a healthy gate keep the endpoint alerting. Series propagation comes from the switch's own suppression instead.
- The fourth tier is an INFERENCE, not an observation (business rule 55): it fires only for endpoints the three observed tiers left unplaced, and an unplaced endpoint had no parent — so it can only ADD suppression, never move an edge. Failure mode is a missed alert, never a false one. Gated on the endpoint's address claim being current under rule 40 (`claimIsFresh`), because a recycled DHCP address would otherwise suppress a departed device behind whoever serves that range now.
- Layer assignment is **physical-first** BFS from any FortiGate (layer 1). Interface + LLDP + mesh edges form the primary adjacency; controller edges are a fallback for assets the physical pass didn't reach. Controller-fallback uses simple-path detection: a 3+ node chain of unattached switches sharing one controller, with exactly two endpoints and no branching, chains correctly off the alpha-hostname endpoint. MCLAG pairs (2-node groups) and any branching/cycled component still attach as siblings to preserve co-layer behavior. Cycles, disconnected subgraphs, or chains through unmonitored intermediates may leave dependencyLayer = null. Kept-edge `detectedVia` prefers mesh > interface > lldp > controller so the audit trail reflects physical cabling when multiple signals exist on a pair.
- **Wireless attachments override the controller signal.** A mesh-leaf AP (station-match on its root AP, from `AssetWirelessStation`, OR `fortinetTopology.meshUplink === "mesh"` — the stamped FortiOS classification works without a root-AP station scrape) gets a `mesh` edge to the root AP and its backwards controller edge is suppressed. A FortiLink switch bridged behind a FortiAP (an AP↔switch `AssetLldpNeighbor` adjacency where the switch is NOT the AP's controller parent — or where the AP is a mesh leaf, since a mesh leaf's wired LLDP adjacency is always a switch bridged behind it, even when stale pre-fix data stamped that switch as its `parentSwitch`) has its FortiLink controller edge suppressed and depends on the AP via LLDP. Both are computed in `recomputeDependencyTree` and passed to `buildDependencyEdgesFromInputs` (`meshEdges`, `bridgeLeafSwitchIds`). The same mesh-leaf rule gates discovery stamping: `parseFortiapMonitorRow` + both detected-device fallback loops never write `parentSwitch` onto a mesh leaf. The non-mesh bridged-switch discriminator (`switch ≠ AP.parentSwitch`) is a heuristic — verify against real fleet data.
- Reconciler runs in BFS layer order so parent's effective state is settled before children evaluate (otherwise multi-tier suppression could oscillate).
- **Suppression silences automations, and exactly one thing may opt out of the silence: the down trigger itself** (business rule 76, `trigger.alertWhenDependencyDown`, read only through `notificationTypes.ruleAlertsWhenDependencyDown`). The opted-in alert fires on the suppression EDGE (the parent's confirmed verdict is the evidence — waiting for the child's own count at half cadence would tell the plant operator late what the pill already says), says DEPENDENCY DOWN, and names the upstream device and the root cause. Its flavour follows the flag: the alert is ENDED and re-raised when the asset's `dependencySuppressed` no longer agrees with it, with no reset actions either way. Maintenance is NOT part of the opt-out (rule 16 wins), reminders and escalation still pause while the asset is suppressed (the escalation sweep's existing check), and `clearSuppressedAlerts` must never retire a `dependencyDown` row — the sweep excludes them in its query, or the engine would re-raise the alert every tick.

**When changing this:**
- Mirror cadence-dispatch changes in BOTH src/services/monitoringService.ts AND src/jobs/monitorAssets.ts. The two are parallel implementations and must stay in lock-step.
- Changing which parent states release a suppressed child? Edit `RELEASES_SUPPRESSION`, not the `notBack` expression — and re-read business rule 38a first. The test for "does this state strand a subtree?" is whether it can persist indefinitely (`unknown`, `passive` can; `warning`, `recovering` cannot — the failure bucket always carries them to `up` or `down`).
- Verify the propagateAfterStatusChange() hook still fires only from the confirmed up/down guard — never from the warning edge (which logs an event but must not propagate) or recovering churn.
- Run the dependencyTreeService.test.ts suite — covers BFS layers, MCLAG siblings, dual-homed multi-parent, all-down semantics, transparent unmonitored parents, confirmed-down-only edge, and the endpoint half (per-signal precedence, single-parent rule, FMG-device-name resolution, and the gate-down / switch-down / all-up suppression matrix for a leaf).
- Adding a signal to the endpoint half? It's one parent per endpoint by design. A new signal takes a place in the precedence ladder — it does not become a co-parent — and it must be device-scoped enough that a stale value can't point at a gate the device was never behind. An INFERRED signal (one derived from an address rather than from something observing the device) goes at the BOTTOM of the ladder and carries its own staleness gate; the IPAM tier is the worked example.
- Smoke-test on dev: pick a live FortiGate, set monitorStatus="down" via direct DB write, wait one reconciler tick (≤60s); confirm child switches/APs flip to dependencySuppressed and emit monitor.dependency_suppressed Events.
- Adding a reason a parent can count against its children (a new overlay, a new status)? It lands in THREE places or the alert lies: `evaluateSuppression.isParentOk` (the verdict), `blameReasonOf` in the same file (the NAME — and its ORDER, since `suppressed` must keep outranking `down` for the walk to reach the root cause), and `dependencyReasonPhrase` in `utils/notificationTemplate.ts` (the sentence). `tests/unit/dependencyBlame.test.ts` builds the same fixtures `dependencyTreeService.test.ts` does.
- Changing what the sweep retires? `tests/unit/notificationSuppressionSweep.test.ts` pins the `dependencyDown: false` exclusion, and `tests/unit/notificationDependencyDownAlert.test.ts` pins the engine half — including that an automation WITHOUT the toggle still drops the asset.
- If the topology endpoint refactor lands: hit /api/v1/map/sites/:id/topology before/after; edge sets must match (same FG→switch / switch→AP edges) modulo the new dependencySuppressed flag on each node.
- Watch for cycles introduced by override edits: the override endpoint must reject inputs that would form a cycle (BFS-back-walk validation).
- Parent resolution from discovery stamps goes through `utils/fortinetParentKey.ts` — never re-hand-roll a `byHostname` map here. See cross-cutting/fortinet-parent-key-resolution.
