# Services — alert delivery, recipients, contacts, directory, automation scripts

Per-service touches (What it owns / Public API / Cross-service deps / Used by / Invariants / When changing this), verbatim from TOUCHES.md. Code references are `path/file.ts → symbolName()` — grep the symbol.

## services/automationScriptService.ts

**What it owns:** The AutomationScript registry (operator-authored scripts referenced by Automation `script` actions) + the AutomationScriptRun lifecycle entry points. **RCE-equivalent surface:** every route sits behind the `automationScripts` key; server scripts run as the polaris service user, agent scripts as root/LocalSystem on the triggering asset.

**Public API:** `listScripts`/`getScript`/`createScript`/`updateScript`/`deleteScript`, `requestScriptRun` (validates exists + enabled + runTarget-compatible; agent runs additionally preflight the TRIGGERING asset's ManagedAgent — installed + active + agentVersion ≥ MIN_AGENT_SCRIPT_VERSION (0.13.0) — BEFORE creating the run, then enqueue the run_script AgentCommand with the sha256-carrying payload and link agentCommandId), `listRuns`, `pruneOldRuns` (90d), `sha256Hex`, `versionAtLeast`/`MIN_AGENT_SCRIPT_VERSION`, `SCRIPT_RUN_TARGET_VALUES`/`MAX_SCRIPT_BODY_BYTES`/`MAX_SCRIPT_TIMEOUT_SEC`.

**Cross-service deps:** `prisma` (AutomationScript/AutomationScriptRun/NotificationRule), `eventLogService.logEvent`, `notificationTypes` (SCRIPT_INTERPRETERS + normalizeRuleToV2 for the delete-referenced scan).

**Used by:** `src/api/routes/automationScripts.ts` (CRUD + test-run), `automationActionService` (script arm → requestScriptRun), `automationScriptRunner` (pruneOldRuns).

**Invariants:**
- sha256 recomputed on EVERY save — it's what agents verify before executing; never accept a client-supplied hash.
- Creation is a warning Event; a body change is a warning Event carrying old+new sha256 — script tampering must be visible in the audit trail/syslog.
- Delete refuses (friendly 409) while any automation's actions or escalation tiers reference the script (scan goes through `normalizeRuleToV2`, so legacy-shaped rows count too).
- Run rows snapshot scriptName + sha256 so history survives script deletion; `notificationId` carries NO FK (alert lifecycle is independent).

**When changing this:** New interpreter → `SCRIPT_INTERPRETERS` in notificationTypes + `interpreterArgv`/extension in automationScriptRunner + the Go agent's scriptexec mirror. Never widen who can call these paths without revisiting the RBAC posture in permissions.ts.

## services/automationScriptRunner.ts

**What it owns:** Server-side execution of pending AutomationScriptRun rows (runOn="server"), driven by the `runAutomationScripts` job (5s tick, web/all role). Claim pending→running (bounded, restart-safe), execFile with timeout + output caps, record results + `automation.script.run` Events, stuck-running sweep, idle-tick retention prune.

**Public API:** `runPendingServerScripts()` (the job tick), `executeServerScript(run)` (exported for tests), `buildScriptEnv(base, context)` (pure — the secret-stripped child environment; unit-tested in tests/unit/automationScripts.test.ts).

**Cross-service deps:** `prisma`, `eventLogService.logEvent`, `automationScriptService.pruneOldRuns`, `src/utils/paths.ts` (STATE_DIR → data/automation-scripts-tmp).

**Used by:** `src/jobs/runAutomationScripts.ts`.

**Invariants:**
- Script execution NEVER happens inline in the engine or the delivery drain — always through this queue (a wedged script must not stall alert evaluation or deliveries).
- The rendered args string travels as a SINGLE argv entry to execFile — never concatenated into a shell string. Alert context rides env vars (POLARIS_ALERT_ID/POLARIS_RULE/POLARIS_ASSET).
- The interpreter resolves through `resolveInterpreterBin` to a known ABSOLUTE path (`INTERPRETER_PATHS`, or `%SystemRoot%\System32\...` on Windows) when one exists on disk, falling back to the bare name (PATH lookup) only when none does — an install with a non-standard layout must keep running, but the inherited PATH should not get first say in which binary executes operator scripts.
- The child environment is `process.env` MINUS secret-shaped keys (`buildScriptEnv`, denylist `/SECRET|TOKEN|PASSWORD|PASSWD|DATABASE_URL|SESSION|CREDENTIAL|PRIVATE_KEY|_KEY$/i`), plus the alert context. This is not a privilege boundary — authoring a script already requires an RCE-equivalent permission — it exists because **stdout is stored on the run row and rendered in the Scripts tab**, so before the scrub a one-line `env` copied DATABASE_URL and POLARIS_SECRET_KEY into a displayed, backed-up, unencrypted column. Denylist not allowlist so PATH/HOME/proxy/locale stay inherited and existing scripts keep working; widening it is a compatibility decision, not just a security one.
- Body goes to a 0600 temp file under the state dir and is ALWAYS unlinked (finally); stdout/stderr capped at 64 KB (a maxBuffer kill classifies as failure, not timeout); SIGKILL on timeout.
- Claim via updateMany with a status re-check so concurrent processes can't double-run; the stuck sweep only flips rows past timeout+60s grace.

**When changing this:** Anything touching the execution model (interpreters, env, caps, temp-file handling) is security-sensitive — human review required before production; keep the Go agent's scriptexec semantics in lockstep (same caps, same hash-verify posture).

## services/contactService.ts

**What it owns:** The address book — `Contact` CRUD, the unified recipient search that backs both the address-book picker and the wizard's typeahead, and the fire-time "who is responsible for this device?" lookup.

**Public API:** `listContacts` (PAGED — `{ contacts, total }`, not an array)/`getContact`/`createContact`/`updateContact`/`deleteContact`, `normalizeContactEmail`, `normalizeContactCondition`, `conditionMeansAllDevices`, `contactFilterOf`, `previewContactAssets`, `searchAddressBook`, `resolveContactsForAsset`/`resolveContactEmailsForAsset`, `bumpContactCache`.

**Cross-service deps:** `prisma`, `eventLogService` (`logEvent`), `notificationTypes` (`deviceFilterConditionSchema`, `evaluateScopeCondition`, `conditionFields`, `scopeConditionStats` + the depth/rule caps), `utils/criteriaToCondition`, `tagAssignmentService` (`normalizeCriteria`, `resolveMatchingAssetIds`, `assetMatchesCriteria`, `collectCidrs`, `cidrsContainingIp`, `SINGLE_ASSET_CANDIDATE_SELECT` — all now only for LEGACY rows), `notificationRecipientService` (`listRecipientUsers`), `utils/ttlCache`, `utils/logger`.

**Used by:** `src/api/routes/contacts.ts` (CRUD + search + preview), `src/api/routes/assets.ts` (`GET /assets/:id/contacts`), `src/services/automationActionService.ts` (`resolveContactEmailsForAsset` on the fire path, for `recipientAssetContacts`), `public/js/automations-address-book.js` (both surfaces), `public/js/automations-wizard.js` (the recipient typeahead + the save-to-book affordance).

**Readers of the state it writes:** the Automations → Address Book tab, the automation wizard's recipient fields, the asset slide-over's General-tab Contacts rows, and every alert whose notify action sets `recipientAssetContacts`.

**Reads are BOUNDED, and the bound is load-bearing (2026-08).** Three separate paths used to read the whole `contacts` table and filter it in JavaScript, which was invisible while the address book was hand-curated and tens of rows deep. It stops being invisible the moment a bulk source can grow the table to the size of the company, so each now has an explicit bound and each bound has a reason: (a) **`listContacts(opts)` returns a PAGE** — `{ contacts, total }`, `q` matched in SQL via `ILIKE`, limit clamped in the service as well as the route (a route is not the only caller). `total` is the unpaged count, so a truncated page stays distinguishable from a complete one — read it, never `contacts.length`. (b) **`searchAddressBook` resolves its contacts half in SQL** with a five-column `select` and `take: limit * 2 + 1`, and deliberately does NOT go through `rowToContact`, which Zod-re-validates both stored filter blobs per row — the typeahead runs on keystrokes and must not pay to validate filters nobody asked about. The doubling is because users and contacts are merged and then deduped by address, so fetching exactly `limit` could leave the page short. (c) **The fire path loads only contacts that could own a device** (`loadFilterCarryingContacts`): a contact with no filter and no pins can never match a triggering asset, so the alert path must not scale with the address book. The two JSON columns are matched as **DB-NULL, not JSON-null**, because the writers pass `undefined` for "no filter". The `ILIKE` predicates are served by GIN trigram indexes on `lower(email)` / `lower(name)` created in migration `20260825050000_contacts_search_indexes` — Prisma cannot express a functional gin_trgm_ops index, so they exist only in SQL, and without them paging bounds the payload without bounding the work. **When adding a reader of this table, say which of the three bounds it falls under.**

**`Contact.origin` has ONE writer, and adoption is a state machine (2026-08, business rule 35).** `directorySyncService` sets it to `"entra"`/`"ad"`; `adoptDirectoryContact` is the only thing that sets it back to `"manual"`. Everything else must treat it as read-only. Three CRUD paths funnel through adoption because `Contact.email` is UNIQUE, so a synced row physically blocks the operator: **create** over a synced address adopts rather than 409s, **update** on a synced row adopts rather than writing values the next run would overwrite, and **delete** on one is refused with a 409 naming the exclusion filter and the adopt path (deleting would succeed and then be undone, which is worse than refusing). Adoption deletes the row's `DirectoryContactSource` rows in the SAME transaction as the origin flip — a row promoted with its provenance intact would be re-adopted every run, and provenance deleted while the row stayed `"entra"` would be a synced row no sync can clean up. Reaching the update/adopt path on a synced row already requires `fullwrite` with no extra code, because synced rows carry `createdBy = null` and `assertOwnership` refuses a null `createdBy` at write level — intentional, not an oversight to tidy. **Visibility:** synced rows and the live GAL are both gated on `automationManagement:read` via `includeDirectorySynced` / `includeLiveDirectory`, which the ROUTE derives from the role — never from the caller's query, so asking for directory rows can't grant them.

**Import-cycle note:** `contactService` imports `notificationRecipientService` for `listRecipientUsers`, so the delivery expander must NOT import `contactService` back. `expandDeliveries` therefore takes the resolved `assetContactEmails` as an option and `automationActionService` does the lookup — the same shape as the region tags it already receives. Keep it that way.

**Region + dynamic recipients are PILLS, not checkboxes** (2026-08). `recipientRegions` resolves through `resolveUsersByRegions` and is valid on every routed channel — only `recipientAllUsers` / `recipientAllRegions` stay Web-Push-only, enforced by the `broadcast` flag in `assertActionRefs`. `recipientDeviceRegion` / `recipientAssetContacts` are To-only in the builder: they're flags on the ACTION while Cc/Bcc are `EmailRecipients` lists, and `expandDeliveries` folds contact addresses into the To owner map only. `emailRecipientsSchema` gained `recipientRegions` so a region pill works wherever it's dropped — the same reasoning that already made roles resolvable in Cc/Bcc.

**Recipient sources on a notify action** (`usersForTarget` + the email branch of `expandDeliveries`): explicit `recipientUserIds`, `recipientRoles` (every user with the Role — matched by role ID so a rename can't reroute), `recipientDeviceRegion` / `recipientScopeRegion` / `recipientRegions` / `recipientAllRegions` / `recipientAllUsers` (all resolve to USERS, so they work on email and web_push alike), plus `addresses` and `recipientAssetContacts` (EMAIL ONLY — an address with no account behind it has no push endpoint). Adding a source means touching the schema, both converters, `usersForTarget`, and — if it belongs in Cc/Bcc — `emailRecipientsSchema` + `resolveEmailRecipients`.

**Two tag namespaces in the recipient index (`notificationRecipientService`).** `IndexedUser` carries BOTH `matchSet` (region ∪ other tags, flattened) and `regionSet` (region tags only). They are not interchangeable:
- `resolveRecipientUsers` (`recipientTags`) and `recipientDeviceRegion` / `recipientScopeRegion` use **`matchSet`** — changing that would alter delivery for existing rules. `recipientTags` is no longer free-form or legacy: since 2026-08 the address book's **Tags** list authors it from the `Tag` registry (Map Regions excluded — those are `recipientRegions`' job), and the flattened match is the RIGHT semantics for it, because a tag is a tag whichever dimension a user carries it in. That is exactly the asymmetry with `recipientRegions`, whose names come from the region catalogue by construction.
- `resolveUsersByRegions` / `resolveUsersInAnyRegion` (the push broadcast modes, where an operator picks a region BY NAME from the map-region catalogue) use **`regionSet`**. A user whose unrelated *other* tag happens to read "Atlanta" must not receive Atlanta's alerts, which is exactly what the flattened set would do.
- `recipientDeviceRegionLevels` (asset-relative level routing) uses **`regionSet`** via `resolveUsersByRegions`, because those names are resolved FROM the map-region catalogue by `regionHierarchyService.deviceRegionsAtLevels` and are regions by construction. **The resulting asymmetry with `recipientDeviceRegion` (which stays on `matchSet`) is deliberate — do NOT unify them.** Retro-fitting `recipientDeviceRegion` onto `regionSet` is a behavior change: any user whose non-region tag coincidentally matches a region name would silently stop receiving alerts they get today, with no UI signal. If that should ever be fixed it needs its own commit, with a pre-flight query listing the affected (user, tag) pairs for a human to review.
Also note the two storage conventions: user/role/group `regionTags` are stored **bare** ("Atlanta"), asset tags carry the **`region:` prefix**. `normalizeNeedle` strips the prefix, so either form may be passed in — but store bare names in `recipientRegions`.

**Invariants:**
- **`email` is stored trimmed + lower-cased.** The unique index is what enforces one row per address, and lower-casing at the boundary is what makes it case-insensitive. It also has to match `resolveEmailRecipients`' normalized set, or a contact address would dedupe inconsistently against a user's.
- **`resolveContactsForAsset` must never scan the fleet.** It is on the alert path. A pin match is a plain id comparison with NO asset load; a filter is evaluated against the ONE triggering asset (`evaluateScopeCondition` for a tree, `assetMatchesCriteria` for a legacy blob); the legacy CIDR containment is a single round-trip across all contacts' CIDRs combined, skipped entirely when no LEGACY row filters by subnet — a tree does its own `ipInCidr` in memory, so a fully folded-forward address book makes no containment query at all. If you add a filter field that needs another relation, extend the select there (`SINGLE_ASSET_CANDIDATE_SELECT` + the `tags` addition) — do not add a query per contact.
- **Exactly ONE filter shape is live per row.** `assetCondition` (the shared condition tree) supersedes the flat `assetCriteria`; a write of one nulls the other, and every read goes through **`contactFilterOf`**, which returns the tree — folding a legacy blob forward via `criteriaToCondition` on the fly. A blob carrying a field the tree can't express (`integration`) is deliberately NOT half-converted: `contactFilterOf` hands it back as criteria so it keeps matching through the flat predicate. Leaving the legacy column populated behind a new condition would be a second, invisible answer to "which devices?".
- **"All devices" comes only from the explicit `assetAllDevices` input flag.** It is STORED as the empty AND group, which `evaluateScopeCondition` reads as true for every asset by boolean identity — so any path that let a malformed or half-built empty tree through would silently hand a contact the whole fleet and every alert with it. `normalizeContactCondition` therefore reads a zero-rule tree as NO filter, and `conditionMeansAllDevices` is the only reader of the marker.
- **A stored condition that no longer validates degrades to "no filter", never to a throw.** `safeStoredCondition` warns and returns null: one bad row must not 500 the address-book list or the fire-time lookup.
- **The contact vocabulary is a SUPERSET, and that asymmetry is deliberate.** `DEVICE_FILTER_FIELD_OPS` = the automations scope fields + `osVersion`/`department`/`location`/`fortigate` + a wildcard `matches`. `matchScopeRule` evaluates the superset; each surface's SCHEMA is what restricts it, so validating against `SCOPE_FIELD_OPS` makes the extra fields unproducible. Do not widen the automations scope to match — `fortigate` needs the sighting relation, and the engine's scope filter runs over the whole fleet every tick. (`interfaceName`, added 2026-08, is the one field that IS in both vocabularies while reading a relation, and it is not a counter-example: it never joins. `scopeInterfaceIndex` answers each leaf with one GROUP BY returning asset ids, so the tick ships verdicts rather than rows — which is the bar a future relation-backed field has to clear before it goes in the narrow vocabulary. `fortigate` has not been given that treatment because one surface asked for it.)
- Targets are the UNION of criteria matches and explicit pins, and — unlike `MaintenanceSchedule` — are deliberately **not** intersected with `monitored: true`. An unmonitored device still has an owner, and event/change automations fire on it.
- `searchAddressBook` dedupes with the **user winning over the contact** on the same address: a `User.id` survives the person changing address, a stored contact string does not.
- Every write calls `bumpContactCache()`. The 30s TTL is what keeps the fire-time path off the table; a write that skips the bump leaves alerts routing on stale ownership for up to 30s.
- Ownership is enforced at the ROUTE (`requireOwnership` + `assertOwnership`), not here — this service is level-agnostic apart from stamping `createdBy` on create.

**When changing this:** Adding a field means threading it through the Zod shape in `routes/contacts.ts`, `ContactInput`, the editor in `public/js/automations-address-book.js` (`filterBody` + fill), and the tests. Changing the device-filter VOCABULARY means `DEVICE_FILTER_FIELD_OPS` + `matchScopeRule` + `SCOPE_FIELD_META` in `notificationTypes.ts` (one catalog serves both builders, so a label added there appears in the address book with no client change) — and if the new field has no `criteriaToCondition` mapping, add it to `UNCONVERTIBLE_FIELDS` rather than letting a legacy blob convert lossily. The flat `TagCriteria` vocabulary is still `tagAssignmentService`'s, shared with maintenance schedules and the app-map discovery rules; contacts now only READ it for un-folded rows. Adding a **dynamic recipient** (an entry naming a rule rather than an address) means the catalogue in `public/js/automations-address-book.js` — it is exported as `PolarisAddressBook.dynamicEntries(maxLevel)` and the wizard's recipient typeahead reads it from there, so declaring one in the wizard instead leaves the picker and the typeahead disagreeing — plus a `pickerEntryToPill` mapping and a `pillsToRecipients` / `recipientsToPills` pair in `automations-wizard.js`, and the fire-time resolver in `notificationRecipientService`. That module is loaded on every page the wizard is (assets / index / map / appmap / automations); adding a wizard page means adding both script tags.

## services/directorySyncService.ts

**What it owns:** The SCHEDULED half of the GAL story (business rule 35) — the exclusion filter's normalization and decision, and the projection of a contact's directory-owned fields from its provenance rows. Its live sibling `directorySearchService` persists nothing; this one is why `Contact.origin` and `DirectoryContactSource` exist.

**Public API:** `runDirectorySync` (the pass), `purgeDirectoryContacts`, `directorySyncAvailable`, `deleteExceedsGuard`, `normalizeDirectorySyncFilter`, `directoryExclusionReason` (PURE), `projectContactFromSources` (PURE), plus the `DirectoryPerson` / `DirectorySyncFilter` / `DirectorySyncSummary` types the two bulk readers produce and consume.

**Cross-service deps:** `utils/integrationFilter` (`matchesWildcard` — the canonical glob-lite matcher every device/VM/interface filter already uses, so an operator who has configured one knows how this behaves).

**Used by:** `entraIdService.listDirectoryPeople` and `activeDirectoryService.listDirectoryPeople` (the bulk readers, which import the types); `discoveryEngine`'s FOURTH post-sync pass (last in the `assetsOnly` block, gated on the two directory types plus `config.enableDirectorySync`); and `api/routes/integrations.ts`, whose PUT calls `purgeDirectoryContacts` when the sync is switched off or the integration disabled, and whose DELETE calls it BEFORE deleting the row — there is no FK on `integrationId`, so this is the only cleanup.

**Invariants:**

- **No directory PII in Events or logs, ever.** Exclusion reasons are categories (`"disabled account"`, `"room mailbox"`), never names or addresses. Events are readable by anyone with events access and are shipped off-host by the syslog and SFTP archivers. The single deliberate exception lives in contactService: `contact.adopted` names the address, because one human act is audited by name while bulk machine activity is anonymous. Do not "fix" that asymmetry.
- **`mailboxKind: "unknown"` is not a claim.** Graph cannot report a mailbox type in bulk, so the Entra reader says `"unknown"` for every user; `directoryExclusionReason` excludes only on a POSITIVE identification. Treating unknown as shared would drop a whole tenant.
- **The projection must be order-independent.** It is a projection precisely so two directories that disagree cannot ping-pong the row on alternating runs. A test asserts `project([a,b]) === project([b,a])` — keep it.
- **Include wins over exclude** for OU and domain, matching `filterDevices`.
- **The deletion half is refused wholesale on an ambiguous read.** `scanned === 0`, or a delete set over `deleteExceedsGuard` (`max(50, 20%)` — the FLOOR matters: on a small book 20% is one row, and the failure being guarded against is categorical, not incremental), skips deletion entirely and raises the Event to warning. A revoked grant must not empty the address book.
- **A contact dies only when its LAST provenance row goes.** Every delete is `origin: { not: "manual" }` AND `directorySources: { none: {} }`, which makes removing an adopted or hand-added row structurally impossible even on a bug.
- **The steady state must stay free.** The diff compares the stored `observed` blob and skips anything identical, so an unchanged directory issues zero writes. A test asserts it; keep it, or every discovery cycle rewrites the whole roster.

**When changing this:** adding a field to `DirectoryPerson` means adding it to BOTH readers (a field only one populates projects as null wherever the other ranks first) and deciding whether it belongs on the `Contact` row — anything that lands there is employee PII in every backup. Adding an exclusion means adding it to `normalizeDirectorySyncFilter`, to the Zod block in `integrations.ts`, and to the Directory tab in `integrations.js`, or the control exists in exactly one of the three places.

## services/directorySearchService.ts

**What it owns:** The address book's live lookup into the organization's directory (GAL) — fanning one typeahead query across every opted-in AD / Entra integration and merging the hits.

**Public API:** `searchDirectory(query, limit)`, `directorySearchAvailable()`, `bumpDirectoryCache()`, `MIN_DIRECTORY_QUERY`, `DirectorySearchEntry`.

**Cross-service deps:** `prisma` (integration rows only), `entraIdService.searchDirectoryEntra`, `activeDirectoryService.searchDirectoryAd`, `utils/ttlCache`, `utils/logger`.

**Used by:** `contactService.searchAddressBook` (when `includeDirectory`), which is reached from `GET /contacts/search?directory=1`.

**Readers of the state it writes:** none — it writes nothing.

**Invariants:**
- **Nothing is persisted, ever.** Results exist for one request plus a 60s cache; only an address an operator actually picks becomes a rule recipient or a saved `Contact`. Do not "improve" this into a periodic sync without a deliberate decision: a sync lands the whole employee roster (names, addresses, titles, departments) in the Polaris DB with its own retention, backup and audit-exposure surface.
- **Query strings and results never reach an Event or a log message.** `Event.details` is readable by anyone with events access and is shipped off-host by the syslog/SFTP archivers; a search term naming a person must not go there. The per-integration failure log deliberately carries only the integration id and type.
- **Opt-in per integration** (`config.enableDirectorySearch`, default false). Both backends need permissions device discovery never required — Graph `User.Read.All` + `Group.Read.All` + `OrgContact.Read.All` (or `Directory.Read.All`), and an AD bind that can read user/group/contact objects. Without the grant every keystroke 403s, so the gate keeps a broken typeahead off installs that haven't set it up. Granting them is a **tenant-admin decision and needs human review** — it widens what Polaris can read from the directory.
- **Failures degrade, they don't propagate.** `Promise.allSettled` per integration, and `searchAddressBook` wraps the whole call — a directory outage must still leave the local users ∪ contacts typeahead working.
- Minimum query length 2 (`MIN_DIRECTORY_QUERY`); the client debounces ~250 ms and the route is rate-limited (`contactSearchLimiter`). All three exist because this is the only keystroke-driven path in Polaris that proxies an external API.

**When changing this:** adding a backend means a `search<Backend>` export returning `DirectoryHit[]` plus a branch in the fan-out and its own opt-in flag — keep the failure isolation. The Entra `/groups` query combines `$search` + `$filter` + `$count=true`, which is the shape most likely to need adjusting against a real tenant; it's flagged in the source.

## services/userTimezoneService.ts

**What it owns:** The per-user display timezone — `User.timezone` (an IANA name, or the literal `"auto"`, default `"auto"`) and `User.detectedTimezone` (the zone that account's BROWSER last reported; client-posted on boot, never operator-set, never shown as a choice).

**Public API:** `AUTO_TIMEZONE`, `serverTimeZone()`, pure `isValidTimeZone(tz)`, pure `normalizeUserTimezone(v)`, pure `resolveTimeZone(stored, detected)`, `listTimeZones()`, `getUserTimezone(userId)`, `setUserTimezone(userId, username, tz)`, `recordDetectedTimezone(userId, tz)`.

**Cross-service deps:** `prisma` (User), `notificationRecipientService.bumpRecipientIndex` (the 30s user index carries the resolved zone), `eventLogService.logEvent`.

**Used by:** `src/api/routes/userTimezone.ts` (`GET|PUT /me/timezone`, `POST /me/timezone/detected`), `src/api/routes/auth.ts` (`/auth/me` echoes `timezone`, `serverTimezone` and `detectedTimezone` so the client can format from the first paint and skip a redundant detected-POST), `notificationRecipientService` (the index projection resolves each recipient's zone, and `expandDeliveries` groups a To line by it).

**Invariants:**
- **`resolveTimeZone` is explicit choice → detected browser zone → server zone, and the MIDDLE step is the whole feature.** Almost nobody opens the picker — their laptop is already in their zone, so the UI looks right — and without the detected step every one of those accounts keeps receiving email on the SERVER's clock, which on a UTC-clocked host is the exact misreading this service exists to stop. Collapsing it back to "auto → server" makes the feature inert for the default account while still passing every test that only exercises an explicit choice.
- **Never call `resolveTimeZone` to decide what the BROWSER renders in.** There `"auto"` means "pass no `timeZone` option and let the platform use its own", which is not the same answer as a resolved name and must not be flattened to one. The client half is `timeZoneOpts()` in [public/js/api.js](public/js/api.js), which returns `{}` on `"auto"`.
- **`normalizeUserTimezone` degrades to `"auto"`, never throws.** It is read on the alerting path from a plain TEXT column; a row naming a zone this build's ICU cannot apply must cost an alert its precise wall clock, never its delivery. The route's Zod schema is the strict half — an operator PUTting a bogus zone gets a 400 rather than a silent downgrade.
- **`detectedTimezone` is a detected fact, not a decision.** `recordDetectedTimezone` writes only when the value CHANGES (it is hit on every page load), is deliberately unaudited, and does not bump the recipient index — the next 30s refresh picks it up. It also refuses anything that doesn't normalize to a real zone, so a client sending garbage cannot move where an account's alerts read from.
- A `setUserTimezone` change writes `user.timezone.changed` and bumps the index. Skipping the bump makes the choice take up to 30s to reach the engine; skipping the Event makes "the email said 03:00 but the chart said 21:00" unanswerable from the Events tab.

**When changing this:** the browser half is `timeZoneOpts()` / `setDisplayTimeZone()` in [public/js/api.js](public/js/api.js) (read synchronously from `localStorage` at load, because api.js is the first script on every page and the first table can paint before `/auth/me` returns) and the account-menu row `_tzMenuItem` / `_openTimezoneModal` in [public/js/app.js](public/js/app.js). Adding a THIRD resolution source means this function, the recipient-index projection, and a decision about where it sits in the order.

## services/notificationPreferenceService.ts

**What it owns:** The per-user notification preference — which delivery method an account wants its alerts on (`email` | `push` | `any`, default `email`, `User.notificationPreference`). Business rule 39.

**Public API:** `NOTIFICATION_PREFERENCES`, `NOTIFICATION_PREFERENCE_LABELS`, `DEFAULT_NOTIFICATION_PREFERENCE`, `NotificationPreference`, pure `normalizeNotificationPreference(v)`, pure `preferenceAllowsTransport(pref, transport)`, `getNotificationPreference(userId)`, `setNotificationPreference(userId, username, pref)`.

**Cross-service deps:** `prisma` (User), `notificationRecipientService.bumpRecipientIndex` (the 30s user index carries the preference), `eventLogService.logEvent`.

**Used by:** `src/api/routes/notificationPreference.ts` (`GET|PUT /me/notification-preference`), `src/api/routes/auth.ts` (`/auth/me` echoes the normalized value so a client reconciles push enrollment on the boot request it already makes), `notificationRecipientService` (the index projection + the `respectUserPreference` filter in `expandDeliveries`).

**Invariants:**
- **The stored preference is the ACCOUNT's, not the browser's.** There is no per-device enable/disable control anywhere any more — `polarisPush.syncToPreference` reconciles each browser's `PushSubscription` to this value at boot instead. Anything that adds a device-local push switch re-opens the bug the rule was written for: "I turned push on" and "my phone buzzes" becoming different facts.
- **`normalizeNotificationPreference` degrades to `email`, never to nobody.** This is read on the alerting hot path from a plain TEXT column; a row holding a value this build has not heard of must fall back to the method everyone has rather than un-address an alert.
- **`preferenceAllowsTransport` answers `true` for every transport that isn't `email` or `web_push`.** A Slack/Teams webhook or a Pushbullet channel posts to one fixed destination and has no per-user recipients, so no preference can be expressed about it and none may withhold it. Callers never ask, but the function must not depend on that.
- **It never decides WHETHER to filter** — only whether a given transport is acceptable. The gate (does this action group offer both methods?) is `automationActionService.actionsCarryBothMethods`, and the per-target opt-in is `respectUserPreference`. Adding the group logic here would put it out of reach of the only caller that can see a group.
- Every change writes `user.notification_preference.changed` and bumps the recipient index. Skipping the bump makes a change take up to 30s to reach the engine; skipping the Event makes "I never got paged" unanswerable from the Events tab.

**When changing this:** the vocabulary is mirrored in three clients — `NOTIF_PREF_LABELS`/`NOTIF_PREF_ORDER` in [public/js/app.js](public/js/app.js) and `PREF_LABELS`/`PREF_ORDER` in [public/js/mobile/more-tab.js](public/js/mobile/more-tab.js) — which is why the GET returns `options`; adding a fourth value means the migration's column default, this file, both clients, and a decision in `preferenceAllowsTransport` about which transports it accepts.

## services/notificationRecipientService.ts

**What it owns:** Routing a fired notification to concrete delivery recipients, and expanding a rule's `targets[]` into `NotificationDelivery` rows.

**Public API:** `resolveRecipientUsers(recipientTags)`, `resolveRecipientUsersByIds(ids)`, `resolveEmailRecipients({recipientUserIds?, addresses?, recipientRoles?, recipientRegions?, recipientTags?})`, `dedupeEmailRecipients(to, cc, bcc)` (pure), `listRecipientUsers()` (builder picker), `scopeRegionTagsOf(scope)`, `expandDeliveries(notificationId, targets, opts {scopeRegionTags?, assetRegionTags?, composedEmail?, escalation?, enforceUserPreference?})` (the level-routing index it needs is resolved through a closure memoized per NOTIFICATION, so a rule with three notify actions reads it once and a rule that never opts in pays nothing), `ExpandDeliveriesOptions` + `ComposedEmail` types, `bumpRecipientIndex()`, `timeZoneByAddress()` (address → the resolved IANA zone that account reads in — the `ackCapabilityByAddress` sibling, built off the same cached index, lowest user id wins a shared address), pure `splitTimeZoneGroups(to, cc, bcc, zoneOf, fallbackZone)` + the `TimeZoneGroup` type.

**Cross-service deps:** `regionScopeService.resolveTagScopesForUser` (effective tags per user), `notificationService.stripRegionPrefix`, `notificationTypes.CHANNEL_TRANSPORT` (channel type → transport), `notificationPreferenceService.{normalizeNotificationPreference,preferenceAllowsTransport}` (business rule 39), `userTimezoneService.{resolveTimeZone,serverTimeZone}` (per-recipient email zones), `prisma` (notificationChannel lookup + users + pushSubscriptions + notificationDelivery).

**Used by:** `src/services/automationActionService.ts` (the notify arm — sole `expandDeliveries` caller; the engine + escalation sweep reach it through `executeActions`), `src/api/routes/notificationRules.ts` (`GET /recipient-users`).

**Invariants:**
- A target's recipients (email/web_push channels) = union of explicit `recipientUserIds` + (when `recipientDeviceRegion`) users matching the TRIGGERING asset's `region:` tag(s) (`assetRegionTags` — engine passes `regionSnapshot(reading.tags)`, the sweep passes `Notification.regionTags`) + (when `recipientScopeRegion`) users matching the rule's scope `region:` tag(s) + `recipientTags` (registry tags, flattened match), plus explicit `addresses` (email). Deduped by user id.
- Recipient matching strips the `region:` prefix and lower-cases both sides, so a scope tag `region:Atlanta` matches a user whose regionTags include `Atlanta`; region + other tags are matched as one union.
- `recipientScopeRegion` resolves against the RULE'S SCOPE region tags (passed in by the engine); `recipientDeviceRegion` resolves against the TRIGGERING ASSET's region tags — the builder now offers only device-region (scope-region renders on old actions that already carry it).
- slack/teams/pushbullet ignore recipients entirely (one fixed-destination row).
- **A composed email splits at most into (distinct recipient timezones x 2 acknowledge variants) rows — never one per person.** Business rule 25 retired the per-recipient fan-out and it stays retired: the acknowledge link works for whoever reads it, so nothing about the LINK splits a send. Two things about the READER still do, and they compose rather than nest — `splitTimeZoneGroups` first, then `splitAckVariants` per group. A fleet whose operators share a zone and can all acknowledge still produces the single row it always did. Cc and Bcc group on the SAME key as To, so an address is mailed in its owner's zone whichever line it sits on and nobody receives two copies.
- **The per-zone split only happens when the caller supplied `composedEmailForTimeZone`.** Without that closure every address falls back to the server zone, `splitTimeZoneGroups` returns one group, and the behaviour is byte-identical to the pre-column send — which is the honest answer for a caller that cannot rebuild its body. The closure is called once per DISTINCT zone and memoized, and the server-zone group reuses the already-built body rather than rebuilding an identical one.
- **`meta.timeZone` is stamped on a per-zone row so the DRAIN's late-bound blocks agree with the body.** The LLDP "Last advertised" row is built at delivery time, after this function has returned; without the stamp it would render in the server's zone and one email would disagree with itself about what time it is. Anything else that comes to be stitched in at drain time has to read the same key.
- **The two broadcast modes are WEB PUSH only, at runtime as well as at save.** `recipientAllUsers` / `recipientAllRegions` are resolved inside `if (transport === "web_push")`. Save-time validation already refused them on a single-channel email action; the runtime gate is what keeps a MULTI-CHANNEL action (push + email, allowed since business rule 39) from mailing the whole roster off a control that lives in the builder's push block and reads as "tell every device".
- **`respectUserPreference` filters USERS only, and only when the caller says the group qualifies.** The target flag AND `opts.enforceUserPreference` must both be set; the option defaults false, so a caller that never opts in behaves exactly as it did pre-feature even against a stored target carrying the flag. Only the caller (`automationActionService`) can decide the group half — the question is "does this actions[] list offer both methods", which no single target can see. Typed addresses and address-book contacts are NEVER filtered: they have no account and expressed no preference, and inventing one for them is the rule 25 posture inverted.
- **`preferenceWithholds` is the guard against the filter delivering NOTHING** (pure, exported, tested). A push-preferring user with zero `PushSubscription` rows stays on the email; an email-preferring user with a null `email` stays on the push. `pushDeviceCounts()` is the one `groupBy` behind it — lazy, memoized per notification, and only reached when a filter is about to drop someone, so a send that never opts in pays nothing. Reachability here means the SUBSCRIPTION EXISTS and nothing more: a push service's 201 is not delivery, and a dead endpoint is only discovered by `deliverNotifications` at send time (`gone` on 404/410), far too late to re-route.
- The user index carries `notificationPreference` alongside each user's tag scope, so a preference change needs `bumpRecipientIndex()` (the setter does it) or it takes up to the 30s TTL to reach the engine.
- Recipients are snapshotted at fire time (delivery rows reflect targets when the rule fired, not when the drain runs).
- With a `composedEmail` (rule has emailComposition), each email target gets ONE row (`target` = joined To list, `meta` = {composed, to, cc, bcc, subject, text, html?}); empty To skips the target. Cc/Bcc dedupe: To wins over Cc, Bcc drops anything visible in To/Cc. Without it, the legacy one-row-per-address fan-out is byte-identical.
- `meta` carries rendered content + recipient addresses only — never channel secrets.
- In-app delivery is never a `NotificationDelivery` row — it's the `Notification` itself.
- ACK LINKS: the acknowledge URL is **one per ALERT, not per recipient** (`ackUrlForEmail(notificationId)` — business rule 25), so `expandDeliveries` resolves the deferred `{ack}` ONCE via `fillComposedAckUrl` before the target loop and every message carries the same working link. A COMPOSED email is therefore **one delivery row** whose `target` is the joined To line, with Cc/Bcc as plain Cc/Bcc. `buildAddressOwnerMap` survives as the thing that DEDUPES that To line across users / typed addresses / contacts (user beats a typed or contact entry for the same address; ties break on lowest id since `User.email` is nullable and not unique) — its owner VALUES are now informational. On an install with no `POLARIS_PUBLIC_URL` the substitution blanks the button away and re-prunes, rather than mailing a literal `{ack}`. **Do not reintroduce a per-recipient split**: it multiplied the send, rewrote the To line every reader sees, and only ever existed to carry a token that no longer exists.
- The `{ack}` token is filled HERE, per recipient, not by `buildTemplateContext` — the context is built once per fire and snapshotted onto `Notification.templateCtx` for everyone to share, so a context key would render it empty before recipients were even known. A composed row that earns no token has `{ack}` stripped rather than mailed literally.
- `applyAckToRows` (pure, exported for tests) resolves `{ack}` for EVERY composed row — filling it for a row that earned a token and blanking it for one that didn't — and must run even when the whole fan-out minted nothing. An automation whose only recipients are typed addresses or address-book contacts is exactly that case, and short-circuiting on "nothing to mint" mailed them the literal `{ack}`.

**When changing this:** keep the tag-match semantics aligned with `scopeMatchesAsset` and `regionScopeService` so rule scope and recipient routing read tags the same way. Bump the user-tag index cache (`bumpRecipientIndex`) if a user/role/group-mapping write must take effect immediately.

## services/alertChartService.ts

**What it owns:** The last-hour CPU / memory / response-time charts embedded in an alert email — sample query, SVG render, PNG rasterization, and token substitution.

**Public API:** `buildAlertCharts(assetId, tokens, {now?, thresholds?, sensorName?, dimension?, metric?, lossWindowMs?})`, `chartTokensIn(...templates)`, `substituteChartTokens(body, charts, {html})`, `attachmentsFor(charts, body)`, `lossBucketMs(windowMs)`, `probeLossSeriesFrom(rows, bucketMs)`, `failSpansFrom(rows, windowEndMs, downThreshold?, recoveryPolls?)`, `outageRunFailures(rows)`, `chartTokenForMetric(metric)`, `isPortScopedAlert(metric)`, `isSdwanScopedAlert(metric)`, `parseSdwanDimension(dimension)`, `resolveSdwanTarget(assetId, metric, dimension)`, `sdwanSeriesFrom(rows, target)`, `sdwanChartLabel(metricLabel, healthCheck, link)`, `loadSensorSeries(...)`, `sensorReadingDisplay(...)`, `CHART_TOKENS`, `CHART_WINDOW_MS`.

**Cross-service deps:** `utils/sparklineSvg` (pure geometry), `@resvg/resvg-js` (lazy import — the same rasterizer appIconService uses), `probeOutageService` (`foldProbeOutages` + `replayProbeStates` + `foldProbeRecoveries` — the shared folds behind the response-time chart's colours), `downDetectionService` (`describeDownDetectionFor` + `recoveryPollsFor` — which automation defines Down here and at what count), `monitoringService.resolveMonitorSettings` (ONLY on the path where an automation sets a reset hold, to convert its stored seconds back to polls), `brandingService.getBranding` (the sensor chart's display unit), Prisma reads of `AssetTelemetrySample` + `AssetMonitorSample` + `AssetHardwareSensorSample` + `AssetPerfSlaSample` + `AssetSdwanRule`.

**Used by:** `src/services/notificationDeliveryService.ts` (the only caller — `emailMessageFor` on composed email rows).

**Invariants:**
- Charts are built at DELIVERY time, never at fire time. The engine's fire path is transition-guarded and hot; the drain is a queue. It also means an escalation email at T+90min charts the last hour AS OF SENDING rather than re-rendering the frozen fire-time context.
- Response time plots SUCCESSFUL probes only. A failed probe has no response time, and plotting it as 0 would draw a fast device instead of an unreachable one.
- **A gap is not a reading, so the CPU / memory / response-time charts SHADE failed polls and BREAK the line over them** (`FAIL_SPAN_TOKENS`, `failSpansFrom` + `sparklineSvg`'s `failSpans`). Excluding failed probes keeps the line honest about VALUES but leaves the polyline interpolating a straight, healthy-looking segment across the exact minutes nothing answered -- on a response-time chart of a down device that is the whole story, drawn as if it never happened. The span gets a red band (lighter than an alarm band, `0.10` vs `0.13`), the fill closes at each run's own extent rather than under the gap, and the bridging segment is a `<linearGradient>` stroke fading out and back in -- nothing at all there would read as a chart that stopped rendering. `failSpansFrom` merges consecutive failures into one span and leaves a run that is STILL failing at the newest sample OPEN to the window end (a device down as the email sends is down to the right edge, not to whenever its last poll landed). Two deliberate exclusions: the LOSS chart (its points already ARE the failures, as a ratio -- banding them would double-draw one fact) and the SENSOR chart (its red already means the device's own alarm bit; two red vocabularies on one chart are unreadable). The query is **PRIMARY probes only** -- the ICMP loss sampler fires every 10s precisely because probes are failing (rule 30, and it never confirms anything), so letting its rows define outage bands would paint failure the operator's configured cadence never declared. The failed COUNT rides the summary line for the same reason the alarm note does: the bands are invisible to a recipient with images blocked.
- Memory uses `memPct` when the source reports a percentage (FortiOS) and `memUsedBytes/memTotalBytes` when it reports bytes (SNMP HOST-RESOURCES, WMI) — the same COALESCE the dashboard memory widget uses.
- Percentage charts pin the axis to 0–100 so two alerts about the same device are comparable; a self-scaling axis would render a quiet 2–4% hour as a dramatic climb.
- EVERY failure degrades to the text summary and never throws: no samples, an unreadable asset, or a missing native resvg binding must not stop the alert from sending.
- Plotted points are capped (`MAX_POINTS`) with the newest always kept — the alerting sample is the one that must survive downsampling.

- The SENSOR chart is keyed on `Notification.dimension` (the engine's dimensionKey, which for both hwSensorValue and hwSensorAlarm is the bare sensor name) and is SKIPPED entirely without one — no query, and the token renders away rather than drawing an empty box on the ~all alerts that are not about a sensor.
- An ALARM automation charts the sensor VALUE, with the device's own alarm periods shaded: the bit says something is wrong, the value says whether it climbed, dropped, or never moved.
- Sensor values are converted for DISPLAY only (C→F per the branding setting), gated on each reading's own stored unit and never on its class — a fan's RPM and a rail's volts pass through. `sensorReadingDisplay` exists so the SENTENCE above the chart uses the same unit as the chart itself.
- `chart.trigger` is an ALIAS resolved from `Notification.metric` via `chartTokenForMetric`; substitution tracks emitted cids so the chart it drew is not drawn again by its own token later in the body.
- **The RESPONSE-TIME chart is about a verdict, so it carries the whole status vocabulary; every other chart carries two colours** (2026-08-29). Its series colour is the Up green (`#2e7d32` — the daylight themes' `--color-success` as flat hex, chosen for the white email card), `recoverSpans` paints an answered-but-still-in-debt poll `#0288d1`, and `failSpans[].kind` is a THREE-way: `"outage"` red, `"dependency"` grey, `"missed"` amber `#ffc107` for a miss that has not yet reached the covering automation's `missedPolls`. Amber vs red is not decoration — red asserts Down, so spending it on the first dropped packet of a three-miss threshold dates the outage two polls before Polaris agreed to it. Gated to that one token (`RECOVER_SPAN_TOKENS`, and `loadFailSpans` is the only place a threshold is resolved); CPU and memory keep their own series colour, exactly as they do in-app. **Both halves come from ONE replay**, `probeOutageService.replayProbeStates`, which is a deliberate mirror of the browser's shared `PolarisMonitorStates.replay` (`public/js/monitor-states.js`) — `failSpansFrom` labels a failed verdict `belowThreshold` when the replay says `warning` and reads its recovery spans off the same states, so the amber/red split and the blue climb cannot disagree with each other OR with the device page. `undefined` threshold is UNKNOWN and keeps every miss red; `null` is PASSIVE and lets nothing go red. `recoveryPolls` costs an asset read only when the automation actually sets a reset hold — without one the answer is the missed-poll count, which is the bucket's own drain. Parity is pinned by [tests/unit/assetIntermittencyBar.test.ts](tests/unit/assetIntermittencyBar.test.ts), which runs the browser and server copies over the same patterns.
- The PACKET-LOSS chart is derived, not stored: `AssetMonitorSample` records one success/failure per probe, so `loadProbeLoss` buckets them and plots the failure ratio. Empty buckets are skipped rather than plotted as 0 — a gap in polling is not a period of perfect health. **Its caption must state the PROBE ratio, never the mean of the buckets.** `probeLossSeriesFrom` returns both (`points` for the line, `ratioPct` for the caption) and `sparklineSvg`'s `avgOverride` prints the latter. An unweighted mean of per-bucket ratios counts a 10-probe bucket the same as a 1-probe one, so it drifts from the engine's reading whenever sampling is uneven -- a polling gap, the anchor trimming a partial bucket, a dependency-suppressed asset's 2x interval, or the ICMP sampler firing every 10s precisely because probes were failing. Prod 2026-08-20 mailed `18.3 %` over `avg 6.7 %`. If you add another bucketed-ratio chart, pass `avgOverride` with it; a chart whose points ARE the quantity (CPU, memory, latency) must leave it unset. **BOTH ANCHORS ARE GONE (2026-09-01), and so are `measuredFromMs` and `sparklineSvg`'s `measured` rule** — they existed only to reconcile a caption that measured less of the window than the line drew, and with the trim removed there is nothing left to mark. `effectiveLossAnchorMs` went with them; `utils/probeLossAnchor.ts` keeps only the writer's predicate. **What the line and the caption now share is an EXCLUSION rather than a window** (business rule 29h, 2026-09-03): the failures of any run that reached `down` — a maximal stretch of consecutive failures holding a row stamped `AssetMonitorSample.assetDown`, onset included — are dropped from BOTH, matching `probeLossQuery`. `outageRunFailures` is the JS mirror of that query's `runId`/`runOutage` window functions and has to stay one; it is exported for the parity test. Dropping it from one and not the other is the exact failure this bullet's first half is about: an alert reading `0.0 %` over a chart captioned `avg 40 %` tells the operator the number is invented. The excluded stretch leaves a GAP in the line, never a run of 0 % — the same treatment a polling gap gets, because nothing was measured about the LINK while the device was dark. A window with no countable probe at all has a null `ratioPct` and no points; a fully-dark window that was never stamped still reads 100 %, which is what asset-down alerts embedding this chart depend on (a blank one reads as "no loss"). The chart still weights burst rows by PACKETS like the query, and still does NOT drop poll rows once burst rows exist — a picture of the window has to be continuous — so its caption can sit a little under the engine's reading on a mixed asset. It is also the one chart whose WINDOW follows the automation (2026-08-20): `lossWindowMs` — resolved by notificationDeliveryService's `lossChartWindowMs` from the rule's trigger through the engine-shared `probeLossWindowSec` (notificationTypes) — makes the graph span exactly the History the alert's ratio was measured over; `lossBucketMs` scales the 2-minute buckets so ~30 points cover any span, and the axis + summary line state the real window. CPU / memory / response time stay last-hour context, and a null `lossWindowMs` (no rule, no loss condition, test alerts) keeps the hour.
- `chartTokenForMetric` also answers for the asset_state fields (`monitorStatus`, `consecutiveFailures`), which are not metrics at all: a down device's story is its response time climbing before it stopped answering. When every probe in the window failed there is no latency left to plot, that chart drops itself, and the loss chart — which the body requests unconditionally — carries it.
- **An SD-WAN alert charts the PATH, not the firewall** (`isSdwanScopedAlert`, 2026-09-09). All five SD-WAN triggers — the three health-check metrics plus the two service-rule state fields (`sdwanRuleStatus` / `sdwanSelectedMember`) — DROP `chart.cpu` / `chart.memory` / `chart.responseTime` / `chart.probeLoss` from the token set even when the body asks for them, and render `chart.sdwanLatency` / `chart.sdwanJitter` / `chart.sdwanLoss` instead. Same argument as the port case one layer out: a FortiGate losing 40% to wan1 is answering its own probes perfectly, so its device graphs are the story of a healthy firewall printed under an alert about a degraded link (reported by an operator 2026-09-09). Unlike the port case the alert is NOT left graphless — `AssetPerfSlaSample` is a real time series. Nothing is force-added to the token set: the default body carries all three (latency, jitter and loss are one picture of a link, and the operator is about to ask which moved), and a body customized before they existed still leads with the right graph through `{chart.trigger}`, which is what the alias is for. The path is resolved by `resolveSdwanTarget`: a METRIC alert's `Notification.dimension` is the engine's `"<healthCheck>|<link>"` key and is parsed (first separator — FortiOS names admit no `|`); a RULE alert's dimension is the service-rule NAME, so it costs one `AssetSdwanRule` read for the rule's `healthChecks` + current `selectedMember`, and a rule with no performance SLA behind it (mode `priority`/`manual`) draws nothing rather than some unrelated health check. `sdwanSeriesFrom` is the pure fold and owns the PICK — these charts are single-series, so it draws the pair the alert names when that pair reported, else the freshest-reporting member with health checks tried in the target's own order (a failover's selected member legitimately has no rows: FortiOS omits a member it could not probe). The dashed line is the FortiGate's OWN SLA target off the sample columns, never the automation's threshold — an automation watching "latency > 150" must not draw its line over a link whose configured target is 80 — and a caller-supplied `thresholds[token]` still wins. These are the only percent-ish charts that do NOT pin 0–100 (an SLA loss target is 1–2%, and a pinned axis draws a breach as a flat line on the floor). `state != "up"` samples become `alarmSpans`, the same band and the same claim as a sensor's own alarm bit — the device's verdict about a reading — and it rides the text summary too, because on a failover email "the member was down" is usually the whole finding. Both the label (`sdwanChartLabel`, budgeted and truncated — the label is drawn at a fixed x beside the right-aligned caption) and the summary state the charted pair, since the pair drawn may not be the one the alert named.
- An alert on an interface's STATE (`ifOperStatus` / `ifAdminStatus` / `poeStatus` — `isPortScopedAlert`) gets NO charts at all: `buildAlertCharts` returns the empty map before any query. A switch with a dead port is answering probes (that is how the port is known to be down), so all four device series are flat and healthy — four graphs of a healthy device under "Interface oper status on port2 is down" bury the finding instead of explaining it. Returning the empty map (rather than filtering the token list) is what makes every `{chart.*}` render away AND lets `pruneEmptyChartSection` drop the "Last hour" heading with them. Only the STATE trio, deliberately — an `ifInErrorRate` / `ifOutBps` alert plausibly correlates with device load and keeps its graphs. `services/alertInterfaceService.ts` supplies what takes their place.

**When changing this:** the `{chart.*}` tokens are DEFERRED — they must stay out of `buildTemplateContext` and out of `Notification.templateCtx`, or the substitution here finds nothing. Deferral is matched by PREFIX (`isDeferredToken` in utils/notificationTemplate), so a new chart token is deferred automatically; an enumerated list was wrong within a week (`{chart.trigger}` shipped, wasn't listed, and was silently blanked at compose time). Adding a chart still means `CHART_TOKENS` + `TEMPLATE_VARIABLES` + a slot in BOTH halves of the default body (`alertEmailTemplate.test.ts` asserts the body asks for the whole catalogue) + an entry in `META` and in `buildAlertCharts`'s `series` record (both are `Record<ChartToken, …>`, so the compiler names anything you forget). A chart keyed on a sub-asset DIMENSION (sensor, SD-WAN path) is skipped when it can't be resolved rather than drawn empty, and if it REPLACES the device charts the way the SD-WAN trio does, say so in the `{chart.cpu}` token description too — the wizard's token picker reads `TEMPLATE_VARIABLES` verbatim and that list is where an operator finds out.

## services/alertBrandService.ts

**What it owns:** The install's letterhead in the top-right corner of an alert email — which artwork the email uses, whether the application name prints beside it, and both rendered forms of the block plus the inline attachment the HTML cites.

**Public API:** `buildAlertBrandBlock()` (the whole delivery-time step — one branding read, one image load, both bodies, memoized 60s), `brandTokensIn(...templates)`, `substituteBrandTokens(body, block)`, `BRAND_LOGO_CID`, plus the pure pieces the tests drive: `renderBrandBlock({name, subtitle, logo}, {html})`, `fitLogo(size)`, `MAX_LOGO_WIDTH` / `MAX_LOGO_HEIGHT`, `EMAIL_LOGO_PATH`, `__resetAlertBrandCacheForTests()`.

**Cross-service deps:** `brandingService.getBranding` + `displayAppName`, `brandLogoService.renderAccentedLogo("light")`, `appIconService.resolveBrandingLogoFile`, `utils/imageMagic.detectImageMagic`, `utils/imageSize.imageSize`, `utils/notificationTemplate.escapeHtml`.

**Used by:** `src/services/notificationDeliveryService.ts` (the only caller — `emailMessageFor` on composed email rows, in the same pass as the charts and the LLDP block); `src/utils/alertEmailTemplate.ts` carries the `{brand.header}` token in both default bodies.

**Invariants:**
- **Which artwork is business rule 27's decision, not this file's.** The email card is white, so the LIGHT-inked variant is the only one that doesn't disappear — `polaris-horiz-light.png`, the horizontal lockup. Because that art already spells the product name, the app name is NOT printed beside it (rule 27's showName=false); an operator's own logo has no wordmark we know of, so it gets the name as its caption. Re-export the brand PNGs and this path changes with them.
- The subtitle renders EITHER WAY — it is the operator's own line of copy, not a caption for the mark. An operator who blanked `appName` deliberately gets no name text at all (rule 27 again: an empty name is a legitimate stored value, which is why nothing here calls `displayAppName` for the visible caption).
- `displayAppName` IS used for the `alt` text and for the plain-text form, because those are the only things naming the sender when images are blocked or when there is no HTML at all.
- `{brand.header}` is a DEFERRED token (`isDeferredToken` matches the `brand.` PREFIX, like `chart.` and `interface.`). It must stay out of `buildTemplateContext` / `Notification.templateCtx`: a context key would render it to "" at compose time and leave this pass nothing to fill — and a fire-time snapshot would freeze the branding into every escalation email sent hours later.
- The logo is an INLINE CID attachment. Not a remote URL (it would need an unauthenticated endpoint and most clients block remote images by default) and not a data: URI (Gmail and Outlook both drop those). The attachment is appended only when the substituted HTML actually cites `cid:polaris-brand-logo`, mirroring `attachmentsFor`.
- **The header row must stay immune to `pruneEmptyRows`.** The two-column header is a two-cell row whose second cell is empty on an install with no letterhead — the exact label/value shape that pass deletes, and deleting it takes the severity line, the subject and the trigger sentence with it. The one-cell `<table>` wrapped around the token in `DEFAULT_ALERT_HTML` is the guard (a span containing a `<table>` never matches; a one-cell row is never a candidate). Any re-layout of that header has to preserve it.
- PNG/JPEG only. A WebP upload has no accent path either (resvg cannot decode it) and mail clients handle it unevenly, so such an install gets the name-and-subtitle block with no image.
- `fitLogo` never enlarges and caps at 150×46: an operator upload can be any size, and an unconstrained 900px banner scaled by the client pushes the headline into a two-word column. Both dimensions are emitted as HTML ATTRIBUTES because Outlook sizes from those, not from CSS.
- Every failure rung degrades — unreadable branding, unresolvable logoUrl, failed accent composite, bad magic bytes, unreadable dimensions — dropping the logo, then the whole block. Nothing throws. Letterhead must never be the reason an alert does not arrive; failures log once per distinct reason (`warnOnce`), never per email.
- Memoized 60s (`CACHE_TTL_MS`) because a drain sends up to `BATCH_SIZE` emails per tick and every one of them wants the identical block. Branding changes on an operator click, so a minute of staleness in letterhead costs nothing — but it means a test must call `__resetAlertBrandCacheForTests()`.

**When changing this:** the block is rendered per body from one shared `parts` object, so a new element has to be added to `renderBrandBlock` (both branches) rather than to one of them. Adding a second `{brand.*}` token means widening `BRAND_TOKENS` + `substituteBrandTokens`; the deferred-token prefix already covers it. If the block can ever contain a `<table>` of its own, re-check the header's prune immunity — the guard is currently a static wrapper in the template, not something this file emits.

## services/alertInterfaceService.ts

**What it owns:** The per-INTERFACE block an alert email carries when the thing that broke is one port — the LLDP-neighbour lookup for that port and both rendered forms of it. It is the answer to what `alertChartService.isPortScopedAlert` removes: an interface-down email with no charts and no LLDP block would be a headline and nothing else.

**Public API:** `buildInterfaceLldpBlocks(assetId, metric, dimension)` (the whole delivery-time step — gate, one read, both bodies), `interfaceTokensIn(...templates)`, `substituteInterfaceTokens(body, block)`, plus the pieces the tests drive directly: `loadInterfaceLldp(assetId, ifName)`, `renderInterfaceLldp(ifName, neighbors, {html})`, `isInterfaceDimensionMetric(metric)`, `INTERFACE_DIMENSION_METRICS`, `INTERFACE_TOKENS`.

**Cross-service deps:** Prisma read of `AssetLldpNeighbor` (read-only — nothing here writes), `utils/fortiapInterfaceAlias.fortiapInterfaceAliases`, `utils/notificationTemplate` (`escapeHtml`, `formatLocalTime`), `utils/alertEmailTemplate.factRow` (so the block matches the facts table's visual language exactly rather than inventing a second one).

**Used by:** `src/services/notificationDeliveryService.ts` (the only caller — `emailMessageFor` on composed email rows, in the same pass as the charts).

**Invariants:**
- The neighbour of a down port is findable ONLY because `persistLldpNeighbors` keeps a vanished row for a 48-hour sticky window (`LLDP_STICKY_WINDOW_MS`) before deleting it. That grace was added for the operator-visible Neighbor column, and this feature now depends on it: shorten or remove it and an interface-down email loses its substance. It is also why every entry prints **Last advertised** and why that row is never omitted — the row predates the outage by definition, so how stale it is IS the finding. The counterpart obligation is on the OTHER readers: a consumer that treats an LLDP row as evidence of a physical CABLE must apply its own, tighter freshness bound, because within this window a row outlives the cable it describes (the Device Map's inter-switch member expansion drew one link as two parallel lines until it started skipping rows older than 1h — see `GET /map/sites/:id/topology` in the skill references (formerly ARCHITECTURE.md)).
- Built at DELIVERY time, for alertChartService's reasons: off the engine's transition-guarded hot path, and an escalation at T+90min re-reads the port rather than replaying a snapshot.
- `{interface.lldp}` is a DEFERRED token (`isDeferredToken` matches the `interface.` PREFIX, like `chart.`). It must stay out of `buildTemplateContext` and `Notification.templateCtx` — a context key would render it to "" at compose time and leave this pass nothing to fill. The prefix rather than an enumerated name is the lesson `chart.trigger` already taught.
- The text form uses **no colons anywhere**. `pruneEmptyTextLines` deletes any "Label:" line with nothing after the colon, and "LLDP neighbor on port2:" matches that shape exactly — the block would delete its own heading. Padded label columns read the same and can't be mistaken for a fact row.
- The token expands to a COMPLETE block (its own `<tr>`, its own heading) or to the empty string. That is what keeps a non-interface alert — or a port with no neighbour — from needing a pruning pass like `pruneEmptyChartSection`.
- The port lookup goes through `fortiapInterfaceAliases`, never a bare equality: a FortiAP's LLDP rows are normalized to whichever of lan1/eth0 its interface inventory reports, so the alert's ifName and the stored `localIfName` can legitimately differ. A switch port's alias set is just itself, so nothing changes there.
- Gated on `INTERFACE_DIMENSION_METRICS` so a non-interface alert costs ZERO queries (a sensor alert's dimension is "TMP1" and would match no row anyway). Note this set is WIDER than alertChartService's `PORT_SCOPED_METRICS`: the counter-rate metrics keep their charts but still want to know what is on the port.
- Every network-supplied string (systemName, chassisId, portDescription, systemDescription) is `escapeHtml`'d in the HTML form — LLDP TLVs are attacker-influenceable on an untrusted port.
- A failed read logs at warn and yields no block. An alert must never fail to send because the LLDP lookup did.

**When changing this:** the block is rendered per body, so any new field has to be added to `neighborFacts` (shared by both forms) rather than to one of them — the HTML and text bodies drifting is exactly what the shared helper prevents. Adding a second `{interface.*}` token means widening `INTERFACE_TOKENS` + `substituteInterfaceTokens`; the deferred-token prefix already covers it. If you add a field whose value can be empty, filter it in `neighborFacts` — `pruneEmptyRows` runs at COMPOSE time and never sees this block, so an empty row here mails an empty cell.

## services/notificationDeliveryService.ts

**What it owns:** Draining pending `NotificationDelivery` rows and dispatching each to its channel.

**Public API:** `drainPendingDeliveries()`, plus the fallback's three pure pieces: `readPushFallback(meta)`, `pushStillInPlay(siblings, userId)`, `alreadyEmailedOnChannel(siblings, channelId, address)` (+ `FallbackSibling`, `PushFallback`).

**Cross-service deps:** the channel senders (`notificationChannels/emailChannel.{sendSmtpEmail,sendM365Email}`, `webhookChannel.sendWebhook`, `pushbulletChannel.sendPushbullet`, `webPushChannel.sendWebPush`), `prisma` (delivery rows + notificationChannel config + pushSubscription prune), `eventLogService.logEvent`.

**Used by:** `src/jobs/deliverNotifications.ts` (15s tick).

**Invariants:**
- Each delivery's destination secrets (SMTP password, webhook URL, VAPID key, …) are read from its `NotificationChannel` at send time, NOT stored on the delivery row.
- A missing/deleted channel (NULL channelId) is a PERMANENT fail (not retried); otherwise ≤3 attempts before flipping to `failed`.
- **A push that dies for good becomes an email** (business rule 39). `enqueuePushFallbacks` runs AFTER the status writes — never before, because it asks whether any of a recipient's OTHER devices are still in play and the rows that just failed have to already read `failed` for that answer to be honest. It is wrapped so a throw costs neither the status writes nor the summary Event; the count rides that Event's details as `emailedInsteadOfPush`.
- **The three guards are pure and exported, not inlined** — every one of them fails silently, in the annoying direction (a duplicate alert) or the dangerous one (no alert at all). `pushStillInPlay` is per RECIPIENT, not per row (`sent` = reached, `pending` = a retry may still land it); `alreadyEmailedOnChannel` is a SUBSTRING test because a composed send is ONE row whose target is the whole joined To list; `readPushFallback` type-checks the stamp so a malformed row is inert rather than a crash on the delivery hot path. `tests/unit/pushEmailFallback.test.ts` imports these, deliberately: an earlier draft mirrored them in the test and the mirror had already drifted.
- **The fallback channel is chosen at EXPANSION time, not here.** `notificationRecipientService` stamps `meta.fallback = {userId, channelId, address}` on each push row from the ACTION'S OWN email channels, because by the time the drain finds out, the subscription has been pruned and nothing is left saying whose endpoint it was. A push-only action stamps nothing and keeps the existing warning — re-routing through some other channel's SMTP config would be Polaris inventing a destination nobody configured for that alert.
- Email rows branch on `meta.composed`: composed rows send ONE to/cc/bcc message from the meta snapshot (to/cc/bcc coerced through a string-array guard — meta is untyped Json); rows without it (incl. pre-upgrade pending rows) take the legacy `titleFor + message + View link` per-address path, byte-identical.
- Charts are substituted HERE, not at fire time, and the bodies get a tidy pass immediately after: `pruneEmptyChartSection` (HTML) drops the "LAST HOUR" heading when every chart token rendered away — which is the NORMAL case for an alert with no asset to chart, e.g. Polaris's own capacity — and `pruneEmptyTextLines` collapses the blank lines those removals leave in the text alternative. Both are pure and live in `utils/alertEmailTemplate.ts`; run them AFTER `substituteChartTokens`, since that pass is what decides a chart had no data.
- A web_push 410/404 prunes the dead `PushSubscription` (by endpoint).
- One alert's charts (and its loss-chart window) are built ONCE PER DRAIN PASS, not once per row — `RenderMemo` + `memoize`, keyed by `notificationId` + the exact chart-token set the body asks for (two notify actions on one rule can compose different bodies). It was introduced when composed emails fanned out one delivery row per recipient so each could carry its own acknowledge token; that fan-out is gone (business rule 25), but one alert still drains as several rows — a rule with more than one notify action, several channels, or a web-push target with a row per enrolled device — and each would otherwise re-run the same sample queries and rasterize the same graphs on a 15s tick. **Keep it per-pass** — a module-level cache would serve a stale snapshot to the escalation email whose whole point is showing the CURRENT hour. Promises are cached, not results, so rows in one concurrency chunk share a build. Pinned by `tests/unit/alertChartRenderMemo.test.ts`.
- Bounded concurrency on sends; one summary audit Event per non-empty drain (no per-delivery Event spam).

**When changing this:** scale-check at 2000 assets — the batch (`BATCH_SIZE`) + concurrency cap keep a delivery spike from stampeding SMTP/webhook endpoints. Never row-scan the full table; always filter `status=pending, attempts<MAX`.

## services/notificationEscalationService.ts

**What it owns:** The escalation sweep — running each rule's escalation TIERS OF ACTIONS (v2: notify / api_call / script, via `automationActionService.executeActions` with `exec.escalation` set) while a notification stays unhandled, and the per-notification `escalationState` bookkeeping. Legacy email tiers normalize to single-notify-action tiers (`normalizeEscalationToV2`) and produce byte-identical emails (parity-tested in notificationEscalationV2.test.ts). **Per-action + value-band aware:** the alert's current severity selects the active CHAINS via `escalationChainsForSeverity` (notificationTypes) — the rule/band LEVEL chain (state keys stay the bare numeric tier indexes pre-feature rows carry) plus one chain per effective action (state keys `a<i>:t<j>` via `escalationTierStateKey`), with per-chain `stopOn` (an acknowledged alert stops "acknowledge" chains while "clear" chains keep escalating); a rule whose only chain is per-action or band-level is still swept (`allEscalationsOf`); tier delays measure from `escalationState.bandSince ?? triggeredAt` so a freshly-entered band restarts its timers.

**Public API:** `runEscalationSweep(now?)` (job entry), `tierIsDue(tier, triggeredAt, tierState, now)` (pure, structural tier type — legacy and v2 tiers both fit; unit-tested), `repeatIsDue(repeat, startAt, state, now)` (pure, unit-tested).

**Cross-service deps:** `prisma` (rules + notifications + assets), `automationActionService.executeActions` (the entire send path — this service no longer builds delivery rows itself), `notificationTypes.normalizeRuleToV2`, `notificationRecipientService.scopeRegionTagsOf`, `notificationEngine.isSuppressedForNotifications`, `src/utils/notificationTemplate.ts` (buildTemplateContext/formatElapsed/notificationsPageUrl), `eventLogService.logEvent`.

**Used by:** `src/jobs/escalateNotifications.ts` (60s tick).

**Invariants:**
- "Unhandled" per the rule's `stopOn`: `acknowledge` stops on ack OR clear; `clear` ignores ack. Cleared always stops (the query excludes cleared rows).
- Renders from the fire-time `Notification.templateCtx` snapshot (+ live `{escalation.tier}`/`{escalation.elapsed}`); pre-feature notifications fall back to a minimal context from the row.
- **Escalation notify composition is a PER-FIELD merge** (tier subject ?? rule subject, tier body ?? rule body — implemented in automationActionService.composeForNotify), always composed, `[ESCALATION n]` prefix only when neither level set a subject. cc/bcc come from the tier action only. Don't "simplify" to whole-object precedence — that breaks subject-only tier overrides.
- A tier counts as SENT (state bump) only when `executeActions` reports ≥1 executed action — dead channels / empty recipients retry next sweep.
- **This function drives TWO kinds of follow-up.** Besides escalation tiers it runs the REPEAT pass (`NotificationRule.repeat`) — re-sending an alert's own notify actions while it stays unhandled. Four invariants there:
  - **Nothing may early-`continue` between the two passes.** The loop checks suppression FIRST and then runs the chain loop and the repeat pass independently. It used to `continue` on `chains.length === 0` before the suppression check, which a repeat-only automation (no chains at all) hits — that single early return silently disables the whole feature.
  - **Repeats use `repeatIsDue`, never `tierIsDue`.** The latter resolves `tier.maxRepeats ?? DEFAULT_MAX_REPEATS`, so a synthetic tier would stop after 5 — the exact cap this feature was asked NOT to have. `stopAfterHours` is the only bound, and it is optional.
  - **Only `REPEATABLE_ACTION_TYPES` (notify) re-run.** Unbounded re-execution of a ticket-creating `api_call` or a registry `script` is a different order of blast radius from an extra email. `validateRuleV2` refuses a repeat on an automation with no notify action anywhere.
  - **The due-cutoff must include repeat intervals AND guard the empty case.** `Math.min()` of nothing is `Infinity`, and `new Date(now - Infinity)` is an Invalid Date that makes the `triggeredAt` filter useless — reachable the moment a repeat-only rule is the only rule.
- **Quiet time (business rule 44) is a HOLD, not a skip.** `repeat.quiet` is a list of recurring windows (`utils/quietTime.ts`, on the Maintenance scheduler's `scheduleShapeSchema` / `currentWindow` — server-local wall clock); `isQuietNow` is resolved ONCE PER RULE per sweep (`quietRules`), never per notification. A due reminder inside a window leaves `tiers.repeat.lastSentAt` untouched — that is the whole mechanism, so the reminder stays due and goes out on the first tick after the window — and stamps `escalationState.quietHeldSince` / `quietHeldCount`. Four things that break it if changed: the sweep must NOT return early on `tierRuns === 0 && repeatRuns === 0` (a hold is a state update with no execution, and the early return silently discards the stamp the post-quiet reminder is built from); the hold is cleared where `tiers.repeat` is bumped and nowhere else (`executed === 0` retries and must still report the silence); the paused Event (`notification.reminders_paused`) is written ONCE per hold, on the stamping sweep, because an 8-hour window ticks 480 times; and quiet governs the REPEAT pass only — escalation tiers run through a window untouched, deliberately.
- **The post-quiet reminder is a different email.** `{repeat.quiet}` (body + push, via `followUpLine`) and the ` · ACTIVE <elapsed>` half of `[REMINDER n · ACTIVE 9h 12m]` (automationActionService.composeForNotify, only when no operator subject template) ride ONLY the reminder that ends a hold. `exec.repeat` therefore carries `{attempt, elapsed?, quietResumed?}`, and the same object reaches `NotificationDelivery.meta.repeat`. The standing `Active for` facts row is SEPARATE — it is `{repeat.elapsed}` in the default template and rides every reminder.
- A repeat and a due escalation tier in the SAME sweep both send. Deliberate: skipping the reminder would drift its clock and make "every 15 minutes" a lie. The wizard warns about the pairing at authoring time instead.
- A repeat is labelled `[REMINDER n]` through the NORMAL-fire composition path (the action's composition wholesale, falling back to the rule's), not escalation's per-field tier→rule merge — a reminder is a re-send of the initial email, not a tier override. `meta.repeat` is a key separate from `meta.escalation` so nothing reading delivery history confuses the two, and the prefix applies only when no subject template was set.
- `notification.repeated` is its OWN audit action. Sharing `notification.escalated` would inflate every "how much did we escalate?" query and make a reminder indistinguishable from an escalation.
- Repeats: only when `repeatEveryMin` is set, gated by `maxRepeats` (default 5) — a run-once tier never re-fires.
- Scales with the active-unhandled notification count, not fleet size; per-tier recipient resolution rides the recipient service's 30s user-index TTL (the old per-sweep cache was dropped with the executeActions cutover — escalation volume is small).

**When changing this:** a malformed `repeat.quiet` must keep degrading to "no quiet time" rather than "never repeats" — `notificationTypes.normalizeRuleToV2` re-parses with `quiet` stripped, and dropping that retry turns "pause overnight" into "never remind anyone again" with nothing reporting it. `repeat` must stay threaded into `notificationEngine.ruleWantsContext` — it gates the `templateCtx` snapshot, and without it a repeat-only automation snapshots nothing and every reminder silently loses `{value}` / `{threshold}` / `{trigger.summary}` / every `{asset.*}` token, i.e. the reminder stops looking like the email it is reminding you about. `public/js/automations.js _ruleToInput` must resend `repeat` for the same reason it resends the bands: the list row's enable toggle PUTs the whole record and `jsonOrClear` maps an omitted nullable Json to `Prisma.DbNull`, so an unlisted field is deleted by flipping the switch (pinned in automationsRuleToInput.test.ts). Also: state keys in `escalationState.tiers` are tier INDEXES — reordering a rule's tiers re-keys them (an already-sent tier position can re-fire); keep that acceptable or key by content hash. Tier-action reference validation lives in `notificationRuleService.assertActionRefs` (unified with top-level actions).

## services/pushSubscriptionService.ts

**What it owns:** The write path for the `PushSubscription` table — per-user Web Push subscriptions stored by the `/push-subscriptions` routes.

**Public API:** `savePushSubscription({userId, endpoint, p256dh, auth, userAgent, surface?, oldEndpoint?})` (upsert by endpoint; re-subscribe re-owns an endpoint that moved to a different user on a shared machine and refreshes the keys), `deletePushSubscription(userId, endpoint)` (owner-scoped deleteMany).

**Cross-service deps:** `prisma` only.

**Used by:** `src/api/routes/pushSubscriptions.ts` (POST/DELETE). Readers of the table live elsewhere: `notificationRecipientService` fans deliveries out to a user's endpoints (and snapshots `surface` into the delivery `meta`), and the web_push sender prunes rows when an endpoint answers 410/404.

**Invariants:**
- Delete is scoped to the owning user — one user can never unsubscribe another's endpoint.
- **`oldEndpoint` lookup AND delete are both scoped to the caller's `userId`.** It's caller-supplied (from the service worker's `pushsubscriptionchange`), so an unscoped query would let a guessed endpoint read another user's `surface` or delete their subscription. Covered by an explicit integration test in `tests/integration/pwaAndPushSurface.test.ts`.
- Upsert re-owns on endpoint collision by design (shared-machine re-subscribe); don't "fix" it into a 409.
- `surface` defaults to `"desktop"` only on a genuine create with nothing to inherit. A rotation mints a NEW endpoint, so there is no row to inherit from — that's exactly why `oldEndpoint` exists, and why dropping it would silently demote mobile subscriptions to desktop deep links.
- The upsert must stay idempotent: `push.js`'s `reconcileSubscription` re-posts the current subscription on EVERY page load as the primary repair for rotated endpoints.

**When changing this:** the endpoint is the business key (`@unique`); anything that changes the stored key fields must stay compatible with what the web_push sender reads at delivery time. `surface` is consumed by `notificationDeliveryService` via `pushDeepLinkUrl` — adding a surface value means adding a path to `PUSH_DEEP_LINK_PATHS` in `src/utils/notificationTemplate.ts` and a route that serves it.

## services/notificationChannelService.ts

**What it owns:** CRUD + secret handling for the `NotificationChannel` registry (Notifications → Delivery tab) — the operator-managed list of outbound delivery integrations.

**Public API:** `listChannels`/`listChannelsForBuilder`/`getChannel`/`getChannelRaw` (secrets, for senders)/`createChannel`/`updateChannel`/`deleteChannel`/`generateWebPushKeys`/`getWebPushChannel`, `MASK`.

**Cross-service deps:** `prisma` (notification_channels), `notificationTypes.CHANNEL_TYPE_META` (per-type field defs incl. which are secret) + `CHANNEL_TRANSPORT`, `notificationChannels/webPushChannel.generateVapidKeys`.

**Used by:** `src/api/routes/notificationChannels.ts` (CRUD + test + generate), `src/api/routes/pushSubscriptions.ts` (`/key` via `getWebPushChannel`), the rule builder (channel picker via `listChannels`), `notificationDeliveryService` (reads channel config at send time via a direct prisma lookup).

**Invariants:**
- Secrets (per the type's `secret:true` field defs — SMTP password, M365 client secret, Pushbullet token, Slack/Teams webhook URL, VAPID private key) are masked on read and preserved on write when the client echoes the mask / sends blank.
- The API never returns an unmasked secret; the web_push private key is never returned at all (only `privateKeySet`).
- `type` is immutable after create; `web_push` is a singleton (create rejects a second one).
- Destination secrets live ONLY on the channel — delivery rows reference the channel by id, never copy its secrets.

**When changing this:** add a new channel type by extending `CHANNEL_TYPES` + `CHANNEL_TYPE_META` (+ `CHANNEL_TRANSPORT`) in `notificationTypes`, a sender under `notificationChannels/`, and a dispatch arm in `notificationDeliveryService`. Mark secret fields `secret:true` so masking covers them.
