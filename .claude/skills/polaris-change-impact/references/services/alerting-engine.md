# Services — automations engine, rules, down detection, packet loss

## services/notificationTypes.ts

**Poll-counted holds (business rule 19):** `forPolls` on every continuous trigger and `sustainPolls` on the reset are the AUTHORITY where set — the engine counts readings — while `forDurationSec` / `sustainSec` stay written as the wall-clock mirror. The pure decision functions live here beside the tier ladder: `leadingRun` (series family), `advanceRun` (current-state family, including the "a repeat of the same poll is not a reading" rule), `sustainedSeverityByRun`, and the `triggerHoldPolls` / `resetSustainPolls` accessors that define "a count wins where present". `resolveTierLadder` inherits the trigger's count into every band that states no duration of its own — a band that states seconds stays wall-clock, deliberately.

**What it owns:** The Automations vocabulary — the discriminated `trigger` Zod union (asset_metric | asset_state | host_metric | event | change | **composite** — a nested AND/OR tree of metric/state leaves, `kind` asset|host, ≤3 deep / 2–10 leaves, and/or only, caps in `validateCompositeTrigger`; a 1-leaf composite collapses to the legacy single trigger via `collapseCompositeTrigger` in the input transforms), the asset `scope` schema, the **rule-shape-v2 layer** (`resetSchema` with hysteresis `clearThreshold` + clear-sustain `sustainSec` + condition-mode reset trees; the `actionSchema` union notify | api_call | script — notify carries `recipientDeviceRegion` alongside `recipientScopeRegion`; escalation v2 tiers-of-actions; **`escalatableActionSchema`** = the three action schemas + an optional per-action `escalation` chain, used ONLY at `ruleInputBaseSchema.actions` + `severityBandSchema.actions` so chains can't nest inside tiers/resolvedActions), `ruleInputSchema` (accepts v2 AND legacy bodies via transform + superRefine cross-validation) / `previewInputSchema` (partial drafts), the pure legacy↔v2 converters (`normalizeRuleToV2`, `normalizeReset`, `targetsToNotifyActions`/`actionsToTargets`, `legacyMirrorOfV2`, `normalizeEscalationToV2`), the **canonical action walk + chain selection** (`allRuleActionRefs` — every gate/detail consumer collects through it; `ruleHasAnyEscalation`; `escalationChainsForSeverity` + `escalationTierStateKey` — the level chain keeps bare numeric state keys, per-action chains key `a<i>:t<j>`), the **follow-up resolvers** (business rule 56: `bandFollowUpSchema` on each band + `effectiveAckNoteForSeverity` for the note; `repeat` on the escalatable NOTIFY schema + `repeatForAction` / `repeatingActionsForSeverity` / `repeatStateKey` / `allRepeatsOf` for the reminder; `parseSeverityBands`), the metric/field/comparator/aggregation/change-type catalogs, the **dimension-space pair** (`dimensionSpaceOf` — a trigger's dimension-filter key set, or null for a whole-device one, which is what business rule 32(b)'s reset lookup tests; `dimensionNounOf` — the same map read for a LABEL, "Interface" / "Sensor" / "IPsec tunnel", which the engine puts on the alert email's component row), and `buildSchemaCatalog()`.

**Public API:** `triggerSchema`, `scopeSchema`, `ruleInputSchema`, `previewInputSchema`, `resetSchema`, `actionSchema` (+ `notifyActionSchema`/`apiCallActionSchema`/`scriptActionSchema`), `escalatableActionSchema` (+ per-type escalatable variants, `EscalatableAction`), `allRuleActionRefs`/`ruleHasAnyEscalation`/`escalationChainsForSeverity`/`escalationTierStateKey` (+ `EscalationChain`, `RuleActionCarrier`), `bandFollowUpSchema`/`effectiveAckNoteForSeverity`/`repeatForAction`/`repeatingActionsForSeverity`/`repeatStateKey`/`allRepeatsOf`/`parseSeverityBands` (+ `BandFollowUp`), `escalationV2Schema`/`escalationTierV2Schema`, `emailCompositionSchema`, legacy `escalationSchema`/`escalationTierSchema`, the converters above, `buildSchemaCatalog`, `Trigger`/`RuleScope`/`RuleInput`/`PreviewRuleInput`/`ResetConfig`/`AutomationAction`/`EscalationV2Config`/… types, `CHANGE_TYPE_ACTIONS`, `ASSET_SCOPED_TRIGGER_TYPES` + `isAssetScopedTrigger` (composite is scoped iff kind="asset"; `event` is deliberately NOT on that list even though it may carry a device filter — see `scopeIsUnconstrained` below), `scopeIsUnconstrained`, the composite helpers (`triggerConditionGroupSchema`, `compositeLeafSchema`, `isTriggerLeaf`, `collectTriggerLeaves`, `triggerConditionStats`, `collapseCompositeTrigger`, `validateCompositeTrigger`, `TRIGGER_GROUP_OPS`), the `*_METRICS`/`*_FIELDS`/`CHANGE_TYPES`/`RESET_MODES`/`TRIGGER_TYPES_WITH_RESET_CONDITIONS` + `triggerTypeAllowsResetCondition`/`METRIC_DIMENSIONS`/`STATE_FIELD_DIMENSIONS`/`DIMENSION_NOUNS`/`API_CALL_METHODS`/`SCRIPT_RUN_TARGETS` constants.

**Used by:** `notificationRules.ts` (validation + schema endpoint), `notificationEngine.ts`, `notificationRuleService.ts`, `notificationEscalationService.ts`, `notificationRecipientService.ts`, `jobs/migrateAutomationRuleShape.ts`, the builder UI (via `/automations/schema`), and **`public/js/automations-portability.js`** (automation export / import: it walks a rule body field by field, so every field in `ruleInputBaseSchema` needs a strip decision there).

**Invariants:**
- Single source of truth — engine, routes, and frontend must read the vocabulary here, never hardcode it.
- `CHANGE_TYPE_ACTIONS` maps each change type to the exact audit Event action the persist* detectors emit AND the event-tail matches; both ends must agree.
- `buildSchemaCatalog().templateVariables` mirrors `TEMPLATE_VARIABLES` from `src/utils/notificationTemplate.ts` — the builder's insert-variable palette renders from it, never a hardcoded list.
- `buildSchemaCatalog().sensorClassUnits` mirrors `SENSOR_CLASS_UNITS` from `src/utils/hardwareSensors.ts` — hwSensorValue's metricMeta unit is the `"(sensor unit)"` placeholder, and the wizard resolves the real unit (°C/RPM/V/A/dBm) from the leaf's `sensorClass` dimension filter via this map (`leafUnit` in automations-wizard.js), the same map the sample classifier stamps into `AssetHardwareSensorSample.unit`.
- **Adding an `ASSET_STATE_FIELDS` entry is a FIVE-site lockstep, and every site past the first fails silently.** The enum here is what the Zod union validates, but a field missing from `FIELD_META` renders as a blank picker row in the wizard, and a field missing an arm in `notificationEngine.resolveAssetStateReadings` validates, saves, and then silently produces no readings forever — an automation that can never fire and never errors. The two beyond this file are just as quiet: **`notificationCadenceService.METRIC_STREAM`** (the field falls back to the probe cadence, so the wizard converts a `forPolls` hold at the 60s ICMP tick instead of the collector's own — see that service's own invariant), and **`alertChartService`** (`chartTokenForMetric` plus the `PORT_SCOPED_METRICS` / `SDWAN_SCOPED_METRICS` sets), which decides whether the alert email draws the device's graphs or the component's. A field reported per dimension also belongs in `FIELD_DIMENSIONS` (the builder's pickers) and `STATE_FIELD_DIMENSIONS` (the "one alert or all of them" note) below. `tests/unit/notificationChangeTypes.test.ts` pins the FIELD_META half. **Decide explicitly what a NULL value means** while you are there: `fortilinkStatus` (business rule 59) produces NO READING rather than a reading of null, because null means "not a FortiGate-managed device" and a null reading would make `!= up` true of every workstation in a fleet-wide scope. **And decide the reading anchor**: the Asset-column fields anchor on `lastMonitorAt`, which is right only when the monitor loop is what refreshes the column. A field with a writer of its own (`fortilinkStatus` ← the 60s controller sweep) must anchor on that writer's own timestamp, or a `forPolls` hold counts ticks during which nothing looked at the device. **Worked example with a loader of its own: `firmwareVsPrimary` (business rule 87)** — enum `current` / `older` / `newer`, resolved by ONE `loadPrimaryFirmwareImages()` findMany per evaluation and an in-memory `firmwareVsPrimary()` per asset (both in `firmwareRepositoryService`), NO READING for a device the Repository cannot place (the fortilinkStatus posture), anchored on `lastSystemInfoAt`, `METRIC_STREAM` = `systemInfo`, no chart token (the default), and `SCOPE_SELECT` gained `serialNumber` + `osVersion` for it; seeded as baseline set V9 (`FIRMWARE_DRIFT_RULES`). Pinned by `tests/unit/firmwareVsPrimary.test.ts` + the FIELD_META case in `notificationChangeTypes.test.ts`.
- **Adding a `HardwareSensorClass` is a four-site lockstep**, and the one that actually bites is the Zod enum: `sensorClass` in `notificationTypes.ts`'s dimensionFilter schema is CLOSED, so a class present in samples but missing there is unselectable in the wizard — the automation simply cannot be authored. The four: the `HardwareSensorClass` union + `SENSOR_CLASS_UNITS` (hardwareSensors.ts), that Zod enum, `DIM_PLACEHOLDER.sensorClass` (automations-wizard.js), and `_hwClassLabel` (assets.js, the System tab column). `sensorClassUnits` and the dimension-values picker follow automatically.
- **`FIELD_META` decides the builder's value box and operator select for an asset-STATE field**, and two of its optional keys exist because the defaults lie on a field whose values are not statuses: `placeholder` replaces the "e.g. up / down" hint, and `equalityOnly` withholds the ordered comparators (`compareValue` can only answer ==/!= about a string that is not a number, so `>=` on one builds a rule that reads false forever). `ifIpAddress` sets both. The wizard reads them in `tgStateValueControl` and the `enumState` operator test — a new key here is inert until that file honours it. A third key, `integralDimension`, names the dimension a reading of the field IS ABOUT rather than one that narrows a set of them. **Every field `STATE_FIELD_DIMENSIONS` reports per component now carries one** (2026-09-16): `ifOperStatus` / `ifAdminStatus` / `ifIpAddress` / `poeStatus` → `ifNamePattern`, `ipsecStatus` → `tunnelName`; the SD-WAN pair reach their health check through a filter row still. The builder keeps that dimension's picker on the condition row (`tgInlineDims`) and hides it from the filter-row lift (`tgLift`'s own supports predicate), so the operator says WHICH component the comparison names instead of reaching for a group filter row. **Adding a per-component state field means adding this key too** — it is the difference between a condition row that says what it is about and one that reads as a fleet-wide statement. It is authoring guidance only — the engine still evaluates an unfiltered leaf, as one reading per pinned port, which a composite then folds per device (`leafTruthByAsset`); that ANY fold is why an unnamed port makes `!= 0.0.0.0` true of every addressed device. **The two entries are integral for DIFFERENT reasons, and the difference is what to weigh when a third is proposed**: on `ifIpAddress` an unnamed dimension makes the comparison meaningless (see the ANY fold above), while on `ipsecStatus` an unnamed tunnel is perfectly coherent — it means every pinned tunnel, one alert each — and the dimension is integral because a tunnel's phase-1 name is not typeable from memory the way `wan1`/`port3` are, so leaving the picker to "+ Condition → Component name" is a control the operator has no reason to go looking for. That is why `ifOperStatus` / `ifAdminStatus` / `poeStatus` stay filter-row fields: per-pinned-port is both a legitimate rule AND a guessable name. Do NOT turn integrality into a required field — `ipsecStatus` with no tunnel is a rule that already exists in installs.
- **`METRIC_DIMENSIONS` / `FIELD_DIMENSIONS` / `DEVICE_FILTER_DIMENSIONS` are the three dimension vocabularies** (published as `metricDimensions` / `fieldDimensions` / `deviceFilterDimensions` on `/schema`; `triggerDimensionApplicable` is the one applicability rule, used by `notificationDimensionService`'s 400 gate). The first two are metric-/field-INTEGRAL dims (sensor class/name, mount, interface, tunnel …); the third — hostname / IP / MAC / manufacturer / model — names the DEVICE and applies to EVERY asset metric and state field (never host metrics), filtering the ASSET SET before any sample query via the engine's `applyDeviceFilters` → `deviceFilterMatch`. **IP and MAC have their own matchers** (`ipDimensionMatch`: CIDR / trailing-dot prefix / exact-or-octet-boundary-prefix, never bare substring — "10.1.1.5" is inside "110.1.1.55"; `macDimensionMatch`: separator-insensitive substring), both MIRRORED in `automations-wizard.js` (`awIpDimensionMatch`/`awMacDimensionMatch`, parity-tested in `automationTriggerFilters.test.ts`) because the builder's match cue selects with the client copy. Identifiers ride `triggerSignature` like every dimension, so same-metric rules with different device filters never carve each other out. The wizard authors ALL of the liftable dims (identifiers + ifNamePattern/tunnelName/mountPathPattern) as **filter rows** in the condition tree — `tgFilterCompile`/`tgFilterLift` — never as always-visible inline inputs — **with one exception, a field's `integralDimension`** (FIELD_META above), which stays on its own condition row and is hidden from the lift. Mind the two senses of "integral" here: METRIC_DIMENSIONS / FIELD_DIMENSIONS are the dimensions a READING is reported per, while `integralDimension` singles out the one a comparison is meaningless without. Either way the stored trigger only ever carries `dimensionFilter`.
- **`BOOLEAN_METRICS` / `isBooleanMetric` is the one test for a 0/1 metric** (`customStateValue`, backed by `AssetStateSample`, and `hwSensorAlarm`, backed by the existing `AssetHardwareSensorSample.alarmStatus` column — see business rule 24 for which to reach for). `BOOLEAN_METRIC_LABELS` names a metric's two states for the builder; `customStateValue` is deliberately absent from it because its labels are per-probe and come from `/schema.stateProbes`, which is better information than a metric-wide default. They live in ASSET_METRICS deliberately — the engine's threshold/debounce/sustain/reset machine already does the right thing on a 0/1 value compared with `==`, and a third trigger type would mean a second copy of hysteresis and per-dimension state. What they must NOT inherit is the numeric surfaces, and every one of those checks the set rather than testing metric names inline: `validateSeverityBands` rejects bands on one (a strictly-increasing threshold ladder over two values is meaningless — and it says so about the METRIC, since an operator who wrote `>= 1` needs to be told the metric is the problem, not the comparator), the wizard's `bandsApplicable` hides the multi-severity toggle, its `numeric` flag hides hysteresis, and the sentence factory's `severityLadderPhrase` ignores any bands riding along on one. `buildSchemaCatalog().booleanMetrics` is how the client learns the set.
- **A notify action is PLURAL, and `notifyChannelIds(action)` is the only reader of the pair.** `channelIds` carries every channel one action delivers through; `channelId` is the PRIMARY and the lossless single-channel mirror every pre-multi-channel reader still names a channel through, so it must always equal `channelIds[0]` — refused (not repaired) by `assertActionRefs`, because picking one of two disagreeing answers is how an alert quietly goes to the wrong destination. `actionsToTargets` expands one action to one `DeliveryTarget` per channel, which is what keeps `expandDeliveries` unaware that an action can be plural. **`notifyActionSchema` must stay a plain ZodObject** — it is a member of the `actionSchema` discriminated union AND is `.extend()`ed into the escalatable variant, and both refuse a `ZodEffects`, which is why its cross-field checks live in `assertActionRefs` rather than in a `superRefine`.
- **`respectUserPreference` must be carried by BOTH `notifyActionSchema` and `deliveryTargetSchema`** (business rule 39). `actionsToTargets` is the RUNTIME path, not just the legacy mirror: a field the action holds and the target drops validates, persists, renders in the wizard and changes nothing at all — the exact bug `recipientDeviceRegionLevels` already carries a warning comment about. The group gate that decides whether the flag does anything lives in `automationActionService.actionsCarryBothMethods`, not here.
- **`trigger.alertWhenDependencyDown` rides the down trigger like `missedPolls`** (business rule 78): optional on `assetStateTrigger`, refused by `validateMissedPolls` off a down-detection trigger and inside a multi-leaf composite, read ONLY through `ruleAlertsWhenDependencyDown(trigger)` (gated on `isDownDetectionTrigger`, so a key stranded on a retyped trigger can never fire about silenced devices), and NOT part of `triggerIdentityOf` (ticking it must not purge the rule's state rows). `buildSchemaCatalog().downDetection` carries `dependencyDownKey` / `dependencyDownLabel` / `dependencyDownHelp` so the wizard renders the control only against a server that accepts the key.
- **Every reader of stored rules goes through `normalizeRuleToV2`** — never read `clearBehavior`/`targets` directly; they're the derived mirror, not the source of truth. Every writer persists v2 AND the mirror (`legacyMirrorOfV2`).
- `ruleInputSchema` output is canonical v2 (`RuleInput`): v2 fields win over conflicting legacy fields; a legacy-only body converts losslessly.
- **A new field on `ruleInputBaseSchema` needs a decision in `stripForExport`** (`public/js/automations-portability.js`), or it is silently exported. Ask whether it names anything install-specific: if it does, drop it from the rule and record it as a named **dependency**; if not, carry it. The `automationPortability` round-trip test asserts every export still parses as `ruleInputSchema`, so a field that breaks the shape fails loudly — but a field that leaks a channel id or a user id passes quietly, which is why the decision is a checklist item and not just a test.
- api_call `url` is STATIC (no {token}s — SSRF-checkable at save); only `bodyTemplate`/`argsTemplate` interpolate. api_call headers are stored unmasked — the no-secrets warning lives in `apiCallMeta.help` + docs.
- Escalation INPUT stays the legacy email-tier shape until the escalation-v2 phase; `normalizeEscalationToV2` already converts both shapes for readers that want the v2 view.
- **Composite invariant:** 1 condition ⇒ legacy single trigger (per-dimension alerting + hysteresis-capable); ≥2 conditions ⇒ composite (per-asset alerting, ANY-dimension leaves, no clearThreshold). `collapseCompositeTrigger` in the input transforms enforces this for every author — never let a caller store a 1-leaf composite.
- **Reset mode `condition` is allowed on every trigger with a continuous condition**, not just composites (`TRIGGER_TYPES_WITH_RESET_CONDITIONS` + `triggerTypeAllowsResetCondition`; the composite-only refusal was lifted 2026-08, business rule 32). `event`/`change` are still refused — they fire on an instant and carry no reading for a tree to watch, which is also why `resetModesByTriggerType` gives them no `condition` entry. They get **`mode:"event"`** in its place (`TRIGGER_TYPES_WITH_RESET_EVENT` + `triggerTypeAllowsResetEvent`, deliberately the exact COMPLEMENT of the condition set — see business rule 32(e)): `reset.resetEvent = {actionPattern, resourceType?}` names the counterpart audit Event that clears the alert. Three things move in lockstep with it — `RESET_EVENT_SUGGESTIONS` (trigger pattern → recovery pattern, published on the catalog as `resetEventSuggestions` and prefilled by the wizard), `normalizeReset` (keeps a patternless event reset intact rather than rewriting it to `manual`, so `validateRuleV2` is what tells the caller a pattern is needed), and `legacyMirrorOfV2` (mirrors it to `clearBehavior:"auto"` with a null `clearAfterSec`, like `condition`). Kind coherence is enforced for ALL trigger types now (a `host_metric` trigger takes host leaves, anything else device leaves): a mismatched leaf resolves against assets that can never report it, so the tree reads permanently false and the alert can only ever be cleared by hand. Keep the catalog and the validator in step — the wizard renders its non-auto radios in `resetModesByTriggerType` ORDER, which is why `condition` leads. **A pair whose two halves share one action cannot be added** — the reset matches actionPattern + resourceType and never `detailsMatch`, so the reset would fire on the trigger's own Event and clear the alert that raised it. Split the writer's verb first (`platform.lifecycle_changed` / `.lifecycle_recovered`, `capacity.severity_changed` / `.severity_recovered`), write the recovery verb ONLY on a landing at the healthy state, and keep both halves on the same subject (same `resourceType`, same absence-or-presence of `resourceName`) or `eventSubjectLabel()` resolves them differently and the clear silently misses. Adding an entry here reaches new installs only: the seed job's V4 marker is stamped everywhere, so an existing install needs its own one-shot (V8 is the worked example).
- **`STATE_FIELD_DIMENSIONS` / `DIMENSION_NOUNS` are derived from the engine's resolvers, not from the form.** `METRIC_DIMENSIONS` doubles as the builder's dimensionFilter field list; the state-side map has no form behind it (a state leaf renders no dimension inputs) and exists so a surface can ask "does this trigger raise one alert per interface?" — which is what the reset step's "clears one alert or all of them" note reads. An asset-state field whose engine resolver starts reporting per dimension must be added here or that note goes quietly wrong.

- **The path* metrics (agent-run path checks, business rule 85)** — `pathLatencyMs`, `pathHttpStatus`, `pathOk` (BOOLEAN_METRICS, labels Reachable/Unreachable), `pathFailurePct` (WINDOWED_RATIO_METRICS; window via `probeLossWindowSec`), `pathHopCount`, `pathTlsDaysLeft`. The asset is the AGENT HOST; the dimension is `checkId` (exact id, `pathCheckFilterMatches`, DIMENSION_NOUNS "path check"). Every lockstep site: METRIC_META + METRIC_DIMENSIONS here, the engine resolvers, `notificationCadenceService.METRIC_STREAM` (`pathCheck`), `alertChartService.PATH_CHECK_SCOPED_METRICS` (no device charts), `notificationDimensionService.DIMENSION_SOURCES.checkId`, `getMetricSeverityTiers`' checkId predicate, `sampleAlertDevice.sampleDimensionFor`, `triggerSummary`'s "of check history". The change type `path_check_path_changed` ↔ `path_check.path_changed` is the `asset.*.changed` family (written unconditionally by the ingest). The builder's check names come from `/automations/schema`'s `pathChecks` (merged in the route, like `stateProbes`).

**When changing this:** Adding a metric/field → also wire its resolver in `notificationEngine` (else it parses but never reads data). Adding a change type → also emit the matching Event from the relevant persist* function. Adding a template token → add it to `TEMPLATE_VARIABLES` + `buildTemplateContext` in the util (and, if asset-sourced, the engine's `ASSET_DETAIL_SELECT`). Adding an action type → extend `actionSchema` + `assertActionRefs` (notificationRuleService) + the execution fan-out + `actionTypes` in the catalog. **Adding a scope dimension → THREE matchers must move in lockstep:** the engine's SQL `scopeWhere` (+ `loadScopeAssets` post-filter for non-SQL-expressible dims like subnetCidrs and `condition` trees, + SCOPE_SELECT if a new column is read — condition evaluation reads manufacturer/model/os/hostname/ipAddress/status), the in-memory `scopeMatchesAsset` twin in notificationRuleService (asset-details tab), and the wizard's Step-2 builder. The condition tree itself evaluates through ONE shared pure function (`evaluateScopeCondition` in notificationTypes) so the tree semantics can't drift; adding a condition FIELD means: SCOPE_FIELD_OPS + matchScopeRule + `SCOPE_FIELD_META` (the catalog's scopeCondition.fields — ONE catalog serves both vocabularies) + (if a new asset column) both selects + a `case` in each of the FOUR client `valueOptions` switches if it publishes an `optionsFrom` (see UI-CANON → Nested condition tree) + a rung on `SCOPE_RANK`/`SCOPE_RANK_LADDER` and a `case` in `conditionRuleRank` if the field names WHICH devices a rule is about (rule 18). **A CIDR-valued field is a pair, not a field**: `subnet` and `ipBlock` (the IPAM block, stored as the block's own CIDR so the pure evaluator needs no table) share one Zod refine via `CIDR_VALUED_FIELDS`, one `matchScopeRule` branch and one client `validate()` test — adding a third to one half and not the others is how a value the builder accepts becomes a 400 on save. **A field backed by a RELATION is its own decision, not a wider select.** `interfaceName` reads `AssetInterface`, which at 2000 devices is an order of magnitude past the fleet, and `loadScopeAssets` re-resolves every rule's scope on the 60s tick — so it is prefetched in SQL by `scopeInterfaceIndex.decorateInterfaceLeafHits`, which stamps a per-leaf verdict map onto each row (`asset.interfaceLeafHits`) that `matchScopeRule` reads INSTEAD of the relation. Consequences to preserve: every fleet-scale loader must decorate before it evaluates (`loadScopeAssets`, `downDetectionService`'s index build, `contactService`'s condition preview) AND so must anything comparing a PEER rule's scope against those rows (the carve-out passes — an undecorated peer leaf reads as "no interfaces", which silently either duplicates an alert or silences one); an absent leaf key means UNKNOWN, so the evaluator falls back to `asset.interfaces` rather than answering false; and single-asset paths join `interfaces` on the one row instead, which beats a second round trip. A relation-backed field also has no business on `scopeRank` — an interface is a component of a device, not a statement of which devices a rule is about. `scopeRegionTagsOf` (recipient service) also mines positive region: tag rules from trees — keep it in mind when changing tag-rule semantics.

## services/notificationService.ts

**What it owns:** Triggered-notification read + lifecycle (View tab + asset tab): region-scoped listing, batch acknowledge/clear, the per-asset bundle, region-prefix stripping, and the **suppression sweep** (`clearSuppressedAlerts` — retires every active alert whose asset is in a maintenance window or dependency-suppressed, business rule 16).

**Public API:** `listNotifications`, `acknowledgeNotifications`, `clearNotifications`, `clearSuppressedAlerts(assetIds?)`, `getAssetNotifications`, `activeAlertSummaryByAsset(assetIds)`, `stripRegionPrefix`, `REGION_TAG_PREFIX`, plus the three pure helpers behind the acknowledge-note policy: `ackNotePolicyOf(row)` (resolves the joined rule's note policy for the severity THIS alert is sitting at — business rule 56), `withAckPolicy(row)` (runs that and flattens the answer onto a list row as a plain boolean, dropping the join) and `ackNoteProblem(needyCount, batchSize, note)` (the refusal message, or null).

**Cross-service deps:** `prisma`, `eventLogService` (`logEvent` + `logEventsBatch`), `notificationRuleService.findRulesMatchingAsset`.

**Used by:** `src/api/routes/notifications.ts` (list/ack/clear), `src/api/routes/assets.ts` (`getAssetNotifications` at `/assets/:id/notifications`, and `activeAlertSummaryByAsset` in `enrichAssetList` for the list's `activeAlert` field), `src/jobs/evaluateNotificationRules.ts` + `src/services/maintenanceScheduleService.ts` (`clearSuppressedAlerts` — the tick-wide sweep and the maintenance entering edge).

**Invariants:**
- Region scope: empty viewer tags = unrestricted (the route passes `[]` for an admin-equivalent caller — business rule 25); else show rows whose snapshotted `regionTags` intersect the viewer's tags PLUS unscoped (empty regionTags) rows.
- Acknowledge/clear are batch (`updateMany`, no per-row await) and always write an audit Event.
- **`activeAlertSummaryByAsset` is ONE query per PAGE**, never a count per row — the assets list ships up to 10 000 rows on the export path. It is deliberately unfiltered by automation relevance (unlike the NOC widgets' pills it answers "is anything wrong with this device") and unscoped by region (the assets list is, so scoping only the indicator would mark a row quiet the operator can open and find noisy). It ranks through `utils/alertSeverity.higherAlertSeverity`; the browser mirror that colours the same indicator is `_alertSevRank` / `assetAlertStrobeColor` in `public/js/assets.js`, pinned to it by `tests/unit/assetAlertIndicator.test.ts`. **`searchService.withAlertSummaries` is the second caller** — it stamps `SearchHit.alert` on the asset and site hits of every search, one query for the whole result set rather than one per hit (search runs a keystroke at a time), which is the property to preserve if that helper is ever moved. **There is a THIRD copy of that rank map** — `sevRank` / `sevColor` in `public/js/mobile/alerts.js`, behind the phone's Assets-list alert flag and the per-asset alerts sheet, pinned by `tests/unit/mobileAssetAlerts.test.ts`. The mobile SPA loads none of `assets.js`, so it cannot import the desktop mirror; any change to the severity vocabulary is a three-file change (server, desktop, phone) plus the `--md-sev-*` tokens in `public/css/mobile.css`, and a device that flags amber on one surface and red on another is what the two tests exist to catch.
- **`acknowledgeNotifications` is where the acknowledge-note policy is ENFORCED**, and it has to stay here: it is the single write path behind every acknowledge surface (Alerts tab, mobile list, and the `/alert-ack.html` page an emailed or pushed Acknowledge button opens), each of which asks for the note in its own markup, so every required field is a courtesy and this refusal is the control. A note-less batch containing any alert whose rule demands one throws 400 — refused WHOLE, because the route takes one shared note for every id and a partial success would leave the alerts that mattered open under a success toast. It runs only when no note was given, so the common path pays nothing.
- **The policy is per SEVERITY, not per rule** (business rule 56): a severity band may carry its own `followUp.requireAckNote`, so the answer is `ackNotePolicyOf(row)` — `effectiveAckNoteForSeverity` against the notification's own `severity` — and a band that states nothing inherits the rule's flag. This is why the enforcement query FETCHES its candidates rather than counting them: it used to be one indexed `count` with `rule: { requireAckNote: true }` in the WHERE clause, and no SQL predicate on the rule row can answer a question about a JSON band. Bounded by the ids the operator selected, reading three small columns, so it stays a per-selection cost and never a fleet-scale one.
- Both list surfaces join that flag through `ACK_POLICY_INCLUDE` (which now also selects the rule's own `severity` + `severityBands`, since the resolver needs them) and flatten it with `withAckPolicy` — a rule-less row (test fire, or an automation since deleted: `Notification.ruleId` is SetNull) reads false, since there is no policy left to enforce.
- **The note has exactly ONE reader**, and both list surfaces keep it reachable by returning whole rows: `acknowledgeNote` rides `listNotifications` / `getAssetNotifications` only because neither narrows with a `select` and `withAckPolicy` spreads the rest through — adding a `select` to either would drop it silently. The reader is the **asset-details Alerts tab's Acknowledge column** (`_loadAssetNotificationsTab` in `public/js/assets.js`). The dashboard Active Alerts widget and the mobile alerts list render `acknowledgedBy` only, so an operator answering a `requireAckNote` prompt is writing for that one column; a second surface that wants the note needs no backend change.

- **`clearSuppressedAlerts` skips `dependencyDown = true` rows, in the QUERY** (business rule 78): an alert raised FOR a dependency-suppressed device by a down automation that opted in is the one alert that is supposed to be live on a suppressed asset, and retiring it here would re-raise it on the next engine tick, forever. The engine owns its end (recovery, or the flavour handoff when the upstream comes back). Plain alerts on such a rule are still retired here and re-raised as dependency-down by the engine.
- **`clearSuppressedAlerts` is a HANDOFF, not a recovery** (business rule 16): soft-clear + release the `NotificationRuleState` row, **no reset actions** — nothing recovered, and mailing "resolved" about a device nobody is polling would be a lie. It lives here rather than in `notificationEngine` because it sweeps **Notification rows**: event and change alerts are created by the event tail's `createMany` with no state row at all, so a state-machine-side clear would miss them. Maintenance outranks dependency when an asset is both. Callers pass `assetIds` only for the maintenance entering edge; unscoped is the 60s safety net and the only path that catches dependency suppression.

**When changing this:** Keep the region-scope rule in sync with `regionScopeService` (the viewer side) and the engine's `regionSnapshot` (the write side). If you add another acknowledge surface, call this function — do not write `acknowledged` directly, or that surface silently opts out of the note policy and the audit Event.

**What it owns:** Notification RULE logic — scope matching, the "rules matching this asset" lookup, rule CRUD, and the change-type subscription cache that gates the persist* change-detectors.

**Invariants:**
- `scopeMatchesAsset`: AND across provided dimensions, OR within each list; `allAssets` short-circuits true; no dimensions + not allAssets ⇒ matches nothing.

It answers true for `{allAssets:true}`, for a bare `{}` and for an empty condition tree. The distinction matters because `scopeMatchesAsset({})` is `false`: `{}` from the builder means "selects nothing", but `{}` on any event automation saved before 2026-09 means "any device" (the wizard discarded the Devices step for that trigger type and posted `{}`). Filtering the event tail on `scopeMatchesAsset` alone would have silenced every one of them, seeded rows included.
- **Every rule that leaves this service goes out through `withV2`** — `listRules`/`getRule` always did, and `findRulesMatchingAsset` joined them in 2026-08 when the asset-details Alerts tab started opening those rows in the edit wizard: a pre-v2 row handed to the builder with NULL `reset`/`actions` opens with its actions missing and SAVES them away. Any new read path that a UI can edit from must do the same.
- Every rule write calls `bumpChangeSubscriptions()` so the persist* detectors pick up new/removed change subscriptions.
- **No path may strand an active alert under a rule the engine no longer evaluates.** `updateRule` clears active alerts + deletes state rows on trigger-identity change (`system:rule-edited`) AND on enabled→disabled (`system:rule-disabled`); `deleteRule` clears active alerts (`system:rule-deleted`) BEFORE the delete (the cascade drops the state rows and `ruleId` goes NULL, after which nothing can auto-clear). Soft-clear only — history survives.

- `getMetricSeverityTiers` must derive thresholds through the SAME primitives the engine evaluates — `resolveTierLadder` for the band ladder, `hwSensorFilterMatches` for dimension selection, `deviceFilterMatch` for the device-identifier skip (a rule whose hostname/IP/MAC/manufacturer/model filter excludes the charted asset must not shade its chart with thresholds that can't fire there). It feeds a CHART that claims to show what an automation would do, so a private re-derivation here would draw a line that disagrees with the alerts. It deliberately skips the rule-18 carve-out: precedence decides which automation notifies, while the reading crosses the same value either way.

**When changing this:** The subscription cache has a 60s TTL fallback; a write must bump it so change emission turns on/off promptly. Any new way to take a rule out of evaluation (new enabled-like flag, archive state) needs the same active-alert cleanup. A new numeric asset metric worth shading on a chart needs nothing here (the ladder is metric-agnostic) — but a new DIMENSION filter does: add its predicate beside `hwSensorFilterMatches` in notificationTypes, use it in BOTH the engine's resolver and `getMetricSeverityTiers`, and thread the identifying fields through the `/metric-thresholds` query.

**Also written by the automations code editor** (`openCodeModal` in `public/js/automations-portability.js`, reached from the wizard's Summary step and the list row menu). It PUTs a hand-edited JSON body, which makes `updateRule`'s full-replace semantics operator-visible for the first time: `normalizeRuleInputCore` maps an ABSENT nullable JSON field to `null` and `jsonOrClear` turns that into `Prisma.DbNull`, so deleting a key in the editor CLEARS that column — and `enabled` / `severity` / `reset` carry Zod defaults, so deleting `enabled` takes a disabled automation LIVE. Three things keep that honest and must stay: the editor renders the COMPLETE body (routed through `_ruleToInput`, already pinned by `automationsRuleToInput.test.ts`), it strips the legacy mirror `targets` / `clearBehavior` / `clearAfterSec` from what it shows (leaving `targets` lets a deleted `actions` be silently rebuilt from it by `normalizeRuleInputCore`, losing per-action escalation and every script / api_call action), and it confirms a diff of the destructive fields before saving. Do not add a merge-onto-current: that would make a deliberate deletion do nothing.

## services/notificationEngine.ts

**What it owns:** The rule evaluator. Threshold/state path (per-metric sample resolvers + the NotificationRuleState machine with forDuration/cooldown + v2 `reset` semantics: auto with hysteresis `clearThreshold` + clear-sustain `sustainSec` via `NotificationRuleState.recoveredSince`, timed via `afterSec` sweep, manual re-arm), **poll-counted holds** (`forPolls` / `reset.sustainPolls` — the engine counts consecutive qualifying READINGS: `Reading.series` + `leadingRun` for a series source, `Reading.readingAt` + `advanceRun` against `metRun`/`clearRun` for a current-state one; `lookbackMsFor` widens the sample fetch so N readings are actually visible), the event-tail path (cursor over Event rows matching event/change rules, each rule's device filter applied per event — business rule 46), all fire-time template rendering (in-app message + composed email via `src/utils/notificationTemplate.ts`), and `previewRule` (dry-run; scope-only mode + hysteresis `wouldClear`/`inDeadBand` per match; `matches` is capped at 200 rows, so the counts the wizard prints are computed over ALL readings and returned separately — `meetsCount`, plus `coveredEvaluated`/`coveredAssets` when precedence carved anything out — and `applyCarveOutToMatches` sorts the carved-out rows to the BACK of `matches` ahead of that cap, because the Devices step lists what the draft WILL alert on and a fleet already covered by per-type automations otherwise fills the whole window with rows it can never fire about). Also owns **precedence carve-out** (a more-specific same-`triggerSignature` rule shadows the assets it covers out of lower-`scopeRank` rules — drop reading, clear active alert `notification.superseded`, reset pending) and **severity bands** (value-driven severity escalation — `tierLadderFor` + the pure `updateTierMetSince`/`sustainedSeverity` resolve the tier under PER-TIER sustained durations against `NotificationRuleState.bandMetSince`, `applyBandTransition` re-notifies per `bandNotify` policy on increase/decrease + eases a dead-banded alert to base severity, `fireResolved` on drop below tier 0, `firingSeverity` tracks the live band), plus the **vanished-state sweep** (`clearVanishedStates` — clears firing/pending rows for assets/dimensions the rule can no longer see; both evaluators).

**Poll-counted invariants (business rule 19).** (a) `Reading.series` is the RAW readings newest-first and only a series source has one — **except under a COUNT window (business rule 66), where it is the series of DISJOINT POLL-GROUP AGGREGATES** and a hold therefore counts GROUPS rather than raw samples — the groups step by their own size, never by one, so consecutive entries share no samples and a run of three is three independent measurements; `reduceReadings` and `resolveHostMetricReading` are the two places that swap it, and everything downstream (`leadingRun`, `tierRuns`, the fire/clear path) is deliberately unaware the numbers were derived. A count window with too few readings yields NO reading at all rather than a partial-window aggregate, so the asset is skipped exactly as an unreporting one is. `lookbackMsFor` is the other half: a count window sizes its fetch from the wall-clock MIRRORS of both counts, doubled, and an API-authored rule carrying no mirror gets the full 6-hour cap — change one without the other and a hold can never be satisfied because the query excluded the readings it needed. RESPONSE TIME layers business rule 67 on top through `reduceReadings`' `prepare` hook: it is the only metric whose misses are FILLED (with the `timeoutMs` the probe recorded) and whose window is TRUNCATED (at the newest `assetDown` row), so its case selects two extra columns the others do not and runs `prepareResponseTimeWindow` before the rolling aggregate. A change to either the fill or the reset must be made there, not in `rollingAggregate`, which stays metric-agnostic — every resolver that gains a series must also stamp `readingAt`, and every one that can't must stamp the right poll anchor (`lastMonitorAt` for probe-backed fields; the SD-WAN rule fields use the rule row's own `updatedAt`, written only by a successful `runSdwanFor` read — never `Asset.lastSdwanAt`, which is stamped on failed reads too, and no longer `lastSystemInfoAt` since the 2026-09 cadence split) or its hold counts engine ticks instead of polls. (b) The runs are zeroed on every path that returns a row to `clear` (`CLEARED_RUNS`) — a stale `metRun` lets the next qualifying reading skip the hold. (c) A current-state run is written ONLY when `advanceRun` reports `advanced`, which is what keeps the hot path transition-write-only. (d) Nothing is migrated: a trigger with no `forPolls` keeps the wall-clock path, so both paths stay live and both need testing.

**Public API:** `evaluateAllNotificationRules` (job entry), `previewRule`, `assetCanTrigger` (the shared trigger gate — monitored + unsuppressed), `loadMaintenanceSpansForEvents` + `suppressedAtEventTime` (the event tail's SECOND gate, asked as of the event's own timestamp — business rule 80a), `buildComposedEmail(comp, ctx)` (also used by the escalation sweep), `assetDetail`/`clearAssetDetailCache` (per-tick asset-detail cache), and the unit-tested pure helpers `compareNum`/`compareValue`/`globToRegExp`/`readingMeets`/`recoveredMeets`/`buildShadowIndex`/`isAssetShadowed`/`carveOutAggregate`/`applyCarveOutToMatches`/`tierForSeverity`/`bandNotifyOf`.

**Cross-service deps:** `prisma` (assets + every sample table + notifications + state + Event + Setting), `eventLogService.logEvent`, `notificationService.REGION_TAG_PREFIX`, `notificationTypes`, `notificationRecipientService` (expandDeliveries + ComposedEmail), `src/utils/notificationTemplate.ts`.

**Used by:** `src/jobs/evaluateNotificationRules.ts`, `src/api/routes/notificationRules.ts` (`previewRule`), `notificationEscalationService` (`buildComposedEmail`).

**Invariants:**
- **ONE trigger gate for every path** (`assetCanTrigger`, business rule 37): an automation fires only about an asset that is `monitored` AND not suppressed (maintenance / dependency — business rule 16, folded in here rather than tested separately). The monitored half is SQL — `scopeWhere(scope, monitoredOnly)`, passed by `evaluateThresholdRule` / `evaluateCompositeRule` / the metric+state previews — and per-row in the event/change tail off the `assetDetail` row (`ASSET_DETAIL_SELECT` carries `monitored` for exactly that). Pushed in AFTER the dimension count so the gate can never make an empty scope (`{}` = match nothing) look non-empty. Two carve-outs in the tail: a NULL detail still fires (the asset row is gone — `asset.deleted` must not be swallowed) and system-scoped events never reach the gate. **Both carve-outs invert for a rule whose scope names devices** (business rule 46): a device filter cannot be satisfied by an event with no asset, nor evaluated against a row that is gone, so a FILTERED event/change rule skips exactly the two cases an unfiltered one keeps. The UNFILTERED `loadScopeAssets` / `loadScopeAssetIds` stays for the surfaces asking a different question — the device-list preview (reports `unmonitoredCount`), the dimension picker, mass pinning.
- **The event tail asks that gate TWICE, and the second time as of the EVENT's timestamp** (business rule 80a). `assetCanTrigger` reads the live Asset row — correct for a threshold rule, where a reading is current by definition, and wrong for the tail, which works off a backlog on a job that runs once a MINUTE. An event is routinely judged up to 60 s after it happened, so **a maintenance window narrower than that tick could suppress nothing at all**: it opened and closed between two ticks and the gate only ever saw an `active` asset. Business rule 80's agent hold made it total rather than intermittent — an upgrade's window is about TWO SECONDS (`maintenance.entered` 10:30:47 → `agent.disconnected` 10:30:49 → `maintenance.exited` 10:30:49), so the hold worked perfectly and the operator was paged anyway. `loadMaintenanceSpansForEvents(assetIds, from, to)` loads `AssetMaintenanceWindow` history overlapping the batch's own span in ONE query keyed by the assets IN THE BATCH (never one per event — that shape is what makes a broad outage expensive at 2000 assets), and the pure `suppressedAtEventTime(spans, assetId, at)` answers it. **Both boundaries inclusive** (at two seconds wide, an event stamped the same millisecond the window closed is the ordinary case). **No grace after `endedAt`** — tempting, because `Event.timestamp` is `@default(now())` (stamped by the DATABASE at insert) while `agentChannelService.detach()` does not await its write, but a grace would also swallow `agent.upgrade_failed`, which `agentInstallService.failUpgrade()` writes immediately AFTER dropping the hold precisely so a dead agent still alerts. **Resets are not gated** (matchers are collected before the trigger gates, so `agent.connected` still clears; gating them would strand a live alert). Does not reach `dependencySuppressed` — a live boolean with no history table — nor the `monitored` half, which is correctly live: stopping monitoring is not an interval and must not deliver the last minute of a device's events. **When changing this:** any harness that drives the tail needs `assetMaintenanceWindow.findMany` in its Prisma mock or the whole tail throws.
- **The one opt-out from that gate is the down trigger's own** (business rule 78): `ruleAlertsWhenDependencyDown(trigger)` (notificationTypes — the ONLY reader of `trigger.alertWhenDependencyDown`) keeps a `monitorStatus == down` automation's DEPENDENCY-suppressed assets in `active` (maintenance still goes to `suppressedIds` — rule 16 wins), and `resolveAssetStateReadings({ dependencyDownReadsDown })` hands each one a SYNTHESIZED reading — `value: "down"`, `Reading.dependencyDown = true`, the probe's own verdict in `ownMonitorStatus` — so the alert fires on the suppression EDGE, not on the device's own count at half cadence. `fire()` then calls `dependencyTreeService.resolveDependencyBlame` (memoized per tick in `_blameCache`, renewed with the asset-detail cache) and writes `Notification.dependencyDown` + `dependencyBlame`, sets `parts.dependency` (the `{dependency.*}` tokens) and swaps `{trigger.summary}` for `dependencyTriggerSummary`; `renderMessage` prints the whole `{dependency.summary}` sentence. **The alert's flavour follows the asset's flag**: for an opted-in rule the tick loads `{ id, dependencyDown }` for its firing rows' notifications, and a `meets` reading whose `dependencyDown` disagrees with the live alert's goes through `handoffDependencyFlavour` — soft-clear as `system:dependency-down` / `system:dependency-released`, release the row, audit `notification.superseded`, NO reset actions — and fires again in the other flavour. A blame walk that fails still lets the alert out, worded without a name.
- **An operator's `messageTemplate` wins over the generated default, and `Notification.message` is the ONLY thing web push, Slack, Teams and Pushbullet send.** Those two facts together are why anything the engine needs every surface to say has to reach the MESSAGE and not just the email body: the default body can carry a new banner or fact row for free, but an automation with a template of its own — which the seeded "Asset down" has (`{asset} is down`) — mails the operator's sentence and pushes it verbatim. Business rule 78's dependency notice is APPENDED to their words for exactly this reason (`renderMessage`, skipped when their template already renders `{dependency.summary}` itself), and a live dev run is what found it: every unit test and the email both looked right. A new must-say fact follows the same rule or it reaches only the readers who open mail.
- Fire only on the clear→firing transition; state writes happen only on transition (hot path scales with *changes*, not fleet size).
- Recovery is acted on only from an explicit not-meeting reading (missing data leaves a firing state alone — including a half-elapsed `recoveredSince` sustain timer, which freezes under maintenance/dependency suppression); `timed` clears purely on its timer. The one carve-out is the **vanished-state sweep** (`clearVanishedStates`, both evaluators): a firing/pending row whose ASSET left the resolved scope (scope edit, tag drift, asset deleted) or whose DIMENSION stopped being covered while the asset still produced other readings (interface admin-downed, mount/tunnel gone, dimensionFilter edit) is cleared (`system:out-of-scope`, Event `notification.out_of_scope`) — those keys would otherwise sit firing forever since the loop only re-evaluates keys that produce readings. Suppressed assets are skipped here (re-checked via asset fetch for out-of-scope candidates so a `status` scope condition can't defeat rule 16) — their live alerts are retired by `notificationService.clearSuppressedAlerts` under their own reason rather than mislabelled "left the scope", and an in-scope asset with NO readings at all stays frozen (collection gap ≠ recovery) — EXCEPT when the row's dimension is PIN-gated and the pin is gone (`pinTestForTrigger`: interfaceIsPinned for the four interface state fields + four counter metrics, tunnelIsPinned for the IPsec pair, storageIsPinned for the three storage metrics, tested against the scope row's own pin arrays — and NULL for a PoE fault condition, whose readings no longer come from the pin set, so pin-testing it would retire the very alerts the carve-out raises): an unpin is a configuration edge the operator made, not a collection gap, and without the exception unpinning a device's ONLY alerting interface left its alert firing forever, because the device then produced zero readings for the rule. Zero extra queries on the steady-state tick.
- Hysteresis dead band (auto + clearThreshold, value between clear and fire thresholds): the firing state holds, and any running sustain timer cancels. For a BANDED rule the held alert additionally EASES to the base severity (`applyBandTransition` to `rule.severity`; notify per `bandNotify.onDecrease`) — a value that crashes from the critical band straight into the dead band in one tick must not park at critical. `recoveredSince` writes are transition-only (met↔recovered edges), never per-tick; it is a firing-state-only field, distinct from the pending-side `conditionMetSince` (nulled on fire). Every state-clearing write (recover / timed sweep / manual re-arm / re-fire) must null `recoveredSince`.
- **Every interface reading is pinned-interface only, bar one value** (business rule 57 — the sub-asset half of rule 37) — the state fields (`ifOperStatus` / `ifAdminStatus` / `ifIpAddress` / `poeStatus`) AND the four counter metrics (`ifInBps` / `ifOutBps` / `ifInErrorRate` / `ifOutErrorRate`), through the one exported predicate `interfaceIsPinned(asset, ifName)` over `Asset.monitoredInterfaces` (in `SCOPE_SELECT` — the Down Interfaces widget's join). A device reports every port it has, most of them idle or unplugged, so an ungated interface rule turns one switch into a page of alerts about ports nobody selected; the pin IS the operator's statement of which ports matter, which is why it is the default with no opt-out (un-pinning is how alerting stops). The counter metrics were gated only INCIDENTALLY before — they read `AssetInterfaceSample`, which became pinned-only in the 2026-08 cutover — which left the window between un-pinning an interface and its last rows aging out (plus any pre-cutover row still inside the lookback) able to alert on a port no longer monitored. `ifOperStatus` additionally requires the sample's `adminStatus === "up"` (an admin-downed port is deliberately down). **The reading is the newest sample row that CARRIES the field, not the newest row** (`interfaceStateSeries` + `interfaceSampleCarries`, both pure and exported): one row is written per port per tick with every interface column on it, so a column can be null because a tick failed to COLLECT it rather than because the device has nothing to report — PoE most of all, being its own pair of walks that can time out while the IF-MIB walk behind the same row succeeds, plus an ifIndex correlation that drops any port it cannot resolve unambiguously. Reading `group[0]` blindly made one such tick indistinguishable from a port with no PSE: the dimension vanished, the switch was still reporting its OTHER pinned ports so `clearVanishedStates` took the "dimension is gone" branch and retired the live alert, and the next readable tick raised a NEW one — a **duplicate alert email per collection gap**, on a port whose state never changed. Null still means "no reading" and is still never mapped to a value (the `hwSensorAlarm` contract, business rule 24); what changed is that a single null no longer decides the question. Unreadable rows are dropped from `Reading.series` too, so a gap neither counts toward a poll-counted hold nor breaks its run (business rule 19). A group with NO readable row anywhere in the lookback window still produces nothing, which is the case the null gate was written for. "Newest non-null wins" is what the hourly rollup already applies to these same columns (`sampleRollupService`'s `ARRAY_AGG(...) FILTER (WHERE ... IS NOT NULL)`), so the engine now agrees with the rollup instead of contradicting it. An interface leaving the pin set stops producing readings and its alert clears via the vanished-state sweep on the next engine tick — the sweep tests the pin set DIRECTLY (`pinTestForTrigger`), so the clear happens even when the unpin leaves the device with no readings for the rule at all (the no-readings collection-gap freeze does not apply to a missing pin). That is what makes the Assets-page **Mass Pinning** section (`massPinService`) safe to unpin in bulk without any alert-cleanup path of its own. **IPsec readings are pinned-tunnel only the same way** — `ipsecStatus` + `ipsecThroughputBps` gate through the exported `tunnelIsPinned(asset, tunnelName)` over `Asset.monitoredIpsecTunnels` (also in `SCOPE_SELECT`). Unlike interfaces the sample table is NOT pinned-only: the full system-info scrape writes every tunnel the gate reports (`cadence="slow"`, 24h, refreshed every scrape — always inside the lookback), so this gate is the ONLY thing keeping a tunnel-down rule from alerting on tunnels nobody selected — which it did until 2026-08. **Storage readings are pinned-mount only the same way** (2026-09) — `storageUsedBytes`, `storageUsedPct` and the forecast metric `storageDaysUntilFull` all gate through the exported `storageIsPinned(asset, mountPath)` over `Asset.monitoredStorage` (also in `SCOPE_SELECT`). Storage is the IPsec case one step worse: the stream walks EVERY mountpath the device reports and writes the unpinned ones `cadence:"slow"` (24h, no rollups), rewritten on every scrape so they never age out of the lookback — so a fleet-wide "disk over 90%" rule alerted on every removable volume, ISO mount, recovery partition, mapped network drive and full-by-design archive share in the fleet, none of which anyone had marked for monitoring. `storageDaysUntilFull` applies the gate at the RESOLVER, not inside `storageForecastService`: the forecast is shared with the NOC dashboard's "days until full" feed, which asks a different question and must keep seeing every mount. **The cutover has a consequence to state plainly**: a rule scoped to devices with an empty pin set goes silent and its firing alerts are retired by the vanished-state sweep as `system:out-of-scope` — the same cutover interfaces and tunnels took, and the mount-path picker has always listed exactly the set that now fires. **`ifIpAddress` is the fourth state field** (2026-09) and rides all of the above unchanged: same table, same pin gate, same `interfaceStateSeries` selection. Two things are its own. A NULL `ipAddress` carries no reading — the device states "unaddressed" as `0.0.0.0`, so null is a port that reported no L3 address at all (every access port on a switch), and mapping it to a value would make all of them satisfy the `!= 0.0.0.0` comparison the field exists for. And the reading AND its series are normalized through `bareInterfaceIp` (`utils/cidr.ts`), so the shape a transport reported the address in (`0.0.0.0` vs the CMDB pair `0.0.0.0 0.0.0.0`) cannot decide whether an operator's comparison matches. What it is FOR: `!= 0.0.0.0` on a named port is how a rule says "this interface actually has an address" — the gate an SD-WAN overlay's packet-loss automation needs, since a health check over an overlay whose underlay WAN port is unaddressed reports total loss that is the underlay's outage to alert about, not the overlay's. In a composite that gate is a leaf ANDed with the loss condition, which means per-DEVICE alerting (the composite contract) and a parent port the operator must have PINNED — an unpinned parent produces no reading, the AND never holds, and the automation is silently inert. The builder's interface picker offers the pin set for exactly that reason.
- **`poeStatus == fault` / `== other-fault` is the ONE carve-out from the pin gate** (2026-09-17, exported `poeFaultCoversUnpinned`) — a PoE fault condition reads every PoE-capable port, pinned or not. The gate's argument is about IDLE components, and it does not hold for this value: RFC 3621 gives an empty port `searching` and a switched-off one `disabled`, so `fault` can only mean the PSE detected a powered device and failed to power it — the device's own alarm bit (business rule 24), and the one PoE event nothing else surfaces, since the AP or camera on the far end never comes up and so never becomes a monitored asset that could go down. **`==` only**: `!= delivering` covers fault AND every empty port in the fleet, which is the storm the gate exists to stop. **The readings come from `AssetInterface`, not `AssetInterfaceSample`** — the sample table has no unpinned rows at all since the 2026-06 cutover, so this could never have been done by deleting a gate; `unpinnedPoeFaultReadings` queries the current-state table (`poeStatus IS NOT NULL`, a 48h `lastSeen` floor because that table is delete-replaced per scrape and freezes wholesale when a device stops being scraped) and **UNIONS** it with the pinned sample readings, so a pinned port keeps its series and fast cadence and only the unpinned ports are new. An unpinned reading therefore has NO series: its `forPolls` hold counts through the firing row's own counter anchored on `lastSeen`, i.e. FULL SCRAPES (`systemInfoIntervalSec`, default 600s) rather than the 60s fast pass. **`pinTestForTrigger` returns null for it** — leave the arm in and the vanished-state sweep retires every unpinned-port alert on its first pass; the rule that replaces it is "un-pinning stops a `== searching` rule and not a `== fault` one". `notificationDimensionService.sourceFor` switches the builder's port picker to the PoE inventory for the same condition (noun "PoE-capable interfaces"), fed by a new `DimensionNarrow` pair (`stateOperator` / `stateValue`) — the only narrowing input that is the row's own comparison rather than a sibling dimension's value, sent by the wizard for `poeStatus` rows alone so no other picker re-fetches on a threshold edit. **When changing this:** the four parts move together — resolver union, `pinTestForTrigger` arm, picker source, and the wizard's `dimStateOfRow` / `awDimStateOfLeaf` — plus a fifth that is easy to miss: the automation's RESET must read the same ports (`coverUnpinnedPoe`, business rule 32(b)), or a healthy port clears the faulted port's alert. And a sixth thing to weigh is that alert state stays keyed per `(rule, asset, dimension)` with no per-asset coalescing, so a PSU browning out on a 48-port switch is 48 alerts, 48 emails and 48 ack links.
- **`sdwanMemberState` is the one SD-WAN state field with NO pin gate, deliberately** (2026-09). It answers "is this WAN member of this performance-SLA health check still alive", reading `AssetPerfSlaSample.state` — the FortiGate's own verdict, normalized to `"up" | "down"` at collection time by `monitoringService.normalizeSdwanState`, so it is never null and every sample carries it. One reading per `(healthCheck, link)`, keyed `"<healthCheck>|<link>"` exactly as the three SD-WAN METRICS key theirs, so a member's state alert and its loss alert name one pair and `alertChartService.parseSdwanDimension` reads both without a second shape. Both dimensions are substring-filtered like the metrics'. The absent pin gate is the deliberate part: interfaces, tunnels and mounts are gated because a device reports every port/tunnel/volume it has and most are nobody's business, whereas a health-check member is an SLA object someone configured — a handful per gate — and `AssetPerfSlaSample` carries no pinned-subset concept to gate on (its `cadence` is always `"fast"` for that reason). A member that stops being reported produces no reading, so the vanished-state sweep retires its alert the same way an unpinned port does. **Why it exists rather than a threshold on `sdwanPacketLoss`:** a WAN port on a cable modem stays oper-up through an ISP outage, so no interface field sees the fault; and the gate may declare a member dead on latency or jitter with loss well under any threshold, so `sdwanPacketLoss == 100` catches only one of the three ways a member dies. It is also the clean form of what a composite `ifIpAddress != 0.0.0.0` AND loss gate was reaching for — with none of that pattern's per-device ANY fold, which cannot tie the interface leaf to the member the loss leaf found. **Hold arithmetic moved with the SD-WAN cadence split (2026-09-23, business rule 13):** `AssetPerfSlaSample` rows are now written by `monitoringService.runSdwanFor` every `Integration.config.sdwanIntervalSeconds` (default 60 s) instead of on the 600 s system-info pass, and this resolver stamps `readingAt` from the sample itself, so a `forPolls` hold on `sdwanMemberState` or the three health-check metrics counts SD-WAN reads — N minutes by default where it used to be N × 10.
- Notification `regionTags` are snapshotted from the asset's `region:` tags at fire time; `templateCtx` is snapshotted only when the rule has emailComposition/escalation (escalation renders from it later, surviving asset deletion).
- `SCOPE_SELECT` stays tight (hot 60s×2000-asset path); the wider `ASSET_DETAIL_SELECT` fetch runs only on FIRE and only when composition/escalation/{asset.*} tokens need it, through the per-tick cache.
- All interpolation goes through `renderNotificationTemplate` (single-brace {token}, single pass, unknown tokens literal) — never hand-rolled replaceAll chains.
- **The counterpart-event reset (`reset.mode="event"`) is matched in the SAME event-tail pass as the triggers** — one batch, one cursor: a second query would either re-read the events or race the cursor advance at the end of the pass. Four invariants. (1) The clear is **same-subject**, keyed exactly like the cooldown (`assetId` when the event names an asset, else `eventSubjectLabel` compared against the stored `assetHostname`) — one agent reconnecting must not clear another's alert. (2) A rule that this same event FIRED drops that event's reset hit, or a glob wide enough to match both halves (`agent.*`) clears the alert it just raised, every tick, forever. (3) Hits apply **after** `createMany` + the fire-time action fan-out, so a disconnect and its reconnect inside one 1000-event batch raise, deliver, then clear rather than being swallowed. (4) `triggeredAt <= ` the clearing event's timestamp, so a disconnect → reconnect → disconnect batch can't clear the SECOND outage with the FIRST recovery. Reset actions fire per doomed alert (the `runEventRuleTimedClear` shape: select only when the rule has `resetActions`, else stay one bulk update); the clear stamps `clearedBy: "system:event-reset"`.
- **The event tail's subject label is computed ONCE** (`eventSubjectLabel` from `utils/alertSubject.ts`) and used for all three fields that must agree: the `{asset}` token, the stored `Notification.assetHostname`, and the cooldown key. The key dedupes on `assetId ?? <label>` against stored rows' `assetHostname`, so letting them drift (label in one, raw `ev.resourceName` in the other) silently stops cooldown from matching across ticks for the system-scoped events — capacity, backups, updates — that have no resourceName at all.
- **An event alert stores `metric`/`dimension` null, and ONE change type is the exception.** Nothing fires as a metric on this path, so those columns stay empty and the email's charts fall through to the device's own story — which is right for an integration failure or a backup, and wrong for a change that is about one sub-asset. `alertChartService.chartKeysForChangeEvent(ev.action, ev.details)` is the whole of the carve-out: it answers null for every action but `change.sdwan.failover`, which stamps `metric = "sdwanSelectedMember"` (the field that genuinely changed — not a stand-in, so the asset page's alert tooltip and the acknowledge page both stay accurate) and `dimension = "<ruleName>|<member it left>"`. The member has to ride the notification because the EVENT's details are the only place it exists: `AssetSdwanRule` is delete-replaced per scrape and by delivery time holds only where the traffic went, so a chart resolved from the table alone draws the healthy link traffic moved ONTO. Keep the helper pure and keep the default null — a new chartable change type is an entry there plus the resolver half in `resolveSdwanTarget`'s shape, never a widening of what the tail stamps by default.
- Scale: batch findMany per sample table (no per-row awaits) — re-check at 2000 assets when adding a metric.
- **A reading of 0 is a READING, never "no data".** Every `valueFn` must map only genuinely non-numeric input to null (`Number.isFinite` checks, not `|| null`, which was a real bug on `customWidgetValue` until 2026-08). Collapsing 0 to null breaks both directions of any rule about zero: a `== 0` / `<= 0` condition can never fire, and an auto-reset rule can never clear, because the recovery value is exactly the one being dropped. This matters most for the 0/1 `customStateValue` metric, where half the value domain is 0 — which is also why `AssetStateSample` stores no row at all for an unreadable sensor rather than storing 0 (see `evaluateStateMap`'s null contract).
- **`hwSensorAlarm` shares `hwSensorValue`'s sampling and dimensions** — same table, same `hwSensorFilterMatches` predicate, same per-sensor dimension key — so a rule can target one named sensor or a whole class exactly as a threshold rule does. It differs in one place that matters: `alarmStatus: { not: null }` is applied **in SQL**, so sensors from sources that publish no alarm bit produce no readings at all rather than being mapped to a value (`alarmStatusToFlag`'s contract, business rule 24). Never "fix" that by coalescing the null to 0.
- **`customStateValue` dimensions are per PROBE ROW** (`${probeId}|${rowKey}`), so every sensor / PSU / fan tray carries its own firing state and its own alert. The dimension KEY is `rowKey` (the stable OID index) while the operator-facing `stateRowPattern` filter and the alert's `dimLabel` use `rowLabel` — so renaming a row keeps its alert instead of clearing one and opening another. `stateProbeId` is matched EXACTLY (a registry key, not a device-reported string); the row pattern is `substringMatch` like every other `*Pattern` dimension.
- **Composite path is separate by design** (`evaluateCompositeRule` + collectLeafRefs/resolveLeafTruths/evalTriggerTreeForAsset/compositeOutcomeForAsset/applySustainedRecovery): per-ASSET state at dimensionKey "" (ANY-dimension leaves, one alert per device), leaves resolved through the UNCHANGED single-trigger resolvers with identical leaves deduped to one query. Never generalize the legacy per-reading loop to cover composites — the two share only fire/recover/upsertState. Missing leaf ⇒ false; asset with zero readings across all leaves ⇒ skipped (state frozen). Orphan sweep: any state row with dimensionKey ≠ "" under a composite rule is cleared + deleted (`system:rule-edited`). Condition-mode reset resolves its tree ONLY against firing assets and is the sole recovery authority while firing (`recover()` treats "condition" like "auto"); auto for composites = !tree, no hysteresis dead band.
- **Condition-mode reset now works on SINGLE triggers too** (business rule 32, 2026-08 — it was composite-only, refused at save): `evaluateThresholdRule` handles it in a dedicated pass AFTER the readings loop, not inside it, because the tree's leaves need not be the trigger's metric — an alert whose trigger metric stopped reporting must still be able to clear, where the auto path deliberately freezes. Three invariants that pass depends on. (1) It **re-reads the firing rows from the DB** (`state: "firing"`), never the pre-loop `states` snapshot: the carve-out, device-down and vanished sweeps run before it and have already cleared rows that snapshot still calls firing, and a row that fired earlier in this same tick must not recover in it. (2) Inside the readings loop the firing branches HAND OFF instead of acting — `rule.reset.mode !== "auto"` must not `recover()` under a reset tree, and the re-met branch must not null `recoveredSince` (it is the TREE's sustain timer, so the trigger re-meeting can't cancel it). (3) Leaf truths resolve **dimension-first, and the per-asset fallback is scoped to leaves in ANOTHER dimension space** (`resolveResetTruths` folding each leaf's readings through BOTH `leafTruthByAsset` and `leafTruthByAssetDim`, one query pass; `dimensionSpaceOf` in `notificationTypes.ts` is the space test — a trigger's dimension-filter key set, or null for a whole-device one): a reset leaf on the firing row's own dimension clears that alert alone, a device-wide leaf (CPU, at dimKey "") falls through to the ANY fold and clears every alert on the device, and a SAME-SPACE leaf with no reading for that component answers `undefined` — no recovery, alert stands. That last clause is business rule 32(b), added 2026-09-18 after the unscoped fallback let a healthy port clear another port's PoE-fault alert. Its other half: `resolveResetTruths` takes `coverUnpinnedPoe` (`poeFaultCoversUnpinned(rule.trigger)`) and threads it through `resolveOneLeafReadings` to `resolveAssetStateReadings`, so a reset leaf reads the same unpinned PoE ports the TRIGGER does — the seeded `!= fault` leaf can never qualify for the carve-out itself, and without this the tree is silent about the faulted port and the alert never clears. **When changing either:** they are one fix in two halves — scoping the fallback without the coverage strands every carve-out alert, and the coverage without the scoping leaves the cross-port clear in place. `evalTriggerTree(node, lookup)` is the shared walker both paths go through — `evalTriggerTreeForAsset` is now a thin wrapper over it, so the composite path is unchanged. Suppressed assets are excluded (frozen, never recovered). Banded rules pass `fireResolvedFirst` so `bandNotify.onResolved` still runs, matching the auto path.
- `notificationRuleService.updateRule` clears the rule's active alerts (by ruleId) + deletes its state rows whenever the trigger IDENTITY changes (`triggerIdentityOf`: type/kind/metric/field/changeType, `system:rule-edited`) OR the rule is DISABLED (`system:rule-disabled` — the engine only evaluates enabled rules, so a disabled rule's alerts would strand uncleared forever); threshold/operator/tree edits keep state. `deleteRule` clears active alerts first (`system:rule-deleted`) — the cascade drops the state rows, after which nothing could ever auto-clear them (Notification.ruleId goes NULL via SetNull). Migration `20260730000000_stranded_alerts_cleanup` healed pre-fix strays and backfilled `firingSeverity` from the live notification's severity (NULL rows read as "at base severity", blocking de-escalation into the base band).
- **Carve-out is same-signature only** (`triggerSignature`): a specific temp automation never silences an unrelated DOWN one. The shadow index is built once per tick over the enabled rule set; the per-asset test reuses the pure `scopeMatchesAsset` (kept in lockstep with `scopeWhere`/`evaluateScopeCondition`). Superseding CLEARS the general alert (handoff is permanent) — distinct from maintenance suppression, which FREEZES firing rows. Same-rank ties both fire.
- **A windowed-ratio metric's `windowSec` is used EXACTLY** (`probeLossPct`; `WINDOWED_RATIO_METRICS` in notificationTypes, published as `windowedRatioMetrics`): resolved by the SHARED `probeLossWindowSec` (notificationTypes — `PROBE_LOSS_MIN_WINDOW_SEC` 5 min floor, `PROBE_LOSS_DEFAULT_WINDOW_SEC` 15 min when the trigger carries none; the alert-email loss chart reads the same function via `probeLossWindowSecFromTrigger` so the graph can't span a different period) — NOT `max(windowSec, DEFAULT_LOOKBACK_MS)`, which exists so a `latest` reading finds a recent sample and would silently measure a 5-minute History over 15. The wizard's base time field is the window for these (label "History"); the hold is its own optional "Sustained for" field (2026-08-20 — `forDurationSec`, engine debounce + per-band `bandMetSince` machinery unchanged).
- **Packet loss only reports on an ANSWERING device** (business rule 29): the `probeLossPct` resolver filters to `assetIsAnsweringProbes` (monitorStatus up/warning; `down`/`recovering`/`unknown` are the asset-down alert’s business), so the composite path and `previewRule` inherit the gate from one place. `evaluateThresholdRule` additionally CLEARS a live loss alert on an asset that stopped answering — carve-out handoff semantics (`clearedBy="system:device-down"`, Event `notification.superseded` with `reason:"device-down"`, no reset actions), the same shape maintenance suppression itself now takes (`clearSuppressedAlerts`), because freezing is what parked a loss alert beside the down alert for a whole outage. `ANSWERING_ONLY_METRICS` is the metric scope — every other metric comes from SUCCESSFUL polls, so a dark device just stops reporting. Note the handoff-clear lives on the single-trigger path; a composite alert carrying a loss leaf freezes like any other no-reading asset.
- **Severity bands stay backward-compatible**: no `severityBands` ⇒ `severityForValue` returns base-or-null, identical to the pre-band fire/clear. Bands are numeric (asset_metric/host_metric) only. On a band change the alert updates severity + message IN PLACE (one row per asset) and stamps `escalationState.bandSince` so the per-band time-escalation restarts; the sweep selects the active severity's chains via `escalationChainsForSeverity` (notificationTypes — band level chain + band/base actions' per-action chains). Value-bands and time-escalation are independent axes.
- **"Sustained for" is per TIER** (business rule 19): the banded path does NOT read `trigger.forDurationSec`/`conditionMetSince` — it resolves `tierLadderFor(rule)` once per rule per tick, rolls `NotificationRuleState.bandMetSince` (`{[severity]: epochMs}`) forward with `updateTierMetSince`, and fires/transitions on `sustainedSeverity` (most-severe tier whose own run outlasted its own duration). The non-banded path is byte-for-byte unchanged. Three properties the write path depends on: the map is persisted only when `tierMetSinceChanged` (transition-only writes at 2000 assets), an empty map stores as SQL NULL (`metSinceJson`), and EVERY state-clearing write nulls it — a stale run would let a re-entering tier fire instantly. Band ESCALATION is gated by the target tier's duration; de-escalation and the dead-band ease-to-base are immediate by design (the lower tier's run is already old, and parking at a band the value no longer satisfies is the bug the dead-band ease exists to prevent).

**Path resolvers (2026-09-23):** `pathLatencyMs` / `pathHttpStatus` / `pathOk` / `pathTlsDaysLeft` read `assetPathCheckSample` (checkId narrowed in SQL; a failed run's null latency is NO reading, the failure is pathOk's); `pathHopCount` reads `assetPathCheckTraceroute`; `pathFailurePct` is ONE `groupBy(assetId, checkId, ok)` over the window, emitting 0 % rows for recovery, NOT gated on `assetIsAnsweringProbes` (the agent's own report — a host that cannot report is naturally silent). Labels come from `pathCheckNames` (one small query per call).

**When changing this:** New metric → add a resolver branch AND the catalog entry in `notificationTypes` (composite leaves get it for free via the shared resolvers); if it is per-dimension, add it to `METRIC_DIMENSIONS` (a new asset-STATE field that reports per dimension goes in `STATE_FIELD_DIMENSIONS`, and its dimension key needs a `DIMENSION_NOUNS` entry) — the reset step's "clears one alert or all of them" note reads those maps. New clear behavior → handle it in `recover()`, the timed-sweep pass, the condition-reset pass, AND the composite transition block. New template token → `TEMPLATE_VARIABLES` + `buildTemplateContext` in the util (+ `ASSET_DETAIL_SELECT` here if asset-sourced). New scope dimension → add it to the `scopeRank` ladder in `notificationTypes` (else it can't participate in precedence), and to `scopeIsUnconstrained` (else a rule narrowed ONLY by the new dimension reads as unfiltered and the event tail fires it about everything). Changing the band state machine → keep `notificationEscalationService`'s `bandSince` handling + `escalationChainsForSeverity` (notificationTypes) in lockstep. New place actions can live → add it to `allRuleActionRefs` (the script gate, `assertActionRefs`, and `ruleWantsAssetDetail` all collect through it).

## services/downDetectionService.ts

**What it owns:** WHO DECIDES A DEVICE IS DOWN (business rule 36). The per-asset resolution of the covering `monitorStatus == down` automation and its `missedPolls` count, cached fleet-wide for `DOWN_DETECTION_TTL_MS` (60s) and invalidated on every automation CRUD write. Precedence is business rule 18's `scopeRank` ladder (never a second system); same-rank ties resolve to the smaller count, then older `createdAt`, then lower `id` (`pickDownWinner`, pure). A device covered by no down automation resolves to `null` = the `passive` monitor status.

**Public API:** `resolveDownThreshold(assetId)` (the probe path's question), `pickDownWinner(rules, asset, sink?)` (pure core), `describeDownDetectionFor(assetId)` (the slide-over/effective-settings view), `previewDownDetectionRemoval(ruleId)` (backs `GET /automations/:id/removal-impact`), `countPassiveAssets()`, `invalidateDownDetectionCache()`, `DOWN_DETECTION_TTL_MS`, `DEFAULT_MISSED_POLLS`, `isDownDetectionTrigger`.

- `src/services/monitoringService.ts` / `src/utils/monitorStatus.ts` — `recordProbeResult` resolves the threshold once per probe; `null` parks the asset at `passive` (counters keep advancing; `runsHeavyCadences` keeps telemetry alive when the last probe succeeded; `isConfigStatusEdge` keeps passive transitions out of `monitor.status_changed` Events and dependency propagation).

- **One ladder, not two** — down-detection authority and alert precedence share rule 18's carve-out groups; every `monitorStatus == down` automation shares ONE `triggerSignature` keyed by operator+value (never dimensionFilter).

## services/probeLossQuery.ts

**What it owns:** The single windowed failed-probe-ratio SQL over `asset_monitor_samples` (UTC-wall-clock-anchored `now() AT TIME ZONE 'UTC'` window, grouped per asset, with every row counted except the failures of a run that reached `down`).

**Public API:** `queryProbeLossRatios({ sinceMinutes, assetIds?, onlyLossy?, limit? })`, `ProbeLossRow`.

**Used by:**
- `src/services/notificationEngine.ts` — the `probeLossPct` trigger (engine mode: every asset with ≥1 successful probe, INCLUDING 0%-loss rows so hysteresis/auto-clear rules recover).
- `src/services/nocDashboardService.ts` — `getPacketLoss` (widget mode `onlyLossy: true`: additionally requires ≥1 failure, orders lossiest-first, caps at `limit`; `limit` null = uncapped via Postgres `LIMIT NULL`).

**Invariants:**
- **The failures of a run that reached `down` are excluded** (business rule 29h, 2026-09-03) — nested subqueries computing `runId` (`sum(CASE WHEN success THEN 1 ELSE 0 END) OVER (PARTITION BY assetId ORDER BY timestamp, id ROWS ...)`) and `runOutage` (`coalesce(bool_or("assetDown") OVER (PARTITION BY assetId, runId), false)`), filtered by `WHERE NOT ("runOutage" AND NOT "success")`. Four things about it:
  - **The unit is the RUN, not the marked row.** `AssetMonitorSample.assetDown` is only stampable from the probe that DECLARES the outage (at the first missed poll nobody knows yet), so excluding stamped rows alone leaves the ONSET — `missedPolls - 1` fully-lost probes — in a denominator the exclusion has already shrunk. The prod case then reads 10.5% instead of 40%: still over the seeded rule's 10% threshold, still a false alert. `tests/unit/probeLossWindow.test.ts` pins that 10% explicitly so the marker-only shortcut cannot come back looking like a simplification.
  - **`coalesce` is load-bearing.** `assetDown` is nullable, so `bool_or` over a run of pre-column rows is NULL, and `NOT (NULL AND NOT success)` is NULL — which WHERE reads as false, dropping every failure in an UNSTAMPED run, i.e. all loss on every asset. Pinned verbatim in `tests/unit/nocDashboardService.test.ts`.
  - **It must not learn `missedPolls`.** That count belongs to whichever automation covers the device (business rule 36) and changes when an operator edits a rule; a run is bounded by successes and needs no threshold. Do not replace this with "drop the N rows before a stamped one".
  - **Do not move it to a time range** (that is the anchor in the next invariant, and it excluded by TIME), and do not extend it to `recovering` — those probes ANSWERED, and a burst that loses packets there is real loss on a shaky device.
- **NO ANCHOR (2026-09-01). The ratio is plainly failed/total over the whole window.** It used to start at `GREATEST("firstOk", "recoveredAt")` — a partitioned `min("timestamp") FILTER (WHERE "success")` plus a LEFT JOIN to `assets` for `Asset.recoveryStartedAt` — so an outage inside the window was trimmed out of its own denominator. That stopped a device reading ~92% the moment it came back from a 55-minute outage; it ALSO collapsed the window of a device flapping to `down` each cycle down to its last few probes, so a badly lossy link reported ~0% loss forever (prod 2026-09-01). Both the window function and the join are gone, which makes this a plain hash aggregate again. **Do not re-introduce a trim here** — the suppression it was doing now lives in the ENGINE (business rule 29), and putting it back would silently restore the flapping bug. `tests/unit/nocDashboardService.test.ts` asserts its ABSENCE (`not.toContain("firstOk")` / `"GREATEST"` / `"LEFT JOIN"`) for exactly that reason.
- **`Asset.recoveryStartedAt` is DORMANT.** Still stamped by the probe path via `stampsRecoveryAnchor` (`utils/probeLossAnchor.ts`, whose reader half was deleted with the anchor); read by nothing. Safe to leave dormant in a way `cooldownSec` was not — a timestamp nobody reads cannot change behaviour.
- **`includeFullyDown` is RETIRED.** With every row counted, an asset with no successful probe reads 100% on its own; the flag existed only to stop the missing anchor dropping it, and its absence read as "no loss" in the NOC widget — the opposite of the truth. Removed from the options type and from `nocDashboardService`.
- **It counts PACKETS, not rows, wherever it can.** An ICMP sweep row (business rule 30's uniform burst sweep) carries `packetsSent` / `packetsReceived` and describes N echoes. Counting such a row as one outcome understated loss badly — a 5-echo burst that got one reply back is an 80%-lossy reading but a perfectly `success: true` row. So `effSent` / `effRecv` switch on `count(*) FILTER (WHERE "packetsSent" IS NOT NULL) > 0`: an asset with burst rows is measured from those sums ONLY, and its response-time poll rows are excluded (that poll may be SNMP/SSH/REST/WinRM, and folding a lost SNMP response into a figure labelled *packet loss* would make the number mean something different per asset). An asset with none falls back to the row ratio, which is the pre-sweep behaviour. **`{total, failed}` kept its shape on purpose** — every caller does `failed/total` unchanged; only the units beneath it moved.
- **The widget HAVING and ORDER BY must be asked of the effective counts too.** A device whose every burst dropped packets while still getting something back has NO failed rows at all, so a row-based `>= 1 failure` test filtered out precisely the device the Packet Loss widget exists to surface.
- **This query counts EVERY `probeKind`** -- one of only two all-kinds readers of `asset_monitor_samples` (with `alertChartService`'s loss chart); every response-time reader filters to primary.
- The engine/widget HAVING difference is a real semantic (0%-loss rows feed hysteresis recovery; the widget hides clean assets) — it is the `onlyLossy` parameter, never re-fork the query.
- All SQL fragments are compile-time literals; user data rides positional parameters only.

**When changing this:** both consumers' post-processing assumes `{ assetId, total, failed }` bigint rows; the window must stay UTC-wall-clock-anchored (the hypertable's timestamps are naive UTC). **The `assetDown` exclusion is a THREE-file lockstep** — this query's window functions, their JS mirror `alertChartService.outageRunFailures` (which since 2026-09-14 feeds only `ProbeLossSeries.engineRatioPct`: the alert loss CHART counts every probe, outage runs included, because a chart cannot announce an exclusion and drawing a flat 0% across the minutes the response-time chart above draws as amber and red dots contradicts it — the mirror still has to track this query exactly, and the parity test compares it against `engineRatioPct`) and the two writers in `monitoringService` (`recordProbeResult` + `runLossSweepFor`); a reader that forgets it reports the outage back as loss, a writer that forgets it reports nothing at all. Behavior is covered by `tests/integration/probeLossQuery.test.ts` (real SQL against Postgres — the exclusion, the amber misses that survive it, and the unstamped rows that prove it is not retroactive) plus the SQL-shape assertions in `tests/unit/nocDashboardService.test.ts` (which assert the absent anchor expressions AND the present exclusion verbatim, so an aliasing change lands there too) and the pure halves in `tests/unit/probeLossAnchor.test.ts` / `tests/unit/probeLossWindow.test.ts`.

## services/automationTestService.ts

**What it owns:** Firing ONE action of an automation draft for real, so the wizard's Summary step can prove delivery works before the rule is saved.

**Public API:** `runTestDelivery({rule, path, target, actorUserId, actorUsername})`, the pure `selectTestActions(rule, path, callerUserId)`.

**Cross-service deps:** `notificationTypes.allRuleActionRefs` (the walk the `path.index` addresses), `automationActionService.executeActions`, `notificationDeliveryService.drainPendingDeliveries({notificationId})`, `notificationRecipientService.scopeRegionTagsOf`, `utils/notificationTemplate.buildTemplateContext`, `eventLogService`.

**Used by:** `src/api/routes/notificationRules.ts` (`POST /automations/test-delivery`, `automationManagement:write`, session callers only — the delivery resolves the CALLER and a bearer token has no user to be).

**Invariants:**
- **The alert is about an INVENTED device, and every fact in the email comes from `utils/sampleAlertDevice` (business rule 65).** It used to fire against whichever real asset the draft matched — `previewRule` picked the device that would actually fire — so the email carried a live hostname, management IP, site code and the device's own admin description, mailed on demand by anyone with `automationManagement:write` to an address they typed, into an inbox nobody treats as inventory. `SAMPLE_ALERT_DEVICE` replaces the asset lookup and `sampleDimensionFor(metric)` the sensor/path lookup; the preview query is gone from this path entirely. No reading is quoted either — `triggerSummary` is called with `value: null` and falls back to stating the CONDITION ("Response time (median over 5 minutes) is above 500 ms"), which is the wording the operator is actually testing; the only honest number available would be some real device's.
- **`assetId` is null on the test Notification** — so a test can never surface on a real device's alert list, `{asset.link}` renders empty and `pruneDeadLinks` drops the "Open device" button, and the email's charts come from `alertChartService.sampleChartSeries` (reached through `Notification.testRun` in `notificationDeliveryService.emailMessageFor`) rather than from anybody's telemetry. `assetHostname` carries `SAMPLE_ALERT_HOSTNAME`, which is what the subject and the acknowledge page show.
- **The TEST marking is not a template token.** `markEmailAsTest` (`utils/alertEmailTemplate`) stamps the subject, an HTML banner and a plain-text line onto the composed message at DELIVERY, after every substitution and pruning pass — so a fully customized email body still carries it and no operator can edit it away. A `{test.notice}` token was rejected for exactly that reason. The `[TEST]` prefix in `Notification.message` remains what marks the push / chat bodies, which print the message directly.
- The test Notification ALWAYS has `ruleId: null` and `testRun: true`, even when the draft is a saved rule. `notificationEscalationService` sweeps `{ cleared: false, ruleId: { in: enabledRuleIds } }`, so a real ruleId would enlist the test alert in the escalation ladder and start paging people on the next 60s tick.
- No `NotificationRuleState` row is written — the engine must not conclude the asset is firing.
- **A test alert clears itself after an hour** and nothing else ever can. `ruleId: null` plus no state row puts it outside every recovery path Polaris has — no engine state to release, no rule for `runEventRuleTimedClear`, no condition to recover — so testing one automation used to leave a permanent alert on whichever device the wizard picked. `notificationService.clearExpiredTestAlerts()` (`TEST_ALERT_TTL_MS`, swept by the `evaluateNotificationRules` 60s tick) soft-clears them with `clearedBy: "system:test-expired"`: history and ack state preserved, no reset actions (there is no rule to define any), so an acknowledge link in an old test email still resolves and reports the alert closed. An hour is deliberate — long enough to open the email and follow its link, short enough to be gone next time anyone opens the device.
- Only `notify` actions run (plus the audit Event in `event` mode). `script` and `api_call` are filtered and reported as `skipped`: a test button that runs a registry script is RCE-by-button, and an api_call would act on a live system.
- The recipients are REWRITTEN to the caller, and that is a rewrite rather than a flag: `recipientUserIds: [caller]` with every other recipient field AND `emailComposition.cc/bcc` dropped. It must be structurally incapable of reaching anyone else, not merely intended to be.
- **There is no recipient mode.** The former `mode: "self" | "recipients"` was REMOVED in 2026-08 rather than defaulted off: a test answers "does this channel work, and what does the message look like", and answering it by paging the on-call is a cost nobody asked for. The field is gone from `testDeliverySchema` too, which is a non-strict `z.object`, so a stale browser tab still posting `"recipients"` has it STRIPPED and reaches only the sender. Do not re-add it without a real requirement — the audit Event is now unconditionally `info` because no variant of this pages real people.
- A destination with **no private form** — a Slack/Teams/Pushbullet webhook posts to one channel — is consequently not testable from the wizard at all. The Delivery tab's per-channel `POST /delivery-channels/:id/test` is where that decision belongs, and the wizard disables those buttons with a pointer to it rather than quietly messaging a team channel.
- Dispatch EXTENDS the existing drain (`drainPendingDeliveries({notificationId})`) rather than cloning `dispatch()`, which owns retries, permanent-fail classification, dead-push pruning and the summary Event. A 20s budget bounds it so a dead SMTP host can't pin an HTTP worker.

**When changing this:** any new recipient field on `notifyActionSchema` must be added to the self-mode rewrite (it lists what it KEEPS, so a new field is dropped by default — verify that stays true). If a new action type can act on the outside world, filter it here too. A new asset-sourced `{asset.*}` token needs its field added to `SAMPLE_ALERT_DEVICE` as well as to the engine's `ASSET_DETAIL_SELECT`, or the test email mails a blank row for a fact the real alert prints — which is how a test quietly stops being a faithful specimen. (This file's own `detailSelect` copy is gone with the asset lookup.)

## services/downDetectionService.ts

**What it owns:** The answer to "what makes THIS device down, who decided that, and how many answered polls it takes to be up again?" Down used to be a Monitor Settings value (`failureThreshold`, resolved through the (integration, assetType) tier hierarchy). It is now owned by the `monitorStatus == down` AUTOMATION covering each asset, via its `missedPolls` count — so an operator can say "core switches after 2 missed polls, page the NOC; workstations after 10, in-app only" from one surface. This service resolves which automation governs each asset and caches that resolution for the probe hot path.

**Public API:** `resolveDownDetection(assetId)` → `{ threshold, recoverySustainSec }` or **null = PASSIVE** (the probe loop's call — BOTH directions from ONE lookup, so the two can never resolve onto different automations); `resolveDownThreshold(assetId)` → the missed-poll count alone, a thin wrapper for callers that only ask the down question; `recoveryPollsFor(verdict, intervalSec)` (pure: the stored reset seconds → a poll count at THIS asset's cadence, floored at the missed-poll count and capped at 100); `describeDownDetectionFor(assetId)` (diagnostics: winner, rank, whether it came via the all-assets fallback, any same-rank conflict — feeds the asset modal, the Alerts tab's Down-detection panel and `GET /assets/:id/effective-monitor-settings`); `previewDownDetectionRemoval(ruleId)` (what deleting or disabling one automation would do: governs / would-fall-back-to-another / would-become-PASSIVE + sample hostnames — builds its own view rather than reading the snapshot's winners, because "who would win instead" is a different question from "who wins", and it only runs when an operator opens a confirm dialog); `countPassiveAssets()`; `invalidateDownDetectionCache()`; `pickDownWinner(rules, asset, sink?)` (pure, the precedence decision); `resetDownDetectionStateForTests()`; `DOWN_DETECTION_TTL_MS`; re-exports `DEFAULT_MISSED_POLLS` + `isDownDetectionTrigger` (both DEFINED in notificationTypes, because validateRuleV2 + the schema catalog need them and importing this service from there would close a cycle).

**Writers of the inputs it reads:** `notificationRuleService.createRule/updateRule/deleteRule` (the rule set — all three call `invalidateDownDetectionCache()` UNCONDITIONALLY); every asset writer in the codebase (scope membership — covered by the TTL only, see Invariants).

**Used by:** `monitoringService.recordProbeResult` (THE hot-path consumer — one call per probe per asset); `jobs/seedBaselineAutomations` (V3 seed, invalidates after seeding). Diagnostics consumers (asset modal / effective-monitor-settings) read `describeDownDetectionFor`.

**Invariants:**
- **NEVER query on the resolve path.** `resolveDownThreshold` runs once per probe per asset — 2000 assets on a 60s cadence — so it must stay ONE `Map.get` over a cached snapshot. `tests/unit/downDetectionCache.test.ts` pins "2000 concurrent lookups ⇒ exactly 2 queries"; that assertion is the point of the file. Not even an indexed `findFirst` is acceptable here: `probePatchBuffer` and `sampleWriteBuffer` exist specifically to collapse per-probe pool acquisitions.
- **One automation answers both directions.** `DownWinner` carries `recoverySustainSec` alongside `threshold`, resolved in the same `Map.get`, because "down after 3 missed" and "up after 5 received" are one operator statement (business rule 36). A second lookup for the recovery half would let a device be declared down by one rule and released by another. The index build therefore selects `reset` as well as `trigger`/`scope`, and `downRecoverySustainSec` (notificationTypes) decides which resets even carry a count — `auto` with a hold, nothing else.
- **The recovery count RAISES the bar and never lowers it.** `recoveryPollsFor` takes `max(threshold, polls)`: the leaky bucket still owes one answer per miss (business rule 30), so a shorter reset is a no-op and a deep outage that out-drained the count is untouched. It rounds rather than ceils, because the wizard produced those seconds by multiplying a whole number of polls by a cadence.
- **The cache stores the RESOLVED winner per asset**, never the rule set for a per-probe walk. Overlapping automations are the central use case, so a per-probe walk would be O(assets x rules) on the hot path.
- **One precedence system, not two.** The winner is chosen by business rule 18's `scopeRank` ladder, and every down automation shares ONE `triggerSignature` (keyed by compared value, NOT by device filter) precisely so the threshold group and the carve-out group are the same set by construction. Change `triggerSignature`'s monitorStatus branch and you change both at once — which is the intent; splitting them would let the automation that alerts differ from the automation whose count governs.
- **Coverage is scope AND device filter.** `ruleCoversAsset` ANDs `deviceFilterMatch` into `scopeMatchesAsset`. Since the signature no longer pins the filter, omitting this would let a `hostname matches "core-"` automation govern every asset in its scope.
- **Same-rank tie ladder: smaller count, then older `createdAt`, then lower `id`.** Smaller-count-wins matches `getMetricSeverityTiers`' existing more-sensitive-wins convention and is the safe direction (both tied automations still FIRE — rule 18 leaves same-rank ties alone — so taking the smaller means neither ever fires later than its own configuration promised). The last two only ever break a tie between EQUAL counts, where the threshold is identical and the tiebreak exists solely to give the winner a stable identity for diagnostics; both are immutable so two Polaris processes never disagree.
- **`fallback` is not an optimization, it is the correctness fix for a new asset.** An asset discovered since the last rebuild is absent from `byAsset` and would otherwise read passive for up to a TTL. An all-assets automation (no scope narrowing, no device filter) covers ANY asset by definition, so answering from it is exact and can never over-claim.
- **Asset scope drift rides the TTL alone — deliberately.** Instrumenting every asset writer is not viable (`discoveryEngine` alone has dozens of write sites, plus the merge services and the asset routes). One TTL is under one probe cycle, so the worst case is a stale-but-valid threshold; the only case where staleness could produce a WRONG verdict is the new asset, and `fallback` makes that exact. Do not half-instrument this.
- **Degrade to PASSIVE, never to a guessed number.** A failed rebuild serves `lastGoodIndex`; with no snapshot at all every asset reads passive. Refusing to render a verdict is strictly safer than inventing one, it is a state the system already models, samples and counters still land, and `createTtlCache` never caches a rejection so it self-heals on the next probe. `invalidateDownDetectionCache()` deliberately does NOT clear `lastGoodIndex` — that is the crash mat, not the answer.
- **Conflicts are reported per rule PAIR, not per asset** (capped at `MAX_CONFLICTS`): one bad config across a 2000-asset fleet must not write 2000 log lines or pin 2000 rows.
- **The zero-rule Event fires on the TRANSITION**, not every rebuild. A fleet with no down automation is judged by nothing, and the thing that would normally alert about that is exactly what was deleted — but a warning every 60s forever is its own kind of useless.

**When changing this:** Adding a way for an automation to define down → it must flow through `pickDownWinner` (keep it pure and unit-tested) AND through `isDownDetectionTrigger`, or the resolver and the validator will disagree about which rules count. Changing the TTL → keep it between 30s and 120s (below, the rebuild stops amortizing across a probe cycle; above, this is the only mechanism catching asset scope drift). Adding a column to the coverage predicates → add it to `DOWN_SCOPE_SELECT` too, and resist reusing the engine's `SCOPE_SELECT`, which drags array columns this resolver never reads. Touching the state machine that consumes this → `tests/unit/monitorStatusStateMachine.test.ts` mirrors the transition logic inline and must move with it, and so does the asset strip's browser-side replay (`_intermittencyStates` in `public/js/assets.js`, pinned by `tests/unit/assetIntermittencyBar.test.ts`) — a bar that disagrees with the pill is the bug that produced the recovery count in the first place. Changing what the recovery half reads → `downRecoveryConsumesSustain` must move in lockstep, or the ENGINE will charge the same wait a second time on top of the one the state machine served.
