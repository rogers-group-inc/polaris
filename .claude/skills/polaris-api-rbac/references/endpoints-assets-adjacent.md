# Endpoints — asset types, monitor settings, conflicts, search, events, aliases

Verbatim from ARCHITECTURE.md → API Endpoints. Gate notation: `key:level`.

### Asset Types — `assets` function key
Operator-extensible asset-type registry, plus the **device-type matching** that decides which bucket a newly discovered device lands in. The historical built-ins (server / switch / router / firewall / workstation / printer / access_point / other, plus `hypervisor` and `kubernetes_cluster`) are seeded as `isBuiltIn=true, isProtected=true` rows and cannot be renamed or deleted — but their MATCHING is editable like any other row's, because `isProtected` guards identity (which code branches on) and nothing branches on how a device got into a bucket. Managed from Server Settings → **Identification → Device Types**. Behavioral special-cases (FortiGate / switch / access_point branches in dependency tree, fortinetTopology, polling source defaults, topology rendering) still fire only for the built-ins — custom types fall through to "other"-like generic behavior — but INFERENCE no longer does: a custom type can claim a device through its own rules. Mounted at `/api/v1/asset-types` BEFORE `/assets` so Express's first-match routing picks the registry endpoints instead of treating "types" as an asset id.
- `GET    /asset-types[?withUsage=1]`           *(read)* — `{ types: [{ id, name, label, description, isBuiltIn, isProtected, createdBy, createdAt, updatedAt, usageCount? }] }`. `usageCount` only included when `?withUsage=1` (one extra `prisma.asset.groupBy` to count assets per type — used by the Manage modal to show "N assets" badges and refuse delete when in-use).
- `GET    /asset-types/:id`                     *(read)* — Single row with `usageCount`.
- `POST   /asset-types`                         *(write)* — Body: `{ name, label, description?, matchRules?, matchContexts?, matchPriority? }`. `name` is lowercased + validated against `/^[a-z0-9_-]{2,32}$/` and rejected if it collides with a built-in. Writes one `asset_type.created` Event. Cache refresh fires immediately so the registry is hot for the next `/assets` write.
- `PUT    /asset-types/:id`                     *(write)* — Body accepts any subset of `{ name, label, description, matchRules, matchContexts, matchPriority }`. **Refuses with 403 on a built-in row only for an IDENTITY change** (name / label / description); the three matching fields are accepted on every row. Rename is transactional: every `Asset` row holding the old name is rewritten to the new name atomically with the registry row update via a `$transaction([asset.updateMany(...), assetTypeDef.update(...)])`. Writes one `asset_type.updated` Event.
- `DELETE /asset-types/:id`                     *(write)* — **Refuses with 403 on built-ins**, and **with 409 when any Asset still references the type** (operator must reassign or delete those assets first). Writes one `asset_type.deleted` Event.
- `GET    /asset-types/match-schema`            *(read)* — `{ fields, ops, contexts, condition, authoritativeSources }`: the matching vocabulary plus the catalogue of paths rules CANNOT reach. **`condition` is the condition-builder catalog** (`matchConditionMeta()` — fields with labels + ops, group operators, operator labels, depth/leaf caps) in the SAME shape `scopeConditionMeta()` publishes for the automations device filter, so the shared `PolarisConditionBuilder` consumes it unchanged and the Device Types card carries no field or operator list of its own (Fortinet controller CMDB, vCenter inventory, Azure Arc, an operator's own edit), each with the reason it outranks them. Its own route, declared before `/:id`, so the Device Types card renders the server's list rather than a second copy that drifts — the `/assets/pin-filter-schema` precedent.
- `POST   /asset-types/match-preview`           *(read)* — Dry run. Body `{ draft? }`; with a draft (`{name, matchRules, matchContexts, matchPriority}`) the unsaved edit is substituted INTO the live registry rather than evaluated alone, since a clause only matters relative to the types that outrank it. Answers `{ examined, matched, byType[], sample[], truncated }` over the assets currently typed **`other`** — the same eligibility the discovery engine applies — with each sample row naming the clause that claimed it. Read-level: it writes nothing.
- `POST   /asset-types/match-apply`             *(write)* — The retroactive step, deliberately separate from saving a rule (a rule edit is cheap to undo, a fleet-wide re-type is not). Re-types the `other` assets the saved rules claim; answers `{ updated, byType[] }` and writes one `asset_type.rules_applied` Event when anything moved.

### Manufacturer Aliases — `requireAdmin`
- `GET    /manufacturer-aliases`                — List every alias row (`{ id, alias, canonical, createdAt, updatedAt }`).
- `POST   /manufacturer-aliases`                — Create. Body: `{ alias, canonical }`. `alias` is normalized to lowercase + trimmed before insert; uniqueness on the lowercased form. 409 on duplicate. Saving refreshes the in-memory cache and runs `applyAliasesToExistingRows()` in the background so existing Asset/MibFile rows pick up the new mapping.
- `PUT    /manufacturer-aliases/:id`            — Update. Either or both of `alias` / `canonical` can be supplied. Same cache-refresh + backfill on save.
- `DELETE /manufacturer-aliases/:id`            — Remove. Cache is refreshed; existing rows are not rewritten (they already hold the canonical value).

### Monitor Settings — mixed scoping
Reads open to any authenticated caller (the asset edit modal's tier-badge UI needs them); writes require **assetsadmin** (admin also passes). All writes invalidate the in-memory resolver cache for the relevant scope and emit one `monitor_settings.{manual|integration|class_override}.{updated|created|deleted}` audit Event. See the **Monitor Settings Hierarchy** section below for the resolution model.
- `GET    /monitor-settings/manual`              *(auth)* — Manual tier (settings for orphan assets — `discoveredByIntegrationId = null`). Returns the saved JSON or `null` when unseeded.
- `PUT    /monitor-settings/manual`              *(assetsadmin)* — Replace the manual tier with the full tier-3 block: `{ intervalSeconds (1..86400), failureThreshold (1..100), probeTimeoutMs (100..60000), telemetryTimeoutMs (1000..120000, optional), systemInfoTimeoutMs (1000..120000, optional), telemetryIntervalSeconds (15..86400), systemInfoIntervalSeconds (60..86400), sampleRetentionDays (0..3650), telemetryRetentionDays (0..3650), systemInfoRetentionDays (0..3650) }`. `telemetryTimeoutMs` / `systemInfoTimeoutMs` are optional/nullable so existing call sites that didn't supply them keep working — null falls through to the hardcoded floor (10000ms each).
- `GET    /monitor-settings/integration/:id`     *(auth)* — Integration tier (settings stored at `Integration.config.monitorSettings`). Returns `{ integrationId, integrationName, integrationType, settings: TierSettings | null }`.
- `PUT    /monitor-settings/integration/:id`     *(assetsadmin)* — Same body shape as the manual tier. Writes the JSON into `Integration.config.monitorSettings` without clobbering other config keys.
- `GET    /monitor-settings/class-overrides`     *(auth)* — List class overrides. Filterable by `?integrationId=` (use the URL sentinel `null` for the manual-tier scope) and `?assetType=`. Each row carries the joined integration `{ id, name, type }`.
- `POST   /monitor-settings/class-overrides`     *(assetsadmin)* — Create. Body: `{ integrationId: uuid | null, assetType, ...partialTierSettings }`. Every settings field is optional — null means inherit from below. 409 if a row already exists for `(integrationId, assetType)`. 400 if `integrationId` is non-null but doesn't reference a real integration.
- `PUT    /monitor-settings/class-overrides/:id` *(assetsadmin)* — Update. Body accepts any subset of the 8 settings fields; each null clears that field (= inherit from below).
- `DELETE /monitor-settings/class-overrides/:id` *(assetsadmin)* — Remove the row.
- `GET    /monitor-settings/asset-overrides`     *(auth)* — Reverse lookup. Returns assets that have at least one of `monitorIntervalSec` / `cpuMemoryIntervalSec` / `temperatureIntervalSec` / `systemInfoIntervalSec` / `probeTimeoutMs` / `cpuMemoryTimeoutMs` / `temperatureTimeoutMs` / `systemInfoTimeoutMs` set OR any per-stream polling column non-null, filterable by `?integrationId=` (URL sentinel `null` = manual scope) and `?assetType=`. Capped at 500 rows. Drives the asset edit modal's "Show other asset overrides under this scope" slide-over.

#### Monitor Settings Hierarchy

Resolution order, most-specific first:

```
asset override  →  (assetType + manual) class override (manual scope only — Phase 2)
                →  per-class streams block on integration  (when discoveredByIntegrationId is set)
                                      Integration.config.<klass>Monitor.streams.<stream>:
                                        - fortimanager / fortigate: fortigateMonitor (assetType=firewall) /
                                          fortiswitchMonitor (assetType=switch) /
                                          fortiapMonitor (assetType=access_point)
                                        - activedirectory / entraid / windowsserver:
                                          workstationMonitor (assetType=workstation) /
                                          serverMonitor (assetType=server)
                →  integration tier   (when discoveredByIntegrationId is set; flat
                                       Integration.config.monitorSettings — used by endpoint
                                       asset types not covered by a per-class subtab set)
                →  systemInfoIntervalSeconds ONLY: derive from integration.pollInterval × 3600
                                      (when discoveredByIntegrationId is set AND tier-3 left it null AND
                                       the per-class streams block didn't set interfaces.intervalSeconds)
                →  manual tier        (when discoveredByIntegrationId is null)
                →  hardcoded floor    (final fallback; never user-visible)
```

- **Tier-1 / per-asset** — columns on `Asset`: `monitorIntervalSec`, `cpuMemoryIntervalSec`, `temperatureIntervalSec`, `systemInfoIntervalSec`, `lldpIntervalSec` *(Phase 2)*, `storageIntervalSec` *(Phase 2)*, `probeTimeoutMs`, `cpuMemoryTimeoutMs`, `temperatureTimeoutMs`, `systemInfoTimeoutMs`. null = inherit. These cadence/timeout fields are the ONLY settings that cascade to the per-asset tier; `failureThreshold` and the three retentions stop at tier-2. CPU/memory and temperature each carry their own per-stream column set as of Slice 2; LLDP and Storage gained their own per-asset cadence columns in Phase 2 alongside the queue carve-out.
- **Tier-2 / class override** — `MonitorClassOverride` row keyed on `(integrationId, assetType)`. **As of Phase 2 this table is manual-scope only** (`integrationId IS NULL`). The `POST` and `PUT` routes reject integration-scoped writes outright with 400; the `migrateMonitorSettingsPerClass` startup job folds historical integration-scoped rows into the per-class streams blocks on each integration and deletes them in the same transaction. Every settings field is nullable; null = inherit. Includes its own `cpuMemoryTimeoutMs` / `temperatureTimeoutMs` / `systemInfoTimeoutMs` alongside `probeTimeoutMs`.
- **Tier-3a / per-class streams (Phase 2 — integration-discovered assets only)** — `Integration.config.<klass>Monitor.streams.<stream>` where the class block is picked by `Asset.assetType`. Per integration type:
  - `fortimanager` / `fortigate` → `fortigateMonitor` (firewall) / `fortiswitchMonitor` (switch) / `fortiapMonitor` (access_point). FortiAP omits storage.
  - `activedirectory` / `entraid` / `windowsserver` → `workstationMonitor` (workstation) / `serverMonitor` (server).
  Each stream cell carries `{polling, credentialId, intervalSeconds, timeoutMs, mibId, failureThreshold?}` — `failureThreshold` only applies on `responseTime`; the resolver ignores it elsewhere. Null on any cell falls through to the flat tier-3 baseline below. Endpoint asset types (printer / router / other / etc.) discovered via FortiGate DHCP or AD/Entra/WinSrv that don't fall into a per-class subtab set bypass this tier entirely and use the flat baseline directly. See `pickClassStreamsBlock` + `applyClassStreamsOverlay` in `monitoringService.ts`.
- **Tier-3b / integration flat baseline or manual** — full tier-settings block (cadence/retention/threshold + the three timeout fields + the Phase 2 LLDP / Storage cadence + timeout fields), complete (no nulls) **except `systemInfoIntervalSeconds` at the integration tier**, which is nullable. Stored at `Integration.config.monitorSettings` for integration-discovered assets, or in the `manualMonitorSettings` Setting row for orphan assets. Existing tier-3 rows written before the LLDP / Storage tuning fields existed fall through to the hardcoded floor (10000ms timeouts, 600s LLDP+Storage interval) via the resolver's `tierFromJson` default until an operator saves new values.
- **Integration pollInterval linkage** (`systemInfoIntervalSeconds` only). When the integration tier doesn't explicitly set this field (operator left it blank, OR the migration job retroactively nulled the literal-default 600s), `loadIntegrationTierSettings` derives the cadence from `integration.pollInterval × 3600` so interface / LLDP / storage / IPsec scrape on the same schedule discovery already runs (1–24h pollInterval → 3600–86400s systemInfo). Ties the heavy-cadence work to a knob operators already understand and cuts interface-sample volume by 24× at the default 4h pollInterval. Explicit per-asset / class / integration-tier values still win. Tracked in `tierSystemInfoFromPollIntervalCache` (parallel to `tierCache`); `resolveMonitorSettingsWithProvenance` reads it to label the provenance `"integrationPollInterval"` so the integration edit modal's Cadence & Retention input renders `Leave blank to follow this integration's discovery interval (currently 4h)`. Manual-tier orphan assets are not eligible (no integration to inherit from) and fall through to the hardcoded floor. Existing 600s defaults are nulled retroactively by the `migrateSystemInfoCadenceLinkage` startup job. The `/assets/:id/effective-monitor-settings` response includes `integration: { id, name, type, pollInterval }` so frontend hints can be rendered without a second round-trip.
- **Hardcoded floor** — values baked into `monitoringService.ts` (60s probe, 60s telemetry, 600s sysinfo, 5000ms probe timeout, 10000ms telemetry timeout, 10000ms system-info timeout, threshold 3, 30d retentions). Final fallback only used when the migration job hasn't seeded tier-3 yet AND the legacy `monitorSettings` Setting row is also gone.

`resolveMonitorSettings(asset)` (in `src/services/monitoringService.ts`) walks the four tiers and returns the effective values. `resolveMonitorSettingsWithProvenance(asset)` returns the same plus per-field `provenance: "asset" | "class" | "integration" | "integration-class" | "manual" | "integrationPollInterval" | "default"` labels and the `classOverrideId` for UI deep-links. **Both derive from one core (`resolveMonitorSettingsCore`, 2026-08 fold)**, so the UI payload is by construction the runtime resolution — polling values are compatibility-gated at every tier with source-default substitution, and `"default"` labels a polling field where no tier supplied a compatible method (the resolved value carries the materialized source default, which may be null when the stream isn't delivered for the source kind). The UI-only extras (per-class origin sub-labels, `classOverrideId`, the pollInterval sub-label) live in the provenance wrapper so the plain resolver stays hot-path cheap. `"integration-class"` (Phase 2 — sub-label of the integration tier) means the value came from the per-class streams block `<klass>Monitor.streams.<stream>` rather than the flat `monitorSettings` baseline, so the asset modal's tier badge reads "FortiSwitch subtab" instead of generic "FortiManager". `"integrationPollInterval"` is a `systemInfoIntervalSeconds`-only sub-label indicating the value was derived from the integration's discovery `pollInterval` rather than read from explicit tier-3 JSON. **Resolver cache key is now `${integrationId}:${assetType}`** (Phase 2 — was previously `${integrationId}`); each per-class branch gets its own cached snapshot. Write paths (the tier CRUD in `monitorSettingsService.ts`, the integration config save) call `invalidateMonitorSettingsCache({integrationId, assetType?})` after every write — when `assetType` is omitted (integration config save), every `${integrationId}:*` entry is walked and dropped.

There is **no probe backoff for confirmed-down hosts, and no acceleration mid-run either**. Down assets keep probing at the resolved `intervalSeconds`, and so does an asset whose failure/recovery run is still being confirmed -- so `down` is reached after `failureThreshold x intervalSeconds`. (The fast-confirm re-probe that shortened that to ~35s regardless of cadence was removed 2026-08-19; `fastConfirmIntervalSec` survives as a dormant column read by nothing, and in-run resolution is now the ICMP loss sampler's job, feeding packet loss only -- business rule 30.) Heavy cadences (telemetry / systemInfo / fastFiltered) are still suppressed while `monitorStatus = "down"` so a wedged peer doesn't burn worker time, but the cheap response-time probe keeps firing — recovery is detected within one base-cadence tick instead of up to 30 minutes.

│   │   ├── pollingCapability.ts    # Does a COLLECTOR EXIST for this (source, stream, method)? Deliberately separate from pollingCompatibility.ts, which answers the different question "is this method MEANINGFUL for this source". Every write validator checked the second and nothing checked the first, so a class of settings validated, persisted, resolved and then collected nothing — invisibly, because `runTelemetryFor` counts a `{supported:false}` stream as a SUCCESSFUL tick and the queue publishers drop the unimplemented transports before enqueueing. `collectorCapability(source, stream, method, {assetType})` returns `{implemented, reason}`; `assetType` matters only on the Fortinet REST paths (a managed FortiSwitch gets up/down only, a FortiAP additionally cpu/mem + temperature off the `wifi/managed_ap` row, a firewall everything but storage). Consumers WARN rather than refuse — a hard 400 would punish an operator re-saving a value they did not create — so `assertPollingCompatible` and `validateAssetUpdate` log, the UI stops OFFERING dead combinations (`_collectorExists` in public/js/integrations.js), and `jobs/auditPollingCapability.ts` names the already-stored ones. **This table is a claim about code elsewhere: flip an entry in the same commit that implements its collector.**
**Cross-transport streams — `processes` + `eventLog`** (migration `20260623000000_processes_eventlog_streams`). Two additional streams flow through the same hierarchy as the original six. They are **not agent-only** — `processes` resolves to agent / SNMP (`hrSWRunTable`/`hrSWRunPerfTable`) / SSH (`ps`,`tasklist`) / WinRM (`Get-Process`); `eventLog` resolves to agent / SSH (`journalctl`,`Get-WinEvent`) / WinRM / REST (FortiOS device log). The allowed method set per stream is enforced by `STREAM_METHODS` + `isMethodValidForStream` in `src/utils/pollingCompatibility.ts` (`processes` rejects REST + ICMP; `eventLog` rejects SNMP + ICMP), and `resolveStream` adopts a tier's method only when it passes BOTH the source matrix AND the stream matrix. Both default to **`disabled`** for every source (`defaultPollingForSource`) — opt-in. Columns mirror the storage stream on `Asset` + `MonitorClassOverride`: `processesPolling`/`eventLogPolling`, `processesIntervalSec(onds)`/`eventLogIntervalSec(onds)`, `processesTimeoutMs`/`eventLogTimeoutMs`, `processesCredentialId`/`eventLogCredentialId`, `processesMibId` (eventLog has no MIB). The integration Monitoring tab renders **Processes** + **Event Log** stream subtabs next to Storage (`_ALL_STREAMS` in `public/js/integrations.js`); `_streamsForClass` scopes them — workstation/server get both, FortiGate gets eventLog only, FortiSwitch/FortiAP get neither. Per-transport collectors land in later phases; the foundational layer is the configuration surface + resolution only.

#### Where each tier is edited

- **Tier-3 integration (Phase 2 per-class)** — each integration's edit modal has a **Monitoring tab** with **per-class subtabs** (FMG / FortiGate: FortiGate / FortiSwitch / FortiAP; AD / Entra ID / Windows Server: Workstations / Servers). Each class subtab carries the six per-stream subtabs (Response Time / CPU/Memory / Temperature / Interfaces / LLDP / Storage; FortiAP omits Storage). Each per-stream subtab holds the polling method, credential, cadence, timeout, and (response-time only) failure threshold. Save Changes serializes each class's stream values into `Integration.config.<klass>Monitor.streams.<stream>` via the regular integration PUT; the flat `monitorSettings` JSON is still written from the FortiGate / Workstations subtab as the "default for endpoint asset types" fallback.
- **Tier-3 manual** — Assets page header → **Monitoring Settings** button → modal's **Manual Monitoring** section. Same per-stream layout. Used by orphan / manually-created assets. Writes via `PUT /api/v1/monitor-settings/manual`.
- **Tier-2 class overrides (manual scope only — Phase 2)** — Assets-page **Monitoring Settings** modal → **Class Overrides** section. The source picker no longer surfaces integrations; the section is labelled "Manual scope only — assets without an integration source." Backend `POST` / `PUT` reject integration-scoped rows with 400. Operators who used to add overrides scoped to a specific integration now use that integration's per-class subtabs (above) which deliver the same effect via the streams block instead of the override table.
- **Tier-1 per-asset** — the asset edit modal's **Monitoring tab** carries the cadence/timeout overrides (`monitorIntervalSec`, `probeTimeoutMs`, plus the per-asset `cpuMemoryIntervalSec` / `temperatureIntervalSec` / `systemInfoIntervalSec` columns), tier-source badges from `/effective-monitor-settings`, and a **Show other asset overrides under this scope** button that opens a slide-over listing peer assets with their own per-asset overrides.

The integration's Monitoring tab additionally carries a **Discovery Defaults** section on FMG/FortiGate types only, with three subtabs (FortiGates / FortiSwitches / FortiAPs). Each subtab holds discovery-time concerns: `addAsMonitored`, `snmpCredentialId`, `sshCredentialId`, `autoMonitorInterfaces`. **Cadence inputs are no longer in these subtabs** — they live in the Cadence & Retention section above and apply uniformly across the integration's entire fleet. The credential rows are **type-aware**: the SNMP picker is rendered only when at least one of the four integration-tier polling dropdowns is set to SNMP, the SSH picker only when at least one is set to SSH, and both stay hidden when neither is selected. Credentials persist regardless of visibility, so flipping back later restores the prior selection.

### Conflicts — `requireAuth` (role-scoped list + resolve)
- `GET    /conflicts`                           — List. Gated on `discoveryConflicts:read` — any holder sees both entity types (the historical networkadmin↔reservation / assetsadmin↔asset role-name split was dropped 2026-08); others see an empty list.
- `GET    /conflicts/count`                     — Badge count; same role scoping as the list.
- `POST   /conflicts/:id/accept`                — Reservation: apply discovered values. Asset: upsert an `AssetSource` row (`sourceKind` = `entra`/`ad`, `externalId` = `proposedDeviceId`) tying the existing asset to the proposed Entra/AD identity, plus overlay Entra/AD fields into empty existing fields. **Hostname has one extra rule:** when the conflict was raised via 15-char NetBIOS truncation (`proposedAssetFields.matchedVia === "netbios"`), the longer canonical hostname replaces the truncated one even when the existing field is non-empty — the truncated form is a NetBIOS quirk, not a deliberate choice. **Phase 4d retired the legacy `assetTag = entra:<id>` / `ad:<guid>` write** — the AssetSource row is now the canonical identity link, and audit trail is captured by the auto-resolve syncLog event. (`prev-*` breadcrumb tags are still written pending conflict-resolution refactor.) **Ghost-sibling lookup** (when a different asset already owns the proposed source's externalId) now queries `AssetSource` by `(sourceKind, externalId)` instead of by `assetTag` — the ghost's non-empty fields are absorbed and the ghost is deleted so the unique-constraint upsert lands cleanly. 403 if caller's role doesn't cover this conflict's entityType.
- `POST   /conflicts/:id/reject`                — Reservation: keep existing, dismiss. Asset: create a separate new Asset for the Entra/AD snapshot, then upsert its `AssetSource` row (`sourceKind` = `entra`/`ad`, `externalId` = `proposedDeviceId`) so the next discovery run finds the new asset by source and doesn't re-fire the collision.
- `GET    /conflicts/:id/chassis-diff`          *(discoveryConflicts:read)* — the per-address diff behind a `chassis-replaced` subnet conflict (business rule 41): the archived old chassis's reservations against the live subnet's, as `{ payload, lines[] }`. Each line carries `ip`, `verdict` (`only-old` | `only-new` | `differs` | `same`), both sides, and `migratable` — false with `notMigratableReason: "device-owned"` for `vip` / `interface_ip` rows, whose truth is the new gate's own config. A separate READ rather than a field on the conflict row, because discovery syncs subnets in Phase 1 and reservations in Phases 3–5, so a payload built at detection time would compare the old chassis against itself. 400 when the conflict isn't a subnet variant; 409 when it is already resolved (`loadPendingConflict`).
- `POST   /conflicts/:id/migrate-reservations`  *(chained: `discoveryConflicts:write` AND `reservations:write`)* — **Subnet chassis conflicts only.** Body `{ ips: [...], adopt?: boolean }`. Carries the named addresses' OLD (archived) reservations onto the live subnet: an `only-old` address is CREATED, a `same`/`differs` address UPDATES the live row in place (which is what `@@unique([subnetId, ipAddress, status])` requires — an insert would violate it). Only `manual` and `dhcp_reservation` lines are eligible (`MIGRATABLE_SOURCE_TYPES`); the rest are skipped with a per-address reason (`device-owned` / `observed` / `device-managed` / `not-in-archive`). Every migrated row lands `sourceType: "manual"` + `dhcpBinding: null` and, where the integration's DHCP push is on, QUEUED (`pushStatus: "pending"` + `pushQueuedAt`, with the dead chassis's `pushedScopeId`/`pushedEntryId`/`pushedToId` null) for `retryQueuedReservationPushes` to send — never pushed inline, since a freshly-installed gate is the device most likely to be briefly unreachable. Does NOT close the conflict (an operator migrates in passes); `adopt: true` additionally runs the normal accept in the same round trip. ONE `subnet.chassis.reservations_migrated` Event per batch naming every migrated and skipped address. Returns `{ ok, created, updated, queuedForPush, skipped[], adopted }`. Chained gate per the `/reassign-ip` precedent — resolving a queue entry and creating reservations are separable grants. Business rule 41.
- `POST   /conflicts/:id/merge`                 — **Asset conflicts only.** TWO bodies, dispatched on the conflict's flavour. **duplicate-IP and duplicate-serial** (business rule 83's record flavour takes the same body, the same chained gate and the same engine): `{ survivorAssetId, absorbAssetIds: [...] }` — the records are one device recorded twice, so the named members are absorbed into the survivor via `assetMergeService.mergeAssets` (sources / MACs / IP history / sightings / agent enrolment / dependency edges move, monitoring OR-carries, the absorbed rows are deleted) and the conflict closes as `accepted` once fewer than two current claims remain — a three-way collision stays open on the survivors. **CHAINED gate: `discoveryConflicts:write` AND `assets:fullwrite`** (it deletes inventory — the destructive tier `POST /assets/:id/merge` moved onto in 2026-09; this line said `write` until business rule 83 shipped the second merge flavour and the two were read side by side). Refusals mirror `/reassign-ip`: 400 on a survivor or target that isn't one of the claimants, or on an empty target list (the survivor is silently dropped from its own list rather than self-merging); the pure `resolveMergeTargets` owns those rules. Writes one `asset.merged` Event per absorb plus the `conflict.accepted` close. Response `{ ok, ipAddress, survivorAssetId, absorbedAssetIds, movedSources, resolved, remaining }`. **Every other flavour**: per-field merge with operator-chosen winners. Body: `{ fieldWinners: { hostname?: "existing"|"proposed", serialNumber?, macAddress?, manufacturer?, model?, os?, osVersion?, assignedTo? } }`. Fields not present in `fieldWinners` fall back to the default accept logic (blank-fill for serial/mac/manufacturer/model/assignedTo, always-overwrite for os/osVersion, NetBIOS-upgrade rule for hostname). AssetSource stamping and ghost-asset absorption are unconditional regardless of selections. Reservation conflicts return 400 — they use the regular accept path. Audit Event message appends the selection map when used.
- `POST   /conflicts/:id/reassign-ip`           — **Duplicate-IP conflicts only** (`proposedAssetFields.collisionReason="duplicate-ip"`). Body: `{ assetId, ipAddress }` — give ONE of the assets sharing the address a different one. **CHAINED gate: `discoveryConflicts:write` AND `assets:write`** (the `/network-scans/:id/adopt` precedent — resolving queue entries and editing inventory are separable grants). Writes `ipAddress` + `ipOverride` + `ipSource="manual"` in one update (operator-pin semantics identical to typing an address in the asset edit form, so the `src/db.ts` override guard defers and a later discovery write reporting the same address releases the pin by itself), closes the asset’s pending ip-override conflict, and stamps an `asset.updated` Event with the field changes. Refusals: 400 on a non-duplicate-IP conflict / an assetId that isn’t one of the claimants / an invalid or unchanged address, 404 on a missing asset, **409 when another network-present asset already records the target address** (that moves the duplicate instead of resolving it). Response `{ ok, ipAddress, newIpAddress, assetId, resolved, remaining }` — the conflict closes as `accepted` when fewer than two current claims remain, otherwise it stays open on the survivors (a three-way collision takes two reassignments). Delegates to `reassignDuplicateIpAsset` in services/duplicateIpConflictService.ts.

**Asset-conflict flavours.** `proposedAssetFields.collisionReason` distinguishes the pathways that raise an asset conflict. The two discovery-sync collision flavours, in decreasing order of confidence:
- `"untagged-collision"` — incoming Entra/AD/vCenter device's hostname matches an existing asset that has no source tag (DHCP-discovered, manually created, etc.). vCenter raises this flavour for both VMs and ESXi hosts (`proposedAssetFields.sourceType="vcenter"`, `assetType` discriminating VM vs host).
- `"duplicate-registration"` — incoming hostname matches an existing asset already tagged by the same source with a *different* deviceId/objectGUID (Entra returned two distinct deviceIds for the same display name — re-enrol, re-image, dual-boot — or AD has two `objectGUID`s for what looks like the same physical computer). Accepting re-keys the existing asset's source row to the incoming externalId (the prior identity is captured in the auto-resolve syncLog Event for audit).

A `bothAssetsExist: true` flag on `proposedAssetFields` marks the **sibling** sub-case of `"untagged-collision"`: the incoming device *already* has its own Polaris asset, and a second, un-linked asset shares its hostname. Raised by the Entra and vCenter (VM + host) sibling checks. It exists to route duplicate-asset cleanup through the Conflicts queue (Apply merge) rather than the asset-details Sources → Merge search. Accept runs the normal ghost-absorb (collision-target survives, the source-owning duplicate is absorbed + deleted); reject creates nothing — `rejectAssetConflict` short-circuits when the proposed `(sourceKind, externalId)` already owns an asset.

**The absorb preserves the duplicate's provenance.** The ghost here is a real multi-source asset, not a placeholder — it routinely holds discovery sources the collision target knows nothing about. So the absorb runs inside ONE transaction that calls the shared `absorbAssetRelations` (from `assetMergeService`) FIRST: every `AssetSource` row plus `AssetMacAddress` / `AssetAssociatedIp` / `AssetIpHistory` / `AssetFortigateSighting` (delete-on-conflict, survivor's row wins) and the `ManagedAgent` enrollment when the survivor has none are re-bound onto the survivor — plus the dependency edges via `transferDependencyEdges` (dependents re-pointed; the ghost's own parent links blank-fill, survivor's win when both sides have some — this path passes no `dependencyWinner`) — *then* the merged field update is applied and *then* the ghost is deleted — so the delete cascade can no longer take them. `resolveMonitoringCarry` OR-s `monitored` across the two rows the same way the operator merge does (adopting the ghost's polling methods / credentials / MIB pins / cadences and unioning its pin arrays when the flip turns the survivor ON, resetting monitor state, recomputing `monitorOverride`, business rule 10 respected), and the blank-fill absorb covers `ipAddress` / `dnsName` / `learnedLocation` / `lastSeenSwitch` / `lastSeenAp` / `snmpLocation` / `learnedAddress` / `department` / `location` / `purchaseOrder` / `acquiredAt` / `warrantyExpiry` / `assetType` (only from `"other"`) on top of the original serial/MAC/manufacturer/model/assignedTo/notes set, keeps the more-recent `lastSeen` through `bumpLastSeen` (rule 12 still applies to the absorbed evidence), and unions the ghost's tags. *Before this fix the ghost delete cascaded its `AssetSource` rows*: merging an AD-only target with a ghost carrying entra + intune + fortigate-endpoint + vcenter-vm left the survivor holding only `ad` plus a thin `vcenter-vm` row re-created from the conflict snapshot — the UI promised the assets would be "combined" while three sources' provenance was destroyed. The `conflict.accepted` Event now itemizes what was carried over. Whatever is NOT re-bound still cascades with the ghost (LLDP / wireless / interface overrides / its own pending conflicts) and its sample hypertable rows orphan and age out — identical to the operator merge. The events.js card swaps in duplicate-asset copy + a "Duplicate assets" badge.

Two further flavours are not hostname collisions at all:
- `"ip-override"` — a discovery write staged an IP that differs from the asset's operator IP pin (`Asset.ipOverride`); raised by `ipOverrideService` after the db.ts guard re-asserted the pin. Carries `proposedAssetFields = { collisionReason, ipAddress: <discovered>, ipSource, overrideIp, hostname }` and no `proposedDeviceId` / AssetSource identity. One pending conflict per asset (refreshed while open; a rejected row suppresses re-raising the same discovered IP). Accept adopts the discovered IP + releases the pin (`ipAddress`+`ipOverride`+`ipSource` in one write so the guard defers); reject keeps the pin, event-only. `/merge` on this flavour degenerates to accept. Renders as a single-row Accept/Reject card in events.js (no per-field picker).
- `"duplicate-ip"` — two or more **network-present** assets (status NOT in `UNMONITORABLE_STATUSES`) record the SAME `Asset.ipAddress`, **at least one of them a type whose address was chosen** (`CONFLICT_ELIGIBLE_ASSET_TYPES` — switch / access_point / firewall / server; endpoint-only collisions are DHCP working and never raise, while an endpoint colliding with infrastructure raises and appears as a claimant); raised by the `detectDuplicateIpAssets` sweep (business rule 40). Carries `proposedAssetFields = { collisionReason, ipAddress, hostname, members: [{ assetId, hostname, assetType, status, monitored, macAddress, ipSource, pinned, lastSeen, ipLastSeen }] }` and no `proposedDeviceId`. **One pending conflict per ADDRESS, not per pair** (a three-way collision is one card), `assetId` points at the lowest-id member so refreshes don’t churn the FK. A member only counts while its claim on the address is CURRENT (operator-owned, or re-asserted within `CLAIM_FRESH_DAYS`), and rows sharing one non-null MAC count as ONE device — a stale DHCP leftover and a device recorded twice are both not address conflicts. **Accept is refused** (nothing to adopt); the two resolution verbs are `POST /conflicts/:id/reassign-ip` (two devices — move one) and `POST /conflicts/:id/merge` with `{ survivorAssetId, absorbAssetIds }` (one device recorded twice — absorb the duplicates), and reject dismisses (the same member set won’t re-raise, a changed one will). Auto-closes as `rejected` by `system:auto-resolved` once the duplicate is gone. Renders as a per-member table with an inline "new IP address" field in events.js (`renderDuplicateIpConflictCard`).

- `"serial-two-controllers"` — ONE managed device (FortiSwitch / FortiAP) whose serial is on the managed roster of TWO controller FortiGates at once, so whichever integration ran discovery last owns its record; raised by the `detectSerialConflicts` sweep (business rule 83) from the `AssetControllerClaim` rows discovery re-asserts per pass — `AssetSource` structurally cannot hold that evidence, its `(sourceKind, externalId)` key being the DEVICE serial. Carries `proposedAssetFields = { collisionReason, deviceSerial, hostname, assetType, sourceKind, claimants: [{ controllerKey, controllerDevice, controllerSerial, controllerAssetId, integrationId, integrationName, firstSeen, lastSeen }] }` and no `proposedDeviceId`; `assetId` is the contested DEVICE. Claimants are folded onto the firewall asset they resolve to before counting, so an HA cluster (and a gate re-registered under a second FMG device entry) is ONE claimant. **REPORT-ONLY**: accept is refused AND there is no resolution verb — whether this is a completed rehome or a stale roster entry is a fact about the gates' configuration, so the fix is there; reject dismisses (dedup on the CLAIMANT set). Auto-closes as `rejected` by `system:auto-resolved` once a claim goes unrenewed past `CLAIM_FRESH_DAYS` (2), which is how a completed move closes its own card. Renders as a per-controller table in events.js (`renderSerialClaimConflictCard`), leading with the gate that spoke last.
- `"duplicate-serial"` — two or more Asset rows carry the same serial number, i.e. one device recorded twice; same sweep, same rule. Carries `proposedAssetFields = { collisionReason, serialNumber, hostname, members: [{ assetId, hostname, assetType, status, ipAddress, macAddress, lastSeen, discoveredByIntegrationId }] }`, one pending conflict per SERIAL, `assetId` the lowest-id member. Placeholder serials (SMBIOS defaults, < 4 chars, a single repeated character) and groups larger than `MAX_PLAUSIBLE_DUPLICATES` (8) never raise — past that count the serial is the suspect. **Accept is refused**; the verb is `POST /conflicts/:id/merge` with `{ survivorAssetId, absorbAssetIds }` (**chained `assets:fullwrite`**, the same body and engine as the duplicate-IP merge), and reject dismisses (dedup on the member set). Renders as `renderDuplicateSerialConflictCard`.

**`entityType="subnet"` — the third entity (business rule 41).** Payload on its own `proposedSubnetFields` column, since the asset variants' `proposedAssetFields` would be a lie about what it holds.
- `"chassis-replaced"` — the FortiGate serving a subnet answered with a serial that is neither the stored `Subnet.fortigateSerial` nor any member of that device's HA cluster, so the physical box was swapped; raised from discovery Phase 1 by `subnetChassisConflictService` AFTER `snapshotSubnet` copies the old chassis's subnet + reservations into the archive, so raising destroys nothing. Carries `proposedSubnetFields = { collisionReason, cidr, blockId, oldSerial, newSerial, oldDeviceName, newDeviceName, archivedSubnetId }`. Dedup is keyed on the (old, new) serial PAIR, not the subnet, so a rejected row suppresses exactly that transition while a box swapped twice raises anew. Accept stamps the new serial onto the subnet (after which the next run reads `same`); reject dismisses. The per-address diff is a SEPARATE read (`GET /conflicts/:id/chassis-diff`) because Phase 1 syncs subnets while Phases 3–5 write reservations — a snapshotted payload would compare the old chassis against itself — and migration (`POST /conflicts/:id/migrate-reservations`) carries chosen `manual` / `dhcp_reservation` lines onto the new gate, creating an `only-old` address and UPDATING a colliding one in place. Renders in events.js as `renderSubnetConflictCard` (old-vs-new identity table, Dismiss / Review reservations / Adopt new chassis) with the diff loaded on demand into `renderChassisDiffPanel` — a per-address checklist whose refused lines show WHY (`device-owned` / `observed` / `device-managed`) rather than being hidden.

`proposedAssetFields.matchedVia` indicates the matching mechanism: `"exact"` (full hostname equality) or `"netbios"` (matched only after truncating one side to 15 chars). NetBIOS-truncation matching pairs an AD `cn`-derived 15-char hostname with the full Entra `displayName` and vice versa, so neither side missing the FQDN-aware rename causes a phantom split.

**Note:** The legacy `"mac-collision"` flavour (Entra-only, raised when the incoming Intune Ethernet MAC matched a MAC ever recorded on another asset) was retired — the Entra sync now treats Ethernet MAC as a positive identity-match signal and silently cross-links, the same way SID does for hybrid-joined devices. See "Hybrid-join cross-link" below for the cascade. Existing `mac-collision` conflict rows in production databases keep rendering through the events.js compatibility branch; no new ones are created.

### Search — `requireAuth`
- `GET    /search?q=<query>`                    — Global typeahead. Classifies input (IP, CIDR, MAC, or text), runs parallel entity queries, returns grouped results (`blocks`, `subnets`, `reservations`, `assets`, `ips`, `sites`) capped at 8 per group. **Multi-term matching**: the (post-scope-strip) query is tokenized by `parseSearchTerms` on whitespace, with double-quoted runs kept whole (`"acme plant" metro` → `["acme plant", "metro"]`, dangling-quote-tolerant); the terms are **AND-combined** so every term must match at least one searched column/pathway for a row to surface (per entity: an `AND: [{ OR: [cols…] }, …]` clause). IP / CIDR / MAC classification (plus the exact-match boosts + MAC normalization) only applies when the operator typed exactly **one** term — a multi-term query is always a plain "match all of these" text search. A single term collapses the AND to one element, preserving pre-multi-term behavior exactly. In `runAssetSearch` the JSON-blob raw scan AND-combines each term's ILIKE within a single blob (first + last name must both appear in the same `associatedUsers` / `observed` value); the side-table pathways (`AssetSource.externalId`, `AssetMacAddress.mac`, `AssetAssociatedIp.ip`, `AssetIpHistory.ip`) likewise require all terms in their single field, so cross-pathway AND (term A in hostname, term B in a side-table MAC) is not matched by design. **Asset search reach** spans direct Asset columns (`hostname` / `dnsName` / `assetTag` / `serialNumber` / `ipAddress` / `manufacturer` / `model` / `macAddress` / `assignedTo` / `department`), plus five parallel cross-search pathways merged into the same 8-row budget: `AssetSource.externalId` (Entra deviceId / AD objectGUID / FortiGate serial — accepts the `entra:` / `ad:` / `fgt:` / `intune:` / `fortiswitch:` / `fortiap:` prefix and strips it), `AssetMacAddress.mac` (full MAC history beyond the primary), `AssetAssociatedIp.ip` (secondary interface IPs the asset holds now), `AssetIpHistory.ip` (every IP the asset has held over time — incl. public WAN / since-rotated addresses), and a JSON-blob substring scan over `Asset.associatedUsers` + `AssetSource.observed` (logged-in users, on-prem SID, UPN, `onPremisesSecurityIdentifier`, etc.). The JSON scan is backed by GIN trigram indexes on both columns (migration `20260507200000_search_json_trgm_indexes`); queries shorter than 3 chars fall back to seq scans, but the 2-char minimum at `searchAll` keeps result sets tiny in that range. `sites` carries firewall assets that have lat/lng coordinates (i.e. pinned on the Device Map); these are queried separately with their own 8-row budget so the Device Map section always has a slot regardless of how many endpoints match. Pinned firewalls also ride along in `assets` (no SQL-level exclusion — `searchAssets` passes an empty baseFilter to `runAssetSearch`) so a search like "HARRIMAN-61F-1" shows the FortiGate in BOTH the Device Map section AND the Assets section; operators expecting to find the firewall under Assets find it there, while the dedicated Device Map slot guarantees a pan-to-marker entry point. The frontend dropdown labels the `sites` group "Device Map" and pan-to-marker on click via `window.polarisMapPanToAsset` (or navigates to `/map.html#site=<id>` from other pages). The `ips` hit resolves the containing subnet and any active reservation. **Scope-prefix shortcuts**: a query starting with `block:` / `b:`, `network:` / `n:`, `asset:` / `a:`, `reservation:` / `r:`, or `map:` / `m:` (case-insensitive, whitespace-tolerant) constrains the search to that one group AND lifts the per-group cap from 8 to `SCOPED_LIMIT=200`. Other groups return empty arrays in the scoped path. Min query length drops to 1 char after the prefix so `block:f` works. `results.query` echoes the original raw input (prefix included) for the desktop dropdown's stale-response check. Both surfaces show a hint panel when the search input is focused with no query yet: desktop `_showSearchShortcutHints` in `public/js/app.js` renders inline rows in the search dropdown; mobile `renderSearchEmpty` in `public/js/mobile/tabs.js` renders a 2×2 MD3 chip grid on the Search tab body (tapping the input from any tab routes to /search so the chips are visible before typing). **Page-aware section ordering**: when the operator is on `/map.html` the Device Map section is hoisted to the top of the dropdown; same logic for `/subnets.html` (Networks), `/assets.html` (Assets), `/blocks.html` (Blocks). **Per-group permission filtering**: each result group is gated on the read access of the function that owns it (`blocks`→ipBlocks, `subnets`→subnets, `reservations`→reservations, `assets`→assets, `sites`→deviceMap; `ips` needs subnets AND reservations since resolveIp reveals both) — denied groups come back empty and their query helpers never run, in both the scoped and unscoped paths (`searchAll(rawQuery, allowed?)`, default all-allowed). Bearer tokens have no role snapshot → every group empty. Covered by `tests/integration/permissionGates.test.ts`. Front-end edit modals render in view-only mode for users without write permission. **Monitor Status pill on asset/site hits**: `asset` and `site` hits carry `status: { kind, label }` — the same five-state monitor pill as the assets-table Status column (Unmonitored / Up / Warning / Down / Recovering / Pending, plus the Dependency Test and Dep. Down overlays, same precedence), computed server-side by `assetMonitorPillState` in `searchService.ts` (unit-tested in `tests/unit/assetMonitorPillState.test.ts`). The desktop dropdown maps `kind` onto the existing `.badge-monitor-*` classes and renders the pill after the hit title (`.gs-item-pill` shrinks it to dropdown scale).
