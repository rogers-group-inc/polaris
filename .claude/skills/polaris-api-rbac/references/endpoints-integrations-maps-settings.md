# Endpoints — integrations, maps, server settings, agents, MIBs, profiles, icons

Verbatim from ARCHITECTURE.md → API Endpoints. Gate notation: `key:level`.

### Integrations — `integrations` function key
> Mount requires `integrations=read`; all write endpoints inside the file are upgraded to `integrations=write` via an inline `router.use(...)`.
- `GET    /integrations`                       — List integrations (paginated). Each row carries `discoveryBaseline: { avgMs, sampleCount } | null` from `discoveryDurationService.getBaselines()` so the card UI can render an "Avg Discovery Time" line operators can size `pollInterval` against. `null` until the rolling window has ≥3 successful runs.
- `POST   /integrations`
- `GET    /integrations/:id`
- `PUT    /integrations/:id`
- `DELETE /integrations/:id`
- `POST   /integrations/:id/test`                — Test connection (also `POST /integrations/test` for unsaved config; `POST /integrations/:id/test/fortigate-sample` + `POST /integrations/test/fortigate-sample` for sample-pull dry runs)
- `POST   /integrations/:id/discover`           — Trigger full discovery run
- `GET    /integrations/discoveries`            — List in-flight discoveries. Each entry: `{ id, name, type, startedAt, elapsedMs, activeDevices: string[], slow: boolean, slowDevices: string[], totalDevices: number | null, completedCount: number, skippedOfflineCount: number, skippedErrorCount: number }`. `slow` flips true when the overall run exceeds its rolling-duration baseline; `slowDevices` lists FortiGates (FMG-only) whose per-device elapsed exceeds that device's baseline. The four progress counters power the sidebar's "N/M complete · K skipped (offline)" line for FMG runs: `totalDevices` is parsed from the `discover.devices` info-level message ("Found N managed device(s) …") and stays null until the roster is fetched; `completedCount` bumps on `discover.device.complete`; `skippedOfflineCount` on info-level `discover.device.skip` (conn_status mismatch — gate down or unmanaged); `skippedErrorCount` on error-level skips and per-device errors. Standalone FortiGate runs leave the counters at their initial values since there's one device. This endpoint also calls the slow-run checker inline, so the UI sees amber within one 4 s poll cycle. See `discoveryDurationService` + the `discoverySlowCheck` job. For FMG-type discoveries, `activeDevices` additionally has the integration name prepended whenever the per-integration FMG worker has any inflight calls (proxy or native), so the sidebar shows the FMG itself as busy during roster fetch + mgmt-IP resolves + native CMDB scrapes — not just during per-device work. In the sidebar popup each `activeDevices` name is clickable (`openDiscoveryDevice` in [public/js/app.js](public/js/app.js)): it resolves the FortiGate name to its firewall Asset by hostname and opens the asset slide-over (in place on `/assets.html`, else via the `#view=asset:` hash); a no-match — the transient FMG self-entry, or a not-yet-inventoried FortiGate — surfaces a toast.
- `GET    /integrations/health-summary`          — Sidebar polling target. Returns `{ failed: [{ id, name, type, lastTestAt }] }` listing enabled integrations whose latest connection test failed (`enabled=true AND lastTestOk=false`). Gated by `integrations=read`. Polled every 30 s by [public/js/app.js](public/js/app.js); rendered as a red sidebar notice (`#integration-failed-status`) that links to `/integrations.html` on click. Pairs with the [integrationConnectionTester](src/jobs/integrationConnectionTester.ts) background job which is the writer that keeps `lastTestOk` fresh.
- `DELETE /integrations/:id/discover`            — Abort an in-flight discovery. *(admin-equivalent: upgraded to `integrations=fullwrite` via an inline `requirePermission` guard — `networkadmin` with `write` can run discoveries but cannot abort them. The frontend hides the abort ✕ for callers below `fullwrite`.)*
- `POST   /integrations/:id/query`              — Manual API proxy. FortiManager: `{method, params}` (JSON-RPC) or `{mode:"fortigate", deviceName, method, path, query?, body?}` (REST direct to a managed FortiGate — FMG resolves the mgmt IP, the integration's direct-mode FortiGate API token authenticates). FortiGate: `{method, path, query?, body?}` (REST). Both REST forms take `method ∈ GET|POST|PUT|DELETE`; `body` is a JSON payload attached for POST/PUT only, and any non-GET writes a warning-level `integration.query.write` Event (ad-hoc device writes are audited, body included). **Both REST forms also accept an optional per-request credential override `{apiToken?, apiUser?}`** (`overrideFortigateCreds`): it swaps `apiToken`/`apiUser` for a standalone FortiGate, or `fortigateApiToken`/`fortigateApiUser` for an FMG in bypass mode — never the FMG's own `apiToken`, which is still needed to resolve the gate's management IP. Exists because bypass mode stores ONE FortiGate token for the whole fleet, so testing a different per-gate token otherwise means editing the integration and repointing discovery/polling/DHCP-push at an unproven credential. The override is used for that one request and persisted nowhere: not on the integration, not in the Event (which records only `usedTokenOverride: true`), and not in the browser's saved-query localStorage entry. A masked-placeholder value (`••••••••`) is rejected rather than sent as a token. It widens no privilege — the route already requires `integrations:write`, which can rewrite the stored token outright. Entra ID: `{path, query?}` GET-only against `graph.microsoft.com`; path must begin with `/v1.0/` or `/beta/`. Active Directory: `{filter?, baseDn?, scope?, attributes?, sizeLimit?}` LDAP search; baseDn defaults to the integration's configured base DN.
- `GET    /integrations/:id/interface-aggregate?class=fortigate|fortiswitch|fortiap|workstation|server` — Auto-Monitor Interfaces "By name" data source. **Served from `Integration.interfaceAggregateCache`** (`getCachedInterfaceAggregate`), the precomputed checklist refreshed at the end of every successful discovery run — so the modal loads instantly instead of running a fleet-wide DISTINCT ON over `asset_interface_samples` on every open. Returns `{ rows: [{ ifName, ifType, deviceCount }], computedAt }` (the heavy per-row `devices[]` list is dropped from the cache — the UI only renders the three fields + a device count), sorted by deviceCount desc. **Live-compute fallback**: when the cache has no entry for this class yet (the window before the integration's first post-feature discovery) the route falls back to `getInterfaceAggregate` and returns `computedAt: null`. The expensive aggregate (latest `AssetInterfaceSample` per `(assetId, ifName)` for assets where `discoveredByIntegrationId = :id` AND `assetType` matches the class, plus synthetic IPsec-tunnel rows for the fortigate class) now runs in the discovery process at end-of-run, not on the interactive web path. There is no operator "Refresh from latest discovery" button anymore — the list re-populates each discovery cycle and the modal shows an "As of last discovery: …" timestamp.
- `POST   /integrations/:id/interface-aggregate/preview` — Live preview for the modal. Body: `{ class, selection: AutoMonitorInterfacesSchema | null, baselineSelection?: AutoMonitorInterfacesSchema | null }`. Returns `{ deviceCount, interfaceCount, perDeviceMax, sampleDevices: [{hostname, pinNames: string[]}], diff? }`. Read-only: does not persist or write `monitoredInterfaces`. `interfaceCount` is the sum of pin lengths produced by `selection` alone (not unioned with operator-pinned interfaces). **`baselineSelection` is optional**: when supplied, the service computes pin sets for BOTH selections from a single DB fetch and returns a `diff: { addedCount, removedCount, addedSample: [{hostname, ifName}], removedSample: [{hostname, ifName}] }` block enumerating per-`(assetId, ifName)` adds/removes. Drives the "+X added · −Y removed" inline delta hint on the auto-monitor card; frontend tracks the previously-sent selection per-card and passes it as the baseline so each checkbox toggle's preview shows what THAT toggle just changed (not the delta from saved). First preview-after-modal-open uses the saved selection as baseline so it shows no diff; subsequent toggles each show their own per-click change. Older UI builds that don't send `baselineSelection` get the same response shape as before — no `diff` field. **As of the cache work, the frontend only calls this endpoint for `byLldp` selections** (topology isn't in the cache); `byNames` / `byPatterns` / `byTypes` previews are computed instantly client-side from the already-loaded `interfaceAggregateCache` rows (`computeClientPreview` in `public/js/integrations.js`) — exact for `byNames`, an upper bound for `byPatterns`/`byTypes` with `onlyUp` (the cache has no per-device `operStatus`), labeled as such. This endpoint stays the authority for the LLDP case and for the **Test against fleet** button.
- `POST   /integrations/:id/interface-aggregate/apply` — Apply-on-save trigger. Body: `{ class }`. Reads the current `selection` from `Integration.config.<klass>Monitor.autoMonitorInterfaces` (whatever was most recently saved) and runs the same apply pass that fires at the end of every discovery: union into each matching asset's `monitoredInterfaces` (additive only). **Fire-and-forget: returns `202 { queued: true }` immediately** and runs `applyAutoMonitorForClass` in the background — the resolve scans every asset's latest interface samples (a multi-second-to-minutes query at fleet scale) and awaiting it wedged the modal's "Applying…" state for minutes. Safe because the apply is strictly additive + idempotent AND re-runs on every discovery (Phase 2c), so a fire-and-forget lost to a process restart self-heals. Writes one `integration.auto_monitor_interfaces.applied` Event on completion when something changed, or `integration.auto_monitor_interfaces.error` (warning) on failure. Called by the integration edit modal's **Save Changes** button for each per-class block whose selection is non-null; the modal confirms "applying in the background" rather than reporting pin counts.
- `POST   /integrations/:id/auto-monitor-assets/preflight` — Save-Changes confirm-modal data source. Body: `{ proposed: { firewall?, switch?, access_point?, workstation?, server? } }` carrying the operator's in-flight `addAsMonitored` choices. Returns `{ integrationId, integrationName, classes: { <classKey>: { currentAddAsMonitored, proposedAddAsMonitored, total, overridden, wouldEnable, wouldDisable } } }` — `wouldDisable` counts assets that would have monitoring swept OFF if this save lands (non-override only), `wouldEnable` counts the inverse, `overridden` counts assets with `monitorOverride=true` that are protected from either direction. Each class entry is included only when `proposed[class]` was supplied. The frontend (`public/js/integrations.js`) calls this from the Save Changes click handler and renders a confirm modal when `wouldDisable > 0` on any class so the operator sees the blast radius before committing.

### Device Map — `requireAuth` (topology-layout writes escalate to `deviceMap=write`)
- `GET    /map/sites`                           — Every firewall Asset with non-null lat/lng. Includes subnet count (via `Subnet.fortigateDevice` match), last-seen status, and a monitor health snapshot: `monitored`, `monitorHealth` (`"up" | "degraded" | "down" | "unknown"`, `null` when unmonitored), `monitorRecentSamples`, `monitorRecentFailures`. **Health is derived from `Asset.monitorStatus`** via `monitorStatusToHealth` (up→up, warning/recovering→degraded, down→down) so the Status Map's red "down" dots agree with the Down Assets / Status Summary widgets, which key off the same five-state machine; the recent-10-sample counts ride along only for the tooltip's "X/Y samples failed" detail (no longer the dot color). The Status Map frontend additionally renders any `dependencySuppressed` site as the distinct "dep" color (never red) — matching Down Assets' default exclusion of suppressed assets (that widget can be toggled to include them, but badges them rather than counting them as independent outages) — and any `status="maintenance"` site as the purple "maint" color (checked before everything else in `healthKey`; a maintenance window freezes `monitorStatus`, so a frozen "down" must not paint red, pulse, or count as an issue for the issues-only filter). Sidebar page entry: "Device Map" (below Dashboard).
- `GET    /map/region-overlay`                  — Read-only region polygons + the derived containment tree, for the Device Map's **Show regions** button: `{ regions: [{id, name, color, polygon, level, depth, parentId, childIds, ancestorIds}], roots, maxLevel, warnings, truncated }`. **Deliberate permission widening:** region polygons otherwise need `mapRegions:read`, but this route lives in `mapRouter` so it inherits the `/map` mount's `deviceMap:read` floor — the button is meant to be available to anyone who can look at the map, and that same viewer already gets every firewall's hostname and coordinates from `GET /map/sites`. **Not** in the dash listener's `API_PATH_ALLOWLIST` and must not be added (the unauthenticated wallboard cannot run the Device Map at all); `tests/integration/dashServer.test.ts` pins the 404. Named with no shared prefix with the `/map/regions` mount so the routing is obvious rather than merely correct.
- `GET    /map/sites/:id/topology/search?q=<query>` — Site-scoped endpoint search powering the topology modal's search box. Matches `q` as case-insensitive substring against `hostname` / `ipAddress` / `macAddress` / `assignedTo` / `dnsName`, scoped to endpoints whose `lastSeenSwitch` references one of THIS site's FortiSwitches. Returns up to 25 results: `{ id, hostname, ipAddress, macAddress, assetType, assignedTo, switchId, switchHostname, port, lastSeen }`. The frontend pulses the matching switch on the Cytoscape graph and navigates to the endpoint's asset details on click.
- `GET    /map/sites/:id/topology`              — Graph payload for the click-through modal. Returns `{ fortigate, switches[], aps[], subnets[], edges[], interfaceEdges[], lldpNodes[], remoteAssetNodes[], lldpEdges[] }`. Each entry in `switches[]` carries `endpointCount` (total endpoints learned on the switch's ports via Phase 7.5 of FMG/FortiGate discovery) and `endpoints[]` — top-25 by recency, each `{ id, hostname, ipAddress, macAddress, assetType, assignedTo, port, lastSeen }`. The right-hand info panel renders these as a collapsible "Endpoints (N)" section nested under each switch with click-through to asset details. The full set is reachable via the search endpoint above. The `fortigate` object carries the same `monitored` / `monitorHealth` / `monitorRecentSamples` / `monitorRecentFailures` fields as `/map/sites` so the modal's root node color matches the pin. Every edge id references a node in the same payload. FortiGate→Switch edges are derived from `Asset.fortinetTopology.uplinkInterface` (the FortiLink interface from `managed-switch/status.fgt_peer_intf_name`). AP→Switch edges come from the AP's own LLDP table (authoritative) or `switch-controller/detected-device` MAC learnings matched against AP base_mac during discovery; APs with no peer switch fall back to a direct FortiGate→AP edge. **Mesh/bridge handling:** a wireless-mesh leaf (`fortinetTopology.meshUplink === "mesh"`) never gets a switch→AP edge — even when stale data stamped a `parentSwitch`, that switch is bridged BEHIND the AP — and any AP↔switch LLDP adjacency involving a mesh-leaf AP (or a switch that isn't the AP's controller parent) is emitted as a `bridgeEdges[]` entry (AP→switch); the client renders it mesh-style, routes the switch behind the AP, and demotes the switch's FortiLink controller edge. **FortiLink fallback edges are dropped when redundant:** FortiOS stamps `fgt_peer_intf_name = "fortilink"` on every managed switch (direct or chained), so an unverified FG→switch controller edge represents the fortilink software aggregate, not a cable — the endpoint's final pass BFSes the assembled graph (controller + interface + LLDP + bridge + MCLAG edges) from the FortiGate with the unverified fallbacks removed, and drops each fallback whose switch is still reachable without it; a switch with no other path keeps its fallback so it never renders orphaned (`verifiedUplink` edges are never dropped). **Inter-switch aggregate links expand to one edge per physical member:** FortiOS reports an LACP/ISL bundle between two managed FortiSwitches as a single aggregate interface (usually the opaque serial-named auto-ISL trunk, e.g. `2DPTD21002999-0`), so the map would otherwise draw one edge labeled with the meaningless aggregate name. Instead, each in-site switch↔switch interface edge is expanded: both sides are resolved to their physical member ports and one edge is drawn per member, pairing the two sides by natural port order — so a 2-member bundle renders as **two** lines (`port11 ↔ port24`, `port12 ↔ port25`), a single physical link stays one, and the aggregate name never shows. Member ports come from two sources, per side in priority order: **LLDP local ports** (each switch advertises its OWN physical port in its neighbor rows — reliable even when the CMDB trunk membership hasn't been scraped) then the CMDB trunk membership via `physicalByParent`/`membersOf` (the `ifParent` linkage back-filled by `overlayFortiswitchTrunkMembers` from the managed-switch CMDB). Only pairs that already have an interface-inferred edge are expanded (LLDP only enriches — it never invents a link); MCLAG pairs are excluded (rendered as the single sibling `mclagEdge`). A side that resolves to nothing degrades to the raw interface name (best effort). **Neither side may claim more cables than the other can terminate:** the pairing decision itself is the pure `pairCableMembers` (`utils/cableMembers.ts`). A lone PHYSICAL member is never repeated across parallel lines — one port terminates one cable — so asymmetric member counts draw `min(a,b)` lines and the surplus is NAMED in the edge's operator-visible reason as *not drawn* rather than rendered; a lone AGGREGATE name IS still repeated, since it labels the whole bundle (that's the side whose CMDB membership wasn't scraped). Link state is a tiebreak, not a filter: a member the device reports as anything but `up` loses to a live sibling, but a side holding exactly one member keeps it whatever its state (a genuinely down link must still render, greyed, rather than vanish), and a member with no reading is kept — unknown is not down. And LLDP consumed as CABLE evidence is bounded by the same 1h `lastSeen` cutoff the tooltip details use: the table's own 48h stickiness window (which exists so the Neighbor COLUMN doesn't flap on a missed advertisement) would otherwise let a row that outlived its cable mint a phantom parallel line for two days after a re-patch. Before those three rules a single cable between two FortiSwitches rendered as `port9 ↔ port27` AND `port10 ↔ port27` (prod 2026-08-24) — the repeated far-end port being the tell, since the old code padded the short side by reusing its lone member across `max(a,b)` lines. Non-switch inter-edges (switch↔cross-site remote) still get single-member aggregate names swapped via `preferPhysicalMember`. FortiSwitch and FortiAP nodes use the same monitor-health color scheme as the FortiGate node — green/amber/red/gray driven by `Asset.monitorStatus` (translated via `monitorStatusToHealth` to the three-state `MonitorHealth` shape). Unmonitored switches/APs render gray. The controller probe path (`probeFortinetController`) maintains `monitorStatus` on these assets via the parent FortiGate's managed-switch/managed-AP inventory. **`interfaceEdges`** carries CMDB-inferred peer links from FortiOS interface naming conventions, computed by `interfaceTopologyService.inferInterfaceTopology` against the latest `AssetInterfaceSample` per (assetId, ifName) for every site asset: aggregate names that encode a peer's serial fragment (auto-stamped FortiLink — e.g. `8FFTV23000001-0` ↔ `S108FFTV23000001`) AND operator-named hostname aggregates (custom MCLAG between non-stacked pairs — e.g. `HILLTOP2-T1024E`). Each entry: `{ source, target, sourceIfName, label, via: "interface", matchVia: "serial" | "hostname" }`. Cross-site peers matched via this pathway are added to `remoteAssetNodes` alongside LLDP-matched cross-site assets. Authoritative — duplicates against `edges` (controller-derived) are dropped, and the LLDP dedupe set is seeded with `interfaceEdges` so a peer link confirmed by both signals only renders once. Rendered as solid teal lines (distinct from the muted gray controller-data edges and the dashed orange LLDP edges). **`lldpNodes` / `remoteAssetNodes` / `lldpEdges`** carry LLDP-derived topology that fortinetTopology can't see: every `AssetLldpNeighbor` row whose `assetId` is the FortiGate or any of its sibling switches/APs is examined, neighbors that resolve back to a sibling are skipped (the authoritative FortiLink/MAC edge already covers them), **neighbors matched to a Polaris asset OUTSIDE this site** are surfaced into `remoteAssetNodes` (separate from ghost LLDP nodes — they're real assets, just at another site; rendered with a solid blue border and a tap-handler that pivots to the asset details page), and unmatched neighbors get a synthesized **ghost** node in `lldpNodes` keyed on chassisId so multi-link aggregates collapse to one. Each LLDP edge carries `targetLabel` (hostname/IP/chassisId for the right-hand info panel) and `targetIsAsset` (true → the link in the panel pivots to the asset details page). The cytoscape graph styles LLDP edges as dashed orange lines, ghost nodes with a dashed orange border, and remote-asset nodes with a solid blue border — distinguishing observed-via-LLDP links from authoritative controller data and "real asset elsewhere" from "non-Polaris device." **Location codes per node:** every `fortigate` / `switches[]` / `aps[]` entry carries `location: { area, building, floor, room, junctionBox } | null` (resolved server-side by `utils/locationCodes.ts`: the `Asset.description`'s codes when it carries any, exclusively; else the device admin description discovery stamped on `fortinetTopology.deviceDescription` — notes are never a source) plus the raw `deviceDescription` (switches/aps). The FortiGate resolves from the description only (no device capture — its device surface would be the 35-char system/global alias). These drive the frontend's grouping hulls (nested rounded rectangles color-coded per level — area rose > building sky-blue > floor violet dashed > room green > jb amber dashed, fitted inside-out so outer shapes grow to enclose inner ones, plus a sibling-separation sweep that pushes non-nested shapes apart so no two ever overlap; drawn as synthetic bottom-layer Cytoscape nodes so `cy.png()` screenshots include them; "Locations" chip toggle at `localStorage["polaris.topology.showLocations"]`, rendered only when codes exist), the solver's same-building/floor row clustering, and the **location views**: when any device carries `b:` or `f:`, a top-left two-row drill-down switcher offers Flat (default, never persisted) + one chip per building (area-prefixed label; clicking selects the whole-building view, and the active building's "All" + floor chips appear in a second row — buildings without floors get no second row) — a building view shows ALL of that building's tagged devices, a floor view just that floor's, both + the FortiGate root, with dashed **portal** stubs where a member's edge crosses to another view (label `→ <view>: <device>`; tap jumps there; untagged devices appear only in Flat; keys are area-scoped `b|<a>|<b>` / `f|<a>|<b>|<f>`; `computeFloorViews` / `partitionElementsForFloor` in topology-render.js). **Right-click description editor:** cxttap on any asset-backed node (firewall / switch / AP / endpoint / matched wireless station / remote asset — not portals, hulls, or LLDP ghosts) opens a small modal editing `Asset.description` in place, pre-filled with the current value and showing the `a:`/`b:`/`f:`/`r:`/`jb:` grouping-shortcut syntax; Save goes through the normal `PUT /assets/:id` pathway (description sync to the device applies when the integration has it on) then silently refreshes the topology so hulls / clustering / the view switcher pick up re-resolved codes. Gated client-side on `assets≥write` (`canManageAssets`). **Node positions are persisted per site AND per view, server-first**: the payload embeds `savedLayouts: { [view]: { view, positions, updatedBy, updatedAt } }` (the `TopologyLayout` rows — the shared hand-tuned map every operator sees); the client prefers those, falling back to the per-browser `localStorage` layout (Flat keeps the legacy bare `polaris.topology.positions:<siteId>` key, floor views append `:<viewKey>`), then the solver default. Drags always write localStorage; `deviceMap=write` callers additionally PUT the blob server-side (debounced ~1s per (site, view), only after a real drag/snap gesture — open/close/refresh alone never PUTs). A **Snap** chip (per-user `localStorage["polaris.topology.snapToGrid"]`, default off) lands drag releases — including hull-drag member moves and multi-select drags — on the column solver's 130×95px lattice; enabling it re-snaps every current position (and, for writers, arithmetically snaps the other views' saved blobs). A **Reset Layout** button in the modal toolbar (between Refresh and Fullscreen) drops the saved positions for the current site's ACTIVE view — localStorage plus (for writers) the server row via the DELETE endpoint — and re-runs the layout against the cached topology data; a non-writer facing a shared server layout gets a toast explaining the reset needs Device Map write.
- `PUT    /map/sites/:id/topology/layout`       *(deviceMap=write)* — Full-replace save of one (site, view) shared layout. Body `{ view: "flat" | "b|…" | "f|…", positions: { [nodeId]: {x,y} } }` (Zod + `sanitizePositions` service re-validation: finite coords, |coord| ≤ 1e7, ≤3000 nodes). 404 unless `:id` is a firewall asset. Returns the saved `{ view, positions, updatedBy, updatedAt }`. Writes a `map.topology.layout_saved` Event (view + nodeCount).
- `POST   /map/sites/:id/topology/layout/checkpoint` *(deviceMap=write)* — The explicit **Save**: stamps the operator's restore point for one (site, view). Same body + validation as the PUT above, and it writes the LIVE blob and `savedPositions`/`savedBy`/`savedAt` in the same statement — the client's debounced drag PUT may not have landed yet, and a restore point of a layout the server never stored would restore a state nobody displayed. 404 unless `:id` is a firewall asset. Returns the saved `{ view, positions, savedPositions, savedBy, savedAt, updatedBy, updatedAt }`. Audited `map.topology.layout_checkpointed`.
- `DELETE /map/sites/:id/topology/layout?view=<key>` *(deviceMap=write)* — **Reset to baseline**. A row carrying a restore point is EMPTIED (`positions` → `{}`) so "Reset to last save" stays available afterwards; a row without one is deleted. 400 on missing/invalid view; idempotent 204 (the Event `map.topology.layout_reset` only fires when a row actually existed, and its message says whether the restore point was kept).

### Application Map (`src/api/routes/applicationMap.ts`, mounted at `/application-map`)

- `GET    /application-map`               *(applicationMap=read)* — The full connectivity graph for appmap.html: `{ generatedAt, nodes[], edges[], savedLayout, stats }` from `applicationMapService.buildApplicationMapGraph()`. Nodes: compound asset parents (**`monitored: true` mapped hosts only** — a stop-monitored / decommissioned / disabled asset drops off the map without losing its pins; with deviceIcon iconUrl), process children (from `Asset.mappedProcesses`, `proc:` id, with listenPorts) AND service children (from `Asset.mappedServices`, `svc:` id — connection rows attributed by their owning `unit`; both child kinds render even with zero connections since they come from the mapped list, not the rows), grey unknown-ip / unknown-ip-group (/24-grouped) / unknown-overflow nodes (resolved-target assets that are only edge endpoints are added regardless of the monitored filter). Edges: one per (source, target) with a per-port breakdown (cap 16 + portOverflow), kind ∈ process | asset | external | external-inbound (child-to-child edges — process↔service alike — are kind `process`). `stats` carries `processCount` + `serviceCount`, and `retentionDays` reports the configured `appMapConnections` retention window (FOREVER = -1) — the client builds its "Seen within" option list from it so the widest option states the real window instead of the old unqualified "All retained", which always meant 7 days regardless of what was kept. Query bounded server-side by that SAME window, so the read and the prune can't disagree.
- `PUT    /application-map/layout`        *(applicationMap=write)* — Full-replace save of the shared drag layout. Body `{ view: "global", positions }` (Zod + the shared `sanitizePositions`). Audited `application_map.layout.saved`.
- `DELETE /application-map/layout?view=global` *(applicationMap=write)* — Reset the shared layout (idempotent 204; Event `application_map.layout.reset` only when a row existed).
- `GET    /application-map/discovery`     *(applicationMap=read)* — The stored discovery-rule set (list UI on Integrations → Polaris Agent) plus the asset types a rule can target and hostname labels for explicit targets: `{version:2, rules[], assetLabels{assetId→hostname}, processCapableAssetTypes[]}`. The client constrains its asset-type picker from that list rather than keeping a second copy of the constant in sync; `assetLabels` lets the list render an auto rule's Devices cell without per-rule round-trips.
- `POST   /application-map/discovery/scope-preview` *(applicationMap=read)* — Body `{ scope, assetIds? }` → `{ total, assets[≤100] }` of monitored assets the scope ∪ explicit assetIds selects (null scope + assetIds = just those assets, matching apply). Backs the wizard's device step so the operator can confirm they picked the hosts they meant before choosing items.
- `POST   /application-map/discovery/inventory` *(applicationMap=read)* — Body `{ scope }` → `{ processes[], services[] }` reported by the assets that scope selects (each row `{ name, deviceCount, mappedCount }`, services adding `platform`/`displayName`). This is what makes the picker granular: it lists what THOSE hosts run, not the whole fleet's inventory. Client-side filtering isn't possible — aggregate rows carry no asset ids.
- `POST   /application-map/discovery/preview` *(applicationMap=read)* — Body `{ rule }` → `{ deviceCount, processPins, servicePins, monitorPins, sampleDevices[≤10] }` counting only what the rule would ADD (a monitor-mode rule adds only monitorPins). Read-gated because it only reports.

### Map Regions — `requireNetworkAdmin` (admin + networkadmin only)
Operator-drawn polygons that auto-tag enclosed FortiGates and their managed FortiSwitches / FortiAPs with `region:<name>`. **Subnet propagation** (in `computeMembership`, which returns `{assetIds, subnetIds}`): beyond the enclosed firewalls and their controller-managed switches/APs, the `Subnet` rows an enclosed firewall serves (`Subnet.fortigateDevice` matching any of that gate's `controllerIdentityKeys` — serial, FMG device name, hostname) inherit the region **themselves**, and so does any asset whose primary IP falls inside one — this is how coordinate-less assets (servers, workstations, standalone devices) get a region tag from the firewall that fronts their subnet (IPv4 only; IPv6 assets are skipped), and how the IPAM Networks list (whose **Sources** column IS `fortigateDevice`) becomes filterable by region. Subnet tags follow the identical provenance-bounded contract, and `ReconcileSummary` counts them separately (`subnetsAdded` / `subnetsRemoved` / `subnetsTouched` alongside the asset counters), so a region edit that touched only networks still writes its Event. Persisted as a single JSON blob in `Setting` keyed `mapRegions` (allocationTemplateService pattern). The reconciler **re-evaluates membership in both directions**, bounded by the `RegionTagAssignment` provenance table (the `TagAutoAssignment` pattern, keyed by region id + a targetType because subnets are targets too): every add records the pair, and the strip half (`diffRegionMembership`) removes the tag only from recorded pairs that no longer belong — so devices that MOVE (a re-pinned gate, a switch repointed to another controller, a subnet re-served by a different gate) shed their old region on the next reconcile, while manual operator attachments (hand-tagging an endpoint server with `region:Atlanta`) and tags predating provenance survive across runs. Manually *removing* the tag from an in-polygon asset will be re-added on the next reconcile — that direction is authoritative by design so polygon membership always implies the tag. Add-then-record ordering makes a crash between the two err toward "operator-owned" rather than toward stripping a tag we never wrote. Region creation upserts a `Tag` registry row at `region:<name>` under category "Map Regions" so it shows up in the asset edit modal's tag picker; rename rotates the registry row (provenance survives — it's keyed by region id); delete removes it and clears the region's provenance. The reconciler runs at four points: inline (await) on every CRUD endpoint, end-of-`syncDhcpSubnets` Phase 13 in `mode in {"full","finalize"}`, a 6-hour periodic job (`reconcileMapRegions.ts`), and the **map-save review** (`POST /map/regions/reconcile`, fired by every Device Map "Save Regions" click — even one with no polygon edits). The map-save review is the one caller that additionally runs the **geometry-authoritative gate pass** (`stripOutOfRegionFirewallTags`): a coordinate-carrying FIREWALL loses any `region:<name>` tag whose polygon no longer contains its pin, provenance row or not — the only path that cleans gate tags predating the provenance table (migration 20260819020000) after a gate moves. The save click is the operator's assertion that the drawn geography is the truth, which is why the periodic job and the discovery-end hook stay provenance-bounded; non-gates, unpinned gates, and tags naming no current region are never touched by the gate pass. Polygon-only edits (drag a vertex without renaming) now re-evaluate like every other pass — targets the smaller polygon no longer covers are stripped where provenance permits. One failing region is logged and skipped rather than aborting the pass. Read access also requires admin/networkadmin since regions are only rendered while editing. **Nesting levels are DERIVED from polygon containment** (`utils/regionHierarchy` via `mapRegionService.getRegionHierarchy`, cached per blob version, never persisted): a region drawn around smaller regions is a container and sits at a higher level, which is what lets alert routing send front-line staff to a device's own region and managers to the division containing it. `level` counts outward from the leaves (1 = contains nothing) and can have GAPS on an uneven tree, while `depth` counts inward from the top and never does — code walks `ancestorIds`, never `level + 1`. Because levels are global, editing one polygon can re-level an ancestor chain and change who gets paged for regions nobody touched, which is what the `region.levels_shifted` Event exists to record.
- `GET    /map/regions`                         — List every region: `{ id, name, polygon: [[lat,lng],...], color, createdBy, createdAt, updatedAt }` **plus its DERIVED nesting facts — `level`, `depth`, `parentId`, `childIds`, `ancestorIds`** (`listRegionsWithLevels`, so nothing is persisted; see the mapRegionService entry). Purely additive: `region-pills.js` reads name + color and the map's edit mode reads polygons, both unaffected. Sorted by name.
- `POST   /map/regions`                         — Create. Body: `{ name (1..64 chars, unique case-insensitive, no control chars), polygon ([[lat,lng],...] with ≥3 and ≤1000 vertices, lat in [-90,90], lng in [-180,180]) }`. Returns the created region. Reconciles inline. Writes `region.created` (details carry the new region's `level` / `depth` / `parentName`) + (when something was tagged) `region.tags_reconciled` + (when the edit moved ANOTHER region's level) `region.levels_shifted` Events.
- `POST   /map/regions/reconcile`               — The **map-save review** behind the Device Map's "Save Regions" button (fired on every save click, even one with no polygon edits). Runs the full provenance-bounded reconcile over every region, then the geometry-authoritative gate pass — a pinned FortiGate loses any `region:<name>` tag whose polygon no longer contains it, provenance row or not (see the section prose above). Returns the combined `MapSaveReviewSummary` (the reconcile counters plus `firewallTagsStripped` / `firewallsTouched`). Writes one `region.tags_reconciled` Event when anything changed. Gated `mapRegions=write`, same as the polygon saves it rides along with.
- `PUT    /map/regions/:id`                     — Update. Body: `{ name?, polygon? }`. Same validation. **Rename path:** strips `region:<oldName>` from every asset that carries it, then add-passes `region:<newName>` to current membership. **Polygon-only edit path:** full re-evaluation of this region — current members gain the tag, provenance-recorded members the smaller polygon no longer covers lose it. Returns the updated region. Writes `region.updated` Event with `previousName` + the region's derived `level`/`depth`/`parentName` for audit, plus `region.levels_shifted` when the edit moved another region's level.
- `DELETE /map/regions/:id`                     — Delete. Strips `region:<name>` from every asset that carries it and removes the `Tag` registry row. Returns 204. Writes `region.deleted` Event, plus `region.levels_shifted` — deleting a container demotes everything that was inside it.

### Agents — runtime + install (mixed scoping)
Inbound agent-runtime routes mounted at `/agents` (see `src/api/routes/agents.ts`; full semantics in polaris-monitoring-discovery → monitoring-architecture (polling / fortinet) and polaris-agent → agent-server-side.md):
- `POST /agents/enroll` *(public; one-shot enrollment token + cert-pin check)*, `POST /agents/samples` / `GET /agents/config` / `POST /agents/heartbeat` / `POST /agents/system-info` *(bearer via `requireAgentBearer`)*, `GET /agents/binary/:filename` *(public, cert-pinned download)*.

Deployment sits one notch above the rest of the router because it runs an installer on the host over a stored SSH/WinRM credential and leaves a service behind — not the act `assets=write` (fix a hostname, retype a serial) describes; the integration-level `agentDeploy.enabled` toggle is the same grant CHAINED onto `integrations=write` (`assertAgentDeployGrant`), and the client withholds the verbs through `canDeployAgent()` / `data-deploy-agent`. Emits `agent.reinstall_kickoff`.

Body `{ ids[] (≤200), sshCredentialId?, winrmCredentialId?, arch?, scriptIds? }` (at least one credential required; `scriptIds` = per-OS `{linux?,darwin?,windows?}` install-method variant, OS-locked + validated up front, applied per an asset's inferred platform). Delegates to `agentInstallService.bulkInstallAgents`: per-asset OS/transport resolved via `inferAgentPlatform` + `pickTransportAndCredential` (Windows → WinRM, SSH fallback; else SSH), run-level preconditions (TLS pin, callback URL, built binaries, credential types) checked once, ineligible assets (existing agent / hypervisor / Fortinet source / unreachable / no matching cred / no binary) returned as `skipped[]` with reasons. Creates `ManagedAgent` rows synchronously (immediate "pending"), then drains the remote installs through a bounded background pool. Returns `{ requested, kicked, skipped[] }`.
- `GET    /assets/agent-install-scripts` *(assets ≥ read)* — the curated install-method catalog (`agentInstallScripts.AGENT_INSTALL_SCRIPTS`) backing the deploy modal's OS-locked "Install method" picker. Returns `{ scripts: [{ id, osPlatform, label, description, isDefault }] }`. Registered BEFORE `GET /:id` so the literal path isn't captured as an asset id.

### MIB Database — mixed scoping
Reads (`list`, `get`, `download`, `facets`, `profile-status`, `structure`, and the MIB-aware `walk`) are open to **admin OR assets-admin** so the team that owns asset onboarding can use the MIB-aware browse + walk surface. Writes (`upload`, `delete`) stay **admin-only**. Routes live in `src/api/routes/mibs.ts` mounted at `/server-settings/mibs` *before* the rest of `/server-settings` so its per-route guards take precedence over the blanket `serverSettingsSystem` read gate on the rest of /server-settings. The same router carries three additional routes under `/std/` (`GET /std`, `GET /std/:key/structure`, `POST /std/:key/walk`) that expose the eleven bundled standard MIBs (System / IF-MIB / IF-MIB Extended / HOST-RESOURCES-MIB / ENTITY-MIB / ENTITY-SENSOR-MIB / LLDP-MIB / POWER-ETHERNET-MIB / BRIDGE-MIB / Q-BRIDGE-MIB / RSTP-MIB) via the same structure + walk shape as uploaded MIBs — see "Standard MIBs" below.
- `GET    /server-settings/mibs?manufacturer=&model=&scope=all|device|generic` *(admin OR assets-admin)* — List uploaded MIBs (filters: manufacturer + model exact match, scope filters generic vs device-specific).
- `GET    /server-settings/mibs/facets`         *(admin OR assets-admin)* — `{ manufacturers: [], modelsByManufacturer: { mfr: [models] } }` — distinct values from already-uploaded MIBs **plus** the asset inventory, so the upload-form datalists aren't empty before the first vendor MIB is uploaded.
- `GET    /server-settings/mibs/:id`            *(admin OR assets-admin)* — Full record including raw `contents`.
- `GET    /server-settings/mibs/:id/download`   *(admin OR assets-admin)* — `text/plain` download with the original filename.
- `GET    /server-settings/mibs/:id/structure`  *(admin OR assets-admin)* — Parsed object tree for the Browse modal. Returns `{ moduleName, imports[], symbols: MibSymbol[], tables: MibTable[], mibId, manufacturer, model, unresolvedCount, unresolvedRoots[] }`. `unresolvedRoots` (from `oidRegistry.findUnresolvedRootSymbols`, empty when `unresolvedCount` is 0) names the distinct EXTERNAL symbols the file references but nothing defines — the actionable cause behind the count, since a module anchored on an IMPORTed symbol fails at its root and takes every symbol chained off it down too (an operator sees "nothing resolved", not "a few gaps"). The Browse modal's warning banner names them and tells the operator to upload the MIB that defines them. Each `MibSymbol` carries `name`, `parentName`, `oidIndex`, `fullOid` (resolved at the MIB's natural scope; null when a dependency is missing), `kind`, `syntax`, `baseType` (`INTEGER` / `Counter32` / `Gauge32` / `TimeTicks` / `OCTET STRING` / `IpAddress` / `OBJECT IDENTIFIER` / `BITS` / `SEQUENCE` / `SEQUENCE OF` / `OTHER`), `enumValues` (`{label, value}[]` for INTEGER types with named values, e.g. `up(1)/down(2)`), `access`, `status`, `description`, `isTableRow`, `indexNames`. Each `MibTable` carries `name`, `rowSymbol`, `columns` (children of the row in OID arc order), `indexNames`, `description`. Parser lives in `src/services/mibService.ts:parseMibStructured` (peer of `parseMib` so a regression in the heavier parser cannot break uploads); OID resolution is provided by `oidRegistry.resolveSymbolsForMib`. Per-symbol parse failures degrade to "name + parentName known, everything else null" rather than dropping the symbol — operators can still walk it, they just don't get decoding.
- `POST   /server-settings/mibs/:id/walk`       *(admin OR assets-admin)* — MIB-aware SNMP walk. Body: `{ assetId, credentialId, objectName, maxRows? }`. Resolves `objectName` against the MIB's structured parse, walks the asset's IP using the supplied SNMP credential via the same `snmpWalkRaw()` primitive the numeric `/assets/:id/snmp-walk` uses, then post-processes results: each row's OID is matched back against the MIB's symbol map (longest-prefix wins, so a table cell's OID resolves to the column symbol rather than the row), `INTEGER` values whose symbol has `enumValues` are decoded into `up(1)`-style labels, `TimeTicks` are rendered as human duration. Response shape: `{ kind: "table" | "scalars", ... , truncated, durationMs, rowCount, decodedCount, host, oid, objectName }`. When every result row's parent matches a single declared `MibTable.rowSymbol`, returns `kind: "table"` with `table: { name, rowSymbol, columns, indexNames, rows: [{ index, cells: { col → {raw, decoded} | null } }] }` so the UI can render a 2D row-per-INDEX grid; otherwise returns `kind: "scalars"` with `entries: [{ oid, symbol, suffix, syntax, baseType, raw, decoded }]`. Each call writes one `asset.snmp_walk` Event with `{ mibId, mibModuleName, objectName, kind, rowCount, decodedCount, truncated, durationMs }` in the details (info on success, warning on probe failure). `decodedCount < rowCount/2` is the operator's hint that the chosen MIB doesn't match the asset's manufacturer — the UI surfaces a yellow banner.
- `POST   /server-settings/mibs`                *(admin)* — `multipart/form-data` upload. Fields: `file` (required), `manufacturer?`, `model?`, `notes?`. The body is parsed by a minimal SMI validator (`mibService.parseMib`) before insert: rejects empty files, files containing NUL/control bytes, anything missing the `<NAME> DEFINITIONS ::= BEGIN ... END` envelope, or files exceeding 1 MB. `moduleName` and `imports` are extracted from the parse and stored on the row. Duplicate `(manufacturer, model, moduleName)` returns 409. Setting `model` without `manufacturer` is a 400 (generic MIBs can't be model-scoped).
- `DELETE /server-settings/mibs/:id`            *(admin)* — Remove a stored MIB.
- `GET    /server-settings/mibs/profile-status` *(admin OR assets-admin)* — Returns one entry per built-in vendor telemetry profile (`{ vendor, matchPattern, example, symbols: [{metric, symbol, resolved, fromModuleName, fromScope}], ready, partial, modelOverrides: [{model, mibCount}] }`). The MIB Database card uses this to render the **Vendor Profile Status** pill. `fromScope` is `"device" | "vendor" | "generic" | "seed"` and reflects which layer of `oidRegistry`'s scoped resolver provided the symbol.

#### Standard MIBs (bundled — RFC/IEEE) — mixed scoping
The twelve canonical SMI/IEEE MIBs the SNMP Walk tab pre-populates in its dropdown (`std:system`, `std:interfaces`, `std:if-ext`, `std:host-resources`, `std:entity`, `std:entity-sensor`, `std:lldp`, `std:poe`, `std:bridge`, `std:q-bridge`, `std:rstp`, `std:ip`) ship as text files under [src/services/stdMibs/](src/services/stdMibs/) and load through `stdMibLibrary.ts`. The last four back the switch physical-layer surfaces: `std:poe` is POWER-ETHERNET-MIB (RFC 3621 — per-port PoE detection status + power class; note it defines NO per-port wattage object, only per-PSE consumption), `std:bridge` is BRIDGE-MIB (RFC 4188 — `dot1dTpFdbTable` MAC forwarding, the `dot1dBasePortIfIndex` basePort→ifIndex join every FDB/STP row needs, and `dot1dStp`), `std:q-bridge` is Q-BRIDGE-MIB (RFC 4363 — the VLAN-aware `dot1qTpFdbTable` a VLAN-aware switch populates instead), and `std:rstp` is RSTP-MIB (RFC 4318). Wire shape matches the uploaded variants so the frontend renders the browse tree + MIB-aware walk identically — see [public/js/assets.js](public/js/assets.js) `_loadAndRenderMibTree` + walk dispatch. Routes are static-segment paths declared before the `/:id/*` catchall in `mibs.ts` so `GET /std` doesn't get eaten by `GET /:id`. Read permission requires `mibDatabase` `read` (admin OR assets-admin); the std bundle is read-only (operators upload custom MIBs through the existing uploaded-MIB routes).
- `GET    /server-settings/mibs/std` *(admin OR assets-admin)* — `[{ key, label, moduleName, rootOid }]` for every bundled MIB. Frontend uses this for the dropdown; the existing hardcoded `_SNMP_STANDARD_MIBS` table in `assets.js` is the primary source today, the endpoint exists for tooling that wants a server-authoritative list.
- `GET    /server-settings/mibs/std/:key/structure` *(admin OR assets-admin)* — Same shape as the uploaded `:id/structure` endpoint, plus `mibId: "std:<key>"`, `moduleName`, `manufacturer: null`, `model: null`, `isStandard: true`. `:key` is the std key without the `std:` prefix (e.g. `lldp` not `std:lldp`); the API client `serverSettings.getStdMibStructure(key)` strips the prefix transparently. Returns 404 for unknown keys.
- `POST   /server-settings/mibs/std/:key/walk` *(admin OR assets-admin)* — Same Zod body (`{ assetId, credentialId, objectName, maxRows? }`) and response shape as the uploaded walk endpoint. Looks the operator's `objectName` up in the std MIB's symbol table, resolves to a numeric OID via `BUILT_IN_OIDS` + the std MIB's own resolved-symbol map, and dispatches `snmpWalkRaw` exactly like the uploaded path. Writes the standard `asset.snmp_walk` Event with `details.mibId = "std:<key>"` (audit logs treat the field as opaque — no UUID FK). LLDP-MIB walks are correctness-validated by the named-number resolver fix in `oidRegistry.tryResolveParts` — `lldpRemTable` resolves to `1.0.8802.1.1.2.1.4.1` through ASN.1 `name(value)` syntax in the root anchor.

- `POST   /server-settings/manufacturer-profiles`                  *(admin)* — `{ manufacturer }`. Manufacturer is alias-canonicalized on insert; pre-populates the seven empty metric rows so the modal opens with the full canvas. 409 if a profile for the canonical form already exists.

The service validates the post-write shape via `validateMetricRowShape` (scalar → symbolB null; double_scalar → both symbols required; table → symbolB+transform null; empty-row state allowed). `defaultTransform` is validated against the matching registry based on `defaultType` — a `CombinerKind` on a `scalar` row (or a `TransformKind` on `double_scalar`) is 400. `defaultMibId` and `defaultMibStdKey` are mutually exclusive — the service rejects requests that try to set both as non-null. `defaultMibStdKey` is validated against the `STD_MIB_KEYS` set; unknown keys are 400'd.

### Device Icons — mixed scoping
Operator-uploaded images that overlay vendor logos on each Device Map topology node's colored status circle. **SVG uploads are transparently rasterized to 512×512 PNG on the way in** via `@resvg/resvg-js` (see `deviceIconService.rasterizeSvgToPng`) and stored as PNG bytes — Cytoscape's `background-image` pipeline can't scale a viewBox-only SVG past the browser's tiny default natural size, so rendering through it leaves the icon stuck at a fixed pixel size and visually anchored upper-left at every zoom. Pre-rasterizing on the server bypasses the whole class of bug, and the `rasterizeStoredSvgIcons` startup job migrates any legacy `image/svg+xml` rows already in the DeviceIcon table. Every icon is keyed to a **manufacturer plus either an asset type or a specific model** — there is no standalone "type-only" / "model-only" / "manufacturer-only" scope, because a "firewall" logo across every vendor would be meaningless. Resolution priority at render time, most-specific-wins: `manufacturer-model: <mfr>/<model>` (specific chassis) → `manufacturer-type: <mfr>/<assetType>` (vendor + role). Both scopes' manufacturer half is canonicalized through the `manufacturerAlias` map so "Fortinet, Inc." and "Fortinet" don't create two rows; the asset's `manufacturer` is canonicalized the same way at resolution time. Type values lowercased; model values preserved as typed. Topology renderer overlays the resolved icon at ~68% of the node so the colored status ring (Up green / Warning amber / Recovering blue / Down red / Unmonitored grey — per the existing five-state machine) stays visible around the logo at a glance. Storage is bytes-in-DB (`DeviceIcon` model). Allowed formats: PNG / JPEG / WebP (256 KB cap) plus SVG (32 KB cap, strict validation). Magic-byte check at upload validates declared mimeType matches actual content for raster formats. **SVG validation is reject-on-pattern, not sanitize** — refusal beats silent rewriting of operator content: the upload must start with `<?xml` or `<svg` (after optional BOM/whitespace) and is rejected outright if any of these patterns is present: `<script>`, `<foreignObject>`, `<iframe>`, `<object>`, `<embed>`, `<!DOCTYPE>`, `<!ENTITY>` (XXE), `<?xml-stylesheet>`, `on*=` event handlers, `javascript:` URLs (entity-escape-aware regex), any external `href`/`xlink:href`/`src` (only in-document `#fragment` refs allowed), `@import` in styles, external `url()` references. Defense-in-depth on the image-serve endpoint: SVG responses get `X-Content-Type-Options: nosniff` and a strict `Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; img-src data:; sandbox` so direct-URL access can't execute anything even if a validator bypass slipped through.
- `GET    /device-icons`                         *(admin)* — List uploaded icons. Each row carries `{ id, scope, key, filename, mimeType, size, uploadedBy, uploadedAt, url }` where `key` is the canonical `"<canonicalManufacturer>/<typeOrModel>"` form and `url` points at the image-serve endpoint below for thumbnail previews.
- `POST   /device-icons`                         *(admin)* — `multipart/form-data` upload. Fields: `file` (required), `scope` ("manufacturer-type"|"manufacturer-model"), `manufacturer` (required; canonicalized via alias map), `typeOrModel` (required; assetType enum value when `scope=manufacturer-type`, free text when `scope=manufacturer-model`). Re-uploading the same canonical key replaces the existing image atomically.
- `DELETE /device-icons/:id`                     *(admin)* — Remove an uploaded icon.
- `GET    /device-icons/:id/image`               *(auth)* — Serves raw bytes with the stored `Content-Type` and `Cache-Control: private, max-age=3600`. SVG responses additionally carry `X-Content-Type-Options: nosniff` + a strict CSP so direct-URL access is locked down. Topology endpoint embeds this URL in each node's `iconUrl` so Cytoscape's `background-image` renders the logo inset over the status-colored node fill (icon at 68% size, centered). Browser HTTP cache deduplicates fetches across re-renders.
