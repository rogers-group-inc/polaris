# Endpoints — /assets

Verbatim from ARCHITECTURE.md → API Endpoints. Gate notation: `key:level`.

### Assets — `requireAuth`
- `GET    /assets`                              — List, **server-side filter / sort / pagination** (the assets page runs `TableSF` in server-side mode like Events; see polaris-ui-canon → "Sortable + filterable data table"). Returns `{ assets, total, limit, offset }`. Filters: `status` / `assetType` (CSV multi-select, single value back-compat), `monitor` (the `_monitor` synthetic chip → `monitored` + `monitorStatus`), per-column operator-aware text filters (`<col>` + `<col>Op` of `contains|not_contains|empty|is_not_empty`), `server` (spans `location`+`learnedLocation`), `lastSeenFrom`/`lastSeenTo`, plus the legacy `department` / `search` / `createdBy`. `sortBy`/`sortDir` are whitelisted (400 otherwise); default `createdAt desc`. The list payload also carries `latitude`/`longitude` (the geographic pin behind the Device Map site marker) for the two sort-only, default-hidden list columns, and **`activeAlert`** — `{severity, count, unacknowledged}` or null, the worst uncleared alert on the row, from ONE `activeAlertSummaryByAsset` query per page (never per row — the export path takes up to 10 000). It drives the strobing dot beside the hostname in the Name column: coloured by that severity, and moving only while something is unacknowledged. `favoriteIds` (CSV) floats the operator's starred assets to the top of the whole result set via a two-bucket query. Indexed by `assets(createdAt)` + `assets(lastSeen)`.

- `POST   /assets/import-pdf`                    — PDF import (assets admin)
- `POST   /assets/oui-lookup` / `POST /assets/:id/oui-lookup`  — OUI vendor lookup (by MAC in body; the `:id` form also stamps the asset)
- `POST   /assets/:id/dns-lookup`               — Reverse PTR lookup (IP → hostname); per-asset, user-triggered
- `POST   /assets/:id/forward-lookup`           — Forward A/AAAA lookup (hostname/dnsName → IP); fills ipAddress when missing
- `DELETE /assets/:id/macs/:mac`                — Remove one MAC from an asset's history (requires `assets` write)
- `GET    /assets/:id/ip-history`               — List IP history entries for an asset (filtered by retention days). Auto-populated by the Prisma query extension in `src/db.ts` whenever any `asset.create` / `asset.update` writes an `ipAddress`, so discovery-sourced IPs are captured without changes to integration services.
- `GET    /assets/ip-history-settings`          — `{ retentionDays }`; 0 = keep forever (default).
- `PUT    /assets/ip-history-settings`          *(assets admin)* — `{ retentionDays }`; saving immediately prunes any history rows with `lastSeen` older than the new cutoff.
- `GET    /assets/source-priority`              — the operator's Sources-column priority `{ order[], integrationPrefix, contributors[{kind,label,mode,describe,fortinetDevice}] }`. `contributors` arrives IN the operator's order (catalogue entries from `utils/assetSourceLocation.ts`) so the drag-and-drop list renders labels + "what this contributes" hints without hardcoding them client-side. Declared before `/:id`.
- `PUT    /assets/source-priority`              *(assets:write)* — `{ order?[], integrationPrefix? }`. Unknown or duplicated source kinds are 400s (the read path self-heals stored rows; a client posting a typo should hear about it); omitted kinds are appended in default order. Returns the same shape as the GET. Audited `asset.source_priority.updated` with the previous order. Takes effect per integration on its next discovery run — that's when `Asset.learnedLocation` is rewritten.
- `GET    /assets/:id/effective-monitor-settings` — Resolved settings for one asset PLUS per-field tier provenance (`asset` / `class` / `integration` / `manual` / `default` — the last meaning no tier set a compatible polling method and the materialized runtime source default is what `resolved` carries), `tier3Source` (`"integration"` or `"manual"`), `classOverrideId` when a class override applies, and `mibLookup: { [uuid]: {moduleName} }` mapping every non-null MIB UUID across the four streams to its `MibFile.moduleName` so the asset-details monitoring chips can render a `MIB: <module>` segment alongside the polling method / cadence / tier label without a second round-trip. Standard MIB ids (the `std:` namespace) are skipped — those resolve through the frontend-local `_SNMP_STANDARD_MIBS` table. Drives the asset edit modal Monitoring tab tier badges AND the asset details monitoring chip stack. See **Monitor Settings Hierarchy** below for the resolution order.
- `POST   /assets/bulk-monitor`                 *(assets admin)* — `{ ids, monitored, monitorCredentialId?, monitorIntervalSec?, probeTimeoutMs? }`. Flips `monitored` on every selected row + applies the supplied credential / cadence overrides uniformly. After the bulk write lands, runs `recomputeMonitorOverrideForAssets(prisma, ids)` (single SQL UPDATE) so each touched asset's `monitorOverride` reflects whether the new `monitored` value diverges from its discovering integration's per-class `addAsMonitored`. Manual / non-integration assets keep `monitorOverride=false`. The polling method comes from the resolver — per-asset choices live on PUT /assets/:id, not here. Returns `{ updated, errors: [{id, error}] }`.
- `GET    /assets/pin-filter-schema`            *(assets:read)* — The **Mass Pinning** section's device-filter vocabulary: `{ scopeCondition: scopeConditionMeta(SCOPE_FIELD_OPS), options: { ...listScopeOptions(), assetTypes, tags }, maxAssets }`. Its own route rather than reusing `/automations/schema` + `/scope-options`, which are gated `automationManagement:read` — pinning an interface must not require permission to edit automations (the `/contacts/filter-schema` precedent, and built from the same shared `scopeConditionMeta` so the vocabularies can't drift). Carries the NARROW automations field set, matching what the automation wizard's Devices step offers. MUST stay above `GET /:id`.
- `GET    /assets/ip-context?ip=`             *(assets:read)* — everything Polaris already knows about ONE address, for the manual Add Asset form. Returns `{ ip, subnet, reservation, arp[], sightings[], switchPorts[], apStations[], existingAssets[], firewall, suggestions, visibility }` (services/ipContextService.ts). Read-only; creates nothing. Declared **before `/:id`** — a bare word would otherwise be captured as an asset id. The two IPAM halves are gated a SECOND time inside the handler on the caller's own `subnets:read` / `reservations:read` (the dashboard precedent), and `visibility` reports which halves were consulted so the panel renders "not shown" instead of asserting "no network found" for a role that could not look. An unparseable or half-typed address answers `200 {ip, unparseable: true}`, not 400: the caller is a debounced keystroke handler and a per-character 400 would be noise, not validation.
- `POST   /assets/pin-inventory`                *(assets:read)* — `{ allAssets? | condition?, facet: "interfaces"|"storage", mode: "count"|"full" }`. Resolves the condition tree SERVER-side via `loadScopeAssetIds` (the client never ships thousands of ids), then: `mode:"count"` → `{ matchedCount }` (the builder's debounced preview), `mode:"full"` → `{ matchedCount, overCap, inventory? }` where inventory is the aggregated-by-name checklist with per-device pinned state so the client renders tri-state from ONE call. A matched set over `MASS_PIN_MAX_ASSETS` (1000) answers `overCap: true` and NO inventory rather than truncating — the tri-state semantics ("pinned on ALL matched devices") are only honest over the complete set, and a silently-cut device list would make a "pin on all" click miss devices the operator believed were covered. A body with neither `condition` nor `allAssets:true` is a 400: a bare `{}` must never quietly mean the whole fleet.
- `POST   /assets/mass-pins`                    *(assets:write)* — `{ pin: [{assetId, name, field}], unpin: [...] }` where `field ∈ interfaces | ipsecTunnels | storage`. DELTAS, not final arrays, so a concurrent hand-pin of an unrelated name on the same asset is never clobbered. Returns `{ updatedAssets, pinsAdded, pinsRemoved, skipped: [{assetId, reason}] }` — an asset whose array would pass the 64-pin cap, a missing id, or a failed write is a per-asset **skip with reason**, never a batch-wide 400 (one 200-port chassis must not veto pins on 400 other switches). One `asset.pins.bulk_updated` Event per call. See `services/massPinService.ts`.
- `POST   /assets/:id/monitor-override/reset`   *(assets write)* — Clears the explicit `monitorOverride` pin and realigns the asset to its discovering integration's per-class Auto-Monitor default: resolves the flag via `getAddAsMonitoredFromConfig`, sets `monitored = <flag>` and `monitorOverride = false`, so discovery resumes auto-managing the asset. 400 when the asset has no `discoveredByIntegrationId` or its assetType isn't subject to Auto-Monitor. Writes one `monitor.override_reset` Event. Backs the "Reset to integration default" button beside the **Asset Override** badge on the asset-details System tab.
- `GET    /assets/:id/monitor-history?range=1h|24h|7d|30d` *or* `?from=ISO&to=ISO`  — Sample stream for the chart. With `range`, the window ends at *now*; with `from`/`to`, both bounds come from the query (span capped at 1 year). Returns `{ range, since, until, tier, bucketSeconds, lastSuccessAt, downDetection, samples, stats: { total, failed, successRate, packetLossRate, avgMs, minMs, maxMs } }`; `range` is `"custom"` when `from`/`to` was used. `responseTimeMs` is null on failed samples (the "packet loss" signal). `lastSuccessAt` is the newest **successful detail** sample at/after `since` (`readLastMonitorSuccessAt`), populated only on rollup tiers and null on detail (where the series answers it) or when no detail success exists in the window: on a rollup tier every sample timestamp is a `bucketStart`, so the chart's stale banner would read a healthy 1-minute probe as ~a day stale the moment the operator switched to 30d. **`downDetection`** is `{ passive, missedPolls, recoveryPolls }` (or null) — the covering automation's two counts, from `describeDownDetectionFor` + `recoveryPollsFor`. The chart replays them through the shared `PolarisMonitorStates.replay` to colour its dive (amber while the count is short of `missedPolls`, red once it reaches it) and its climb (blue until `recoveryPolls` answers have landed), so the line speaks the same four states as the Last-30-min strip above it. It rides THIS payload rather than a second request because a threshold arriving later would repaint the outage under the operator; `passive: true` means nothing may go red, and an absent block is the unknown case that keeps every miss red. `recoveryPolls` costs an extra asset read only when the automation actually sets a reset hold — otherwise it IS the missed-poll count.
- `POST   /assets/:id/snmp-walk`                *(admin)* — Operator-driven SNMP walk for the asset details **SNMP Walk** tab. Body: `{ credentialId, oid?, maxRows? }`. `credentialId` is any stored SNMP credential (not necessarily the asset's monitor credential — admins can spot-check a host with a different community). `oid` defaults to `1.3.6.1.2.1.1` (system subtree); validated as a numeric dotted OID. `maxRows` defaults to 500, hard-capped at 5,000. Returns `{ rows: [{oid, type, value}], truncated, durationMs, oid, host }` — `type` is the symbolic ASN.1 type name (Counter32, OctetString, OID, IpAddress, ...) and `value` is a printable representation (UTF-8 OctetString when printable, hex otherwise; IpAddress is dotted-quad). Walks the asset's `ipAddress` directly — does not consult the asset's resolved polling method, so it works on any asset including unmonitored ones. Each call writes one `asset.snmp_walk` Event (`info` on success, `warning` on failure). 400 if the asset has no IP or the credential is not type `snmp`; 502 if the SNMP session itself fails.
- `POST   /assets/:id/probe-now`                *(user-or-above)* — Run an immediate response-time probe AND telemetry (CPU/memory), temperature, and system-info pulls in parallel; returns `{ success, responseTimeMs, error?, telemetry: { supported, collected, error? }, temperature: { supported, collected, error? }, systemInfo: { supported, collected, error? } }`. Per-stream statuses let the caller's toast tell the operator which streams polled and which failed. The desktop System tab no longer carries a Poll Now button (it became **Discover Now** — see `/rediscover` below); this endpoint now backs the MOBILE asset sheet's refresh icon and pull-to-refresh, and remains the API surface for an on-demand poll (`collected: false` with an `error` is the common case when, e.g., FortiManager-discovered assets in proxy mode have no direct `fortigateApiToken` configured — the SNMP-override probe succeeds but the FortiOS REST system-info call throws "FortiManager direct-mode API token not configured"). The `temperature` stream dispatches on `temperaturePolling` independently from `telemetry`'s `cpuMemoryPolling`, so the toast can show "CPU/memory ok · temperature failed via REST" when only the sensor-info endpoint is unreliable on a branch-class FortiGate. An empty sensor list is rendered as `temperature: n/a (no sensors)` rather than a failure. The endpoint first runs the originating integration's filter via `assetMatchesIntegrationFilter` in `src/utils/integrationFilter.ts` — FMG/FortiGate/Entra check `deviceInclude`/`deviceExclude` against the asset's hostname; AD checks `ouInclude`/`ouExclude` against the OU path. If the asset is out of scope the call returns `409` with the reason in `error` and on every stream's `error`, no probe traffic leaves the host, and one `asset.refresh` Event is written at level `warning` with message `Poll blocked: <name> — <reason>`. The FMG/FortiGate `interfaceInclude` / `interfaceExclude` is applied a layer down inside `collectSystemInfoFortinet` so the System tab interface table mirrors discovery's scope — VLAN sub-interfaces are kept when their parent survives the filter (hiding the parent would orphan its children, so the filter walks the parent → child relationship before dropping rows). Otherwise each call writes one `asset.refresh` Event (level `info` on full success, `warning` on any partial failure) so manual polls are auditable — the periodic monitorAssets job only writes events on up/down transitions.
- `POST   /assets/:id/rediscover`               *(assets write)* — Run discovery scoped to ONE asset. Backs the asset-details System tab's **Discover Now** button, which replaced Poll Now and absorbed the old Re-discover button. `resolveDiscoveryScopeForAsset` (`src/services/discovery/assetDiscoveryScope.ts`) decides which integration runs and how the run is narrowed; the route stays thin. Valid on a firewall asset carrying a `fortinetTopology.role === "fortigate"` stamp discovered by an enabled FortiManager or standalone-FortiGate integration; on a `fortiswitch`/`fortiap` asset, which resolves to its CONTROLLER gate through `src/utils/fortinetParentKey.ts` (never by matching `controllerFortigate` against `Asset.hostname`) and scopes the run to that gate — a switch is only ever discovered as a by-product of its controller's pass, and `finalize-scoped` is exactly the per-gate ghost-switch/AP cleanup it needs; and on a DIRECTORY, HYPERVISOR or CLOUD asset — Entra/Intune by `deviceId` (Graph `$filter=deviceId eq`), AD by `objectGUID` (an LDAP `(objectGUID=\xx\xx…)` filter from `config.baseDn`), vCenter by moref read off `Asset.virtualization` (`vcenter-vm` / `vcenter-host`; NOT the source externalId, which is the instanceUuid), and Azure Arc by ARM resource id. An `intune` row resolves to the owning Entra run (Intune enrichment has no run of its own); a source whose integration row is missing or of the wrong type is never scoped; an `arc-k8s` cluster row is not scopeable (it comes from the cluster query a scoped run skips). Every other asset gets a 400 whose message NAMES the reason (agent-reported, sysDescr-only and manual assets are told no discovery owns them) so the UI can render the button disabled with that text instead of hiding it. 404 only when the asset does not exist. Resolves the FMG device name from `fortinetTopology.deviceName` (hostname fallback — same resolver precedent as descriptionSyncService's device-targeted writes), re-checks `assetMatchesIntegrationFilter` against both the hostname and the resolved device name (409 + warning `asset.rediscover` Event when the gate is filtered out — mirrors probe-now), and 409s while any discovery is already running for the integration (`isRunActive` pre-check + `triggerDiscovery`'s coalescing boolean return closing the TOCTOU window; the pg-boss `singletonKey` is the last-line guard). Scoped runs pass a structured `DiscoveryScope` — `triggerDiscovery(integrationId, actor, { scope, scopeLabel })`; the union (`fmg-device` / `entra-device` / `ad-object`, in `src/services/discovery/discoveryScope.ts`) travels in the pg-boss `DiscoveryJobPayload` while the run row keeps a flat display label (`scopeLabel`, the asset's hostname for a directory device whose scope identifier is an opaque GUID). **A scoped asset-only run skips all four fleet-wide post-sync passes** — agent auto-deploy, interface/storage auto-monitor, presence verification, GAL sync — via the exported pure gate `assetOnlyPostSyncPassesEnabled` (unit-tested in `tests/unit/syncSweepPhaseGate.test.ts` beside `sweepPhaseEnabled`): they read the DB fleet-wide rather than the run's result, and auto-deploy in particular would start agent installs across every agent-less device because one operator clicked Discover Now on one workstation. **A scoped vCenter run additionally suppresses three sync passes** (`vcenterPassEnabled`): the dependency-edge delete-replace (scoped to EVERY VM the integration owns — it would wipe VM→host suppression fleet-wide), the datastore delete-replace (it would empty the table), and the disappearance sweep, which carries a second independent guard in `vcenterSweepBlockedReason` because it decommissions assets. Entra/AD/Arc syncs have no fleet-absence passes to suppress (audited 2026-09-08). FMG assets ride the full run machinery (DiscoveryRun row with `scopeDeviceName` stamped, progress, abort, pg-boss handoff) but narrows the roster to the one device inside `discoverDhcpSubnets` (AFTER the raw roster is captured into `knownDeviceNames`, same protection as the device filter) and finalizes in `"finalize-scoped"` mode (Phase 2b per-controller switch/AP decommission ONLY — see the SyncMode notes in the FMG Discovery Workflow section); standalone-FortiGate assets get a plain full run (the integration IS the single gate). Scoped runs do NOT stamp `Integration.lastDiscoveryAt` (the scheduler's next full run is unaffected) and skip the integration-level slow-run duration sample. 202 `{ message, integrationId, integrationName, deviceName, viaController }` + one `asset.rediscover` Event. `viaController: true` means the run targets a DIFFERENT device than the asset clicked (a switch/AP's controller gate) — the UI names it in a toast, because a run against a device the operator did not click is otherwise surprising. For a switch/AP the integration filter is re-checked against the CONTROLLER gate, not the child: the include/exclude patterns name gates. The button watches the shared `/discoveries` poll for appear→disappear to refresh the asset, with a graceful fallback toast for roles that can't read `/discoveries`.
- `GET    /assets/:id/system-info`              — Asset details System tab: latest interface + storage + telemetry snapshot. Returns `{ monitored, lastTelemetryAt, lastSystemInfoAt, telemetry: {...}|null, interfaces: [...], storage: [...], temperatures: [...], ipsecTunnels: [...], lldpNeighbors: [...] }`. Both the `interfaces` and `ipsecTunnels` queries anchor to `lastSystemInfoAt` (the full pass's write timestamp) rather than the raw newest sample — the fast cadence only writes PINNED rows, so ordering by raw timestamp would hide every unpinned interface/tunnel within a minute of a fast walk. Each anchor clamps down to the newest sample when it's ahead (transient collect failure / agent split-push), and the ipsec query additionally falls back to the newest batch when the anchor pass produced zero ipsec rows. `lldpNeighbors` is the full set of `AssetLldpNeighbor` rows for the asset (current state, not a time-series); each entry includes `localIfName`, full LLDP TLVs (chassisId/portId + subtypes, port description, system name/description, management IP, capabilities), `firstSeen` / `lastSeen`, the source transport (`"fortios"` | `"snmp"`), and a `matchedAsset: { id, hostname, ipAddress, assetType } | null` cross-link when the neighbor resolved to a Polaris asset by management IP, chassis MAC, or hostname. Empty arrays when no scrape has run yet. The set additionally carries **peer-inferred** rows (`source = "peer-inferred"`) synthesized from `Asset.fortinetTopology` via `peerInferredLldpService` so a FortiSwitch's ports facing managed APs, and a FortiGate's FortiLink interfaces facing managed switches, show up in the Neighbor column even though those edges don't appear in a direct LLDP scrape (FortiSwitches in managed mode consume LLDP without re-publishing via SNMP LLDP-MIB). Inferred rows are deduped against real rows on `(localIfName, matchedAssetId)` — real LLDP wins on collision, including the aggregate/member case (a row learned on a FortiLink member port suppresses the inferred row on the `fortilink` aggregate). The frontend renders inferred entries in italic with a tooltip explaining the inference.
- `GET    /assets/:id/custom-widgets`            — Custom MIB tab payload (Slice 7). Resolves the asset's manufacturer through the `ManufacturerProfile` cache, applies optional per-widget `modelPattern` gating against `Asset.model`, and returns each applicable widget's definition plus a window of recent `AssetCustomWidgetSample` rows (up to 60 per widget, oldest first — line charts read the window directly; gauges + tables use `latest`). Response: `{ manufacturer, profileId, polling, lastCustomWidgetAt, widgets: [{ id, name, symbol, mibId, type, widgetType, transform, displayOptions, order, modelPattern, samples, latest, stateMap, labelSymbol, stateRows? }] }`. **State probes** (`widgetType="state"`) carry no `samples`/`latest` — their 0/1 readings live in `AssetStateSample`, so the handler additionally fetches the recent rows for every applicable state probe and attaches each probe's CURRENT state as `stateRows: [{rowKey, rowLabel, value, rawValue, timestamp}]` (newest-first scan keeping the first sighting of each `(probeId, rowKey)`; one scrape writes a probe's whole row set at one timestamp, so the take cap covers several full snapshots). Rows are sorted problem-first (per the probe's `stateMap.trueIsProblem`) then by name, since an operator opening the tab is looking for what's wrong and shouldn't have to scan a 60-row sensor table. Empty `widgets` array when the manufacturer has no widgets defined (the frontend hides the tab in that case) or the widget set doesn't match the asset's model. Samples are produced by `collectAndRecordCustomWidgets()` which rides the telemetry cadence (Slice 7b): after every successful `runTelemetryFor` pass, the helper walks each applicable widget over the asset's resolved SNMP transport, applies the widget's transform, and persists scalar or table rows into `AssetCustomWidgetSample` while bumping `Asset.lastCustomWidgetAt`. A `widgetType="state"` widget takes the state-probe branch instead: walk the value symbol, walk `labelSymbol` too when set (a failed label walk degrades to bare indexes rather than costing the alarm state), map every reading through `joinStateRows`/`evaluateStateMap`, drop the unreadable ones, and write `AssetStateSample` rows (a scalar probe keeps only the first readable row with `rowKey=""` and the probe's name as its label). Table probes are capped at `MAX_STATE_ROWS_PER_PROBE` (500) rows per scrape with a warn-level log when truncated — each row costs a per-scrape DB row AND a NotificationRuleState row in the engine, and a probe silently dropping rows would look like a healthy one. Both sample writes plus the `lastCustomWidgetAt` bump ride one `$transaction`. SNMP-only in v1; FortiOS REST custom widgets land in a follow-up.
- `GET    /assets/:id/telemetry-history?range=1h|24h|7d|30d` *or* `?from&to`  — CPU/memory time-series. Returns `{ range, since, until, samples, stats: { total, avgCpuPct, maxCpuPct, avgMemPct, maxMemPct } }`. memPct is computed from `memUsedBytes / memTotalBytes` if the source supplied bytes only.
- `GET    /assets/:id/interface-history?ifName=...&range=...`  — Per-interface counter samples; sized by interface (a 30-port switch with one row per 10 min ≈ 4,300 samples per 30-day range). Includes `inErrors` / `outErrors` (cumulative IF-MIB / FortiOS error counters) so the asset-detail interface slide-over can derive a per-interval error rate. The response also surfaces the latest sample's `alias` / `description` at the top level (FortiOS CMDB `alias` + `description`, SNMP `ifAlias`) so the slide-over header can show `<alias> (<ifName>)` and render the comment in the **Interface Comments** editor. `description` is the *resolved* value (override if set, else discovered); `discoveredDescription` and `overrideDescription` are also returned separately so the editor can label the source and show the device-reported value as ghost text when no override is set. The response also carries `lldpNeighbors`: the LLDP rows whose `localIfName === ifName` (usually 0 or 1, sometimes >1 on shared media); each row includes the same fields as the system-info endpoint plus a `matchedAsset` cross-link, so the slide-over can render an LLDP neighbor card with a clickable system name that opens the matched asset's view modal. Peer-inferred rows are merged in here too (same dedup rule as `/system-info` — see that endpoint for details), filtered to the requested ifName.
- `PUT    /assets/:id/interfaces/:ifName/comment` *(assets admin)* — Set or clear the Interface Comments override. Body: `{ description: string | null }` (max 255 chars; null or empty string deletes the override row so the discovered FortiOS CMDB description shows through again — the device-side description is never deleted). Polaris-local by default; when the asset's originating integration has `syncDescriptions` on (business rule 14), a saved comment is also pushed to the device via `descriptionSyncService.syncDescriptionsOnSave` and the response gains `sync: { attempted, status?, error? }` (best-effort — the override row persists even when the push fails; the discovery reconcile retries). Writes one `asset.interface.comment_updated` Event (+ `asset.interface.description.pushed|push_failed` when a push was attempted).
- `GET    /assets/:id/hardware-history?range=...[&sensorName=...]`  — Per-sensor hardware-reading time-series. Samples carry `{ timestamp, sensorName, sensorClass, unit, value, alarmStatus? }`; returns `{ samples, stats: { total, avgValue, minValue, maxValue } }`. Backed by the `hardware` retention entity / tier router.
- `GET    /assets/:id/metric-thresholds?metric=…[&sensorName=&sensorClass=]` — The severity thresholds that would fire on this asset's charted metric (`assets:read`), so a detail chart can shade its line with the engine's own numbers. Returns `{metric, tiers[{severity, operator, threshold, ruleId, ruleName}]}` ordered least → most severe, from `notificationRuleService.getMetricSeverityTiers`: every enabled scope-matching automation contributes either its `resolveTierLadder` (numeric single trigger — tier 0 plus each severity band) or each composite leaf on that metric at the rule's severity. `sensorName`/`sensorClass` identify the charted sensor so a rule whose dimensionFilter doesn't select it is skipped. Only ordered comparators appear (`==`/`!=` shade nothing); ties at one severity keep the more sensitive threshold; hot (`>=`) and cold (`<=`) tiers of the same severity are both returned. Consumed by `_severityChartLayer` in assets.js.
- `GET    /assets/:id/storage-history?mountPath=...&range=...`  — Per-mountpoint usage samples. SNMP-monitored assets only.
- `GET    /assets/:id/ipsec-history?tunnelName=...&range=...`  — Per-tunnel IPsec samples (status timeline + cumulative bytes). FortiOS-monitored assets only.
- `GET    /assets/:id/sdwan-members`  — Per-WAN-member health summary (aggregate up/down, per-health-check latency/jitter/loss, recent up/down status strip, + IP/link/bytes joined from the latest interface sample). Drives the "SD-WAN Members" table above the rules.
- `GET    /assets/:id/perf-sla-links`  — Distinct (healthCheck, link) pairs + latest SLA thresholds. SD-WAN data-exists gate + selector source for the SD-WAN tab.
- `GET    /assets/:id/perf-sla-history?healthCheck=...&link=...&range=...`  — Per-member SD-WAN Performance SLA latency/jitter/packet-loss gauges over time (tier-aware).
- `GET    /assets/:id/sdwan-rules`  — Current-state SD-WAN service rules (selected member + members/criteria/health-checks/destination/status + priority zones), one row per rule from the `asset_sdwan_rules` table, ordered by FortiOS rule priority. No history endpoint — SD-WAN rules are current-state.
- `GET    /assets/:id/upstream`  — The three upstream devices the General tab names (Last Seen Switch / AP / Firewall), each as `{ name, port?, lastSeen?, asset }` where `asset` is `{ id, hostname, ipAddress, assetType, status, monitorStatus, managementAccess }` or **null** when the stored name resolves to nothing (an unadopted switch, a gate another integration hasn't discovered yet — a legitimate state, so the UI keeps rendering the name as plain text). - `PUT    /assets/:id/processes/:name/config`  — Operator log-path config for a pinned program (`logSource` auto|journald-unit|file-glob + `logPathGlob` wildcard + notes). Upserts `AssetProcessConfig`; delivered to the agent via `GET /agents/config`'s `pinnedProcesses`. Writes `asset.process.log_config_set`.
The assets list and single-GET attach a synthesized `ipContext` field to each row: `{ subnetId, subnetCidr, reservation: { id, createdBy, sourceType } | null } | null` (null when the asset has no IP, or no non-deprecated subnet contains the IP). The list also attaches `monitoringMethods: string[]` — the reduced set of transports the asset is actually monitored by, computed by `computeMonitoringMethods` in `enrichAssetList` (`assets.ts`): `[]` when unmonitored, `["agent"]` when a `ManagedAgent` is `active` (the agent owns all streams), else the distinct resolved per-stream polling methods from `resolveMonitorSettings` (cached tiers, no per-row DB hit) with ICMP treated as subordinate — reachability-only, so it surfaces only when it's the sole method. Drives the Assets table's **Monitored Via** column (label per method, "Multiple" when several differ). The Assets page reads it to render a **View Lease** button on rows whose IP lives in a known subnet — clicking it navigates to `/subnets.html#ip=<subnetId>@<ipAddress>`, where the network slide-over opens scrolled to that IP's row. To reserve or release IPs, operators use the network slide-over directly (no asset-row Reserve/Unreserve buttons).

- `PUT    /assets/sighting-settings`            *(assetsQuarantine write)* — `{ sightingMaxAgeDays }`. Max 3650.
- `GET    /assets/:id/sightings`                *(auth)* — DHCP sighting history for this asset (list of `{ fortigateDevice, source, ipAddress, lastSeen, integrationId, subnetName, vlan }`). `subnetName` + `vlan` are resolved at request time by matching the stored `ipAddress` against subnets discovered on the same `fortigateDevice` — both are null when the IP doesn't fall inside any known subnet on that device (e.g. the subnet has been deleted or the sighting predates the `ipAddress` column).
- `GET    /assets/:id/sources`                  *(auth)* — Per-discovery-source view of an asset (Phase 3a of the multi-source asset model). Returns every `AssetSource` row attached to this asset with the originating integration's name + type joined in, sorted in stable presentation order (`entra` → `intune` → `ad` → `fortigate-firewall` → `fortiswitch` → `fortiap` → `manual`). Each entry: `{ id, sourceKind, externalId, integration: { id, name, type } | null, observed, state, inferred, syncedAt, firstSeen, lastSeen }`. `state` is `deriveAssetSourceState(sourceKind, observed)` from `src/utils/assetSourceState.ts` — the source's own enabled/disabled verdict normalized to `{ state: "enabled" | "disabled" | "unknown", kind: "account" | "runtime" | "none", label, field, value }`, so a caller doesn't have to know that Entra says `accountEnabled: false` where AD says `accountDisabled: true` and vCenter says `powerState: "POWERED_OFF"`. Rows are **collapsed by `(sourceKind, integrationId)`, keeping the most-recent (`lastSeen`-desc) row per source** — so a `fortigate-endpoint` source whose MAC-keyed `externalId` churned (each MAC change spawns a new `AssetSource` row and orphans the old one) renders as a single card instead of several near-identical ones. Serial/GUID-keyed kinds (`fortigate-firewall`/`switch`/`ap`, `ad`, `entra`, `intune`) have stable externalIds and never collapse; the dropped MAC/IP detail still surfaces in the Firewall Sightings + IP History tables on the same tab. Powers the **Sources** tab on the asset details modal — operators can see what each integration independently said about the device.
- `POST   /assets/:id/sources/:sourceId/split`  *(admin)* — Recovery action. Detaches the chosen `AssetSource` row from this asset and binds it to a freshly-created Asset whose discovery-owned fields are seeded from the source's `observed` blob via `projectAssetFromSources([source])`. The new Asset gets a `split-from-asset` tag plus a source-kind hint (`entraid` / `activedirectory` / `fortigate` / etc.). **Phase 4d retired the `assetTag` write here** — the AssetSource row that just got re-bound is the canonical identity link; the legacy `entra:`/`ad:`/`fgt:` assetTag prefixes were back-compat markers that re-discovery already stopped consulting in Phase 2. Refusal rules: source not on this asset (404), source is the asset's only source (409 — would leave the original orphaned), source is `sourceKind="manual"` (409 — backfill marker, not a real discovery source). Returns `{ originalAssetId, newAssetId, movedSourceId, newAsset }`. Asset-row FKs (monitoring samples, IP history, sightings, quarantine, conflicts) all stay on the **original** asset; the new Asset starts clean. Writes one `asset.split` Event with details `{ originalAssetId, newAssetId, sourceId, sourceKind, externalId }`.
- `GET    /assets/:id/polling-history`          *(auth)* — Polling-history summary for the merge comparison: how much sample history the asset holds across the monitor-probe + telemetry streams and all three retention tiers (detail / hourly / daily rollups). Returns `{ oldestAt, newestAt, spanDays, sampleCount, monitor: { oldestAt, newestAt, sampleCount }, telemetry: {...} }`. `sampleCount` is **stitched** so overlapping tier coverage isn't double-counted (all of daily + hourly buckets past daily coverage + detail rows past hourly coverage — `readPollingHistorySummary` in `sampleHistoryService.ts`); the UI presents it as approximate. Feeds the Merge Assets modal, which shows each side's history, **auto-selects the survivor with the longer history** (span first, count as tiebreak — the absorbed side's samples are orphaned by a merge), and warns in the confirm step when the operator overrides toward the shorter side.
- `POST   /assets/:id/merge`                    *(admin)* — Operator-driven asset merge — the **inverse of Split**. Absorbs another asset into this one. Body: `{ otherAssetId, survivor: "this" | "other" (default "this"), fieldWinners?: { <field>: "this" | "other" }, dependencyWinner?: "this" | "other" }`. The operator picks which side survives (keeps its monitoring history + quarantine state + FKs) and resolves each differing field; `fieldWinners` keys are a subset of `MERGEABLE_FIELDS` (`src/services/assetMergeService.ts`), any omitted field defaults to blank-fill. Delegates to `mergeAssets()` in `assetMergeService.ts`: **re-binds ALL of the absorbed asset's `AssetSource` rows onto the survivor** (via the shared `absorbAssetRelations` — no `(sourceKind, externalId)` collision possible — globally unique — so the survivor becomes multi-source; this is the key difference from the automatic `mergeDuplicateHostnameAssets` job, which cascade-deletes the ghost's sources. `acceptAssetConflict`'s sibling-conflict absorb calls the same helper as of the fix below, so both operator-facing merges preserve provenance identically), transfers `AssetMacAddress` / `AssetAssociatedIp` / `AssetIpHistory` / `AssetFortigateSighting` (delete-on-conflict against the survivor's existing rows), re-binds the `ManagedAgent` enrollment iff the survivor has none, union-merges tags, keeps the more-recent `lastSeen`, applies field winners (clamping `acquiredAt ≤ lastSeen`), **OR-s `monitored`** (either side monitored ⇒ survivor monitored; when that flips the survivor ON it also adopts the absorbed row's `MONITOR_CONFIG_FIELDS` — per-stream polling methods / credentials / MIB pins / interval+timeout overrides, ghost's non-null wins — and UNIONs its `MONITOR_PIN_FIELDS` monitored/mapped arrays, resets `monitorStatus` + failure/success counters, and recomputes `monitorOverride`; skipped when the merged status resolves to `decommissioned`/`disabled` per business rule 10. Response: `carriedMonitoring` + `monitorFieldsAdopted`, both also stamped on the `asset.merged` Event), then deletes the absorbed asset. **Dependency edges survive** (`transferDependencyEdges`, shared with the conflict absorb): devices depending on the absorbed asset are re-pointed at the survivor (self-edges + duplicate (child, survivor, source) rows left to cascade), the absorbed asset's own parent links blank-fill onto a survivor with none, and when BOTH sides have parent rows `dependencyWinner` decides wholesale (omitted = survivor keeps its own; never a union — one device has one real upstream and a union weakens all-down suppression). The merge modal renders each side's effective parents (+ infra dependent count) as a comparison row that becomes a highlighted conflict with Keep A/B radios when both sides' parent sets differ. `lastSeenSwitch`/`lastSeenAp` carry with lastSeen-recency semantics (blank-fill; both-sides-set → the more recently seen record wins) so the endpoint dependency edge can re-derive. The absorbed asset's interface-comment overrides, LLDP/wireless rows, and pending Conflicts **cascade-delete**; its sample/telemetry/rollup/custom-widget time-series are **orphaned and aged out via `drop_chunks`** (no FK since migration `20260615000000` — a cascade delete would decompress their TimescaleDB chunks into bloat, prod incident 2026-06-08). Either way the survivor keeps its own history and the absorbed asset's is not carried over (the UI surfaces monitored status + sources + each side's polling-history size from `GET /assets/:id/polling-history` and auto-selects the longer-history side as survivor — operator-overridable; the confirm dialog quantifies the history being deleted, warns when the shorter side was kept, and warns the loss is permanent). Refusal rules: self-merge (400), either asset missing (404). Returns `{ survivorId, absorbedId, movedSources, movedMacs, movedIps, movedIpHistory, movedSightings, movedManagedAgent, movedDependencyParents, replacedDependencyParents, movedDependents, appliedFields }`. Writes one `asset.merged` Event. Powers the **Merge asset…** button on the Sources tab.
- `GET    /assets/:id/dependencies`             *(auth)* — Read effective + computed + override parents AND direct children for the dependency-suppression DAG. Returns `{ asset: { id, hostname, assetType, dependencyLayer, dependencySuppressed, dependencySuppressedAt }, effectiveParents, computedParents, overrideParents, hasOverride, children, childrenTruncated, childCount }`. Each parent entry is `{ id (row id), parent: { id, hostname, assetType, dependencyLayer, monitorStatus, monitored }, source, detectedVia }`. **Resolution rule**: if any `source="override"` rows exist for this asset, the override set is the effective set (computed rows ignored); otherwise every NON-override row is effective — `computed` (Fortinet infra), `endpoint` (an endpoint's leaf edge) and `vcenter` (VM→host) alike. Both this split and the per-child binding rule tested `source === "computed"` literally until 2026-08, which hid the endpoint and vCenter halves from the tree even though the reconciler was suppressing on them. Empty override set = explicit "no parents" pin. The `children` array carries two layers down (direct children + grandchildren) — every asset that has THIS asset in its **effective** parent set plus, nested under each direct child, that child's own effective children. Each child entry: `{ id, hostname, assetType, dependencyLayer, monitorStatus, monitored, dependencySuppressed, source, detectedVia, childCount, grandchildren: [...] }` where each grandchild has the same shape minus `grandchildren`/`childCount`. Sorted within each layer by type (firewall→switch→access_point) then hostname. **The downward view is INFRA-ONLY at both layers** (`FORTINET_INFRA_ASSET_TYPES`, filtered in SQL — `take` applies before any in-memory filter, so a gate with 300 switch children would otherwise fill the read and report nothing). The endpoint half of the DAG makes every workstation / server / printer a child of the switch, AP or gate that last saw it, and a site gate is the last-seen device for the entire site, so those rows would bury the two or three an operator opened the tree to read. They are excluded here deliberately even though they are real edges the reconciler suppresses on — an endpoint's dependency is shown on its OWN General tab, as the parent above it, which is where the suppression it drives is worth explaining. Caps therefore bound a controller FortiGate's managed switches/APs, not the endpoint half: `DEP_INFRA_CHILD_CAP` 300 direct + `DEP_GRANDCHILD_CAP` 500 grandchildren, with `childrenTruncated` set when the direct read overflowed. `childCount` counts INFRA children only (a findMany over the indexed `parentAssetId` with the relation type filter, deduped per child — a groupBy can't filter on a relation) so the UI's "+N" hint can never become an endpoint tally, which is exactly the noise the type filter removes. Drives the General-tab Dependency Tree block on the asset details modal so the common firewall → switch → AP chain renders without click-through; operators still click through for anything deeper than two layers.

- `GET    /assets/:id/connection-path`          *(auth)* — Resolve the upward chain from this asset to its upstream FortiGate so the Device Map topology overlay can dim everything off-path. Returns `{ asset: {id, hostname, ipAddress, macAddress, assetType, monitorStatus}, hops: ConnectionPathHop[], alternateUplinks: number, siteId: string | null }`. Each hop carries `kind: "endpoint" | "switch" | "firewall"`, the asset row's id + hostname + ipAddress + macAddress + assetType + monitorStatus + monitored flag, plus optional `endpointPort` (port label parsed from the leaf endpoint's `lastSeenSwitch`, populated on the first switch hop) and `uplinkInterface` (the switch's local interface that goes UP, from `fortinetTopology.uplinkInterface`). Resolution: firewall short-circuits to a single-hop self-path; switches/APs walk upward from themselves; endpoints (workstations / servers / printers / other) parse `Asset.lastSeenSwitch = "<switchId>/<port>"` to find the upstream switch, then walk. The upward walk reads `AssetDependencyParent` rows (override rows take precedence over computed) and picks the parent with `monitorStatus="up"` AND most-recent `lastMonitorAt` for MCLAG / dual-homed switches; remaining-parent counts are summed across hops into `alternateUplinks` so the UI can hint "+N alternate uplinks." Falls back to `fortinetTopology.controllerFortigate` / `parentSwitch` when dependency rows are empty (fresh installs before the backfill job runs, or freshly-discovered switches awaiting recompute). Capped at 16 hops as a sanity guard against pathological data. `siteId` is the firewall asset id at the top of the chain when the walk reached one; null when the chain terminated short (orphan asset with no `lastSeenSwitch`, or upstream chain not yet discovered). Resolver lives at [src/services/connectionPathService.ts](src/services/connectionPathService.ts); consumed by the Device Map topology modal which overlays the endpoint as a Cytoscape node + dims off-path elements.
