# Authentication & RBAC

Verbatim from CLAUDE.md → Authentication & RBAC.

Sessions are PostgreSQL-backed (`connect-pg-simple`), 8-hour max age, HttpOnly/Secure/SameSite=Lax cookies.

**Dynamic-role model (post-cutover).** RBAC is enforced via `requirePermission(functionKey, level)` from [src/api/middleware/permissions.ts](src/api/middleware/permissions.ts). Each route declares the function key it gates + the required access level; the resolver consults the caller's `Role.permissions` matrix denormalized into `req.session.roleSnapshot` at login. The matrix is `{ [functionKey]: "none" | "read" | "write" | "fullwrite" }` over a 33-key catalogue. The five built-in roles (`admin` / `readonly` / `networkadmin` / `assetsadmin` / `user`) are seeded by `prisma/migrations/20260524000000_roles_table_cutover` so existing accounts keep their pre-cutover access exactly. Admin creates custom roles from the Roles section under Users → Manage Roles.

| Built-in role | Locked? | Pre-cutover behavior preserved |
|---|---|---|
| `admin` | Protected — cannot be edited or deleted; hidden from the editable list | every function = `fullwrite` |
| `readonly` | Protected | every function readable by non-admins = `read`, admin-only functions = `none` |
| `networkadmin` | Editable, cannot delete | IP space / integrations / map-regions / discovery-conflicts write; read elsewhere |
| `assetsadmin` | Editable, cannot delete | assets / quarantine / monitor-settings write + own-subnet/own-reservation write |
| `user` | Editable, cannot delete | own-subnet / own-reservation write; read elsewhere |

**Ownership model for networks, reservations, contacts and credentials.** `subnets`, `reservations`, `contacts` and `credentials` carry an ownership dimension (`hasOwnershipDimension` in the catalogue is the authoritative list — `networkScan` joined it in the Discovery visibility cutover): `write` lets the caller edit only rows where `createdBy` matches their username; `fullwrite` bypasses the ownership filter. Built-in `user` and `assetsadmin` are seeded with `write`, `networkadmin` and `admin` with `fullwrite`. Route handlers branch on `req.permissionLevel` (set by `requireOwnership(functionKey)`). **`credentials` joined the set 2026-09-04** (migration `20260904050000_credential_ownership_and_probe_readonly`, business rule 43): `write` creates and reaches only rows the caller created, `fullwrite` reaches any, and `POST /credentials/test` is scoped the same way whenever it names a stored `id` — that path merges the row's real secrets into the probe, so testing a peer's credential is borrowing their password rather than reading anything. `Credential.createdBy` is stamped once at create, never rewritten by an edit, and `null` (every row predating the column — deliberately not backfilled) is UNOWNED and therefore fullwrite-only. Every built-in role stays at `credentials=read`, so the dimension only starts mattering when an admin grants `write`; the LIST stays readable at `read` because the Asset Monitoring credential picker needs the names. **A `dhcp_lease` is not a reservation:** it's observed device presence, so reserving an IP that currently shows a lease is a plain *create* (gated on the caller's `reservations:write`), NOT a release of someone's row — `reservationService.createReservation` supersedes the observed lease server-side via `releaseSupersededDhcpLeaseAt`, which **delegates to `releaseReservation`** (so on push-enabled subnets the FortiGate lease is expired via `releaseDhcpLease`, on read-only subnets it's a pure DB release — identical to the old client `release+create` flow, minus the route ownership gate). This parallels how `createReservation` already supersedes `dns_resolved` via `releaseDnsResolvedAt`. The create's collision check excludes `dhcp_lease`, `dns_resolved`, **and lease-backed `fortiswitch`/`fortinap` rows** (`Reservation.dhcpBinding === "lease"` — see business rule 23); `manual`/`dhcp_reservation`/`vip`/`interface_ip` and infra rows that aren't lease-backed are authoritative and still 409. The takeover set has one definition, `isSupersedableByCreate` in `reservationService.ts`, shared by the 409 check and the supersede-release. Because the take-over is a create, the IP-panel "Reserve" button (desktop `_openLeaseReserveModal` + mobile reserve sheet) no longer issues a separate ownership-gated DELETE. (The `owner` column is display metadata with no role in the ownership gate — on discovered rows it carries the matched asset's `assignedTo`; on manual creates/updates it auto-stamps to the caller's username when not explicitly typed. Gating rides `createdBy` only.)
**Function-key catalogue (33 keys).** Single source of truth in `src/api/middleware/permissions.ts:FUNCTION_KEYS`. (Newest — **`savedDashboards`**, migration `20260904040000_saved_dashboards`: named dashboard canvases, private or PUBLIC. `read` = list them + keep your own private ones (the same act the ungated `/me/dashboard` already allows, so there is nothing to withhold); `write` = PUBLISH one, which reaches every operator and the unauthenticated Dash wallboard; `fullwrite` = delete anyone's. Its OWN key rather than riding a page's gate the way `SAVED_FILTER_SCOPES` does, because the Dashboard page has no function key to inherit — it is gated per WIDGET. Seeded admin=fullwrite, networkadmin/assetsadmin=write, **readonly=read AND user=read** — the readonly level is load-bearing twice over: a plain `user` must still be able to keep private dashboards, and the Dash wallboard answers as the built-in readonly role, so that level is what lets a wallboard load a published screen at all. Before that — **`networkScan`**, migration `20260825040000_network_scan`: the active-scan **Discovery** feature — create / edit / run a saved sweep of operator-supplied IP ranges and adopt what answers. Its OWN key rather than part of `assetsProbe` (probe-now / SNMP walk on ONE existing asset), because an unannounced sweep is IDS-visible and is exactly the capability an admin may want to withhold from someone who may still edit inventory. `read` = browse the Discoveries you can see (your own + every shared one) + watch a run; `write` = create / run / import + edit and delete **your own**; `fullwrite` = edit and delete anyone's. Seeded admin=fullwrite, readonly=read, networkadmin/assetsadmin=write, **user=none** (that role exists for IP-space self-service). It carries `hasOwnershipDimension` since the 2026-09 private/public cutover (migration `20260904060000_network_scan_visibility`, which adds no key — only columns), with one deliberate difference from `subnets` / `reservations` / `contacts`: PUBLISHING is not the escalated level, because sharing is the feature and the roles that author Discoveries hold `write`, not `fullwrite` (business rule 34g). ADOPTING is chained: `POST /network-scans/:id/adopt` requires this key's `write` AND `assets:write`, the `PUT /application-map/discovery` precedent — so "may scan" and "may create assets" stay separable. Before that — **`contacts`**, migration `20260810000000_contacts`: the address book, and the third key to carry the **ownership dimension** (`hasOwnershipDimension`) alongside `subnets` / `reservations` — `read` browses, `write` adds and edits/deletes only rows the caller created, `fullwrite` manages anyone's. Seeded admin=fullwrite, readonly=read, networkadmin/assetsadmin/user=write. Before that — the **Automations cutover**, migration `20260721000000_automations_rbac_rename`: `notifications` → **`alerts`** and `notificationManagement` → **`automationManagement`** (levels carried over verbatim), plus new **`automationScripts`** — automation script-registry CRUD + attaching script actions; **RCE-equivalent** (server scripts run as the polaris service user, agent scripts as the agent's user — unprivileged on Linux, LocalSystem on Windows), seeded `fullwrite` only for admin-equivalent roles (users+roles=fullwrite), else `none`. Runtime compat: `LEGACY_KEY_ALIASES` + `permissionOf()` in `permissions.ts` resolve the old key names from pre-deploy session snapshots and `normalizePermissions` folds them on write — never remove that without a session-invalidation plan. Prior additions: `applicationMap` (`20260721000000_application_map` — Application Map page/graph read + shared-layout write, mirrors deviceMap: admin=fullwrite, other built-ins=read), `maintenanceManagement` (`20260715000000`), the notification keys (`20260628000000`), `processControl` (`20260627000000` — now vestigial: process/service control was removed in the Satellite-posture change, so the key remains in the catalogue for matrix compat but gates nothing); removed: vestigial `reservationPush` (`20260703000000`).) Exposed at `GET /api/v1/roles/functions` so the frontend matrix UI renders without hardcoding the list. Adding a new key requires a migration to seed it on every existing Role + a corresponding guard at the route layer; removing one requires a migration to strip it (`normalizePermissions` also drops unknown keys on the next role write).

**A key may declare a SHORTER ladder than the four levels** (`levels` on `FunctionKeyDef`, 2026-09-04 — business rule 43). `assetsProbe` is the first and holds `none | read`: a probe dials the device and writes nothing in Polaris, so Read is the whole grant and the two cells above it were radio buttons no route ever asked for. Enforced three ways that must not drift — `normalizePermissions` clamps a stored or incoming value DOWN into the ladder (never up: a `fullwrite` on a read-only key means "as much as possible", so rounding up would silently grant and resolving to `none` would silently revoke), `permissionOf` clamps on READ so a session snapshot stamped before a ladder narrowed still resolves, and `requirePermission` **throws at module load** when a route asks for a level its key cannot hold (that route could never be granted, and would present as an unexplainable 403 instead of a red build). `public/js/users.js` renders a dash instead of a radio for an unsupported cell and the bulk "set every row to" control clamps per row, off the same `levels` array. An ownership-dimensioned key must keep both `write` and `fullwrite` — that pair IS the dimension (`tests/unit/permissionLevelLadders.test.ts` pins it).

**Session role snapshot + cache invalidation.** `req.session` carries `roleId` + a denormalized `roleSnapshot` stamped at login. Every `requirePermission` call hits a module-level `Map<roleId, updatedAt>` cache first (O(1)); a Role write bumps the map via `bumpRoleVersion(roleId, updatedAt)` and the next request from any session holding the stale snapshot triggers ONE Prisma fetch + `req.session.save()` to refresh. Changing a user's `roleId` takes effect on next login; changing a role's permissions takes effect on the next request for every session that holds the role.

**Region tags + other tags (storage-only consumer pending).** `Role`, `User`, and `GroupMapping` each carry two operator-typed tag dimensions: `regionTags: String[]` and `otherTags: String[]` (free-form). Empty = unrestricted. Effective scope for a session is `union(role, user, group-derived)` per dimension. Returned by `GET /api/v1/auth/me` as `{ regionTags: { user, role, group, effective }, otherTags: {...} }`. Group-derived tags are re-resolved live from `User.ssoGroups` on each `/auth/me` (never persisted onto the user's own columns, so operator-set tags survive a re-login). Normalization is shared in `src/utils/tagNormalize.ts`. **Assign Tags edits both dimensions through the ONE tag picker**: a map region already IS a registry tag (`region:<name>` in the locked Map Regions category), so the separate Region Scope control listed the same names twice in the same dialog. The prefix carries the split instead — the picker seeds each region tag under its registry name and `_splitUserTagScope` routes anything so prefixed back to `regionTags`, bare, which is what keeps region-ONLY consumers (`resolveUsersByRegions`, level-scoped routing, Device Map "My regions") reaching the same people. The role slide-over and Group Mappings still carry the two pickers separately. The **Users list draws BOTH dimensions** under the username (`userTagPillsHtml`, regions in their map colour then tags in their registry colour) — it drew regions alone while Region Scope was its own control, which after the merge read as “my tags did not save”. The browser picker behind the second dimension (Users → a username → **Assign Tags**, the role slide-over, and Group Mappings) offers the `Tag` registry as selectable pills and creates a registry row — in an operator-chosen **category** — for a typed name that isn't in it when the caller holds `serverSettingsSystem:fullwrite` — but the stored values stay bare free-form strings with **no FK to that registry**, so deleting a tag there strips nothing from any principal's scope. **A region RENAME carries these columns with it and a region DELETE never strips them** (`regionScopeService.renameRegionInPrincipalScopes` / `principalsScopedToRegion`, called from the `/map/regions` PUT and DELETE): the columns hold bare region names with no FK to any registry, so a rename that left them behind revoked every scoped operator's region in silence — tag present, matching no region, every name-resolving consumer (Device Map "My regions", the dashboard region filter, `recipientDeviceRegion`, level-scoped routing) quietly reaching nothing. A delete has no new name to move an assignment to, so the assignment survives and a warning Event names who now holds a dangling one. The rename bumps `notificationRecipientService.bumpRecipientIndex()`. The downstream consumer (list filters, map scoping) still lands in a separate change.

**SSO/LDAP login + IdP group mapping.** Beyond local accounts and Azure SAML, Polaris supports **OIDC** (Authorization-Code + PKCE via `openid-client`; `oidcAuthService.ts`), **LDAP/AD bind** login (`ldapAuthService.ts` over the shared `ldapClient.ts`; LDAP routes through the existing `POST /auth/login` form), and **Entra Application Proxy header-based SSO** (`entraProxyAuthService.ts`; for installs published externally through Entra App Proxy — see below). `authProvider` is now `"local" | "azure" | "oidc" | "ldap" | "entra-proxy"`. At SSO/LDAP login the user's IdP groups are matched against `GroupMapping` rows (`groupMappingService.resolveGroupsToAccess`, scoped by provider — `GROUP_MAPPING_PROVIDERS = oidc/ldap/saml/entra-proxy`) to assign a role + tags: **highest-privilege role wins** (`rankRole` in `permissions.ts`), tags from all matched groups union. No match → keep an existing user's role (new user → `readonly` + `needsRoleReview`). Group-mapping CRUD is gated on `users=fullwrite` (no new function key) and exposed at `/api/v1/group-mappings`; managed in the UI under Users → Group Mappings. **Security caveat:** a mapping to an admin-equivalent role makes IdP group membership a path to Polaris admin (outside the `lastAdminEquivalent` guard) — `groupMappingService` stamps a warning Event when one is created/updated. OIDC requires `POLARIS_PUBLIC_URL` (derives the redirect URI); Azure-AD's `groups` claim emits group object-IDs (GUIDs), so map those IDs unless the IdP is configured to emit names.

**Entra App Proxy header SSO (`entra-proxy`).** For installs published through Microsoft Entra Application Proxy with Entra ID pre-authentication + header-based SSO: App Proxy authenticates the user in the cloud and forwards their claims (UPN, object-ID GUID, group object-ID GUIDs) as operator-named **plain HTTP headers** (configured in the App Proxy SSO blade). Polaris reads them at `GET /auth/entra-proxy/login`, matches on `User.azureOid` (shared with SAML — a user who signs in both ways converges to one account), provisions via `ssoProvisioning`, and stamps a session. **The headers are UNSIGNED — the entire security model is source-IP trust:** Polaris honors the identity headers ONLY from operator-allowlisted App Proxy connector IPs (checked against `req.ip`; empty allowlist = header login disabled, fail closed), and a strip middleware (`api/middleware/entraProxyHeaders.ts`) removes them from every untrusted request as defense in depth. Users arriving from a trusted source are silently auto-logged-in (no login page) via the app.ts protected-page branch; a fallback button shows on the login page only when the request is trusted + carries headers. Config + trusted-IP allowlist + header-name mapping live on Users → Authentication → App Proxy (Setting key `entraProxy`, no secrets). The **Test** button reports the request's source IP as Polaris sees it — the value to put in the allowlist. Note: Entra silently omits the groups header past ~150 groups unless the App Proxy app uses "groups assigned to the application".

**Role-bound bearer tokens.** Each `ApiToken` is bound to a Role at mint time (migration `20260706000000_api_tokens_role_cutover` — replaced the prior fixed scope strings `assets:read` / `dashboard:read` / `assets:quarantine`; legacy tokens were mapped onto seeded `api-*` roles with matching matrices). Token callers pass the same `requirePermission` gates as sessions: the token's role matrix is resolved through an in-process cache invalidated by `bumpRoleVersion`, so a token reaches exactly what its role grants — including filter-don't-403 surfaces like `/search` and `/dashboard/noc-summary`. `requireSessionOrTokenPermission` is retired. `integrationIds` on the token is required when the bound role grants `assetsQuarantine` ≥ write (per-integration quarantine scoping is unchanged). Binding a token to an admin-equivalent role logs an `api_token.admin_equivalent` warning Event (same posture as group mappings). A role bound to any token refuses deletion (friendly 409). **CSRF exemption:** requests carrying `Authorization: Bearer` skip the CSRF token check in `csrf.ts` — cross-site attackers can't attach custom headers, and this is what lets token writes (quarantine push, role-granted mutations) through; authentication is still fully enforced downstream. Write routes reachable by tokens attribute Events via `requestActor(req)` (`api:<token name>`) from `auth.ts`.

**A CSRF exempt entry matches a whole path SEGMENT, never a bare string prefix.** `EXEMPT_PATH_PREFIXES` in `api/middleware/csrf.ts` lists the paths that skip the token check — pre-session or token-authenticated surfaces with no session to carry a CSRF token (`/api/v1/auth/login`, `/api/v1/auth/azure/`, `/api/setup/`, `/api/v1/agents/`, `/api/v1/ha/enroll`). `api/middleware/csrf.ts → isExemptPath()` requires the request path to equal an entry or be nested under it with a `/`; entries may be written with or without a trailing slash. **Do not go back to `startsWith`.** With a bare prefix match the `/api/v1/ha/enroll` entry — a node-registration endpoint whose only defense is the one-shot token in its body — ALSO exempted the operator routes `/api/v1/ha/enrollments/:id/approve` and `/reject`, because "enrollments" starts with "enroll". Approve is the gate that releases a bundle carrying `.env` (so `POLARIS_SECRET_KEY`), the nginx private key and the database passwords, so it is the last route in the app that should lose CSRF, and the whole enrollment design is that a token buys only the right to ASK while an operator approves against evidence. Segment matching also keeps the two exemptions that really are nested — `POST /api/v1/auth/login/totp` and `GET /api/v1/ha/enroll/:requestId` — so adding an entry no longer risks a sibling route sharing its letters. Pinned by the "CSRF posture" case in `tests/integration/haEnroll.test.ts`.

**Last-admin invariant.** `roleService.countAdminEquivalentUsers` + `roleService.isAdminEquivalentRole` (in `src/services/roleService.ts`) back the guard that refuses any operation that would leave Polaris with zero users holding `users=fullwrite` AND `roles=fullwrite`. Enforced in `src/api/routes/users.ts` on `PUT /users/:id/role` and `DELETE /users/:id`.

**No-escalation invariant (business rule 48).** The mirror of the last-admin guard, and neither replaces the other: that one refuses to DEMOTE the last admin, this one refuses to PROMOTE into the tier. `assertNoPrivilegeEscalation(req, targetPermissions, subject)` in `src/api/middleware/permissions.ts` throws **403** when the target permission set is admin-equivalent and the caller's own is not. Enforced at the four sites that could otherwise mint one: `POST /roles`, `PUT /roles/:id` (only when the body carries `permissions`), `POST /users`, `PUT /users/:id/role`. Both `users=write` and `roles=write` sit a rung below admin-equivalent and both used to be enough — the shortest path needed no existing account at all (`POST /users` on an admin-equivalent role, with a password the caller chooses). The self-edit checks ("you cannot change your own role") were never escalation guards: the escalation runs through somebody else's row. The caller's level comes from `req.roleSnapshot` then `req.session.roleSnapshot`, so a role-bound bearer token is held to the same bar as a session, and **no snapshot resolved counts as NOT admin** — it fails closed. Not four-eyes: an admin-equivalent caller is unaffected, and any target that is not admin-equivalent skips the check entirely. Server-side provisioning (`ssoProvisioning`, the seed) is outside it — no actor to test. The predicate is shared with `rankRole`'s group-mapping tie-break (`isAdminEquivalentPermissions`) so "which role wins an SSO mapping" and "who may grant it" cannot drift.

Rate limiting: 10 login attempts / 15 min per IP (limiter in `src/app.ts`). Additional per-surface limiters live in `src/api/middleware/rateLimits.ts`: TOTP confirm/disable (10 / 15 min, mirrors login), OIDC login kick-off (30 / 15 min), Entra App Proxy header login (60 / 5 min — deliberately generous: all App Proxy users share the connector IP, and there's no guessable-credential surface), IdP-driven SSO callbacks + the public `/entra-proxy/config` probe (300 / 5 min — a callback carries a signature-validated assertion rather than a guessable credential, so the limiter bounds flood volume, not guessing; per-IP, and one NAT egress address can carry a whole site's shift-start logins), admin maintenance/backup/logo/login-access routes (120 / 5 min), SIEM quarantine verify (300 / 5 min), agent bearer router (1200 / 5 min — per-IP, far above any healthy agent's cadence), agent binary downloads (60 / 5 min). The first-run setup server has its own limiters (whole server 600 / 5 min; DB-touching wizard routes 30 / 15 min) built from the same `makeRateLimiter` factory. Azure SAML SSO is optional; users are auto-provisioned on first login with the `readonly` role.

**Stale-Secure-cookie gotcha (HTTPS → HTTP downgrade):** A `Set-Cookie` from a non-secure origin is silently rejected by Firefox/Chrome if a same-name `Secure`-flagged cookie already exists, and the rejection extends to `Max-Age=0` deletions. The middleware in `csrf.ts` detects the case (HTTP request, no `polaris_csrf` cookie sent at all) and returns a specific error message instructing the operator to clear cookies for the site. The frontend in `public/js/api.js` does a parallel pre-check before mutating requests. Operator-clears-cookies path is the only reliable recovery on Firefox/Chrome.
