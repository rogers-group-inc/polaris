# Endpoints — auth, IPAM, dashboards, users/roles/tokens/credentials

Verbatim from ARCHITECTURE.md → API Endpoints. Gate notation: `key:level`.
All routes are prefixed `/api/v1/`. Auth guards are applied in `src/api/router.ts`.

### Auth — public
- `POST   /auth/login`
- `POST   /auth/logout`
- `GET    /auth/me`                             — Session probe. Returns `{ authenticated: false }` for unauthenticated callers; otherwise `{ authenticated: true, username, authProvider, role: { id, name, color, isProtected, permissions, updatedAt }, regionTags: { user, role, group, effective }, otherTags: { user, role, group, effective } }` (`color` read live each call; `group` is re-resolved from `User.ssoGroups` via `resolveGroupsToAccess` so a GroupMapping edit shows next page load without re-login). The frontend reads `role.permissions[functionKey]` to gate menu items / buttons (see `permAtLeast()` in `public/js/app.js`).
- `GET    /auth/azure/config`                   — Azure SSO feature flag
- `GET    /auth/azure/login`                    — Initiate Azure SAML login
- `POST   /auth/azure/callback`                 — SAML assertion callback
- `POST   /auth/azure/logout`                    — SAML single-logout
- `GET    /auth/oidc/config`                    — OIDC feature flag (login page button)
- `GET    /auth/oidc/login`                     — Initiate OIDC Authorization-Code login (stashes state/nonce/PKCE in session, redirects to IdP)
- `GET    /auth/oidc/callback`                  — OIDC code exchange + ID-token validation + provision. Top-level GET, so SameSite=Lax session cookies are sent (unlike the SAML POST callback)
- `GET    /auth/entra-proxy/config`             — Entra App Proxy header-SSO flag: `{ enabled, available }` (`available` = this request arrived from an allowlisted connector carrying identity headers → drives the fallback login button; booleans only). Public.
- `GET    /auth/entra-proxy/login`              — Read Entra App Proxy identity headers on THIS request, validate source-IP trust, provision, stamp session, redirect to validated `?next=` (default `/`). Both the login-page button and the app.ts silent auto-login land here; all failures redirect to `/login.html?error=…`. Rate-limited (`entraProxyLoginLimiter`, 60/5min).
- LDAP login uses the shared `POST /auth/login` form (routes to LDAP when the account is an LDAP user or the username is unknown and LDAP is enabled)
- SSO/LDAP config (admin, `serverSettingsSystem:write`): `GET|PUT /auth/azure/settings` + `POST /auth/azure/test`, `GET|PUT /auth/oidc/settings` + `POST /auth/oidc/test`, `GET|PUT /auth/ldap/settings` + `POST /auth/ldap/test`, `GET|PUT /auth/entra-proxy/settings` + `POST /auth/entra-proxy/test`
- `POST   /auth/login/totp`                     — Second step of two-phase login when TOTP is enabled. Body: `{ pendingToken, code, isBackupCode? }`. `pendingToken` is returned by `POST /auth/login` whenever the caller's account has `totpEnabledAt` set — until this endpoint consumes it, the session is not issued.

### TOTP self-management — `requireAuth`
- `GET    /auth/totp/status`                    — `{ authProvider, enabled, enrolling, backupCodesRemaining }`
- `POST   /auth/totp/enroll`                    — Starts enrollment for the current user. Returns `{ secret, otpauthUri, qrSvg }`. Only allowed on `authProvider = "local"` accounts that are not already fully enrolled.
- `POST   /auth/totp/confirm`                   — Finalize enrollment by verifying the first 6-digit code. Body: `{ code }`. Returns `{ ok, backupCodes: string[] }` — shown once.
- `DELETE /auth/totp`                           — Self-disable. Requires a current TOTP or backup code. Body: `{ code, isBackupCode? }`.

### Subnets — `requireAuth`
- `GET    /subnets`                             — List (filter by blockId, status, tag, createdBy)
- `POST   /subnets`
- `GET    /subnets/:id`                         — Get + reservation list
- `PUT    /subnets/:id`
- `DELETE /subnets/:id`                         — 409 if active reservations exist
- `POST   /subnets/next-available`              — Auto-allocate next available subnet of given prefix length
- `POST   /subnets/bulk-allocate`                — Allocate multiple subnets in one call from a template. Body: `{ blockId, prefix, entries: [{name, prefixLength, vlan?} | {skip: true, prefixLength}], tags?, anchorPrefix? }`. Each non-skip entry becomes a subnet named `<prefix>_<entry.name>` (e.g. `Riverbend_Hardware`). **Skip entries** reserve address space inside the packed region without creating a subnet — used to leave gaps between allocations. **Anchor-based, all-or-nothing:** entries are packed into a single contiguous region aligned to `max(anchorPrefix, smallest-block-containing-the-group)`; `anchorPrefix` defaults to 24 if omitted. The whole call happens in one transaction — either every subnet is created or none are. Response: `{ created, anchorCidr, effectiveAnchorPrefix }`.
- `POST   /subnets/bulk-allocate/preview`        — Non-mutating preview of the above. Same body minus `prefix` and `tags`, with a lenient entry schema (no name required) so the modal can live-update footprint while the user is still filling rows. Response: `{ fits, anchorCidr, effectiveAnchorPrefix, assignments, totalAddresses, slashTwentyFourCount, blockCidr, error }`.
- `GET    /subnets/exclusions`                   *(subnets:read)* — every `SubnetExclusion` (business rule 42), each decorated with `matchCount` + up to 20 `matches` naming the live networks it covers. Declared BEFORE `/:id` or the literal path is captured as a subnet id. Read-level because what has been kept OUT of the networks list is exactly the thing worth being able to look up while reading it.
- `POST   /subnets/exclusions`                   *(subnets:**fullwrite**)* — exclude a CIDR. Body `{ cidr, name, notes? }`; the CIDR is normalized (host bits zeroed) and IPv4-only, a duplicate 409s. Returns the created row WITH its `matchCount`/`matches` — networks already in the list are reported and deliberately left in place, so an operator sees what an exclusion did NOT clean up. Writes `subnet.exclusion.created`.
- `PUT    /subnets/exclusions/:id`               *(subnets:**fullwrite**)* — name / notes only. The schema carries no `cidr`: it is the exclusion's identity, and re-pointing one in place would silently un-exclude the space the operator excluded — changing the range is a DELETE plus a POST. Writes `subnet.exclusion.updated`.
- `DELETE /subnets/exclusions/:id`               *(subnets:**fullwrite**)* — stop excluding. Discovery may record that address space again on its next run. Writes `subnet.exclusion.deleted`.
- `GET    /subnets/archived`                     *(subnets:read)* — retired subnets, newest first (business rule 41). Query `?cidr=&blockId=&fortigateSerial=&limit=&offset=`; `cidr` is a substring match, `limit` defaults 50 / caps 200, and `total` is the UNPAGED match count. Each row carries `_count.reservations`. MUST stay declared before `GET /subnets/:id`, or `/subnets/archived` is captured as a subnet id.
- `GET    /subnets/archived/:id`                 *(subnets:read)* — one retirement with every `ArchivedReservation` it held, ordered by address.
- `POST   /subnets/:id/archive`                  *(subnets:**fullwrite**)* — surfaced as **Archive** in the Networks row menu. Retire a subnet: snapshot it + its reservations into the archive, then delete the live row, freeing its CIDR so a replacement gate's identical address space can be recorded. Returns `{ archivedSubnetId, cidr, reservationCount }` and writes one `subnet.archived` Event. `fullwrite` rather than the ownership-aware `write` every other mutation on this router uses: a discovered subnet carries `createdBy: null` so an ownership-scoped caller could never reach one anyway, and retiring a site's address space is not an own-rows action. Deliberately NOT subject to business rule 4's active-reservation protection — that guards against accidental DESTRUCTION, and this preserves everything it moves.
- `POST   /subnets/:id/refresh`                  *(user-or-above)* — Per-subnet "refresh from device" action invoked by the **Refresh** button in the IP panel slide-in. Queries the originating FortiGate for ONE DHCP scope (CMDB reservations + live leases) using whichever transport the integration is configured for (FMG proxy / FMG direct / standalone FortiGate REST), reconciles against Polaris's reservation rows for the same subnet, and bumps `Subnet.lastDiscoveredAt` on success. Intentionally narrower than the full `discoverDhcpSubnets` pipeline — only touches `dhcp_reservation` + `dhcp_lease` rows on this subnet, leaves manual / VIP / interface-IP rows alone (the IP-level conflict reconciliation that the full sync runs is deferred to the next integration-wide discovery cycle). 400 when the subnet wasn't discovered by an FMG/FortiGate integration or has no `fortigateDevice`. Returns `{ lastDiscoveredAt, created, updated, released, skipped }`. Writes one `subnet.refresh` Event. See `subnetRefreshService.ts`.

### Reservations — `requireAuth`
- `GET    /reservations`                        — List (filter by owner, projectRef, status, createdBy). Each row is decorated with `pushEligible: boolean` computed from the row's `subnet.integration` (true when the originating integration is `fortimanager`/`fortigate` AND `config.pushReservations === true` AND `ipAddress` is non-null). The integration config blob is stripped from the response — callers only need the computed flag and config can carry credentials. The mobile Reservations tab uses this flag to color the **Reserve** button green when confirming will also write the entry to the FortiGate.
- `POST   /reservations`                        — Create. An omitted `owner` auto-stamps to the caller's username (mirrors the PUT auto-stamp; an explicitly typed owner wins). Body accepts an optional `macAddress` (12 hex with optional `:`, `-`, or `.` separators). When the target subnet was discovered by an FMG integration with `pushReservations=true`, MAC becomes **required** and the create attempts a write+verify against the FortiGate — see `reservationPushService.ts`. Outcomes: (a) push success → reservation returned with `pushStatus="synced"` and `pushedScopeId`/`pushedEntryId` stamped; (b) **transient device-side failure** (FortiGate offline, FMG unreachable, network timeout, generic 5xx — classified by `classifyPushError`) → reservation persists with `pushStatus="pending"`, `pushQueuedAt=now`, `pushAttempts=1`, `pushError=<message>`, and the retry job pushes it once the gate recovers (see "Queued push lifecycle" below); (c) **permanent failure** (4xx, verify mismatch, auth) → create aborts with a clear 4xx/5xx (no Polaris ghost). **Pre-flight optimization**: if the originating FortiGate's firewall Asset is monitored AND `monitorStatus="down"`, the transport attempt is skipped entirely and the row is queued immediately (saves the 15s+ transport timeout on the create critical path). Audit Events: `reservation.push.succeeded` (info, synced path), `reservation.push.queued` (info, transient path), `reservation.push.failed` (warning, permanent path) — in addition to the usual `reservation.created` Event. The same MAC + push behavior applies to `POST /reservations/next-available`.
- `POST   /reservations/next-available/preview` — Which addresses WOULD be allocated: `{ subnetId, count (1..64), contiguous? }` → `{ ips, count, contiguous }`. Backs the IP panel Auto-Allocate modal's **Multiple IPs** mode, which fills a row per address so the operator can name each one before anything is written. Creates nothing, so it is gated `reservations:read` rather than the ownership gate the create carries; declared before `/:id`. Selection is `reservationService.findNextAvailableIps` over the pure `utils/ipAllocation.ts`, and the taken-set is EVERY active reservation regardless of `sourceType` — so a VIP or an interface IP is simply never offered. `contiguous` is refused rather than downgraded when it can't be met (409 naming the largest run that exists) — a short run is not what was asked for. The modal then creates each row through `POST /reservations` with an explicit `ipAddress`, ONE REQUEST PER ADDRESS: a push-eligible network writes every reservation to the FortiGate, so a 40-address batch behind one request would outlive the proxy read timeout with nothing to show. Per-row requests buy progress while it runs, a per-row outcome when it finishes, and an honest report when an address was claimed by someone else between the preview and the create. Ceiling is `MAX_BULK_ALLOCATE` (64) — a bound on how big a form an operator can be asked to fill in, not a database limit.
- `GET    /reservations/:id`
- `PUT    /reservations/:id`                    — Update. **Refuses (409) on a `vip` or `interface_ip` row** — see the DELETE note below.  Body accepts `hostname` / `owner` / `projectRef` / `expiresAt` / `notes` plus `macAddress` (string; empty clears it, only allowed on non-push-eligible subnets). When the subnet is push-eligible AND the MAC changes, the service pushes a PUT to the FortiOS reserved-address entry via `updatePushedReservation()`, verifies on read-back, then commits the Polaris write — device-side failure throws and the Polaris row stays untouched so the two views never drift. Discovered (never-pushed) DHCP reservations look the entry up by IP on the resolved scope and are upgraded to "Polaris-pushed" on success. Hostname-only or notes-only changes are NOT re-pushed (the FortiOS description only refreshes as a side effect of a MAC update — when MAC changes, the new hostname/notes are picked up alongside). **Queued rows (`pushStatus="pending"`) skip the device-update path entirely** — the new payload is just stashed in Polaris and the retry job will use it on the next push attempt. MAC may be freely changed on a queued row (still required, can't be cleared). Audit: `reservation.push.updated` (info) on success, `reservation.push.update_failed` (warning) on failure.
- `DELETE /reservations/:id`                    — Release. **Refuses (409) on a `vip` or `interface_ip` row**: a FortiGate virtual IP and a statically-configured router/firewall interface address are owned by the DEVICE's own config, not by anything Polaris granted, so Polaris reports them and offers no Reserve / Release / Edit. Creating over one was already refused (neither sourceType is in `isSupersedableByCreate`, so the collision check 409s); `assertNotDeviceOwned` in the route file closes the other two verbs. Enforced at the ROUTE layer rather than in the service, because discovery's own reconcile still has to refresh and retire these rows. The IP panel renders both read-only with a purple `.ip-dot-device-config` status dot ("VIP" / "Interface"), and the mobile reservations tab drops Edit + Release for the same two types.  Best-effort unpush from the FortiGate before flipping the row to `released`. Device-side failure does **not** block the release — Polaris release proceeds and writes `reservation.unpush.failed` (warning) so the orphan on the device is auditable. "Already absent" (operator deleted on the device) writes `reservation.unpush.succeeded` with `alreadyAbsent: true`. **Queued rows (`pushStatus="pending"`) skip both the unpush AND the lease-release blocks** — nothing has been written to the device yet, so there's nothing to clean up; the release just flips the Polaris row and writes `reservation.push.queued.released` (info) for the audit trail. **Discovered `dhcp_lease` rows additionally fire a best-effort lease release** against the originating FortiGate (`POST /api/v2/monitor/system/dhcp/release-lease` with `{ip}`, routed through the same FMG-or-standalone-FortiGate transport as reservation push), gated on the originating integration's `pushReservations` toggle (the **DHCP Push** tab — both halves of the Polaris → FortiGate DHCP write path live under that single toggle). When the toggle is off, freeing a lease only flips the Polaris row and the FortiGate is not contacted. When it's on, FortiOS only forgets the *current* lease — the same client can DHCP-acquire the IP back on its next request, so this is "expire now" not a block. Success writes `reservation.lease_release.succeeded` (info); device-side failure writes `reservation.lease_release.failed` (warning) without blocking the Polaris release.

#### Stale-reservation alerts (mixed scoping)
- `GET    /reservations/stale-settings`         *(auth)* — `{ staleAfterDays }`. 0 = disabled.
- `PUT    /reservations/stale-settings`         *(admin)* — `{ staleAfterDays }`. Default 60. The setting feeds both the `flagStaleReservations` job and the alert lister; lowering it is reflected within ~6 hours (the next job tick).
- `GET    /reservations/alerts?show=active|ignored` — Default `active` returns non-ignored stale rows **on non-deprecated subnets**; `ignored` returns every row the operator has set `staleIgnored=true` regardless of threshold or subnet status so admins can review and un-silence. Each entry: `{ id, ipAddress, hostname, macAddress, subnetId, subnetCidr, subnetName, createdAt, lastSeenLeased, lastSeenArp, staleNotifiedAt, daysSinceSeen, fortigateDevice, pushedToId, pushedToName, assetLastSeen, assetPresenceMatch }`. `assetPresenceMatch` (`"mac" | "ip" | null`) + `assetLastSeen` report the Asset that correlated to the reservation; `daysSinceSeen` counts from the freshest of the DHCP lease, the ARP confirmation (`lastSeenArp`), and that asset's lastSeen, so a statically-addressed device that's still on the network never appears here. Reservations whose subnet is `deprecated` (its owning FortiGate was decommissioned) are excluded from the active list/count entirely — the network is gone, so per-IP stale alerts would be noise.
- `GET    /reservations/alerts/count`           — Just `{ count }`. Always counts the **active** list — ignored rows don't drive the sidebar badge.
- `POST   /reservations/:id/snooze`             *(user-or-above)* — Sets `staleSnoozedUntil = now + staleAfterDays` so the row is suppressed from the active alert list. Cleared automatically when discovery sees the IP active again. Returns `{ reservationId, snoozedUntil, daysAdded }`. Writes `reservation.stale.snoozed` (info).
- `POST   /reservations/:id/stale-ignore`       *(networkadmin)* — Permanently ignore stale alerts on this row (`staleIgnored=true`). NOT cleared by discovery activity; operator's intent persists across online/offline cycles. Writes `reservation.stale.ignored` (info).
- `DELETE /reservations/:id/stale-ignore`       *(networkadmin)* — Un-ignore. Writes `reservation.stale.unignored` (info).

#### Queued push lifecycle (mixed scoping)
- `GET    /reservations/push-queue`             *(auth)* — Lists every reservation in `pushStatus IN ("pending", "failed_permanent") AND status="active"`, sorted by `pushQueuedAt` ascending (oldest first). Each row carries the full reservation plus `subnet: { id, cidr, name, vlan, fortigateDevice }` and `pushedTo: { id, name, type, enabled }` so the UI can render hostname / IP / MAC / target FortiGate / integration name without N+1 fetches. Drives the **Push queue** filter view in the Events page Alerts panel.
- `GET    /reservations/push-queue/count`       *(auth)* — `{ count }`. Contributes to the Events Alerts button badge and the single Events sidebar dot, alongside discovery conflicts (`/conflicts/count`) and stale-reservation alerts (`/reservations/alerts/count`). The dot is red when there are conflicts and yellow otherwise (red precedence); there is no separate IPAM dot.
- `POST   /reservations/:id/retry-push`         *(reservations write — own rows; fullwrite for any)* — Operator-triggered single-row retry. Allowed when `pushStatus IN ("pending", "failed_permanent")`. Bypasses the monitored-gate `monitorStatus="up"` readiness gate AND the unmonitored-gate exponential backoff window. `failed_permanent` rows are flipped back to `pending` first so the retry path treats them uniformly. Still respects eligibility re-check (subnet drift cancels the queue + keeps the Polaris row as plain manual) and discovery-supersede (collision → `failed_permanent`). Returns `{ outcome: "synced" | "transient" | "permanent" | "cancelled" | "superseded", reservation }`. Writes `reservation.push.queued.retry_manual` (info) on entry, plus the same per-outcome Events the periodic retry tick emits.

### Dashboard — `requireAuth` (per-section permission filtering)
- `GET    /dashboard/summary[?sections=blocks,recent,assetTypes,monitorAlerts][&recentSourceTypes=manual,dhcp_reservation,...]` — Backs the home Dashboard's built-in IP-space widgets. `?sections=` narrows the response to the named sections so each widget fetches only what it renders (widgets call it via the 15s-memoized `PolarisWidgets.getSummary({sections,...})`); absent = the full legacy shape `{ blockUtilization, recentReservations, assetTypeCounts, monitorAlerts, monitorAlertsOverflow }`. Unknown section names drop silently. Every section is served through a 10s server-side TTL cache (keys carry the recent-section params) so concurrent widgets/tabs share one computation; permission-denied sections return empty without entering the cache. `blockUtilization` is reused from `utilizationService.getGlobalUtilization()` (no extra DB hit). `recentReservations` is the 10 most-recent active reservations — default filter is `sourceType="manual"` so DHCP discoveries / leases / VIP echoes don't crowd out reservations a person actually typed in; the optional `recentSourceTypes` query param (comma-separated source-type names) lets a widget broaden the filter (e.g. include `dhcp_reservation` to surface Polaris-pushed reservations alongside manual rows). Unknown source-type values are dropped silently; if every value is unknown the filter becomes a no-op rather than 0 rows. Each row includes hostname, MAC, createdBy, and the resolved `{subnetId, subnetCidr, subnetName, vlan}` so the card renders without a second fetch. `assetTypeCounts` is a `prisma.asset.groupBy` over `assetType` excluding `status in (decommissioned, disabled)` — feeds the SVG pie chart. `monitorAlerts` is monitored assets currently in `warning` or `down`, ordered by `monitorStatusChangedAt desc nulls last` (newest transitions first), capped at 50 with `monitorAlertsOverflow` flagging when there's more. **Filter-don't-403 gating**: the dashboard is the redirect target for users bounced off gated pages, so the endpoint never 403s — instead each section is gated on the caller's read access (`ipBlocks≥read` → blockUtilization, `reservations≥read` → recentReservations, `assets≥read` → assetTypeCounts + monitorAlerts) and denied sections return empty arrays with the response shape unchanged. Bearer-token callers have no role snapshot → all sections empty. Covered by `tests/integration/permissionGates.test.ts`.
- `GET    /dashboard/noc-summary[?feeds=topCpu,downNodes,...]` — Feed endpoint backing the SolarWinds-style NOC widgets (status tiles, Down Assets, Down Interfaces, Highest Avg CPU/Memory, Slowest Response, Packet Loss, Highest Disk Usage, Highest Temperature, Stale Polls, Recent Reboots, Active Alerts, Sites with Issues, Status Map uses `/map/sites` instead). `?feeds=` (names from `nocDashboardService.NOC_FEED_NAMES`; `status` = the three tile keys, `downNodes` unwraps `.nodes`) narrows to the named subset so each widget fetches only its own feed and renders as soon as that query returns; unknown names drop silently; absent = the full payload. Every (feed, filter, cap) computation is served through a 10s server-side TTL cache (`NOC_FEED_CACHE_TTL_MS`) shared across widgets/tabs/kiosk walls. The full shape: `{ statusCounts:{total,up,down,warning,unknown,recovering,maintenance}, uptimePercent, activeAlertCount, downNodes[], downInterfaces[], downIpsecTunnels[], topCpu[], topMemory[], slowestResponse[], packetLoss[], diskUsage[], temperature[], stalePolls[], recentReboots[], activeAlerts[], sitesWithIssues[] }` (`diskUsage[]` rows carry a `detail` = mount path; `temperature[]` rows are per-sensor — latest reading per (asset, sensorName) from the temperature-class rows of `asset_hardware_sensor_samples`, always °C, with `detail` = sensor name). **Maintenance-window assets are excluded from every down/warning/stale feed** (`status="maintenance"` freezes `monitorStatus`, so the frozen value is not live state — the shared `NOT_IN_MAINTENANCE` where-spread in `nocDashboardService`, mirrored in the sites-with-issues raw SQL and the `/summary` monitorAlerts clause) and are instead counted into `statusCounts.maintenance` (still in `total`, never in up/down/warning/unknown or the uptime gauge) — the Status Summary widget's purple "Maint" tile. `?includeDependencyDown=1` (the Down Assets widget's gear toggle; "1"/"true"/"yes") drops the `dependencySuppressed: false` filter from the `downNodes` feed — absent (the default) keeps suppressed assets out so a dead gate reads as ONE outage rather than one per device behind it, and the flag participates in that feed's cache key (`usesDepDown`) so a toggled widget can never be served the excluded list. Every `downNodes[]` row carries `dependencySuppressed`, which the widget renders as a "Dep. Down" badge. `downNodesTotal` = the TRUE (uncapped) down-asset count from an indexed `asset.count` over the same where — the Down Assets widget stamps it as a red pill on its header, so the overall number is exact even when `downNodes[]` is clipped by the row cap. `downInterfaces[]` = interfaces that are admin-up but oper-down AND selected for monitoring — the CTE joins `assets` on `ifName = ANY(monitoredInterfaces)` so only pinned interfaces qualify, filtered before the LIMIT (`getDownInterfaces`, one windowed single-pass CTE over `asset_interface_samples` for latest-per-`(asset,ifName)` + last-up timestamp, then a monitored-scope hydrate findMany), each row `{assetId, hostname, ipAddress, assetType, ifName, ifLabel, gate, lastUpAt}` where `gate` = the FortiGate the interface lives on (firewall → own hostname; managed FortiSwitch/FortiAP → parent `learnedLocation`). `downIpsecTunnels[]` = fully-down IPsec tunnels that are ALSO selected for monitoring — same pin gate as interfaces, joining `assets` on `tunnelName = ANY(monitoredIpsecTunnels)` before the LIMIT, so an unpinned tunnel (e.g. one riding a dead parent link, whose CMDB-synthesized samples stay perpetually fresh) never shows as an outage (`getDownIpsecTunnels`, same CTE shape over `asset_ipsec_tunnel_samples` where `status='down'`), each row `{assetId, hostname, ipAddress, assetType, tunnelName, parentInterface, remoteGateway, gate, lastUpAt}` — `parentInterface` is the phase1-interface WAN port the tunnel rides. The frontend `downInterfaces` widget (labeled "Down Interfaces") merges both arrays into one gate-grouped list — gates ordered **youngest outage first** (newest `lastUpAt` among the gate's rows; the row-limit clip also keeps the freshest outages), rows **alphabetical by name within each gate**, and the merged pre-clip total stamped as a red pill on the widget header (`PolarisWidgets.setHeaderCount`) — rendering a down tunnel's parent physical interface inline; its config has per-kind toggles (`showInterfaces` / `showTunnels`). Sections computed by `nocDashboardService.getNocSummaryPayload` (feed registry + per-feed TTL cache), each scale-checked flat to 2000 assets (groupBy / count / one windowed DISTINCT-ON or aggregate / one bounded findMany — no per-row awaits). Same **filter-don't-403** contract as `/summary`: asset-sourced sections gate on `assets≥read`, Event-sourced sections (`activeAlerts`, `recentReboots`) on `events≥read`; denied sections return empty/zero with the shape unchanged (and never enter the cache). Accepts optional per-widget filters `?assetTypes=` (the enabled built-in types) + `?regionTags=` (region names — the caller's "My regions" or a widget's Selected-regions pick) + `?fortigates=` (FortiGate device names — the widgets' Selected-FortiGates per-site narrowing; matches assets behind any named gate via `learnedLocation` / `AssetFortigateSighting`, exact-insensitive — the same haystacks as the tag/maintenance "Behind FortiGate" criteria — with the `__none__` sentinel = the picker's "(No FortiGate)" entry for gate-less assets; combined with regions + asset types this builds one-site dashboards, e.g. a single gate's switches/APs) → `resolveFilteredAssetIds` (cached per filter) constrains every requested feed to the matching asset set. Frontend memoizes for ~15s **per (feeds, filter, limit)** via `PolarisWidgets.getNocSummary(opts, feeds)`. `topCpu`/`topMemory` rank by the per-asset **average of the most-recent N samples** (not the instantaneous last reading) — N comes from `?samples=` (the widgets' "Average over" gear control; default 10, clamped to a 100 ceiling, 1 = latest sample only; the frontend omits the param at the default so those widgets share one cached payload, and only the sample-averaged feeds key their server cache on it); `slowestResponse` averages a fixed most-recent 10. `packetLoss[]` excludes assets at 100% loss (zero successful probes in the window, enforced in the SQL HAVING) — a hard-down node is Down Assets material, not packet loss. Every list widget has a shared Row-limit control (`5/10/20/50/100/1000`; helpers in `public/js/widgets/index.js`); a widget picking the **1000** option sends `?limit=N` (clamped to a 1000 ceiling) which caps every *requested* feed at N — ≤100 omits the param, shares the default-cap payload, and clips client-side (the four `_topnBar` widgets default to a 20-row limit with the red-row guarantee; see the widgets file-map entry). The `summary` endpoint takes a parallel `?recentLimit=` (default 10, clamped 1000) for the recentReservations widget. The `getNocSummary`/`getSummary` fetches carry a 20s client abort-timeout so a large request degrades instead of hanging the widget.

### User Dashboard — `requireAuth`
Per-user dashboard layout. One row per user in `UserDashboard`; absent row = empty dashboard. No admin override (strictly per-caller); no Event audit log (UI preference, not security-relevant).
- `GET    /me/dashboard` — Returns the caller's layout, or `{ version: 3, dashboards: [], activeId: "" }` when no row exists yet (drives the "Customize Page → Add Widgets" empty-state). NOT re-validated — a stored legacy v1/v2 row is returned untouched and wrapped into one "Dashboard 1" tab client-side.
- `PUT    /me/dashboard` — Zod-validates the full v3 layout, upserts, returns the saved shape. Layout shape: `{ version: 3, dashboards: [{ id (uuid), name, columns: Column[] }], activeId }` where `Column = { id (uuid), width 3|4|6|12, widgets: WidgetInstance[] }` and `WidgetInstance = { id (uuid), type, height 1|2|3, config }`. Caps: ≤24 dashboards, ≤12 columns and ≤64 widgets each; `activeId` must name one of them. The column/widget schema + caps come from `utils/dashboardLayout.ts`, SHARED with the saved-dashboard registry so a blob one surface accepts is always renderable by the other. The client always normalizes to v3 before saving, so PUT only accepts v3.

### Table tabs — scope-resolved function key (per-user)
The Assets page's view tabs. Same scope→key resolution as saved filters below, but both verbs need only **read**: a tab is the operator's own view of data they can already see, so a readonly user gets tabs. Strictly per-caller (no admin override), no Event audit — UI preference, the `/me/dashboard` pattern. Session callers only.
- `GET /me/table-tabs?scope=assets` — `{ version: 1, tabs: [{ id, name, state, savedFilterId, savedFilterName }], activeId }`, or the empty layout `{version:1,tabs:[],activeId:""}` when the caller has never saved tabs (the client then materializes one default tab from whatever the table is showing and doesn't write until something changes).
- `PUT /me/table-tabs?scope=assets` — full replace. ≤20 tabs, unique ids, names ≤40 chars; each tab's `state` goes through the same `sanitizeFilterState` a preset does. A stale `activeId` (tab closed in another window) falls back to the first tab instead of 400-ing the layout away.

### Saved dashboards — `savedDashboards`
Named dashboard canvases (Dashboard → Dashboards ▾). Unlike saved filters this has its OWN function key, because the Dashboard page has no key to inherit — it is gated per WIDGET. The `savedDashboards:read` floor is declared INSIDE the route file, so the SECOND mount (the Dash wallboard listener, session-less and GET-only) shares it; publishing is checked per request from the payload's `visibility`. Mutations are session callers only — a dashboard has an owner, and the wallboard mount 405s every write verb.
- `GET    /saved-dashboards`             *(`savedDashboards:read`)* — `{ dashboards: [{ id, name, visibility, ownerId, ownerName, isOwner, widgetCount, layout, createdAt, updatedAt }] }` — everything the caller owns plus every other user's `public` one, name-ascending. **Also mounted on the Dash wallboard listener**, where there is no session: that caller gets PUBLIC rows only and nothing reads as owned.
- `GET    /saved-dashboards/:id`         *(`savedDashboards:read`)* — one row. **404, not 403**, when the caller can't see it (the `GET /alerts/:id` posture — that an id exists is itself something an anonymous wallboard viewer shouldn't learn). Declared LAST on the mount. The wallboard re-reads its pinned screen through this.
- `POST   /saved-dashboards`             *(read; `write` when `visibility:"public"`)* — Body `{ name, visibility, layout }`. Keeping a PRIVATE dashboard needs only read, because the ungated `/me/dashboard` already stores the same layout; PUBLISHING is what reaches other operators and the unauthenticated wallboard. A same-(owner, name) POST **updates** instead of duplicating. 201 with the saved DTO. Session callers only (the wallboard mount is GET-only app-wide, so this doesn't exist there).
- `PUT    /saved-dashboards/:id`         *(owner only, same level rules)* — Rename / change visibility / replace the layout.
- `DELETE /saved-dashboards/:id`         *(owner: read; someone else's: `fullwrite`)* — 204. The fullwrite branch is housekeeping (a departed colleague's published screen).

`layout` is validated by `sanitizeDashboardLayout` over the same `utils/dashboardLayout.ts` schema `/me/dashboard` uses — this blob is replayed into other operators' browsers and onto unauthenticated wallboards.

### Saved table filters — scope-resolved function key
Named filter+sort presets for a list page (Assets → Filters ▾). There is no dedicated function key: the request's `scope` resolves to the key that already gates that page (`assets` → `assets`), checked inline with `ensureRoleSnapshot` + `hasPermission` because the key isn't known until the body/query is read. Session callers only — a preset has an owner, and bearer tokens have no user identity (401).
- `GET    /saved-filters?scope=assets`   *(scope key: read)* — `{ filters: [{ id, scope, name, visibility, ownerId, ownerName, isOwner, state, createdAt, updatedAt }] }` — everything the caller owns plus every other user's `public` preset, name-ascending. Orphaned private rows (owner deleted) match nobody and are invisible.
- `POST   /saved-filters`                *(scope key: read; `write` when `visibility:"public"`)* — Body `{ scope, name, visibility, state }`. Publishing to everyone is a write to shared state; keeping a private preset only needs the read the page already required. A same-(scope, owner, name) POST **updates** the existing row instead of duplicating, so the client's "save over this name" flow is one call. 201 with the saved DTO.
- `PUT    /saved-filters/:id`            *(owner only, same level rules)* — Rename / re-scope visibility / replace state. `scope` cannot be changed.
- `DELETE /saved-filters/:id`            *(owner: read; someone else's: `fullwrite`)* — 204. The fullwrite branch is housekeeping (a departed colleague's shared preset).
`state` is validated by `sanitizeFilterState` on every write — see the service entry; anything table-sf.js can't itself produce is a 400 rather than stored.

### Users — `users` function key
- `GET    /users`                               *(read)* — Every row is returned with the joined `role: { id, name, color, isProtected, isBuiltIn }` and `regionTags: string[]` (per-user scope).
- `POST   /users`                               *(write)* — Body: `{ username, password, roleId, regionTags?, otherTags? }`. The legacy `role: <enum>` field is no longer accepted. Refused with **403** when `roleId` names an admin-equivalent role and the caller is not admin-equivalent (business rule 48) — this was the shortest escalation path in the API, since it needs no existing account and the caller picks the password.
- `GET    /users/:id`                           *(read)*
- `DELETE /users/:id`                           *(write)* — Refused with 409 when this would leave Polaris with zero users holding `users=fullwrite` AND `roles=fullwrite` (last-admin-equivalent invariant).
- `PUT    /users/:id/password`                  *(write)* — Local accounts only.
- `PUT    /users/:id/role`                      *(write)* — Body: `{ roleId }`. Refused with 400 when reassigning yourself; **403** when the target role is admin-equivalent and the caller is not (business rule 48 — the self-check is not an escalation guard, since the escalation goes through somebody else's row); 409 when this would break the last-admin-equivalent invariant. Auto-clears `needsRoleReview` since picking a role is an implicit review.
- `PUT    /users/:id/regions`                   *(write)* — Body: `{ regionTags?: string[], otherTags?: string[] }` (each optional; omitted dimension left unchanged, empty array clears). Validation via `tagNormalize`: trim, drop empties, dedupe case-insensitively, ≤64 entries, each ≤64 chars. Writes one `user.regions_updated` Event with the per-dimension from/to diff. These are operator-set tags only — group-derived tags are computed at `/auth/me`, never written here.
- `DELETE /users/:id/totp`                      *(write)* — Admin-initiated TOTP reset (for "lost device" recovery). Clears the secret and backup codes so the user can re-enroll on next login.
- `GET    /users/role-review-notifications`     *(read)* — Sidebar feed. Returns `{ users, count }` where `users` is every row with `needsRoleReview=true`, ordered by `lastLogin` asc, projected to `{ id, username, role: { id, name, ... }, regionTags, displayName, authProvider, email, lastLogin, createdAt, ... }`. Polled every 30s by [public/js/app.js](public/js/app.js) for admins only.
- `DELETE /users/:id/role-review`               *(write)* — Dismiss the new-user notification for one user (global — hides the row for every admin).

### Roles — `roles` function key
- `GET    /roles`                               *(read)* — Every Role with `{ id, name, description, permissions, regionTags, color, isBuiltIn, isProtected, userCount, createdAt, updatedAt }`. The frontend filters `isProtected=true` rows (admin + readonly) out of the editable list.
- `GET    /roles/:id`                           *(read)*
- `GET    /roles/functions`                     *(read)* — `{ accessLevels: ["none","read","write","fullwrite"], functions: FunctionKeyDef[] }` — the 25-key catalogue with `{ key, label, description, hasOwnershipDimension? }`. Single source of truth backing the permissions slide-over matrix.
- `POST   /roles`                               *(write)* — `{ name, description?, permissions, regionTags?, color? }`. Name validated against `/^[A-Za-z0-9_-]{2,32}$/` + case-insensitive uniqueness against existing names + the reserved `admin` / `readonly`. `color` validated as `#rrggbb` (empty/null clears). Permissions normalized: unknown function keys dropped, missing keys defaulted to `"none"`. Refused with **403** when the submitted matrix is admin-equivalent (`users` AND `roles` both `fullwrite`) and the caller is not — business rule 48.
- `PUT    /roles/:id`                           *(write)* — Body accepts any subset of `{ name?, description?, permissions?, regionTags?, color? }`. Refused with 403 when the role is `isProtected=true` (admin / readonly), and with **403** when the body carries a `permissions` matrix that is admin-equivalent while the caller is not (business rule 48 — this is what stopped a `roles=write` holder adding the two grants to the role they already hold; a partial update that omits `permissions` is unaffected). Bumps the role-version cache + writes one `role.updated` Event with per-field diff (including a per-functionKey `permissionChanges` map listing only the keys whose level changed).
- `DELETE /roles/:id`                           *(write)* — Refused with 409 when `isBuiltIn=true` OR when any user holds the role (admin must reassign first).

### Group Mappings — mounted at `/group-mappings`, gated `users:fullwrite`
- `GET    /group-mappings`                      — All mappings (optional `?provider=oidc|ldap|saml`). Each: `{ id, provider, groupKey, groupLabel, roleId, roleName, regionTags, otherTags, enabled, description, createdAt, updatedAt }`.
- `GET    /group-mappings/:id`
- `POST   /group-mappings`                      — `{ provider, groupKey, roleId?, regionTags?, otherTags?, enabled?, description? }`. `groupKey` normalized per provider (LDAP lowercased-DN, OIDC/SAML exact); 409 on duplicate `(provider, groupKey)`. Warning Event when `roleId` is admin-equivalent.
- `PUT    /group-mappings/:id`                  — Subset of the above (provider is immutable).
- `DELETE /group-mappings/:id`

### API Tokens — `apiTokens` function key (read at mount; writes escalate to `apiTokens=write`)
- `GET    /api-tokens`                          — List all tokens (`{ tokens[], roles[], quarantineIntegrations[], apiBaseUrl }`). `roles` is the role catalogue (`{ id, name, description, grantsQuarantineWrite, adminEquivalent }`) for the "acts as role" dropdown; `quarantineIntegrations` is the FMG/FortiGate roster (`{ id, name, type, enabled, pushQuarantineEnabled }`) so the UI can render the per-token integration picker and the "push disabled — integration off / pushQuarantine toggle off" alert without a second round-trip. `apiBaseUrl` is the address external callers dial — `POLARIS_PUBLIC_URL`'s origin + `/api/v1` (`getPublicApiBaseUrl` in `utils/publicUrl.ts`), `null` when that env var is unset/malformed, in which case the tab falls back to the browser's own origin and says so. Hashes are never returned.
- `POST   /api-tokens`                          — Create. Body: `{ name, roleId, integrationIds?: string[], expiresAt? }`. `integrationIds` is REQUIRED + non-empty when the chosen role grants `assetsQuarantine` ≥ write; ignored otherwise. Each id must reference a real integration of type `fortimanager` or `fortigate`. Binding an admin-equivalent role logs an `api_token.admin_equivalent` warning Event. Returns `{ token: ApiTokenSummary, rawToken: string }` — `rawToken` is shown once and never recoverable.
- `POST   /api-tokens/:id/revoke`               — Mark as revoked (token stops working immediately); row is kept for audit.
- `DELETE /api-tokens/:id`                      — Hard-delete the token row.

### Credentials — mixed scoping
- `GET    /credentials`                         *(auth)* — List stored credentials with secrets masked. Read-open so any role's Asset Monitoring tab can render the credential picker.
- `GET    /credentials/usage`                   *(auth)* — Effective-usage asset count per credential, keyed by credential id (`{ [credId]: number }`). Drives the **Assets** column on the Stored Credentials table in one round-trip. Computed by `credentialService.getCredentialUsageCounts()` — one `asset.findMany` + class-override + integration lookups, resolving the FK fall-through (asset stream → asset default → class override → integration default) in memory. Registered before `/:id` so "usage" isn't read as an id.
- `GET    /credentials/:id`                     *(auth)* — Single credential, masked.
- `GET    /credentials/:id/usage`               *(auth)* — Full usage breakdown for one credential (`credentialService.getCredentialUsage`): `{ total, assetLevel[], classLevel[], integrationLevel[], classRefCount, integrationRefCount }`. Each asset lands in its most-specific tier bucket (asset > class > integration), so `total` is a true distinct count. Drives the credential **usage slide-in** in Server Settings → Credentials, whose asset rows deep-link to `/assets.html#view=asset:<id>`. Resolves by FK wiring ("where is this credential configured"), not by polling-method type-match. Since discovery stamps the integration's credential onto each discovered asset's `monitorCredentialId`, a stamped default whose value is one of the asset's integration's credentials is reclassified asset → integration level (only a per-stream slot or a default the integration doesn't provide is genuine asset-level).
- `POST   /credentials`                         *(credentials ≥ write)* — Create. Body: `{ name, type: "snmp"|"winrm"|"ssh", config }`. Type-specific config is validated server-side. Stamps `createdBy` from the session username — the ownership dimension (business rule 43), so the author can edit the row later and a bearer-token create (no username) lands UNOWNED and fullwrite-only.
- `PUT    /credentials/:id`                     *(credentials ≥ write, own rows; fullwrite for any)* — Update. Type cannot be changed after creation. Resubmitting the mask sentinel for a secret field preserves the stored value. `assertOwnership` runs on the loaded row before the body is even parsed; the update takes no `createdBy`, so an edit can never adopt someone else's credential.
- `DELETE /credentials/:id`                     *(credentials ≥ write, own rows; fullwrite for any)* — 409 if any asset effectively uses the credential (via `getCredentialUsage` — asset / class-override / integration-default tiers, all 8 per-stream slots + the `monitorCredentialId` default), with a level-aware message; also 409 when no asset resolves to it but a class override or integration default still references it (deleting would silently null those out).
- `POST   /credentials/test`                    *(credentials ≥ write; own rows when `id` is given)* — Exercise a credential against a chosen target without persisting anything. **Ownership-scoped whenever the body names a stored `id`**, checked before any target resolution or device I/O: that path merges the row's REAL secrets into the probe, so an ungated test route would let a write-level caller aim a peer's password at any host in inventory — a read-shaped route that lends out a secret (business rule 43). Testing an unsaved form (no `id`) needs only `write`, the secret in that body being one the caller typed. Body: `{ assetId?, host?, type, config, id? }` — the target is EITHER an asset (borrow its address) or a hand-typed `host`, and the schema `refine` requires one of them (except for `restapi`, which carries its own `baseUrl` and needs neither). The two answer different questions: an asset test aims at real inventory, a typed host is what you need BEFORE the device is onboarded, or when it never will be one (a staging unit, a vendor demo, a local stub). `assetId` WINS when both arrive, so a stale `host` left in a body can't redirect a probe aimed at an asset. A typed host goes through `normalizeProbeTarget` (utils/probeTarget.ts), which REFUSES a URL / embedded port / path rather than salvaging a host out of it — the discarded parts are owned by the credential (`useHttps`/`port`/`path`) or by the transport's default, so accepting them would dial something other than what the operator typed and then attribute the result to the credential; the refusal is returned as a test RESULT, not a 4xx, so the modal renders it inline beside the field. `details.hostSource` (`"asset"` | `"manual"`) is audited on the `credential.tested` Event, because probing known inventory and probing a freely-chosen address are materially different acts when reviewing what Polaris reached out to. Note this adds no reach a `credentials:write` caller lacked — a `restapi` credential has always been testable against an arbitrary `baseUrl`. When `id` is present, masked secrets in `config` are merged from the stored credential via `mergeConfigPreservingSecrets()` so the operator can edit and test without retyping the password. Resolves the asset's host from `ipAddress || dnsName || hostname`, then dispatches to `monitoringService.probeCredentialAgainstHost()` (icmp/snmp/winrm/ssh/restapi/http — the same one-shot probe primitives used by the response-time monitor; note `icmp` is reachable only from internal callers, since the body's `type` validates against the CREDENTIAL type enum). Returns the standard probe shape `{ success, responseTimeMs, error?, host }`, plus — for `http` credentials only — **`httpDiagnostics`** `{ url, statusCode, contentType, bytesRead, bodyTruncatedAtCap, excerpt, excerptTruncated, matched }`. That block is the point of the test flow for this type: an HTTP check's expectation is a string the operator has to pick OUT of the device's response, and pass/fail gives them nothing to pick from — so the modal renders the request line as dialed, the status, and a 4 KB body excerpt under the verdict, and the loop is save-with-a-path → test → read the body → paste a distinctive string into Expected content → test again. `matched` is reported SEPARATELY from `success` because with `failOnMismatch` off those two legitimately disagree, and `matched: null` means "no expectation configured yet" rather than "no match". The response BODY never enters the `credential.tested` Event (only `httpStatus` / `httpUrl` / `httpMatched` are audited — arbitrary device output would otherwise ride every pg_dump and syslog forward), and no response header other than `content-type` is returned, since a full dump would surface a live `Set-Cookie`. Validation failures are returned in the same shape rather than 4xx so the modal renders them inline alongside probe failures. Drives the **Test Connection** button on the add/edit credential modal in Server Settings → Credentials, which opens a second modal with an asset autocomplete (powered by `GET /assets?search=…&limit=25` — not the global `/search` endpoint, whose 8-per-group cap and pinned-firewall→`sites` partition silently dropped firewalls from the picker) and reports the result inline. Each call writes one `credential.tested` Event (info on success, warning on failure).
