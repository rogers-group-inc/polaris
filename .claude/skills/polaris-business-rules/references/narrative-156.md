## Rule 156 — An asset leaves nothing behind when its row goes, and a merge carries the operator's intent to the survivor

**How it was found.** The 2026-11-11 orphan audit asked what Polaris creates that an operator cannot remove through the UI once the thing it belonged to is gone. For assets the answer was structural. Every delete path — `DELETE /assets/:id`, the bulk delete, the operator merge, both automatic ghost merges, the conflict-resolution absorb — ended at `prisma.asset.delete` and trusted the foreign-key cascade. The cascade is thorough for what has a foreign key. But about a dozen places hold an asset id with none: three string arrays (`PathCheck.assetIds`, `Contact.assetIds`, `MaintenanceSchedule.assetIds`), two JSON blobs (`NotificationRule.scope.assetIds`, the Application Map's rules in a `Setting`), and plain columns on tables left without a foreign key on purpose (`LogFlagRule`, `AssetProcessConfig`, `AssetProcess`, `AssetService`, `AssetSdwanRule`, `AssetInventoryScrape`, `AgentCommand`, `AutomationScriptRun`). No delete path touched any of them, and there was no sweep.

What that produced, concretely:

- An asset- or process-scoped log-flag rule became unreachable. Its only editor opens from the asset's own pinned process and lists rules for that asset, so with the asset gone the rule could not be found — yet it was still loaded and compiled into the rule cache, and the stored-regex audit could report a bad pattern in a rule nobody could open.
- A path check kept a pin to the dead host. The editor draws a checkbox only for a host that still exists but re-posts the whole stored pin list on save, so the dead id was preserved on every save with no way to untick it. It also satisfied the "this check runs somewhere" validation, so a check pinned only to a deleted host saved cleanly and ran nowhere.
- A script queued for the host's agent stayed `pending` (rule 155 now expires it; before that, forever).
- Process, service, SD-WAN and inventory-scrape rows stayed in the database with nothing reading them.

**A merge was worse than a delete.** After a merge the same ids named the *absorbed* record. `absorbAssetRelations` moved sources, the side tables, dependency edges and the agent, and nothing else — so the survivor silently dropped out of every path check, contact, maintenance window and automation the absorbed record had been pinned to, and lost its per-process log configuration. The sharpest case: a merge that moves the Polaris Agent to the survivor. The absorbed record's `PathCheckSource` rows cascade away, the pin still names the absorbed id, and the path check simply stops running on that host. Nothing reports it. A merge is supposed to be "these two records are one device"; quietly discarding what the operator had said about one of them is the opposite.

**The decision.** One service, `assetRemovalService`, with two entry points called by every path that removes an asset row:

- `afterAssetsDeleted(ids)` — prune the three pin lists and the Application Map rules, delete the FK-less per-asset rows, and withdraw commands and agent script runs still waiting on the device.
- `afterAssetMerged(from, to)` — replace the absorbed id with the survivor's in the pin lists, automation scopes and Application Map rules; move the absorbed record's log-flag rules and per-process log configuration to the survivor (the survivor's own configuration for the same program wins a clash); move commands riding an agent that moved with the merge; then purge whatever is left under the absorbed id.

**Why after the commit and not inside the transaction.** None of these rows cascade, so they are all still present once the delete or merge has committed — nothing is lost by waiting. Doing the re-point inside a merge transaction that then rolled back would have moved the operator's intent off a record that still exists, which is a worse failure than a stale reference. And the Application Map's rules are a `Setting` blob read and written by its own service outside any caller's transaction. So both entry points run post-commit, are best-effort, and log rather than throw: a failure leaves references stale, exactly as they always were before this service existed, and never undoes a delete the operator asked for.

**Why not a Prisma hook in `src/db.ts`.** The single delete already has one there (releasing `dns_resolved` reservations), and a hook would have guaranteed coverage of any future delete path. It was rejected for the same transaction reason: a hook on `asset.delete` fires for the merge paths' `tx.asset.delete` too, and would run its clean-up on the base client while the merge is uncommitted. Explicit calls after each commit are the honest shape. The cost is that a new path that deletes an asset row must call the service; `tests/unit/assetRemovalCoverage.test.ts` scans `src/` for `asset.delete(` / `asset.deleteMany(` and fails on a file that does not also import it.

**Never widen a target — clause (a).** Several lists read "empty" as "everything". An automation's `scope.assetIds` is an AND filter that is simply absent when the list is empty (`notifications/scope.ts`), so emptying it turns "this automation is about that one device" into "every device". An Application Map rule with no device filter and no pins means every monitored asset. So:

- An automation's scope is **re-pointed on a merge and left alone on a delete.** A dead id matches no device, which is the correct reading of an automation about a device that no longer exists; the operator removes it in the wizard, where it is visible.
- An Application Map **auto** rule that loses its last device is deleted, exactly as un-pinning the last device does (`applyPinChangesToConfig`). A **manual** rule with no filter keeps its last dead id rather than widen. Anything else is pruned.
- The three string-array pin lists are safe to empty: a path check with no pins and no filter targets nothing, a contact's pins are unioned with its filter, and a maintenance schedule's targets are `union(criteria, assetIds)` with an empty union meaning none.

**The bulk delete — clause (b).** `prisma.asset.deleteMany` runs no per-row hook, so the `dns_resolved` reservations the single delete releases in `src/db.ts` were left behind by a bulk delete, as active system reservations on addresses nothing held. `bulkDeleteAssets` now releases them for each id first, while the asset's name and address can still be read.

**A dead pin is refused on save — clause (c).** `pathCheckService.normalizeCheckInput` drops any pinned id that names no asset. With the delete-time prune this should never be needed again, but it makes the editor self-healing for a pin that got through some other way, and it closes the "saves cleanly, runs nowhere" hole at the validation that was supposed to catch it.

**A private Discovery with no owner — clause (d).** The same audit, the same shape, on the user side. `NetworkScan.owner` is `onDelete: SetNull`, and `listScans` showed a caller what they own or what is public. Deleting a user therefore left their private Discoveries owned by nobody and still private: visible to no one, the administrator included, with the targets, credential ids and every run's hits still in the database. `getScanForWrite` answered 404 before the route's own `fullwrite` housekeeping check could run. Two fixes were considered. Deleting a user's private Discoveries with the account (what rule 140 does for private saved filters and dashboards) was rejected because it does nothing for the rows already stranded on existing installs, and deleting scan results in a migration is not something to do without asking. Instead a private Discovery with **no owner** is visible to `networkScan:fullwrite` — the level that already edits and deletes Discoveries that are not its own — so it can be republished or deleted. A private Discovery that still has an owner stays private to that owner at every level; nothing about a living user's privacy changes. `updateScan` already refuses to make an ownerless row private, so the housekeeper's choices are publish it or delete it.

**The migration.** `20261111120000_orphan_asset_references` removes what earlier deletes and merges already left on an existing install: dead ids in the three pin lists, the FK-less rows, and commands and agent runs waiting on a device that is gone. It deliberately does not rewrite automation scopes or Application Map rules (clause (a)). A fresh install has none of these rows and no seed job writes them, so there is no seed-side twin. Its timestamps are `now() AT TIME ZONE 'UTC'` (the naive-UTC trap). `tests/integration/assetRemoval.test.ts` plants leftovers the way a pre-156 release left them, runs the migration's statements, and checks both that they go and that a living asset's rows are untouched.

**What this rule does not cover.** Decommissioning is not deletion: the row stays, and so do its references (rule 123 handles the agent's pins; rule 40(k) the address). Sample and rollup rows have no foreign key by design and age out on retention. `NotificationRuleState` rows for a deleted asset are cleared by the evaluator on its next tick and are a retention question, tracked in `docs/ORPHAN-AUDIT-LEDGER.md` with the rest of the audit. The agent software left running on a host whose asset was deleted is also tracked there — it is outside the database.

**Scale.** The clean-up's cost is proportional to what referenced the removed assets, never to the fleet: three indexed array reads (`hasSome`), one JSON-path read for automation scopes on a merge, one `Setting` read, and one batched transaction per 500 ids. A 2000-asset bulk delete is four chunks.
