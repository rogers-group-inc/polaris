## Rule 159 — A fibre-channel login names the asset that reports its WWN, else the one asset its registered host name answers to — never a guess

**The request (2026-11-11).** With a Cisco MDS 9148S monitored over SNMP (rule 154 had just filled its identity), the operator asked what else SNMP could say about a fibre-channel switch — "what is connected to what". FC does not run LLDP, so nothing in Polaris could draw those links. Walks of the switch, done together in the session, showed what it publishes:

- `fcIfFLoginTable` (CISCO-FC-FE-MIB), one row per logged-in device, indexed `ifIndex.vsan.loginIndex`, with its port and node WWNs. Eighteen logins in VSAN 101, one device per port.
- `fcIfErrorTable`, per-port cumulative counters. fc1/5 had 2.3 billion invalid transmission words, and fc1/8 — a storage-array port — had 309 CRC errors. That is why the counters are kept beside the logins.
- `fcNameServerTable` (CISCO-NS-MIB), indexed `vsan.d.a.p`. Its symbolic node name, on Emulex HBAs, reads `Emulex SN1200E2P FV14.2.589.5 DV14.0.0.21 HN:<host>.<domain> OS:Linux`.
- `cfdmiHbaPortTable` (CISCO-FDMI-MIB), indexed `vsan.<hba id>.<port wwn>`, the host name each HBA registered. The storage array registers its port labels here (`PURE01-ct0`, `PURE01-ct1`) and no symbolic name.
- `fcIfElpTable` was empty: the switch has no ISLs; the site runs two separate fabrics.

The operator saw their host names in the `HN:` field and proposed using them to match the connectivity to assets, with a Fibre Channel tab on each server showing fabric A and fabric B.

**Why the WWN does not match anything yet.** Polaris stores no WWNs on hosts: neither the agent nor the vCenter integration reports HBAs today. So a WWN on the switch side meets nothing, and the only bridge to an asset is the name the HBA registered. That is the rule-91 situation exactly — a name is not an identity — so the match is taken only when exactly one asset answers to it, and is recorded as `matchMethod: "name"` so the UI can say how it was made. When a host source reports its own WWNs (the vCenter SOAP fetch already reads `HostSystem`; `config.storageDevice.hostBusAdapter` carries them), that becomes the firm match and outranks the name.

**How names compare.** An exact hostname or DNS name wins when unique. Failing that, short names are compared, but a FQDN on one side meets only a SHORT name on the other: `esx07.a.com` and `esx07.b.com` are different hosts. An empty `HN:` (ESXi's driver writes `HN:OS:VMware ESXi 8.0.3` when the host has no FQDN set) and a domain-only value (`.example.com`) name nothing.

**Joining.** The four tables are joined on the port WWN. The login table's own index is documented as "an arbitrary value" (on the MDS it happens to equal the FC address); joining on it would work here and break on the next vendor.

**What is kept.** The switch's ports and logins as current state, full-replaced each pass with `firstSeen` kept, because the operator's question is "what is plugged in now". A device logging out is the one change worth an Event (`asset.fc_logins_changed`, warning): on the walked switch, fc1/13–15 had error history and nothing logged in.

**The MIBs come from the operator.** The collector names every object by its symbol and resolves it through the registry at the asset's scope, the vendor-knowledge boundary `tests/unit/noEnterpriseOids.test.ts` enforces: CISCO-FC-FE-MIB, CISCO-NS-MIB and CISCO-FDMI-MIB (with their imports) must be uploaded. The first build used literal OIDs and that test refused it. The upside is that a device whose manufacturer scope has no FC MIB costs no query at all.

**Scale.** A device that is not an FC switch costs one GETNEXT per system-info pass when the MIB resolves at its scope, and nothing when it does not. An FC switch costs six more walks and one candidate query per pass.

**Rejected.** Matching by WWN prefix or vendor OUI (identifies a vendor, not a host); reading zoning to decide what a host "reaches" (deferred; the host view says "on this switch's VSAN", nothing more); a profile-widget implementation (one column per widget, raw indexes, WWNs garbled by the value decoder — shown to the operator first and set aside).

**The host reports its own WWNs (2026-11-11, the second batch).** The operator asked whether the MAC address could do the job instead of the host name, "assuming Polaris is aware of fibre-channel interfaces on the assets". FC has no MAC; the WWN is its equivalent, and Polaris knew no host's WWN. The MAC-format address inside an NAA-1 WWN (`10:00:` + 48 bits) was considered and rejected as a match key: it comes from the HBA vendor's own pool and is no Ethernet card's MAC, so it would almost never hit and could hit the wrong device. Instead the hosts report their WWNs themselves:

- **The Polaris Agent** (0.29.0) adds `fcPorts` to its system-info push. On Linux it reads `/sys/class/fc_host` (world-readable, so the unprivileged tier sees it), plus model / firmware from `scsi_host` and the driver from `/sys/module`. On Windows it reads `MSFT_InitiatorPort`, whose WWNs are flat hex strings; `MSFC_FibrePortHBAAttributes` nests them in an embedded object the agent's WMI library cannot decode reliably. It also reads `MSFC_FCAdapterHBAAttributes` for the model, applied only when every adapter agrees, because the two classes share no key. The wire keeps "cannot say" (absent) apart from "none" (`[]`).
- **vCenter** adds `config.storageDevice.hostBusAdapter` to the SOAP host fetch both the monitor loop and discovery already make; discovery's Pass A2 records it per ESXi host. A WWN there is an xsd:long, a SIGNED decimal, so a WWN whose top bit is set arrives negative (`wwnFromVimLong`).

Both land in `AssetHbaPort` per (asset, source). The switch's next pass matches a login to the asset reporting its WWN (`matchMethod: "wwn"`), and that outranks the name. Two assets claiming one WWN is still no match. Linux's `fabric_name` also lets a server say which fabrics it is on when only one of their switches is monitored, and the server tab lists the host's ports with the switch port that sees each one (or none).

**Not yet.** The standard FC-MGMT-MIB (RFC 4044) for other vendors, Device Map links, and alerts for a host that lost a fabric or a port whose error counters are climbing. Windows port state, speed and fabric name are not read (they live in the embedded object). None of the host side has been run against a real HBA; the SOAP shape is from the vSphere API reference, and the Windows classes from Microsoft's documentation.

## Rule 159a — An FC port's error counters are an interface's counters: sampled with its pin, alerted on as a rate per minute

**What asked for it (2026-11-11).** With the logins in place, the operator said: "I need to be able to alert on FC port error counters. On the interface table, can I see those errors? Can I see the WWN?" Neither was possible. The counters were held only as the latest value on `AssetFcPort`, so there was no series to put a rate threshold on. The Interfaces table showed the IF-MIB in/out error total and nothing FC. The MAC column was blank on every FC port: an MDS reports a port's own WWN as its `ifPhysAddress`, and `snmpMacFromBuffer` keeps only 6-byte values, so the 8-byte WWN was dropped.

**Why the interface sample, not a table of its own.** An FC port is an interface. The operator already pins it to say "record history for this port", the pinned fast pass already runs at the response-time cadence, the sample table already has hourly / daily rollups and retention, and the interface error-rate metrics already read that table with the pin gate, the name pattern and the port tag filter. A new hypertable would have needed every one of those again. So the counters became one JSON column on the interface sample (`fcErrors`) plus first / last in the rollups. Seven counters as fourteen BigInt rollup columns per tier was rejected as width for no reader. The JSON is ARRAY_AGG'd like every other last-value column.

**The fast pass reads them in its own PDU, for FC ports only.** The `fcIfErrorTable` columns are GET at each pinned port whose IF-MIB ifType is fibreChannel(56). A device with no pinned FC port asks nothing, and neither does an MDS's Ethernet mgmt port. The PDU is separate from the IF-MIB multi-GET for the reason duplex's is: an SNMPv1 agent answers a GET naming one missing instance with noSuchName for the whole PDU, and that must cost the FC counters, never the octets. The objects resolve at `snmpVendorScope`, the same scope the full pass reads the FC tables at, so the two passes cannot disagree about whether the MIB is there.

**Per minute, not per second.** These counters move a handful at a time on a failing optic. The interface error rates are per second because they are read against traffic. An FC CRC rate of "0.0003 errors/s" is a number no operator can set a threshold on, so the five metrics are (Δ × 60) / Δt. One metric per counter, because they mean different faults: CRC and invalid-word counts point at the optic, cable or connector; link failures and loss of sync or signal point at a link going down. The two link-reset counters are stored and charted but not offered as metrics (a reset is usually the consequence of the others). A counter that went backwards was cleared on the switch (`clear counters`). It yields no reading for that tick, never a negative rate, as `rateReadings` already treats every counter.

**Only rows that carry a reading.** A pass that read no FC counters (the full pass before a port is FC-identified, a GET that timed out) writes a sample without `fcErrors`. The resolver asks for `fcErrors IS NOT NULL`. Otherwise such a row would pair with a real one as "the newest two" and the port would read "no rate" every other tick.

**The WWN.** It comes from `ifPhysAddress` only on ifType 56. An 8-byte address on another interface type (an EUI-64 on an IPoIB or FireWire port) is not a WWN, and calling it one would make it match nothing at best. It is stored on `AssetInterface.wwn`, current state, not on the sample: it never changes per minute.

**The Interfaces table.** Three columns appear once any port is FC: **WWN**, **Logged in** (the matched asset as a link, else the registered name, then the WWN it logged in with, +N for more) and **FC errors** (the five counters an operator acts on, summed, each in the tooltip, amber when a corruption counter is non-zero). It uses the Fibre Channel tab's labels: `_FC_ERROR_COLS` moved to `assets-system.js`, which loads first, so the two surfaces cannot name a counter differently. The counters and logins come from `AssetFcPort` / `AssetFcLogin` joined by ifName (`getFcByInterface`), not from a second copy on `AssetInterface`.

**The charts (approved on a design canvas, 2026-11-12).** The first canvas drew the FC errors as stacked bars, coloured by counter, under one dashed threshold. The operator asked two questions. Do the colours follow the automation's severity bands? Not in that draft, but the CPU, memory, sensor and path-latency charts already do. And is that how a regular interface's errors look? They did not: two thin lines, in errors amber, out errors purple, counts per interval, no thresholds. They asked for the same treatment on every port. The approved version:

- **Both charts are stacked bars in the automation's unit.** Errors are per second (what `ifIn/OutErrorRate` compares) and FC counters are per minute. The number on the axis is then the number the operator typed. The old error chart's "errors per interval" changed meaning with the range (a minute on 1h, an hour on 7d) and could not carry a threshold at all.
- **Bands follow the existing convention.** Each band is a dashed line with a caption, and the series it reads takes the band's colour inside it (`PolarisChartSeverity.severityAt` per bar, where the line charts use a gradient). In errors moved from amber to the accent so amber only means Warning.
- **The axis reaches the lowest band.** A quiet port still shows how far it is from alerting.
- **Only automations that read this port draw a band.** The thresholds endpoint took a sensor or a path check, never a port. It now takes `ifName` / `alias` and applies the engine's own `interfacePatternMatch` and `interfaceTagMatch`. The port tags are read in one query, and only when a rule filters on a tag.
- **FC link counters are diamonds.** Link failures and loss of sync or signal are rare, discrete events; as bars they would be invisible beside a burst of invalid words. Each is a diamond above the plot, in the band colour of its own automation.

**The email.** The default body already leads with `{chart.trigger}`, so an error-rate or FC alert now resolves it to a new `chart.interface`: the port's last hour as a line, in the metric's unit, with the rule's threshold dashed. It reuses `storageThresholdFromTrigger`, widened to these metrics. The canvas drew bars, but every email chart is the sparkline renderer, and a second renderer for one chart was not worth it. The device charts stay beside it (the existing reasoning: an erroring port plausibly correlates with load). An FC alert's `{interface.lldp}` block also names what is logged into the port, because an FC port has no LLDP. That block was the canvas's "Logged in" fact.

**Not yet.** FC-MGMT-MIB for non-Cisco switches.

**The phone (approved on a Polaris Mobile canvas, 2026-11-12).** The phone's interface page draws the same two charts with `PolarisCharts.barChart` (`public/js/mobile/charts.js`): errors per second in the throughput chart's `--md-primary` / `--md-tertiary` (no longer `--md-error` / `--md-warning` lines), FC errors per minute with the link-event diamonds, and the same per-port bands from `metric-thresholds?ifName=`, in `--md-sev-*` (informational → `--md-sev-info`). The captions and diamonds are HTML over the plot, because the SVG is stretched (`preserveAspectRatio="none"`) and would squash them. The line under each chart names the automations whose bands it drew, because captions at 350 px are small. An FC port also gains WWN and FC errors detail rows, and **Logged in** cards where an empty LLDP Neighbor section stood.
