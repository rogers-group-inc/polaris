## Rule 25 — An alert you can't acknowledge from where you read it isn't really acknowledgeable — and who acknowledged it is a session, not a link

`POST /alerts/acknowledge` has existed since the notifications feature shipped, gated `alerts:write`, with **zero frontend call sites**: the asset-details Alerts tab and the mobile Alerts list both rendered alerts read-only, so `escalation.stopOn: "acknowledge"` — offered on every escalation chain the wizard builds — could in practice only ever be stopped by clearing. Acknowledgement now reaches the three places an alert is actually read. **In-app** (the Alerts tab + the mobile list) calls the existing route. **Email and web push** carry a link to the alert's own acknowledge page.

That link was a single-use token for one release, and the reason it is not any more is worth stating first, because the token version was not obviously wrong. `NotificationAckToken` was a 192-bit secret minted per (recipient, channel) at delivery fan-out and redeemed at a PUBLIC `/ack/:token` route mounted above `session()` and `csrfMiddleware`. It bought one genuinely good thing: acknowledging from a phone's mail client in a single tap, with no password. Everything else it bought was cost. **The token had to name a person**, because the row it writes records WHO acknowledged — so a composed email, which renders ONE body, could not carry a link that worked for more than one reader. The first shape of that compromise withheld the button unless exactly one To address was user-owned with cc/bcc empty, which withheld it from essentially every real automation. The second shape kept the body and split the MESSAGE: `planComposedEmails` fanned the To line out into one delivery row per recipient, each with its own token. That worked, and it multiplied the send — one SMTP message per person, one chart-rasterization pass per person until a per-drain memo was added to stop it, and a To line that no longer showed the reader who else was on the alert. It also meant address-book contacts and typed addresses got a deliberately button-less copy of the same mail, because there was no account to file the acknowledgement under. And the whole apparatus had to be defended: the GET kept inert against mail-gateway prefetch, the route mounted above the session middleware so a Safe Links scan could not mint a `connect-pg-simple` row, a live permission re-check at redemption so a role downgrade invalidated links already sitting in mailboxes, a 30-day TTL, an hourly prune, and a sha256 digest chosen over the house argon2id pattern specifically because argon2 on the alert fan-out path would spend seconds of blocked CPU per large alert.

**Polaris already has a way to know who someone is.** The link is now `/alert-ack.html?id=<notificationId>` — it names the ALERT and carries no credential of any kind. `alert-ack.html` is listed in `protectedPages`, so an unauthenticated reader is bounced to the login page and lands back on the alert signed in; a reader who already has a session never sees a login form at all. Identity is that session, and `alerts:write` is enforced by the same `POST /alerts/acknowledge` route the in-app surfaces use. The trade is explicit: an emailed acknowledgement now costs a login when you do not already have one, and in exchange the entire token apparatus — table, TTL, prune job, unauthenticated route, permission re-check, per-recipient fan-out — is gone, along with the last unauthenticated state-changing surface in Polaris.

Six decisions carry it. (a) **The email is ONE message again.** `expandDeliveries` resolves `{ack}` once per alert (`fillComposedAckUrl`) and writes a single delivery row whose `target` is the joined To list; Cc/Bcc are just Cc/Bcc. The chart memo (`RenderMemo`) stays — it is no longer load-bearing for email, but one alert still drains as several rows when a rule has more than one notify action, or a web-push target with a row per enrolled device. (b) **Every recipient Polaris cannot identify gets the button; one it can is asked first.** A contact or a typed address gets the same working link; whether they can act is decided at the page, and the honest answer to "can this person acknowledge" is a login prompt rather than a missing control. This is the one place the new design is weaker on its face — someone forwarded the mail can now see that an acknowledge page exists — and it costs nothing, because they still cannot get past the login. That reasoning stops where Polaris already knows the answer (2026-08-28). An address belonging to an account whose role holds `alerts` below `write` gets the same alert with the button taken out: the page can only refuse them, and a button that exists to be refused is noise in an inbox that already carries a lot of alert mail. The cost is a bounded, partial return of the fan-out the token design forced — `ackCapabilityByAddress` maps address → the role's level and pure `splitAckVariants` splits To/Cc/Bcc into an ack copy and a no-ack copy, so a send is TWO messages at most however many people are on it, and a message with no read-only recipient still writes the single row it always did. Two shape rules keep both copies deliverable: a variant that loses its whole To line promotes its Cc into To rather than dying on the empty-To guard, and a variant left holding only Bcc goes out one message per address so the blind list stays blind. **Unknown means capable, in both directions** — an address with no account keeps the button, and where two accounts share one address (`User.email` is neither unique nor required) whichever may act decides, because withholding from someone who may acknowledge is the worse error. The button-less body is the SAME substitution an install with no `POLARIS_PUBLIC_URL` already produced (`fillComposedAckUrl(body, null)`), so the pruning was already written and already tested; the one gap it exposed was an operator template with a bare `<a href="{ack}">` instead of the shipped template's cell-wrapped button, which is why `pruneDeadLinks` grew a bare-anchor fallback. Push is simpler, because a subscription always has an account behind it: the payload carries no `ackUrl` at all and `sw.js` renders no Acknowledge action. And what this withholds from is a genuinely read-only role, not merely someone an admin never got round to promoting — migration `20260828030000_alerts_ack_write_capable_roles` raised `alerts` to `write` on every role already holding write or fullwrite on any other function key, which is the whole "everyone except read-only" policy expressed once, in the matrix, where the in-app Ack button reads it too. (c) **Loading is a GET and acknowledging is a POST.** Outlook Safe Links, Proofpoint and every other mail gateway fetch each link before a human sees it. That was the sharpest edge of the token design and it survives here for free: the prefetch carries no session, and even with one the page acts only when someone presses the button. (d) **The page gate is `alerts:read`, not `write`.** Someone whose role can see alerts but not acknowledge them reaches the page and is told so; bouncing them to "/" would leave them on a dashboard with no explanation of where their link went. (e) **A web-push Acknowledge action OPENS the page** instead of acting from the tray. One tap became two, and in exchange the note gets typed (a tray button has no text field, which the token design had to special-case with a recoverable `"note_required"` answer) and the acknowledger is a real session. It shares the tray with at most one other button: `Notification.maxActions` is 2 on every browser that renders actions, and the overflow is dropped from the END, so `sw.js` lists candidates in priority order and slices — Acknowledge, then **Open device**, then **Ignore**. Acknowledge leads because it is the only one that changes state and stops an escalation. Open device is second because it goes somewhere the body tap does not: the tap follows the server-chosen deep link to the alerts LIST, right for triaging several alerts at once and two taps away from the one box this alert is about. Ignore is last, and rides only a `requireInteraction` alert, because it is the one candidate whose job the platform already does — a Windows toast carries its own close button, and a non-sticky notification clears itself on the OS banner timer. Ignore sends nothing at all: a tray button carries no session, so it cannot mean the alert was handled, and the alert goes on repeating and escalating exactly as if the push had never been read. (f) **`GET /alerts/:id` answers 404, not 403**, when the caller's region scope excludes the alert — which alerts exist outside your regions is not something a route should confirm.

The return trip is a **cookie**, not a `?next=` query parameter. `utils/loginRedirect.ts` drops a 10-minute `polaris_next` when `app.ts` bounces an unauthenticated request off any protected page, and every login path consumes it. There are five ways into Polaris (local, the TOTP second step, SAML, OIDC, Entra App Proxy) and three of them hand the browser back on a URL Polaris does not control; worse, the SSO callbacks call `req.session.regenerate()`, so a session-stashed target does not survive the very step it would have to survive. The cookie is deliberately not HttpOnly, because `login.js` reads it after a local login — safe by construction, since `safeNextPath` reduces whatever comes back to a same-origin PATH and refuses `/login.html` itself, so the worst a forged value achieves is landing an operator on another page of their own Polaris.

**And the note is per-automation optional or mandatory** (`NotificationRule.requireAckNote`, the wizard's in-app alert card, default off): "someone looked at it" is enough for a noisy interface flap, while a critical outage wants the operator to say what the problem was and what they did. It is enforced in **`acknowledgeNotifications`**, not in the dialog, because that one function backs every read surface — the modal's required field, the ack page's `required` textarea and the mobile note sheet are each just the local courtesy. Three decisions follow: a **batch is refused whole** (the route takes ONE note for every id, so acknowledging the note-free half under a success toast would leave the alerts that mattered open — the bulk dialog therefore demands a note when ANY selected alert's automation does); the ack page treats the resulting **400 as form validation**, re-rendering with the reason rather than becoming a dead end; and a **rule-less alert reads false** (a test fire, or one whose automation was deleted — `ruleId` is SetNull), because there is no policy left to enforce and refusing to let anyone close it out would be worse than a missing note. The flag rides each row of `GET /alerts`, `GET /alerts/:id` and `GET /assets/:id/alerts` as a flat boolean (`withAckPolicy`) so no surface has to fetch the automation to know how to ask. And **the note has to be readable somewhere**, or requiring it is theatre: it rode both list payloads for free but was rendered by nothing until 2026-08, so the answer to "what was the problem and what did you do" was stored on the row and shown to no one. The asset-details Alerts tab's **Acknowledge** column is that reader — note first, acknowledger and time under it, and "No note" rather than an em dash when someone acknowledged in silence, since a blank there reads as an alert nobody has touched. The acknowledge page shows it back too, once there is one. The dashboard widget and the mobile list still show only who; they need no backend change to follow.

**A fourth entrance, and why it is a copy of the card rather than a shortcut** (2026-09). The Down Assets widget is where an outage is usually SEEN first, and until now clicking a row did the only thing it could — open the device page, where the operator then had to find the Alerts tab and pick the row out of it. Three steps to say "I've got this". The row now offers **Acknowledge alert… / Open device** instead, and Acknowledge opens the ack page's own card in a modal (`PolarisAlertAckModal`, built from the shared `PolarisAlertAckView` markup). It is deliberately NOT the bare note prompt the Alerts tab uses: the operator arrived from a row that said only "this host is down", and before they put their name on something they need to see WHICH alert, what raised it, how bad it is and whether someone beat them to it — exactly what the emailed card already shows. Everything above still holds through it, because it is the same card and the same `POST /alerts/acknowledge`: a 403 is a STATE rather than a toast, the 400 re-renders the form, and it re-reads afterwards so the acknowledger's name is the honest one. It sends no `source` — that closed set names the emailed page and the push action, and this is neither. Two things the widget decides rather than the modal: the menu is offered only for an UNACKNOWLEDGED alert (an alert someone owns is nothing to act on, so the click keeps its old behaviour and opens the device), and only to a role holding `alerts:write` — a courtesy, since the route is still the control, and the modal renders its refusal either way on the surfaces that cannot check.

## Rule 26 — A generated MAC is a placeholder until the network proves otherwise

A DHCP reservation is a MAC→IP binding, so reserving an IP for a device that isn't racked yet needs a MAC before there is a device to supply one; the IP panel's **Generate** button synthesizes one. Before this, that MAC was `02:` + 5 bytes of `Math.random()` from two duplicated client-side copies, marked as synthetic nowhere — so the entry sat on the gate matching nothing, the device arrived, DHCP'd with its real MAC, missed the reservation and took a pool address, and the reservation looked correct on both sides while doing nothing forever. **The prefix is the marker, and the only one.** `reservationMacPlaceholder` (Setting, default `02:0F:5E`, Server Settings → Identification) is what makes a stored MAC recognizable as synthetic — there is deliberately no boolean column on Reservation and no Conflict row, because the prefix is visible on the FortiGate's own reserved-address table, so an operator reading the gate can tell which entries are waiting on a device without consulting Polaris. `normalizePlaceholderPrefix` (`utils/mac.ts`) accepts 1–5 hex octets and **rejects any prefix that isn't locally-administered unicast** — that rejection is load-bearing: pointing this at a real vendor OUI (`00:50:56`) would make that vendor's genuine devices look like placeholders and hand discovery permission to overwrite them, whereas a locally-administered prefix cannot be assigned to a vendor, so no factory MAC can fall inside the placeholder space. (`AA:BB:CC` is legal here for the same reason — 0xAA has the LA bit set.) **Adoption** (`placeholderMacAdoptionService`, discovery Phase 7.7, double-gated on `config.pushReservations` + `config.adoptDiscoveredMac`, both default off, FMG + standalone parity) replaces such a MAC with the real one when the gate reports a device at that reserved IP, and re-pushes the corrected binding. Evidence is the **ARP table** and **device inventory** only, keyed `(fortigateDevice, ip)` like Phase 7.6 so overlapping RFC1918 subnets behind different gates can't cross-match; ARP wins over inventory (a live L2 binding beats a cache whose `is_online` lags), an online inventory row beats an offline one, and two ARP rows disagreeing about one address drop it permanently — a duplicate IP on the wire is not something to burn into DHCP config. DHCP lease entries are deliberately NOT evidence (a device whose MAC doesn't match never gets the reserved address, so it can't appear there) and neither is `Asset.ipAddress` (not device-scoped). Five guards make the unattended overwrite defensible: the stored MAC must be a placeholder, the observed MAC must **not** be (never swap one synthetic value for another — that also makes the legacy `02` prefix safe, since a genuine `02:` device presents that same `02:` MAC in ARP and is skipped rather than churned), it must differ, it must not already be held by another active reservation in the same subnet (FortiOS would refuse it *permanently*, parking the row), and the row must not be at `failed_permanent`. The gate write goes through `updatePushedReservation` — **device first, verified by read-back, Polaris second** — so the two views can't diverge; a `pending` row skips device contact and lets the retry tick carry the new MAC. Bounded **per RUN, not per call** (`AdoptionBudget`, 50): in FMG mode `syncDhcpSubnets` runs once per managed gate, so a per-call ceiling would multiply by gate count. Audited per row (`reservation.mac.adopted` / `reservation.mac.adopt_failed`). **Changing the prefix is not retroactive in either direction** and the settings card confirms before saving. Related fix in the same change: Phase 6's DHCP-entry MAC overwrite (a bare `prisma.reservation.update` with no push) is now **skipped for rows carrying push pointers** — it was silently diverging Polaris from the gate for any pushed row, and left unfixed it would have adopted the placeholder away in Polaris while the gate kept it forever.

## Rule 27 — A logo is picked by theme; a name is text only when the picture doesn't already say it

The shipped Polaris art is theme-paired (`public/img/brand/polaris-{horiz,vert,symbol}-{dark,light}.png`): the dark-theme wordmark is light blue and the light-theme one near-black, and the symbol's wedges are white on one and navy on the other — so painting the wrong variant makes the logo *disappear* rather than merely look off. Horizontal art on the login card, vertical in the sidebar. The two variants of a pair are **normalized to one geometry** (the vendor exports were not — the vertical light star was ~39% larger relative to its wordmark), so a theme flip swaps the file and moves nothing on screen; re-exported art has to be re-normalized, see the skill references (formerly ARCHITECTURE.md) → `public/img/brand/`. **One module decides** — `public/js/brand-logo.js` (`PolarisBrandLogo.resolve/applyTo`), consumed by the desktop login, the mobile login, the sidebar and the Customization preview, because four surfaces each deriving the rule is four chances to disagree; it picks by theme **FAMILY, not by theme id** — since the three-theme cutover there are `morning`, `noon` and `nightfall` but still only two sets of art, so `morning` and `noon` both take the light files with no third asset and an id comparison would silently miss every daylight theme but the one it names. `PolarisBrandLogo.currentTheme()` answers that family (deferring to `app.js`'s `isLightTheme` where it exists — brand-logo.js loads *before* app.js and also runs on the login page, the mobile SPA and the dash wallboard, which never load it at all), and it repaints on the `themechange` event `_setTheme` fires **and** on a `data-theme` MutationObserver, so a theme set by any other means (the pre-CSS boot, the OS listener, another tab) is covered too. A morning → noon flip changes no family and forces no re-fetch. It also registers the `prefers-color-scheme` listener that keeps a user who has **never** chosen a theme tracking their OS. With nothing in `localStorage["polaris-theme"]` every bootstrap (`js/theme-init.js`, `app.js`, `mobile/app.js`, `dash-boot.js`) resolves the OS preference, landing on `morning` for a light preference and `nightfall` otherwise — and each of them now VALIDATES a saved value against its known list first, because the retired `dark`/`light` ids name no token block and trusting one would render the whole install unstyled. Nothing is persisted by that path: staying unsaved *is* the "follow my system" state, and the theme picker is the opt-out. **The Application Name is a caption for a custom logo only.** The Polaris art carries the wordmark, so printing the name under it says it twice — `showName` is false whenever the shipped art is in play, and `appName` may therefore be stored EMPTY (`displayAppName` is the fallback for the surfaces that must print one: page titles, the PWA manifest, the acknowledge page). The operator's `subtitle` is their own line of copy and renders either way. **Placement is per surface** (`logoOnLogin` / `logoOnSidebar`, both default on, Server Settings → Customization → Logo): switching one off returns THAT surface to the Polaris mark without discarding the upload. **The accent** (`logoAccent`) composites the theme's `polaris-symbol-*.png` onto the bottom-right of the operator's logo at ~50% of its longest side (`ACCENT_FRACTION`, clamped to half its shortest so a wide banner isn't swallowed) — rendered **server-side** by `brandLogoService` and served from the public `GET /server-settings/branding/logo-accent.png`, not as a per-surface CSS overlay, so the geometry can't drift between login, sidebar and mobile. It renders per theme (`?theme=`), which both picks the right symbol variant and gives the `<img>` a new URL to re-fetch on a theme flip; otherwise the path is fixed (the upload route reuses one filename), so it answers `no-cache` + a strong ETag over the source mtimes **and the theme**, and 302s to the plain logo whenever there is nothing to accent.

## Rule 28 — The Windows build is the authority; the product name is not

Microsoft never updated the registry key `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProductName` when Windows 11 shipped, so it still reads **"Windows 10 Pro" on every Windows 11 client**. That key is what WMI's `Win32_OperatingSystem.Caption` and `systeminfo` read, which means this is not one broken integration but *every* source at once — AD's `operatingSystem`, Intune/Entra (which collapse it to a bare "Windows" anyway), and gopsutil's `Platform` inside the Polaris Agent. So the projection's priority order cannot fix it: whichever source wins is equally wrong. The **build number** is always right (it comes from `CurrentBuild`, not the frozen display string), so `normalizeWindowsOs` (`src/utils/osNormalize.ts`) derives the family from it and labels the pair with the release operators actually speak in: `"Windows 10 Pro"` + `"10.0.22631.7219"` → `"Windows 11 Pro"` + `"23H2 (10.0.22631.7219)"`. **Family from a threshold, release from a table** — deliberately different mechanisms: `build >= 22000 ⇒ Windows 11` never goes stale, so a build shipped after this code was written still gets the right family, while the release table does go stale and an unlisted build therefore keeps its RAW `osVersion` rather than being guessed at. **Windows Server is excluded entirely** (any os string containing "server"): its ProductName is already correct, and build 26100 is BOTH Windows 11 24H2 and Windows Server 2025, so the threshold would relabel a 2025 server as a workstation. Applied at **write** time — in `projectAssetFromSources` AND in the `db.ts` Asset hooks (the catch-all for the inline writers) — not at render, because the Assets table's OS/Firmware **filter and sort**, CSV/PDF export, `os`/`osVersion` tag criteria, maintenance criteria and automation scope conditions all read the stored columns: an "os contains Windows 11" rule is only true if the column says so. Two properties keep that safe to run on every write: it is **idempotent** (a re-write of its own output is a no-op, or the label would nest — `"23H2 (23H2 (…))"`), and it **reads no row** (the build comes from whatever `osVersion` the same write stages, so the monitor hot path pays nothing). Normalizing only on the way to the DB would make `projectionDriftService` report permanent os drift, which is why the projection normalizes its own output too. Not retroactive: existing rows correct themselves when their integration next re-projects them (rule 22's pull-based precedent), and there is no backfill job.

## Rule 29 — One outage is one alert: packet loss is what happens while the device is answering

`probeLossPct` is the only metric whose INPUT is failed probes, which made it the only one that could raise a second alert about an outage `monitorStatus == down` already owns. Two gates bound WHEN it may alert and one marker bounds WHICH PROBES it is made of (h), and all three are about the same distinction — *lossy* is not *dark*. (a) **Only an ANSWERING device reports loss**: `assetIsAnsweringProbes` (notificationEngine) admits `up` and `warning` and nothing else — `passive` included in the exclusion (business rule 36): a dark passive device sits at 100% loss indefinitely and there is no asset-down alert to supersede the loss alert, that alert being precisely what is missing, so admitting it would park a permanently-firing, never-clearing alert on every device an operator just told Polaris to stop judging. `warning` is deliberately IN — it is 1..`failureThreshold`-1 consecutive failures on a device still replying, i.e. the state a lossy-but-alive device lives in (an alternating pass/fail device never reaches `down` at all), so gating on `up` alone would silence the feature's whole purpose. `down` and `recovering` are OUT (`recovering` is the tail of the same outage — asset-down is still live until successes reach the threshold), as are `unknown`/null (nothing measured yet). The filter sits in the `probeLossPct` resolver so the composite-trigger path and the wizard's preview inherit it from one place; `evaluateThresholdRule` separately **clears** a live loss alert on an asset that stopped answering (`clearedBy="system:device-down"`, `notification.superseded` Event with `reason:"device-down"`) rather than freezing it — the carve-out's handoff semantics, because freezing is exactly what used to park a packet-loss alert next to the asset-down alert for the whole outage. No reset actions on that path (the alert isn't recovering; mailing "loss resolved" about a device that just went dark would be worse than silence). Metric-scoped via `ANSWERING_ONLY_METRICS` — every other metric is derived from SUCCESSFUL polls, so a dark device simply stops producing readings. (b) **THE ANCHOR IS GONE (2026-09-01), and its removal is the rule.** From 2026-08 the ratio started at `GREATEST(first success in window, Asset.recoveryStartedAt)`, trimming any outage out of its own denominator. The reasoning was sound as far as it went: a device unreachable for part of the window had no probes there to lose, and without the trim a device recovering from a 55-minute outage read ~92% the moment it came back and kept alerting for a full window — firing *because* it was healthy again.

What the trim also did, and what nobody noticed for a month, is silence the case the metric exists for. Only an outage-ending recovery stamps `recoveryStartedAt` — chosen deliberately so a flapping device passing through `warning` would not restart its own window every few probes. But a device flapping hard enough to reach `down` each cycle stamps it on EVERY recovery, collapsing the window to the last few probes and reporting **~0% loss forever**. Prod 2026-09-01: a device sawtoothing to 100% loss every seven minutes, charted plainly as such, captioned `avg 0%`. A badly lossy link that Polaris insisted was clean is the exact failure `probeLossPct` was added to catch, and no amount of tuning the anchor fixes it — the trim cannot tell an outage it should discard from an outage it should count, because they are the same shape.

So the measurement is now plainly **failed/total over the whole window**, and the false alert the anchor prevented is handled where it belongs — at the alert, and (from 2026-09-03) on the individual probes the outage explains rather than on the window they sit in (h). Keeping the number honest and deciding separately what deserves paging someone is the separation the anchor blurred; what the anchor got wrong was not that it excluded something but that it excluded by TIME, and an outage and a lossy hour are the same shape when all you can see is where they start. `Asset.recoveryStartedAt` is still stamped (`utils/probeLossAnchor.ts` keeps the writer, whose reasoning is now only of historical interest) and **read by nothing** — dormant on the `cooldownSec` precedent, and safe to leave that way in a sense `cooldownSec` was not: a dormant timestamp cannot change behaviour, where a dormant cooldown silenced alerts.

(c) **A reading at or above the automation's own `ignoreAtOrAbove` ceiling is not a reading.** This is what replaced the anchor. The default is **100**, which suppresses only a total outage and leaves every rule authored before the control behaving exactly as it did. Lowering it is how an operator says "an outage that has just ended is not a lossy link": with every miss counted, a device back from a 55-minute outage genuinely reads ~92% until the outage ages out of the window, and at 90 that never fires. The predicate is `readingAtOrAboveCeiling` (notificationTypes, pure), applied in the `probeLossPct` resolver so the composite path and the preview inherit it from the same place as gate (a).

Polaris does NOT move the default to buy its own quiet. The shipped baseline "High packet loss" rule is scoped to ALL ASSETS, so at 100 it would trail a second alert behind every outage on every device — it therefore carries `ignoreAtOrAbove: 90` of its own (`BASELINE_LOSS_CEILING_PCT`), and the **V5 one-shot** (`migrateLossCeilingV5`, marker `seedBaselineAutomationsV5LossCeilingSeededAt`) retrofits that onto existing installs, whose seed marker means they will never re-seed. Bounded like V3's retire step and V4: only `probeLossPct` triggers stating NO ceiling, and only rules never edited (`updatedAt === createdAt`). An edited rule is left alone AND **named in a warning Event** — silently narrowing someone's tuned alert is worse than leaving it noisy, but they have to be told it will now alert after outages.

(d) **Both gates CLEAR, and that is not incidental.** A dropped reading is indistinguishable from "stopped reporting" to `clearVanishedStates`, which FREEZES — and a frozen loss alert escalating beside the asset-down alert for a whole outage is the duplicate this rule exists to stop. The engine therefore tracks the two handoffs separately (`notAnsweringIds`, `saturatedIds`), clears with `clearedBy="system:device-down"` or `"system:reading-saturated"`, and stamps `notification.superseded` with the matching reason. Neither runs reset actions: nothing recovered.

(e) **It counts PACKETS, not rows, wherever it can.** An ICMP sweep row (business rule 30's uniform burst sweep) carries `packetsSent` / `packetsReceived` and describes N echoes, so counting it as one outcome understated loss badly — a 5-echo burst that got one reply back is an 80%-lossy reading but a perfectly "successful" row. An asset with any burst rows in the window is measured from those sums and its response-time poll rows are EXCLUDED, because that poll may be SNMP/SSH/REST/WinRM and folding a lost SNMP response into a figure labelled *packet loss* would make the number mean something different per asset depending on how it happens to be monitored. An asset with no burst rows falls back to the row ratio, which is exactly the pre-sweep behaviour. `{total, failed}` kept its shape through all of this; the units beneath it moved from rows to packets, so no caller changed.

(f) **`windowSec` IS the reading** — it is History, not smoothing — with `forDurationSec` as its own optional sustain knob (`WINDOWED_RATIO_METRICS`, `probeLossWindowSec`, floored at `PROBE_LOSS_MIN_WINDOW_SEC`).

(g) **The chart and the caption now cover the same window.** `ProbeLossSeries.measuredFromMs` and `sparklineSvg`'s `measuredFrom` marker existed only to reconcile a caption that measured less than the line drew; with the anchor gone there is nothing to mark and both are removed. The chart weights burst rows by packets like the query, but deliberately does NOT drop poll rows once bursts exist — a picture of the window has to be continuous, and dropping half its samples would leave visible holes. The consequence is accepted and small: on a mixed asset the caption can sit slightly under the engine's reading. `includeFullyDown` is retired too — with every countable row in the ratio, a fully-dark asset reads 100% on its own rather than needing an opt-in to avoid vanishing from the NOC widget (where vanishing read as "no loss", the opposite of the truth).

(h) **The failures of an outage are the outage, not the link** (2026-09-03). The two gates above bound whether a reading may raise an alert. Neither can see the case an operator actually reports, because by the time it happens the device is healthy: a FortiSwitch went dark for twelve minutes, came back, and its 30-minute window still carried the outage — so it read **40 %**, a "High packet loss" WARNING arrived minutes AFTER the recovery, and it was about the outage the down alert had already reported. The answering gate is silent (the device is answering); the ceiling cannot help either, because 40 % is a completely ordinary reading for a genuinely lossy link and a ceiling low enough to suppress it would discard exactly the readings the metric exists to produce.

The distinction the ceiling cannot draw is not *how big is this number* but **which probes is it made of**. The failures of an outage ARE that outage; a miss taken while the device was answering is packet loss. So the marker goes on the sample at write time — `AssetMonitorSample.assetDown`, the exact shape of `dependencyDown` before it (rule 38b): nullable, catalog-only on the hypertable, never set on a success, and read as false when NULL so the rows written before it still count and the change is **not retroactive**. The probe path stamps it from `nextStatus`, the status that probe RESULTS in; the ICMP burst sweep stamps it from the verdict the configured transport has ALREADY reached, since it never calls `recordProbeResult` and so reaches no verdict of its own.

**The unit of exclusion is the RUN, not the marked row, and that is not a detail.** `assetDown` can only be stamped from the probe that DECLARES the outage onward: when the first missed poll is written, nobody knows yet whether it begins an outage or is one lost packet. Dropping only the stamped rows therefore leaves every outage's ONSET — `missedPolls - 1` fully-lost probes — inside a denominator the exclusion has already shrunk, and the prod case above then reads **10.5 %** instead of 40 %: quieter, still over the seeded rule's 10 % threshold, still a false alert a full window after the device came back. So the run is reconstructed at read time instead — consecutive failures between successes are one group, a group holding any stamped row is an outage entire, its failures go and the answered probe that opens it stays. `probeLossQuery` does it with two window functions (`runId` = successes-so-far per asset, `runOutage` = `coalesce(bool_or(assetDown), false)` over that group; the `coalesce` is load-bearing, since `NOT (NULL AND NOT success)` is NULL and WHERE reads that as false, which would drop every failure in an UNSTAMPED run — all loss, everywhere), and `alertChartService.outageRunFailures` is its JS mirror.

Reconstructing beats counting back `missedPolls - 1` rows, and not only because it is simpler. **That count is the covering automation's** (business rule 36): it differs per device, it changes the moment an operator edits a rule, and a reader that hardcoded it would silently mis-measure every device whose automation says something else. A run is bounded by successes and needs to know no threshold at all.

**Its narrowness is the rest of the design, and is what separates it from the anchor in (b).** The anchor excluded by TIME and threw away everything before the last recovery, which is how a flapping device came to report ~0 % loss forever. This excludes by outage: only runs that actually REACHED `down` go. A run of misses that stayed below the threshold is loss and counts in full, an alternating device never reaches `down` at all and is measured exactly as it was, and a device that is genuinely lossy AND had an outage keeps every miss on either side of it. Read off the chart: **the amber misses are loss, the red ones are the outage.**

**One definition, so the number and the picture of it agree.** Every loss reader applies the same run rule — `probeLossQuery` (the engine's `probeLossPct` and the NOC Packet Loss widget behind it) and `alertChartService`'s loss chart, in BOTH its line and its caption. The SQL and the JS are a mirrored pair and have to stay one. Splitting them is the failure that chart exists to avoid: an alert reading 0.0 % over a graph captioned *avg 40 %* tells an operator the number is invented. The excluded stretch leaves a **gap** in the line rather than a run of 0 %, which is the treatment an unpolled stretch already gets — nothing was measured about the link while the device was dark, and drawing 0 % would claim it was perfect at the one moment it was unreachable. A window that was ENTIRELY one outage therefore draws nothing and captions null, and `pruneEmptyChartSection` removes it: an empty chart is not a claim, where a flat 0 % line under an alert about an outage would be.

Two things deliberately do NOT change. `readMonitorHistory.stats.packetLossRate` — the "Packet loss" figure on the asset page's monitor-history panel — is a different number answering a different question: failed/total of the response-time poll over whatever range the operator has the chart set to, sitting beside `successRate` and the sample counts it must stay consistent with. An outage is exactly what that panel is being asked about. And the Device Map's `degraded` traffic light ("Packet loss — N/M recent samples failed") stays a fixed-count read of recent primary rows; it describes a node that is answering unreliably right now, not a windowed ratio, and it has its own `down` state directly beside it.

## Rule 30 — Confirmation is the configured cadence's job; ICMP only fills in the loss ratio

`monitorStatus` reaches `down` when N missed polls are OUTSTANDING against the operator's configured transport at the operator's configured `intervalSeconds`. For a device that simply stops answering that is still N misses in a row, so time-to-down is unchanged at `N × intervalSeconds`; what changed is the intermittent device, and the bucket that made that work is the paragraph below. **N is the covering automation's `missedPolls` (default 3), not a Monitor Settings value** — see business rule 36; `failureThreshold` on the settings tiers is dormant. What this rule is about is the CADENCE half, which is unchanged: it still comes from the monitor-settings hierarchy — 3 minutes at a 60s cadence, **15 at 300s** — and the figure the monitor-settings card reports is the figure you get. `resolveProbeIntervalSec` (monitoringService, pure + unit-tested) therefore applies exactly ONE clamp: **dependency suppression** (parent dark ⇒ 2× interval, never poll harder into an upstream outage; a `disabled` stream has nothing to slow). **This replaced the fast-confirm re-probe** (2026-08-17 → 2026-08-19), which re-probed a mid-confirmation asset at `fastConfirmIntervalSec` so confirmation cost ~35s regardless of cadence. It was removed because it made the counters a function of a second, tighter cadence that operators could not see in the number they had configured, and because the resolution it bought during a run is worth more as *loss data* than as a faster verdict. `fastConfirmIntervalSec` stays as a **dormant** column (migration `20260817000000`; dropping it would cost an irreversible migration for no gain) read by nothing, and is no longer surfaced on the three monitor-settings cards. What replaced it is the **ICMP loss sweep** (`src/utils/lossSweep.ts` deciding who and how often, `src/utils/burstPing.ts` doing the measuring, `runLossSweepFor` running it, on the existing `lossSample` cadence / pg-boss queue / worker pool and `POLARIS_MONITOR_LOSS_SAMPLE_WORKERS` — those names deliberately kept, since renaming them would orphan a persisted queue and an operator-set env var for nothing). It went through one failed shape first, and that history is the rule. **v1 (2026-08-19) was a per-asset SAMPLER** — a single ping every 10s while an asset sat in `warning` or `recovering` — and it was **disabled the next day**: sampling only while probes were already failing oversamples failure, so the alert's reading diverged visibly from the wall-clock average its own chart drew (rule 29d). There is no way to correct that bias after the fact; the only fix is to stop creating it. **v2 (2026-09-01) is a UNIFORM BATCHED SWEEP** and ships enabled: every eligible asset, every cycle, a burst of 5 echoes, whatever state it is in. Uniform spacing is what makes the ratio mean what an operator thinks it means, and it is affordable only because the pinger is batched — one `fping` process per 500 targets, bounded by burst period rather than host count, so a 2000-asset fleet costs 4 process spawns where v1's shape would have cost 2000. (fping is optional, not required: RHEL ships it only via EPEL and Windows Server has no build, so a bounded per-host fan-out keeps loss CORRECT where it is absent, just slower — `resolveSweepIntervalSec` floors the cadence at what the installed pinger can actually finish, because publishing sweeps faster than they drain grows the queue without bound.) Rows carry `probeKind="icmp"`, a NULL `responseTimeMs`, and the new `packetsSent` / `packetsReceived` pair that lets ONE row describe a burst — which is what makes loss a ratio of PACKETS rather than of poll outcomes, and so what finally separates it from down detection. Anchored by `Asset.lastLossSampleAt`, stamped in one `updateMany` for every asset actually attempted. It **never calls `recordProbeResult`** — it cannot move `consecutiveFailures` / `consecutiveSuccesses` or `monitorStatus` — because ICMP does not authenticate the device it reaches: a second transport voting on `down` would make the state mean whichever of the two answered last, an ICMP-blocked host would false-`down` on its first transient miss, and a device whose SNMP agent had died would never confirm down at all. **`down` assets are now IN the sweep**, reversing v1: that exclusion was a corroboration argument (an uncorroborated ping reply from a host that had taken over the address would drag a dead device's loss down from 100% to something reading like congestion) and it was load-bearing only while loss shared a stream with down detection. It no longer does, and the engine's own answering gate already stops a down device raising a loss alert (rule 29a), so excluding them would only punch a hole in the series at the moment an operator wants to read it. **Dependency-suppressed assets are in it too**, reversing v1's COST argument — five extra packets inside a sweep that was already running, where the old shape would have put every asset behind a dead gate into its own 10s ping loop; their failures are still marked explained via `AssetMonitorSample.dependencyDown` (rule 38b), which is a rendering question rather than a sampling one. The only exclusions left are not `monitored` (covering rule 10's four unmonitorable statuses), `maintenance` (rule 16's one status that keeps `monitored` true while polling stops), and `responseTimePolling === "disabled"` — rule 30 already reads that as the operator saying do not reach out to this device, and it has to extend to ICMP or the setting means less than it says. Note `agent` is NOT excluded any more: "I use the agent for status" must not silently mean "do not measure this network's packet loss". **`probeKind` splits the readers:** the ONLY all-kinds readers are `probeLossQuery` (both modes) and `alertChartService`'s loss chart — that is the point of the sampler — while every response-time reader filters to primary (`probeKind IS NULL OR 'primary'`; NULL is the pre-feature value and means primary). That list is the engine's `responseTimeMs`/`uptimeSec` metrics, the alert-email RTT chart, `sampleHistoryService`'s detail tier + `readLastMonitorSuccessAt` (an ICMP reply is not a success of the monitored service), the NOC response-time ranking, the Device Map's traffic light (a fixed-COUNT window, which mixed rows would silently shrink from ~10 minutes to ~100 seconds mid-incident), **and every rollup** — folding incident-only rows into 400-day aggregates would make historical loss non-comparable across time, so the sampler's resolution lives and dies with the detail retention window. The three monitor-settings cards keep the DERIVED **"Declare Down after (seconds)"** entry (`_polarisMonDownAfterCalc`, shared by render and the live sync, unit-tested), now computed as `interval × (threshold − 1) + probe timeout` and writing `failureThreshold` — operators think in "down after 30 seconds", and storing that as a second setting would just be a number that could disagree with the product of the two that already exist. In cursor mode the sampler's due-set is capped per pass (`LOSS_SAMPLES_MAX_PER_PASS`, 200, logged on truncation) because `runMonitorPass` awaits the whole pass under the light tick's guard and a site-wide outage must never delay the probes that decide whether those assets are down; pg-boss mode has its own pool and a 15s job expiry instead. Both due-set paths call the one resolver and mirror the sampler's due-check (`computeDueWork` + the pg-boss publisher in `jobs/monitorAssets.ts`); their due-sets are contractually identical, so a second copy of this arithmetic is exactly how they would drift.

**The counter is a leaky bucket, not a run length (2026-08).** A missed poll adds one to `Asset.consecutiveFailures`; an ANSWERED poll takes one back, floored at zero. It stopped being a literal consecutive count because a run length forgets an outage the instant one packet answers, and that cuts both ways. A device losing two polls out of every three never reached a verdict in either direction — every single answer reset the run to zero, so the count sawtoothed between 1 and 2 forever and the chronically lossy device stayed invisible to down detection while looking healthy on the pill. And a device already at `threshold - 1` was handed a completely clean slate by one lucky poll, so an outage that had been one probe from being declared started over from nothing. The bucket keeps the debt: three misses then an answer is still two outstanding, and the next miss lands on three rather than on one. **The LEVEL decides the verdict and the outcome of the current probe only breaks the tie below the threshold** — `cf >= threshold` is `down` whatever this probe did, `cf > 0` is `warning` on a miss and `recovering` on an answer, `cf == 0` is `up`. Letting a success win outright would mean a device dark for an hour (cf=60) reads `recovering` on one answered packet out of sixty, and since a down automation tests `monitorStatus == down`, that one packet would clear the alert. Four consequences. **Recovery is now symmetric and free**: draining 3 → 2 → 1 → 0 takes exactly `threshold` answers, the same number of confirmations `consecutiveSuccesses` used to count, so the machine no longer consults it (the column is still written — it is a true fact and it is charted — it simply decides nothing). **`recovering` no longer means “was down”**: it means answering with misses still outstanding, which is reachable straight out of `warning`, so a device that missed twice and then answered is visibly climbing back instead of sitting in amber. **`consecutiveFailures` is no longer a run length**, so the automatable field was relabelled “Missed polls outstanding” — the KEY is unchanged because stored automations reference it, but a rule reading `>= 5` now fires on five outstanding, which a flapping device can reach without ever missing five in a row. And **“Declare Down after” is a floor, not a promise**: `interval × (threshold − 1) + probe timeout` is exact for a device that simply stops answering, and is the fastest possible verdict for one that answers intermittently, which is the honest way round. Mirrored client-side by `PolarisMonitorStates.replay` in `public/js/monitor-states.js` — the ONE browser copy, read by the Last-30-min strip, the desktop response-time chart and the phone's, each of which used to decide it privately — and server-side by `probeOutageService.replayProbeStates` for the alert-email charts; pinned in both directions by `tests/unit/monitorStatusStateMachine.test.ts`, whose parity block reads `monitoringService.ts` itself — the stub in that file is a hand-copy, and it silently pinned the old machine through this very rewrite until the guard was added.

**The bucket gained a CEILING, and an answered probe became unconditionally `recovering` (2026-09-01).** Both halves of the paragraph above were right about what they were solving and wrong about what they left unbounded, and the two defects met on the response-time chart.

The first is the debt. Nothing capped the climb, so `consecutiveFailures` tracked the LENGTH of the outage rather than the operator's definition of one. A FortiGate dark overnight at a 60 s cadence came back at `cf` around 480, and since a success only ever takes one back, it owed 480 answered probes — eight hours — before it could read `up`. Its down alert holds through `down`/`recovering`/`warning` (`DOWN_ALERT_HOLDING_STATES`), so the alert kept repeating hourly and escalating to the L2 recipients for the whole of the following morning, about a device that was answering every poll. The paragraph above defends the unbounded climb explicitly — "a device dark for an hour (cf=60) reads `recovering` on one answered packet out of sixty" — and that concern is real; the mistake was paying for it with an unbounded debt when the alert layer already handles it. `recovering` is a HOLDING state, so one lucky packet clears nothing either way.

So `nextFailureBucket` locks the level at `bucketCapFor(threshold, recoveryPolls)` — the larger of the missed-poll count and the covering automation's reset count — the moment a miss carries it to the threshold. Recovery costs exactly that cap, however long the outage ran: a four-minute outage and a four-day one are the same climb, and the climb is the number the operator wrote down. A miss anywhere in it re-locks the bucket at the cap, so a flapping device still cannot walk itself out of an outage. `MAX_MISSED_POLL_BUCKET` (100) is the absolute ceiling and the passive device's cap, matching the `missedPolls` maximum so no covered asset is ever capped by the constant rather than by its own rule.

The second is the colour. The verdict rule read "the LEVEL decides" without qualification, so a probe that ANSWERED while the bucket sat at or above the threshold was `down`. Defensible for a verdict — the asset genuinely is down until the debt drains — but the response-time chart has no way to paint an `ok` point in the down colour (`_chartPointColor` offers an `ok` point exactly two answers: the series colour or the recovering blue), so those probes fell through to the plain series GREEN. A long outage drew red, then GREEN, then blue, then green, and read as though the device had recovered, broken, and recovered again. The Last-30-min strip directly above it colours straight off the same replay and drew them RED, so two surfaces stacked on the same screen described the same probes in opposite terms — precisely what that shared vocabulary exists to prevent.

With the bucket capped, an answered probe during an outage is unambiguously the device climbing back, so `monitorStatusFor` returns `recovering` for ANY answered probe with `cf > 0`. The level still decides what a MISS means. Nothing downstream loosens: the alert ends at `up`, which is when the drain has served the reset count.

Two clean-ups fall out. `consecutiveSuccesses` now decides nothing at all — the bucket's own level is the whole of the verdict AND of the recovery arithmetic — so `owesRecoveryConfirmation` and the `Asset.awaitingRecoveryConfirm` bit it read are retired (rule 36). And the machine moved OUT of the inline block in `recordProbeResult` into two exported pure functions in `utils/monitorStatus.ts`, which is what let `tests/unit/monitorStatusStateMachine.test.ts` stop hand-copying it — that copy had already silently pinned a retired machine once, through the very rewrite that introduced the bucket.

Existing rows self-heal: `nextFailureBucket` clamps with `min(cap, cf)` before it moves the level in either direction, so an over-cap row converges on its own automation's number at its next probe of either outcome. `jobs/clampFailureBucket.ts` sweeps them at boot anyway, for the readers that reach the column before that probe lands — the strip's tooltip, `runsHeavyCadences`, and `consecutiveFailures` as an automatable `asset_state` field.

**A probe may also decline to be a reading (2026-08).** `ProbeResult.skipped` is neither a hit nor a miss: no `AssetMonitorSample`, no counter movement, no state transition — only `lastMonitorAt`, so the cadence keeps its spacing instead of re-firing on every tick. It exists because of the vCenter polling method, where the thing that answers for a device is not the device. `readVcenterAsset` splits two outcomes that look identical from the outside: vCenter ANSWERED and this VM was not in the answer (deleted at source — a real finding, so the probe fails and names it), versus Polaris could not ASK at all (vCenter down, credential rejected, integration disabled). Counting the second as a miss would declare an entire virtual fleet down at the same instant on a hypervisor-manager hiccup, and a fleet-wide simultaneous outage alert is the one alert nobody can act on. The distinction is the same one rule 38 draws for a dependency-explained miss — Polaris knows why it has no reading — except there is nothing to chart here, because nothing was measured.

**The second skip: `responseTimePolling === "disabled"` (2026-08-28).** For a while the vCenter case above was the only one, on the reasoning that every other transport talks to the device itself, where failing to reach it IS the measurement. That reasoning is sound and it does not cover `disabled`, which is not a transport at all — it is the operator saying *don't poll this*. Nothing was measured, so it is a skip by the same definition.

It had been a *failure*, and the mechanism is worth recording because it is a gap in an otherwise uniform pattern rather than a wrong decision. Every stream's queue publisher checks its resolved method before enqueueing — `lldp` and `storage` and `processes` all do, inline. The response-time probe's push did not. So `disabled` was queued like any other value, reached `probeAsset`, matched no dispatch branch, and fell through to `Unknown polling method "disabled"` — a failed `ProbeResult`. `recordProbeResult` guards `skipped` and `agent` and had no reason to guard a third thing, so it wrote a failed `AssetMonitorSample` and advanced `consecutiveFailures`. An operator switching Response Time off therefore watched the device march to `down` over the next N polls, with the alert naming an outage that was not happening. The one place that already had it right was the loss sampler's own predicate, which excluded `null`, `"disabled"` and `"agent"` explicitly. (That module was retired for the burst sweep on 2026-09-01 — `utils/lossSweep.ts` keeps the `"disabled"` exclusion for the same reason and drops the `"agent"` one, since an agent-monitored host still sits on a network whose packet loss is a real fact.)

The fix is a shared pure predicate, `responseTimeProbeShouldQueue` in `utils/pollingCompatibility.ts`, called by BOTH publishers — `computeDueWork` and the pg-boss publisher in `jobs/monitorAssets.ts`, which are a required lockstep pair and are exactly the kind of duplicated condition that drifts. `probeAsset` additionally returns a `skipped` result for `disabled`, which is not redundant: it covers operator-triggered `/probe-now`, and it covers a `disabled` stored in a JSON tier (`manualMonitorSettings`, an `Integration.config` per-class block) that no publisher-side gate can be sure it has seen. **`"agent"` deliberately still queues** — `probeAsset` returns a synthetic success so the probe counter keeps incrementing under `transport="agent"`, and `recordProbeResult` early-returns before any DB write; dropping it from the queue would silently change that metric.

**A queued job is not a second poll (2026-09-10).** An ICMP-polled FortiSwitch charted 94 response-time samples in an hour, in pairs a few seconds apart on a ~75 s rhythm, while SNMP-polled devices beside it charted cleanly at one a minute. Nothing about the device was wrong. The pg-boss publisher re-evaluates the due set every 5 s, and the probe queue's `stately` policy absorbs a re-publish only while the earlier job is still QUEUED; while that job is ACTIVE, one more may queue behind it. ICMP status probes run as batched chunks keyed by chunk index, and a chunk runs until its slowest target times out, which, with any dead host among 250, is the full probe timeout: one whole publisher tick. `lastMonitorAt` is only stamped when the readings are recorded, so the next tick still saw the chunk as due and queued a copy behind it, and that copy pinged the same hosts again as soon as the first finished. SNMP escaped only because its per-asset probe finishes in tens of milliseconds; a per-asset probe to a dark host at a 5 s timeout could double the same way.

The chart was the visible half. The half that matters for this rule is that a dead host took two misses per cycle, so it reached N in half the configured time, and "N missed polls" stopped meaning N polls. The fix keeps the queue policy (it is what stops a backlog piling up) and closes the gap at pickup instead. Both job shapes carry the probe interval the publisher resolved, and the worker re-runs the publisher's own due check against the freshest stamp it can see (`probeStillDue`), including the probe-patch buffer's unflushed value, because the queued copy activates before the 2 s flush reaches the row. A duplicate records nothing at all, not even the `lastMonitorAt` that a `skipped` probe bumps, because the earlier job's stamp is the real anchor. Batched readings are also now stamped at the instant the echoes went out rather than when the chunk finished, which removes the probe timeout from the ICMP cadence and puts each dot where the measurement actually happened.

## Rule 31 — The login page is the way back in, so restricting it is opt-in and must refuse to lock you out

"Skip login page" redirects unauthenticated visitors straight to SSO — on PROTECTED pages, and since 2026-09-06 on `/login.html` itself, which until then loaded the form for anyone who typed the URL ("skip" read as hide-from-navigation; operators expected hide). `/login.html` stays out of `protectedPages`, and two query keys still draw the form, each stopping a loop or a lockout: `?error=` (an SSO attempt just failed and bounced here — every SAML / OIDC / App Proxy failure redirect carries it, and redirecting again would ping-pong with the IdP forever) and `?local=1`, the recovery path when the IdP is down, which local + LDAP accounts reach by typing it and which the Session tab's hint names. A logout never lands on the login page at all: every desktop logout landing — account menu, inactivity timer, the server-side idle check — is `/signed-out.html`, a page with NO form (`public/signed-out.html` + `public/js/signed-out.js`, `?reason=inactivity` from a closed set selecting the sentence) whose Sign in button opens the bare `/login.html`, so the skip setting decides what comes next — SSO when it is on, the form when it is off — and a silent `prompt=none` provider can't sign the operator straight back in the moment they log out; the phone's counterpart is its one-shot sessionStorage marker. That key is deliberately guessable, not a secret, so the password surface is still reachable from anywhere by anyone who knows it, which some installs don't want. `loginAccessConfig` (`{enabled, ipScope, allowedCidrs}`, Server Settings → Web Server → Local Login Access, **default off**) restricts it by source IP, resolving through the same `utils/ipScope.ts` the Dash wallboard gates on. Six decisions carry it. (a) **Both halves or neither**: the gate covers `/login.html` AND `POST /auth/login` + `/auth/login/totp`, because the form is a plain POST to a JSON API — gating only the page is cosmetic, the endpoint gate is the control. (b) **The two refusals differ deliberately**: the page is DROPPED (socket destroyed, no response — the dashServer stealth posture, so a scanner can't confirm a local login path exists), the API answers the SAME generic 401 a wrong password gets, since "you're on the wrong network" is a fact worth learning. Every blocked POST writes a warning `auth.login.blocked_source` Event, bounded by the existing 10-per-15-min login limiter mounted above it. (c) **SSO is never gated** — SAML, OIDC and App Proxy must keep working from anywhere, and that is exactly what makes restricting the password path survivable. (d) **LDAP is gated, because it shares `POST /auth/login`** — an install whose remote users bind against LDAP should leave this off or scope it to include them; the "Skip login page" checkbox now says so. (e) **It fails OPEN** (`isLoginSourceAllowed` swallows a settings read error): a DB blip must not become the lockout the feature prevents, and no attacker can induce one. The PUT's anti-lockout guard is the mirror of the rising-edge SSO check on `skipLoginPage` — it refuses a scope excluding the admin's own `req.ip` and names the address it saw, and it restricts new LOGINS rather than live sessions, so a too-narrow save is still undoable from the open session. (f) **It is only as true as `req.ip`** — behind two proxies with a one-hop `TRUST_PROXY`, `req.ip` is the INNER proxy's RFC1918 address, so an "rfc1918" scope would admit the entire internet while reading as enforced. That is why the GET returns `callerIp` and the card prints it: the failure is invisible without it.

## Rule 32 — A reset condition answers "what has to become true again", so it starts as the trigger inverted — and it resolves where the alert lives

Unchecking "reset when the trigger is no longer true" used to leave only *timed* and *manually only* on a single-condition automation: the custom-condition builder was composite-only (`validateRuleV2` refused a `reset.condition` on any other trigger), so the two things an operator actually wants — a different recovery value, or recovery measured on something else — had no home. The mode is now offered on every trigger with a continuous condition (`TRIGGER_TYPES_WITH_RESET_CONDITIONS`; `event`/`change` fire on an instant and are still refused, client and server), and unchecking the box lands on it **pre-seeded with the trigger inverted** — same comparator flip `resetSentence` has always rendered (`invertedLeaf`; a 0/1 flag flips its VALUE, not its comparator), extended to trees by `invertedTree` (**De Morgan** — group operators flip alongside each leaf, which is what keeps the result expressible in an and/or-only vocabulary). Severity bands are ignored: every tier recovers at tier 0, so the base condition is the only one there is anything to invert. Four decisions carry it. (a) **The tree is the SOLE recovery authority while firing** — the trigger falling away does not clear the alert and the trigger re-meeting does not cancel the reset's sustain timer (`recoveredSince` belongs to the tree). That contract already existed for composites; `evaluateThresholdRule` now honors it too, in a dedicated pass after the readings loop rather than inside it, because the tree's leaves need not be the trigger's metric at all — an alert whose trigger metric stopped reporting must still be able to clear, where the auto path deliberately freezes. That pass **re-reads the firing rows from the DB** rather than trusting the pre-loop `states` snapshot the carve-out / device-down / vanished sweeps have since invalidated, so a row cleared as superseded this tick can't then be "recovered", and a row that only just fired can't recover in the tick it fired. Suppressed assets stay frozen. (b) **Resolution is DIMENSION-FIRST with a per-asset fallback** (`resolveResetTruths`): a per-mount or per-interface alert whose reset leaf sits on that same dimension space clears independently of its siblings, while a leaf on a device-wide metric (CPU, memory, monitor status) reports nothing at `assetId|port2`, falls through to the ANY-dimension fold composites use, and therefore clears every alert on the device together. Both halves are wanted — "clear port2 when port2 recovers AND the box's CPU is under 70" evaluates each half where that half lives — so the wizard says which one the operator is building instead of picking for them. (c) **Kind coherence is enforced on single triggers too**, not just composites: a device trigger with a `host_metric` reset leaf (or the reverse) resolves against assets that can never report it, so the tree reads permanently false and the alert could only ever be cleared by hand. (d) **Reset leaves inherit the trigger's measurement window** — the reset step has no window control and must not grow one (rule 29c), so an aggregated reset condition is measured over the same period as the trigger; when the trigger reads `latest` there is no period to average over and the save is refused with a message that says so, rather than the trigger step's message pointing at a field that isn't there.

**(e) The two triggers a condition is refused on get the counterpart EVENT instead (2026-08).** "They reset on a timer or by hand" was the honest answer only for as long as the alternative was a condition tree, and it produced automations that lie: the seeded "Agent disconnected" rule cleared itself after four hours whether or not the agent ever came back, so the Alerts tab said the fleet was healthy on the strength of a clock. An event automation has no reading to recover — but it usually has a recovery EVENT, because Polaris writes both halves of the pair itself (`agent.disconnected` / `agent.connected`, `integration.discover.error` / `.completed`, `agent.upgrade_failed` / `.upgrade_succeeded`). `reset.mode = "event"` is that pair, and `TRIGGER_TYPES_WITH_RESET_EVENT` is deliberately the exact COMPLEMENT of `TRIGGER_TYPES_WITH_RESET_CONDITIONS`: a continuous trigger already recovers on its own reading, and letting an unrelated Event clear a live threshold alert would hide a device still over the line. Four decisions carry it. **Same-subject is not configurable** — the clear is keyed on the identity the notification already stores (`assetId` when the event names an asset, else the resource label), because one agent reconnecting says nothing about another's, and offering a toggle would only offer a way to get it wrong. **An event that both fires and clears a rule only fires it**: a glob wide enough to match its own recovery (`agent.*` on both sides) would otherwise clear the alert it just raised, every tick, forever, so a rule that matched an event as a trigger drops that event's reset hit. **Resets apply after the batch's own fires land** — within one 1000-event batch a disconnect and its reconnect can both arrive, and the disconnect genuinely happened, so it is raised, delivered, then cleared rather than swallowed. And **the recovery pattern is prefilled, not guessed**: `RESET_EVENT_SUGGESTIONS` maps trigger pattern → counterpart and is published in the builder catalog, so the wizard fills the field from the server's own list rather than the browser inventing a verb — a new event automation whose action has a known counterpart starts on this mode instead of on a timer. Existing installs are carried forward by the seed job's V4 one-shot, which repoints ONLY rules whose pattern has a known counterpart, that are still on a timer, and that the operator has never edited (`updatedAt === createdAt`) — an edited timer is a decision, and changing when someone's tuned alert clears is worse than leaving it on a clock.

**And `cooldownSec` is not a reset at all — which is why it is gone.** It sat on the reset step from the beginning, where it read as part of how an alert clears; it decides how often a NEW alert may be raised and does nothing to one that is already up. Moving it to the Actions step's in-app-alert card, beside the other two properties of the alert RECORD (`requireAckNote`, `repeat`), fixed where it read but not whether it earned its place: sitting inches from "Repeat this notification", it invited operators to reach for it to answer a question repeat answers better, and its own help text had to spend three clauses saying what it does NOT limit (reminders, escalation, an alert already up). It was retired from the builder in 2026-08.

The DATA went with the control, and that pairing is the rule. The engine still enforces the column, so removing only the field would have left rules holding a suppression nothing on screen states and nothing in the UI can edit — an automation silent for twenty minutes with no surface anywhere in Polaris able to explain why, which is worse than either keeping the control or dropping the behaviour. `jobs/clearNotificationCooldowns.ts` nulls it fleet-wide behind a one-shot marker, and writes its audit Event FIRST: the Event names every affected rule and its old value in seconds, because the UPDATE is what makes those numbers unrecoverable and an operator who wants the suppression back has nowhere else left to read it. One Event for the sweep rather than one per rule, so fifty cooled-down automations can't push a day of unrelated history off the 7-day retention window.

What survives is the column and the two engine checks, **dormant** — the `failureThreshold` precedent from business rule 36. An API caller may still set a cooldown deliberately; the wizard simply never reads one back and writes null on every save, so it cannot outlive the next edit in the builder. The list row's enable/disable toggle, which PUTs the whole record, still carries a stored value through unchanged — that toggle must not be a way to silently discard configuration its operator never opened.

## Rule 33 — A device that answers is not a device that works — and the check that proves it belongs to the VENDOR, not to a login

ICMP proves a NIC answers and SNMP/SSH prove a management plane answers. Neither proves the thing the device exists to do still works: a web server that has lost its backend still completes the handshake and still returns 200, with an error page in the body. The **HTTP check** is one GET against the device's own address, up/down decided by the status code and optionally by a string the response body must contain (`utils/httpCheck.ts` decides, `probeHttp` in monitoringService owns the socket). It shipped as a POLLING METHOD and was **retired as one in 2026-08**; it is now a **manufacturer custom widget** (`ManufacturerCustomWidget.widgetType = "http"`). The move is about where a check DEFINITION belongs: as a polling method it had to ride an `http`-typed Credential, which made the thing that answers "how do I log in to this vendor" also carry "which path, expecting what" — so a second path meant a second copy of the same password, and rotating the password meant editing every path. Keyed by manufacturer + optional `modelPattern` instead, it varies on the axis a check actually varies on: every Axis camera answers the same VAPIX path, and a blank model pattern means every device of that manufacturer. Eight decisions carry it. (a) **The body match is the load-bearing half**: a 200 whose body doesn't match FAILS, with the missing content named. There WAS a `failOnMismatch` toggle letting a mismatch pass anyway — it made sense while this drove `monitorStatus` and reachability-only semantics were a reasonable ask, but a widget only RECORDS an outcome and an automation decides what "down" means, so a mismatch stored as a PASS would make `expectBody` decorative (nothing downstream could tell the two apart). It is stripped on save; a laxer rule is expressed by leaving `expectBody` empty and judging on the status code. (b) **Status is judged before content**: a 401 is a broken credential, not missing content, and blaming the body sends the operator to the wrong field. (c) **Redirects are never followed** — a 302 to a login page is the single most common way an HTTP health check reports "up" about a device serving nothing; an operator who wants the 3xx sets `expectStatus` to it. (d) **The body is capped** at 64 KB and the request torn down at the cap, which bounds both a device streaming a log file at the check path and the text an operator-authored `regex` runs against — that pattern is not analyzed for backtracking (nothing static can be); `contains` is the default for the same reason, and a truncated miss SAYS it was truncated. The regex is COMPILED at save by `validateHttpCheckDefinition`, the SAME function the Test Connection flow uses, so a check cannot pass a live test and then be rejected when it is saved. (e) **The credential is authentication and nothing else**, with **no "none" mode**: an unauthenticated check is a widget with no credential attached, which is the same outcome without an empty row that still reads as configuration. `credentialId` is `SetNull` — deleting a credential must not silently delete the check that used it. (f) **The auth scheme is STATED, not guessed.** `authMode` (`bearer` | `basic` | `digest`) is explicit because Basic and Digest carry the same username/password pair, so nothing stored could distinguish them — and the obvious inference (try Basic, fall back on a 401) would send the password in cleartext to any device that answered a Digest challenge, which is precisely the exposure Digest exists to prevent. **Digest is a handshake, not a header** (`utils/digestAuth.ts`, RFC 7616): the response hash is keyed on a server-issued nonce, so `probeHttp` fires bare, reads the 401 challenge and re-fires exactly ONCE — never a loop, because a server rejecting a correctly-computed response will reject it again and retrying past that turns a wrong password into a request amplifier aimed at the device; the second request inherits what REMAINS of the probe timeout. The nonce is deliberately NOT cached: that would cut the steady state to one request but requires a strictly-increasing `nc`, trading a cheap doubling of a cheap request for a replay-shaped failure that only appears under concurrency. It matters for exactly the devices this exists for — Axis OS answers VAPIX with Digest and 11+ disables Basic by default; cameras, PDUs and older BMCs are the same story. (g) **It no longer moves `monitorStatus`.** Each scrape writes a 0/1 to **`AssetStateSample`** (alertable through the existing `customStateValue` metric with no engine change) plus the round-trip time to `AssetCustomWidgetSample` as a gauge, so a slow-but-passing endpoint is visible before it starts failing. The 0/1 is written PASS OR FAIL — the opposite of the state-PROBE rule, which drops an unreadable row because 0 there is a positive claim of health about hardware that may not exist; here a failed request IS the reading, and dropping it would make an outage indistinguishable from a device nobody checked. The gauge is written only on success (a failed request has no meaningful duration). Up/down for such a device therefore comes from whatever transport its responseTime stream uses — usually ICMP. The check also runs INDEPENDENTLY of the SNMP widget gate: an HTTP check must not depend on whether the device also answers SNMP, and a failed SNMP session no longer aborts the pass. `Asset.httpCheckPath` still overrides just the path, for the single device whose endpoint sits elsewhere. (h) **`netGuard` is deliberately NOT applied** — every other outbound-HTTP path in Polaris (automation `api_call` actions, webhooks) SSRF-checks its target because the URL is config pointed at arbitrary hosts, whereas this target is the monitored asset's own private address, the same one the SNMP / SSH / WinRM probes already dial, so a guard rejecting RFC1918 would reject the entire feature. It is also happy to dial a NAME rather than an IP (`dnsName || hostname` when there is no `ipAddress`): a TLS check against a name is the check an operator means, since the cert and any vhost routing are keyed on it. **Tailoring a check is a first-class flow**, because the expectation is a string that has to be picked OUT of the device's response: `POST /credentials/test` accepts a full check definition alongside the credential and returns `httpDiagnostics` — request line as dialed, status, content-type, byte count, cap flag, match verdict, the auth schemes the device asked for, and a 4 KB body excerpt — so the loop is point it at a device, read the body, paste a distinctive string into Expected content, re-test, then save the settled values onto the widget. The response BODY is deliberately kept out of the `credential.tested` audit Event (arbitrary device output would ride every pg_dump and syslog forward), and no response header beyond `content-type` is returned, since a full dump would put a live `Set-Cookie` into the modal.

## Rule 34 — An active scan finds things; a separate grant adds them

Every other discovery pathway in Polaris asks something that already knows the device (a controller, a directory, a hypervisor, a tenant). A **Discovery** (`NetworkScan`) instead sweeps addresses the operator names, which makes it the only Polaris feature that touches hosts it has no prior relationship with — so the posture matters more than the mechanism. Seven decisions carry it. (a) **Scanning and adopting are separate grants.** Authoring and running ride the `networkScan` key; `POST /network-scans/:id/adopt` chains `assets:write` on top (the `PUT /application-map/discovery` precedent). A role may therefore be allowed to find out what is on a range without being allowed to put it in inventory, and the wizard renders that state rather than discovering it at the POST — Export and Save work, **Create assets** is absent with a reason. A `read`-level caller gets a read-only walkthrough, since a scan run by one operator is legitimately handed to another to adopt. (b) **It is opt-in and IDS-visible, and says so.** There is no scheduler and no shipped default range: a scan happens because an operator pressed a button. `arpPrimeService`'s file header already warns that an unannounced sweep of every reserved IP is what IDS dashboards flag, and this is more aggressive than that sweep. The wizard does NOT say so — an operator-removed banner (2026-08-25): an operator who reaches a screen headed "which addresses should Polaris sweep" already knows they are scanning, so the warning read as noise on every visit while the posture it describes is enforced by the mechanism (no scheduler, no shipped default range, a separate grant) rather than by being read. Pacing, batching, a hard target cap and swallowed per-target errors all follow that service. (c) **Some addresses are excluded regardless of what the operator typed** — loopback, link-local (including the `169.254.169.254` cloud-metadata address), multicast and unspecified: the `netGuard` blocklist minus its RFC1918 allowance, since RFC1918 *is* the point here. They are filtered out of the expansion and COUNTED in `droppedTargetCount` alongside over-the-cap truncation, because silent removal reads as "the range is clean". (d) **New addresses only.** A responder whose address an Asset already carries is excluded server-side and reported as a count, so "nothing new" is distinguishable from "nothing there". The corollary is deliberate and worth stating so it doesn't read as an oversight: **a re-run enriches nothing** — it is a way to find what has appeared, not a sync. (e) **No `network-scan` sourceKind.** Adopted assets are created exactly like the manual `POST /assets` path (fields inline, `ipSource="manual"`, the `db.ts` extension minting the `manual` AssetSource row), because `projectAssetFromSources` has ZERO rules for a kind outside its union: such a row would contribute nothing to the projection while `projectionDriftService` compared projection against the stored row, i.e. a drift-log generator. Adding rules instead would put a one-time scan blob in competition with a later agent for hostname priority, which is the wrong outcome. Scan provenance goes where discovery already puts it — the one-time `Asset.notes` boilerplate plus an audit Event. (f) **SNMP goes through the gate, always.** `withSnmpGate(host, port, …)` is not optional here: many switch and AP SNMP agents are single-threaded, and a scan that skips it contends with the monitor loop's probes on the very hosts Polaris already polls. Identification reuses the one exported probe surface (`probeCredentialAgainstHost`) and the exported `snmpWalkRaw` rather than reaching into the module-private per-transport probes. (g) **A Discovery is private or shared, and sharing is what `write` buys** (2026-09-04). Scoping a sweep is real work — which ranges are actually in use, which credentials answer on them, which interfaces are worth pinning on what it finds — and until this change there was no way to hand that work to a colleague except by exporting a file and asking them to import it. `NetworkScan` therefore grew `visibility` (`private` | `public`) + `ownerId`, the `SavedTableFilter` / `SavedDashboard` model, with `createdBy` reused as the username snapshot rather than a second `ownerName` column. Five things follow. **Visibility governs seeing and RUNNING; ownership governs editing.** `listScans` returns own ∪ public, every by-id read goes through `assertScanVisible`, and `triggerScan` asks only whether the caller can SEE the row — running somebody else's shared Discovery is the entire point of publishing one. Editing and deleting stay the owner's, with `networkScan:fullwrite` as the housekeeping override for someone else's row or for an orphan left by a deleted account; that check lives in the route because it needs `req.permissionLevel`. **Invisible answers 404, not 403** (the `GET /alerts/:id` posture) — that a private Discovery exists is not other operators' business, and its name is a site name. A run inherits its Discovery's visibility for the same reason: the hits ARE the recon material, so `/runs/:runId` must not be a way around a private row. **Publishing needs nothing above the `write` every mutation here already needs**, which is where this diverges from saved filters and dashboards: those mounts sit at `read` and spend `write` to mark the publish, but this mount's floor is already `write` for any change, and `networkadmin` / `assetsadmin` hold `write` and not `fullwrite` — requiring more would have put sharing out of reach of exactly the roles that author Discoveries. So `hasOwnershipDimension` is now true on the key (edit/delete = own vs any) while the shared-write escalation deliberately is not. **Name uniqueness moved from global to per-owner**, because a 409 naming a row the caller cannot see is both a dead end and a disclosure; the migration is safe because existing names were globally unique. **Existing rows migrate as `public`, new ones default to `private`.** Every saved Discovery is visible to every `networkScan:read` holder today, so migrating them to private would have hidden colleagues' saved work as the side effect of shipping a sharing feature; from here on an author opts in. Two smaller consequences, both of the same shape — a row nobody can see is a row nobody can fix: a caller with no user identity (a bearer token) may not create a PRIVATE Discovery, and a row whose owner is NULL may not be made private. Visibility is deliberately absent from the `.discovery.json` export — it is an ownership fact about one install, not portable configuration — so an import lands private.

## Rule 35 — The GAL is a mirror, not a source of truth — and Polaris only ever deletes what it wrote

Polaris could already SEARCH the organization's Global Address List live: one typeahead query fanned out to Microsoft Graph and LDAP, merged, and **persisted nothing**, so only an address an operator actually picked became a stored `Contact`. That design was deliberate and this rule reverses it, which is worth stating plainly rather than quietly overwriting: the header of `directorySearchService.ts` argued that a bulk sync lands the entire employee roster — names, addresses, titles, departments, phone numbers — in Postgres with its own retention, backup and audit-exposure surface, to make a typeahead marginally faster. What changed is the ask. Alert recipients and device ownership are chosen from the address book, and curating that book by hand for a company of this size is not something anyone will keep up with; a directory that is already the system of record for who works here should be able to fill it. So the roster is now stored, and the whole rule is about what it costs and what bounds that cost.

**What lands where.** Every non-excluded GAL entry becomes a `Contact` row carrying primary SMTP address, display name, job title, department and phone, plus a per-source `observed` blob in `DirectoryContactSource` holding the same fields and the AD distinguished name or Entra object id. All of it rides every `pg_dump` the install produces, including the off-host backup copies. None of it may reach `Event.details` or the logs — those are readable by anyone holding events access and are shipped off-host by the syslog (CEF) and SFTP archivers, so the sync's own Events carry COUNTS ONLY. The one deliberate exception is `contact.adopted`, which names the address exactly as `contact.created` already does: a single act by a person is audited by name, bulk machine activity is anonymous. Do not "fix" that asymmetry. Granting Graph tenant-wide directory scopes, and accepting the retention posture, are decisions for a human before the toggle is switched on.

**(a) Provenance decides deletion.** This is the `TagAutoAssignment` / `RegionTagAssignment` pattern, with one adaptation forced by `Contact.email` being UNIQUE: a synced row and a hand-added row for the same address cannot coexist, so provenance governs the DELETE half only, and the CREATE half is handled by never writing over a claimed address. A person present in both AD and Entra owns ONE contact with TWO provenance rows, and the contact dies only when the last one goes. Because `email` is unique, a synced row also physically BLOCKS an operator from creating that person by hand — which is why creating or editing over a synced address ADOPTS the row (origin → `manual`, `createdBy` stamped, provenance deleted in the same transaction) rather than failing. Adoption is what preserves this rule's own guarantee: an adopted row has no provenance, so the reconcile will never remove it. Deleting a synced row is refused outright with a 409 naming the exclusion filter and the adopt path, because a delete would succeed and then be silently undone by the next run — leaving the operator believing the address was gone. Reaching the adopt path already requires `fullwrite` with no extra code, since synced rows carry `createdBy = null` and `assertOwnership` refuses a null `createdBy` at write level.

**(b) A Polaris account or a curated contact wins.** SSO-provisioned users (SAML, OIDC, LDAP) have addresses that are also in the GAL, so without this the sync would mint a duplicate entry for every colleague who can already log in. The claimed-address set is recomputed each run — `Contact where origin = 'manual'` unioned with every `User.email`, compared case-insensitively because `User.email` is nullable, non-unique and not normalized — so an account created AFTER the first sync retires the synced row on the next run rather than coexisting with it forever.

**(c) An empty read is ambiguous, so it never wipes.** The same lesson as `persistMacTable` and `persistInterfaces`: a source that answered but returned nothing is indistinguishable from a source that has nothing, and the two want opposite handling. A revoked Graph grant, an expired secret or an unreachable DC would otherwise present as "everyone left the company" and empty the address book in one pass. So a run that scanned zero entries, or whose delete set exceeds the guard, skips the deletion half entirely, records it in the summary, and raises the Event to warning.

**(d) Visibility is gated on `automationManagement`, not `contacts`.** Every built-in role holds `contacts` at read or better, so gating synced rows on that key would gate nothing: any account could enumerate and export the entire company directory. `automationManagement` is seeded `fullwrite` for admin and assetsadmin and `none` for readonly, networkadmin and user, so it does real work. The live GAL fan-out takes the SAME gate, because it serves the same people from the same directory a query at a time — gating the stored copy alone would be a gate in name only. Both FILTER rather than 403, the posture `/search` and `/dashboard/noc-summary` already use; and a gated caller who asks for ONLY the synced rows gets an EMPTY page, never the manual rows, because answering a question nobody asked reads as a broken filter rather than as a boundary.

**(e) Counts, never names.** See "what lands where" above: the run Event reports scanned / created / updated / deleted / excluded and the dominant exclusion reason, and names nobody. Per-row Events are not written at all — twenty thousand of them would flood the 7-day retention table AND put the roster into `Event.details`, which is precisely the exposure this rule spends its other four invariants bounding.
