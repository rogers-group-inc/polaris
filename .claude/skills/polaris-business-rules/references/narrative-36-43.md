## Rule 36 — The automation decides what "down" means; a device no automation covers is never judged

Down used to be a Monitor Settings value: `recordProbeResult` compared `consecutiveFailures` against a `failureThreshold` resolved through the (integration, assetType) tier hierarchy. That put the number that decides an outage in a settings card scoped by integration and asset type, while the thing operators think of as "my down alert" — the automation, with its device filter — could not touch it, and there was no way to say "core switches are down after 2 missed polls and page the NOC; workstations after 10 and stay in-app". Now a `monitorStatus == down` automation carries a **`missedPolls`** count and that count IS the definition of down for every device it covers (`downDetectionService.resolveDownThreshold`, called once per probe). **Precedence is business rule 18's existing ladder, not a second system**: all down automations share ONE `triggerSignature`, so the same most-specific-wins rule decides both whose count governs a device and which automation alerts on it — which is what makes overlapping device filters (the central use case) explainable, and what lets the wizard's existing carve-out warnings describe down-detection coverage with no new concept. On a same-rank TIE the **smaller count wins** (the more-sensitive definition — matching `getMetricSeverityTiers`' existing convention, and the safe direction: both tied automations still fire, so the smaller means neither fires later than its own config promised), then older `createdAt`, then lower `id` for a stable diagnostic identity. **A device covered by NO down automation reads `passive`** — the sixth `monitorStatus` value. It is still polled, still sampled, still charted; Polaris simply renders no verdict about a device nobody asked it to judge. Four things follow, and each is a place the naive reading breaks something: the counters **keep advancing** while passive (so a surface can tell "passive and answering" from "passive and dark" without a new column, and an asset that later gains coverage converges on its very next probe instead of restarting its run at zero); the heavy cadences run for a passive asset **whose last probe succeeded** (`runsHeavyCadences` — a bare `=== "up"` gate would stop telemetry/interfaces/storage for every passive device and every chart would silently go flat with nothing erroring); entering or leaving passive is a **CONFIGURATION edge** (`isConfigStatusEdge`) that writes no `monitor.status_changed` Event and fires no dependency propagation, because one rule save can move thousands of assets across that line at once and the rule-CRUD audit trail already records the cause; and anything testing `!== "up"` as a proxy for "unreachable" must exempt it — the DHCP-push deferral in `reservationService` would otherwise defer a passive FortiGate's pushes **forever**. **Deleting every down automation blinds the fleet, and the thing that would alert about that is what was deleted** — hence a one-shot `monitor.down_detection_absent` warning Event on the transition into a zero-rule fleet, a `passive` bucket in the NOC rollup (never folded into `unknown`, which renders as "never probed"), and the `polaris_down_detection_assets{coverage}` gauge. `failureThreshold` stays on the settings tiers as a **dormant** column read only by the V3 seed that mirrors each install's pre-cutover thresholds forward (the `fastConfirmIntervalSec` precedent — dropping it would cost an irreversible migration for no gain); the cadence and probe timeout still come from that hierarchy, which is what business rule 30 is about.

### The way back up (2026-08-29)

The cutover above gave the automation the way DOWN and left the way back to fall out of the leaky bucket: `missedPolls` doubled as the recovery threshold, so three misses cost three answers. That is a reasonable default and it is not what the wizard's own reset step appears to promise. The reset asks "must stay cleared for N **polls**" — the operator who writes "down after 3 missed, reset after 5 received" is describing a device coming back, watches the Assets pill go green on the third answer, and reasonably reads the difference as a bug. The asset's intermittency strip is where this surfaced: it replays the state machine cell by cell, so it went green at three while the alert it was raised by sat firing for another five minutes.

So the reset sustain now reaches the state machine as well as the alert row. `DownWinner.recoverySustainSec` rides the same down-detection snapshot as the threshold — the SAME automation must answer both directions, or the two could resolve onto different rules — and `recoveryPollsFor` resolves it to polls. Since 2026-08-29 the reset can state that count OUTRIGHT (`reset.sustainPolls`, alongside `recoverySustainPolls` on the snapshot — see rule 19), and a stated count is used as-is: no cadence, no division, no asset read. A rule authored before counts were stored still carries seconds only, and those are converted back at the asset's own `intervalSeconds` at probe time rather than trusting the frozen arithmetic the wizard did at authoring time — which is what keeps "5 polls" meaning five polls after someone changes the interval. That division ROUNDS rather than ceils, so a cadence that does not divide evenly hands the operator their own number back instead of quietly adding one.

Four decisions bound it.

**The drain is a floor, never a ceiling.** A reset asking for fewer answers than the bucket owes cannot make recovery faster — business rule 30's bucket still wants one answer per miss — so `recoveryPollsFor` takes `max(threshold, polls)`. An automation with no auto reset, or one that resets immediately, gets exactly the pre-change behavior, which is every automation authored before this existed. **Superseded in part on 2026-09-01**: the clause that used to close this paragraph — "and a deep outage that already out-drained the count is untouched" — was true and was the defect. The bucket now LOCKS at `max(threshold, recoveryPolls)` on the verdict miss, so the drain no longer out-runs the reset on exactly the long outages the count mattered most for. `max(threshold, polls)` survives unchanged as the cap itself.

**It needed one bit of memory, and the counters could not fake it — until the cap removed the question (RETIRED 2026-09-01; what follows is why the column exists and why it is now dormant).** At `consecutiveFailures == 0` a success run of N is ambiguous: either a bucket that drained from N, or a healthy device that has simply answered N times. The confirmation hold must apply to the first and never to the second. Inferring it from `consecutiveSuccesses >= threshold` paints two amber cells into every ordinary blip on a healthy device; inferring it from the previous status loses the memory the moment a mid-run miss parks the asset in `warning`, letting a flapping device out of its run on one answer. Hence `Asset.awaitingRecoveryConfirm` (migration `20260829000000_recovery_confirmation`): armed on the transition into `down`, cleared on the transition into `up`, carried through everything in between — including across the probe-patch buffer's merge, where the preserve-on-absent rule has to be `??`/COALESCE rather than truthiness, because `false` is a real value that must land. It defaults false, which is right for existing rows: an asset mid-outage at upgrade time recovers on the drain the way it always did, and its next `down` arms it.

**The engine must not charge the wait twice.** `monitorStatus == down` stops being met the instant the asset reads `recovering`, so plain `!meets` would clear the alert on the FIRST answered packet and then the engine's own `sustainSec` would add five more minutes on top of the five polls the machine just served. `downRecoveryConsumesSustain` settles both halves: `engineSustainSec` returns 0 for such a rule, and `recoveredMeets` holds the alert through `down`, `recovering` AND `warning` (`DOWN_ALERT_HOLDING_STATES`) so it ends when the device actually reads `up`. Warning is in that set deliberately — a device that answered once and then missed again is further from recovered than one that is climbing, and letting it clear the alert would reward flapping.

**Only an `auto` reset counts.** `manual` and `timed` say nothing about how many probes must answer, and a `condition` tree is already the sole recovery authority while an alert fires (business rule 32a) — a poll count layered underneath would be a second clock that disagrees with it. `downRecoverySustainSec` returns null for all four.

Two consequences worth stating. `recovering` can now occur at `cf == 0`, a state unreachable before, so `runsHeavyCadences` admits it: the asset is answering every probe and is amber only because its automation asked for more confirmations, which is not a thing that should decide how fresh its charts are. And the asset strip's client-side replay tracks the same fact by OBSERVING a down within the window rather than by the stored bit it cannot see — a bar whose first cells predate the outage would otherwise have to guess.

### The cap serves the count, so the memory is gone (2026-09-01)

The design above holds the asset in `recovering` at `cf == 0` until a success run reaches the reset count, and needs `Asset.awaitingRecoveryConfirm` to know which devices owe one. Business rule 30's bucket ceiling makes the whole arrangement unnecessary: the level now LOCKS at `max(missedPolls, recoveryPolls)` on the verdict miss, so a device that went down is already carrying exactly the debt the operator asked for, and the ORDINARY drain serves it. Five answers to `up` on a "reset after 5 received" automation, from a bucket that jumped to 5 — no hold at zero, no stored bit, and the ambiguity that bit resolved (at `cf == 0`, is this a drained bucket or a healthy device's success run?) cannot arise, because the debt itself carries the answer.

It also fixes what the floor left broken. Under the old shape a deep outage out-drained the reset — seven misses cost seven answers and a 5-poll reset added nothing on top — so the number the operator wrote down stopped applying at exactly the outages that mattered most. Now it always applies, and a four-minute outage and a four-day one cost the same climb.

`owesRecoveryConfirmation` is deleted from `utils/monitorStatus.ts` and `recordProbeResult` no longer writes the column. `Asset.awaitingRecoveryConfirm` survives **dormant** — the `cooldownSec` and `failureThreshold` precedent, dropping it costing an irreversible migration for no gain — and `jobs/clampFailureBucket.ts` zeroes it once fleet-wide so a stale `true` can never be mistaken for live state by a later reader. `consecutiveSuccesses` is left maintained and charted but now decides nothing anywhere. The probe-patch buffer keeps its optional `awaitingRecoveryConfirm` plumbing, written by nobody.

One thing this does NOT change: the engine still must not charge the wait twice. `downRecoveryConsumesSustain` and `DOWN_ALERT_HOLDING_STATES` are untouched, and they are also what keeps rule 30's answered-probe-is-always-`recovering` change from clearing a down alert early — `recovering` is a holding state, so the alert still ends only at `up`.

### The automation also decides what colour Down is (2026-09-01)

Every surface painted `down` red. Red was never a property of the state, though — it is what `critical` looks like, and `critical` is simply the default severity of every down automation Polaris seeds. An operator who rates outages on a device class `warning` has said something about how those outages should read, and the product overrode it everywhere at once.

So `DownWinner.severity` rides the same down-detection snapshot as the threshold and the reset count — the SAME automation answers all three, for the same reason the two counts already share it — and reaches the browser on the `downDetection` block of the effective-settings and monitor-history payloads as a severity NAME rather than a colour, because the palette belongs to whichever client is drawing. Four surfaces read it: the Last-30-min strip, the desktop response-time chart, the phone's, and the chart rasterized into the alert email.

The palette is duplicated by necessity — `downSeverityHex` in `utils/severityStyle.ts` for the email, `DOWN_SEV_COLOR` in `public/js/chart-severity.js` for the browser, nothing crossing that boundary — and `tests/unit/downSeverityColor.test.ts` pins the two to each other, because one outage drawn two different colours depending on where you read it is the failure this whole vocabulary exists to prevent.

Three decisions bound it. It is deliberately **not** the alert-wide `severityHex`: that colours a whole alert — an email's severity bar, a Teams card — where nothing competes with it, while these land on a chart already spending amber on a below-threshold miss (`#ffc107`), blue on a recovering probe (`#0288d1`) and grey on a dependency-explained one (`#9aa0a6`), so each value is pulled deliberately deeper than the neighbour it sits beside. **`critical` keeps `#d32f2f`**, the red every surface already used, so a default install is pixel-identical, and an absent or unrecognized severity — passive devices and unresolved automations both — falls back to it rather than understating a verdict Polaris is still asserting. And the **Status pill does not move**: its text already names the state, so the colour there is redundant, and recolouring it would make the Down and Missed badges the same colour in a list column where an operator reads them as a set.

The `warning` case is the honest limit. Its down colour (`#f9a825`) and the below-threshold miss amber are two shades of one yellow — the price of honouring the operator's rating on a chart that already spends amber on the climb toward that same verdict. They stay separable by the tooltip, which names the state and the running count, and by the pill above the chart. Deepening it far enough to be unmistakable would stop being the yellow the operator asked for.

## Rule 37 — An automation only fires about a device Polaris is actually polling

Two facts had drifted apart: whether an automation *covers* a device (its scope matched) and whether Polaris *watches* that device (`monitored = true`). A scope is a device filter, so it deliberately selects on inventory attributes and says nothing about polling — and for the metric triggers that was harmless, because an unmonitored device produces no samples and therefore no readings. It was not harmless for the two trigger families that read something other than a sample.

**The incident shape.** `monitorStatus` is a stored column, and turning monitoring off does not clear it — `clampMonitoredState` resets the counters and leaves the last verdict standing, deliberately, so the assets table can show where a device was when polling stopped. The `asset_state` resolver reads that column straight off the scope row. So a device that was down when an operator shelved it kept its `monitorStatus = "down"`, kept matching a `monitorStatus == down` automation forever, and kept an alert firing about a device nobody had polled since. Nothing cleared it either: the vanished-state sweep only clears rows whose asset left the SCOPE, and the asset had not left the scope — it had left the fleet. The event and change tail had the mirror-image version: it fires on new `Event` rows and never looked at `monitored` at all, so a firmware change or a discovery failure on a decommissioned host raised an alert exactly as loudly as one on a production firewall.

**The decision is one gate, not a per-trigger-type judgement.** `assetCanTrigger(asset)` — `monitored` **and** not suppressed — is applied by every path: the threshold loop, the composite loop, the metric and state previews, and the event/change tail. It folds in business rule 16's maintenance/dependency suppression rather than sitting beside it, because the question an operator asks is singular ("will this alert on that box right now?") and answering it from two places is how the two halves drifted in the first place. The four lifecycle statuses that cannot carry monitoring at all — decommissioned / disabled / storage / quarantined — reach this gate through business rule 10 rather than being retested here; that is the whole point of clamping `monitored` at the DB layer instead of teaching every consumer the status list.

**Event and change triggers were the deliberate exception, and reversing that is the substance of this rule.** The prior reasoning was that those triggers fire on audit events rather than readings, so nothing about them requires a live poller — a discovery failure or an asset edit is real whether or not anyone is watching the device. That is true and still beside the point: an operator who turns monitoring off has said "stop telling me about this box", and honouring that for five trigger types and not two makes the setting mean nothing they can predict. The cost is accepted openly: an audit-worthy change to an unmonitored asset now produces an `Event` row (visible on the Events page, shipped by the syslog and SFTP archivers) and no alert.

**Two carve-outs inside the tail, both about not swallowing a real signal.** A **null** asset detail fires — the row is GONE, and the case that matters is `asset.deleted`, where refusing to alert because the asset can no longer be found would silence exactly the event worth hearing. **System-scoped** events (capacity, backups, updates, lockouts — the 12 seeded event automations are mostly these) carry no `assetId`, never reach the gate, and are unaffected.

**The monitored half is SQL, not a filter after the fact.** `scopeWhere(scope, monitoredOnly)` pushes `monitored: true` into the WHERE on every evaluation load, so the engine's per-tick read shrinks to the fleet it can actually judge instead of loading shelved inventory to discard it — which matters at 2000 assets on a 60-second tick. It is pushed in **after** the dimension count, so the gate can never make an otherwise-empty scope (`{}` = match nothing) look like it selected something. And because un-monitoring now takes a device out of the scope load, the existing vanished-state sweep **clears** its live alerts as `notification.out_of_scope` — the fix for the frozen alert falls out of the gate rather than needing its own sweep.

**The raw resolver survives, because three other surfaces ask a different question.** `loadScopeAssets` without the flag still exists for: the Step-2 device-list preview, which reports the unmonitored remainder as a separate count rather than hiding it (an operator has to be able to see that their filter covers 40 devices of which 12 will never alert); the dimension-value picker and mass pinning, which are about what devices *have*, not what they fire; and `Contact.assetCondition`, where ownership is an address-book fact — a contact still owns a device nobody polls, and the editor says so in as many words. Any new consumer has to answer which of those two questions it is asking before picking a form.

## Rule 38 — A device behind a dark parent is not accused, and it is not released on one packet

Dependency suppression already answered "don't alert about a switch whose gate is down." Two things it did not answer turned out to matter as much: **when** the suppression ends, and what the charts say about the hours it covered.

**Releasing on `recovering` un-did the whole point.** The evaluator's parent test was `monitorStatus !== "down"`, which makes `recovering` a healthy parent. But `recovering` is the state a device enters on its FIRST successful probe after an outage and stays in until it has passed the covering automation's success threshold — one answered packet, and a failure drops it straight back to `down`. So a gate that answered once released every switch and AP behind it, all of which were still failing their own probes, all of which immediately started their own down runs, and the single upstream outage re-alerted device by device as exactly the storm suppression exists to prevent. Worse on a flapping gate, which could do it repeatedly.

The fix is **hysteresis, and only on the two states where it means something.** Entering suppression is unchanged — a parent has to be confirmed `down`, because `warning`/`recovering` flapping must never drag a healthy subtree into Dep. Down. Leaving it additionally counts `recovering` as down, decided by the child's own persisted `dependencySuppressed` (`SuppressionAssetState.currentlySuppressed` selects the side of the asymmetry). Every other state stays "ok" in both directions on purpose: `unknown` (never probed), `passive` (rule 36 — no automation renders a verdict on it) and `warning` are not claims that the parent is unreachable, and gating release on them would strand a subtree in Dep. Down with nothing that could ever clear it. Note the release cascades one layer per pass rather than all at once, which is correct: a gate coming back does not mean the switch under it has, and the AP under THAT switch stays suppressed until its own parent is genuinely up.

**The charts were calling an explained gap an outage.** A suppressed asset is still probed — at half cadence, because it may answer over a redundant path or out-of-band management — and those probes fail. Every failure was written indistinguishable from a real one, so a device sat behind a dead gate for six hours and its charts drew the red dive that means *this device stopped answering and we don't know why*, in the one case where Polaris knew exactly why.

So the probe row carries the reason: `AssetMonitorSample.dependencyDown`, set by `recordProbeResult` from the asset row's own `dependencySuppressed` (never re-derived on the probe path — the reconciler owns that flag, and deciding it twice would give two answers), rolled up as `dependencyFailureCount`. `probeOutageService` classifies each window as an `OutageKind`, and every chart surface — desktop, phone, compare, alert email — draws `dependency` in grey.

Four decisions inside that:

- **Same shape, different colour.** The line still dives to the baseline, because nothing was measured; only the accusation is dropped. It is deliberately not a band — bands mean "the gap is explained *and* expected", which is maintenance-window vocabulary (rule 16, UI-GUIDE section 15). A dependency outage is explained but nobody scheduled it.
- **A run splits at a change of kind.** Misses that were unexplained when they happened are not retroactively excused by the parent going down later, and a tail that keeps failing after the parent recovers goes back to red — that tail is a real outage, and it is the most important thing on the chart.
- **A rollup bucket must qualify WHOLE.** Grey only when `dependencyFailureCount >= failureCount`; a bucket mixing explained and unexplained misses stays red, because part of that hour is still unaccounted for. A NULL count — a bucket rolled up before the column existed — reads as zero, i.e. red, which is the safe direction.
- **The reason is stored, not reconstructed.** No table keeps a history of when each asset was suppressed, and inferring it after the fact from parent status history would be a second, disagreeing answer to a question the probe path could simply record.

The grey is duplicated in four places by design (`_CHART_DEP_COLOR` in `public/js/assets.js`, read by `assets-compare.js`; `DEP_COLOR` in `public/js/mobile/charts.js`; `DEP_COLOR` in `src/utils/sparklineSvg.ts`), the same way the failure red already is. Change one, change all of them, or one outage renders two ways.

## Rule 39 — How a person wants to be reached is theirs, not the automation's — but an automation that only offers one way still reaches them

Polaris could always send an alert by email and by web push. What it could not do was ask the person on the other end which they wanted. Two things followed from that, and both of them were bad.

**Enrollment was a per-browser switch pretending to be a preference.** "Enable push" lived in the account menu and on the Automations page, and it enrolled *that browser*. So an operator who turned push on at their desk did not have push on their phone, had no way to find that out except by not being paged, and had to remember to do it again on every device — including after a reinstall, a new laptop, or clearing site data. "I turned push on" and "my phone buzzes" were different facts, and only one of them was visible.

So the switch is gone. What the operator answers now is **how they want to be alerted** — Email (the default), Push, or both — and the answer lives on `User.notificationPreference`, not in the browser. Every client reads it at boot and reconciles *its own* subscription to it: choosing Push on the laptop enrolls the phone the next time it is opened, and switching back to Email un-enrolls every device the same way. Enrollment stopped being a decision and became the consequence of one.

The one thing that boot-time reconcile will not do is **prompt**. `Notification.requestPermission()` needs live user activation on Safari and a page load has none, so a browser that has never been asked stays un-enrolled until the operator picks the preference *there* — which is why the choice is a menu item and a bottom sheet rather than a dialog with a Save button several awaits away from the click, and why the row says which of those two states this device is in. Where permission is already granted the subscribe is silent, which covers every browser that has ever enrolled.

The preference is **saved even when the browser refuses the prompt**. It is an account-wide answer and the operator's other devices may honour it, so the toast reports what happened *here* rather than the save quietly not happening. The one exception is **iOS outside standalone**, where choosing push saves nothing and routes to the install steps instead: Apple grants Web Push only to a home-screen app, so a preference this phone cannot honour, chosen on this phone, is a promise Polaris would be breaking on the spot. For the same reason the chooser disables the push options **only when the SERVER has no Web Push channel** — an unsupported or permission-denied browser may not withhold a choice that belongs to the account.

**An action can now be plural, which is what makes the preference expressible at all.** A notify action carries `channelIds` — several channels, one recipient list — because "page the on-call by email and by push" was two actions with two copies of the same recipients, and a preference could not be stated across them. `channelId` survives as the primary and the lossless single-channel mirror every legacy reader still names a channel through; `assertActionRefs` refuses a payload where the two disagree rather than repairing it, because picking one of two answers is how an alert quietly goes to the wrong destination. `actionsToTargets` expands one action to one `DeliveryTarget` per channel, so nothing below that line knows an action can be plural.

**And then the gate, which is the whole rule.** A notify action may opt into `respectUserPreference`: deliver to each recipient only through the channel their own preference accepts. But it is consulted **only when the action group actually offers both methods** — otherwise the preference would *delete* the alert instead of routing it. An email-only automation whose recipient prefers push would reach nobody, silently, and nothing anywhere reports a recipient who was filtered out.

The group is the `actions[]` list being executed — the rule's own actions, one severity band's, the reset list, or a single escalation tier's — which is exactly the unit the wizard grays the checkbox on. A **multi-channel action counts on its own**: one action carrying an SMTP channel and a Web Push channel offers both methods by itself, and that is the shape the checkbox was really added for. The test lives in `automationActionService.actionsCarryBothMethods` (server) and `hostOffersBothMethods` (wizard) — same question, same answer, so the checkbox is never enabled on a group the server would ignore it for. `expandDeliveries` defaults `enforceUserPreference` to false, so a caller that never opts in behaves exactly as it did before the feature even if a stored target carries the flag.

Four smaller decisions carry it:

- **Only accounts are filtered.** A typed address and an address-book contact have no Polaris account and therefore no preference; withholding their copy on a preference they never expressed would be inventing one for them. Same posture as the acknowledge-capability split in rule 25: unknown means deliver.
- **A preference routes an alert; it never deletes one.** `preferenceWithholds` keeps a recipient on the channel they did NOT pick whenever the one they did pick cannot reach them — a push-preferring account with no enrolled device still gets the email, an email-preferring account whose `User.email` is null still gets the push, and an account neither can reach is kept on both rather than dropped from both. Without it the two halves cancel: the filter removes them from one channel and the other has nowhere to send, so they are simply absent from the alert and nothing anywhere reports an omitted recipient. The device count is one `groupBy`, read only when a filter is actually about to drop someone and memoized per notification.
- **A push that dies for good is re-routed to email at SEND time.** The drain is the only place the second signal arrives: a push service answering 404/410 means that subscription is dead, so `enqueuePushFallbacks` queues an email instead. Three guards keep it from mailing people who were reached perfectly well — it is per RECIPIENT rather than per row (`pushStillInPlay`: an account with three enrolled browsers has three delivery rows and two may have succeeded, and `pending` means a retry may still land it), it uses the ACTION'S OWN email channel (stamped into the push row's `meta.fallback` at expansion time, so no alert is re-routed through an SMTP config nobody picked for it, and a push-only action still has nowhere to go), and it never sends twice (`alreadyEmailedOnChannel`, a SUBSTRING test because a composed send is one row whose target is the whole joined To list). The body is cloned from a sibling email row on the same channel so a custom composition carries over. Its real value is bounded and worth stating: because a 410 also PRUNES the subscription, every later alert takes the fire-time path above instead — so this rescues exactly one alert per dead endpoint.
- **Reachability is the only thing Polaris can honestly check.** A subscription EXISTS or it does not. Whether the phone is on, online, or looked at is not knowable: a 201 from a push service means it accepted the message for later delivery, not that it arrived. A genuinely dead endpoint surfaces later still, at SEND time, when it answers 404/410 and `deliverNotifications` prunes it — too late to re-route that alert. So the fallback is deliberately pre-send and subscription-shaped; anything promising “fall back when the phone didn’t buzz” would be a lie.
- **An unrecognized preference means email, never nobody.** `normalizeNotificationPreference` degrades anything it does not know to `"email"`, the method everyone has. A plain TEXT column holding a value this build has not heard of must not un-address an alert.
- **The broadcast toggles stayed push-only.** "Send to All Users" / "All User Regions" live in the builder's push block and read as *tell every device*. On a mixed action they now apply to the push half alone (gated on `transport === "web_push"` in `expandDeliveries`), because letting them widen the email half would mail the whole roster off a control that never said so. Save-time validation loosened in step: broadcast is refused only when an action carries **no** push channel at all, since the toggles are renderable the moment one is selected.
- **The preference is audited.** `user.notification_preference.changed` is written on every change, because "I never got paged" has to be answerable from the Events tab.

## Rule 40 — Two assets on one address is a conflict; one asset on a stale address is not

Polaris has always refused to let two reservations sit on one address — one active reservation per IP per subnet, backed by a unique index (rule 3). Inventory has no such constraint, and cannot have one: two Asset rows carrying the same `ipAddress` is exactly the state discovery has to be able to REPRESENT in order for anyone to be told about it. A unique index there would make the second write fail somewhere in a discovery phase, which is how a duplicate address becomes a log line nobody reads instead of a queue entry somebody acts on.

So nothing noticed. A duplicated address is one of the few faults that breaks every layer at once — routing is ambiguous, whichever device answers first owns the monitoring verdict for both, a quarantine push isolates whichever one the gate's ARP cache happens to hold — and the two devices involved usually look individually fine, which is what makes it hard to find by hand. The fix is a sweep (`detectDuplicateIpAssets`, every 10 minutes) that raises a third `entityType="asset"` Conflict flavour, `duplicate-ip`, alongside a `conflict.detected` Event — the same action string the ip-override flavour already stamps, so the baseline **IP conflict detected** automation alerts on it with no new wiring.

**A sweep, not a write-time hook.** An asset's IP is staged by something like seventeen projection write sites — every discovery phase, the agent push, the sighting-driven update, the operator form. Hooking them all would be seventeen chances to miss one, and a duplicate is not a property of the write that created it: it is a property of the FLEET at a moment. One grouped query answers it for every address at once, its CTE narrowing to duplicated addresses before returning a single row, so a 2000-asset fleet hands back the collisions rather than the fleet. A clean fleet issues zero writes.

**The hard part was not finding duplicates — it was not reporting the fake ones.** DHCP reuses addresses constantly, and an Asset keeps the last address a writer staged on it until another write moves it. So a laptop that left the building three weeks ago still records `10.1.1.50`, the printer that got the lease next records `10.1.1.50` too, and a naive `GROUP BY "ipAddress" HAVING count(*) > 1` reports it as a conflict — along with hundreds of others, on a fleet where `decommissionStaleAssets` deliberately waits 30 days before touching a quiet row. A queue like that is worse than no queue, because the real duplicate is in it somewhere.

A member therefore counts only while its **claim** on the address is current, and the two ways a claim stays current are deliberately different in kind:

- **Operator-owned claims never expire.** `ipOverride` equal to the recorded address, or `ipSource="manual"`, is a person saying *this device is at this address*. There is no cadence behind it to go stale, so nothing may time it out.
- **A discovered claim must have been re-asserted** within `CLAIM_FRESH_DAYS` (7). The timestamp read is the `(asset, ip)` row in `AssetIpHistory`, not the asset's own `lastSeen` — the `db.ts` extension bumps that history row on EVERY asset write staging `ipAddress`, including one that stages the value unchanged, so it tracks the discovery/agent cadence rather than change. Seven days is generous because that cadence is the integration's `pollInterval`, which operators routinely set to hours.

Preferring the per-address timestamp over the device's presence is the whole point, and it is worth being explicit about why: a device that is demonstrably up (`lastSeen` fresh, because a probe or a presence check reached it) but whose *recorded* address nobody has re-asserted in months has a stale RECORD, not a duplicate address. Falling back to `Asset.lastSeen` at all is only for rows with no history at all — one predating the extension, or one pruned — where the asset's presence is the best evidence available and reporting the pair for review beats being silently blind to it.

**And it takes equipment somebody addressed on purpose.** The freshness gate keeps stale records out of the queue, but it says nothing about whether a *live* duplicate is worth a human's attention — and on a DHCP fleet most live duplicates are two endpoints trading a pool address between them, which is not a fault, it is DHCP working. So a group only raises when at least one claimant is a type whose address was CHOSEN: `CONFLICT_ELIGIBLE_ASSET_TYPES` — a switch, an access point, a FortiGate, or a server. Those four are statically addressed or DHCP-reserved, so two of them on one address is always a fault; a workstation, printer or handset is handed whatever the pool has free.

**One qualifying member is enough, and the others still ride the card.** The alternative — considering only those four types and ignoring every other claim — reads simpler and hides the case that matters most: an endpoint that DHCP'd onto an access point's static address is an outage on the access point, and Polaris would have shown a single uncontested claim and said nothing. So the scan still loads every network-present claim on a qualifying address, the endpoint appears in `members[]` with its type visible, and the operator usually resolves it by giving the ENDPOINT a new address. Eligibility is tested on the CURRENT claims rather than on everything the scan returned, so a departed switch's leftover record cannot license a conflict between two live laptops.

Two consequences worth naming. The list is a **constant, not a Setting** — it is a claim about which equipment has deliberate addressing, not a per-install preference, and a settings surface for it would need an asset-type picker nothing else in the conflict path has; operator-added custom types therefore fall outside it by design, the same way every other `assetType`-branching consumer treats them. And **narrowing it needs no migration**: a pending conflict whose members stop qualifying is retired by the reconcile's own auto-close path on the next pass, which is also what happens when an operator retypes a device. `hypervisor` (an ESXi host, which an operator saying "servers" may well have meant — VMs are typed `server`, hosts are not) and `router` are the two deliberately-omitted candidates, left out until somebody decides they belong rather than added on an assumption.
**It takes two devices, not two rows.** The other false positive is one physical device recorded twice: two Asset rows, same MAC, same address. That is a duplicate RECORD, which `mergeDuplicateHostnameAssets` or an operator merge fixes, and calling it an address conflict would send the operator to renumber something that does not need renumbering. `distinctDeviceCount` collapses members sharing one non-null MAC into a single device; a null MAC proves nothing about sameness, so each of those counts as its own device.

That check only catches the duplicate records that agree on a MAC, though — and the ones that reach the queue are exactly the ones that do not: two rows for one device whose MACs differ (a wired and a wireless NIC), or where one side never learned a MAC at all. So the card has to be able to say *these are the same device* as well as *one of these has to move*, which is why the conflict has **two resolution verbs and no single "resolve" button**.

Four decisions about the row itself:

- **One pending conflict per ADDRESS, never per pair.** A three-way collision is one card carrying every claimant in `proposedAssetFields.members[]`. Per-pair rows would mean three cards for three devices and a resolution on one of them silently invalidating the other two.
- **The row's `assetId` is the lowest-id member.** A `Conflict` needs its FK, and the FK's cascade is what makes deleting one of the assets clean up the conflict — so the pick has to be STABLE across refreshes rather than following whichever member was sighted most recently.
- **Accept is refused, because there is nothing to adopt.** Every other conflict flavour has a proposed value; this one has two rows that are both, factually, what Polaris was told. Accepting would mark the conflict resolved while both devices still answer to the address. There are two verbs instead, one per cause.
- **Two devices → `POST /conflicts/:id/reassign-ip`.** A new address typed on ONE member, written with the asset form's own pin semantics — `ipAddress` + `ipOverride` + `ipSource="manual"` in a single update, so the `db.ts` override guard defers to it and discovery converging on the same address later releases the pin by itself (rule 22's ip-override machinery, reused rather than re-implemented). It **refuses an address another network-present asset already records**, since that moves the duplicate instead of resolving it, and it closes the conflict only when fewer than two current claims remain — a three-way collision stays open on the survivors and takes two reassignments, which is honest about the work left.
- **One device recorded twice → `POST /conflicts/:id/merge`.** The same route as the per-field asset merge with a different body (`{ survivorAssetId, absorbAssetIds }`), because to an operator it is the same verb. It absorbs the named members into the survivor through `assetMergeService.mergeAssets` — the engine the asset page's Merge modal and `acceptAssetConflict`'s ghost absorb already use, so sources, MACs, IP history, sightings, the agent enrolment, dependency edges and the monitoring OR-carry all behave exactly as they do there rather than a fourth time. Three decisions inside it: it accepts **no field winners** (blank-fill is what every automatic absorb uses, and per-field control already exists on the Sources tab, which the confirm text points at); the survivor is **silently dropped from its own target list** rather than attempting a self-merge, and every id must be a member of THIS conflict, so nothing can reach an asset the card never showed (`resolveMergeTargets`, pure and unit-tested); and `Conflict.assetId` is **re-pointed at the survivor before the first merge**, because deleting an absorbed asset CASCADES to conflicts pointing at it and would otherwise destroy this row mid-operation, taking the audit trail of how the duplicate was resolved with it. The card's confirm NAMES every record about to be deleted rather than counting them — the absorbed row's monitoring history is permanently lost, and that is not a thing to summarize.
- **Reject means dismiss, and it is the dedup marker.** Some duplicates are known and tolerated. A rejected row suppresses the re-raise for exactly that member set; a changed set — a third device joining, one leaving — is a different fact and raises again.

And a duplicate that resolves itself (a device decommissioned, a discovery write moving one row onto its real address) **closes itself** on the next pass, as `rejected` by `system:auto-resolved` — the auto-resolution convention `resolveStaleReservationConflicts` and `resolvePendingIpOverrideConflicts` already use. Nothing may leave a resolved collision sitting in the queue, because a queue that keeps entries after the problem is gone stops being read.

One limitation, stated rather than papered over: the Event is asset-scoped (`resourceType: "asset"`), so an automation firing on it obeys rule 37 — an unmonitored asset triggers nothing. A duplicate between two assets neither of which Polaris polls still lands in the Conflicts queue and its badge, but it will not page anyone. That is the same trade the rest of the alerting surface makes, and the queue is the backstop.

## Rule 41 — A subnet dies with its FortiGate; the chassis, not the name, says which gate that is

**The invariant.** A discovered `Subnet` records the SERIAL of the chassis serving it (`Subnet.fortigateSerial`), tri-state: NULL is unknown and constrains nothing, a value is the chassis that last served it. Each run compares it against the reporting device's whole cluster serial set (`utils/chassisIdentity.ts:classifyChassis`) — absent-stored LEARNS, unreadable-discovered is UNKNOWN and never "different", a member of the same HA cluster is the SAME gate, and anything else raises the `chassis-replaced` Conflict. And a retired subnet MOVES to `ArchivedSubnet` / `ArchivedReservation` rather than sitting in `subnets` as `deprecated`, because a retired row still occupies `@@unique([blockId, cidr])`.

### What went wrong

An operator replaced a FortiGate with a different model, keeping the IP addressing. The old gate was decommissioned and its subnets went `deprecated`. The new gate's subnets never appeared in IPAM — and never would have, on any future run.

Two independent defects, and it took both to make the state permanent.

**The CIDR was unrecordable.** Discovery's Phase 1 builds `subnetByCidr` from NON-deprecated rows only, so the new gate's `10.x.0.0/24` found no match and fell through to the create path. `createSubnetRowChecked`'s committed-state overlap re-read counts EVERY row in the block, deprecated included, so it threw 409 and the subnet landed in `skipped`. Invisible to the update path, blocking to the create path — every run, forever, with the tell being a self-overlap message no one reads:

    Skipped subnet 10.x.0.0/24: Subnet 10.x.0.0/24 overlaps with existing subnet 10.x.0.0/24

It was never only the network, either. `findSubnetForIp` also skips deprecated rows, so every DHCP lease, DHCP reservation, VIP and interface IP the new gate reported inside that space was dropped with it.

**Phase 2 was deprecating live subnets.** Phase 1 re-points a matched subnet's `fortigateDevice` in a batched DB update but never mirrored the change onto the in-memory row; Phase 2 decides staleness by filtering that same in-memory array against the roster. So a subnet Phase 1 had just re-pointed at a renamed or replaced gate still carried the OLD name in memory, wasn't in the roster, and was deprecated by Phase 2 **in the same run that had just re-pointed it** — after which defect one made the state permanent. A plain gate rename was enough to trigger it. Phase 2a, the stale-FIREWALL sweep, had long since learned this class of lesson (`haStandbyOfUnreadCluster` — "absence of evidence is not evidence of absence"); the subnet sweep never got the same care.

### Why serial, not name

Both defects trace to one ambiguity: `fortigateDevice` is a NAME, and a name cannot distinguish a rename from a replacement. Those need opposite handling — a rename should re-point silently, a replacement must be reported — and the code had no way to tell them apart, so it did the wrong thing for both.

The name-only model also left a THIRD case entirely silent, and it is the common one. An RMA or warranty swap normally reuses the device name. Then the CIDR matches, the name matches the roster, Phase 2 leaves it alone, and the new chassis **silently inherits every reservation row of the old one** — including rows marked `pushStatus: "synced"` whose `pushedScopeId` / `pushedEntryId` address a DHCP entry inside a scope on a box that no longer exists. Nothing looks wrong, which makes it worse than the failure that started this.

Serial is chassis identity and is never renamed. The stale-firewall sweep already matched firewalls by serial first and hostname second; subnets simply never got the same treatment.

### The four decisions

**(a) Tri-state, in both directions.** A NULL stored serial means unknown and LEARNS on first sight — which is why the migration deliberately backfills nothing: every pre-existing row converges on its own, and a backfill could only have guessed chassis identity from a name. Symmetrically, an unreadable serial THIS run is unknown and applies no constraint. That second half is load-bearing: mapping it to "different" would let one failed CMDB read declare every subnet on the fleet replaced. The same discipline `AssetDependencyParent.managedSwitchSerials` uses.

**(b) The comparison is against a SET, per device.** A cluster has several chassis and FMG's device record flips its top-level `sn` to whichever member is active, so comparing against a single stored value would report a replacement on every failover — the largest false-positive risk in the feature. The test is membership in the reporting device's own chassis set (its serial plus every `ha_slave[]` member). Per DEVICE and not fleet-wide, because an old chassis re-registered in FMG under a different device entry — a gate repurposed to another site — genuinely IS a replacement for this subnet, and a fleet-wide set would call it unchanged.

**(c) Raising is additive; nothing is destroyed on an automatic detection.** The old chassis's subnet and reservations are COPIED into the archive and the live rows are left exactly as they are. No release, no re-push, no delete. The worst a false positive can cost is one conflict card and one archive row. Raising also deliberately does NOT re-point the stored serial: while the conflict is pending, `Subnet.fortigateSerial` still names the chassis Polaris last agreed served the space, which keeps the detection derivable from the subnet row itself rather than dependent on the conflict row surviving. Accepting is what moves it. Dedup is keyed on the (old, new) serial PAIR rather than the subnet, so a rejected row suppresses exactly that transition while a box swapped a second time raises again.

**(d) An archive, not a status — and it locks by construction.** Freeing the CIDR is the first reason: moving the row out of `subnets` is the only thing that releases the unique index, and no partial index was needed once the row simply left. The second reason is that a retired reservation is then unreachable BY CONSTRUCTION. There are ~50 `prisma.reservation.*` write sites across a dozen files; a "locked" status would need a guard at each one and a promise that no future writer forgets. An archived row is not in `reservations` at all. Compare `assertNotDeviceOwned`, which has to sit at the route layer precisely because discovery still writes the VIP rows it protects — here nothing legitimately writes a retired subnet, so the stronger mechanism is available and is the one used.

Three consequences of that choice, each deliberate. The archive carries **no foreign keys** out to `ip_blocks` or `integrations`: `Subnet.block` is `onDelete: Cascade`, so an FK would let deleting a block erase the archive — the exact opposite of what it is for. Block and integration identity are denormalized instead, the `DirectoryContactSource.integrationId` reasoning. The device-side push **pointers are not copied**, only push state: `pushedScopeId` / `pushedEntryId` / `pushedToId` address an entry inside a scope on a chassis that no longer exists, and carrying them forward would let a future restore or unpush aim a delete at whatever now occupies those ids on a different box — a loaded gun in a table whose purpose is review. And it is **not a retention entity**; nothing prunes it, because subnets number in the thousands at most and the point is posterity.

Archiving is also deliberately exempt from rule 4's active-reservation deletion protection. That protection exists to stop accidental DESTRUCTION; this preserves everything it moves.

### Retiring the dead row is discovery's job, not an API call

The first cut of this rule shipped the archive as an operator action and left it there. That was wrong, and it showed up immediately: an install that had already had a gate replaced ran a discovery on the fixed build and got **the same skipped-subnet event as before**.

The reason is where the chassis comparison sits. It lives inside Phase 1's `if (existing)` branch, and `existing` comes from `subnetByCidr` — which excludes deprecated rows. For a subnet that was ALREADY deprecated, which is every subnet on an install whose gate was swapped before the feature existed, the comparison never ran at all: the lookup missed, the create path was reached, and the committed-state overlap check refused it on the dead row. `classifyDeprecatedSupersede` being correct did not matter, because nothing called it. The only remedy was `POST /subnets/:id/archive`, an endpoint with no button behind it.

So Phase 1's create path now consults a second index of the deprecated rows (`deprecatedByBlockCidr`, keyed exactly as `@@unique([blockId, cidr])` is) and retires one in place when a live gate re-reports its range.

**It only fires when a DIFFERENT gate is serving that space**, because two very different situations reach this point:

- the subnet died with its gate and another box now serves the range — retire the dead row so the new one can be recorded. This is the case the rule exists for.
- an operator deliberately deprecated a subnet its gate STILL serves, to stop allocating from it. Discovery re-reports it every cycle, and archiving there would silently undo that decision and hand the range back as active.

Serial decides it where both sides have one; the device NAME is the fallback for rows predating the serial column, which is exactly the population that needs this. When the name matches and there is no stored serial the two cases are genuinely indistinguishable, and the answer is to KEEP — a wrongly-kept row is a skipped subnet somebody can archive by hand, while a wrongly-archived one silently reactivates a range somebody retired on purpose.

The skip that remains now **names the fix** (`a deprecated network still holds this range — archive it to free the address space`) instead of the bare `Subnet X overlaps with existing subnet X`. That self-overlap message was true, useless, and the reason this went unnoticed for a whole release.

Matching is **exact-CIDR only**. A deprecated `/23` partially overlapping a new `/24` is a different judgement — it is not the same address space coming back — so it still falls through to `createSubnetRowChecked` and is reported as the genuine overlap it is.

Ordering matters and is load-bearing: the excluded-address check (business rule 42) runs BEFORE this, so a CIDR an operator has declared out of scope never reaches the archiving path.

### What rule 23 keeps

A decommissioned managed device still gives its address back. The release happens while the subnet is live, exactly as before — archiving is a later, separate act, and it snapshots whatever state the reservations are in at that moment. Rule 23 is unchanged.

### The diff

`GET /conflicts/:id/chassis-diff` compares the archived old chassis against the live subnet, per address: `only-old` / `only-new` / `differs` / `same`. It is computed ON READ rather than snapshotted into the conflict row, because discovery syncs subnets in Phase 1 and reservations in Phases 3–5 — a payload built at detection time would compare the old chassis against itself — and reading it live also means the card can never show a diff that has since gone stale.

### Migration: the explicit act that writes

Raising archives a copy and stops. Carrying chosen addresses forward onto the new chassis is `migrateArchivedReservations` (`POST /conflicts/:id/migrate-reservations`), and five decisions shape it.

**Only two source types are migratable.** Migration answers "the new box does not know about an assignment somebody MADE", which is exactly `manual` (an operator reserved it) and `dhcp_reservation` (a MAC→IP binding configured on the old gate). Everything else is refused with a reason of its own, and the reasons are not interchangeable: `vip` / `interface_ip` are **device-owned** (read-only in Polaris everywhere else, and the new gate's own config states them — carrying one forward would write Polaris's memory of a dead box over a live device's truth); `dhcp_lease` / `dns_resolved` are **observed**, not assigned (a lease is a sighting of a client that may not even be there, and turning one into a reservation would invent an assignment nobody made); and `fortiswitch` / `fortinap` / `fortimanager` / `fortigate` are **device-managed** infrastructure whose devices are still on the wire, so the new gate re-discovers them within a cycle and migrating at best does nothing and at worst fights rule 23's give-the-address-back lifecycle. Refused lines are still SHOWN on the card — hiding one would leave an operator wondering where an address they remember went.

**A colliding line is UPDATED, not inserted.** An `only-old` address is created; a `same` or `differs` address already has a live row, so the migration overwrites that row in place. This is what "overwrite from the old subnet to the new one" has to mean anyway, and it is also what `@@unique([subnetId, ipAddress, status])` requires — an insert would violate it.

**Every migrated row lands `manual` with `dhcpBinding: null`**, whatever the archived row was, and the two reasons agree. Only a `manual` row is pushable at all (`pushReservations` pushes manual rows, and discovery flips one to `dhcp_reservation` when it later sees it on the device), so landing as `dhcp_reservation` would produce a row claiming the gate serves an address the gate has never heard of. And with push disabled the claim is Polaris's alone, which is precisely what `manual` + `dhcpBinding: null` states under rule 23's split — sourceType is who owns it, dhcpBinding is how the gate hands it out, and no gate is handing this out.

**The push is QUEUED, never inline.** Where the integration's DHCP push is on, the row is written `pushStatus: "pending"` with `pushQueuedAt` and `retryQueuedReservationPushes` drains it. A freshly-installed gate is exactly the device most likely to be unreachable for a few minutes, and an operator's migrate must not fail on that. The old chassis's push POINTERS are never carried — they aren't even archived — so a migrated row starts with `pushedScopeId` / `pushedEntryId` / `pushedToId` null and earns its own.

**Migrating does not close the conflict.** An operator may migrate a few lines, look again, and migrate more, so the diff has to stay reachable; adopting the chassis is the separate act that closes it (`adopt: true` on the same call does both in one round trip). The route carries a CHAINED gate — `discoveryConflicts:write` AND `reservations:write`, the `/reassign-ip` precedent — because resolving a queue entry and creating reservations are separable grants and this needs both.

One Event per batch (`subnet.chassis.reservations_migrated`, the `subnet.bulk-allocated` convention) rather than one per row, but it names every address migrated and every one skipped, so the audit trail stays specific.

## Rule 42 — Some address space is not one network, and the way to say so is to exclude it

**The invariant.** A `SubnetExclusion` is a CIDR the operator has declared out of scope for the networks list. It is **global, not per block**; its `cidr` is its **identity**, normalized on write and **frozen after create** (the PUT takes `name` / `notes` only); it is **IPv4-only**; and it **covers itself and anything narrower, in that direction only**. Nothing may record excluded space and nothing may raise a conflict about it: `createSubnetRowChecked` — the one seam every subnet-creating path passes through — refuses it 409, the two allocators fold excluded ranges into their taken-space list so auto-allocate STEPS OVER them rather than failing on them, and discovery skips a covered scope WHOLE in Phase 1 (no create, no update, no chassis comparison) and exempts the row from the Phase 2 stale sweep. **Adding an exclusion destroys nothing** — networks already in the list that it covers are reported back (`matchCount` / `matches`) and left in place. Managed on IPAM → Networks → **Exclusions**, gated `subnets:read` to look and `subnets:fullwrite` to change.

### What went wrong

Polaris models a subnet as ONE row per CIDR — `@@unique([blockId, cidr])`, which is exactly right for address space an operator allocates and carves. But a large fleet has address space that is the *same at every site*: a management VLAN, an out-of-band range, the fixed subnet a vendor appliance ships with. Every site's FortiGate reports it as its own DHCP scope, so discovery arrives with the same CIDR from forty different gates.

Before rule 41 that was noise. The first site discovered created the row, every other site's copy matched by CIDR and fell into the update branch, and the row's `fortigateDevice` was re-stamped to whichever gate happened to be processed last — a subnet whose "Sources" column named an arbitrary site, and which therefore inherited an arbitrary site's `region:` tag through `mapRegionService`. Wrong, but quiet.

Rule 41 made it loud. The row now carries the serving chassis's SERIAL, and a serial that is neither the stored one nor a member of the reporting device's HA cluster is by definition a replacement. Forty sites means forty serials for one row, so:

- every discovery run reads `replaced` on the shared subnet — correctly, by the rule's own definition;
- each one archives a snapshot of the subnet plus its reservations (`snapshotSubnet`), so the archive fills with copies of a subnet nobody retired;
- each one raises a `chassis-replaced` Conflict, and because dedup is keyed on the (old, new) serial PAIR, a fleet cycling through forty gates raises a *different* pair each run — the dedup marker never matches, so the queue grows one card per run per site;
- and the card describes a chassis swap that never happened, which is the worst kind of alert: it is not a false positive in the mechanism, it is the mechanism working correctly on data that was never one subnet to begin with.

Rule 41 is not wrong. The premise it rests on — that a subnet row corresponds to one piece of address space served by one chassis — is simply not true of a subnet several sites serve identically, and no amount of chassis-identity logic can fix a row that should never have existed.

### Why an exclusion rather than a smarter conflict

Three alternatives were available and each is worse.

**Make the subnet key (blockId, cidr, gate).** This is the "model it properly" answer, and it is a schema change reaching every reservation, every push pointer, `findSubnetForIp`, the IP panel, utilization, region tags and rule 41 itself — to represent something the operator does not want represented at all. Nobody is asking to see forty copies of a management VLAN in the networks list. They are asking not to see it.

**Suppress the conflict when the CIDR looks shared.** Any heuristic here ("more than N gates report it") decides on Polaris' guess rather than the operator's statement, and it stays wrong for the case that matters: a genuinely shared /24 that TWO sites serve looks exactly like an RMA swap. The distinction is not in the data — it is in what the operator intends, so it has to be stated.

**Let the operator delete the row.** Deleting solves nothing, because the next discovery run recreates it. There was no way to say "and stay gone".

An exclusion is the operator's statement, and it is the smallest one that works: this CIDR is not one network, so do not try to record it.

### The decisions that carry it

**Global, not per block.** The entire reason a CIDR needs excluding is that several sites serve it; scoping the exclusion to one block would let the same CIDR be recorded through another block and reproduce the problem one level up.

**Containment is one-directional.** An exclusion covers itself and everything inside it, so excluding a /16 excludes the /24s within it — which is how an operator excludes a whole management range in one row. It deliberately does NOT cover a WIDER discovered CIDR: excluding one /24 must never silently swallow a /8 someone discovers, because that would remove far more address space from the list than the operator named, and it would do it invisibly. When several exclusions cover the same CIDR the MOST SPECIFIC one is reported, so the refusal names the row an operator would actually delete to let the subnet through.

**Excluded space is TAKEN space to an allocator, not a refusal.** `allocateNextSubnet`, `bulkAllocate` and `previewBulkAllocate` append the overlapping exclusions to the same list of taken CIDRs they already hand `findNextAvailableSubnet` / `packIntoAnchor`. A caller asking for "any free /24" gets the next one that is genuinely free; a 409 naming an exclusion would turn a policy into an obstacle the operator has to notice and route around by hand. The preview builds that list identically to the write, or it would show a plan the write then rejects — the same trap the two paths already share for sibling overlap.

**One enforcement seam for creation.** The check lives inside `createSubnetRowChecked` for exactly the reason the overlap re-read does: manual create, auto-allocate, bulk allocate and the discovery create all pass through it, so one check covers every path and a future path inherits it for free. Its `opts.exclusions` parameter exists so a caller that already loaded the set — discovery, once per run, in the same `Promise.all` as its other prologue reads — pays no round trip per created subnet. The scale reasoning is the usual one: at 100 assets nobody notices, at 2000 a per-row read inside a discovery phase is a phase that got slower for no reason.

**Discovery skips the entry WHOLE, and where that skip sits is the point.** It is placed ABOVE the existing-row branch, not just before the create, because the conflict this feature exists to prevent is raised by the UPDATE side. Skipping only creation would have left every site still re-stamping the shared row and still tripping the chassis check. Phase 2 exempts covered rows for a second-order reason: with Phase 1 no longer re-stamping them their `fortigateDevice` is frozen at whichever site claimed the row first, so the moment that ONE gate leaves the roster the stale sweep would deprecate a subnet the operator told discovery to leave alone — and `deprecated` is precisely the state rule 41 exists to keep subnets out of.

**Adding an exclusion never destroys anything.** A network already in the list that the exclusion covers is reported on the response (`matchCount`, plus up to twenty named `matches`) and left exactly where it is; the create Event says so too. An exclusion is a statement about what gets recorded from now on, not a delete. Retiring the row that is already there stays the operator's explicit `POST /subnets/:id/archive`, which is the verb that actually preserves its reservations — having a config write silently archive or delete address-space records as a side effect is how an operator loses data to a checkbox. The count is reported rather than hidden for the same reason the Network Discovery preview reports how many targets inventory already carries: "nothing happened" and "something happened that I did not tell you about" must not look alike.

**The CIDR is frozen; only the name moves.** Re-pointing an exclusion at different address space in place would un-exclude what the operator excluded and exclude something they never named, in one edit, with no trace beyond an audit line — so changing the range is a delete plus an add, two acts that each say what they do. The name is editable because a typo in a label is not a change in policy. The route schema carries no `cidr` at all, so this is a property of the API and not just of the dialog.

**IPv4 only, refused at the door.** The containment math is `netmask`-backed like everything in `utils/cidr.ts`, and the address space this exists for — site management VLANs published by FortiGate DHCP — is v4. Storing a v6 exclusion that could never match anything would look like it worked, which is worse than a 400 that says it is not supported.

### What it does not do

It does not hide an excluded CIDR from anything except the networks list and discovery's writers. An asset addressed inside excluded space is still an asset, `dns_resolved` reservations still cannot be created there (there is no subnet to hold them, which is the same answer as before), and `findSubnetForIp` simply finds nothing — leases, DHCP reservations, VIPs and interface IPs inside an excluded range are not recorded, which is the intended consequence of the range not being a network in Polaris.

It is also not a retention entity, not per-integration, and carries no FK to anything: an exclusion outlives the integration, block and gate that made it necessary.

## Rule 43 — A grant is only as narrow as the act it names

**The invariant.** Three permission levels were describing acts they did not match, and each is fixed in the same direction — the level a route asks for is the level the act deserves.

1. **Deploying the Polaris Agent is `assets=fullwrite`, not `write`.** Every verb that pushes, replaces or removes the agent on a host (`POST /assets/:id/agent/install|retry|reinstall|upgrade`, `DELETE /assets/:id/agent`, `POST /assets/bulk-agent-install`) requires the top level of the assets key. Turning an integration class block's **`agentDeploy.enabled` ON is the same grant, CHAINED** onto `integrations=write` (`assertAgentDeployGrant`) — turning it OFF, and any save that leaves it unchanged, needs nothing extra. Reads (`GET /:id/agent`, `GET /agent-install-scripts`) stay at `read`.
2. **`assetsProbe` is a read-only key.** Its ladder is `none | read` (`levels` on `FunctionKeyDef`), and probe-now / SNMP walk / DNS lookup are gated at `read`. The one thing on that key that actually WROTE — the dependency-test outage simulation — moved to **`assetMonitorSettings=fullwrite`**.
3. **`credentials` carries the ownership dimension.** `write` = create, plus edit / delete / **test-with** only the rows you created; `fullwrite` = any row. `Credential.createdBy` is stamped once at create and no update path rewrites it; `null` is UNOWNED (every row predating the column, deliberately not backfilled) and therefore fullwrite-only.

### What went wrong

**Deploying the agent was an inventory edit.** `assets=write` is the level that lets an operator fix a hostname, retype a serial, change an asset's type. It was also the level that let them run an installer on someone else's machine over a stored SSH or WinRM credential and leave a service behind — and, through an integration checkbox, do that unattended to every newly-discovered device of a class, on every discovery cycle. Those are not the same act, and the built-in roles show why the difference matters: `assetsadmin` exists to manage inventory and holds `assets=write`, so fleet deployment came free with the inventory job. `networkadmin` holds `assets=read` and could not deploy to one device — but holds `integrations=write`, which reached the auto-deploy toggle, so the narrow grant was bypassable through a route that never mentions assets at all. That is why the toggle is chained rather than merely documented: a capability with two doors has to be gated at both.

Only the ON transition is gated, and the asymmetry is deliberate. A role that inherits an integration with auto-deploy already enabled must still be able to turn it off; refusing the save in both directions would leave the more dangerous state as the only reachable one.

**The probe key had two levels nothing could ever ask for.** `assetsProbe` was gated at `write` everywhere it appeared, so `read` granted exactly nothing — a role set to Read-Only on Asset Probes could not probe — and no route asked for `fullwrite` at all. Two of the four radio buttons in the role matrix were decoration an admin could nonetheless click, and a third was the real switch under the wrong label. The honest shape is `none | read`, because a probe reads a device and changes nothing in Polaris, which is what the key's own description always claimed.

Levels are now declared per key (`levels` on `FunctionKeyDef`) and enforced three ways so the shape cannot drift: `normalizePermissions` clamps a stored or incoming value DOWN into the ladder (never up — a stored `fullwrite` on a read-only key means "as much as possible", so rounding up would be a silent grant while resolving it to `none` would be a silent revocation), `permissionOf` clamps on read so a session snapshot stamped before a ladder narrowed still resolves correctly, and the `requirePermission` factory **throws at module load** if a route asks for a level its key cannot hold. That last one matters more than it looks: such a route is permanently unreachable — nothing can grant the level — and it would present as an unexplainable 403 rather than a broken build.

The migration folds every stored matrix at or above `read` down to `read`, so no role loses the ability to probe. The one capability that would otherwise have been lost is the one that never belonged there: **dependency-test writes.** It stamps `Asset.dependencyTestUntil` and can briefly mask a real outage on every monitored child of its target, and its own code comment read "strictly admin-only — assets-admin and network-admin do NOT have access." The gate said `assetsProbe=write`, which `networkadmin`, `assetsadmin` and the plain `user` role all held; the comment had been wrong about the code for as long as both existed. Making the key read-only removed the last level that could express "admin" there, so the simulation moved to `assetMonitorSettings=fullwrite` — admin-only in every built-in seed, and the right neighbourhood for a control that changes how monitoring reads.

**A credential was a shared secret with no owner.** The store held one flat list: any `credentials=write` role could rename, re-point or delete a credential another operator created — including the SSH key half the fleet's agents were installed with. The dimension applied is the one `subnets`, `reservations` and `contacts` already carry, implemented with the same three pieces (`requireOwnership` on the route, `assertOwnership` once the row is loaded, `createdBy` stamped on create) rather than a new mechanism.

Two decisions inside it are not obvious. **`POST /credentials/test` is ownership-scoped when it names a stored `id`**, because that path merges the row's REAL secrets into the probe (`mergeConfigPreservingSecrets`) so an operator can retest without retyping a password. Left open, it would let a write-level caller aim a peer's credential at any host in inventory — a read-shaped route that lends out a secret. Testing an unsaved form (no `id`) stays open at `write`, since the secret in that body is one the caller typed. And **an unowned row is fullwrite-only.** `createdBy` is not backfilled, in either direction: inventing an owner for the credentials an install already had would hand a write-level operator every secret in the store, and the honest reading of a row nobody claims is that only a fleet-wide grant should touch it. The LIST stays readable at `read` throughout — the gate is on writes, not on knowing a credential exists, because the Asset Monitoring tab's picker needs the names.

### What it does not do

It does not create a function key. Agent deployment rides the level above `assets=write` rather than a key of its own, which keeps the matrix from growing a row for every dangerous verb — but it does mean an operator granted `assets=fullwrite` for any other reason can deploy. If that separation is ever wanted, a key is the next step, and the client-side gate (`canDeployAgent` / `data-deploy-agent`) is already the single place to repoint.

It does not retro-scope credentials. Nothing is reassigned, nothing is deleted, and an admin who wants a shared credential to stay shared changes nothing: every built-in role sits at `credentials=read`, so the dimension only starts mattering the moment someone is granted `write`.

And it does not change what a probe can reach. `assetsProbe=read` dials exactly what `assetsProbe=write` dialled — the narrowing is about which cells the matrix offers and which level the routes name, not about what the act does.
