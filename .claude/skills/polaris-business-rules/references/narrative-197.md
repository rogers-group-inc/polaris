# Business rule 197 — full narrative

<a id="rule-197"></a>

## Rule 197 — The in-app updater's migrations never stall live writes: fail fast on a lock, retry only a migration that runs as one transaction, cancel the session on timeout

**The incident (2026-11-23, prod).** The update carrying rule 196 failed at "Run migrations" after the 300 s limit, and during it several agent-polled devices went Down and came back Up. The only pending migration, `20261123120000_ipsec_template_totals`, created a table and added a foreign key to `assets`. `ADD CONSTRAINT … FOREIGN KEY` takes SHARE ROW EXCLUSIVE on the REFERENCED table, which conflicts with the ROW EXCLUSIVE lock every INSERT and UPDATE takes. A transaction that had written to `assets` stayed open, so the ALTER queued behind it. Postgres then queued every later writer behind the ALTER (head-of-line blocking): agent check-ins and the probe patch buffer stopped landing, and devices missed polls. The exec timeout killed the Prisma CLI, but its native `schema-engine` child kept running. Its backend kept waiting, because a backend blocked on a lock does not notice its client has gone. The migration completed minutes later, after the update had already reported failure; the services were never restarted onto the new build. Reproduced locally on TimescaleDB pg17 the same day.

**What the guard does.** `services/migrationGuardService.ts → runGuardedMigrateDeploy` replaces the bare `execAsync("… migrate deploy")` in `updateService.ts → applyUpdate`:

1. **Fail fast.** The migrate child gets its own `DATABASE_URL`: the direct URL (`utils/dbConnections.ts → getDirectDatabaseUrl`, so PgBouncer is bypassed as the docs always required), plus `options=-c lock_timeout=10000` (merged with any options the operator set) and `application_name=polaris-migrate-update` (`guardedMigrateUrl`). A statement that cannot get its lock in 10 s is cancelled (SQLSTATE 55P03), so writers stall for at most that long per attempt instead of for as long as the blocker lives.
2. **Retry only what is provably clean.** Prisma 7 runs a migration's statements one at a time with no transaction around them. In the measured case, the `CREATE TABLE` before the blocked FK stayed committed, so a retry fails on "already exists" and the operator must reconcile by hand. A migration that starts `BEGIN;` and ends `COMMIT;` (`isTransactionWrapped`) is all-or-nothing. After any failure of one, the guard runs `migrate resolve --rolled-back <name>`, so the database is never left in P3009. If the failure was a lock wait, it backs off (15 / 30 / 45 / 60 s, the last repeating) and tries again until the step's 5-minute deadline. An earlier run's failed wrapped migration (P3009 on the first attempt) is resolved and re-applied at once, so re-running a failed update is the operator's whole recovery.
3. **Recognise the lock wait without Prisma's help.** For a wrapped migration Prisma loses the real error: it records the failure on the aborted connection and prints only "current transaction is aborted". So while each attempt runs, a sampler on its own direct `pg.Client` reads `pg_stat_activity` once a second for our application_name waiting on a `Lock`, and `pg_blocking_pids` for who holds it. A wait it saw makes the failure a lock failure. The holder (application_name, pid, state, transaction age, last statement) goes on the step card, in the success summary and in the failed Event, which answers "what was holding it" that the 2026-11-23 forensics could not.
4. **Clean up on timeout.** When the exec timeout fires, the guard terminates every backend carrying our application_name, so nothing keeps running against the schema after the update has given up. The next run's P3009 path picks up a wrapped migration's failed row.

**The convention that makes (2) work.** Every migration from 2026-11-24 on starts with `BEGIN;` and ends with `COMMIT;`. `tests/unit/migrationsRunAsOneTransaction.test.ts` fails on any that does not, unless it carries a `-- polaris:no-transaction: <reason>` line (CREATE INDEX CONCURRENTLY, a TimescaleDB call that commits internally). Older migrations are applied on every install and are never edited, because that would change their checksum. A non-wrapped migration that hits the lock timeout is not retried: the step fails at once, names the migration, and says statements before the blocked one may be applied.

**Where it does NOT apply.** The boot-time `polaris-migrate` oneshot, `docker-entrypoint.sh`, the setup scripts and `deploy/update-linux.sh` (which stops the unit first) run migrations with the app stopped. Nothing is waiting on them, and a lock timeout there would only keep the app from starting.

**The cost of the convention.** When a wrapped migration has a genuine SQL error, Prisma's output says only "current transaction is aborted". The statement's own error is in PostgreSQL's log, and the guard's failure note says so. In development the error shows in the container log (`podman logs`).

**Scale.** Independent of fleet size: one migrate child, one probe connection and one `pg_stat_activity` query a second while the step runs.

**Rejected.**
- *A pre-flight that waits for no long transactions.* The prod holder's identity is still unknown; a pathological holder would wait out the whole step. The lock timeout bounds the harm whoever holds the lock.
- *Apply migrations ourselves inside a transaction and record them in `_prisma_migrations`.* It reimplements Prisma's runner and checksum, and breaks on the statements that cannot run in a transaction block.
- *A lock_timeout on the boot-time migrate.* With the app stopped there is nothing to protect, and failing would stop it from starting.
- *Killing only the CLI.* That is what happened on prod: the engine child and its backend outlived it.

Pinned by `tests/unit/migrationGuardService.test.ts` (URL, parsing, every retry and give-up branch, the sampler with fake timers, the timeout terminate), `tests/unit/updatePipeline.test.ts` ("migrate step through the migration guard") and `tests/unit/migrationsRunAsOneTransaction.test.ts`. Verified end to end against TimescaleDB pg17 on 2026-11-24: with a session holding ROW EXCLUSIVE on `assets` for 25 s, a wrapped FK migration failed attempt 1 in 3 s, named the holder, was marked rolled back, and was applied on attempt 2.
