# Business rules 30–45 — the invariants

Each rule as CLAUDE.md stated it: the invariant plus a pointer into the narrative file (`narrative-25-35.md` / `narrative-36-43.md`), which records the incident or constraint that forced it. Rule numbers are a stable citation key — never renumber; retire a rule in place and give a new one the next free number.

30. **Confirmation is the configured cadence's job; ICMP only fills in the loss ratio** — `monitorStatus` reaches `down` when N missed polls are OUTSTANDING against the operator's configured transport at their configured `intervalSeconds`. **The counter is a LEAKY BUCKET WITH A CEILING, not a run length and not an unbounded debt**: a miss adds one to `consecutiveFailures`, an answered poll takes one back (floored at 0), and the level **LOCKS at `bucketCapFor(N, recoveryPolls)`** — the larger of the missed-poll count and the covering automation's reset count — the moment a miss carries it to N. The whole machine is two pure functions in `utils/monitorStatus.ts`, `nextFailureBucket` + `monitorStatusFor`, which the probe path CALLS rather than reimplements. The verdict: `cf == 0` is `up`, an **ANSWERED probe is `recovering` whatever the level**, and a MISS is `down` at or above N and `warning` below it — the level decides what a MISS means, the outcome decides everything else. So time-to-down is `N × intervalSeconds` for a device that stops answering and longer for one that flaps; **recovery costs exactly the cap, however long the outage ran**; and a miss anywhere in the climb re-locks the bucket, so a flapping device cannot walk itself out of an outage. **The cap and the always-recovering answered branch both landed 2026-09-01, and both were bugs.** Unbounded, a device dark overnight at a 60 s cadence reached `cf ≈ 480` and then owed 480 answered polls — eight hours — before it could read `up`, with its down alert repeating and escalating throughout, because `DOWN_ALERT_HOLDING_STATES` holds that alert until `up`. And with the answered branch BELOW the threshold test, a probe that answered while the bucket was still at or above N read `down` — which the response-time chart has no way to paint on an `ok` point, so it fell through to the plain series green and an outage drew red → GREEN → blue → green, reading as two recoveries. One lucky packet still cannot clear the alert: `recovering` is a holding state. `consecutiveSuccesses` is still maintained and still charted but **decides nothing** — the bucket's own level is the whole of the verdict AND of the recovery arithmetic, which is why `owesRecoveryConfirmation` is gone and `Asset.awaitingRecoveryConfirm` is dormant (business rule 36). Pre-ceiling rows self-heal on their next probe of either outcome (`nextFailureBucket` clamps before it moves the level) and are swept once at boot by `jobs/clampFailureBucket.ts`. **N is the covering automation's `missedPolls` (default 3), not a Monitor Settings value** — see business rule 36; `failureThreshold` on the settings tiers is dormant. **Nor is the COLOUR fixed**: `down` is drawn in that automation's own severity (`downSeverityHex` / `PolarisChartSeverity.downColorOf`), so red is what `critical` looks like rather than what Down means. Down detection was the only poll-counted decision until 2026-08-29, when every other trigger's hold and reset became counts too (rule 19) — this one still stands apart in WHERE it is counted: at the probe, which is the poll, rather than in the rules engine. The CADENCE half is unchanged: it still comes from the monitor-settings hierarchy, and the figure the monitor-settings card reports is the figure you get. `resolveProbeIntervalSec` applies **exactly one clamp**: dependency suppression (parent dark ⇒ 2× interval). **A probe can also decline to be a reading**: `ProbeResult.skipped` writes no sample and moves neither counter — it bumps `lastMonitorAt` alone, so the cadence keeps its spacing. Two sources: the vCenter probe when vCenter itself is unreachable, and **`responseTimePolling === "disabled"`**, which is the operator saying don't poll. The second was a *failure* until 2026-08-28: every other stream's publisher checked its resolved method before queueing and the probe's did not, so `disabled` reached `probeAsset`'s dispatch, fell past every branch to the unknown-method error, and was recorded as a missed poll — switching Response Time off drove the asset to `down`. Both publishers (`computeDueWork` + `jobs/monitorAssets`, the lockstep pair) now gate on the shared `responseTimeProbeShouldQueue`, and `probeAsset` returns `skipped` as the backstop for `/probe-now` and for a `disabled` sitting in a JSON tier no publisher gate can see. A skip is not a miss, so N consecutive misses still means N times the transport actually answered nothing about a device it could reach. **Nor is a re-queued job a second reading** (2026-09-10). The stately probe queue lets one job queue behind an ACTIVE job with the same key, and a batched ICMP chunk (or a probe to a dark host) outlives the 5 s publisher tick. The same poll therefore ran twice, seconds apart: two samples per cycle, and two misses toward N. Jobs now carry the resolved interval and the worker re-runs the due check at pickup (`probeStillDue`); a duplicate records nothing, not even `lastMonitorAt`. The ICMP loss sweep **never calls `recordProbeResult`** (ICMP does not authenticate the device it reaches), so it informs the loss ratio and can never move `monitorStatus`. It replaced the per-asset sampler on 2026-09-01: that one ran only while an asset looked unhealthy, which was itself a sampling bias (rule 29d) and is why it shipped disabled; the sweep is uniform — every eligible asset, every cycle, `down` and dependency-suppressed included — and ships enabled, batched through `utils/burstPing.ts` so a 2000-asset fleet costs four process spawns rather than two thousand. `probeKind` splits the readers: only `probeLossQuery` and the alert-email loss chart read all kinds — every response-time reader, and every rollup, filters to primary. → [narrative-25-35.md#rule-30](narrative-25-35.md#rule-30)

31. **The login page is the way back in, so restricting it is opt-in and must refuse to lock you out** — `loginAccessConfig` (default **off**) restricts local login by source IP via `utils/ipScope.ts`. It gates **both halves or neither** — `/login.html` AND `POST /auth/login` + `/auth/login/totp` — because the form is a plain POST to a JSON API. The page is **dropped** (socket destroyed, stealth posture); the API answers the **same generic 401** a wrong password gets, and writes `auth.login.blocked_source`. **SSO is never gated** (that's what makes this survivable); **LDAP is**, sharing the login route. It **fails open** on a settings read error, and the PUT refuses a scope excluding the caller's own `req.ip`. Only as true as `req.ip` — the GET returns `callerIp` for exactly that reason. → [narrative-25-35.md#rule-31](narrative-25-35.md#rule-31)

32. **A reset condition answers "what has to become true again", so it starts as the trigger inverted — and it resolves where the alert lives** — the custom-condition mode is offered on every trigger with a continuous condition (`TRIGGER_TYPES_WITH_RESET_CONDITIONS`; `event`/`change` are refused), pre-seeded with the trigger inverted (`invertedLeaf`, and `invertedTree` applying De Morgan so the result stays and/or-only). Four decisions carry it: (a) while firing, **the tree is the sole recovery authority** — evaluated in its own post-loop pass that re-reads firing rows from the DB; (b) resolution is **dimension-first with a per-asset fallback**, so a per-port alert clears independently while a device-wide leaf clears them together; (c) **kind coherence is enforced** on single triggers too; (d) reset leaves **inherit the trigger's measurement window** and have no window control of their own; (e) the two triggers a CONDITION is refused on get the **counterpart Event** instead (`TRIGGER_TYPES_WITH_RESET_EVENT`, the complement set) — `agent.disconnected` clears on `agent.connected`, scoped to the SAME subject the alert is about and prefilled from the server-published `RESET_EVENT_SUGGESTIONS` map, so an event automation is no longer stuck clearing itself on a timer whether or not anything recovered. And **`cooldownSec` was RETIRED from the builder** (2026-08) — it decided how often a NEW alert may fire, and had moved to the Actions step for that reason, but "Repeat this notification" answers the question operators were actually reaching for it to answer. The column and the engine's two checks survive, **dormant**, the `failureThreshold` precedent (business rule 36): the `clearNotificationCooldowns` one-shot nulls it fleet-wide (auditing each rule's old value FIRST, since the update destroys it), and the wizard writes null on every save, so a value an API caller re-sets cannot outlive the next edit in the builder. Removing the control without clearing the data would have left a rule silenced by a number no Polaris surface could show or edit. → [narrative-25-35.md#rule-32](narrative-25-35.md#rule-32)

33. **A device that answers is not a device that works — and the check that proves it belongs to the VENDOR, not to a login** — the HTTP check is a **manufacturer custom widget** (`ManufacturerCustomWidget.widgetType="http"`), not a polling method (retired 2026-08): a check varies by vendor AND model while a login varies by vendor, so sharing one row meant duplicating passwords. Decisions: the **body match is load-bearing** (a 200 whose body doesn't match FAILS; no lax toggle); **status is judged before content**; **redirects are never followed**; the body is **capped at 64 KB**; the credential is **authentication only, with no "none" mode**; **`authMode` is stated, not guessed** (Digest is a handshake — fire bare, read the challenge, re-fire **exactly once**); it writes `AssetStateSample` 0/1 **pass or fail** plus a success-only RTT gauge and **never moves `monitorStatus`**; and **`netGuard` deliberately does not apply**, the target being the monitored asset's own private address. → [narrative-25-35.md#rule-33](narrative-25-35.md#rule-33)

34. **An active scan finds things; a separate grant adds them** — a **Discovery** (`NetworkScan`) sweeps addresses the operator names, making it the only Polaris feature that touches hosts it has no prior relationship with, so the posture matters more than the mechanism. Seven decisions carry it: **scanning and adopting are separate grants** (`networkScan` authors and runs, `assets:write` chains on adopt, and the wizard RENDERS the missing grant rather than discovering it at the POST); it is **opt-in and IDS-visible**, with no scheduler and no shipped default range; **credential order is the try order** and the first method that answers wins; **adoption is new-addresses-only**, so a re-run enriches nothing and "nothing new" stays distinguishable from "nothing there"; it is deliberately **neither an 8th integration type nor a `DiscoveryRun` row**; and there is deliberately **no `network-scan` AssetSource kind**; and a Discovery is **private or shared**, where visibility decides who may see and RUN one while ownership decides who may edit it (`networkScan:fullwrite` reaching anyone's), an invisible row answering 404 rather than 403, `name` unique per owner, existing rows migrated public and new ones defaulting private, and the export carrying no visibility at all. → [narrative-25-35.md#rule-34](narrative-25-35.md#rule-34)

35. **The GAL is a mirror, not a source of truth — and Polaris only ever deletes what it wrote** — directory sync is opt-in per integration (`config.enableDirectorySync`, default off, deliberately separate from `enableDirectorySearch`, which still persists nothing) and runs as a post-sync pass of the owning integration's discovery run, never as its own scheduler job. Five invariants bound it: (a) **provenance decides deletion** — `DirectoryContactSource` records every (integration, directory object) the sync created, and a `Contact` dies only when its LAST provenance row goes; a hand-added row has none and is never touched, which is also why adoption drops provenance; (b) **a Polaris `User` or a manual `Contact` on an address wins** — the sync never creates over either, and an account created later retires the synced row on the next run; (c) **an empty or catastrophically-shrunken read never wipes** — zero entries, or a delete set over the guard, skips the deletion half and warns, because a revoked grant must not empty the address book; (d) **synced entries are gated on `automationManagement`, not `contacts:read`** — and so is the live GAL fan-out, since gating one and not the other leaves the roster reachable a query at a time; (e) **no directory PII reaches `Event.details` or the logs** — the run Event carries counts only, because Events are readable by anyone with events access and are shipped off-host by the syslog and SFTP archivers. → [narrative-25-35.md#rule-35](narrative-25-35.md#rule-35)

36. **The automation decides what "down" means; a device no automation covers is never judged** — a `monitorStatus == down` automation carries a **`missedPolls`** count, and that count IS the definition of down for every device it covers (`downDetectionService.resolveDownThreshold`, called once per probe); precedence is rule 18's existing ladder — same-rank ties resolve to the **smaller count**, then older `createdAt`, then lower `id`. **A device covered by NO down automation reads `passive`**, the sixth `monitorStatus` value: still polled, still sampled, still charted — Polaris just renders no verdict. The counters keep advancing while passive; heavy cadences run for a passive asset whose last probe succeeded (`runsHeavyCadences`); entering/leaving passive is a **configuration edge** (`isConfigStatusEdge` — no `monitor.status_changed` Event, no dependency propagation); anything testing `!== "up"` as a proxy for "unreachable" must exempt it. A zero-rule fleet stamps a one-shot `monitor.down_detection_absent` warning Event. `failureThreshold` stays on the settings tiers as a dormant column read only by the V3 seed. **The same automation owns the way back UP** (2026-08-29): its reset hold — collected by the wizard in POLLS — holds the asset in `recovering` until that many probes have ANSWERED (`recoveryPollsFor`, which reads the STATED count `reset.sustainPolls` when there is one and falls back to dividing the `sustainSec` mirror by the asset's own cadence for a rule authored before counts were stored), so "down after 3 missed, reset after 5 received" describes the pill and not just the alert. **Since 2026-09-01 the DRAIN itself serves that count**: the bucket locks at `max(missedPolls, recoveryPolls)` on the verdict miss, so an outage owes exactly the operator's number of answers and no more — a four-minute outage and a four-day one cost the same climb. It was a FLOOR before, which meant a deep outage out-drained the reset and the number the operator wrote down stopped applying at exactly the outages it mattered most for. Two consequences: **`Asset.awaitingRecoveryConfirm` and `owesRecoveryConfirmation` are RETIRED** — the ambiguity that stored bit resolved (at `cf == 0`, a success run of N could be a drained bucket or a healthy device) cannot arise when the bucket carries the whole debt, so the column is dormant on the `cooldownSec` precedent and zeroed once by `jobs/clampFailureBucket.ts` — and the ENGINE must not charge the wait twice — `downRecoveryConsumesSustain` zeroes the engine-side sustain and makes `recoveredMeets` hold the alert through `down`/`recovering`/`warning` so it ends when the device reads `up` rather than on its first answered packet. Only `mode: "auto"` counts; a `condition` reset is its own recovery authority (rule 32a) and layering a poll count under it would be two clocks. **The automation also decides what colour Down is** (2026-09-01): `down` is painted in the covering automation's own `severity` on every surface — the Last-30-min strip, the desktop and phone response-time charts, and the chart rasterized into the alert email — through one palette duplicated by necessity in `downSeverityHex` (`utils/severityStyle.ts`, for the email) and `DOWN_SEV_COLOR` (`public/js/chart-severity.js`, for the browser), pinned to each other by `tests/unit/downSeverityColor.test.ts`. Red is what `critical` looks like, and critical is merely the default severity of a seeded down automation; an operator who rates an outage on a device class `warning` has said something about how it should read. `critical` keeps `#d32f2f` so a default install is unchanged, and an absent or unrecognized severity — passive devices and unresolved automations both — falls back to it rather than understating a verdict Polaris is still asserting. The palette is deliberately NOT `severityHex` (which colours a whole alert, where nothing competes): these land on charts already spending amber on a below-threshold miss, blue on a recovering probe and grey on a dependency-explained one, so each value is pulled deeper than the neighbour it sits beside. `warning` vs the miss amber is the closest pair and is a real limit rather than a bug — a warning-severity outage and the misses that built it are two shades of one yellow, separated by the tooltip and by the pill, which names the state outright. The **Status pill deliberately does NOT move**: its text already names the state, and recolouring it would make the Down and Missed badges the same colour in a list column where they are read as a set. → [narrative-36-43.md#rule-36](narrative-36-43.md#rule-36)

37. **An automation only fires about a device Polaris is actually polling** — ONE gate, `assetCanTrigger` in `notificationEngine`, applied by EVERY trigger path: the asset must be `monitored` **and** not suppressed (maintenance window / dependency-suppressed — business rule 16, which this rule now subsumes rather than sitting beside). The monitored half is pushed into SQL for the threshold, composite and metric/state-preview loads (`scopeWhere(scope, monitoredOnly)`) and checked per row in the event/change tail off the `assetDetail` row. **Event and change triggers were the deliberate exception and no longer are**: firing about a device nobody polls made "an automation covers it" and "Polaris watches it" two different answers. The four statuses that cannot carry monitoring at all fold in through business rule 10 rather than being retested here. Three consequences: un-monitoring a device **clears** its live alerts through `clearVanishedStates` (`notification.out_of_scope`) the way leaving the scope does — which is the bug that forced the rule, since `monitorStatus` is NOT cleared when monitoring stops and a `monitorStatus == down` automation kept firing forever about a shelved device; a **null `assetDetail` still fires** (the asset row is GONE — an `asset.deleted` event must not be swallowed), as do system-scoped events, which carry no assetId; and the raw unfiltered scope resolver stays for the surfaces asking a different question — the device-list preview REPORTS the unmonitored remainder, and the dimension picker, mass pinning and `Contact.assetCondition` are not about firing. → [narrative-36-43.md#rule-37](narrative-12-24.md#rule-3

38. **A device behind a dark parent is not accused, and it is not released on one packet** — two halves of dependency suppression that had been left implicit. (a) **Release is asymmetric.** Entering suppression still needs every effective parent confirmed `down` (`warning`/`recovering` flapping must never drag a healthy subtree in), but LEAVING it counts `recovering` as down too — a parent mid-recovery has answered ONE packet and is still short of the covering automation's success threshold, so releasing there un-suppresses a subtree whose own probes are all still failing and the outage re-alerts device by device as plain Down. The child's persisted `dependencySuppressed` selects the side (`SuppressionAssetState.currentlySuppressed`); `unknown`, `passive` and `warning` stay ok in both directions, or a subtree could strand in Dep. Down with nothing able to clear it. Release cascades one layer per pass, which is correct — a gate coming back does not mean the switch under it has. (b) **A miss the upstream explains is GREY, not red.** A suppressed asset is still probed (half cadence — it may answer over a redundant path), and every failure used to be indistinguishable from a real one. `recordProbeResult` now stamps `AssetMonitorSample.dependencyDown` from the asset row's own flag (never re-derived — the reconciler owns it), the rollups carry `dependencyFailureCount`, and `probeOutageService` hands every chart an `OutageKind`. Same dive, no accusation; deliberately NOT a band (that vocabulary is maintenance's, rule 16). A run **splits at a change of kind**, a rollup bucket must qualify WHOLE (`dependencyFailureCount >= failureCount`; NULL reads as red), and the grey is duplicated in four places by design like the red already is. → [narrative-36-43.md#rule-38](narrative-36-43.md#rule-38)

39. **How a person wants to be reached is theirs, not the automation's — but an automation offering one way still reaches them** — `User.notificationPreference` (`email` default | `push` | `any`) is an ACCOUNT setting, not a browser switch: the "Enable push" toggle is gone from the account menu, the mobile More tab and the Automations page, and every client instead reconciles ITS OWN subscription to the stored preference at boot (`polarisPush.syncToPreference`), which is what makes "prefer push" mean push on every device. That reconcile **never prompts** (no user activation at page load), so a browser that has never been asked stays un-enrolled until the operator picks the preference there; the preference is **saved even when the browser refuses**, being account-wide. A notify action is now **plural** — `channelIds` carries several channels behind one recipient list, `channelId` survives as the primary and the lossless single-channel mirror (`notifyChannelIds` is the ONLY reader of the pair; `assertActionRefs` refuses a payload where the two disagree), and `actionsToTargets` expands one action to one DeliveryTarget per channel so nothing downstream knows an action can be plural. On top of that, `respectUserPreference` delivers to each recipient only through the channel their own preference accepts — consulted **ONLY when the action group offers BOTH methods** (`actionsCarryBothMethods` server-side, `hostOffersBothMethods` in the wizard, which grays the checkbox), since in a single-method group the preference would DELETE the alert rather than route it. Only ACCOUNTS are filtered (a typed address or an address-book contact expressed no preference — unknown means deliver, the rule 25 posture), and **a preference never deletes an alert**: `preferenceWithholds` keeps a recipient on the channel they didn't pick when the one they did pick can't reach them (no enrolled device, or a null `User.email`) — reachability meaning the SUBSCRIPTION EXISTS, since a 201 from a push service is not delivery and a dead endpoint only surfaces at send time, where `enqueuePushFallbacks` re-routes it to the action's own email channel behind three guards (per-recipient not per-row, the action's own channel, never twice) — worth exactly one alert per dead endpoint, since the 410 also prunes the subscription and every later alert takes the fire-time path, an unrecognized preference normalizes to `email` rather than to nobody, and the two broadcast toggles stayed push-only (applied on `transport === "web_push"` alone, so a mixed action never mails the whole roster off a control that never said so). Changes write `user.notification_preference.changed`. → [narrative-36-43.md#rule-39](narrative-36-43.md#rule-39)

40. **Two assets on one address is a conflict; one asset on a stale address is not** — `Asset.ipAddress` carries no uniqueness constraint (two rows holding one address is the state discovery has to be able to REPRESENT in order to report it, unlike the IPAM half's per-subnet unique index — rule 3), so the duplicate is found by a sweep (`detectDuplicateIpAssets`, 10m) and reported as the `duplicate-ip` Conflict flavour + a `conflict.detected` Event, which is what the baseline "IP conflict detected" automation alerts on. Seven decisions carry it. (a) **Only network-present assets count** — status NOT in `UNMONITORABLE_STATUSES` (business rule 10), i.e. `active` + `maintenance`; a shelved, disabled or decommissioned row is not on the wire. (b) **A stale record is not a duplicate.** DHCP reuses addresses constantly and an Asset keeps the last address a writer staged until another write moves it, so a departed device's row sits on an address its successor legitimately holds — reporting those would bury the real ones. A member counts only while its claim is CURRENT: operator-owned (`ipOverride` equals the address, or `ipSource="manual"`) never expires, and a discovered one must have been re-asserted within `CLAIM_FRESH_DAYS` (7) — measured on the `(asset, ip)` `AssetIpHistory` row, which the `db.ts` extension bumps on EVERY write staging `ipAddress` (so it tracks cadence, not change), with `Asset.lastSeen` as the fallback for a row that predates the extension. The per-address timestamp is preferred over the asset's presence on purpose: a device that is up but whose recorded address nobody has re-asserted in months is a stale RECORD. (c) **It takes two DEVICES, not two rows** — members sharing one non-null MAC are one device recorded twice, which is a merge's problem (`mergeDuplicateHostnameAssets`), not an address conflict; a null MAC proves nothing, so each counts as its own device. (d) **One pending row per ADDRESS, never per pair** — a three-way collision is one card carrying every claimant in `proposedAssetFields.members[]`, and the row's `assetId` is the lowest-id member so a refresh can't churn the FK its cascade rides on. (e) **Accept is refused, because there is nothing to adopt — there are TWO verbs instead, one per real cause.** Two devices: `POST /conflicts/:id/reassign-ip`, a new address typed on ONE member, written with the asset form's own pin semantics (`ipAddress` + `ipOverride` + `ipSource="manual"` in one update, so the override guard defers and discovery converging on it later releases the pin by itself) — and it **refuses an address another network-present asset already holds**, which would move the duplicate rather than resolve it. One device recorded twice: `POST /conflicts/:id/merge` with `{ survivorAssetId, absorbAssetIds }`, which absorbs the named members into the survivor through `assetMergeService.mergeAssets` — the same engine the asset page's Merge modal uses, so provenance/MACs/IP history/dependency edges/monitoring carry identically — accepting **no field winners** (blank-fill is what every automatic absorb uses; per-field control lives on the asset's Sources tab) and re-pointing `Conflict.assetId` at the survivor BEFORE the first merge, since deleting an absorbed asset cascades to conflicts pointing at it. Reject means dismiss, and the rejected row is the dedup marker: the SAME member set never re-raises, a changed one does. (f) **A duplicate that resolves itself closes itself**, as `rejected` by `system:auto-resolved` — nothing may leave a resolved collision sitting in the queue; that same path is what retires a conflict whose members stop qualifying, so narrowing (g) needs no migration. (g) **One claimant has to be equipment somebody ADDRESSED on purpose** — `CONFLICT_ELIGIBLE_ASSET_TYPES` (`switch` / `access_point` / `firewall` / `server`, the last covering vCenter VMs, which are typed `server`). Two endpoints trading a pool address is DHCP working, not a fault; an endpoint sitting on an access point's address is an outage. So ONE qualifying member raises the group and every other claimant still rides the card (the endpoint is what took the address, and the operator usually resolves it by moving the endpoint). Eligibility is tested on the CURRENT claims, so a departed switch's leftover record can't license a conflict between two live laptops. It is a constant, not a Setting — a claim about which equipment has deliberate addressing rather than a per-install preference — and `hypervisor` (an ESXi host) and `router` are deliberately outside it pending a call on whether they belong. → [narrative-36-43.md#rule-40](narrative-36-43.md#rule-40)

41. **A subnet dies with its FortiGate, and the chassis — not the name — says which gate that is** — a discovered `Subnet` records the SERIAL of the gate serving it (`Subnet.fortigateSerial`) alongside `fortigateDevice`'s name, because a name cannot tell a RENAME from a REPLACEMENT and those need opposite handling. **Tri-state in both directions** (`utils/chassisIdentity.ts:classifyChassis`): a NULL stored serial is unknown and LEARNS on first sight (so the migration backfills nothing — every existing row converges on its own), and an unreadable serial THIS run is unknown and applies no constraint, never "different", or one failed CMDB read would declare the whole fleet replaced. **The comparison is against a SET, per device** — the reporting gate's own serial plus every `ha_slave[]` member — because FMG flips a cluster's top-level `sn` to whichever member is active and comparing against one value would report a replacement on every failover; per DEVICE and not fleet-wide, since a chassis re-registered under another FMG device entry is genuinely a replacement for THIS subnet. Anything outside that set raises the `chassis-replaced` Conflict (`subnetChassisConflictService`, the first `entityType="subnet"` variant), which is **additive**: the old chassis's subnet + reservations are COPIED to the archive, nothing is released, re-pushed or deleted, and the stored serial is deliberately NOT re-pointed while the conflict is pending (the pending row IS the unresolved state; accepting moves it). Dedup is keyed on the (old, new) serial PAIR, so a rejected row suppresses exactly that transition while a second swap raises anew. This closes a case that was previously SILENT: a same-name RMA swap matched by CIDR, matched the roster, and let the new chassis inherit every reservation row of the old one, `pushStatus: "synced"` and dead device-side pointers included. **Discovery RETIRES a dead row itself**: Phase 1's create path consults a second index of the deprecated rows (`deprecatedByBlockCidr`, keyed exactly as the unique index is) and archives one when a live gate re-reports its range — but ONLY when a DIFFERENT gate is serving it (`classifyDeprecatedSupersede`), since an operator who deprecated a subnet its own gate still serves would otherwise have that decision silently undone. Serial decides where both sides have one; the device NAME is the fallback for rows predating the column, and a matching name with no stored serial is genuinely ambiguous and KEPT (a wrongly-kept row is a skipped subnet someone can archive by hand; a wrongly-archived one reactivates a retired range). Exact-CIDR only — a deprecated /23 partially overlapping a new /24 is a different judgement and is still reported as a real overlap. The remaining skip NAMES the fix rather than emitting the old self-overlap message, and the rule 42 excluded-address check runs BEFORE it so an out-of-scope CIDR never reaches archiving. This was the feature's blind spot on release: the chassis comparison sits inside the `if (existing)` branch and `existing` excludes deprecated rows, so on an install whose gate was already swapped it never ran at all and the operator saw the identical skipped-subnet event on the fixed build. **And a retired subnet MOVES to `ArchivedSubnet` / `ArchivedReservation` rather than going `deprecated`** — a deprecated row still holds `@@unique([blockId, cidr])` while being invisible to discovery's lookup index, so its CIDR became unrecordable rather than reusable (every run skipped it with a self-overlap message, and `findSubnetForIp` dropped every lease, DHCP reservation, VIP and interface IP inside it too); moving the row out is the only thing that frees the index, and it makes the retired rows **locked by construction** rather than by a guard at each of ~50 reservation write sites. Archiving is deliberately exempt from rule 4's active-reservation protection (that guards against destruction; this preserves). Rule 23 is unchanged — a decommissioned managed device still gives its address back, while the subnet is live. A second, independent defect fixed in the same change: Phase 1 re-pointed a matched subnet's `fortigateDevice` in the DB but never mirrored it onto the in-memory row Phase 2 filters, so a subnet re-pointed at a renamed or replaced gate was deprecated by Phase 2 **in the same run** — a plain gate rename was enough. → [narrative-36-43.md#rule-41](narrative-36-43.md#rule-41)

42. **Some address space is not one network, and the way to say so is to exclude it** — a `SubnetExclusion` is a CIDR the operator has declared out of scope for the networks list, managed on IPAM → Networks → **Exclusions**. It exists because a Polaris subnet is ONE row per CIDR while some address space is the SAME at every site (a management VLAN, an out-of-band range, an appliance's fixed subnet): the first site discovered claims the row, every other site collides with it, and since rule 41 that collision is a CONFLICT rather than noise — each site's gate answers with its own serial, so the shared row reads `replaced` on every run and raises a `chassis-replaced` card about a box nobody swapped, with a fresh (old, new) pair each time so dedup never catches it. **Global, not per block** (the CIDR needs excluding precisely because several sites serve it; a per-block exclusion would let it in through another block). **`cidr` is the IDENTITY** — normalized on write and FROZEN after create (the PUT and its Zod schema take `name`/`notes` only), because re-pointing an exclusion in place would un-exclude what the operator excluded and exclude what they never named, in one edit; changing the range is a delete plus an add. **Containment is ONE-directional**: an exclusion covers itself and anything narrower (so a /16 excludes the /24s in it) and deliberately NOT a wider discovered CIDR, or excluding one /24 would silently swallow a /8; the MOST SPECIFIC match is reported so a refusal names the row to delete. **One enforcement seam for creation** — `createSubnetRowChecked`, for the same reason rule 20a's overlap lock lives there: manual create, auto-allocate, bulk allocate and the discovery create all pass through it, and `opts.exclusions` lets a caller that already loaded the set (discovery, once per run) pay no read per row. **The ALLOCATORS treat excluded ranges as taken space, never as a refusal** — folded into the list handed to `findNextAvailableSubnet` / `packIntoAnchor`, so "any free /N" steps over an exclusion instead of 409-ing on it, and `previewBulkAllocate` must build that list identically or the preview shows a plan the write rejects. **Discovery skips a covered scope WHOLE** (Phase 1, ABOVE the existing-row branch — the conflict comes from the UPDATE side, so skipping only the create would fix nothing) and exempts the row from the **Phase 2** stale sweep, since its `fortigateDevice` is frozen at whichever site claimed it first and deprecating it when that one gate leaves the roster would put it in exactly the `deprecated` state rule 41 exists to avoid. **Adding an exclusion destroys NOTHING** — networks already listed that it covers come back as `matchCount`/`matches` and are left in place (retiring one stays `POST /subnets/:id/archive`, the verb that preserves reservations); a config write must not delete address-space records as a side effect, and the count is reported rather than hidden so "nothing happened" and "something happened I wasn't told about" don't look alike. IPv4-only, refused at the door rather than stored as a row that could never match. Reads `subnets:read`, mutations `subnets:**fullwrite**` (the archive's reasoning — fleet-wide, over discovered rows whose `createdBy` is null). → [narrative-36-43.md#rule-42](narrative-36-43.md#rule-42)

43. **A grant is only as narrow as the act it names** — three permission levels described acts they did not match, and all three move the same way. (a) **Deploying the Polaris Agent is `assets=fullwrite`, not `write`**: install / retry / reinstall / upgrade / uninstall + `POST /assets/bulk-agent-install` all run an installer on someone else's host over a stored SSH/WinRM credential and leave a service behind, which is not the act `assets=write` (fix a hostname, retype a serial) describes — `assetsadmin` got fleet deployment free with the inventory job. Enabling an integration class block's **`agentDeploy.enabled` is the SAME grant, CHAINED** onto `integrations=write` (`assertAgentDeployGrant` in `api/routes/integrations.ts`), because a capability with two doors has to be gated at both: `networkadmin` holds `assets=read` and could not deploy to one device, but reached the fleet-wide checkbox through a route that never mentions assets. Only the ON transition is gated — a role that inherits an enabled block must still be able to switch it off. Reads stay at `read`; the client withholds the verbs through `canDeployAgent()` / `data-deploy-agent`, never `canManageAssets()`. (b) **`assetsProbe` is a READ-ONLY key** (`levels: ["none","read"]`): it was gated at `write` everywhere, so `read` granted nothing and `fullwrite` was asked for by no route — two dead radio buttons an admin could still click. The one thing on the key that WROTE, the dependency-test outage simulation (it stamps `Asset.dependencyTestUntil` and can mask a real outage), moved to **`assetMonitorSettings=fullwrite`** — the admin-only level its own code comment always claimed and the `assetsProbe=write` gate never delivered. (c) **`credentials` carries the ownership dimension**: `write` creates + reaches own rows, `fullwrite` reaches any, `POST /credentials/test` included whenever it names a stored `id` (that path merges the row's REAL secrets into the probe, so it lends a password rather than reading anything), and an unowned row — `createdBy` null, never backfilled — is fullwrite-only. Ladder narrowing is enforced by `normalizePermissions` (clamps DOWN, never up), `permissionOf` (clamps on read, for pre-deploy session snapshots) and `requirePermission` (throws at module load on an ungrantable level). → [narrative-36-43.md#rule-43](narrative-36-43.md#rule-43)

44. **A quiet window withholds the reminder, not the alert — and the reminder that follows says how long** — an automation's `repeat.quiet` is a list of up to 8 recurring windows (`utils/quietTime.ts`, validated by the Maintenance scheduler's own `scheduleShapeSchema` and evaluated by its `currentWindow`/`nextWindow`, so every time is SERVER-LOCAL wall clock and a 22:00–06:00 window survives DST and midnight identically to a maintenance window). Since a day carries a LIST of hour ranges and each day may keep its own, ONE window says "nights during the week, all weekend" — which is why the wizard edits a single window with the shared `PolarisRecurrence` day/hours editor and lists any others (a one-shot, a monthly freeze) read-only rather than offering to rewrite them. Five things it is, and one it is not. (a) **Held, never skipped**: the sweep does not advance `escalationState.tiers.repeat.lastSentAt` on a reminder it withholds, so that reminder stays DUE and goes out on the first tick after the window ends — there is nothing to schedule, a held reminder is simply an overdue one. (b) **The reminder that ends a hold reports the silence**: the hold is stamped on `escalationState.quietHeldSince` / `quietHeldCount`, and that stamp puts `{repeat.quiet}` ("Reminders resumed after a quiet period — this alert has been active for 9h 12m.") in the body and `· ACTIVE 9h 12m` in the `[REMINDER n]` subject, because the question after a silent night is how long this has been going on, not which reminder number arrived. The subject marker rides ONLY that reminder — on every reminder it would mean nothing — and only when no operator subject template is set, the same condition the `[REMINDER n]` prefix already carried. The standing `Active for` facts row is separate and rides EVERY reminder (it renders "" and prunes away on the initial alert). (c) **The hold is closed by the SEND, not by the window ending**: a reminder whose channel was dead retries next sweep and must still be the one that reports the silence. (d) **A hold only exists where a reminder was actually withheld** — quiet with nothing due stamps nothing, so a reminder that comes due 20 minutes after the window ended is an ordinary reminder and says so. (e) **A malformed quiet blob must not silence the reminders it was only supposed to pause**: `normalizeRuleToV2` re-parses the repeat config with `quiet` stripped rather than reading the whole thing as "never repeats", which would have turned "pause overnight" into "never remind anyone again" — invisible until someone missed an outage. What it is NOT: quiet time does not touch the first alert, the escalation tiers, or the reset notifications. A tier exists to chase a specific person harder, so silencing it from a control that says "reminders" would weaken an escalation the operator configured somewhere they weren't looking; `escalation.stopOn` and `repeat.stopOn` are still the only things that stop either. `stopAfterHours` is wall time from the fire, quiet included (the wizard warns about the pairing rather than extending the deadline), and the maintenance / dependency suppression pause is NOT a quiet hold — it `continue`s before the repeat pass and retires the alert outright (business rule 16). → [narrative-44-48.md#rule-44](narrative-44-48.md#rule-44)

45. **An address places a device only through the gate that owns it, and only a device nothing else can place** — for an asset with an IP address and NO MAC, `lastSeenSwitch` / `lastSeenAp` are derived by the `resolveIpUpstreamChain` sweep (`services/ipUpstreamChainService.ts`, boot + 90s then every 10 min, scheduler role) along ONE chain: IP → containing subnet's owning FortiGate (`Subnet.fortigateSerial` first, `fortigateDevice` second, through `utils/fortinetParentKey.ts` — never a hostname match) → THAT gate's `AssetArpEntry` → MAC → the `AssetMacTableEntry` learned port with the fewest MACs (`<hostname>/<ifName>`) and the `AssetWirelessStation` carrying the MAC or the address. **Four refusals:** another gate's ARP row never counts, and with no owning gate resolvable the address is accepted only when exactly ONE gate reports it (the overlapping-RFC1918 scoping of rules 17 and 26); two MACs at the address on the owning gate is `ambiguous`, not a pick (rule 26's ARP rule); an address claim that is not current under rule 40's model (`claimIsOperatorOwned` never expires, a discovered claim needs its `AssetIpHistory` row within `CLAIM_FRESH_DAYS`) is skipped; and ARP / FDB / station rows older than `EVIDENCE_FRESH_MS` (24h) are not evidence, because those tables are delete-replaced per scrape and an older row means the writer stopped answering. **MAC-less assets ONLY** (`macAddress IS NULL`, infra types excluded): a MAC-bearing asset already has Phase 7.5 and the FortiAP station scrape as writers, with a different label format, and a second writer would ping-pong the column and audit both halves every tick — the sweep writes only what no other writer can. **The MAC is derived and never adopted onto the asset** (adoption makes the row eligible for MAC-keyed dedupe and merge, and a wrong adoption merges two devices; that step is a follow-up behind an opt-in Setting, the rule 26 precedent). **Stamps are never cleared** — absence of evidence is not a move — and are written only on change, id-sorted inside `$transaction` chunks under `retryOnDeadlock`, with `asset.switch_port.changed` / `asset.wireless_ap.changed` Events (actor `system:upstream-chain`) batched AFTER each commit. Set-based end to end; no per-asset awaits. The Add Asset form's `/ip-context` panel gained the same station lookup (`apStations[]`, `matchedBy: "mac" | "ip"`). → [narrative-44-48.md#rule-45](narrative-44-48.md#rule-45)

46. **A device filter on an event automation filters the event's SUBJECT** — an `event` or `change` automation's `scope` selects which devices it fires ABOUT, and the event tail (`runEventTail` in `notificationEngine.ts`) enforces it: for a filtered rule, the Event's asset must be selected by `scopeMatchesAsset` or the fire is skipped. The test is read BEFORE the fired-this-event stamp, not with the state gates — an automation whose filter does not name the device is not watching that event at all, so it must not suppress its own reset either. Two refusals follow from "the subject is a device": an event that names no asset — an integration, a user, a login, the host itself — cannot satisfy a device filter, so a FILTERED automation never fires on one (an unconstrained one still does, which is how the twelve seeded event automations keep working); and neither does an event whose asset row is already gone (`asset.deleted`), because there is nothing left to test the filter against. **"Unconstrained" is its own question, asked first** — `scopeIsUnconstrained()` in `notificationTypes.ts`: `{allAssets:true}`, a bare `{}`, or a condition tree with no rules in it. It cannot be folded into `scopeMatchesAsset`, which answers false for `{}` (a builder-authored scope with no dimensions selects nothing) — the right answer for the builder and exactly the wrong one for every event automation saved before 2026-09, all of which carry `{}` meaning "any device". The trigger type is `scoped: true` in `buildSchemaCatalog` so the wizard SAVES the Devices step instead of discarding it, and `previewRule` answers a filtered event draft with the device list its filter selects (plus the note that the list is who it would fire about, not who is triggering now). `ASSET_SCOPED_TRIGGER_TYPES` still excludes `event` on purpose: that list answers "is this automation about a device", which is what the asset-details Alerts tab asks, and an all-assets `integration.discover.error` automation is about an integration, not about each of 2000 devices. Carve-out precedence is untouched — `triggerSignature` returns null for event and change (rule 18), so a filtered event automation neither carves out nor is carved out. → [narrative-44-48.md#rule-46](narrative-44-48.md#rule-46)
47. **A PostgreSQL client is chosen by the server's MAJOR and verified with `--version` before it is trusted — never spawned by bare name.** `pg_dump` refuses a server newer than itself, so `backupService.resolvePgTool()` reads `SHOW server_version_num`, looks for `/usr/pgsql-<N>/bin`, `/usr/lib/postgresql/<N>/bin` or the Windows install dir for that major (a NEWER major is accepted; an older one never), falls back to PATH only when nothing versioned exists — and when the server's major cannot be read at all, takes the NEWEST versioned client before PATH (the shell twin first borrows each versioned `psql` to ask the server; the host most likely to have no `psql` on PATH is the one that just removed AppStream 13 without `alternatives --auto`, 2026-09-10) — then runs `--version` on whatever it picked and compares majors (`src/utils/pgClientTools.ts`). A `pg_dump` older than the server refuses the backup with the sentence the operator needs — both versions, the path, the fix — as the AppError itself, never behind "see the server log"; `psql` only warns across majors, so for it only "cannot be run" is fatal. `deploy/update-linux.sh` carries the same logic in shell (`resolve_pg_tool`, `$PG_DUMP`, `$PSQL`); `setup-rhel-nodb.sh` installs PGDG's versioned client instead of RHEL's unversioned `postgresql` (which is PostgreSQL 13 on RHEL 9); both RHEL installers and both nodb installers compare the client major to the server's instead of asking `command -v` whether a file exists; `check:versions` flags a bare `dnf install -y postgresql`; CI's `integration` job installs `postgresql-client-17` by name rather than using the runner image's own client, and both that major and its `postgres:17-alpine` service container are `postgres-major` sites so they cannot drift apart (2026-09-10); the Maintenance tab shows the resolved tools and their compatibility. Presence is not compatibility, `alternatives --display` reports its own bookkeeping rather than the file on disk, and the Platform Lifecycle card grades the server — none of them can see this. → [narrative-44-48.md#rule-47](narrative-44-48.md#rule-47)

48. **Nobody hands out authority they do not hold** — admin-equivalence is `users=fullwrite AND roles=fullwrite` (`isAdminEquivalentPermissions`), and a caller who lacks it may not create it, on a role or on a user. `assertNoPrivilegeEscalation(req, targetPermissions, subject)` in `api/middleware/permissions.js` refuses with a **403** at the four places the grant could be minted: `POST /roles` and `PUT /roles/:id` (a `roles:write` holder writing the two fullwrite grants — onto a new role, or onto the role they already hold), and `POST /users` and `PUT /users/:id/role` (a `users:write` holder creating an account on an admin-equivalent role **with a password they choose**, or promoting an existing one into it). Before this, the write/fullwrite distinction on those two keys meant nothing: either delegated permission was a one-step path to full control of the install, and the shortest one needed no existing account at all. **It is not four-eyes** — a caller who already holds admin-equivalence is unaffected, and the check is skipped entirely whenever the target permission set is not admin-equivalent, so every ordinary role edit is untouched. **It is the mirror of the lastAdminEquivalent guard, and neither replaces the other**: that one refuses to DEMOTE the last admin (rule 43's neighbourhood, enforced by `countAdminEquivalentUsers`), this one refuses to PROMOTE into the tier; the self-edit checks on `PUT /users/:id/role` ("you cannot change your own role") were never escalation guards at all, since the escalation runs through somebody else's row. **The caller's own level is read from the request's role snapshot** — `req.roleSnapshot` for a bearer token, `req.session.roleSnapshot` otherwise — so a role-bound API token is held to the same bar as a session, and a request with no snapshot resolved is treated as NOT admin (it must never fail open). The predicate is shared with `rankRole`'s group-mapping tie-break so the notion cannot drift between "which role wins an SSO mapping" and "who may grant it". Server-side provisioning is deliberately outside the rule: `ssoProvisioning` and the seed have no escalating actor to test. → [narrative-44-48.md#rule-48](narrative-44-48.md#rule-48)

49. **An upgrade never refuses for want of a credential it can find itself, and never records one it has not proved** — `resolveUpgradeCredential` in `services/agentInstallService.ts` answers what an agent upgrade connects with, in one order: the operator's explicit `credentialId` if the request carried one, else the row's `installCredentialId`, else the Polaris-managed SSH deployment credential for the platform (`windowsSshOnboardingService.getOnboardingState`; darwin takes the Linux one). **An id that no longer resolves counts as absent, not as an error** — `ManagedAgent.installCredentialId` is written ONLY at install time and its FK is `ON DELETE SET NULL`, so deleting a credential silently strands every agent installed with it, and an install predating the column (migration `20260514010000`, added with no backfill) never had one at all. Before the fallback existed, `startUpgrade` threw on those rows BEFORE touching `installStatus`, so they stayed `active` and out of date and every `upgradeAllOutdated` fan-out re-skipped them with **no Event, no `installError` and nothing on the asset panel** — a host stranded this way sat on its original binary indefinitely while the fleet moved on. Only an EXPLICIT `credentialId` that does not resolve is still an error: an operator who names a credential is told it is wrong rather than quietly connected with another. **The transport follows the credential's TYPE, never the row's `installTransport`** — for a healthy row the two always agree (the install routes refuse a credential whose `type` does not match the chosen transport), and it is what makes the fallback work at all, because migration `20260609000000` backfilled `installTransport='winrm'` onto EVERY pre-existing Windows row and the managed credential is key-only, so honouring the column would hand a passwordless credential to `winrmConnectionFromCred` and die on "missing username or password" on exactly the rows that needed help. A WinRM credential on a non-Windows agent is refused. **An adopted credential is written back onto the row on SUCCESS and only on success** (with its transport, in the same update that returns `installStatus` to `active`): reaching the host is the proof, so a genuinely WinRM-only box fails to connect, keeps what it had recorded, and lands as `upgrade_failed` with a real reason — itself an upgradeable status. An operator override is never adopted; Polaris does not record a choice it did not make. A row the fan-out still cannot upgrade now writes an `agent.upgrade_skipped` Event against the asset, so the silence that hid this is gone. **Upgrade only** — install, reinstall and uninstall still require a credential on file (`hasInstallCredential` gates the Reinstall button; force-remove is the escape). → [narrative-44-48.md#rule-49](narrative-44-48.md#rule-49)

50. **A response the app did not write is a response with the app's headers missing — an unmatched route is ANSWERED, never dropped to the framework's default handler.** `src/app.ts` mounts a catch-all after the `/api/v1` router that calls `next(new AppError(404, "Not found"))`, so `errorHandler` answers it and the response keeps the headers `buildHelmetOptions()` already set. Reaching Express's built-in `finalhandler` instead **replaces** the `Content-Security-Policy` with its own `default-src 'none'`, and because neither `frame-ancestors` nor `form-action` falls back to `default-src`, every 404 in the app advertised unrestricted framing and form submission while every matched route carried the real policy (HawkScan Medium "CSP: Wildcard Directive" on `/robots.txt` and `/sitemap.xml`, 2026-09-10); its HTML body also echoed the request back ("Cannot GET /robots.txt"). The 404 message is **fixed, never built from the request** — nothing the caller sent is reflected. The asymmetry under `/api/v1` is deliberate and not a gap: `requireAuth` is mounted ahead of any route match, so an unknown API path answers **401** to an anonymous caller and the JSON 404 only once authenticated — the API does not tell an anonymous caller which endpoints exist. The edge is the second half of the same invariant: `deploy/nginx/polaris.conf` emits HSTS itself and `proxy_hide_header`s the upstream's copy (two `Strict-Transport-Security` headers is non-compliant per RFC 6797 §8.1 — a UA processes only the first, so "browsers take the strongest seen" was never true) and sets `server_tokens off`. A scan aimed straight at `npm run dev` cannot see the edge half at all, which is what `deploy/nginx/README-scan-harness.md` exists for. → [narrative-44-48.md#rule-50](narrative-44-48.md#rule-50)

51. **`DATABASE_URL` is a DRIVER URL — its `sslmode` value is TRANSLATED into the libpq vocabulary, never copied.** The parameter name is shared between node-postgres (which reads `DATABASE_URL`) and libpq (which `pg_dump` / `psql` read from `PGSSLMODE`); the value space is not. node-postgres accepts `no-verify`; libpq accepts only `disable` / `allow` / `prefer` / `require` / `verify-ca` / `verify-full` and exits 1 on anything else. `libpqSslMode(value)` in `utils/pgEnv.ts` maps `no-verify` → `require` — the same posture, since only `verify-ca` and `verify-full` validate the chain — and **refuses an unrecognized value rather than dropping it**, because omitting `PGSSLMODE` lets libpq fall back to `prefer` and silently downgrades an operator who asked for TLS to opportunistic TLS. The wizard is the producer: `setup/setupRoutes.ts → buildConnectionString` writes `sslmode=no-verify` whenever "Allow self-signed certificate" is ticked, and it is correct to keep doing so — the URL is for the driver. Copied through verbatim it meant **every backup path failed on every install created that way**: manual, scheduled and pre-update, plus restore (psql takes the same overlay), all behind `Database backup failed — see the server log`, with the real cause (`pg_dump: error: invalid sslmode value: "no-verify"`) visible only in the container log (Docker/Unraid install, 2026-09-11). The scripted RHEL / Ubuntu installs never saw it — `deploy/update-linux.sh` dumps as the local `postgres` user over a unix socket and builds no URL at all — so this is structurally a remote-database and container-deployment failure, and a green scripted install proves nothing about it. **This is rule 47's other half**: 47 says the client binary that got chosen must be able to work against the server; 51 says the connection parameters handed to it must be in that client's own vocabulary. Neither is checked by the other, and both failed for months behind the same sentence. → [narrative-44-48.md#rule-51](narrative-44-48.md#rule-51)
