# Business rules 30–84 — the invariants

The filename keeps its original range: it is a stable citation key linked from code and the other skills. Each entry is the CONTRACT layer of a rule — what must hold today, the functions and columns that hold it, the rules it leans on — in about 150 words, ending with a pointer into the narrative file that records the incident, the reasoning and the dated history (verbatim, including the long-form invariant each rule carried here until 2026-09-22). Rule numbers are a stable citation key — never renumber; retire a rule in place and give a new one the next free number (`npm run rules:next`).

30. **Confirmation is the configured cadence's job; ICMP only fills in the loss ratio** — `monitorStatus` reaches `down` when N missed polls are OUTSTANDING against the operator's configured transport at their configured `intervalSeconds`. **The counter is a LEAKY BUCKET WITH A CEILING** (`utils/monitorStatus.ts` → `nextFailureBucket` + `monitorStatusFor`, which the probe path CALLS): a miss adds one to `consecutiveFailures`, an answered poll takes one back (floored at 0), and the level LOCKS at `bucketCapFor(N, recoveryPolls)` the moment a miss carries it to N. The verdict: `cf == 0` is `up`, an ANSWERED probe is `recovering` whatever the level, a MISS is `down` at or above N and `warning` below it. Recovery costs exactly the cap however long the outage ran; `consecutiveSuccesses` decides nothing (`polaris-domain-model` → dormant-columns.md). **N is the covering automation's `missedPolls`** (rule 36), never a Monitor Settings value; the CADENCE still comes from the monitor-settings hierarchy, and `resolveProbeIntervalSec` applies exactly one clamp (parent dark ⇒ 2× interval). **A probe may decline to be a reading**: `ProbeResult.skipped` (the vCenter probe when vCenter is unreachable; `responseTimePolling === "disabled"`, gated by the shared `responseTimeProbeShouldQueue` in both publishers) writes no sample and moves no counter, bumping `lastMonitorAt` alone; a re-queued duplicate job records nothing (`probeStillDue`). **The ICMP loss sweep never calls `recordProbeResult`** — it runs uniformly over every eligible asset every cycle through `utils/burstPing.ts`, and `probeKind` keeps its rows out of every response-time reader and rollup (only `probeLossQuery` and the email loss chart read all kinds). → [narrative-25-35.md#rule-30](narrative-25-35.md#rule-30)

31. **The login page is the way back in, so restricting it is opt-in and must refuse to lock you out** — `loginAccessConfig` (default **off**) restricts local login by source IP via `utils/ipScope.ts`, gating **both halves or neither**: `/login.html` (socket destroyed, stealth posture) AND `POST /auth/login` + `/auth/login/totp` (the same generic 401 a wrong password gets, plus `auth.login.blocked_source`). LDAP shares the login route and is gated; **SSO is never gated**, and a RATE LIMITER counts as a gate — `/auth/azure/login` carries its own `ssoEntryLimiter`, and **an SSO entry ceiling must never sit below the callback ceiling behind it**. It **fails open** on a settings read error; the PUT refuses a scope excluding the caller's own `req.ip`, which the GET returns as `callerIp`. Pinned by `tests/unit/loginAccessService.test.ts` and `tests/integration/loginAccessGate.test.ts`. → [narrative-25-35.md#rule-31](narrative-25-35.md#rule-31)

32. **A reset condition answers "what has to become true again", so it starts as the trigger inverted — and it resolves where the alert lives** — custom-condition mode is offered on every continuous trigger (`TRIGGER_TYPES_WITH_RESET_CONDITIONS`; `event` / `change` refused), pre-seeded with `invertedLeaf` / `invertedTree` (De Morgan, and/or-only). (a) While firing, **the tree is the sole recovery authority**, evaluated in its own post-loop pass over rows re-read from the DB. (b) Resolution is **dimension-first**; the per-asset fallback is reserved for a leaf in ANOTHER dimension space (`dimensionSpaceOf`), a leaf with no reading for the firing component says nothing, and reset leaves inherit the trigger's port coverage (`coverUnpinnedPoe`, rule 57). (c) Kind coherence is enforced on single triggers too. (d) Reset leaves inherit the trigger's measurement window. (e) `event` / `change` get the **counterpart Event** instead (`TRIGGER_TYPES_WITH_RESET_EVENT`, prefilled from `RESET_EVENT_SUGGESTIONS`), scoped to the SAME subject; a signal writing one verb for both directions is split (`capacity.severity_recovered`, `platform.lifecycle_recovered`), and the trigger's own direction lives in `trigger.detailsMatch`, which the wizard renders and saves. `cooldownSec` is retired from the builder and dormant (`polaris-domain-model` → dormant-columns.md); the wizard writes null on every save. → [narrative-25-35.md#rule-32](narrative-25-35.md#rule-32)

33. **A device that answers is not a device that works — and the check that proves it belongs to the VENDOR, not to a login** — the HTTP check is a **manufacturer custom widget** (`ManufacturerCustomWidget.widgetType="http"`), not a polling method (retired 2026-08): a check varies by vendor AND model while a login varies by vendor, so sharing one row meant duplicating passwords. Decisions: the **body match is load-bearing** (a 200 whose body doesn't match FAILS; no lax toggle); **status is judged before content**; **redirects are never followed**; the body is **capped at 64 KB**; the credential is **authentication only, with no "none" mode**; **`authMode` is stated, not guessed** (Digest is a handshake — fire bare, read the challenge, re-fire **exactly once**); it writes `AssetStateSample` 0/1 **pass or fail** plus a success-only RTT gauge and **never moves `monitorStatus`**; and **`netGuard` deliberately does not apply**, the target being the monitored asset's own private address. → [narrative-25-35.md#rule-33](narrative-25-35.md#rule-33)

34. **An active scan finds things; a separate grant adds them** — a **Discovery** (`NetworkScan`) sweeps addresses the operator names, the only Polaris feature that touches hosts it has no prior relationship with. **Scanning and adopting are separate grants** (`networkScan` authors and runs, `assets:write` chains on adopt, and the wizard RENDERS the missing grant); it is **opt-in and IDS-visible**, with no scheduler and no shipped default range; **credential order is the try order** and the first method that answers wins; **adoption is new-addresses-only**; it is neither an integration type nor a `DiscoveryRun` row, and there is no `network-scan` AssetSource kind. A Discovery is **private or shared**: visibility decides who may see and RUN one, ownership who may edit it (`networkScan:fullwrite` reaches anyone's); an invisible row answers 404, `name` is unique per owner, existing rows were migrated public, new ones default private, and the export carries no visibility. → [narrative-25-35.md#rule-34](narrative-25-35.md#rule-34)

35. **The GAL is a mirror, not a source of truth — and Polaris only ever deletes what it wrote** — directory sync is opt-in per integration (`config.enableDirectorySync`, separate from `enableDirectorySearch`, which persists nothing) and runs as a post-sync pass of the owning integration's discovery run. (a) **Provenance decides deletion**: `DirectoryContactSource` records every (integration, directory object) the sync created; a `Contact` dies only when its LAST provenance row goes, a hand-added row has none, and adoption drops provenance. (b) **A Polaris `User` or a manual `Contact` on an address wins.** (c) **An empty or catastrophically-shrunken read never wipes** — the deletion half is skipped with a warning. (d) Synced entries AND the live GAL fan-out are gated on `automationManagement`, not `contacts:read`. (e) **No directory PII reaches `Event.details` or the logs** — counts only. → [narrative-25-35.md#rule-35](narrative-25-35.md#rule-35)

36. **The automation decides what "down" means; a device no automation covers is never judged** — a `monitorStatus == down` automation's **`missedPolls`** IS the definition of down for every device it covers (`downDetectionService.resolveDownThreshold`, once per probe) and is the trigger's ONLY timing number: the wizard states it in `Sustained for (polls)` and zeroes `forPolls` / `forDurationSec` on a bare down trigger. Precedence is rule 18's ladder; same-rank ties resolve to the **smaller count**, then older `createdAt`, then lower `id`. **A device covered by NO down automation reads `passive`**: polled, sampled, charted, no verdict; entering or leaving it is a configuration edge (`isConfigStatusEdge`), and anything testing `!== "up"` for "unreachable" must exempt it. A zero-rule fleet stamps `monitor.down_detection_absent` once. **The same automation owns the way back UP**: its reset hold in POLLS (`recoveryPollsFor`, from `reset.sustainPolls` or the `sustainSec` mirror divided by the cadence) sets the bucket cap of rule 30, so an outage owes exactly the operator's number of answers; `downRecoveryConsumesSustain` stops the engine charging the wait twice, and only `mode: "auto"` counts (a `condition` reset is its own authority, rule 32a). `failureThreshold` and `Asset.awaitingRecoveryConfirm` are dormant (`polaris-domain-model` → dormant-columns.md). **The automation also decides what colour Down is**: `down` is painted in the covering automation's severity on every chart through one palette in two files (`downSeverityHex` / `DOWN_SEV_COLOR`, pinned by `tests/unit/downSeverityColor.test.ts`); the Status pill does not move. The palette itself is `polaris-ui-canon` → canon-charts-widgets.md's. → [narrative-36-43.md#rule-36](narrative-36-43.md#rule-36)

37. **An automation only fires about a device Polaris is actually polling** — ONE gate, `assetCanTrigger` in `notificationEngine`: the asset must be `monitored` AND not suppressed (maintenance window or dependency-suppressed), applied by EVERY trigger path, event and change included. The monitored half is pushed into SQL for the threshold, composite and preview loads (`scopeWhere(scope, monitoredOnly)`) and checked per row in the event tail. Rule 10's four unmonitorable statuses fold in through `monitored`. Un-monitoring a device **clears** its live alerts through `clearVanishedStates` (`notification.out_of_scope`), because `monitorStatus` is NOT cleared when monitoring stops. A **null `assetDetail` still fires** (`asset.deleted` must not be swallowed), as do system-scoped events. The raw scope resolver stays for surfaces asking a different question (the device-list preview, the dimension picker, mass pinning, `Contact.assetCondition`). Division of labour: rule 16 says what a maintenance window does to the asset, this rule is the gate that reads it, rule 78 is the one opt-out from the suppression half, and rule 80a adds the event-time gate beside this one. → [narrative-36-43.md#rule-37](narrative-36-43.md#rule-37)

38. **A device behind a dark parent is not accused, and it is not released on one packet** — (a) **Release is asymmetric.** Entering suppression needs every effective parent confirmed `down`; LEAVING it needs the parent genuinely BACK. The release side is a WHITELIST, `RELEASES_SUPPRESSION` = `up`, `unknown`, `passive` (neither of the last two is a claim about reachability), so `down`, `recovering` AND `warning` all hold. The child's persisted `dependencySuppressed` selects the side (`SuppressionAssetState.currentlySuppressed`); release cascades one layer per pass. (b) **A miss the upstream explains is GREY, not red.** A suppressed asset is still probed; `recordProbeResult` stamps `AssetMonitorSample.dependencyDown` from the asset row's own flag (never re-derived — the reconciler owns it), the rollups carry `dependencyFailureCount`, and `probeOutageService` hands every chart an `OutageKind`. A run splits at a change of kind, a rollup bucket must qualify WHOLE (`dependencyFailureCount >= failureCount`; NULL reads red), and it is deliberately NOT a band — that vocabulary is maintenance's (rule 16). (c) **A suppressed device keeps its own count, at the configured cadence, and leaves with its parent.** `resolveProbeIntervalSec` takes no asset state — no slow-down under suppression — and `recordProbeResult` runs the bucket regardless of `dependencySuppressed`, so the layers behind a recovering parent drain alongside it; `evaluateSuppression`'s layer-order walk then releases, in ONE pass, every layer whose own status already reads `up`, and only those (a child still `recovering` is released but holds ITS children). The reconcile reads `monitorStatus` through the probe-patch buffer (`getPendingProbePatch`), because `propagateAfterStatusChange` fires before that buffer flushes and would otherwise see the parent as it was before the edge. → [narrative-36-43.md#rule-38](narrative-36-43.md#rule-38)

39. **How a person wants to be reached is theirs, not the automation's — but an automation offering one way still reaches them** — `User.notificationPreference` (`email` default | `push` | `any`) is an ACCOUNT setting: every client reconciles ITS OWN subscription to it at boot (`polarisPush.syncToPreference`) without prompting, and a browser at permission `default` is **asked once** (`polarisPush.shouldOfferEnrollment`, recorded in `localStorage` when the offer is SHOWN; never on iOS outside the installed app). The preference saves even when the browser refuses. A notify action is **plural**: `channelIds` behind one recipient list, `channelId` as the primary mirror (`notifyChannelIds` the only reader; `assertActionRefs` refuses disagreement), expanded by `actionsToTargets` to one DeliveryTarget per channel. `respectUserPreference` filters ACCOUNTS only (a typed address or contact expressed no preference — unknown means deliver, rule 25), and only when the action group offers BOTH methods (`actionsCarryBothMethods` / `hostOffersBothMethods`). **A preference never deletes an alert**: `preferenceWithholds` keeps a recipient on the other channel when the chosen one cannot reach them, and `enqueuePushFallbacks` re-routes a dead endpoint (410) to the action's own email channel once. An unrecognized preference normalizes to `email`; the two broadcast toggles stay push-only. Changes write `user.notification_preference.changed`. → [narrative-36-43.md#rule-39](narrative-36-43.md#rule-39)

40. **Two assets on one address is a conflict; one asset on a stale address is not** — `Asset.ipAddress` carries no uniqueness constraint (unlike rule 3's per-subnet index), so the duplicate is found by the `detectDuplicateIpAssets` sweep (10m) and reported as the `duplicate-ip` Conflict + a `conflict.detected` Event. (a) **Only network-present assets count** (status not in `UNMONITORABLE_STATUSES`). (b) **A claim counts only while CURRENT**: operator-owned (`ipOverride` equals the address, or `ipSource="manual"`) never expires; a discovered one needs its `(asset, ip)` `AssetIpHistory` row within `CLAIM_FRESH_DAYS` (7). (c) **Two DEVICES, not two rows** — members sharing a non-null MAC are a merge's problem. (d) **One pending row per ADDRESS** (`proposedAssetFields.members[]`; `assetId` is the lowest member). (e) **Accept is refused**; the verbs are `POST /conflicts/:id/reassign-ip` (refuses an address another present asset holds) and `POST /conflicts/:id/merge` (through `assetMergeService.mergeAssets`, `Conflict.assetId` re-pointed first); reject dismisses that member set. (f) **A resolved collision closes itself** (`rejected` by `system:auto-resolved`). A group qualifies by ANY of: (g) a claimant in `CONFLICT_ELIGIBLE_ASSET_TYPES` (`switch` / `access_point` / `firewall` / `server`); (h) claimants with disjoint `AssetSource.sourceKind` sets AND a deliberate address (`vipInfo`, `dhcpBinding="reservation"`, or `DELIBERATE_RESERVATION_SOURCE_TYPES` — three columns because rule 23 makes them three facts); (i) an operator-owned claim (`claimIsOperatorOwned`). `qualifiedBy` records which. **Write time triggers it too**: `POST /assets` and an IP-changing `PUT /assets/:id` run `reconcileDuplicateIpForAddresses` scoped to the touched addresses and return the card as `ipConflict`; `GET /assets/ip-check` simulates the incoming claim through the same `groupCurrentClaims`. Imports are not triggers. **Merging takes `assets:fullwrite`**; reassign stays `write`. (j) **An offline device's address may be BLANKED, and discovery fills the blank**: `POST /conflicts/:id/clear-ip` (`clearDuplicateIpAsset`, same gate as reassign) writes `ipAddress=null`, drops any pin and records the old address in `Asset.ipCleared`; the `db.ts` override guard (`applyIpCleared`) passes the first DIFFERENT staged address through and releases the hold, drops a re-staging of the blanked address while another network-present asset still records it, and lets it back once nothing does. Operator IP writes (form, reassign) null `ipCleared`; a form save re-sending the blank field is a no-op. → [narrative-36-43.md#rule-40](narrative-36-43.md#rule-40)

41. **A subnet dies with its FortiGate, and the chassis — not the name — says which gate that is** — a discovered `Subnet` records `fortigateSerial` beside `fortigateDevice`, because a name cannot tell a RENAME from a REPLACEMENT. `utils/chassisIdentity.ts` → `classifyChassis` is **tri-state in both directions**: a NULL stored serial learns on first sight, an unreadable serial THIS run applies no constraint, and the comparison is against a SET per device (the gate's own serial plus every `ha_slave[]`). Anything outside it raises the **additive** `chassis-replaced` Conflict (`subnetChassisConflictService`): subnet and reservations copied to the archive, nothing released or re-pointed while pending, dedup on the (old, new) serial pair. **Discovery retires a dead row itself**: Phase 1's create path archives a deprecated row when a DIFFERENT gate re-reports its exact CIDR (`classifyDeprecatedSupersede`, `deprecatedByBlockCidr`); a same-gate or ambiguous match is KEPT, and the rule 42 exclusion check runs first. **A retired subnet MOVES to `ArchivedSubnet` / `ArchivedReservation`** rather than going `deprecated`, which frees the `(blockId, cidr)` index and locks the retired rows by construction; archiving is exempt from rule 4. Rule 23 is unchanged. Phase 1 must mirror a re-pointed `fortigateDevice` onto the in-memory row Phase 2 filters. **(a) One swap is one decision, and the old chassis's ASSET retires by chassis too**: Phase 2a's `judgeRosterFirewall` calls a firewall whose serial is gone from the roster but whose name a gate READ this run answers with a different chassis set `replaced` — decommissioned with `reason: "chassis-replaced"` and NO controller cascade (the name belongs to the new chassis's children); an unread gate or a serial-less row stays `keep`. The per-subnet rows group by `chassisSwapKey`: `adoptChassisSwap` / `rejectChassisSwap` act on every pending row of one pair, adopt may `mergeAssets` the old gate into the new (dropping the dead serial's `fortigate-firewall` source and the old MAC rows) and deletes the old chassis's controller claims; the badge counts a pair once. → [narrative-36-43.md#rule-41](narrative-36-43.md#rule-41)

42. **Some address space is not one network, and the way to say so is to exclude it** — a `SubnetExclusion` is a CIDR the operator declared out of scope for the networks list (IPAM → Networks → **Exclusions**), for address space that is the SAME at every site and would otherwise raise a `chassis-replaced` card (rule 41) every run. **Global, not per block.** **`cidr` is the IDENTITY**: normalized on write, FROZEN after create (the PUT and its Zod schema take `name` / `notes` only). **Containment is ONE-directional** — an exclusion covers itself and anything narrower, never a wider discovered CIDR — and the MOST SPECIFIC match is reported. **One enforcement seam for creation**, `createSubnetRowChecked` (`opts.exclusions` lets discovery load the set once per run); **the allocators treat excluded ranges as taken space, never a refusal**, and `previewBulkAllocate` builds the same list. **Discovery skips a covered scope WHOLE** in Phase 1, above the existing-row branch, and exempts it from the Phase 2 stale sweep. **Adding an exclusion destroys NOTHING** (`matchCount` / `matches` reported). IPv4-only. Reads `subnets:read`, mutations `subnets:fullwrite`. → [narrative-36-43.md#rule-42](narrative-36-43.md#rule-42)

43. **A grant is only as narrow as the act it names** — (a) **Deploying the Polaris Agent is `assets=fullwrite`** (install / retry / reinstall / upgrade / uninstall, `POST /assets/bulk-agent-install`); enabling a class block's `agentDeploy.enabled` CHAINS the same grant onto `integrations=write` (`assertAgentDeployGrant`), on the ON transition only; the client withholds the verbs through `canDeployAgent()`. (b) **`assetsProbe` is read-only** (`none | read`); the dependency-test outage simulation moved to `assetMonitorSettings=fullwrite`. (c) **`credentials` carries the ownership dimension**: `write` creates and reaches own rows, `fullwrite` reaches any, `POST /credentials/test` naming a stored `id` included; an unowned row is fullwrite-only. Ladders are clamped by `normalizePermissions`, `permissionOf` and `requirePermission`. (d) **A rung exists only where it grants something the rung below does not** (migration `20260922000000_rbac_catalogue_hygiene`; `processControl` removed; `fullwrite` survives only on an ownership key or a named act, pinned by `tests/unit/permissionLevelLadders.test.ts` → "no dead top rung"). Downloading a backup is `serverSettingsData=write` (a `none | write` ladder); the auto-decommission thresholds ride `assetMonitorSettings`. **`readonly` is the FLOOR for every built-in role**, except `user` holding `networkScan=none`. (e) **The gap (d) recorded is closed** (migration `20260923000000_authentication_function_key`): the four identity providers' settings and test routes, the passkey policy and the password policy moved to a new **`authentication`** key (`none | read | write`), so `serverSettingsSystem` now tops out at `write`; seeding is DERIVED from each role's old System level (`fullwrite`→`write`, `read`→`read`, `write`→`read` — the one tightening) and MUST precede the fold, or every admin-equivalent role reads as a plain `write` holder. Group mappings stay on `users=fullwrite`; the login-page source-IP restriction stays on `serverSettingsSystem`. (f) **One act on two keys is the same defect inverted** (migration `20260923010000_fold_manufacturer_aliases`): `manufacturerAliases` is FOLDED into `manufacturerProfiles` (catalogue 33 → 32), because an alias rewrites `Asset.manufacturer` fleet-wide and that value selects the device's profile; the routes keep `/api/v1/manufacturer-aliases`; seeding takes the LOWER of the two stored levels; the migration's `pg_temp.perm_rank` MUST be `CREATE OR REPLACE` because `prisma migrate deploy` runs every pending migration in one session. Pinned by `tests/unit/manufacturerAliasesFoldLockstep.test.ts`. (g) **Flashing a switch, access point or FortiGate is `assets:write`, NOT a named act** (operator decision 2026-09-26, reversing the 2026-09-25 design): whoever may edit an asset may upgrade it. `POST /assets/:id/firmware-upgrade` is gated at `assets:write` and the asset card's reads at `assets:read`; the `firmware` key governs the Repository alone (`read` sees it, `write` uploads and manages images) and has no Full Read-Write rung (migration `20260926000000_firmware_key_repository_only` rewrites any stored `fullwrite`). Consequence to keep in view: every role holding Assets Read-Write — the built-in `networkadmin` and `assetsadmin` included — can reboot network hardware; the approval dialog and rule 87's gates are the remaining guard. Rule 48 is the promotion guard beside this. → [narrative-36-43.md#rule-43](narrative-36-43.md#rule-43)

44. **A quiet window holds the reminder, never skips it — and the reminder that follows says how long** — the hold mechanics rule 92 inherits (since 2026-10-03 the windows are the automation's `quietTime` or a global `QuietTimeSchedule`, resolved by `quietTimeHoldService.resolveQuietHold`, no longer a per-action `repeat.quiet`; quiet now reaches the escalation tiers too and, in the `all` mode, the first alert — rule 92 owns both). (a) **Held, never skipped**: no `escalationState` key is advanced on a withheld send, so it goes out on the first sweep after the window. (b) **The reminder that ends a hold reports it**: `escalationState.quietHeldSince` / `quietHeldCount` put `{repeat.quiet}` in the body and `· ACTIVE 9h 12m` in the `[REMINDER n]` subject (only when no operator subject template is set). (c) **The hold is closed by the SEND**, not by the window ending. (d) **A hold exists only where a send was actually withheld.** (e) **A malformed policy must not silence anything**: `parseQuietTimeConfig` reads an unreadable `quietTime` as "no quiet time", the loud direction. `stopAfterHours` is wall time from the fire; the maintenance / suppression pause is NOT a quiet hold (rule 16). → [narrative-44-48.md#rule-44](narrative-44-48.md#rule-44)

45. **An address places a device only through the gate that owns it, and only a device nothing else can place** — for an asset with an IP address and NO MAC, `lastSeenSwitch` / `lastSeenAp` are derived by the `resolveIpUpstreamChain` sweep (`services/ipUpstreamChainService.ts`, scheduler role, every 10 min) along ONE chain: IP → owning FortiGate (`Subnet.fortigateSerial` first, `fortigateDevice` second, through `utils/fortinetParentKey.ts`) → THAT gate's `AssetArpEntry` → MAC → the `AssetMacTableEntry` port with the fewest MACs and the `AssetWirelessStation` carrying it. **Four refusals**: another gate's ARP row never counts (with no owning gate, exactly ONE reporting gate is accepted); two MACs at the address is `ambiguous`; a claim not current under rule 40 is skipped; ARP / FDB / station rows older than `EVIDENCE_FRESH_MS` (24h) are not evidence. **MAC-less assets ONLY** (`macAddress IS NULL`, infra types excluded). **The derived MAC IS adopted**, guarded by `partitionAdoptableMacs` (refused when another asset carries it, or two candidates resolve to it), in the same `$transaction` as the stamps, audited `asset.mac.adopted`, mirrored into `AssetMacAddress` as `ip-upstream-arp`. Stamps are never cleared and written only on change; set-based end to end. Rule 55 is the READ-side counterpart (IPAM as a last-resort parent). → [narrative-44-48.md#rule-45](narrative-44-48.md#rule-45)

46. **A device filter on an event automation filters the event's SUBJECT** — an `event` or `change` automation's `scope` selects which devices it fires ABOUT, and `runEventTail` requires the Event's asset to pass `scopeMatchesAsset`, tested BEFORE the fired-this-event stamp so a non-matching automation does not suppress its own reset. A FILTERED automation never fires on an event naming no asset (an integration, a user, the host) nor on one whose asset row is gone; an unconstrained one still does. **"Unconstrained" is asked first** — `scopeIsUnconstrained()` in `notificationTypes.ts` (`{allAssets:true}`, a bare `{}`, or a condition tree with no rules); it cannot fold into `scopeMatchesAsset`, which answers false for `{}`. The trigger is `scoped: true` in `buildSchemaCatalog` so the wizard saves the Devices step, and `previewRule` answers with the device list the filter selects. `ASSET_SCOPED_TRIGGER_TYPES` still excludes `event` (that list answers "is this automation about a device"). `triggerSignature` stays null for event and change (rule 18). → [narrative-44-48.md#rule-46](narrative-44-48.md#rule-46)
47. **A PostgreSQL client is chosen by the server's MAJOR and verified with `--version` before it is trusted — never spawned by bare name** — `pg_dump` refuses a server newer than itself, so `backupService.resolvePgTool()` reads `SHOW server_version_num`, looks for the versioned bin dir for that major (`/usr/pgsql-<N>/bin`, `/usr/lib/postgresql/<N>/bin`, the Windows install dir; a NEWER major is accepted, an older never), falls back to PATH only when nothing versioned exists, takes the NEWEST versioned client when the server's major cannot be read, then runs `--version` on its pick and compares majors (`src/utils/pgClientTools.ts`). 132. **A Hardware Sensors table is what its profile row says, and nothing a vendor ships is in code** — Operator decision 2026-10-23. (a) On a manufacturer profile's `temperature` row of type `table` (metric row or override), the row's symbol is the table's VALUE column and `defaultSensorColumns` / `sensorColumns` (JSON, `utils/hardwareSensors.ts → SensorColumns`) names the rest: `nameSymbol`, `alarmSymbol` with `alarmMap` (the state-probe modes; absent = `nonzero`), a fixed `sensorClass`, a `tenths_to_units` scale. (b) The SNMP collector walks those symbols, resolved per rule 131, and joins them on the index (`sensorTableRows`); it walks a table ONLY for a `table` row. The `/fortinet/i` manufacturer dispatch and the three fgHwSensorTable OID literals are gone, so a Fortinet device with no such row, or no FORTINET-FORTIGATE-MIB uploaded, falls to ENTITY-SENSOR-MIB like any vendor. (c) A blank value is null, never 0. (d) Columns on another metric are a 400; on a non-table temperature row they are cleared. (e) Migration `20261024020000_sensor_table_columns` rewrites `fgHwSensorTable` rows to `fgHwSensorEntValue` + `FORTIGATE_SENSOR_COLUMNS`, the seed and an old export's import do the same.
