# Business rules 12–29 — the invariants

Each rule as CLAUDE.md stated it: the invariant plus a pointer into the narrative file (`narrative-12-24.md` / `narrative-25-35.md`), which records the incident or constraint that forced it. Rule numbers are a stable citation key — never renumber; retire a rule in place and give a new one the next free number.

12. **`Asset.lastSeen` means verified network presence** — written ONLY through `bumpLastSeen()` in `src/utils/assetInvariants.ts`, which no-regresses and stamps `lastSeenSource` provenance. **Polling is authoritative for monitored assets**: when `monitored === true`, `bumpLastSeen` refuses the discovery-origin sources (`discovery`, `device-inventory`, `dhcp-lease`, `vcenter`, `arc`) so they can't advance presence past what polling established; a failed probe writes nothing. Device inventory outranks the DHCP lease for unmonitored assets, and Fortinet-discovery-owned infra never takes client-sighting presence at all. Never write `Asset.lastSeen` directly — route through `bumpLastSeen` (or the probe patch on the monitor hot path). → [narrative-12-24.md#rule-12](narrative-12-24.md#rule-12)
13. **SD-WAN monitoring is opt-in, read-only, FortiOS-only** — gated per-integration by `Integration.config.pullSdwan` (default false; FMG + standalone parity). Writes the `AssetPerfSlaSample` SLA time-series and delete-replaces the `AssetSdwanRule` current-state table. **Never writes to the device.** The runtime selected route is *inferred* when FortiOS won't expose it over REST, and is labeled as such in the UI. → [narrative-12-24.md#rule-13](narrative-12-24.md#rule-13)
14. **Description sync is opt-in and Polaris-primary** — gated per-integration by `Integration.config.syncDescriptions` (default false). **A non-empty Polaris value always wins** (pushed on save, re-asserted by every reconcile, device-side edits overwritten); **an empty Polaris field adopts** the device value. No conflict state exists. `decideDescriptionSync(polaris, device)` is the pure decision; all device I/O rides `reservationPushService`'s Transport. Under FMG central management, pushes are additionally mirrored into FMG's database via JSON-RPC `update` (never `set`). → [narrative-12-24.md#rule-14](narrative-12-24.md#rule-14)
15. **Location codes ride device descriptions; notes are operator-only** — `a:`/`b:`/`f:`/`r:`/`jb:` codes are parsed server-side by `src/utils/locationCodes.ts` from device descriptions captured into `fortinetTopology.deviceDescription`. `Asset.description`'s codes win **exclusively** when it carries any (no per-key fall-through); `Asset.notes` is deliberately NOT a source. **Discovery never writes `Asset.notes` on an existing asset.** → [narrative-12-24.md#rule-15](narrative-12-24.md#rule-15)
16. **Maintenance windows pause everything; status flips are scheduler-managed** — `maintenanceScheduler` holds `Asset.status="maintenance"` with the prior status parked in `maintenanceReturnStatus` — which since rule 10's widening can only ever hold `active`, every other status being unmonitorable and therefore untargetable. It stops ALL server-driven polling, counts the asset as DOWN for child dependency suppression (unless the schedule's `suppressChildren` is off), and silences notifications for it and every dependency-suppressed child — **retiring the alerts that were already live** rather than freezing them (`clearSuppressedAlerts` in `notificationService`, run on the entering edge and again ahead of every engine tick: soft-clear with `clearedBy="system:maintenance"` / `"system:dependency-suppressed"`, state-row released, NO reset actions, and a still-bad condition re-earns its debounce and fires anew after the window; it sweeps Notification rows because event/change alerts carry no state row). **Discovery/system writers must never write status over a maintenance asset**; deletion-at-source (the discovery decommission sweeps) is the one carve-out. **A schedule's recurrence states DAYS AND HOURS, and a day carries a LIST of hour ranges** (`hours[]` for every matched day, `hoursByDay[]` per day, an empty list meaning all day; the legacy single `startTime`/`endTime` pair is still read, in that one resolution order) — so one day produces zero or more occurrences, and each range is its OWN occurrence with its own start. That matters because the operator-release check identifies an occurrence by its start: an operator who ends maintenance during the 09:00 window stays released for that window and re-enters for the 14:00 one, which is the behaviour a single range per day could not express. Two ranges on the SAME day may therefore not overlap (refused at validation — two occurrences over one instant make "which occurrence is this" unanswerable); overlap ACROSS days is allowed and ordinary (a Friday night running into an all-day Saturday), and resolves to the earliest-STARTING containing occurrence. The shape, its validator and its evaluator are shared verbatim with automation quiet time (business rule 44), and so is the browser's editor for it (`PolarisRecurrence`). Open `AssetMaintenanceWindow` rows are the restart-safe source of truth, and dashboards treat maintenance as its own state, never an outage. → [narrative-12-24.md#rule-16](narrative-12-24.md#rule-16)
17. **ARP presence evidence for stale reservations; the sweep is opt-in** — discovery Phase 7.6 stamps `Reservation.lastSeenArp` whenever a gate's ARP table binds an active reservation's IP to its **reserved MAC**, keeping statically-configured / ICMP-silent devices out of the stale list. MAC match is required, matching is scoped per (fortigateDevice, ip), and **absence of an ARP entry is never negative evidence**. The cache-priming ARP presence sweep (`Integration.config.arpPresenceSweep`) is default off because it is IDS-visible. → [narrative-12-24.md#rule-17](narrative-12-24.md#rule-17)
18. **Automation precedence is same-trigger, most-specific-wins** — two automations watch the same thing iff their `triggerSignature` matches (host/event/change/composite are exempt). **`monitorStatus` is keyed by operator+value, NOT by dimensionFilter** — it is a single per-asset column, so every `== down` automation lands in ONE group whatever its device filter (they must be able to carve each other out), coverage is tested as scope AND device filter (`peerCoversAsset` / `carveOutPeerCovers`), and this same group decides whose missed-poll count governs each asset (business rule 36 rides this ladder rather than inventing a second precedence system). Among those, the higher `scopeRank` (all assets < device type < OS < manufacturer < model < tag < region < IP block < subnet < hostname) **carves out** the assets it covers from every lower-rank one: readings dropped, any active alert cleared as `notification.superseded`, pending debounce reset. Same-rank ties both fire. `buildShadowIndex` / `isAssetShadowed` in the engine; `previewRule` warns in both authoring directions. → [narrative-12-24.md#rule-18](narrative-12-24.md#rule-18)
19. **Severity bands escalate one alert by value, each on its own clock** — tiers stack on the base trigger; **severities must strictly increase** (thresholds need not be monotonic — most-severe MET tier wins). Tiers share the base sampling and **share ONE hold** — the trigger's: the builder stopped offering a per-tier "sustained for" in 2026-08-28 (one hold per severity was four clocks doing one job, and it read as a property of the base severity it sat inside), so a band carries no `forDurationSec` and `resolveTierLadder` gives it the trigger's. The ENGINE still honours a per-tier value on an API-authored rule — `NotificationRuleState.bandMetSince` is per tier and always was (`resolveTierLadder` → `updateTierMetSince` → `sustainedSeverity`, all pure) — but the wizard DROPS one it loads rather than saving a hold nothing on screen states. A tier may still override the comparison operator. **The hold is COUNTED IN READINGS, not seconds** (2026-08-29): a trigger states `forPolls` and a reset states `reset.sustainPolls`, and where those are set the engine counts consecutive qualifying readings — `forDurationSec` / `sustainSec` survive as the wall-clock mirror (what the prose reads, and what sizes the sample window the engine fetches to see N readings). Two families resolve it: a SERIES source (every sample table, plus the Polaris host's own metrics) is counted statelessly off its own samples (`leadingRun`), while a CURRENT-STATE source (the Asset columns, the SD-WAN rule table, the windowed-ratio metrics recomputed per tick) counts observations on `NotificationRuleState.metRun`/`clearRun`, advancing only when that stream's poll anchor moved (`advanceRun`) — the engine's 60s tick must never count five polls against a device polled every five minutes. A band that carries its own `forDurationSec` stays wall-clock. Nothing is migrated: a rule stating only seconds keeps the old behaviour until it is re-saved from the builder. One alert per asset climbs and eases severity in place; de-escalation is immediate, and the hysteresis dead band eases to the base severity. `bandNotify` governs delivery on each transition. → [narrative-12-24.md#rule-19](narrative-12-24.md#rule-19)
20. **Subnet writes serialize per block; secrets are encrypted at rest; a backup you cannot restore is not a backup** — three operability invariants. (a) **Overlap checks are check-then-insert**, so every subnet-creating path must go through `createSubnetRowChecked()` or `lockBlockForSubnetWrites()` in `subnetService.ts` (per-block `pg_advisory_xact_lock`), never a bare `prisma.subnet.create`; the same medicine covers the `mapRegions` JSON blob via `withRegionBlobLock` in `mapRegionService`. (b) **Secrets at rest**: the Prisma extension in `db.ts` seals/opens the secret leaves of `Credential`/`Integration`/`NotificationChannel`/`Setting` config — sealing is per-model, **opening is all-models** (relation reads never fire per-model hooks). Raw SQL bypasses the extension. (c) **Backup/restore** is streamed end to end, wraps restore in `timescaledb_pre_restore()`/`post_restore()`, and a failed pre-update backup ABORTS the update by default. → [narrative-12-24.md#rule-20](narrative-12-24.md#rule-20)

21. **SSH host-key verification is opt-in and fails closed** — `SshConfig.verifyHostKey` (default OFF; ON for newly created credentials) enables trust-on-first-use pinning against the `SshHostKey` table via `sshHostKeyService.verifyOrPin`: no pin stores and accepts, a match accepts, a **changed key refuses the connection** and stamps `ssh.host_key.mismatch`. `buildHostVerifier` in `utils/remoteExec.ts` is shared by BOTH `ssh2.connect` call sites and **fails closed** — an internal error refuses rather than silently skipping. Pins are per `(host, port)` in their own table, never on `Credential.config`. → [narrative-12-24.md#rule-21](narrative-12-24.md#rule-21)

22. **The Sources column is `location || learnedLocation`, and which source supplies the learned half is operator-ordered** — priority lives in the `assetSourcePriority` Setting and feeds the **projection**, not just rendering (the column's filter, sort, "behind FortiGate X" criteria and Device Map narrowing all read `learnedLocation`). The contributor catalogue is `utils/assetSourceLocation.ts`: **field** contributors carry a real location string, **label** contributors contribute their own name. Propagation is pull-based and **not retroactive**. Invariant: **a source blob may never be built from the projection's own output** — that laundered an AD OU path into a FortiGate-sourced field and accumulated a prefix per cycle. → [narrative-12-24.md#rule-22](narrative-12-24.md#rule-22)

23. **Who owns an IP and how the gate hands it out are two facts, not one** — `Reservation.sourceType` answers ownership; `Reservation.dhcpBinding` (`null` | `"lease"` | `"reservation"`) answers how the gate serves it. Phase 5 records the binding via the pure `decideInfraDhcpBinding`, writing only on change, and deliberately **never flips `sourceType`, never stamps `expiresAt`**, and fills `macAddress` only from the lease entry. A `"lease"` row is operator-takeover-able exactly like a `dhcp_lease` (`isSupersedableByCreate`); `"reservation"` and `null` stay authoritative. **A managed device that goes away gives its address back** (`releaseInfraReservationsForAssets` on decommission — never on "no longer discovered"), with a 6h reconcile as backstop. Polaris writing the binding itself is double-gated (`pushReservations` + `autoReserveFortinetInfra`, both default off). → [narrative-12-24.md#rule-23](narrative-12-24.md#rule-23)

24. **Alert on the device's own alarm bit before inventing a threshold for it** — **`hwSensorAlarm`** reads `AssetHardwareSensorSample.alarmStatus`, the per-sensor bit the collectors already write; prefer it over a threshold on the reading, since the device knows its own per-model limits. **`customStateValue`** (state probes) is the mechanism for status OIDs Polaris does NOT already collect, and is deliberately not the answer for Fortinet hardware sensors. Shared invariant: `alarmStatusToFlag` returns `0 | 1 | null` and the engine **excludes null in SQL** — a source publishing no alarm bit must never have its absence mapped to 0. **That invariant binds the SNMP varbind decoder too**: `snmpVbToNumber` returns `null` for an absent or empty value and never 0, because `snmpGetScalar` resolves `null` on an error varbind and `Number(null) === 0` turned every unpublished OID into a confident zero — which also suppressed the HOST-RESOURCES-MIB fallback, guarded on `cpuPct == null`. An unrecognized non-empty status maps to 1; ENTITY-SENSOR-MIB's `unavailable(2)` maps to NULL, never alarm (an empty SFP cage is not a fault). **And an absent reading must not be read as an absent DIMENSION either**: an interface state field takes the newest sample row that CARRIES it (`interfaceStateSeries` / `interfaceSampleCarries` in `notificationEngine`), never `group[0]`, because one row is written per port per tick with every column on it and a tick that failed to collect just one writes that column null on a row the rest of which succeeded. Reading the newest row alone made a dropped PoE walk indistinguishable from a port with no PSE — the dimension vanished, `clearVanishedStates` retired the live alert, and the next readable tick raised a NEW one, i.e. a duplicate alert email per collection gap on a port whose state never changed. Unreadable rows leave `Reading.series` too, so a gap neither counts toward a poll-counted hold nor breaks its run. Same discipline at the collector: only a walk that ANSWERED may be cached as "no PSE" (`poeWalkOutcome`), since `.catch()`-ing an error into an empty Map let one timeout blank PoE for 30 minutes. → [narrative-12-24.md#rule-24](narrative-12-24.md#rule-24)

25. **An alert you can't acknowledge from where you read it isn't really acknowledgeable — and who acknowledged it is a session, not a link** — acknowledgement reaches all three read surfaces (in-app, email, web push). Email and push carry the SAME URL, `/alert-ack.html?id=<notificationId>`, naming the alert and nothing else: the page behind it is an ordinary logged-in Polaris page, so an unauthenticated reader signs in first (returning to the alert via the short-lived `polaris_next` cookie, `utils/loginRedirect.ts` — a cookie rather than `?next=` because three of the five login paths bounce through an IdP and `regenerate()` the session), and identity comes from that session. Five consequences. **The email is one message again** — a shared body carries a link that works for whoever reads it, so `expandDeliveries` substitutes `{ack}` ONCE per alert and stopped fanning the To line out one message per recipient; the only thing that still splits a send is capability, and that is TWO copies at most (`splitAckVariants`), never one per person. **Every recipient Polaris can't vouch for gets the button** — an address-book contact or a typed address has no account behind it, so permission is decided at the page rather than by withholding a control, and `alerts:write` is enforced by the acknowledge route with the page merely reporting the refusal (which is why the PAGE gate is `alerts:read`: bouncing a read-only reader to "/" tells them nothing about where their link went). **A recipient it CAN vouch for is asked first**: an account whose role holds `alerts` below `write` is mailed the same alert with the button pruned out — `ackCapabilityByAddress` → pure `splitAckVariants` splits a composed body's To/Cc/Bcc into an ack copy and a no-ack copy (`fillComposedAckUrl(body, null)`, the same blanking an install with no `POLARIS_PUBLIC_URL` already gets), the plain per-address path stamps `meta.noAck`, and web push omits `ackUrl` so `sw.js` renders no Acknowledge action. **The tray carries at most TWO actions** (`Notification.maxActions` is 2 everywhere that renders them at all, and the overflow is dropped from the END), so `sw.js` lists them in priority order and slices: **Acknowledge** (the only one that changes state), then **Open device** (`assetUrl` — the alert's own device page, absent on an alert with no asset; deliberately NOT the body tap's destination, which is the server-chosen alerts list), then **Ignore** (offered only on a `requireInteraction` alert, since a transient one clears itself on the OS banner timer). Ignore closes the toast and sends NOTHING — a tray button carries no session, so it cannot mean "handled"; the alert keeps repeating and escalating. Unknown means capable in both directions: an address with no account keeps the button, and where two accounts share one address whichever may act decides. The policy behind the withholding is a ROLE policy — migration `20260828030000_alerts_ack_write_capable_roles` raised `alerts` to `write` on every role already holding write anywhere else, so what's left is a genuinely read-only role. **Loading is a GET and acknowledging is a POST**, so a mail gateway prefetching every link — Outlook Safe Links, Proofpoint — cannot acknowledge anything, and no unauthenticated state-changing surface remains. **A push Acknowledge action OPENS the page** rather than acting from the tray: that is where the note is typed, and the session is what records the acknowledger. And **`GET /alerts/:id` answers 404, not 403**, for an alert outside the caller's region scope. `requireAckNote` is still enforced in `acknowledgeNotifications`, not in any dialog, so every surface obeys it; a batch is refused whole. Retired with the single-use token: `NotificationAckToken`, `utils/ackToken.ts`, the public `/ack/:token` route, and the per-recipient `planComposedEmails` fan-out. → [narrative-25-35.md#rule-25](narrative-25-35.md#rule-25)

26. **A generated MAC is a placeholder until the network proves otherwise** — the `reservationMacPlaceholder` prefix (Setting, default `02:0F:5E`) is **the only marker** that a stored MAC is synthetic; there is deliberately no boolean column, because the prefix is visible on the gate's own reserved-address table. `normalizePlaceholderPrefix` (`utils/mac.ts`) **rejects any prefix that isn't locally-administered unicast**, so no factory MAC can fall inside the placeholder space. Adoption (`placeholderMacAdoptionService`, Phase 7.7, double-gated on `pushReservations` + `adoptDiscoveredMac`, both default off) swaps in the real MAC on **ARP-table and device-inventory evidence only**, behind five guards, device-first and read-back-verified. Changing the prefix is not retroactive in either direction. → [narrative-25-35.md#rule-26](narrative-25-35.md#rule-26)

27. **A logo is picked by theme; a name is text only when the picture doesn't already say it** — the shipped art is theme-paired, so painting the wrong variant makes the logo *disappear* rather than look off; the variant is chosen by theme **FAMILY, never by id** (three themes, two sets of art), and **`public/js/brand-logo.js` is the single decider** for all four surfaces (desktop login, mobile login, sidebar, Customization preview). The two variants of a pair are normalized to one geometry, so a theme flip moves nothing. The **Application Name is a caption for a custom logo only** — `showName` is false whenever the shipped wordmark is in play, so `appName` may be stored empty. Placement is per surface (`logoOnLogin` / `logoOnSidebar`); the accent composite renders **server-side** so geometry can't drift. → [narrative-25-35.md#rule-27](narrative-25-35.md#rule-27)

28. **The Windows build is the authority; the product name is not** — `ProductName` still reads "Windows 10 Pro" on every Windows 11 client, so AD, Intune/Entra and the agent are all equally wrong and no projection priority can fix it. `normalizeWindowsOs` (`src/utils/osNormalize.ts`) derives the **family from the build via a threshold** (`>= 22000 ⇒ Windows 11`, never goes stale) and the **release from a table** (an unlisted build keeps its raw `osVersion` rather than being guessed at). **Windows Server is excluded entirely** — build 26100 is both Windows 11 24H2 and Server 2025. Applied at **write** time (projection + the `db.ts` Asset hooks) because filters, sorts, exports and scope conditions read the stored columns; it is idempotent and reads no row. Not retroactive. → [narrative-25-35.md#rule-28](narrative-25-35.md#rule-28)

29. **A miss taken while the device is DOWN is the outage, not the link; everything else counts** — `probeLossPct` is the only metric whose input is *failed* probes, which is what makes it the one metric that can raise a second alert about an outage `monitorStatus == down` already owns. Until 2026-09-01 that was prevented inside the ARITHMETIC, by trimming the window back to the last recovery; it is now prevented by marking the individual probes the outage explains (h) and by two gates at the ALERT. (a) **Every other miss counts.** The ratio is plainly failed/total over the window — no anchor, no trimming, and the one exclusion is per-row rather than per-window. The two anchors it used to carry (`GREATEST(first success in window, Asset.recoveryStartedAt)`) stopped a device reading ~92% the moment it came back from a 55-minute outage, but they also collapsed the window of a device flapping to `down` every cycle down to its last few probes, so a badly lossy link reported ~0% loss **forever** — the exact failure the metric exists to catch. `Asset.recoveryStartedAt` is still stamped (`utils/probeLossAnchor.ts`) and read by **nothing**, dormant on the `cooldownSec` precedent. (b) **It counts PACKETS, not rows, wherever it can.** An ICMP sweep row carries `packetsSent` / `packetsReceived` and describes a whole burst, so an asset with any burst rows in the window is measured from those sums and its response-time poll rows are left out — that poll may be SNMP/SSH/REST/WinRM, and folding a lost SNMP response into a figure labelled *packet loss* would make the number mean something different per asset. An asset with no burst rows falls back to the row ratio. `{total, failed}` kept its shape through the change; the units beneath it moved. (c) **Only an answering device reports loss**: the resolver admits `up` and `warning` only (`assetIsAnsweringProbes`; `passive` is excluded — a dark passive device sits at 100% loss with no asset-down alert to supersede it, business rule 36). (d) **A reading at or above the automation's own `ignoreAtOrAbove` ceiling is not a reading** (default **100**, so an untouched rule is unchanged and only a total outage is suppressed). This is what replaced the anchor: with every miss counted, a device back from a long outage genuinely reads ~92% for the rest of the window, so an operator who does not want an alert trailing every outage lowers the ceiling. Polaris opts its OWN all-assets baseline rule out at **90** rather than moving the default, and the V5 one-shot (`seedBaselineAutomationsV5LossCeilingSeededAt`) retrofits that onto **unedited** loss rules on existing installs, naming any edited one in a warning Event rather than narrowing it. (e) **Both gates CLEAR, never freeze** (`notification.superseded`, reason `device-down` or `reading-saturated`). A dropped reading is indistinguishable from *stopped reporting* to `clearVanishedStates`, which freezes — and a frozen loss alert escalating beside the asset-down alert for a whole outage is the duplicate this rule exists to stop. (f) **`windowSec` IS the reading** — History, not smoothing — with `forDurationSec` as its own optional sustain knob (`WINDOWED_RATIO_METRICS`, `probeLossWindowSec`). (g) **The chart and the caption cover the same window.** `measuredFromMs` and `sparklineSvg`'s `measuredFrom` marker are gone with the anchor they existed to reconcile; the chart weights burst rows by packets too, but unlike the query it does NOT drop poll rows once bursts exist — a picture of the window has to be continuous, so its caption may sit a little under the engine's reading on a mixed asset. `includeFullyDown` is retired: with every countable row in the ratio, a fully-dark asset reads 100% on its own. The chart also steps over the same `assetDown` rows the query does — in BOTH the line and the caption, because an alert reading 0.0% over a chart captioned *avg 40%* tells an operator the number is invented — leaving the outage as a GAP rather than a stretch of implausible 0%. (h) **The failures of an outage are the outage, not the link** (2026-09-03). `AssetMonitorSample.assetDown` is stamped on a failed probe from the status that probe RESULTS in (`monitorStatusFor`), and on an ICMP sweep row from the verdict the configured transport has already reached — the `dependencyDown` pattern of business rule 38b — but **the unit of exclusion is the RUN, not the marked row**: every maximal stretch of consecutive failures holding any stamped row is dropped whole, ONSET included, by `probeLossQuery`'s `runId`/`runOutage` window functions and their JS mirror `alertChartService.outageRunFailures`. It has to be, because the marker can only go on from the probe that DECLARES the outage — at the first missed poll nobody yet knows whether it begins one — and dropping only the stamped rows leaves `missedPolls - 1` fully-lost probes in a denominator the exclusion has already shrunk, which still reads over 10% for a whole window after recovery. Reconstructing the run also keeps this out of the business of knowing how long an outage is: `missedPolls` belongs to whichever automation covers the device (business rule 36), so it differs per asset and changes when a rule is edited, while a run is bounded by successes and needs no threshold at all. It exists because neither gate above can see the case an operator actually reports: a switch dark for twelve minutes comes back, starts ANSWERING, and its 30-minute window still reads 40% — under any sensible ceiling — so a "High packet loss" warning lands minutes AFTER the recovery about the outage that already paged someone, and a ceiling low enough to catch it would discard every genuine 40% reading too. Narrow, which is what separates it from the retired anchor: only runs that actually REACHED down go, so a run of misses that stayed below the threshold is loss and still counts in full, and an alternating device — which never reaches `down` at all — is measured exactly as it was. NULL reads as false (coalesced), so the change is not retroactive. `readMonitorHistory.stats.packetLossRate` is a DIFFERENT number and deliberately unchanged: it is the failed/total of the response-time poll over whatever range the asset page's chart is showing, where an outage is exactly what the operator is asking about. → [narrative-25-35.md#rule-29](narrative-25-35.md#rule-29)
