# Business rules 12–29 — the invariants

Each entry is the CONTRACT layer of a rule — what must hold today, the functions and columns that hold it, the rules it leans on — with a pointer into the narrative file (`narrative-12-24.md` / `narrative-25-35.md`), which records the incident, the reasoning and the dated history (verbatim, including the long-form invariant a rule carried here until 2026-09-22 where one was cut back). Rule numbers are a stable citation key — never renumber; retire a rule in place and give a new one the next free number (`npm run rules:next`).

12. **`Asset.lastSeen` means verified network presence** — written ONLY through `bumpLastSeen()` in `src/utils/assetInvariants.ts`, which no-regresses and stamps `lastSeenSource` provenance. **Polling is authoritative for monitored assets**: when `monitored === true`, `bumpLastSeen` refuses the discovery-origin sources (`discovery`, `device-inventory`, `dhcp-lease`, `vcenter`, `arc`) so they can't advance presence past what polling established; a failed probe writes nothing. Device inventory outranks the DHCP lease for unmonitored assets, and Fortinet-discovery-owned infra never takes client-sighting presence at all. Never write `Asset.lastSeen` directly — route through `bumpLastSeen` (or the probe patch on the monitor hot path). → [narrative-12-24.md#rule-12](narrative-12-24.md#rule-12)
13. **SD-WAN monitoring is opt-in, read-only, FortiOS-only** — gated per-integration by `Integration.config.pullSdwan` (default false; FMG + standalone parity). Writes the `AssetPerfSlaSample` SLA time-series and delete-replaces the `AssetSdwanRule` current-state table. **Never writes to the device.** The runtime selected route is *inferred* when FortiOS won't expose it over REST, and is labeled as such in the UI. → [narrative-12-24.md#rule-13](narrative-12-24.md#rule-13)
14. **Description sync is opt-in and Polaris-primary** — gated per-integration by `Integration.config.syncDescriptions` (default false). **A non-empty Polaris value always wins** (pushed on save, re-asserted by every reconcile, device-side edits overwritten); **an empty Polaris field adopts** the device value. No conflict state exists. `decideDescriptionSync(polaris, device)` is the pure decision; all device I/O rides `reservationPushService`'s Transport. Under FMG central management, pushes are additionally mirrored into FMG's database via JSON-RPC `update` (never `set`). → [narrative-12-24.md#rule-14](narrative-12-24.md#rule-14)
15. **Location codes ride device descriptions; notes are operator-only** — `a:`/`b:`/`f:`/`r:`/`jb:` codes are parsed server-side by `src/utils/locationCodes.ts` from device descriptions captured into `fortinetTopology.deviceDescription`. `Asset.description`'s codes win **exclusively** when it carries any (no per-key fall-through); `Asset.notes` is deliberately NOT a source. **Discovery never writes `Asset.notes` on an existing asset.** → [narrative-12-24.md#rule-15](narrative-12-24.md#rule-15)
16. **Maintenance windows pause everything; status flips are scheduler-managed** — `maintenanceScheduler` holds `Asset.status="maintenance"` with the prior status parked in `maintenanceReturnStatus` (only ever `active`, per rule 10). A window stops ALL server-driven polling, counts the asset as DOWN for child dependency suppression unless the schedule's `suppressChildren` is off, and silences notifications for it and every suppressed child by RETIRING the alerts already live rather than freezing them (`clearSuppressedAlerts` in `notificationService`: `clearedBy="system:maintenance"` / `"system:dependency-suppressed"`, no reset actions; a still-bad condition re-earns its debounce after the window). Discovery and system writers never write status over a maintenance asset; deletion-at-source is the one carve-out. Open `AssetMaintenanceWindow` rows are the restart-safe source of truth, and dashboards treat maintenance as its own state, never an outage. The recurrence shape — a day carries a LIST of hour ranges, each range its own occurrence, same-day ranges may not overlap — is shared verbatim with quiet time (rule 44) and specified once in `polaris-domain-model` → alerting.md § Recurrence shape. A device may be taken off a schedule from its own side only out of the EXPLICIT list, and the last explicit target deletes a criteria-less schedule. Rule 37 owns the alerting gate a window feeds; rule 80 owns the holds Polaris takes for its own operations. → [narrative-12-24.md#rule-16](narrative-12-24.md#rule-16)
17. **ARP presence evidence for stale reservations; the sweep is opt-in** — discovery Phase 7.6 stamps `Reservation.lastSeenArp` whenever a gate's ARP table binds an active reservation's IP to its **reserved MAC**, keeping statically-configured / ICMP-silent devices out of the stale list. MAC match is required, matching is scoped per (fortigateDevice, ip), and **absence of an ARP entry is never negative evidence**. The cache-priming ARP presence sweep (`Integration.config.arpPresenceSweep`) is default off because it is IDS-visible. → [narrative-12-24.md#rule-17](narrative-12-24.md#rule-17)
18. **Automation precedence is same-trigger, most-specific-wins** — two automations watch the same thing iff their `triggerSignature` matches (host/event/change/composite are exempt). **`monitorStatus` is keyed by operator+value, NOT by dimensionFilter** — it is a single per-asset column, so every `== down` automation lands in ONE group whatever its device filter (they must be able to carve each other out), coverage is tested as scope AND device filter (`peerCoversAsset` / `carveOutPeerCovers`), and this same group decides whose missed-poll count governs each asset (business rule 36 rides this ladder rather than inventing a second precedence system). Among those, the higher `scopeRank` (all assets < device type < OS < manufacturer < model < tag < region < IP block < subnet < hostname) **carves out** the assets it covers from every lower-rank one: readings dropped, any active alert cleared as `notification.superseded`, pending debounce reset. Same-rank ties both fire. `buildShadowIndex` / `isAssetShadowed` in the engine; `previewRule` warns in both authoring directions. → [narrative-12-24.md#rule-18](narrative-12-24.md#rule-18)
19. **Severity bands escalate one alert by value, each on its own clock** — tiers stack on the base trigger; **severities must strictly increase** (thresholds need not be monotonic — the most-severe MET tier wins). Tiers share the base sampling and **ONE hold, the trigger's**: a band carries no `forDurationSec` and `resolveTierLadder` gives it the trigger's; the engine still honours a per-tier value on an API-authored rule (`NotificationRuleState.bandMetSince` is per tier), but the wizard DROPS one it loads. A tier may override the comparison operator. **The hold is COUNTED IN READINGS, not seconds**: a trigger states `forPolls`, a reset states `reset.sustainPolls`, and `forDurationSec` / `sustainSec` survive as the wall-clock mirror that sizes the sample fetch and feeds the prose. A SERIES source is counted statelessly off its own samples (`leadingRun`); a CURRENT-STATE source counts observations on `NotificationRuleState.metRun` / `clearRun`, advancing only when that stream's poll anchor moved (`advanceRun`). A rule stating only seconds keeps wall-clock behaviour until re-saved from the builder. One alert per asset climbs and eases severity in place; de-escalation is immediate, the hysteresis dead band eases to the base severity, and `bandNotify` governs delivery on each transition. → [narrative-12-24.md#rule-19](narrative-12-24.md#rule-19)
20. **Subnet writes serialize per block; secrets are encrypted at rest; a backup you cannot restore is not a backup** — three operability invariants. (a) **Overlap checks are check-then-insert**, so every subnet-creating path must go through `createSubnetRowChecked()` or `lockBlockForSubnetWrites()` in `subnetService.ts` (per-block `pg_advisory_xact_lock`), never a bare `prisma.subnet.create`; the same medicine covers the `mapRegions` JSON blob via `withRegionBlobLock` in `mapRegionService`. (b) **Secrets at rest**: the Prisma extension in `db.ts` seals/opens the secret leaves of `Credential`/`Integration`/`NotificationChannel`/`Setting` config — sealing is per-model, **opening is all-models** (relation reads never fire per-model hooks). Raw SQL bypasses the extension. (c) **Backup/restore** is streamed end to end, wraps restore in `timescaledb_pre_restore()`/`post_restore()`, and a failed pre-update backup ABORTS the update by default. Pinned by `tests/unit/secretsAtRest.test.ts` (b) and `tests/integration/backupRestore.test.ts` (c); (a) has no pinning test today. → [narrative-12-24.md#rule-20](narrative-12-24.md#rule-20)

21. **SSH host-key verification is opt-in and fails closed** — `SshConfig.verifyHostKey` (default OFF; ON for newly created credentials) enables trust-on-first-use pinning against the `SshHostKey` table via `sshHostKeyService.verifyOrPin`: no pin stores and accepts, a match accepts, a **changed key refuses the connection** and stamps `ssh.host_key.mismatch`. `buildHostVerifier` in `utils/remoteExec.ts` is shared by BOTH `ssh2.connect` call sites and **fails closed** — an internal error refuses rather than silently skipping. Pins are per `(host, port)` in their own table, never on `Credential.config`. → [narrative-12-24.md#rule-21](narrative-12-24.md#rule-21)

22. **The Sources column is `location || learnedLocation`, and which source supplies the learned half is operator-ordered** — priority lives in the `assetSourcePriority` Setting and feeds the **projection**, not just rendering (the column's filter, sort, "behind FortiGate X" criteria and Device Map narrowing all read `learnedLocation`). The contributor catalogue is `utils/assetSourceLocation.ts`: **field** contributors carry a real location string, **label** contributors contribute their own name. Propagation is pull-based and **not retroactive**. The same order decides the **merge modal's** per-field winner defaults — an unranked kind ranks LAST, "an empty value never overwrites one" outranks the order in both directions, and for Type the `other` catch-all counts as empty (`isGenericAssetType`) on every merge path. Invariant: **a source blob may never be built from the projection's own output.** → [narrative-12-24.md#rule-22](narrative-12-24.md#rule-22)

23. **Who owns an IP and how the gate hands it out are two facts, not one** — `Reservation.sourceType` answers ownership; `Reservation.dhcpBinding` (`null` | `"lease"` | `"reservation"`) answers how the gate serves it. Phase 5 records the binding via the pure `decideInfraDhcpBinding`, writing only on change, and deliberately **never flips `sourceType`, never stamps `expiresAt`**, and fills `macAddress` only from the lease entry. A `"lease"` row is operator-takeover-able exactly like a `dhcp_lease` (`isSupersedableByCreate`); `"reservation"` and `null` stay authoritative. **A managed device that goes away gives its address back** (`releaseInfraReservationsForAssets` on decommission — never on "no longer discovered"), with a 6h reconcile as backstop. Polaris writing the binding itself is double-gated (`pushReservations` + `autoReserveFortinetInfra`, both default off). → [narrative-12-24.md#rule-23](narrative-12-24.md#rule-23)

24. **Alert on the device's own alarm bit before inventing a threshold for it** — **`hwSensorAlarm`** reads `AssetHardwareSensorSample.alarmStatus`, the per-sensor bit the collectors already write; **`customStateValue`** is for status OIDs Polaris does NOT already collect, and is not the answer for Fortinet hardware sensors. **Absence is never zero**: `alarmStatusToFlag` returns `0 | 1 | null` and the engine excludes null in SQL; `snmpVbToNumber` returns `null` for an absent or empty varbind, never 0; ENTITY-SENSOR-MIB's `unavailable(2)` maps to null, an unrecognized non-empty status to 1. **An absent reading is not an absent DIMENSION either**: an interface state field takes the newest sample row that CARRIES it (`interfaceStateSeries` / `interfaceSampleCarries` in `notificationEngine`), never `group[0]`, and unreadable rows leave `Reading.series`, so a collection gap neither counts toward a poll-counted hold nor breaks its run. At the collector, only a walk that ANSWERED may be cached as "no PSE" (`poeWalkOutcome`). → [narrative-12-24.md#rule-24](narrative-12-24.md#rule-24)


25. **An alert you can't acknowledge from where you read it isn't really acknowledgeable — and who acknowledged it is a session, not a link** — acknowledgement reaches in-app, email and web push through ONE URL, `/alert-ack.html?id=<notificationId>`, an ordinary logged-in page: an unauthenticated reader signs in first and returns via `utils/loginRedirect.ts` (the `polaris_next` cookie AND the SAML RelayState, because no single carrier crosses all five login paths), and identity comes from the session. **The email is one message, full stop**: `expandDeliveries` substitutes `{ack}` ONCE per alert and writes ONE delivery row per notify action whose `target` is the whole To line; nothing about a reader — acknowledge capability or timezone — splits a send (the body renders in the INSTALL's zone and names it, `{time.zone}`). **Every recipient gets the button**; `alerts:write` is enforced by the acknowledge route and the page (gated `alerts:read`) reports the refusal. PUSH alone omits `ackUrl` for a role holding `alerts` below `write`. **The tray carries at most TWO actions**, sliced from Acknowledge → Open device → Ignore (Ignore sends nothing). **Loading is a GET, acknowledging a POST.** A push Acknowledge OPENS the page. **An alert that is OVER carries no button**: the three all-clear sends pass `noAck`, which blanks `{ack}` and stamps `meta.noAck`. `GET /alerts/:id` answers 404, not 403, outside the caller's region scope — and an admin-equivalent caller (`users` + `roles` at fullwrite) has NO region scope on the alert reads at all, because the widget and asset tab that open the card are unscoped and the POST never was; `requireAckNote` is enforced in `acknowledgeNotifications`, a batch refused whole. Retired: `NotificationAckToken`, `utils/ackToken.ts`, `/ack/:token`, `planComposedEmails`, `ackCapabilityByAddress`, `splitAckVariants`. → [narrative-25-35.md#rule-25](narrative-25-35.md#rule-25)

26. **A generated MAC is a placeholder until the network proves otherwise** — the `reservationMacPlaceholder` prefix (Setting, default `02:0F:5E`) is **the only marker** that a stored MAC is synthetic; there is deliberately no boolean column, because the prefix is visible on the gate's own reserved-address table. `normalizePlaceholderPrefix` (`utils/mac.ts`) **rejects any prefix that isn't locally-administered unicast**, so no factory MAC can fall inside the placeholder space. Adoption (`placeholderMacAdoptionService`, Phase 7.7, double-gated on `pushReservations` + `adoptDiscoveredMac`, both default off) swaps in the real MAC on **ARP-table and device-inventory evidence only**, behind five guards, device-first and read-back-verified. Changing the prefix is not retroactive in either direction. → [narrative-25-35.md#rule-26](narrative-25-35.md#rule-26)

27. **A logo is picked by theme; a name is text only when the picture doesn't already say it** — the shipped art is theme-paired, so painting the wrong variant makes the logo *disappear* rather than look off; the variant is chosen by theme **FAMILY, never by id** (three selectable themes plus a transit waypoint, two sets of art), and **`public/js/brand-logo.js` is the single decider** for all four surfaces (desktop login, mobile login, sidebar, Customization preview). The two variants of a pair are normalized to one geometry, so a theme flip moves nothing. The **Application Name is a caption for a custom logo only** — `showName` is false whenever the shipped wordmark is in play, so `appName` may be stored empty. Placement is per surface (`logoOnLogin` / `logoOnSidebar`); the accent composite renders **server-side** so geometry can't drift. → [narrative-25-35.md#rule-27](narrative-25-35.md#rule-27)

28. **The Windows build is the authority; the product name is not** — `ProductName` still reads "Windows 10 Pro" on every Windows 11 client, so AD, Intune/Entra and the agent are all equally wrong and no projection priority can fix it. `normalizeWindowsOs` (`src/utils/osNormalize.ts`) derives the **family from the build via a threshold** (`>= 22000 ⇒ Windows 11`, never goes stale) and the **release from a table** (an unlisted build keeps its raw `osVersion` rather than being guessed at). **Windows Server is excluded entirely** — build 26100 is both Windows 11 24H2 and Server 2025. Applied at **write** time (projection + the `db.ts` Asset hooks) because filters, sorts, exports and scope conditions read the stored columns; it is idempotent and reads no row. Not retroactive. → [narrative-25-35.md#rule-28](narrative-25-35.md#rule-28)

29. **A miss taken while the device is DOWN is the outage, not the link; everything else counts** — `probeLossPct` is the one metric whose input is FAILED probes, so it is the one that can raise a second alert about an outage `monitorStatus == down` already owns. (a) The ratio is plainly failed/total over the window — no anchor, no trimming; `Asset.recoveryStartedAt` is dormant (`polaris-domain-model` → dormant-columns.md). (b) **It counts PACKETS where it can**: an asset with ICMP burst rows (`packetsSent` / `packetsReceived`) is measured from those sums and its poll rows are left out; an asset with none falls back to the row ratio. (c) **Only an answering device reports loss** (`assetIsAnsweringProbes`: `up` and `warning`). (d) **A reading at or above the automation's `ignoreAtOrAbove` ceiling is not a reading** (default 100; Polaris's own baseline rule opts out at 90). (e) **Both gates CLEAR, never freeze** (`notification.superseded`, reason `device-down` / `reading-saturated`). (f) **`windowSec` IS the reading**; `forDurationSec` is a separate optional sustain. (h) **The unit of exclusion is the RUN**: every maximal stretch of consecutive failures holding an `AssetMonitorSample.assetDown`-stamped row is dropped whole, onset included (`probeLossQuery`'s `runId` / `runOutage` window functions, mirrored by `alertChartService.outageRunFailures` into `engineRatioPct`). (g) The email chart's `ratioPct` counts every countable probe and may read higher than the alert that fired; `readMonitorHistory.stats.packetLossRate` is a different number and unchanged. → [narrative-25-35.md#rule-29](narrative-25-35.md#rule-29)
