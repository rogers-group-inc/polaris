# Business rule 200 — full narrative

<a id="rule-200"></a>

## Rule 200 — A source that no longer finds its device says Missing on the Sources tab, and saying so changes nothing else

**The ask (2026-11-24, owner).** "What happens when a previously discovered asset in Entra ID or AD is deleted from AD or Entra ID?" — and then: "can the sources page for assets that were once discovered by those, update to indicate that they are no longer found by those sources?" Scope: every source with a disappearance check, kept indefinitely, and "I assumed the sources tab would just be updated to say Missing instead of Enabled." The card was designed on a canvas first and approved as drawn: the state badge reads **Missing** (`badge-expired`, amber — distinct from the red Disabled), the meta line leads with "Missing since <date>", the observed values stay, dimmed under "Last known values. Not found in <integration>'s full reads since <date>.", and the "Reported state by source" roll-up gains a Missing line.

**What the tab said before.** Two silences, depending on a toggle. With rule 70's `decommissionMissing` OFF (the default), the directory sweep returned before reading anything: a deleted computer object's `ad` row lingered with its last observed blob and an `Enabled` badge, indistinguishable from a live source except for a "Synced" date that stopped moving. With it ON — and always for vCenter and the hypervisor platforms — the row was deleted, so the card simply vanished, and the only trace was the `asset.*.decommissioned` Event. Neither told the operator "this system used to report the device and no longer does". The FortiGate roster sweeps (Phase 2a / 2b) decommission switches, APs and gates without touching their source rows at all, so their cards also went on reading Connected / Online from the last read.

**Why two shapes rather than one column.** The obvious design is one column, `missingSince`, and never deleting rows. It was rejected because roughly sixty readers treat "an AssetSource row exists" as "this source claims the device": the projection, the vCenter / hypervisor "no claim left → decommission" test, the integration-detach "nothing else reports it" test, the hostname-collision "untagged" test, the ghost-merge "authoritative source" test, identity matching, the merge dialog's ranking. Keeping rows that a sweep deletes today would change every one of those answers, and each would need its own `missingSince: null` filter to stay correct. So the rule keeps the existing semantics exactly and adds information beside them:

- Where a row **already stays** (sweep off, Fortinet roster), it gains a stamp. Those rows always counted everywhere; they still do. Nothing new is claimed.
- Where a row **is already deleted**, it is still deleted, after a copy goes to `AssetSourceRetired`. Nothing reads that table but the Sources tab, so no claim, match or decommission test can see it.

**The sweep now runs with the toggle off.** Rule 70's narrative explained why an OFF sweep left stale rows alone: "deleting them is the same judgement wearing a smaller hat". Stamping is not deleting — the row still counts — so the OFF pass now runs behind every guard rule 70 defines (a scoped / cancelled / capped / empty read, the raw pre-filter identifier set, the scale guard) and only stamps. A read too suspect to decommission on is too suspect to call a device missing on, so the guards apply unchanged; when one fires with the toggle off the pass is silent, as it was. With the toggle ON, a row stamped during an earlier OFF period is judged like any other gone row — exactly what would have happened to it had the toggle been on all along — and its retired copy keeps the ORIGINAL stamp, the day it first went missing, not the day the sweep acted.

**Re-appearance.** A device that comes back clears its stamp: the directory and Generic API sweeps clear every stamped row whose identity is present in the raw read (a filtered-out device is present, so a filter edit never leaves a false Missing), and the two Fortinet infra upserts write `missingSince: null`. A retired copy is never edited; it is hidden while a live row with its `(sourceKind, externalId)` exists — on this asset or another, since a device that returns may be matched to a fresh asset — and replaced if the identity is retired again, so there is at most one copy per identity.

**Kept indefinitely.** The owner chose no expiry. The table is bounded anyway (rule 158's concern): one row per identity, cascade-deleted with its asset, carried to the survivor by a merge (`absorbAssetRelations`). The ghost-merge path (`assetGhostMergeService`) deletes the ghost's live rows as placeholders and lets its copies cascade with it — those were never authoritative.

**What deliberately does not see it.** Rule 199's Assets-list Sources column counts live rows only. A stamped live row is counted there (it is still a source row, and the tab shows it); a retired copy is not — it is a record of a source that LEFT, and counting it would make "N sources" and the `sources` filter claim a source the asset no longer has. The merge dialog filters copies out of its ranking for the same reason, and a copy can never be split (it is not an `AssetSource`).

### Rule 200 — the invariant as stated in full

Every disappearance sweep marks instead of forgetting. Live rows (rule 70 / 70(a) / Generic API with the sweep off; the FortiGate roster sweeps) get `AssetSource.missingSince`, first time kept, cleared when the source reads the device again. Rows a sweep deletes (rule 70 on, vCenter, Unraid / TrueNAS / Proxmox, Generic API on) are copied to `AssetSourceRetired` first, one per identity. Only the Sources tab reads either, as `state: "missing"`; nothing that decides projection, claims, matching or decommissioning does.
