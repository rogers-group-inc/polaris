# Business rule 198 — full narrative

<a id="rule-198"></a>

## Rule 198 — A gate's OS fingerprint is a source claim, never an asset write; (a) a review card whose device is already linked to its asset is closed

**The report (2026-11-24, prod).** An Azure Arc-enrolled RHEL 8.10 server on Supermicro hardware had four sources: Entra ID and Intune (`Linux` / `8.10`), the FortiManager's detected-device inventory (`Linux` / `8.10`), and Azure Arc (`Red Hat Enterprise Linux 8.10 (Ootpa)` / kernel `4.18.0-553.125.1.el8_10.x86_64`). The operator saw the OS and OS Version "keep overwriting each other", and no Event ever recorded the change. An Arc hostname-collision card was also still pending, its "Existing asset" column showing `Linux` / `8.10`.

**Cause 1 — Phase 7 wrote the fingerprint first and asked the projection afterwards.** `syncDeviceInventory` wrote the row's `osVersion` onto every endpoint it matched, every run ("set-always"), and `os` when the asset had none. Phase 11 (`applyEndpointProjection`) re-projected the asset from all its sources and put Arc's kernel string back, since Arc outranks Intune, Entra and `fortigate-endpoint` in `OS_VERSION_RULES`. Between the two phases — minutes on a large FortiManager — the asset read `8.10`. The change-event baseline is taken at first touch and diffed at the end of the run, so the round trip netted to nothing and was never logged. The design dates from the Phase 3b cutover, when Phase 11 was added as a corrective pass precisely because Phase 7's write was wrong for MDM-owned assets ("Intune's `10.0.19045` overwritten by FortiOS's coarser `10.0` on every device-inventory pass"). The correction fixed where the run ended, not what the asset showed during it.

**Cause 2 — the source blob echoed the asset.** `buildFortigateEndpointObservedBlob` built the `fortigate-endpoint` row from the asset row itself. The row only "said" `8.10` because Phase 7 had just written `8.10` to the asset. Removing the write alone would have made the row record whatever the projection last chose — Arc's RHEL string — and a FortiGate-only fleet would have lost its OS entirely.

**What the rule does.** Phase 7 stages the row's `os` / `osVersion` per asset in a run-scoped `Map` (`inventoryOsByAsset`, last non-empty value per field when several gates report one client) and writes neither. Phase 10 passes the staged value to `upsertFortigateEndpointSource`; the blob records the fingerprint, else what the row said last time (the row's own prior `observed`, only when it belonged to this asset), else — for a first stamp with no fingerprint — the asset's value, as before. Phase 11 projects as it always did. The result: the asset shows Arc's / Intune's / the agent's value throughout the run, a FortiGate-only endpoint still gets the gate's fingerprint (from Phase 11, a few phases later in the same run), and the `fortigate-endpoint` row on the Sources tab now records what the gate actually said.

**The no-MAC exception.** Phase 10 keys the row on the asset's MAC and skips an asset without one. An inventory row that matched an asset with no MAC, and carried none itself, would stage a fingerprint nothing ever reads, so for that asset Phase 7 keeps its old direct write (`os` when empty, `osVersion` always). Such a row is matched by serial-hostname or address, never a DHCP-lease hostname (rule 91(f)), so the case is rare.

**What did not change.** Fortinet infrastructure stages and writes nothing (its firmware comes from its own discovery loop; prod 2026-07). A refused hostname-only match (rule 91(b)) stages nothing. Device-type inference (rule 164) still reads the row's OS facts. Phase 7's new-asset create path still writes the row's OS: the new asset has no other source, and the projection over its one `fortigate-endpoint` row yields the same value.

**Cause 3 and clause (a) — a card whose question had been answered stayed open.** Pending identity cards are only closed by an operator or by rule 91(a)'s refusal sweep. When the device was linked to the card's asset some other way — an earlier card's Accept, Arc's serial or vmUuid cross-link, an operator merge — the card stayed pending, kept refreshing a stale snapshot, and offered an Accept that would re-stamp the link and overwrite OS and identity fields from that snapshot (Accept defaults `os` / `osVersion` to the proposed value). `dismissLinkedIdentityConflicts` runs at the start of each discovery run, beside `dismissRefusedHostnameConflicts`, over the integration's pending `untagged-collision` / `duplicate-registration` / `mac-collision` cards. It looks up the `(sourceKind, externalId)` Accept would stamp — `conflictIdentityKey`, the same casing rules — and closes a card whose link is on the card's own asset as `accepted` by `system`, one `conflict.accepted` Event each with `reason: "already-linked"`. A link on a different asset is the duplicate-asset question (the `bothAssetsExist` flavour) and is left for the operator; `bothAssetsExist` cards are skipped outright.

**The card label (no rule — a display fix in the same change).** The asset-conflict card named every source other than vCenter and AD "Entra ID" / "Entra / Intune", so the Arc card above read as an Entra card. `listConflicts` now attaches `source` (`assetConflictSourceDescriptor`: `kind`, `platform`, `device`, `column`) to each identity card from the same `conflictSourceFor` Accept uses, and `public/js/events.js` reads it, falling back to the old guess for a response without it.

**Scale.** Phase 7 adds one `Map` entry per matched endpoint — less work than the write it replaces, and the flush stages fewer fields. Phase 10 reads no more rows (the prior row was already preloaded). The sweep is two reads per run over the pending cards (a handful), however large the fleet.

**Rejected.**
- *Keep the write, but skip it when a higher-ranked source exists.* It re-implements the projection's ranking inside Phase 7, and the two would drift.
- *Keep writing, and only stop the netted change from being silent.* It records the flip instead of removing it.
- *Leave the blob as an echo and read the fingerprint from a new observed key.* The Sources tab would keep showing the projection's value as the gate's claim — the provenance bug behind cause 2.
- *Delete already-answered cards.* The card is the record of the question; closing it `accepted` with an Event keeps the history the Events page and the resolved-card view read.

Pinned by `tests/unit/deviceInventory.test.ts` (staged not written, last value wins, the no-MAC write, infra and refused matches stage nothing), `tests/unit/endpointSources.test.ts` (the fingerprint reaches the upsert), `tests/unit/fortigateEndpointOsFingerprint.test.ts` (the blob's precedence and the reported source set projecting to Arc's values) and `tests/unit/conflictResolutionService.test.ts` (the sweep's four outcomes and the descriptor).
