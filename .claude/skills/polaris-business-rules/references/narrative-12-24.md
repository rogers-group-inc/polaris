## Rule 12 — `Asset.lastSeen` means verified network presence

written ONLY through `bumpLastSeen()` in `src/utils/assetInvariants.ts` (no-regress: it only advances, and stamps `Asset.lastSeenSource` provenance alongside). Valid evidence: live DHCP lease (`seenLeased`), FortiGate device-inventory sighting (the FortiGate's own per-client `last_seen` timestamp — never discovery-run time), connected FortiSwitch/FortiAP, firewall answering discovery, agent heartbeat, answering monitor probe, presence-verification ping, operator-resolved conflict. **Polling is authoritative for monitored assets**: when `Asset.monitored === true`, the monitor probe is the sole authority for presence — `bumpLastSeen` refuses the discovery-origin sources (`discovery`, `device-inventory`, `dhcp-lease`, `vcenter` — a powered-on VM / connected ESXi host reported at scrape time — and `arc`) so they can't advance `lastSeen` past what polling established. A successful probe stamps `lastSeen = now, lastSeenSource = "probe"` (written through the `probePatchBuffer` bulk-update in `recordProbeResult`, not a Prisma write); a failed probe writes nothing, so a monitored-but-down device's `lastSeen` freezes at its last successful poll even if a FortiGate still reports it `is_online` in device inventory. Active/operator sources (`probe`, `agent`, `ping`, `conflict-*`) are never deferred. (Repointing a managed FortiSwitch/FortiAP's response-time stream to poll "via parent FortiGate" / the controller rather than direct SNMP is the fix when the device is genuinely up but unpollable directly.) **Device inventory outranks the DHCP lease** (unmonitored assets): when a MAC appears in this cycle's device inventory, the lease path skips its bump so the inventory's real `last_seen`/`is_online` wins — a bound-but-idle lease (device leased an IP then went home) must not stamp `now`. Lease-only assets keep the lease bump. **Fortinet-discovery-owned infra never takes client-sighting presence**: firewall/switch/access_point assets carrying a `fortinetTopology` stamp skip BOTH the dhcp-lease and device-inventory bumps — their presence comes only from their own discovery loop (gated on answered-live / connected / `!offline`) and the probe, so an offline-in-FMG gate sighted as a DHCP client of another gate (lingering lease binding, stale cached `is_online`) can't keep freshening its lastSeen; the fortigate-firewall AssetSource row's lastSeen likewise freezes on offline cached-CMDB pulls. Operator-typed non-Fortinet "firewall"/"switch" assets (no topology stamp) keep the endpoint-style bumps. Directory timestamps (Entra `lastSyncDateTime`, AD `lastLogonTimestamp`) deliberately do NOT write it — they stay on the `AssetSource` rows and surface as "Last Directory Activity" in the slide-over; the Entra duplicate-registration tiebreaker compares those directory timestamps, not `lastSeen`. (vCenter and Azure Arc are the exceptions among discovery integrations: vCenter's `power_state`/`connection_state` and Arc's `properties.status === "Connected"` are real-time truth READ AT SCRAPE TIME — categorically different from the stored historical timestamps directory sources carry — so unmonitored VMs/hosts/Arc machines DO get a `"vcenter"` / `"arc"`-sourced bump; both are in the deferred set, so polling stays authoritative once monitoring is on. For Arc the evidence timestamp is always RUN TIME, never `properties.lastStatusChange`, which records when the status last CHANGED and so is 90 days stale on a machine that has been Connected for 90 days.) Presence evidence also gates status resurrection: a remembered-but-offline inventory/switch/AP entry must not flip a `decommissioned` asset back to `active`. `decommissionStaleAssets` consults directory/agent `AssetSource.lastSeen` as a veto so cloud-only laptops don't age out. Never write `Asset.lastSeen` directly — route through `bumpLastSeen` (or the probe patch on the monitor hot path).

## Rule 13 — SD-WAN monitoring is opt-in, read-only, FortiOS-only

Gated per-integration by `Integration.config.pullSdwan` (default false), on both the FortiManager and standalone FortiGate integrations. When on, the heavy/system-info pass for FortiGate firewalls also calls `collectSdwanFortinet` (`/api/v2/monitor/virtual-wan/health-check` + `/api/v2/cmdb/system/sdwan`). It writes the `AssetPerfSlaSample` **SLA-metrics time-series** (latency/jitter/loss per WAN member — append-only, rolled up + retained), and refreshes the `AssetSdwanRule` **current-state** table (one row per rule, delete-replaced per scrape via `persistSdwanRules` — no history/timeline). Never writes to the device. The asset modal's **SD-WAN** tab appears only for FortiGate firewalls with data. The runtime "selected route" per rule is **inferred** (first candidate member up in priority order) when FortiOS doesn't expose it over REST — clearly labeled in the UI; verify the exact endpoint/field shapes on a real FortiOS 7.x device. Rules configured for zone-based selection (`priority-zone`) carry no interface members — `parseSdwanRules` resolves their candidates from the preferred zones' member interfaces and records the zones in `priorityZones`, so the UI lists each zone's members (grouped) instead of an empty cell.

## Rule 14 — Description sync is opt-in and Polaris-primary

Gated per-integration by `Integration.config.syncDescriptions` (default false), on both the FortiManager and standalone FortiGate integrations (Description Sync tab). **A non-empty Polaris value always wins**: pushed to the device on save and re-asserted by every reconcile, so device-side edits are overwritten (audited with the value they replaced — `asset.description.pushed` `overwroteDeviceValue` detail). **An empty Polaris field adopts** the device value (`asset.description.adopted` / `asset.interface.description.adopted` Events) — clearing the Polaris description is how an operator takes the device's value. No conflict state exists (the earlier newest-edit-wins three-way merge was retired 2026-07; legacy `conflict` sync-state rows resolve on the next reconcile by pushing the Polaris value). `Asset.descriptionSync.value` / `AssetInterfaceOverride.syncedValue` persist the last synced value (bookkeeping for the FMG-mirror device-agrees check + the UI badge, not a merge base). A device-side *clear* never removes a Polaris value (the push re-asserts it). `decideDescriptionSync(polaris, device)` is the pure decision. Surfaces: interface comments (`AssetInterfaceOverride`) ↔ FortiGate `system/interface` description / FortiSwitch port description; `Asset.description` ↔ FortiGate `system/global` alias / FortiSwitch managed-switch description / FortiAP wtp **`location`** (AP Manager's field — wtp `comment` doesn't exist in FMG's copy, so installs strip it; confirmed on a live FMG 7.x). All device I/O rides `reservationPushService`'s Transport (works in FMG proxy AND bypass/direct modes + standalone). Runs at save time (always pushes, best-effort, never blocks the Polaris write) plus a Phase 13.7 discovery reconcile that re-pushes drift / adopts into empty fields and is the retry path — no queue. Clearing a Polaris value is local-only (no device-side delete). Push verifies by read-back; transport errors never mutate sync state. FortiOS field shapes (alias cap, ports child-table PUT) are flagged verify-on-real-device in `descriptionSyncService.ts`; the wtp `location` cap is confirmed at 35 chars. **FMG central management:** each FMG discovery start detects whether the ADOM centrally manages FortiAPs / FortiSwitches (`detectCentralManagement` → stamped on `Integration.config.centralManagement`, rendered on the integration card after the FMG Proxy row); for a centrally-managed class, device-side description pushes are additionally **mirrored into FMG's database** — wtp `location` into the controller FortiGate's device DB (`/pm/config/device/<fgt>/vdom/root/wireless-controller/wtp`, where AP Manager's per-AP rows live), switch descriptions into the ADOM-level `obj/fsp/managed-switch` table — via plain JSON-RPC `update` (never `set`, never an install) so the next install doesn't revert them, and the reconcile batch-heals FMG-side drift for values the device already agrees on. See polaris-change-impact → services (the `services/descriptionSyncService.ts` entry).

## Rule 15 — Location codes ride device descriptions; notes are operator-only

FortiSwitch/FortiAP admin descriptions (managed-switch CMDB `description` / wtp `location` with `comment` fallback — `location` is the sync surface and the only field present in FMG's copy under central AP management) are captured on every FMG + standalone FortiGate discovery cycle into `fortinetTopology.deviceDescription` (`buildDeviceDescriptionStamp` in `discoveryEngine.ts`), and `a:`(area)/`b:`(building)/`f:`(floor)/`r:`(room)/`jb:`(junction box) codes are parsed from them server-side by `src/utils/locationCodes.ts` (effective codes: the `Asset.description`'s codes when it carries any — EXCLUSIVELY, no per-key fall-through, so removing a code from the description removes the node from that group even while the device copy lags a sync cycle — else the device description's; `Asset.notes` is deliberately NOT a source, notes never inform the topology map) to drive Device Map grouping hulls, row clustering, and floor views. **Discovery never writes `Asset.notes` on an existing asset** (the former description→notes mirror and its `notesSyncedFrom` provenance were removed 2026-07); the only discovery-authored notes content is the one-time `Auto-discovered from FortiGate …` boilerplate stamped at asset creation. Interplay with rule 14: with `syncDescriptions` ON, codes maintained in the Polaris description push to the device (Polaris-primary); device-only codes show through only while the Polaris description carries no codes at all.

## Rule 16 — Maintenance windows pause everything; status flips are scheduler-managed

> The notification half of this rule is now one clause of a wider gate — see **[rule 37](#rule-37)**: `assetCanTrigger` tests `monitored` AND this rule's suppression, and every trigger path (the event/change tail included) applies it. Read both before changing either; the suppression semantics below are unchanged.

While a `MaintenanceSchedule` window is active for a monitored asset, the `maintenanceScheduler` holds `Asset.status="maintenance"` with the prior status parked in `maintenanceReturnStatus` (restored when the last window closes; a manually-set "maintenance" is parked verbatim so exit can't loop). **Parking can only ever hold `active` now**, and that is a consequence nobody costed at the time: business rule 10's unmonitorable set grew to cover `storage` and `quarantined` in 2026-08, `decommissioned` and `disabled` were always in it, and `maintenance` is the window itself — so targeting's `∩ monitored` leaves exactly one status a maintained asset can arrive in. Two integration fixtures here entered from `storage` and `quarantined` to prove parking round-trips a non-trivial value; the widening clamped both to `monitored=false` at create time, they stopped being targets, and this file went red on main for three pushes. The product answer that settles it: a window on a shelved or quarantined device would be a no-op, because a quarantined device already fails every probe by design and a shelved one is not polled at all — there is nothing for a window to silence. `tests/integration/maintenanceSchedules.test.ts` pins both halves (parking from `active`; an unmonitorable status is never entered). `status="maintenance"` stops ALL server-driven polling (`MONITOR_CANDIDATE_WHERE` in `monitoringService` — shared by both the cursor pass and the pg-boss publisher — excludes it; presence-verification pings and `decommissionStaleAssets` skip it too; agent pushes and the operator's explicit Poll Now still work), makes the asset count as DOWN for child dependency suppression (`evaluateSuppression` treats it like an active `dependencyTestUntil` overlay — unless the schedule's `suppressChildren` toggle is off, in which case suppression ignores the maintenance status and the asset evaluates by its frozen `monitorStatus`, so dependents keep monitoring/alerting; OR-ed across an asset's open windows, surfaced as the "Mark dependent devices as down" checkbox on the builder + both ad-hoc paths), and silences notifications for the asset AND for every dependency-suppressed asset (`isSuppressedForNotifications` in `notificationEngine`: readings dropped, `pending` state rows reset so a still-bad condition re-earns its debounce post-window, `firing` rows retired by the suppression sweep below; escalation sends pause). **Discovery/system writers must never write status over a maintenance asset** (Entra/AD sync, FortiSwitch state sync, lease-presence flip, and the `lastSeen`-aging `decommissionStaleAssets` job are guarded; the reconcile self-heals anything missed by re-flipping and absorbing the clobbered value into `maintenanceReturnStatus`). **Deletion-at-source is the one carve-out:** the discovery decommission sweeps (Phase 2a firewalls + its controller cascade onto their managed FortiSwitches/FortiAPs / Phase 2b FortiSwitches+FortiAPs) DO judge maintenance assets and call `releaseAssetsForDecommission` — window closed `endReason="decommissioned"`, parked status cleared, `status="decommissioned"` written in the same transaction (so the reconcile can't re-enter or self-heal-reflip; the `monitored=false` clamp keeps it out of the target set, and the spent ad-hoc schedule self-deletes). Roster/inventory absence is config truth, not reachability (an offline device stays in the FMG roster; a powered-off switch/AP stays CMDB-protected), so a device deleted mid-window must not sit in maintenance and then be restored to `"active"`. An operator status write moving OFF "maintenance" wins: the assets PUT route calls `operatorReleaseAsset` first (windows closed `endReason="operator"`, which suppresses scheduler re-entry for that occurrence). Open `AssetMaintenanceWindow` rows are the restart-safe source of truth; closed rows feed the labeled chart bands. Dashboard surfaces treat maintenance as its own state, never an outage: the NOC feeds (`nocDashboardService`, mirrored by `/summary` monitorAlerts) exclude `status="maintenance"` from every down/warning/stale list — the frozen `monitorStatus` is not live state — and bucket it as `statusCounts.maintenance`; the Status Map dot and Status Summary "Maint" tile paint it purple (matching the assets-page pill). Events: `maintenance.entered` / `maintenance.exited` / `maintenance_schedule.*`.

**A window opening on top of a live alert now ENDS it (2026-08-28).** Suppression used to freeze `firing` rows so that exiting maintenance couldn't double-fire an alert that was already active. What that produced in practice was announced downtime with a red row sitting beside it for the whole window and *nothing able to end it*: the readings that would have recovered the alert are precisely what maintenance stops collecting, so a frozen alert could only outlive the window it was announced for, and an operator looking at the board during a planned change saw exactly the noise the window exists to remove. `clearSuppressedAlerts` (in `notificationService`, the lifecycle side, not the engine) soft-clears every ACTIVE alert whose asset is suppressed — `clearedBy="system:maintenance"` or `"system:dependency-suppressed"` (maintenance wins when an asset is both: it is the downtime the operator announced), one `notification.suppressed` Event each — and releases the `NotificationRuleState` row that owned it, since a `firing` key pointing at a dead notification can never fire again. Three decisions carry it. **It is a handoff, not a recovery** — the same contract as the precedence carve-out (rule 18) and the packet-loss/device-down clear (rule 29): NO reset actions run, because nothing recovered and mailing "resolved" about a device nobody is polling would be a lie; the Event is the audit trail. **The condition re-earns its debounce**: a device still bad when the window closes fires a NEW alert rather than resurrecting the old one, which is the honest reading — the old alert's evidence is a window old, and the pending rows were already being reset on exactly that reasoning. **And it sweeps `Notification` rows, not state rows**, which is why it does not live in the engine's per-rule loops: event and change alerts are created by the event tail's `createMany` with no `NotificationRuleState` at all, so a state-machine-side clear would have missed the automations most likely to have fired on the way into a window (`agent.disconnected`, a firmware change, a discovery failure). Two callers: the `maintenanceScheduler`'s own entering edge, so an ad-hoc "enter maintenance now" clears the board while the operator is still looking at it, and the 60s `evaluateNotificationRules` tick ahead of the rules — the safety net, and the only thing that catches **dependency** suppression, whose flag is owned by the dependency reconciler and has no edge of its own here. Both calls are best-effort: a failed sweep must never cost the fleet a tick of evaluation or leave a status flip half-applied.

**A day is a LIST of hour ranges (2026-09-06).** The recurrence used to carry one `startTime`/`endTime` pair for the whole schedule, which said "these days, that window" and could say nothing else. Two things operators kept asking for fall outside it: different hours on different days (patching runs at 22:00 on weeknights but the shop is available all day Saturday), and more than one window on a day (a 09:00–11:00 change and a 14:00–16:00 one). The shape now states hours as `hours[]` — the ranges that apply to every matched day — with `hoursByDay[]` overriding individual days (daily/weekly only, keys within the day selector, an empty list meaning all day for that day). `resolveDayRanges(shape, dow)` is the ONE resolution order — the day's own hours, else `hours`, else the legacy pair, else all day — and it is what makes the change non-breaking: every row written before this reads exactly as it did, which matters more than usual here because `parseStoredShape` warns-and-SKIPS a schedule whose shape no longer validates, so a rejected legacy row would be a maintenance schedule that silently stopped running.



The consequence that reaches the rest of the system is that **a day produces zero or more occurrences, and each range is its own occurrence with its own start**. `occurrencesStartingOn` returns an array, `currentWindow` answers with the CONTAINING range rather than the day, `nextWindow` skips a range already over, and `expandOccurrences` caps on occurrences rather than days. That is not bookkeeping: the operator-release check compares the release time against `currentWindow(...).start`, so an operator who ends maintenance by hand during the 09:00 window stays released for that window and re-enters for the 14:00 one — behaviour a single range per day could not express at all.



Which is also why **two ranges on the SAME day may not overlap** (`overlapProblems`, refused at validation in the editor and at the API, naming both ranges). "22:00–06:00 and 23:00–01:00" is a mistyped end time every time, and two occurrences over one instant make "which occurrence is this" unanswerable for the release check and for the `AssetMaintenanceWindow` rows. Overlap ACROSS days is deliberately allowed, because it is not a mistake: "Mon–Fri 22:00–06:00 plus all day Saturday" has Friday's overnight range running into Saturday's all-day one, and that is the most ordinary schedule anyone writes. Where two occurrences do overlap, `currentWindow` returns the earliest-STARTING one that contains the instant — deterministic, but describing that range rather than the whole contiguous stretch, so the modal's "until" can read Saturday 06:00 on an asset that stays in maintenance all weekend.



The whole shape, its validator, its evaluator and its browser-side editor are shared with automation quiet time (business rule 44) rather than copied: `PolarisRecurrence` in `public/js/recurrence-editor.js` renders the seven day rows for both the Maintenance modal and the automations wizard, because two editors of one shape drift into saving two different things, and two summarisers into describing the same window two ways on two pages.

## Rule 17 — ARP presence evidence for stale reservations; the sweep is opt-in

Every FMG/standalone-FortiGate discovery cycle already reads each gate's ARP table; sync Phase 7.6 stamps `Reservation.lastSeenArp` (and clears `staleNotifiedAt`/`staleSnoozedUntil`, same re-arm semantics as a live lease) whenever the table binds an active dhcp_reservation's IP to its **reserved MAC** on the owning device — minutes-fresh L2 presence that keeps statically-configured / ICMP-silent devices (which never pull a lease) out of the stale list. `effectiveLastSignalMs` in `reservationStaleService` folds it in as a third real signal alongside `lastSeenLeased` and the correlated `Asset.lastSeen`. MAC match is required (a different MAC answering the reserved IP is not presence), matching is scoped per (fortigateDevice, ip) so overlapping RFC1918 subnets behind different gates can't cross-match, and absence of an ARP entry is NEVER negative evidence (reach depends on routing + firewall policy). The **ARP presence sweep** (`Integration.config.arpPresenceSweep`, DHCP Push tab, default off, FMG + standalone parity) additionally primes each gate's ARP cache right before its table read: `arpPrimeService` fires one fire-and-forget UDP datagram per reserved IP — per-gate targets only, paced batches, ~2s settle inside the FortiOS neighbor-cache GC window — so even quiet-but-live devices resolve into the table. Opt-in because the sweep is IDS-visible.

## Rule 18 — Automation precedence is same-trigger, most-specific-wins

Two automations "watch the same thing" iff their `triggerSignature` matches (asset_metric metric + dimensionFilter / asset_state field + dimensionFilter; host/event/change/composite are exempt, signature `null`). **`monitorStatus` is keyed differently and deliberately** (2026-08-25): by the compared **operator+value** and NOT by the dimensionFilter, because it is a single per-asset column with no reading dimensions — the only filter it can carry is a DEVICE filter, which narrows the asset set rather than the reading. So every `== down` automation lands in ONE group whatever its device filter (they must be able to carve each other out), while `== down` and `== warning` are correctly different things to watch. Two consequences: coverage is now tested as scope AND device filter (`peerCoversAsset` / `carveOutPeerCovers`, so a `hostname matches "core-"` peer only shadows the core switches), and this same group is what decides **whose missed-poll count governs each asset** — business rule 36's down-detection authority rides rule 18's ladder rather than inventing a second precedence system. Note a `monitorStatus == warning` rule no longer shadows a `== down` rule (they were one group before). Among same-signature automations, the more-specific one (higher `scopeRank` on the ladder all assets 0 < device type 1 < OS 2 < manufacturer 3 < model 4 < tag 5 < region 6 < subnet 7 < hostname 8; only positive rules count — negatives/none/notAll broaden; a `region:` tag outranks a plain tag; lifecycle status, assetId + **`interfaceName`** are OFF the ladder — an interface is a component of a device, not a statement of WHICH devices an automation is about, so "switches with a fortilink port" ties with "switches" rather than carving it up) **carves out** the assets it covers from every lower-rank one: `evaluateThresholdRule` drops those readings (no fire), clears any active alert (`notification.superseded`; maintenance clears its alerts too since 2026-08-28, under its own reason — rule 16), and resets pending debounce. Same-rank + same-signature ties both fire. Index built once per tick (`buildShadowIndex`), per-asset test reuses the pure `scopeMatchesAsset`. **A peer's scope may read facts the evaluated rule's scope never asked for**, and coverage is tested against the SAME asset rows the rule loaded: `interfaceName` is resolved out-of-band (`scopeInterfaceIndex`, since joining the interface inventory on a 60s tick is the 2000-asset anti-pattern), so the tick decorates those rows for every peer in the signature group before testing coverage. Leaving that out does not fail loudly — an unresolved leaf reads as "this device has no interfaces", which quietly makes an interface-filtered peer cover nothing (positive operator) or everything (negative one), i.e. a duplicate alert or a silenced one. Authoring-time preview (`previewRule`) warns both directions: `carveOut.carvesFrom` (this specific draft removes N devices from lower-rank automation X) + `carveOut.carvedOut`/per-match `excludedBy` (this general draft's devices already covered by more-specific Y).

## Rule 19 — Severity bands escalate one alert by value, each on its own clock

A numeric automation (asset_metric/host_metric) can stack `severityBands` on the base trigger: tier 0 = `rule.severity` at `trigger.threshold` for `trigger.forDurationSec`, each band a higher `{threshold, severity, operator?, forDurationSec?, actions, escalation}`. **Severities must strictly increase** tier-over-tier (`validateSeverityBands`; UI defaults a new tier one rank up + blocks lowering); tiers **share the base sampling** (aggregation / window / dimensionFilter) but may carry their own ordered `operator` and their own **sustained duration** (both fall back to the trigger's). The value is resolved once and compared to each tier; the **most-severe MET tier wins**, so per-tier thresholds need not be monotonic. **"Sustained for" is per tier, not per rule** — "loss > 5% for 30 min = warning, > 25% for 5 min = critical" is one automation, so a shared `conditionMetSince` can't express it: the engine keeps `NotificationRuleState.bandMetSince` (`{[severity]: epochMs}`, each tier's continuously-satisfied run, rewritten only when a tier enters or leaves) and takes the most-severe tier whose OWN run has outlasted its OWN duration (`resolveTierLadder` → `updateTierMetSince` → `sustainedSeverity`, all pure + unit-tested). Consequences that follow from that and are deliberate: a higher tier can fire before the base tier has served its time (each tier earns its own severity); a value climbing between bands never restarts the lower tier's run; a tier that drops out and returns restarts only ITS clock, so flapping into critical never sustains while a steady warning still fires. **De-escalation is immediate** (the lower tier's run is already old) and dropping below tier 0 clears every run. `severityForValue` remains the instantaneous tier-0 membership test; the alert is **one row per asset** whose severity climbs and eases in place. `bandNotify` policy governs delivery: `onIncrease` (default on) runs the entered band's actions; `onDecrease` (default off) runs the destination band's actions; `onResolved` (default on, below tier 0) runs the reuse-the-alert-or-dedicated resolved actions then clears. In the hysteresis dead band (auto reset + `clearThreshold`, value below tier 0 but above the clear line) the alert stays active but **eases to the base severity** — it must not park at a higher band the value no longer satisfies. Each band's own time-escalation is swept band-aware (`escalationChainsForSeverity` in notificationTypes — the band's level chain + its actions' per-action chains, with the empty-band fallback to the base actions mirrored; timers restart from `escalationState.bandSince`, stamped on every crossing). Value-bands (severity) and time-escalation (delivery tiers) are independent axes and coexist. **The BUILDER offers one hold, not one per tier (2026-08-28).** Everything above is the ENGINE's contract and is unchanged — `bandMetSince` is still per tier, a band's own `forDurationSec` is still honoured, and an API-authored ladder can still give each tier its own clock. What changed is what the wizard writes: it renders a single "Sustained for" on the trigger and every tier inherits it, because four holds were four clocks doing one job and the base tier's field (moved inside the base severity group so it would read as that tier's) made the shared hold look like a property of the lowest severity. A rule loaded with per-tier holds LOSES them on the next save from the wizard — deliberately, since the alternative is a rule behaving in a way nothing on screen states. An install that needs "warning for 30 min, critical for 5" writes it through the API. **Where that one hold SITS took two more passes (2026-08-31).** Moved out of the base severity group it came to rest between the first tier and the second and read as the first tier's own — the same misreading in a new place, a number directly above a block being read as belonging to it. It now lives back INSIDE the base severity block, below that block's conditions, and every added tier renders the same field again as a **disabled mirror** (`syncBandDurationMirrors`) carrying the trigger field's value and its label — "History (polls)" on a windowed ratio, "Measured over (polls)" on an aggregate, repainted live as the operator types and as a cadence answer lands. Each tier stating the count it will wait out is what makes "applies to every severity level" visible rather than asserted, and it is what lets the base tier hold the editable copy without that copy reading as the lowest severity's. A mirror hides itself when the trigger states no hold, or has no hold field at all (an all-down-detection tree), where an empty disabled box in each tier would read as a field each tier was meant to fill in. Two consequences follow from the hold now folding away with its block: `data-hold-off` marks a field the TRIGGER switched off so unfolding a severity block can't re-offer it (that is how a CPU automation once rendered a second "Sustained for" captioned about packet loss), and the mirrors read that attribute rather than the field's display, or folding the first tier would blank the number out of every tier below it. That same change recounted every hold and window in the builder in POLLS rather than minutes (see rule 30 for why a reading is the unit that decides anything), and the follow-up (2026-08-29) made the ENGINE count them, because a count the engine measured in seconds was still a wall-clock hold wearing a different label.

**What a hold means now.** A trigger states `forPolls` and a reset states `reset.sustainPolls`; where either is set it is the authority and the engine counts consecutive qualifying READINGS. `forDurationSec` / `sustainSec` remain written as the wall-clock mirror — they are what the sentences and the alert email read, and what sizes the sample window the engine has to fetch to SEE N readings (`lookbackMsFor`, twice the mirror, capped at 6 hours). Nothing is migrated: a rule that states only seconds keeps the old behaviour exactly, until it is re-saved from the builder (which shows a count and therefore stores one).

Sources split two ways, because they have to:

- A **series source** — every sample table, plus the Polaris host's own 30-second metrics — hands the engine its recent readings newest-first (`Reading.series`), and the run is the leading count of qualifying ones (`leadingRun`). Stateless, so it is exact whatever the engine's tick spacing is, and a device that stopped reporting has no readings to count rather than one stale sample re-counted every tick.
- A **current-state source** — the Asset columns (`monitorStatus`, `status`, `consecutiveFailures`, `dependencySuppressed`, `quarantined`), the delete-replaced SD-WAN rule table, the windowed-ratio metrics recomputed per tick, and a composite tree's own outcome — has no series at all, so the run lives on `NotificationRuleState.metRun` / `clearRun` and advances only when that stream's poll anchor moved (`advanceRun`; `lastMonitorAt` for the probe-backed fields, `lastSystemInfoAt` for SD-WAN, the newest leaf reading for a tree). Without that gate the 60-second engine tick would count five "polls" against a device polled every five minutes.

Three consequences worth stating. A run is **consecutive**: one reading back under the line zeroes it, however long it was — this is not the probe loop's leaky bucket (rule 30), which is counting misses outstanding rather than a condition holding. The runs are **zeroed whenever a row returns to `clear`**, or a stale `metRun` would let the next qualifying reading fire immediately and skip the hold. And a **band that states its own `forDurationSec` stays on the wall clock** (`resolveTierLadder` gives it no `forPolls`): per-tier counts would need a per-tier run map on the state row, for a shape the builder cannot produce — every tier that INHERITS the trigger's hold inherits its unit too.

The four failures this replaced, all of them the same bug wearing different clothes: a device that stopped reporting satisfied a hold on ONE reading (the 15-minute "find the latest sample" lookback re-presented it at every tick); a slow-cadence device fired on fewer readings than asked whenever a poll was late; a fast-cadence device could not fire faster than the 60-second tick however short its hold; and "must stay cleared for" had all three problems on the way back out.

## Rule 20 — Subnet writes serialize per block; secrets are encrypted at rest; a backup you cannot restore is not a backup

Three operability invariants added by the 2026-08 production-readiness remediation. (a) **Subnet overlap** (rules 1 + 2) is a check-then-insert, so it is only as strong as what serializes the two halves. Every subnet-creating path (`createSubnet`, `allocateNextSubnet`, `bulkAllocate`, the DHCP-discovery create in `discoveryEngine`) now goes through `createSubnetRowChecked` or `lockBlockForSubnetWrites` in `subnetService.ts`, which take a per-block `pg_advisory_xact_lock` BEFORE re-reading siblings; a UNIQUE index on `subnets (blockId, cidr)` is the backstop for the exact-duplicate case. `allocateNextSubnet` retries on a lost race rather than 409-ing, because the caller asked for "any free /N". There is deliberately no exclusion constraint for general overlap — stock PostgreSQL has no GiST-indexable `&&` for `inet`/`cidr`. **The same medicine now covers the `mapRegions` blob** (2026-08-25): every region create / update / delete is a read-modify-write of ONE JSON `Setting` value — load the whole array, change one element, write the whole array back — so two overlapping writers both read the same starting array and the second write silently discarded the first one's edit. That was not theoretical: the Device Map's edit mode saved every changed polygon at once with `Promise.all`, so dragging three regions and clicking Save reliably persisted only one while all three PUTs returned 200 and the toolbar reported "3 regions saved". `withRegionBlobLock` in `mapRegionService` takes a `pg_advisory_xact_lock` (classid `0x504c5255` "PLRU", the next in the PLRS/PLRT sequence) as the first statement of a transaction wrapping the read AND the write; the map now also saves sequentially, so N dirty polygons no longer park N requests on that lock each holding a DB connection. One lock for the whole blob, because the unit being rewritten IS the whole blob — a per-region lock would serialize nothing. Proven by `tests/integration/mapRegionConcurrentWrites.test.ts`, which needs a real database: a mocked Prisma makes the advisory lock a no-op and would pass either way. (b) **Secrets at rest**: the Prisma extension in `db.ts` seals/opens the secret-named string leaves of `Credential.config`, `Integration.config`, `NotificationChannel.config` and `Setting.value` (`utils/secretBox.ts` + `utils/configSecretFields.ts`). The extension is the enforcement seam precisely because several legacy route files still read those models with inline Prisma. **Sealing is per-model; OPENING is all-models**, because Prisma query extensions fire for top-level operations only — a per-model open hook never runs for a relation read like `asset.findUnique({ include: { monitorCredential: true } })`, which is how the monitor hot path loads every credential it polls with, how reservation push loads the FortiGate token, and how description sync loads its integration. So the open pass is its own `$extends` layer (`openNestedSecrets` over `$allModels.$allOperations`) that walks whole results, gated by a zero-allocation `containsSecretField` pre-scan and an `isWalkable` plain-object check so rebuilding a row can't turn its `Date` columns into `{}`. Sealing is a NO-OP without `POLARIS_SECRET_KEY`, and `openValue` never throws — a wrong key degrades to "this credential stopped authenticating", never to an exception on every monitor tick. Raw SQL bypasses the extension; the only raw reader of these columns (`monitorOverrideService`'s `integrations.config #>> '{…,addAsMonitored}'`) touches no secret field. (c) **Backup/restore** lives in `services/backupService.ts`: streamed end to end (never `execSync`/`readFileSync`/`gzipSync`), connection via libpq PG* env vars rather than argv, and the restore wrapped in `timescaledb_pre_restore()` / `timescaledb_post_restore()` in three separate psql sessions with post_restore in a `finally`. A failed pre-update backup ABORTS the update by default (`applyUpdate(password, allowWithoutBackup=false)`) — migrations are irreversible, so a silently-missing backup is the difference between a bad update and an unrecoverable one.

## Rule 21 — SSH host-key verification is opt-in and fails closed

Polaris passed no `hostVerifier` to ssh2 until 2026-08, so EVERY SSH connection accepted whatever host key was presented: agent install (which SFTPs a script and runs it as root), agentless process collection, and the SSH monitor probe alike. `SshConfig.verifyHostKey` enables trust-on-first-use pinning against the `SshHostKey` table via `sshHostKeyService.verifyOrPin` — no pin stores and accepts, a match accepts, a CHANGED key **refuses the connection** and stamps a warning `ssh.host_key.mismatch` with both fingerprints. It is **opt-in, default OFF** (default ON only for newly created credentials), mirroring WinRM's `verifyTls`: turning it on globally would break every install whose hosts were never pinned. `buildHostVerifier` in `utils/remoteExec.ts` is shared by BOTH `ssh2.connect` call sites (`withSshClient` + `monitoringService.probeSsh` — the only two) so they can't drift, and it **fails closed** — an internal error refuses the connection rather than silently skipping verification. Pins are per `(host, port)` in their own table, never on `Credential.config`, because one credential spans a fleet of hosts. Deleting a pin (Integrations → Polaris Agent → Windows SSH Deployment) is the documented recovery for a legitimately rebuilt or re-keyed host and is audited at warning level, since it re-opens first-use trust. **TOFU only detects a key CHANGING** — enabling it against a running fleet pins whatever currently answers, so it is strongest on a greenfield rollout where the pin is taken at deploy time.

## Rule 22 — The Sources column is `location || learnedLocation`, and which source supplies the learned half is operator-ordered

An asset known to several discovery sources at once has several competing answers to "where is it?" (an AD OU path, a controller FortiGate, an Azure Arc onboarding, an Intune enrollment), and which one an operator wants to read is a site convention Polaris can't decide. The assets table's **Sources** column (formerly "Server"; the `data-sf-key` stays `_server` so saved presets keep working) renders the operator's `location` when set, else `Asset.learnedLocation`. The priority behind that second half lives in the `assetSourcePriority` Setting (`{order[], integrationPrefix}`, drag-to-reorder on Assets → Settings → Sources, `assetSourcePriorityService`), and it feeds the **projection** — not just rendering — because the column's filter, its sort, "behind FortiGate X" tag/maintenance criteria and the Device Map's per-site narrowing all read `learnedLocation`. The catalogue of contributors is `utils/assetSourceLocation.ts`: **field** contributors carry a real location string (AD `ouPath`, FortiSwitch/FortiAP `controllerFortigate`, fortigate-endpoint device name, vCenter `clusterName`/`hostName`), **label** contributors have nothing location-shaped to say and contribute their own NAME (`arc` → "Azure Arc", `arc-k8s`, `intune`, `entra`) so the column names who knows the device instead of sitting blank. **Azure Arc is deliberately label-mode:** its only location-ish field is the Azure resource group — a billing container whose name ("updatemanager") tells an operator nothing — which stays on the observed blob and the Sources tab. Never contribute the Azure region (it says where the RECORD lives). `polaris-agent` / `manual` / `fortigate-firewall` never contribute; the `fortigate-endpoint` rule stays suppressed when ANY Fortinet infra source exists — fortigate-firewall / fortiswitch / fortiap — whatever the order says (invariant, not preference: a managed device's site label is its own identity or its controller, and the pre-adoption DHCP sighting row outlives the adoption). Propagation is **pull-based** — the projection runs in the discovery process, so `refreshProjectionPriority()` installs the order at boot in every role and at the top of every `runDiscovery`; reordering is **not retroactive**, each integration's assets re-project on its next run. **The default order is closest-to-a-place first**: sighting FortiGate → the label-only cloud sources (arc / intune / entra / arc-k8s) → vCenter cluster → AD's OU path → fortiswitch / fortiap. The gate is the only contributor naming a physical place; an OU path is org structure that reads as a location only because sites tend to name OUs after buildings; fortiswitch/fortiap sit last where rank is inert (those kinds only exist on assets with no competitor). A **source blob may never be built from the projection's own output**, which is the rule this contributor broke twice: `fortigate-endpoint`'s `observed.learnedLocation` used to be copied off `Asset.learnedLocation` at flush time, so it accumulated the render's `<integration>:` prefix one segment per cycle AND, on a domain-joined laptop, laundered AD's OU path into the blob as something the FortiGate had supposedly said (`CENTRALFMG1:OU=Computer Workstation2` in the column, prod 2026-08). The blob now takes the gate name from the discovery pathway that did the sighting.

## Rule 23 — Who owns an IP and how the gate hands it out are two facts, not one

`Reservation.sourceType` answers the first; `Reservation.dhcpBinding` (`null` | `"lease"` | `"reservation"`) answers the second. Conflating them is what made a FortiLink-addressed FortiAP unreservable: Phase 3a/3b create a `fortiswitch`/`fortinap` row for **every** managed switch/AP, and the address can come from the gate's own DHCP lease table via the `dhcpByHostname` fallback — so Polaris recorded a dynamic lease as an authoritative reservation (plain "Active" pill, no Reserve action) while the FortiGate's DHCP page reported the same address `Not Reserved`. Phase 5 is the only pass that can see the difference, and before this it had **no branch** for those two source types: the entry fell through to a bare `continue`, dropping the fact every cycle and (silently) breaking the "path-* counters sum to entriesTotal" property of its own summary Event. The Phase 5 infra branch now records the binding via the pure `decideInfraDhcpBinding` (`src/utils/infraDhcpBinding.ts`), writing **only on change** because it runs per DHCP entry per cycle. Three deliberate non-writes there: `sourceType` is never flipped (ownership is unchanged and the row's Phase 5b sweep exclusion + decommission semantics depend on it); `expiresAt` is **never** stamped (a lease carries one, and that would hand these rows to `expireReservations` — a live AP's row would expire on the gate's lease clock, be re-created next discovery, and churn); and `macAddress` is fill-only **from the lease entry**, never from `ap.baseMac`, since only the MAC the gate saw requesting the address is the one a future MAC→IP push could bind. A `"lease"` row is takeover-able by an operator Reserve exactly like a `dhcp_lease` (`isSupersedableByCreate`), and releasing it is a pure DB release — neither unpush branch nor the lease-expiry branch fires for it, so claiming an AP's address never bounces its lease. `"reservation"` and `null` stay authoritative: absence of evidence is not evidence the address is free. Phase 3a/3b's conflict-raise is gated on `reservationBelongsToInfraDevice` (MAC, else hostname, else "Polaris pushed it") — without that, the first operator reservation of an AP's IP would raise a conflict card per AP on the next cycle. **A managed device that goes away gives its address back** (`releaseInfraReservationsForAssets`, called from the Phase 2a controller cascade, the Phase 2b stale-infra sweep, both asset DELETE routes, the operator decommission branch of `PUT /assets/:id`, and `decommissionStaleAssets` — every call site filtered to `switch`/`access_point`, since the same predicate would otherwise match a Polaris-pushed reservation on an ordinary server): it delegates to `releaseReservation`, so the CMDB unpush + lease expiry + audit Events all come for free, and it is bounded per invocation because that call can perform device I/O and a controller cascade can cover hundreds of APs. **"No longer discovered" is deliberately NOT a release trigger** — an offline AP stays in its controller's roster (business rule 16's config-truth-vs-reachability line), so the release hangs off the existing decommission decision rather than a second staleness rule. `reconcileOrphanedInfraReservations` (6h job) is the backstop for a decommission that happened while the gate was unreachable; its pure `classifyOrphanInfraRow` releases on an explicitly decommissioned device, but for "no device found at all" — which is also what a transient discovery state looks like — releases only rows Polaris never pushed, because a false positive on a pushed row would delete a reserved-address entry on a live gate. **Optionally, Polaris writes the binding itself** (`infraReservationPushService`, a post-sync discovery pass): double-gated on `config.pushReservations` (the transport nucleus, re-checked server-side via `integrationPushEnabled`) AND `config.autoReserveFortinetInfra`, both default off, on the DHCP Push tab of BOTH Fortinet integration types. It turns a managed device's dynamic lease into a real `reserved-address` entry on its own gate — **pinning an address the device already holds, so pool occupancy never changes** (this is not a mechanism for claiming free space; the pool-capacity question is deferred because Polaris stores no DHCP range and has no subnet-utilization alerting). This is the only DHCP write in Polaris that happens on a schedule rather than because an operator acted on one IP, so it is bounded per cycle (`RUN_CEILING`), low-concurrency, MAC-from-the-lease-table-only, read-back-verified, and never re-attempts a row carrying push state — a permanent refusal is recorded as `pushStatus="failed_permanent"` + `pushError`, which both drops the row from the candidate set and surfaces the device's own message in the IP panel, instead of being retried every cycle. The push pointers it stamps are exactly what the lifecycle release's pinned-unpush branch needs, so decommissioning the device removes the entry.

## Rule 24 — Alert on the device's own alarm bit before inventing a threshold for it

Two boolean asset_metrics exist, and which one to reach for is decided by whether Polaris already collects the fact. **`hwSensorAlarm`** reads `AssetHardwareSensorSample.alarmStatus` — the per-sensor bit the FortiOS REST `sensor-info` and SNMP `fgHwSensorTable` collectors ALREADY write on the normal hardware-sensor cadence, and which the asset System tab already renders as its STATUS column. It needs no operator configuration, works on every transport that fills the column, and shares `hwSensorValue`'s `sensorClass` / `sensorNamePattern` dimensions (same `hwSensorFilterMatches` predicate), so a rule can target one named sensor or a whole class. Prefer it over a threshold on the reading: the device knows its own per-model limits, and for a fan tray or a PSU the health lives in the bit rather than in any comparable number (a FortiGate PSU reports `1` forever and signals failure only through the alarm). **`customStateValue`** (business rule/`AssetStateSample`, state probes) is the general mechanism for status OIDs Polaris does NOT already collect — any vendor, any table — and is deliberately NOT the answer for Fortinet hardware sensors: pointing a probe at `fgHwSensorEntAlarmStatus` re-walks an OID the collector already walks, into a second table, to alert on a value sitting in the first one, and gives two copies of one truth that can disagree. The shared invariant is the NULL rule: `alarmStatusToFlag` (`src/utils/hardwareSensors.ts`) returns `0 | 1 | null` and the engine excludes `alarmStatus: null` **in SQL**, because a source that publishes no alarm bit (the FortiAP-controller path) must not have its absence mapped to 0 — that would assert health nothing ever checked, clearing live alerts and making every such sensor look verified-healthy. An unrecognized non-empty status maps to 1, not null: it's a claim something is off-nominal, and dropping it would go silent on a real fault. **The ENTITY-SENSOR-MIB walk now DOES publish the bit**, from `entPhySensorOperStatus` via `entityOperStatusToAlarm`: `nonoperational(3)` → `"alarm"`, `ok(1)` → `"ok"` (needed so a cleared fault resolves), and — the load-bearing case — **`unavailable(2)` → NULL, never `"alarm"`**, because an empty SFP cage reports unavailable and a port with no transceiver in it is not a fault; mapping it to alarm would fire on every unused port on the switch. Note the bit means something narrower here than on the Fortinet paths: it reports whether the SENSOR is functioning, not whether the reading is inside its limits. For "this optic is degrading but not yet dead", use a severity-band automation on the dBm `hwSensorValue` instead (business rule 19). **The same invariant now holds one layer down, at the varbind decoder.** `snmpVbToNumber` (`services/monitoringService.ts`) used to fall through to `Number(v)` for anything it didn't recognize, and `Number(null)` is a perfectly finite **0** — so every OID a device does not publish decoded as a confident zero rather than as "no reading". `snmpGetScalar` returns exactly that `null` for an error varbind (noSuchObject / noSuchInstance / endOfMibView), which made the failure indistinguishable from a healthy device reporting zero, and worse than merely wrong: because `0` is not `null`, the HOST-RESOURCES-MIB fallback in `collectTelemetrySnmp` (guarded on `cpuPct == null`) never ran to correct it. A FortiSwitch whose empty `Asset.model` had misrouted it onto the FortiGate OIDs therefore charted a flat 0.0% CPU and 0.0% memory forever, with no error anywhere (prod 2026-08-31, FSR-112D-POE; the misroute itself is fixed by `fortinetClassHint`). Absence and empty now decode to `null`; a genuine zero is still believed, since the distinction being drawn is "said zero" vs "said nothing". The visible consequence is that a series which used to sit convincingly at zero now shows a GAP — which is the honest reading, and looks like data loss precisely because the old behavior was silent.

**And a third instance, one layer further out: an absent reading is not an absent DIMENSION** (2026-09). The two cases above are about not mapping null to a VALUE. This one is about not mapping it to a verdict on whether the thing being measured still exists. An `AssetInterfaceSample` row is written per port per tick with every interface column on it, so a column is null either because the device has nothing to report there or because that column's own collection failed while the rest of the row succeeded — and PoE is the column most able to fail alone, being its own pair of walks (`collectPoePortsSnmp`) that can time out while the IF-MIB walk feeding the same row answers fine, with an ifIndex correlation on top of it that drops any port it cannot resolve unambiguously (RFC 3621 provides no join, so `poeIfNameByIndex` matches on an interface name's trailing number and refuses ties). The engine's state resolver read `group[0]` — the newest row, readable or not — and dropped the port when its column was null, which is correct for a port with no PSE and catastrophic for one whose walk merely timed out. The port stopped producing a reading; the switch went on reporting its OTHER pinned ports, so `clearVanishedStates` took the "dimension is gone" branch rather than the collection-gap freeze; the live alert was retired as `notification.out_of_scope`; and the next readable tick raised a brand-new alert, with a new `Notification` row, a new delivery and a new email. **A duplicate alert email per collection gap, on a port sitting in `fault` the entire time** — and because the alert really was cleared and really was re-raised, nothing in the alert's own history looked wrong. Two fixes, at the two ends. At the collector, only a walk that ANSWERED may be taken as evidence: the status walk resolves to `null` on error instead of being `.catch()`-ed into an empty Map, and `poeWalkOutcome` (`utils/poePorts.ts`, with the rest of the PoE decision table) splits `unreadable` from `no-pse` so the 30-minute `poeAbsentCache` is written only for the latter — collapsing them let ONE timeout claim a healthy switch had no PSE and blank `poeStatus` on every sample for the next half hour, which is far longer than any lookback window and therefore a guaranteed clear-and-re-raise. At the engine, the reading is the newest row that CARRIES the field (`interfaceStateSeries` / `interfaceSampleCarries`, both pure and exported), and unreadable rows are dropped from `Reading.series` as well, so a gap neither counts toward a poll-counted hold nor breaks its run (business rule 19). `ifOperStatus` requires `adminStatus` to be present as well as `operStatus`, since the admin-up gate downstream reads it and a row missing it is no more usable than one missing the status itself. A group with NO readable row anywhere in the lookback window still produces nothing — that is a port with no PSE or one that genuinely stopped reporting, and both should still clear. Note this is the engine catching up to the ROLLUP rather than inventing a rule: `sampleRollupService` has always reduced these same columns with `ARRAY_AGG(...) ORDER BY "timestamp" DESC FILTER (WHERE ... IS NOT NULL)`, so the hourly bucket rode through a gap that the live evaluator treated as the end of the world. Where they disagreed, the rollup was right.
