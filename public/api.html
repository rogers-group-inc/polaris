Overview

Polaris exposes a JSON REST API for external systems — SIEM-driven quarantine, NOC kiosks and wallboards, inventory consumers, and automation scripts. Every endpoint lives under the versioned base /api/v1, requests and responses are JSON (Content-Type: application/json), and authentication is a bearer token minted in Polaris (see Authentication).

This reference covers the endpoint groups intended for external callers. Polaris has many more endpoints backing its own UI; those are internal, undocumented here, and may change without notice — build against what this page documents.

Deprecated path aliases

Three resource groups were renamed and keep their old paths mounted as deprecated aliases: /notifications → /alerts, /notification-rules → /automations, and /notification-channels → /delivery-channels. Responses on the old paths carry a Deprecation: true header plus a Link: <successor>; rel="successor-version" header naming the replacement. Use the new paths in new integrations.

Authentication

External callers authenticate with a long-lived bearer token, created by a Polaris administrator under Server Settings → API Tokens. The raw token is shown once at creation and looks like polaris_<32-character-tail>. Send it on every request: 

curl -H "Authorization: Bearer $POLARIS_TOKEN" \
  /api/v1/assets?limit=5

Every token is bound to a Role at creation and can do exactly what that role's permission matrix allows — the same permission gates Polaris applies to logged-in users. For least privilege, have your administrator create a purpose-built role (for example, assets read-only) rather than binding an admin-equivalent role.

  • Bearer requests are exempt from CSRF checks — no CSRF token or cookie is needed.
  • A missing, revoked, expired, or malformed token gets the same 401 as no token at all; the API does not distinguish.
  • A token may be limited to trusted hosts — a list of IP addresses and CIDRs set when it is created. A valid token sent from any other address gets a 403 whose message names the source address Polaris saw (behind a reverse proxy, check that it forwards the client address). A token with no list is accepted from anywhere.
  • A request the token's role does not permit gets a 403 — except on the handful of aggregate endpoints documented as filter-don't-403, which return the sections the role can read and leave the rest empty.
  • There is no token-introspection endpoint: GET /auth/me answers {"authenticated": false} for bearer callers. To smoke-test a token, call a cheap endpoint its role can read (for example GET /assets?limit=1) and check for 200.
  • Writes made with a token are attributed in the Polaris audit log as api:<token name>.
Ownership-scoped resources need fullwrite. Networks (subnets), reservations, and contacts carry an ownership dimension: write lets a caller edit only rows they created, identified by the session username. A bearer token has no username, so a token bound to a role with plain write on those keys can create rows but gets 403 on every edit/delete of an existing row. Bind tokens that must manage IPAM rows to a role granting fullwrite on subnets / reservations.

Errors & rate limits

Every error is JSON with a single error string:

{ "error": "Reservation not found" }

Status conventions:

  • 400 — validation failure; the message names the offending field.
  • 401 — missing or unusable credentials.
  • 403 — authenticated, but the token's role lacks the required permission, or the token was sent from outside its trusted hosts.
  • 404 — no such resource, or one outside the caller's visibility scope (Polaris deliberately answers 404 rather than 403 for scoped-away resources).
  • 409 — the request conflicts with current state (overlapping subnet, deleting a block with active reservations, duplicate reservation).
  • 429 — rate-limited; back off and retry. Machine-facing surfaces such as quarantine verify have generous per-IP budgets sized far above healthy polling cadences, so a 429 usually means a runaway loop.
  • 5xx — server-side failure; the body still carries { "error": ... } where possible.
Aggregate feeds (/dashboard/*) are cached server-side for ~10 s and shared across callers — poll them at a wallboard cadence (every 10–30 s), not in a tight loop.

Assets & inventory

Device inventory reads. Gate: assets:read unless noted.

GET /assets assets:read

List devices. Response: { assets, total, limit, offset } — total is the full filtered count, so page with it rather than assets.length.

Query parameters:

  • limit (default 50, max 10000), offset (default 0). There is no page parameter.
  • search — case-insensitive match across hostname, DNS name, IP, MAC, asset tag, and assigned-to.
  • status, assetType, monitor — comma-separated multi-value. monitor accepts Unmonitored, Monitored, Dep. Down, Up, Missed, Warning, Down, Recovering, Passive, Pending.
  • Per-column text filters: pass the column name (hostname, ipAddress, serialNumber, assetTag, manufacturer, model, os, macAddress, assignedTo, purchaseOrder, dnsName, description) plus an optional <column>Op of contains (default), not_contains, empty, is_not_empty.
  • ipAddress also takes ipAddressOp=in_networks: a comma-separated list of IPv4 networks, matched when the primary IP falls in any of them. Each entry is a partial address (10.1 = 10.1.0.0/16), a suffix with a leading dot (.50 = last octet 50, .1.50), a full address (exact) or a CIDR (10.1.16.0/20); at most 50, and an invalid entry is a 400.
  • department (contains match), lastSeenFrom / lastSeenTo (YYYY-MM-DD).
  • sortBy (whitelisted column names; an unknown value is a 400) + sortDir (asc default when sorting; default order without sortBy is newest first).
curl -H "Authorization: Bearer $POLARIS_TOKEN" \
  "/api/v1/assets?search=fw-&status=active&limit=25"
GET /assets/:id assets:read

One device — the full asset record at the top level (not wrapped), including monitoring state, discovered attributes, associated IPs and MAC addresses. 404 when absent.

addressConfidence scores every address on the device, keyed by IP: { "10.20.30.4": { score, evidenceScore, discoveryScore, band, evidenceBand, parts, penalties, sustained } }. score is 0–100 and includes an operator's pin or typed address; evidenceScore is the network evidence alone; discoveryScore (0–100) is discovery's evidence alone — no operator, no polling — and is what the automatic pin release compares. band is high (80 and up), medium (50), low (20) or very-low. Each entry in parts is one kind of evidence — { kind, label, device, seenAt, hours, value }: the device's own interface table, a gate seeing it online (kind detected-ambiguous, and worth far less, when the gate's ARP table shows that network card with several addresses), a held DHCP reservation or lease, a configured reservation, an ARP entry on a gate, the management IP a FortiGate, FortiSwitch or FortiAP record names, a vCenter guest or host IP, a Proxmox, Unraid or TrueNAS host, VM or container record, an Azure Arc profile, a FortiGate endpoint record, a Generic API feed, or how long Polaris's own polling has answered on it — and each entry in penalties is { kind, factor, detail }, a multiplier applied to the score: alive-elsewhere, claimed-elsewhere, or arp-elsewhere — the address rests on what a gate detected, no ARP entry backs it, and a gate's ARP table has that MAC at a different address. sustained is true while Polaris's own polling is answering on the address: its evidence is then not aged in score and evidenceScore, while discoveryScore still ages it. Nothing alerts on the score; it only picks the address an unpinned device moves to and when a pin is released. The list (GET /assets) carries the compact form, { score, band } per address.

GET /assets/:id/sources assets:read

Which discovery sources claim this device (Entra / Intune / AD / FortiGate / vCenter / agent / manual …). Response: a JSON array of { id, sourceKind, externalId, integration, observed, firstSeen, lastSeen }.

GET /assets/:id/sightings assetsQuarantine:read

FortiGate DHCP/endpoint sighting history — where the device was last seen on the network. Response: a JSON array, newest first, each row carrying the FortiGate, source, IP, timestamps, plus resolved subnetName and vlan. Note the gate: this read belongs to the quarantine key, not assets.

GET /assets/:id/dependencies assets:read

The device's dependency context: { asset, effectiveParents, computedParents, overrideParents, hasOverride, children, childrenTruncated, childCount, haPeer }. children lists infrastructure-type children only, capped at 300 (childrenTruncated flags overflow). Every node — asset, each effectiveParents[].parent, haPeer, each child and grandchild — carries activeAlert: { severity, count, unacknowledged } for its uncleared alerts (worst severity first), or null when nothing is firing. Every node also carries serialNumber and ipAddress: a hostname is not an identity (FortiLink fleets name their switch-ids per site, so two switches in one tree can both read "IDF-1"), and a client telling them apart needs one of those two fields.

Device onboarding (writes)

Creating a device and putting it under monitoring is two calls: POST /assets carries inventory fields only, and the monitoring switch plus its credential wiring live on PUT /assets/:id. Credentials themselves are not created over the API in the normal flow — an operator saves them once under Server Settings → Credentials and the integration references the stored row by id.

GET /assets/ip-check assets:read

Ask, before creating or re-addressing a device, whether an address is already in use. Query: ip (required), excludeAssetId (the asset being edited, so it is not reported as colliding with itself), and optionally assetType and macAddress for the incoming device. Returns { ip, holders[], wouldConflict, qualifiedBy, canMerge }: every network-present asset already recording the address (each with claimCurrent — a stale record is listed but does not collide), whether saving would raise a Duplicate IP conflict, and whether the caller may merge assets (assets:fullwrite). The answer is computed with the same rules the save applies, so a wouldConflict: true here is a conflict the write will raise. 400 on an invalid address.

curl -H "Authorization: Bearer $POLARIS_TOKEN"   "/api/v1/assets/ip-check?ip=10.20.30.4&assetType=switch"
POST /assets assets:write

Create a device. Body (all optional, but give it at least an address or a hostname): { ipAddress?, macAddress?, hostname?, dnsName?, assetTag?, serialNumber?, manufacturer?, model?, assetType?, status?, location?, latitude?/longitude?, department?, assignedTo?, os?, acquiredAt?, warrantyExpiry?, purchaseOrder?, notes?, description?, tags? }. assetType defaults to other and status to active. An all-zero macAddress is stored as no MAC (on PUT /assets/:id it clears the field). azure: tags in tags are dropped: that namespace is mirrored from Azure resource tags by the Azure Arc integration and nothing else may write it. 201 with the created record, plus ipConflict: when the new device's address is already recorded by another network-present asset, Polaris raises a Duplicate IP conflict on the spot (rather than on its ten-minute sweep) and returns it as { conflictId, ip, qualifiedBy, members[] }; otherwise null. Ask before writing with GET /assets/ip-check below.

Monitoring fields are not accepted here — monitored and every *CredentialId belong to the PUT below. A device created by this endpoint is a manual-source asset: only response time gets a source default (ICMP), so every other stream stays dark until a polling method is chosen for it.

curl -X POST -H "Authorization: Bearer $POLARIS_TOKEN"   -H "Content-Type: application/json"   -d '{"hostname":"sw-branch-12","ipAddress":"10.20.30.4","assetType":"switch"}'   "/api/v1/assets"
PUT /assets/:id assets:write

Update any field POST /assets accepts, plus the monitoring surface: { monitored?, monitorCredentialId?, monitorIntervalSec? (5–86400), probeTimeoutMs? (100–60000) }, the per-stream polling methods { responseTimePolling?, cpuMemoryPolling?, temperaturePolling?, interfacesPolling?, lldpPolling?, storagePolling? } (one of rest_api, snmp, winrm, ssh, icmp, agent, vcenter, fortimanager, disabled), and the per-stream credentials { responseTimeCredentialId?, cpuMemoryCredentialId?, temperatureCredentialId?, interfacesCredentialId?, lldpCredentialId? }. null clears a slot and falls back to the next settings tier. When the update changes ipAddress, the response carries ipConflict exactly as POST /assets does — the conflict on the new address, or null — and a conflict the device just moved off is closed in the same call. tags replaces the device's tags, except that its azure: tags (Azure Arc's) are always kept and any azure: tag in the body is ignored.

Refusals worth coding against:

  • 400 — Credential … not found, naming the id. It is well-formed but matches no stored credential (commonly one deleted and recreated in the UI, which issues a new id).
  • 400 — a credential whose type cannot serve the stream's transport, e.g. an ssh credential on a stream polling over SNMP. The pairing is snmp→snmp, winrm→winrm, ssh→ssh, rest_api→restapi; ICMP, Disabled, Agent, vCenter and FortiManager take no per-asset credential, and a credential left beside one of those is accepted as staged config. monitorCredentialId is never type-checked — it is the fallback for every stream at once, and those streams may legitimately poll over different transports.
  • 400 — a polling method the asset's discovery source does not support, or ICMP on any stream but response time.
  • 409 — monitored: true on a status that cannot carry monitoring (decommissioned / disposed / lost / disabled). Change status first.
  • 400 — setting or clearing status: "quarantined" (use the quarantine endpoints below).
curl -X PUT -H "Authorization: Bearer $POLARIS_TOKEN"   -H "Content-Type: application/json"   -d '{"monitored":true,"cpuMemoryPolling":"snmp","cpuMemoryCredentialId":"'$CRED_ID'"}'   "/api/v1/assets/$ASSET_ID"
POST /assets/bulk-monitor assets:write

Flip monitoring on many devices at once: { ids: [uuid, …], monitored, monitorCredentialId?, monitorIntervalSec?, probeTimeoutMs? } → { updated, errors: [{ id, error }] }. A mixed selection is normal, so per-id problems (an unknown id, a status that cannot be monitored) are reported in errors with HTTP 200 while the rest of the batch still applies. An unknown monitorCredentialId is the exception and fails the whole call with 400 — it applies to every id in the batch, so nothing would be written correctly.

POST /assets/bulk-tags assets:write

Add, remove or replace tags on many devices at once: { ids: [uuid, …], mode: "add" | "remove" | "replace", tags: [string, …] } → { updated, unchanged, notFound: [uuid, …], tags }. add keeps each device's own tags and appends the new ones; remove strips them from the devices that carry them; replace leaves each device with exactly tags, except that region:, prev-entra:, prev-ad: and azure: tags are kept. An azure: tag in tags is ignored in every mode — Azure Arc owns that namespace. Unknown ids come back in notFound with HTTP 200. An empty tags is a 400 for add and remove (replace with none clears), as is adding a region: tag that names no map region.

DELETE /assets/:id assets:write

204. 409 for a quarantined device — release it first.

PUT /assets/:id/primary-address assets:write

Pin the address the device is monitored on: { mac, ip } → { assetId, mac, ip }. The pair must be one of the device's own addresses — an entry in associatedIps on GET /assets/:id, each of which names its mac, the gate that reported it (device) and medium. Reading GET /assets/:id first checks the device's DHCP lease and reservation entries against IPAM: one IPAM has released, or holds for a different MAC, is dropped from the list. ipAddress becomes the pinned IP and discovery stops changing it; the one exception is a renumber — when the pinned IP has not been seen for 24 hours and the same MAC now has exactly one recently seen address, the pin moves to it. Pinning replaces an IP typed through PUT /assets/:id, and typing or clearing the IP there, or ipRevertToDiscovered, releases the pin. The device's identity macAddress is not changed.

  • 409 — the pair is not on the device's address list (type an address that is not there through PUT /assets/:id instead).
  • 409 — a FortiGate, FortiSwitch or FortiAP managed by a Fortinet integration; it is monitored on its management IP.
  • 400 — mac is not a MAC address.
  • 400 — ip is an IPv6 address; use PUT /assets/:id/primary-ipv6.
curl -X PUT -H "Authorization: Bearer $POLARIS_TOKEN"   -H "Content-Type: application/json"   -d '{"mac":"AA:BB:CC:DD:EE:FF","ip":"10.20.30.4"}'   "/api/v1/assets/$ASSET_ID/primary-address"
DELETE /assets/:id/primary-address assets:write

Release the pin → { ipAddress }. The device moves to the address on its own list (associatedIps) with the highest evidenceScore — network evidence including polling, no operator weight; a tie keeps the current address. Only when the list is empty does the address go back to what discovery reports (a device no source reports keeps the one it has). A device with no pin is left as it is.

PUT /assets/:id/primary-ipv6 assets:write

Pin the device's primary IPv6 address: { ip } → { assetId, ipv6Address }. The primary IPv6 is ipv6Address on GET /assets/:id; it is shown beside ipAddress and never replaces it. A device with no ipAddress is monitored on it. Without a pin Polaris picks it from the device's IPv6 entries in associatedIps; a pinned one is left alone. The address is stored in canonical form.

  • 409 — IPv6 is off for this Polaris install.
  • 400 — ip is not an IPv6 address, or is loopback, link-local or multicast.
curl -X PUT -H "Authorization: Bearer $POLARIS_TOKEN"   -H "Content-Type: application/json"   -d '{"ip":"2001:db8::4"}'   "/api/v1/assets/$ASSET_ID/primary-ipv6"
DELETE /assets/:id/primary-ipv6 assets:write

Release the pin → { ipv6Address }, the automatic choice made straight away (null when the device has no IPv6 address, or IPv6 is off). A device with no pin is left as it is.

POST /assets/:id/address-check assets:write

Score an address before pinning it or typing it in: { ip, probe? } → { ip, evidenceScore, evidenceBand, score, band, discoveryScore, sustained, parts, penalties, warn, warnBelow, probe }. The fields are those of addressConfidence on GET /assets/:id; an address the device has never been seen on scores 0. warn is true when evidenceScore is below warnBelow (50). With probe: true the server sends the address one ping (2-second timeout) and probe is { answered, error }, otherwise null — a reply shows something answers there, not that it is this device, so it is reported beside the score rather than counted in it. Only a check: nothing is written, and PUT /assets/:id and PUT /assets/:id/primary-address never refuse a low score.

  • 400 — ip is not an IP address.
  • 404 — no such device.
curl -X POST -H "Authorization: Bearer $POLARIS_TOKEN"   -H "Content-Type: application/json"   -d '{"ip":"10.20.30.4","probe":true}'   "/api/v1/assets/$ASSET_ID/address-check"
GET /credentials credentials:read

List stored monitoring credentials so an integration can resolve the id it needs by name: a JSON array of { id, name, type, config, createdBy, createdAt } with every secret masked (community strings, passwords, private keys, passphrases and API tokens all read ••••••••). type is one of snmp, winrm, ssh, restapi, http.

Quarantine (SIEM flow)

Network quarantine pushes MAC-based address-group entries to every FortiGate that has recently sighted the device. Gates: assetsQuarantine:read for reads, assetsQuarantine:write for actions — and a token whose role grants quarantine write is additionally scoped to the integrations picked when the token was minted; pushes touching any other integration are refused with a 403.

The recommended flow for a SIEM integration:

GET /assets/quarantine-availability assetsQuarantine:read

Preflight — is quarantine push configured anywhere? { pushEnabled, integrationCount, pushEnabledCount }. With pushEnabled false a push can only fail ("0/0 FortiGate(s) accepted").

GET /assets?search=<mac|ip|hostname> assets:read

Find the asset id. search matches MAC, IP, and hostname in one parameter, so pass whatever identifier the SIEM event carries.

POST /assets/:id/quarantine assetsQuarantine:write

Body: { "reason": "..." } (optional, ≤500 chars). Response: { assetId, status, targets, succeededCount, failedCount, message } with a per-FortiGate targets[] breakdown.

Refusals: 400 for infrastructure types (firewall / switch / access point) and for a device with no known MAC; 409 with no recent sightings (nothing to push to); 502 when zero FortiGates accepted the push (the device's status is not flipped in that case).

curl -X POST -H "Authorization: Bearer $POLARIS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"reason":"EDR: credential theft detected"}' \
  "/api/v1/assets/$ASSET_ID/quarantine"
POST /assets/:id/quarantine/verify assetsQuarantine:write · rate-limited

Re-reads each FortiGate to confirm the quarantine entries are still in place. Response: { targets, driftDetected }; drift is persisted and audited. This is the one machine-facing endpoint with its own rate limiter (300 requests / 5 min / source IP — far above a healthy verify cadence).

GET /assets/:id/quarantine-status assetsQuarantine:read

{ id, status, statusBeforeQuarantine, quarantineReason, quarantinedAt, quarantinedBy, quarantineTargets }.

DELETE /assets/:id/quarantine assetsQuarantine:write

Release. Restores the device's prior status and monitoring; device-side unpush failures are reported ({ assetId, newStatus, unpushedFrom, failedToUnpush, message }) but never block the release. 409 when the device is not quarantined.

POST /assets/bulk-quarantine assetsQuarantine:write

Body: { "ids": [...], "reason": "..." } (≤500 ids). Response { results }, one { id, ok, message } per input in order — one bad asset never fails the batch. Release counterpart: POST /assets/bulk-quarantine/release with { "ids": [...] }.

GET /assets/sighting-settings assetsQuarantine:read · PUT at write

The sighting max-age window ({ sightingMaxAgeDays }, default 180) — how recent a FortiGate sighting must be to count as a push target. PUT accepts { "sightingMaxAgeDays": 0–3650 }.

Related refusals elsewhere: PUT /assets/:id refuses setting or clearing status: "quarantined" directly (use these endpoints), and DELETE /assets/:id answers 409 for a quarantined device — release first.

Dashboard & NOC feeds

Aggregate wallboard/kiosk feeds. All three endpoints follow the filter-don't-403 contract: sections the token's role cannot read come back empty with the response shape unchanged, never as an error — so a read-only kiosk token renders whatever it is entitled to. Responses are cached server-side for ~10 s and shared across callers.

GET /dashboard/noc-summary per-feed: assets/events/alerts/maintenanceManagement read

The NOC feed bundle. ?feeds= selects a comma-separated subset of status, downNodes, downInterfaces, downIpsecTunnels, topCpu, topMemory, slowestResponse, packetLoss, diskUsage, temperature, storageForecast, stalePolls, sitesWithIssues, recentReboots, activeAlerts, maintenanceSchedules, sdwanRuleFailovers, sdwanSingleLink, sdwanSlaHeadroom, sdwanFlaps1h, sdwanFlaps24h, sdwanCompliance1h, sdwanCompliance24h; absent = all. Filters: hideAssetTypes (CSV of the asset types to EXCLUDE — built-in or operator-added; assetTypes is the legacy inverse and names the ENABLED built-ins, from which the hidden set is derived as the built-ins it omits — sending both unions them), regionTags, fortigates (all CSV), limit (≤1000; each feed has its own default cap), samples (top-N averaging depth, ≤100, default 10), includeDependencyDown=1.

Response is a flat map of the requested feeds. Three feeds fan out: status → statusCounts + uptimePercent + activeAlertCount; downNodes → downNodes + downNodesTotal (true uncapped count); activeAlerts → activeAlerts + activeAlertsTotal. Feed gates: recentReboots needs events:read, activeAlerts needs alerts:read, maintenanceSchedules needs maintenanceManagement:read, everything else assets:read.

maintenanceSchedules lists the maintenance schedules in effect right now — {id, name, deviceCount, matchedCount, filtered, assetTypes[{assetType, count}], kind, adhoc, suppressChildren, startedAt, endsAt, endsAtUtc}, soonest-ending first. startedAt/endsAt are the Polaris server's local wall clock (YYYY-MM-DDTHH:MM, no offset — the recurrence engine evaluates against that clock), and endsAtUtc is the same window end as a true instant for computing a countdown. Unlike every other feed, an asset filter does not narrow the rows: a schedule is listed when ANY of its devices is in scope and is then reported whole, with matchedCount giving the in-scope share.

The seven sdwan* feeds read the SD-WAN data FortiGates report (FortiManager-managed or standalone, with SD-WAN collection on) and are empty otherwise. sdwanRuleFailovers lists enabled service rules that are down or carrying traffic off their preferred member — {assetId, hostname, ipAddress, site, ruleName, mode, state: "down"|"failedOver", selectedMember, preferredMembers[], updatedAt}; only lowest-cost (SLA) and manual rules can be failed over. sdwanSingleLink lists gates with two or more WAN paths left with one or none — {assetId, hostname, ipAddress, site, alivePaths, totalPaths, alive[], downMembers[], lastSampleAt}; an overlay tunnel counts as the port it rides. The other five are top-N rows ({id, hostname, ipAddress, site, value, detail}): sdwanSlaHeadroom is the % of the health check's SLA target a live member uses (15-minute average, worst metric; 100 is the target); sdwanFlaps1h/24h count up → down drops per member; sdwanCompliance1h/24h give the % of scrapes OUT of SLA per health check and member (compliance is 100 minus it), omitting pairs that never left SLA. The four windowed feeds share one computation cached for about two minutes.

curl -H "Authorization: Bearer $POLARIS_TOKEN" \
  "/api/v1/dashboard/noc-summary?feeds=status,downNodes,activeAlerts&limit=50"
GET /dashboard/summary per-section: ipBlocks/reservations/assets read

?sections= subset of blocks, recent, assetTypes, monitorAlerts (absent = all). Response keys (only requested sections appear): blockUtilization, recentReservations (recentSourceTypes + recentLimit ≤1000 filter it), assetTypeCounts, and monitorAlerts + monitorAlertsOverflow (list capped at 50).

GET /dashboard/filter-options assets:read

{ assetTypes, regions, fortigates, tags, automations } — the values the dashboard widget filters accept. assetTypes is { name, label } entries: every built-in type followed by every operator-added type the asset-type registry carries (plus any custom name still worn by a live asset whose registry row is gone), registry-labelled. tags is the distinct asset tags across the live fleet, region: tags excluded (they are regions). Empty arrays (not 403) without assets:read. automations is { id, name, enabled, triggerType } per automation, disabled ones included — the alert widgets' Automations filter, which matches each alert's ruleIds — and is gated on alerts:read instead (empty without it).

Path Monitor

A path check is an HTTP / HTTPS request, a TCP connect or a ping that the Polaris Agent (0.21.0 or later) runs from each host it is pointed at, with an optional traceroute of the path. A check's hosts are its Sources filter plus any pinned assets, intersected with hosts running an active agent. A check has no threshold of its own and never changes a host's Up / Down status: alert on it with an automation on the path* metrics (pathOk, pathLatencyMs, pathFailurePct, pathHttpStatus, pathHopCount, pathTlsDaysLeft) or on the path_check.path_changed event. Check endpoints gate on the pathChecks key; the per-host readings under /assets/:id gate on assets:read, because they describe that asset.

A check can also run from the Polaris server itself (runOnServer: true), alone or beside agent hosts. The server is not an asset: its results come back as the first /results row (server: true, assetId: null) and through the three /path-checks/:id/server… readings. They raise an automation alert only on a path* trigger (or the path_check_path_changed change trigger) carrying "includeServer": true — a single condition, never with a reset.mode of condition — and that alert has assetId: null and assetHostname: "Polaris server". A path* automation's devices are always its scope ANDed with Polaris Agent installed, and a composite may not mix path* conditions with any other. Pointing the server at a target also needs networkScan:write — creating a server-run check, turning the server on, changing what a server-run check sends, or re-enabling one returns 403 without it. Turning the server off, renaming a check or changing its agent hosts does not need it.

GET /path-checks pathChecks:read

{ checks: [...] }, by name. Each check carries its definition (below) plus a fleet summary: sourceCount (hosts running it), okCount / failCount (hosts whose latest run passed / failed — a host with no result yet is in neither), unexpectedCount (of the failing, those whose run still got an HTTP answer, just not the expected status or body) and lastRunAt. maintenance: { inMaintenance, windows[] } says whether it is paused by a maintenance schedule right now; each window carries scheduleId, scheduleName, startedAt and the current occurrence's end as until (the server's wall clock, "YYYY-MM-DDTHH:MM") and untilUtc.

curl -H "Authorization: Bearer $POLARIS_TOKEN" \
  "/api/v1/path-checks"
GET /path-checks/:id pathChecks:read

One check, same shape as a list row. 404 when it does not exist.

GET /path-checks/:id/results pathChecks:read

Maintenance schedules

A maintenance schedule pauses either assets or path checks — never both in one schedule — for a one-time window or on a recurrence. An asset in maintenance stops being polled and alerted on; a path check in maintenance stops running on every agent host and on the server, and its path* automations neither fire nor send reminders or escalations. An alert already open stays open and recovers on its own once the window ends. All times are the Polaris server's wall clock, written "YYYY-MM-DDTHH:MM" with no offset — read GET /maintenance-schedules/server-time before building one. Every route gates on maintenanceManagement; a write applies at once, so a schedule that is already in its window takes effect before the call returns.

GET /maintenance-schedules maintenanceManagement:read

{ schedules: [...] }, newest first. ?target=assets or ?target=pathChecks lists only that kind (400 on any other value). A schedule is { id, name, enabled, criteria, assetIds, pathCheckIds, schedule, suppressChildren, createdBy, createdAt, updatedAt }.

GET /maintenance-schedules/server-time maintenanceManagement:read

{ now, timeZone, offsetMinutes } — the server's wall clock in the form every schedule time uses, its IANA zone, and its UTC offset (east-positive).

POST /maintenance-schedules maintenanceManagement:write

Create a schedule; 201 with { schedule }. Body:

  • name (required, ≤200), enabled? (default true).
  • Assets: criteria? (an asset filter — hostname, IP / subnet, model, manufacturer, OS, asset type, integration, behind-FortiGate; not status) and / or assetIds? (≤500). Only monitored assets enter. suppressChildren? (default true) marks devices behind an asset in maintenance as down for dependency suppression.
  • Path checks: pathCheckIds (≤500), instead of the two above. 400 on a body carrying both, or naming a check that does not exist.
  • schedule: a one-time window { "version": 1, "kind": "oneshot", "startAt", "endAt" } — or "startNow": true in place of startAt to start at the server's own now — or a recurrence { "version": 1, "kind": "recurring", "freq": "daily" | "weekly" | "monthly" | "yearly", … } with daysOfWeek (weekly, 0 = Sunday), dayOfMonth (monthly) or month + day (yearly), and hours: [{ startTime, endTime }] ("HH:MM"; an end at or before the start runs past midnight; omitted = all day), plus optional activeFrom / activeUntil dates.

A one-time schedule naming a single asset or a single path check, with no criteria, removes itself once its window has ended.

Search

GET /search?q= per-group read keys · filter-don't-403

Global typeahead across seven groups. Response: { query, blocks, subnets, reservations, assets, ips, sites, ipsec } — every group always present; groups the role can't read (or that didn't match) are empty arrays. Group gates: blocks→ipBlocks, subnets→subnets, reservations→reservations, assets→assets, sites→deviceMap, ipsec→assets; the ips cross-reference needs both subnets and reservations read.

  • Minimum 2 characters (1 when scoped). Terms are AND-combined; "quoted phrases" stay whole; single terms get IP/CIDR/MAC special-casing.
  • Scope prefixes: block:/b:, network:/n:, asset:/a:, reservation:/r:, map:/m:, tag:/t: (tag spans blocks + networks + assets), ipsec:/vpn:/v:.
  • ipsec hits are a FortiGate's phase-1 tunnels (newest state at or after the gate's last full system-info pass) and the peers / VPN users connected through them, matched on tunnel name, remote gateway, peer id, user name, underlay or overlay address. type is "ipsec", id is <gateAssetId>|tunnel|<name> or <gateAssetId>|conn|<name>, status is up/down/partial, and context carries assetId (the gate), kind, tunnelName or name, remoteGateway, userName, and peerAssetId/peerHostname when the far end resolves to an asset. The gate's own hostname is not a searched column.
  • A query of 8+ characters that reads as a thumbprint — a TLS SHA-256 fragment (hex, colons / spaces / dashes ignored) or an SSH host-key fingerprint fragment (with or without SHA256:) — also returns the asset(s) that pin belongs to, live or archived on decommission, first in assets, with context.pinMatch { kind: "ssh"|"tls", host, port, archived }. Needs serverSettingsSystem read as well as assets.
  • Caps: 8 hits per group unscoped; 200 for a scoped query. No paging — scope the query instead.

IPAM: Reservations

Single-IP (or full-subnet) entries. Reads: reservations:read; writes: reservations:write, ownership-scoped like networks (tokens need fullwrite to edit/delete/retry). Every reservation carries a sourceType — manual for API/UI-created rows, discovery types (dhcp_lease, dhcp_reservation, vip, interface_ip, dns_resolved, observed, …) for rows Polaris observed. observed is an IPv6 address a FortiGate saw a client using without assigning it (SLAAC or static); it carries an expiresAt a day past its last sighting. An IPv6 ipAddress is stored in its compressed lower-case form, and is never pushed to a FortiGate.

GET /reservations reservations:read

{ reservations, total, limit, offset } (default limit 50, max 200). Filters: subnetId, owner, projectRef, status (active / expired / released).

Body: { subnetId, ipAddress?, hostname, owner?, projectRef?, expiresAt?, notes?, macAddress? }. Omit ipAddress to reserve the whole subnet. 201 with the reservation. An all-zero macAddress (00:00:00:00:00:00, any separators) is a 400: it names no device. Omit it instead.

Collision semantics: an existing active row at the same address is a 409 — unless it is merely observed presence (dhcp_lease, dns_resolved, observed, or a lease-backed infra row), which the create supersedes in place. Device-owned rows (vip, interface_ip) and authoritative types always 409. A deprecated subnet refuses new reservations.

On a network whose integration pushes DHCP reservations, notes becomes the FortiGate entry's description, which FortiOS holds 255 characters of — including the Polaris/<user>: … [<hostname>] wrapper Polaris writes around it. An over-length notes (or hostname) is a 400 naming the budget and the overage; nothing is truncated. The same applies to PUT /reservations/:id when it changes either field. Networks Polaris does not push to have no such limit.

Automations

An automation is a rule: a trigger evaluated over the devices its scope selects, a severity, and what happens when it fires (actions, escalation, repeat, reset). Every endpoint gates on automationManagement. Two action types need a second key when a rule carrying them is saved: a script action needs automationScripts:write, a reboot action needs assets:write (403 otherwise; removing one never needs it). Saving, editing and deleting each write an Event.

The rule body is large and versioned by its own vocabulary, so build against GET /automations/schema rather than a hardcoded list: it returns every metric, state field, comparator, aggregation, change type, action type and severity the server accepts, plus the names behind the ids a condition can carry (state probes, path checks, custom widgets). Draft a rule with POST /automations/preview before creating it — it reports which devices the draft would cover and how many readings meet it right now, and writes nothing.

An asset_state trigger on monitorStatus == down is not only an alert: its missedPolls is how down detection is defined for its devices, and a device no such automation covers is never declared down. alertWhenDependencyDown: true also alerts when a device is silenced because its parent is down. Check GET /automations/:id/removal-impact before deleting or disabling one.

GET /automations automationManagement:read

{ rules: [...] }. Each rule is the stored, normalized (v2) body below plus its id, createdAt, updatedAt. An api_call action's custom header values are secrets and come back masked ("••••••••").

curl -H "Authorization: Bearer $POLARIS_TOKEN" \
  "/api/v1/automations"
GET /automations/schema automationManagement:read

The builder vocabulary: the enums every field takes, each metric's dimensions and units, and stateProbes, pathChecks, customWidgets (id → name, for conditions that carry an id) and dimensionPickers. Read it once per session; it changes only when Polaris is updated or a profile, path check or widget is added.

POST /automations automationManagement:write

Create a rule; 201 with { rule }. Body (validated against the same schema the UI uses; 400 names the field):

  • name (required, ≤200), description?, enabled? (default true), severity? — notice | informational | warning | serious | critical (default warning).
  • trigger (required), one of: { type: "asset_metric", metric, operator, threshold, aggregation?, windowSec?, windowPolls?, forPolls?, dimensionFilter? } (a reading such as cpuPct, hwSensorValue, customStateValue, pathOk); { type: "asset_state", field, operator, value, forPolls?, missedPolls?, alertWhenDependencyDown? } (a state such as monitorStatus; the last two only on monitorStatus == down); { type: "host_metric", … } (the Polaris server itself); { type: "event", actionPattern, resourceType?, minLevel?, detailsMatch? } (an audit Event, glob on its action); { type: "change", changeType, dimensionFilter? }; or { type: "composite", kind: "asset" | "host", op: "and" | "or", children, forPolls? } (a tree of metric / state conditions). Operators are > >= < <= == !=. A hold (forPolls) counts readings. A window is windowSec (seconds of samples) or windowPolls (the last N readings; wins when set).
  • scope? — the device filter: { "allAssets": true }, or assetTypes, tags, manufacturers, …, or a condition tree. {} selects no devices except on an event trigger. Only monitored devices alert; POST /automations/preview lists what a scope selects.
  • actions? — up to 20, each one of notify (a delivery channel id from /delivery-channels plus recipients), api_call, script, event, reboot; each may carry its own escalation tiers.
  • reset? — absent means manual (never clears by itself); { "mode": "auto" } clears when the condition stops.
  • resetActions?, repeat?, escalation?, severityBands? (numeric metrics only), bandNotify?, cooldownSec?, messageTemplate?, emailComposition?, groupByAsset? (one alert per device for per-component triggers), requireAckNote?, quietTime? (null = the global schedules apply, { ignoreGlobal: true } = never held, or a policy of its own).

DELETE /automations/:id automationManagement:write

204. Its open alerts are cleared.

GET /automations/:id/removal-impact automationManagement:read

What removing this rule does to down detection: { isDownDetection, governs, wouldFallBackToAnother, wouldBecomePassive, sampleHostnames } — wouldBecomePassive devices are covered by no other down-detection rule and would stop being declared down.

POST /automations/preview automationManagement:write

Dry-run a draft. Accepts a partial draft: { scope } alone lists the devices it selects; { trigger, scope } evaluates current readings. Returns { supported, totalEvaluated, totalAssets?, unmonitoredCount?, meetsCount, matches, carveOut?, … } — meetsCount is how many readings meet the trigger now, and carveOut says which devices a more specific rule already owns. Event and change triggers have no current reading and answer supported: false. Writes nothing.

POST /automations/dimension-values automationManagement:read

{ metric, dimension, scope, narrow? } → the values the draft's devices actually report for one condition dimension (sensor classes, interface names, state probe rows…), so a filter names a value that exists. Companion: POST /automations/poll-cadence { metric?, scope } → how often those devices take the reading, to turn a hold in polls into seconds.

GET /automations/scope-options automationManagement:read

The values a scope filter can name: manufacturers and models in the inventory, IPAM networks. GET /automations/recipient-users lists the users a notify action can address.

POST /automations/test-delivery (send one action of a draft for real, to the caller only) needs a signed-in user and answers 401 to a bearer token — there is no user to deliver it to.

MIB Database

The SNMP MIB modules Polaris resolves symbol names against. Polaris bundles the IETF / IEEE standard MIBs (SNMPv2-MIB, IF-MIB, HOST-RESOURCES-MIB, ENTITY-MIB, ENTITY-SENSOR-MIB, LLDP-MIB, POWER-ETHERNET-MIB, BRIDGE-MIB, Q-BRIDGE-MIB, RSTP-MIB, IP-MIB) and no vendor's: a vendor's objects resolve only from the module you upload, under that vendor's manufacturer name. Endpoints gate on mibDatabase.

GET /server-settings/mibs mibDatabase:read

Uploaded modules: [{ id, filename, moduleName, manufacturer, model, imports, size, notes, uploadedBy, uploadedAt }]. Filters: scope=all|device|generic, manufacturer, model (case-insensitive exact). manufacturer: null is a generic module, resolved for every device.

curl -H "Authorization: Bearer $POLARIS_TOKEN" \
  "/api/v1/server-settings/mibs?manufacturer=APC"
POST /server-settings/mibs mibDatabase:write

Upload one module as multipart/form-data: file (the MIB text, ≤ 6 MiB — 413 beyond), optional manufacturer, model (needs a manufacturer) and notes. The text must parse as an SMI module (<NAME> DEFINITIONS ::= BEGIN … END); binaries are refused. (manufacturer, model, moduleName) is unique — 409 on a second copy. 201 with the stored row plus symbolCount, unresolvedCount and unresolvedRoots: [{ symbol, module }]: a non-empty list names the module still missing (a vendor leaf module usually IMPORTs a core module — upload both, the core one first).

curl -X POST -H "Authorization: Bearer $POLARIS_TOKEN" \
  -F "file=@FORTINET-CORE-MIB.mib" -F "manufacturer=Fortinet" \
  "/api/v1/server-settings/mibs"
GET /server-settings/mibs/:id/structure mibDatabase:read

The module parsed: symbols: [{ name, parentName, fullOid, kind, syntax, baseType, enumValues, access, status, description, isTableRow, indexNames }] and tables: [{ name, rowSymbol, columns, indexNames }], each symbol's fullOid resolved (or null), plus unresolvedCount and unresolvedRootDetails naming what to upload. This is the endpoint to read when choosing which symbol a profile row should walk. GET /server-settings/mibs/:id returns the row with its contents; /:id/download the raw file.

POST /server-settings/mibs/:id/walk mibDatabase:read

Walk one object of this module on a device: { assetId, credentialId, objectName, maxRows? } (maxRows ≤ 5000, default 500; the credential is an SNMP one). Returns the values decoded against the module — enum labels such as onLine(2), and a table grouped into rows when the object is a table. Use it to confirm a symbol answers before putting it in a profile.

GET /server-settings/mibs/std mibDatabase:read

The bundled standard modules by key (std:system, std:interfaces, std:host-resources, std:entity-sensor, …). /std/:key/structure and POST /std/:key/walk work like the uploaded-module pair. GET /server-settings/mibs/facets lists the manufacturers and models in the inventory with device counts — the names to upload under.

DELETE /server-settings/mibs/:id mibDatabase:write

204. Profile rows that resolved through it read unresolved until it is uploaded again.

Manufacturer profiles

A manufacturer profile says which MIB symbol carries each SNMP telemetry metric for one vendor: model identity, CPU, memory, hardware sensors and storage (the interfaces, lldp and wirelessStations rows are descriptive and change nothing), with device-type defaults and per-model exceptions under each, plus custom widgets and state probes. A profile governs the devices whose manufacturer is its name (after aliases), and — only when no profile carries a device's own name — those its matchPattern ("also applies when") matches. Its symbols resolve from MIBs uploaded under its name. Endpoints gate on manufacturerProfiles; patterns are RE2 (no look-around or back-references), case-insensitive, ≤ 512 characters. Every write writes an Event, and the row-level writes return warnings: [] naming any symbol that does not resolve — a warning, never a refusal.

GET /server-settings/manufacturer-profiles manufacturerProfiles:read

{ profiles, transforms, combiners, metricTransforms }. Each profile summary carries id, manufacturer, metricCount, overrideCount, widgetCount and its readiness: ready (every symbol resolves), partial, unresolvedCount, unresolvedSymbols. GET …/suggestions lists the manufacturer names already in use (with device counts) and not yet profiled — create profiles under one of these, or the profile matches no device.

curl -H "Authorization: Bearer $POLARIS_TOKEN" \
  "/api/v1/server-settings/manufacturer-profiles"
GET /server-settings/manufacturer-profiles/:id manufacturerProfiles:read

{ profile }: manufacturer, matchPattern, metrics (eight rows, each with its overrides) and widgets. Every configured row carries readiness: { a, b, columns? } — per symbol, resolved, the module and layer it resolved from, or a hint naming what to upload.

POST /server-settings/manufacturer-profiles manufacturerProfiles:write

{ manufacturer } → 201 with the new profile and its eight empty metric rows. 409 when the (alias-normalized) name already has one. PUT /:id { matchPattern } sets or (null) clears "also applies when", tested against "<manufacturer> <os> <pinned MIB module>".

PUT /server-settings/manufacturer-profiles/:id/metrics/:metricKey manufacturerProfiles:write

Set a metric row (metricKey: model | cpu | memory | temperature | interfaces | storage | lldp | wirelessStations; temperature is the Hardware Sensors row). Fields, all optional on a partial update:

  • defaultSymbol, defaultSymbolB, defaultType — scalar (a GET of .0), double_scalar (two symbols, defaultSymbolB required) or table.
  • defaultTransform — on double_scalar a combiner naming what the pair is (a_over_b_as_percent = used / total, a_over_a_plus_b_as_percent = used / free, …); on a scalar temperature row only tenths_to_units; none on a table.
  • defaultAggregate — none | avg | sum: walk a column and average or sum its rows (CPU tables, memory pools).
  • defaultLabel — the storage mount path or the single sensor's name.
  • defaultParsePattern / defaultParseTemplate — model row only: a regex with a capture group and a $1 template that turn the raw value into the device model. The model is adopted only while the device's model is empty.
  • defaultSensorColumns — temperature rows of type table only, where defaultSymbol is the sensor table's value column: { nameSymbol, alarmSymbol, alarmMap, sensorClass, transform } (alarmMap a state mapping such as { "mode": "nonzero" }, the default; sensorClass fixes every row's class; transform only tenths_to_units). Cleared on a row that is not a table, refused on any other metric.
  • defaultMibId (an uploaded module) or defaultMibStdKey (a bundled one) — which module the row's symbols come from, used to explain an unresolved symbol. Not both.

All three symbol fields cleared returns the row to "no opinion": the standard MIBs answer for that metric. { metric, warnings }.

curl -X PUT -H "Authorization: Bearer $POLARIS_TOKEN" -H "Content-Type: application/json" \
  -d '{"defaultType":"table","defaultSymbol":"fgHwSensorEntValue",
       "defaultSensorColumns":{"nameSymbol":"fgHwSensorEntName","alarmSymbol":"fgHwSensorEntAlarmStatus"}}' \
  "/api/v1/server-settings/manufacturer-profiles/$PROFILE_ID/metrics/temperature"
POST /server-settings/manufacturer-profiles/:id/metrics/:metricKey/overrides manufacturerProfiles:write

Add a scoped row under a metric: the same fields without the default prefix (symbol required), plus its scope — assetType (a device type), modelPattern, or both, never neither — and order. A device type with no pattern is that type's default; one per type per metric (409 for a second). For each metric the most specific row wins: type + model, then model, then the type's default, then the metric row. A model-pattern row with no type also settles the device's family for every metric of the profile, so give a family a row on every metric it needs. 201 with { override, warnings }. PUT and DELETE …/overrides/:overrideId edit and remove one.

POST /server-settings/manufacturer-profiles/:id/widgets manufacturerProfiles:write

Add a custom widget: name, widgetType (gauge | line | table | state | http), symbol and mibId (an uploaded module; both omitted on http), type (scalar | table), transform?, displayOptions? (min, max, unit, warningAt, warningWhen: "below"), modelPattern?. A state widget (a state probe, alertable per row through the customStateValue metric) needs stateMap: { mode, values?, trueLabel?, falseLabel?, trueIsProblem? } (nonzero | zero | equals | notEquals | gte | lte) and takes labelSymbol?, the sibling column naming each row. An http widget takes httpCheck: { useHttps?, port?, path?, expectStatus?, expectBody?, matchMode?, verifyTls?, … } and credentialId? (an http credential). A new widget polls no device until it is switched on for it (below). PUT and DELETE …/widgets/:widgetId edit and remove one; an edit keeps the widget's id, so automations on a state probe keep working.

PUT /server-settings/manufacturer-profiles/:id/widgets/:widgetId/assets manufacturerProfiles:write + assets:write

{ enable?: [assetId], disable?: [assetId] } (≤ 5000 each) — switch the widget on or off per device. Switching on a device the widget does not apply to is a 400; off always succeeds. → { enabled, disabled } (rows changed). GET the same path (manufacturerProfiles:read + assets:read) lists the devices it applies to, each with enabled.

GET /server-settings/manufacturer-profiles/:id/export manufacturerProfiles:read

The whole profile as a portable file, { format: "polaris.manufacturer-profile", version: 1, manufacturer, matchPattern, mibs, metrics, widgets, layout } — MIBs as { moduleName, manufacturer, model }, a widget's credential as { name }, no ids, no secrets, no per-device switches, no MIB text. GET …/:id/code is the same with each override's and widget's id, and PUT …/:id/code { file } makes the profile match it — a full replace: rows left out are cleared or deleted. Returns { changes }.

POST /server-settings/manufacturer-profiles/import/preview manufacturerProfiles:write

{ file } → { manufacturer, targetProfileId, items, mibs }: every importable item (id, kind, label, action: "create" | "replace", missingMibs, missingCredential, blocked) and each MIB the file names with present. Writes nothing. Then POST …/import { file, items: [id] } imports only the chosen items into the profile for that manufacturer (created when there is none) and returns { profileId, results: [{ id, ok, error? }] } — one failure never stops the rest. Upload the MIBs it reports missing first: a widget whose MIB is missing is blocked, a metric row imports but reads unresolved.

DELETE /server-settings/manufacturer-profiles/:id manufacturerProfiles:write

204. Its devices fall back to the standard MIBs for every metric.

GET /manufacturer-aliases manufacturerProfiles:read

The alias map that folds vendor spellings into one name before any profile is looked up ([{ id, alias, canonical }]). POST { alias, canonical }, PUT and DELETE /:id at manufacturerProfiles:write; a change rewrites the manufacturer on existing devices and MIBs.

Events (audit tail)

The audit log — the natural SIEM pull companion to the quarantine push. Retention is 7 days by default (older rows are pruned; syslog/SFTP archival is the long-term store).

GET /events events:read

{ events, total, limit, offset } (default limit 50, max 200).

  • level, resourceType — comma-separated multi-value (levels: info, warning, error; resource types enumerable via GET /events/resource-types).
  • action, resourceName, actor, message, device text filters, each with an optional <field>Op (contains default, not_contains, empty, is_not_empty).
  • resourceId exact match; since / until timestamps (floored by the retention window).
  • assetId — every event about one asset, whatever it is filed under: the asset's own resourceType=asset rows plus its alerts' notification.* rows (fired, escalated, cleared). Every returned event carries an assetId field (null when it is about no single asset) and an assetName — that asset's current hostname, else its IP, null when the asset no longer exists. device filters on that name (hostname or IP); its empty / is_not_empty mean about no asset / about one.
  • sortBy ∈ timestamp, level, action, resourceType, resourceName, actor, message + sortDir; default newest first. Sorting by level orders by severity, not alphabetically.
curl -H "Authorization: Bearer $POLARIS_TOKEN" \
  "/api/v1/events?level=warning,error&since=2026-09-01T00:00:00Z&limit=200"

To tail incrementally, page with offset inside a since window, or track the newest timestamp you have seen and pass it as the next poll's since.

Served to private networks only — access is configured in Server Settings → API Tokens → API Documentation Access.
